# exec-report — 기술 문서를 보고용 문서로 옮기기

`docs/` 본문은 소스 경로와 라인 번호가 촘촘히 박힌 **검증용 문서**다. 그대로는 비전문가가 읽지 못한다. 이 스킬은 같은 내용을 **읽는 사람이 판단할 수 있는 형태**로 옮기는 절차다.

산출물은 `docs/report/<번호>-<제목>-보고.md` 이고, 목차는 `docs/00-목차.md` 의 "보고용 문서" 절이 관리한다.

## 이 스킬이 지키는 것

1. **원본을 요약하지 않는다. 번역한다.** 분량을 줄이는 게 목적이 아니라 *용어와 근거 제시 방식*을 바꾸는 것이다. 근거(코드)는 오히려 늘어난다.
2. **모든 기능 설명에는 실제 코드와 GitHub 링크가 붙는다.** "그렇다더라"가 아니라 "여기 있습니다"여야 보고가 성립한다.
3. **확인하지 못한 것을 반드시 별도 절로 적는다.** 보고서의 신뢰는 여기서 나온다. 특히 "어느 쪽이 빠른가"를 재지 않았으면 반드시 명시한다.
4. **정정 이력을 숨기지 않는다.** 틀렸다가 고친 항목은 경위를 짧게 남긴다.
5. **결론을 과장하지 않는다.** 측정하지 않은 것에서 우열을 말하지 않는다.

---

## 절차

### 1단계 — 원본과 계획서를 대조해 빠진 항목부터 찾는다

**보고서를 쓰기 전에 원본 기술 문서를 먼저 보강한다.** `plan/01-비교항목-정리.md` 의 해당 축 "확인할 질문" 목록과 원본 문서를 한 줄씩 대조한다.

> 실제 사례: `A-2-01` 을 보고서로 옮기려다 `plan/01` 의 A-2 질문이 "탐색 공간, 컷오프, **힌트**"인데 **힌트가 통째로 빠져 있는 것**을 발견했다. 보고서에서 가장 실무적인 항목("문제 쿼리 한 건만 급히 손볼 수 있는가")이 여기서 나왔다.

빠진 항목을 찾으면 **원본 문서에 먼저 반영**하고, 그다음 보고서를 쓴다. 보고서에만 있고 원본에 없는 내용을 만들지 않는다.

### 2단계 — 인용할 코드를 확정하고 실재를 확인한다

기능 하나당 코드 발췌 하나가 원칙이다. **5~15줄**이 읽기 좋다.

```bash
# 인용할 파일이 실제로 그 경로에 있는지 (버전 간 이동이 잦다)
test -f works/trino/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java && echo OK

# 라인 번호 확정
grep -n "maxReorderedJoins" works/trino/.../OptimizerConfig.java
```

**부정 주장("~기능이 없다")은 반드시 검색으로 확인한다.** 이 프로젝트에서 실제로 틀린 적이 있다 — "Trino에는 통계 없음 분기가 없다"고 썼는데 있었고, 동작이 다를 뿐이었다.

```bash
# 예: "Trino SQL 에는 힌트 문법이 없다" 를 주장하기 전에
grep -oin "hint" works/trino/core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4
# → hInt 2건이 나오지만 MonthInterval 의 부분 문자열이었다. 이런 확인 없이 쓰면 사고가 난다
```

### 3단계 — GitHub 영구 링크를 만든다

브랜치가 아니라 **비교 기준 태그**를 쓴다. 태그는 `scripts/testenv/versions.env` 의 `WORKS_*_REF` 와 반드시 같아야 한다.

```
https://github.com/trinodb/trino/blob/483/<works/trino 이후 경로>#L<시작>-L<끝>
https://github.com/StarRocks/starrocks/blob/4.0.14/<works/starrocks 이후 경로>#L<시작>-L<끝>
```

### 4단계 — 코드 기준값을 읽는 사람의 단위로 환산한다

**코드의 숫자를 그대로 옮기면 안 된다.** 읽는 사람이 쓰는 단위로 바꾸고, 원래 값과 다르면 그 이유를 적는다.

> 실제 사례: StarRocks 는 같은 파일 안에서 `4`·`50` 은 **조인 연산 개수**, `10`·`16` 은 **테이블 개수**로 쓴다. 초안에서 이를 뭉뚱그렸다가 단계 구간이 세 줄 틀렸다. 전부 테이블 개수로 환산하고 주의 문구를 달아 해결했다.

환산했으면 **환산했다는 사실 자체를 문서에 밝힌다.** 코드를 직접 열어본 사람이 숫자가 다른 이유를 알 수 있어야 한다.

### 5단계 — 코드 블록마다 "읽는 법"을 붙인다

코드만 있으면 비전문가에게는 장식이다. 블록 아래에 **▸ 읽는 법** 한 문단을 붙여, *이 코드의 어느 부분이 무엇을 뜻하는지* 짚는다. 변수명 하나를 지목하는 방식이 효과가 좋다.

개발진이 소스에 남긴 주석 중 **판단 근거가 담긴 것**은 그대로 인용할 가치가 있다.

> 예: `// 10 table join reorder takes more than 100ms` → 기본값을 10으로 잡은 실측 근거다. 설계 의도를 보여주는 자료로 보고에서 힘을 갖는다.

### 6단계 — 발췌 정확성을 스크립트로 대조한다

보고 자리에서 "이 코드가 원문 그대로냐"는 질문이 나온다. 눈으로 확인하지 말고 대조한다.

```bash
python3 .claude/skills/exec-report/scripts/verify-code-blocks.py docs/report/01-조인-순서-결정-보고.md
```

링크의 라인 범위와 바로 뒤 코드 블록을 `works/` 클론과 문자 단위로 비교한다.

- **가독성을 위해 줄인 발췌는 불일치로 잡힌다. 정상이다.** 대신 그 블록에 *무엇을 줄였는지* 반드시 표기한다 — `*(발췌입니다. 로그 출력 줄은 생략했습니다.)*`
- 표기 없는 불일치는 **고쳐야 할 오류**다

### 7단계 — 목차 갱신과 커밋

`docs/00-목차.md` 의 "보고용 문서" 표에서 해당 행의 상태를 갱신한다. 커밋 메시지에는 **무엇을 검증했고 무엇을 줄였는지**를 적는다.

## 보고서 뼈대

`references/template.md` 에 있다. 절 구성은 다음과 같다.

| 절 | 내용 | 비고 |
|---|---|---|
| 한 장 요약 | 비교표 + 한 문장 결론 | 이것만 읽어도 되게 |
| 1. 왜 이걸 봤나 | 이 항목이 실무에서 왜 중요한지 | 기술 배경 아님 |
| 2~3. 각 제품의 방식 | 설명 → **코드** → 읽는 법 | 제품당 3~5개 기능 |
| 4. 실제로 돌려서 확인한 것 | 실측 결과, 정정 이력 | 없으면 "안 했다"고 명시 |
| 5. 실무에서 의미 있는 차이 | 운영자 관점 2~3가지 | 보고의 알맹이 |
| 6. 확인하지 못한 것 | 항목 / 이유 / 필요한 것 | **생략 금지** |
| 7. 참고 | 원본 문서, 실험 기록, 소스 링크 | |

## 사용법 예시

### 예시 1 — 기술 문서 한 건을 보고서로 옮긴다

```
docs/A-2-02-조인-분배-방식.md 를 상사 보고용으로 만들어줘
```

진행 순서:
1. `plan/01` A-2 질문과 대조해 원본에 빠진 항목이 있는지 확인 → 있으면 원본부터 보강
2. 기능 3~5개를 골라 코드 인용 지점 확정 (`grep -n` 으로 라인 번호)
3. `docs/report/02-조인-분배-방식-보고.md` 작성
4. `verify-code-blocks.py` 로 대조
5. `docs/00-목차.md` 상태 갱신 후 커밋

### 예시 2 — 이미 쓴 보고서에 코드를 추가한다

```
보고서에 기능 설명마다 실제 코드도 넣어줘
```

링크만 있고 코드가 없는 상태에서 출발한다. 3단계(링크)는 이미 되어 있으므로 **2 → 5 → 6단계**만 수행한다. 발췌 후 반드시 6단계로 대조한다.

### 예시 3 — 여러 문서를 묶어 종합 보고한다

```
A-2 문서 3건을 하나의 보고서로 합쳐줘
```

축 단위 종합은 문서별 "실무에서 의미 있는 차이" 를 모아 **결정 기준표**로 재구성한다. 코드 발췌는 축당 3~4개로 줄이고 나머지는 링크만 남긴다. "확인하지 못한 것"은 **합집합**으로 적는다 — 한 문서에서 못 한 것이 다른 문서에서 해결됐다면 그렇게 밝힌다.

### 예시 4 — 실측 없이 코드만으로 쓴다

```
아직 테스트 환경 없이 코드만 봤는데 보고서 쓸 수 있어?
```

가능하다. 단 4절을 **"실제로 돌려서 확인한 것 — 없음"** 으로 두고, 6절에 *"동작 검증을 하지 않았으므로 코드 독해가 틀렸을 가능성이 있다"* 를 명시한다. 이 프로젝트에서 **실측이 코드 독해를 두 번 뒤집었다**. 검증 없는 보고서는 그 사실을 함께 알려야 한다.

## 흔한 실패 (이 프로젝트에서 실제로 겪은 것)

| 실패 | 어떻게 드러났나 | 예방 |
|---|---|---|
| 부정 주장을 확인 없이 씀 | "Trino에 통계 없음 분기가 없다" → 실제로는 있었고 동작만 달랐다 | 2단계의 grep 확인 |
| 코드 기준값을 그대로 옮김 | 단위가 섞여 있어 단계 구간이 3줄 틀림 | 4단계 환산 |
| 코드 독해만으로 원인을 단정 | "임계값 때문에 플랜이 다르다" → 실제 원인은 통계 부족이었다 | 실측 후 작성, 정정 이력 보존 |
| 발췌를 원문처럼 제시 | — | 6단계 대조 + 생략 표기 |
