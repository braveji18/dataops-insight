## 1. 비교 관점

푸시다운은 "연산을 데이터에 가깝게 내린다"는 한 문장으로 요약되지만, 실제로는 성격이 다른 두 개의 문제다.

1. **플랜 내부의 이동** — 술어를 조인 아래로, 집계를 조인 아래로, LIMIT 을 UNION 아래로. 엔진이 자기 플랜 트리 안에서 노드를 옮기는 일이다
2. **엔진 경계를 넘는 이동** — 술어를 스캔에, 나아가 파일 리더나 원격 SQL 소스에 넘기는 일. 여기서는 **"저쪽이 정말 해 줄 수 있는가"** 를 누군가 판단해야 한다

첫 번째에서는 두 엔진이 거의 같은 곳에 도달한다. 갈리는 것은 두 번째, 그리고 **집계를 조인 아래로 내릴지 말지의 임계값**이다.

결론부터: **범위는 대등하다. 다른 것은 (가) 규칙을 어디에 묶어 두는가, (나) 엔진 경계에서 누가 판단하는가, (다) 집계 푸시다운의 감소비 임계값 — 이 셋이고, (다)는 같은 통계에서 실제로 반대 결론을 만든다.**

### 2-1. 위치 — 고정 파이프라인, 같은 최적화기를 일곱 번

### 2-5. 집계를 조인 아래로 — 부분집계만, NDV 2배 게이트

`iterative/rule/PushPartialAggregationThroughJoin.java`.

적용 대상은 **부분(PARTIAL) 집계 하나짜리 group-by** 로 제한된다 — `:65-72`:

```java
return aggregationNode.getStep() == PARTIAL && aggregationNode.getGroupingSetCount() == 1;
```

내릴지 말지는 `skipPartialAggregationPushdown` (`:201-246`)이 정한다. 조건 셋 중 하나라도 걸리면 포기한다.

| 라인 | 조건 | 뜻 |
|---|---|---|
| `:217` | `joinRowCount > 1.1 * sourceRowCount` | 조인이 행을 불리면(팽창 조인) 내리지 않는다 |
| `:229` | 원래 group-by 키 수 < 내려갈 group-by 키 수 | 키가 늘어나면 이득이 없다 |
| `:241` | `isNaN(ndv) \|\| ndv * 2 > sourceRowCount` | **감소비 2배 미만이면 내리지 않는다.** 통계가 없어도 내리지 않는다 |

기본값은 **켜짐** — `sql/planner/OptimizerConfig.java:78` `pushPartialAggregationThroughJoin = true`.

이 규칙이 도는 자리는 `PlanOptimizers.java:1009-1021`, **`AddExchanges`/`AddLocalExchanges` 이후**다. 즉 교환 노드가 다 박힌 뒤에 부분집계만 살짝 내린다. 새 셔플을 만들지 않는다.

이렇게 과감할 수 있는 이유가 하나 더 있다. 부분집계는 **런타임에 스스로 꺼진다** — `OptimizerConfig.java:97-98`:

```java
private boolean adaptivePartialAggregationEnabled = true;
private double adaptivePartialAggregationUniqueRowsRatioThreshold = 0.8;
```

입력의 80% 이상이 유니크하면 집계를 포기하고 그냥 흘려보낸다. 플랜에서 잘못 내려도 손해가 제한된다.

### 3-3. 조인 술어는 여기도 덩어리다

규칙 개수만 보면 "StarRocks 는 잘게 쪼갰다"고 읽기 쉽지만, **조인 부분은 아니다.**

### 3-4. 스캔으로의 술어 — 협상 없이 흡수

`rule/transformation/PushDownPredicateScanRule.java`. 대상 스캔 타입을 `SUPPORT` 집합에 **17종** 열거한다(`:44-61`) — OLAP, Hive, Iceberg, Hudi, Delta, Paimon, Kudu, ES, Schema, Binlog …

```java
private static boolean isSupportedMinMaxConjuncts(LogicalScanOperator scanOperator, ScalarOperator operator) {
```

이 화이트리스트가 `EXPLAIN` 의 `MIN/MAX PREDICATES` 줄이 된다. **어떤 술어가 프루닝에 쓰이는지를 엔진이 하드코딩으로 정한다** — 커넥터가 자기 능력을 신고하는 경로가 없다.

### 3-5. 원격 SQL 소스만 잔여를 분리한다

예외가 하나 있다. `PushDownPredicateToExternalTableScanRule.java` 는 **MySQL / JDBC / ODPS 스캔에 한해** 술어를 둘로 나눈다. 클래스 주석이 이유를 밝힌다(`:44-45`):

```java
// Because the external table may not support the functions in StarRocks,
// to be on the safe side, we only push down partial predicates to the external table
```

무엇을 보낼 수 있는지는 `rewrite/ExternalTablePredicateExtractor.java:142-186` 의 방문자가 정한다. 통과 목록은 **상수 / 컬럼 참조 / BETWEEN / 이항 비교 / AND·OR / IN / IS NULL / (일부) CAST** 뿐이고, 그 밖은 전부 `visit()` 의 `return false` 로 떨어진다.

### 3-6. 집계를 조인 아래로 — 별도 트리 재작성, 통계 사다리

StarRocks 의 집계 푸시다운은 규칙 집합이 아니라 **독립된 트리 재작성 단계**다. `QueryOptimizer.java:689` 가 `pushDownAggregation()` 을 부르고, 그 안(`:826-878`)에서:

```java
// Reorder joins before applying PushDownAggregateRule to better decide where to push down aggregator.
// For example, do not push down a not very efficient aggregator below a very small broadcast join.
logicalJoinReorder(tree, rootTaskContext);
```

**집계를 내리기 위해 조인 순서를 먼저 정한다.** Trino 가 교환 노드 삽입 이후에 부분집계만 옮기는 것과 위치가 완전히 다르다.

판단은 `rule/tree/pdagg/PushDownAggregateCollector.java` 의 `checkStatistics` (`:487-618`)다.

**모드** (`:79-83`, 세션 변수 `cbo_push_down_aggregate_mode`, 기본 **0**):

| 값 | 뜻 |
|---|---|
| `-1` | 끔 |
| `0` | auto (기본) |
| `1` | 전부 내림 |
| `2` | 중간 카디널리티까지 |
| `3` | 높은 카디널리티까지 |

**group-by 키의 카디널리티 3단 분류** (`:627-645` + `statistics/StatisticsEstimateCoefficient.java:40-42`):

| 등급 | 조건 (NDV × 계수 vs 행 수) | 계수 |
|---|---|---|
| low(0) | `NDV × 1000 ≤ rows` | `LOW_AGGREGATE_EFFECT_COEFFICIENT = 1000` |
| medium(1) | `NDV × 100 ≤ rows < NDV × 1000` | `MEDIUM_AGGREGATE_EFFECT_COEFFICIENT = 100` |
| high(2) | 그 외 **또는 통계 미상** | — |

즉 **감소비 100배 미만이면 무조건 high** 다. 통계가 없어도 high 로 떨어진다(`:630-632`).

그 위에 5단 사다리가 얹힌다(`:573-616`). 요지만:

- high 가 없고 low+medium 이 딱 1개 → 내린다
- high 가 2개 이상, 또는 medium 3개 이상, 또는 high 1 + medium 1 이상 → 내리지 않는다
- high 1개 + low ≤ 2 → **모드 3 이상일 때만** 내린다

`immediateChildOfSmallBroadcastJoin` 인 경우 별도 상한이 붙는다(`:543-551`, NDV 10만 / 조합 NDV 100만).

**내려가는 집계의 모양도 다르다.** Trino 는 부분집계 하나를 넣지만, StarRocks 는 `update serialize` → `EXCHANGE(HASH_PARTITIONED)` → `merge finalize` 로 **완전한 2단계 분산 집계**를 조인 아래에 새로 만든다(4-2 실측).

StarRocks 에도 런타임 회피 장치는 있다 — `streaming_preaggregation_mode` 기본 `auto` (`qe/SessionVariable.java:1436`), BE 가 `be/src/exec/aggregate/aggregate_streaming_node.cpp:115` 의 `should_expand_preagg_hash_tables()` 로 해시 테이블 확장을 포기한다. **이 안전장치 자체는 양쪽에 다 있다.**

### 3-7. 집계 → 메타데이터

`PushDownAggToMetaScanRule` 은 `max/min/count/dict_merge/column_size` 를 메타 스캔으로 내린다. 다만 **`[_META_]` 힌트로 메타 스캔을 명시한 쿼리에만** 걸린다(`:24-26` 주석). 일반 쿼리의 자동 최적화가 아니다.

## 4. 실측

전체 절차·조건은 `docs/evidence/A-2/20260904-pushdown-scope-probes.md`.

### 4-1. 협상의 유무가 플랜에 그대로 보인다

Iceberg 파티션 테이블을 만들어 파티션 컬럼과 비파티션 컬럼에 같은 형태의 술어를 걸었다.

| | 파티션 컬럼 `l_linestatus = 'F'` | 비파티션 컬럼 `l_shipdate > DATE '1998-01-01'` |
|---|---|---|
| Trino 483 | `TableScan[... constraint on [l_linestatus]]` — **필터 노드 없음** | `ScanFilterProject[..., filterPredicate = ...]` |
| StarRocks 4.0.14 | `IcebergScanNode` + `PREDICATES: ...` | `IcebergScanNode` + `PREDICATES: ...` |

Trino 는 커넥터가 `enforced` 로 신고한 술어를 **플랜에서 지웠다.** StarRocks 는 두 경우의 플랜이 같다 — 파티션 프루닝은 하지만(`partitions=1/2`) 술어는 스캔 conjunct 로 남는다.

`EXPLAIN (TYPE IO)` 로 보면 Trino 가 무엇을 받았는지도 보인다.

| 술어 | `constraint.columnConstraints` |
|---|---|
| `l_shipdate > DATE '1998-01-01'` | `l_shipdate` 도메인 기록됨 |
| `l_orderkey % 7 = 0` | `[ ]` |

StarRocks 의 대응물은 `MIN/MAX PREDICATES` 줄이고, 같은 두 술어에서 같은 방향으로 갈렸다.

### 4-2. 같은 통계에서 집계 푸시다운 결론이 갈린다

두 엔진 모두 `supplier.s_nationkey` 의 NDV 를 **25**, 행 수를 **100** 으로 알고 있다(Trino `SHOW STATS`, StarRocks `EXPLAIN COSTS` 로 각각 확인).

| 쿼리 | 내려갈 group-by 키 | 감소비 | Trino | StarRocks(기본) |
|---|---|---|---|---|
| `supplier ⋈ nation` | `s_nationkey` (NDV 25 / 100행) | **4배** | ✅ 조인 아래 | ❌ |
| `lineitem ⋈ supplier` | `l_suppkey` (NDV 100 / 60175행) | **602배** | ✅ 조인 아래 | ✅ |

2-5와 3-6의 임계값이 그대로 나온다. Trino 는 `ndv * 2 > sourceRowCount` — 2배면 통과. StarRocks 는 100배가 안 되면 high 등급이고, 기본 모드(auto)에서 high 1개는 내리지 않는다.

`SET cbo_push_down_aggregate_mode = 1` 로 강제하면 StarRocks 도 첫 쿼리에서 조인 아래로 내린다. **게이트가 막은 것이 아니라 임계값이 막은 것**이다.

두 번째 쿼리에서 실제로 만들어진 모양:

```
StarRocks                                Trino
6:HASH JOIN                              InnerJoin
|----5:AGGREGATE (merge finalize)        ├─ Aggregate[type = PARTIAL, keys = [l_suppkey]]
|    4:EXCHANGE (HASH_PARTITIONED)       │  └─ ScanFilter[lineitem]
3:AGGREGATE (update serialize) STREAMING └─ ...
2:IcebergScanNode (lineitem)
```

StarRocks 는 **셔플을 하나 더 만들었고**, Trino 는 스캔 바로 위에 부분집계 하나만 얹었다.

### 4-3. 나머지는 동등하다

| probe | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 조인 등가 전이 추론 (`l_orderkey < 100` → `o_orderkey < 100`) | ✅ | ✅ |
| outer join → inner 단순화 | ✅ | ✅ |
| GROUP BY 아래로 술어 | ✅ | ✅ |
| 단순 LIMIT → 스캔 | ✅ | ✅ |
| ORDER BY + LIMIT → TopN (스캔에는 limit 없음) | ✅ | ✅ |
| LEFT JOIN + LIMIT → 보존측에만 | ✅ | ✅ |

마지막 항목에서는 양쪽 다 `LEFT JOIN` 을 `RIGHT OUTER JOIN` 으로 뒤집고 보존측 스캔에만 limit 을 달았다. **플랜이 사실상 동형이다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino | StarRocks |
|---|---|---|
| 술어 푸시다운 단위 | 방문자 1개(1,576줄, `visit*` 18개) | 규칙 18개 집합 — 단, 조인은 `JoinPredicatePushdown` 623줄 |
| 반복 방식 | 파이프라인에 **7번 명시적으로 배치** | 규칙 집합을 **6번 호출**, 각 호출이 고정점까지 |
| `Push*` 규칙 수 | 54 | 40 (+ 트리 재작성 3) |
| 구조체 필드 푸시다운 | 규칙 13개 | 방문자 1개 |
| CTE 아래로 푸시다운 | 대응 규칙 없음 | 전용 규칙 4개 |
| **엔진 경계 판단 주체** | **커넥터** (`applyFilter` 등 8종 SPI) | **엔진** (하드코딩 화이트리스트) |
| 술어 3분할 | enforced / unenforced / unsupported | 없음 — 전부 스캔 conjunct |
| 집계 푸시다운 위치 | 교환 노드 삽입 **이후** | 논리 재작성 중, **조인 순서 결정 이후** |
| 집계 푸시다운 대상 | 부분집계만 | 완전한 2단계 집계(셔플 추가) |
| 집계 푸시다운 임계값 | 감소비 **2배** | 감소비 **100배**(medium) / **1000배**(low) 기준 3등급 + 5단 사다리 |
| 통계 없을 때 | 내리지 않음 | 내리지 않음 (high 등급으로 떨어짐) |

### 5-2. 경계 판단 주체가 다른 이유

Trino 는 **자기가 모르는 데이터 소스**를 상대한다. Kafka, Elasticsearch, PostgreSQL, Iceberg 가 각각 무엇을 평가할 수 있는지 엔진이 알 방법이 없다. 그래서 물어보는 창구(SPI)를 열고, 답을 못 받으면 자기가 한다. `applyFilter` 주석이 이 관계를 명시한다 — *"Connectors should expect this method to be called multiple times during the optimization of a given query"* (`ConnectorMetadata.java:1417-1418`).

StarRocks 는 **자기 BE 를 상대한다.** BE 가 무엇을 평가할 수 있는지 FE 가 안다. 그래서 물어볼 필요가 없고, 술어를 그냥 스캔에 붙인 뒤 BE 가 알아서 하게 둔다. 외부 SQL 소스(JDBC/MySQL)만 예외적으로 잔여를 분리하는데, 그것도 **엔진 안의 고정 화이트리스트**로 판단한다.

이 비대칭은 A-2-02의 게이트 축 차이(바이트 vs 행 수)와 같은 뿌리다. **Trino 는 남의 통계·능력에 의존하고, StarRocks 는 자기 것을 신뢰한다.**

운영 관점의 귀결:

- **Trino** — 커넥터가 `applyFilter` 를 게을리 구현하면 푸시다운이 통째로 사라진다. 대신 잘 구현된 커넥터에서는 술어가 플랜에서 아예 없어져 재평가 비용이 0이 된다
- **StarRocks** — 커넥터 구현 품질과 무관하게 술어는 항상 스캔까지 간다. 대신 **프루닝에 쓸 수 있는 술어의 형태가 엔진에 고정**돼 있어, 새 소스가 더 많은 걸 할 수 있어도 FE 코드를 고치지 않으면 쓸 수 없다

이것은 A-5-01(커넥터 추가 난이도)에서 다시 나올 축이다.

### 5-3. 집계 푸시다운 임계값이 50배 차이 나는 이유

임계값만 놓고 어느 쪽이 옳다고 말할 수 없다. **감당해야 할 위험이 다르기 때문이다.**

- Trino 가 내리는 것은 **부분집계 하나**다. 새 셔플이 없고, 잘못 내려도 런타임에 스스로 꺼진다(2-5). 위험이 작으니 임계값을 낮게 잡을 수 있다
- StarRocks 가 내리는 것은 **셔플을 포함한 완전한 분산 집계**다. 잘못 내리면 없어도 될 셔플이 하나 늘어난다. 위험이 크니 임계값을 높게 잡는다

즉 **임계값 차이는 푸시다운 산출물의 무게 차이에서 따라 나온 것**이지, 한쪽이 보수적이라는 성향 차이가 아니다.

다만 실무적으로는 결과가 남는다. **4-2의 감소비 4배 케이스처럼, 중간 정도로 줄어드는 star schema 조인에서 StarRocks 는 기본 설정으로 집계를 내리지 않는다.** 그런 워크로드가 반복된다면 `cbo_push_down_aggregate_mode` 를 2 또는 3으로 올리는 것이 튜닝 손잡이다.

### 5-4. "규칙 개수"로 비교하면 안 된다

54 vs 40 이라는 숫자는 커버리지 차이가 아니라 **묶는 단위의 차이**다.

- 구조체 필드 푸시다운: Trino 13개 규칙 = StarRocks 1개 방문자
- 조인 술어: Trino 방문자 메서드 1개(`visitJoin`, 280줄) ≈ StarRocks 규칙 2개 + 공용 클래스 623줄
- CTE: Trino 0개 vs StarRocks 4개 — 이건 **실제 기능 차이**(A-2-05)

실측(4-3)에서 술어·LIMIT 계열이 전부 동등하게 나온 것이 이 해석을 뒷받침한다.

### 5-5. 운영자 개입 수단

| | Trino | StarRocks |
|---|---|---|
| 푸시다운 관련 세션 속성 | 10개 (`SystemSessionProperties.java` 기준) | 22개 (`SessionVariable.java` 기준, 런타임 필터 포함) |
| 커넥터 푸시다운 전면 차단 | `allow_pushdown_into_connectors` | 대응물 없음 |
| 표현식 푸시다운 범위 조절 | `complex_expression_pushdown` | `push_down_heavy_exprs`, `enable_lambda_pushdown` |
| 집계 푸시다운 | `push_partial_aggregation_through_join` (on/off) | `cbo_push_down_aggregate_mode` (**5단계**) |
| 조인 술어 푸시다운 | 없음(항상 켜짐) | 없음 — `OptimizerContext.enableJoinPredicatePushDown` 은 내부 플래그이고 다단계 MV 재작성 경로에서만 꺼진다(`QueryOptimizer.java:525-527`) |

**StarRocks 의 손잡이가 더 많고 더 세분돼 있다.** 특히 집계 푸시다운은 on/off 가 아니라 5단계다. 다만 대부분 `INVISIBLE` 플래그가 붙어 `SHOW VARIABLES` 에 나오지 않는다(`SessionVariable.java:1993-2008`) — 소스를 봐야 알 수 있다.

반대로 **커넥터로의 푸시다운을 통째로 끄는 스위치는 Trino 에만 있다.** 커넥터가 푸시다운을 잘못 처리할 때 이 스위치 하나로 문제를 격리할 수 있다는 뜻이고, "남의 구현에 의존한다"는 설계에서 필연적으로 필요한 안전장치다.

## 6. 결론

**범위는 대등하다. 성격이 다르다.**

- **플랜 내부 이동**(술어 전이 추론, outer join 단순화, 집계·LIMIT·TopN 관통)은 실측 6항목이 전부 동등하게 나왔다. **이 축에서 우열은 없다**
- **엔진 경계**에서 갈린다. Trino 는 커넥터에게 물어보고 답에 따라 술어를 **플랜에서 제거**한다. StarRocks 는 묻지 않고 항상 스캔에 붙인다. 이것은 페더레이션 엔진과 자체 스토리지 엔진의 위치 차이에서 나온 필연에 가깝다
- **조인 아래 집계 푸시다운**은 같은 통계에서 반대 결론이 나온다. 임계값이 2배 대 100배로 두 자릿수 차이 나기 때문이고, 그 차이는 각자가 내리는 집계의 무게(부분집계 vs 셔플 포함 완전 집계)와 짝을 이룬다

**튜닝할 때 알아야 할 것**

| 상황 | Trino | StarRocks |
|---|---|---|
| 푸시다운이 안 될 때 첫 확인 | `EXPLAIN (TYPE IO)` 의 `columnConstraints` — 커넥터가 받았는가 | `EXPLAIN` 의 `MIN/MAX PREDICATES` — 프루닝에 쓰이는가 |
| 집계가 조인 아래로 안 내려갈 때 | 통계(NDV) 확인. 감소비 2배가 안 되면 설계상 안 내린다 | `cbo_push_down_aggregate_mode` 를 2~3으로 |
| 커넥터 푸시다운이 오작동할 때 | `allow_pushdown_into_connectors=false` 로 격리 | 대응 스위치 없음 |

### 아직 답하지 않은 것

- **실행 시간** — 전 항목 미측정. 어느 임계값이 실제로 빠른지는 이 랩에서 말할 수 없다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **다중 노드** — worker/BE 1대. 집계 푸시다운은 셔플 비용과 함께 판단되므로 노드 수에 반응할 수 있다. A-2-02·A-2-03과 같은 한정이다
- **JDBC/원격 SQL 푸시다운의 실측** — 3-5의 화이트리스트는 코드로만 확인했다. 현재 랩에 JDBC 카탈로그가 없다
- **커넥터별 푸시다운 능력의 폭** — Trino 50+ 커넥터가 `applyFilter`/`applyAggregation` 을 각각 어디까지 구현하는지는 **A-5-02** 의 주제다. 이 문서는 옵티마이저 쪽 경계까지만 다뤘다
- **StarRocks 네이티브 테이블** — 전부 Iceberg 외부 테이블로만 쟀다. OLAP 스캔의 prefix index / bitmap / zonemap 경로는 C-1-02
- **MV 를 이용한 재작성** — 집계를 "내리는" 것이 아니라 "미리 계산해 둔 것으로 바꾸는" 경로는 **A-2-06**
