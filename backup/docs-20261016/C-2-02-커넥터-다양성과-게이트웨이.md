1. **커넥터 다양성 그 자체** — 개수가 곧 기능인가

## 2. 커넥터 다양성

### 2-1. 목록

`plugin/` 에서 `ConnectorFactory` 를 구현한 것을 셌다 — **27개**다.

```
ai-functions base-jdbc bigquery blackhole cassandra datasketches delta-lake
elasticsearch example-http faker google-sheets hive hudi iceberg jmx kafka
lakehouse loki memory mongodb opensearch pinot prometheus redis redshift
thrift tpcds tpch
```

여기에 **`base-jdbc` 를 상속한 관계형 DB 커넥터 15개**가 더 있다(`A-5-02` 2-2) — clickhouse, druid, duckdb, exasol, ignite, mariadb, mysql, oracle, postgresql, redshift, singlestore, snowflake, sqlserver 등.

문서화된 커넥터는 **39개**다(`docs/src/main/sphinx/connector/*.md`).

StarRocks 는 **10종**이다(`A-5-01` 3-2).

```
ES HIVE ICEBERG JDBC HUDI DELTALAKE PAIMON ODPS KUDU UNIFIED
```

### 2-2. 개수보다 종류가 문제다

**두 목록을 겹쳐 보면 성격이 드러난다.**

| 갈래 | Trino | StarRocks |
|---|---|---|
| 레이크 테이블 포맷 | hive, iceberg, delta-lake, hudi, lakehouse | **HIVE, ICEBERG, DELTALAKE, HUDI, PAIMON** |
| 관계형 DB | **15종**(base-jdbc 계열) | JDBC **1종**(대상 DB 무관 공용) |
| 검색엔진 | elasticsearch, opensearch | ES |
| NoSQL / KV | cassandra, mongodb, redis | KUDU |
| 스트리밍 | **kafka** | 없음(적재는 Routine Load — `C-1-04`) |
| 관측 데이터 | **prometheus, loki, jmx** | 없음 |
| SaaS / 클라우드 | **bigquery, google-sheets, snowflake** | ODPS |
| 벤치마크·테스트 | tpch, tpcds, memory, blackhole, faker | 없음 |
| 특수 | **ai-functions, datasketches** | 없음 |

**StarRocks 는 레이크 포맷이 더 촘촘하다** — Paimon 이 있는데 Trino 에는 없다.

**Trino 는 그 밖의 모든 칸에서 넓다.** 특히 관측 데이터(prometheus/loki)와 SaaS(bigquery/sheets)는 StarRocks 에 대응물이 아예 없다.

### 2-3. 관계형 DB 15종 대 1종

`A-5-02` 에서 확인한 대로 차이가 개수만이 아니다.

- **Trino**: 방언마다 별도 클라이언트가 있고 `supportsTopN`·`implementAggregation`·`convertPredicate` 를 각자 구현한다. **11개 방언이 `supportsTopN` 을 재정의**한다
- **StarRocks**: JDBC 하나로 처리하고 **대상 DB 종류와 무관하게 같은 술어 화이트리스트**를 쓴다(`A-2-04` 3-5)

**즉 "PostgreSQL 을 조인해 쓴다"는 요구에서 두 제품의 격차가 개수 비율(15:1)보다 크다.**

### 2-4. 다양성이 기능인 이유

`plan/01` 이 이 항목을 "커넥터 다양성 자체가 기능"이라고 적은 것은 정확하다. **연합 질의(federation)는 커넥터가 여럿일 때만 성립하는 기능**이기 때문이다.

```sql
-- Trino: 서로 다른 시스템을 한 쿼리에서 조인
SELECT o.*, c.tier
FROM iceberg.sales.orders o
JOIN postgresql.crm.customers c ON o.cust_id = c.id
JOIN elasticsearch.logs.events e ON e.order_id = o.id
```

StarRocks 도 여러 카탈로그를 붙일 수 있으나, **붙일 수 있는 종류가 10개로 닫혀 있어** 이런 조합의 폭이 좁다.

## 3. Trino Gateway

### 3-1. 이 저장소에는 없다

`trino/` 트리에서 Gateway 구현을 찾을 수 없다. 문서에서도 실질적 언급이 없다(HTTP 서버 속성 문서에 스치듯 나올 뿐이다).

**Trino Gateway 는 별도 저장소의 프로젝트**다. 따라서 **이 비교 연구의 소스코드 비교 대상이 아니다.**

### 3-2. 그럼에도 언급하는 이유

`B-4-01` 3-1 에서 확인한 사실 때문이다 — **Trino 코디네이터는 단일 지점**이고, 공식 문서가 *"one coordinator and zero or more workers"* 라고 명시한다.

그 한계를 클러스터 안에서 풀지 않고 **밖에서 푸는 것이 Trino 진영의 답**이다. 클러스터를 여러 개 두고 앞에 라우터를 세운다.

**이 구조는 StarRocks 와 대조된다.** StarRocks 는 FE 를 LEADER/FOLLOWER/OBSERVER 로 이중화해 **클러스터 안에서** 푼다(`B-4-01` 2-1).

| | 제어 평면 이중화 방식 |
|---|---|
| Trino | **클러스터를 여러 개** + 게이트웨이(별도 제품) |
| StarRocks | **FE 를 여러 대** + 자동 선거(내장) |

**Trino 쪽이 무상태 설계와 잘 맞는다.** 워커에 상태가 없고 메타데이터도 갖지 않으니(`B-4-01` 2-2) 클러스터를 통째로 복제하는 것이 자연스럽다. StarRocks 는 메타데이터를 소유하므로 그럴 수 없다.

### 3-3. 검증할 수 없는 항목임을 명시한다

Gateway 의 실제 능력(라우팅 정책, 무중단 배포, 클러스터 간 부하 분산)은 **다른 저장소를 봐야 하고 이 연구의 범위 밖**이다. 여기서는 **"Trino 진영이 이 문제를 클러스터 밖에서 푼다"는 구조적 사실**만 기록한다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 커넥터 수 | **27** (+ JDBC 계열 15) | **10**(열거형) |
| 문서화된 커넥터 | 39 | — |
| 레이크 포맷 | hive/iceberg/delta/hudi/lakehouse | **+ Paimon** |
| 관계형 DB | **15종, 방언별 최적화** | 1종, 공용 화이트리스트 |
| 관측 데이터 | prometheus, loki, jmx | **없음** |
| SaaS | bigquery, google-sheets, snowflake | ODPS |
| 스트리밍 읽기 | kafka | 없음 |
| 제어 평면 이중화 | **클러스터 다중화 + Gateway**(별도 제품) | **FE 다중화 + 자동 선거**(내장) |

### 5-2. 왜 개수가 벌어졌나

`C-2-01` 5-2 의 결론이 그대로 여기 나타난다 — **SPI 가 있으니 코어 팀이 아닌 사람도 만들 수 있었다.**

`loki`(로그 집계), `faker`(테스트 데이터 생성), `ai-functions`, `datasketches` 같은 커넥터는 **코어 로드맵에서 나올 만한 것이 아니다.** 필요한 사람이 만들어 넣은 것이다.

StarRocks 의 10종은 전부 **"분석 대상이 될 만한 데이터 저장소"** 다. 로드맵에서 나온 목록의 모양이다.

### 5-3. 다양성의 대가

`A-5-02` 에서 확인한 것을 다시 적는다 — **커넥터마다 능력이 다르다.** `applyFilter` 는 18개가 구현했지만 `applyAggregation` 은 3개, `applyJoin` 은 1개(JDBC 공용)다.

즉 **"커넥터가 있다"가 "잘 동작한다"를 뜻하지 않는다.** 사용자는 쓰려는 커넥터의 실제 구현 범위를 확인해야 하고, 그 정보는 커넥터 문서에 흩어져 있다.

StarRocks 는 10종에서 동작이 일관된다 — 엔진이 전부 처리하므로(`A-5-02` 3-1) 커넥터에 따라 달라질 여지가 적다.

### 5-4. 이 축이 제품 선택에 미치는 영향

**연합 질의가 요건이면 Trino 외에 선택지가 없다.** 반대로 요건이 아니면 이 축의 격차는 **의미가 없다.**

`A-5-01` 6절에서 내린 결론과 같다 — "붙여야 할 데이터 소스가 다양하고 계속 늘어난다면 Trino, 소스가 고정돼 있고 그 위에서 최대 성능을 뽑아야 한다면 StarRocks."

**이 문서는 그 결론에 숫자를 붙인 것**이고, 새로운 판단을 더하지는 않는다.

## 6. 결론

**비교가 아니라 부재다. 다만 이 축의 무게는 요건에 따라 0 이 될 수도 있다.**

- **커넥터 27(+JDBC 15) 대 10.** 레이크 포맷은 StarRocks 가 오히려 촘촘하고(Paimon), 그 밖의 모든 갈래에서 Trino 가 넓다
- **관계형 DB 는 15:1** 이고, 방언별 푸시다운 최적화까지 감안하면 격차가 개수 비율보다 크다
- **관측 데이터·SaaS·스트리밍 읽기·테스트용 커넥터**는 StarRocks 에 대응물이 없다
- **Trino Gateway 는 별도 저장소**라 이 연구에서 검증할 수 없다. 기록하는 것은 **"제어 평면 이중화를 클러스터 밖에서 푼다"는 구조적 사실**뿐이다

**실무 결론**

1. **연합 질의(서로 다른 시스템을 한 쿼리에서 조인)가 요건이면 Trino 가 유일한 선택이다**
2. **요건이 아니면 이 축은 무시해도 된다.** Iceberg 만 본다면 커넥터 27개는 아무 이득이 없다
3. **관계형 DB 를 자주 조인한다면 격차가 특히 크다.** StarRocks 는 방언별 최적화가 없다(`A-2-04` 3-5)
4. **Paimon 을 쓴다면 StarRocks 가 유일한 선택이다** — Trino 483 에 Paimon 커넥터가 없다
5. **커넥터의 존재를 능력으로 읽지 말 것.** 푸시다운 구현 범위를 확인해야 한다(`A-5-02` 2-2)

### 아직 답하지 않은 것

- **실측 전무.** 랩에 카탈로그가 하나뿐이라 연합 질의를 시험할 수 없다. 이 축을 검증하려면 랩에 PostgreSQL·Elasticsearch 등을 추가해야 한다
- **Trino Gateway** — 별도 저장소라 소스를 보지 않았다. 라우팅 정책·무중단 배포 능력은 확인 불가
- **커넥터별 성숙도** — 27개 중 어느 것이 운영에 쓸 만한지 판단할 근거가 없다
- **StarRocks 의 `UNIFIED` 커넥터** — 여러 포맷을 묶는 커넥터인데 구조를 확인하지 않았다(`A-5-01` 에서도 남긴 항목)
- **연합 질의의 성능** — 서로 다른 시스템을 조인할 때 어느 쪽이 얼마나 밀어내는지는 `A-5-02` 의 코드 조사까지만 했다
