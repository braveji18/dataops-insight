# [보고] Trino vs StarRocks 비교 (6) — 미리 계산해둔 결과를 자동으로 활용하는가

> 상세 기술 문서: `docs/A-2-06-MV-쿼리-재작성.md`
>
> 이 보고서의 모든 코드는 위 두 버전의 **실제 소스에서 그대로 발췌**한 것이며,
> 각 제목의 링크로 GitHub에서 원문을 바로 확인하실 수 있습니다.

## 한 장 요약

무거운 집계를 **미리 계산해 저장해두는 기능**(머티리얼라이즈드 뷰, 이하 "미리계산표")은 두 제품 모두 갖고 있습니다. 그런데 결정적인 차이가 하나 있습니다 — **사용자가 원본 테이블을 대상으로 쓴 조회를, 엔진이 알아서 미리계산표로 바꿔주는가**입니다.

| | Trino | StarRocks |
|---|---|---|
| 미리계산표 만들기·갱신 | 가능 (연결 모듈이 지원하는 경우) | 가능 |
| **조회를 자동으로 바꿔주기** | **불가** — 조회문에 이름을 직접 적어야 함 | **가능** |
| 자동 변환 전용 코드 규모 | **0줄** | 약 **18,000줄** |
| 원본이 바뀐 뒤(갱신 전) 기본 동작 | **낡은 결과를 계속 제공** | 미리계산표를 **쓰지 않고** 원본 조회 |
| 미리계산표를 만들 수 있는 연결 모듈 | **3개** | 제품 자체 기능 |

**결론: 이 항목은 이번 비교 전체에서 가장 뚜렷한 기능 격차입니다. StarRocks 우위이며, 그 대신 조회 계획의 예측 가능성을 일부 포기합니다.**

---

## 1. 왜 이걸 봤나

미리계산표는 **인덱스와 같은 성격의 성능 수단**이 되어야 합니다. 관리자가 만들어두면 기존 조회가 알아서 빨라지는 것이 이상적입니다.

자동 변환이 없으면 미리계산표는 **애플리케이션이 알아야 하는 물건**이 됩니다.

- 미리계산표를 새로 만들어도 **조회문을 고쳐야** 이득이 생깁니다
- 미리계산표를 지우면 그것을 참조하던 **조회가 깨집니다**
- BI 도구가 자동으로 만들어내는 조회문에는 **적용할 방법이 없습니다**

반대로 자동 변환이 있으면 편하지만, **같은 조회문이 미리계산표 유무에 따라 다르게 실행**되므로 조회 계획을 예측하기 어려워집니다. 응답 시간을 보장해야 하는 업무에서는 이것이 부담이 됩니다.

## 2. Trino의 방식 — "조회문이 이름을 적었을 때만 동작한다"

### 2-1. 미리계산표는 연결 모듈의 기능이고, 기본은 미지원이다

Trino에서 미리계산표는 엔진 기능이 아니라 **저장소 연결 모듈이 선택적으로 제공하는 기능**입니다.

**[ConnectorMetadata.java#L1700-L1709](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/connector/ConnectorMetadata.java#L1700-L1709)**

```java
    default void createMaterializedView(
            ConnectorSession session,
            SchemaTableName viewName,
            ConnectorMaterializedViewDefinition definition,
            Map<String, Object> properties,
            boolean replace,
            boolean ignoreExisting)
    {
        throw new TrinoException(NOT_SUPPORTED, "This connector does not support creating materialized views");
    }
```

▸ **읽는 법** — `default` 로 선언된 기본 구현이 **곧바로 "지원하지 않음" 오류를 던집니다.** 연결 모듈이 이 부분을 직접 구현해야만 미리계산표를 만들 수 있습니다.

**483 기준으로 실제 구현한 연결 모듈은 3개입니다** — Iceberg, Lakehouse(Iceberg를 포함한 묶음), BigQuery(BigQuery 쪽에 위임). Hive 연결 모듈 단독으로는 지원하지 않습니다.

### 2-2. 조회문이 미리계산표 이름을 적었을 때만 동작한다

**[StatementAnalyzer.java#L2345-L2350](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/analyzer/StatementAnalyzer.java#L2345-L2350)**

```java
            Optional<MaterializedViewDefinition> optionalMaterializedView = metadata.getMaterializedView(session, name);
            if (optionalMaterializedView.isPresent()) {
                MaterializedViewDefinition materializedViewDefinition = optionalMaterializedView.get();
                analysis.addEmptyColumnReferencesForTable(accessControl, session.getIdentity(), name, getBranchName(table));
                if (isMaterializedViewSufficientlyFresh(session, name, materializedViewDefinition)) {
                    // If materialized view is sufficiently fresh with respect to its grace period, answer the query using the storage table
```

*(이어지는 처리 코드는 길어서 진입 조건과 개발진 주석까지만 인용했습니다.)*

▸ **읽는 법** — 첫 줄의 `getMaterializedView(session, **name**)` 에서 `name` 은 **조회문에 적힌 이름**입니다. 즉 이 코드는 **사용자가 미리계산표를 직접 지목했을 때만** 실행됩니다. 원본 테이블을 대상으로 쓴 조회는 이 분기에 들어오지 않습니다.

그리고 이 판단이 **최적화 단계가 아니라 조회문 해석 단계에서** 이뤄진다는 점이 중요합니다. **Trino의 최적화 단계에는 미리계산표 관련 처리가 하나도 없습니다.**

### 2-3. 원본이 바뀌어도 기본값은 "계속 쓴다"

**[StatementAnalyzer.java#L2456-L2459](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/analyzer/StatementAnalyzer.java#L2456-L2459)**

```java
            if (materializedViewDefinition.getGracePeriod().isEmpty()) {
                // Unlimited grace period
                return true;
            }
```

▸ **읽는 법** — `getGracePeriod()`(허용 지연 시간)를 지정하지 않으면 `// Unlimited grace period`(**무제한**)로 보고 `return true` — 즉 **"충분히 신선하다"고 판정**합니다. 미리계산표를 만들 때 허용 지연 시간을 명시하지 않는 것이 기본이므로, **원본이 아무리 바뀌어도 갱신 전까지 옛 결과를 계속 제공합니다.**

4-3에서 실제로 확인했습니다. 상태 조회에는 "낡음(STALE)"으로 표시되는데도 옛 데이터를 읽습니다.

### 2-4. 낡았다고 판정되면 정의를 펼쳐 원본을 읽는다

**[StatementAnalyzer.java#L2359-L2363](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/analyzer/StatementAnalyzer.java#L2359-L2363)**

```java
                else if (shouldFailWhenStale(materializedViewDefinition)) {
                    throw semanticException(VIEW_IS_STALE, table, "Materialized view '%s' is stale", name);
                }
                // This is a stale materialized view and should be expanded like a logical view
                return createScopeForMaterializedView(table, name, scope, materializedViewDefinition, Optional.empty());
```

▸ **읽는 법** — 낡았을 때 두 갈래입니다. **오류를 낼지**(`VIEW_IS_STALE`), 아니면 **미리계산표의 정의를 펼쳐 원본에서 직접 계산할지**. 기본은 후자입니다 — [MaterializedViewDefinition.java#L35](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/metadata/MaterializedViewDefinition.java#L35) 에 기본 동작이 `INLINE`(펼치기)으로 지정돼 있습니다.

```java
    public static final WhenStaleBehavior DEFAULT_WHEN_STALE_BEHAVIOR = INLINE;
```

▸ **읽는 법** — 즉 **결과가 항상 정확합니다.** 다만 2-3의 무제한 허용 지연 때문에 "낡았다"는 판정 자체에 좀처럼 도달하지 않습니다.

## 3. StarRocks의 방식 — "원본 조회를 알아서 바꿔준다"

### 3-1. 자동 변환 전용 코드가 약 18,000줄이다

`머티리얼라이즈드 뷰 자동 변환` 전용 폴더에 파일 35개, 약 **18,000줄**이 들어 있습니다. 본체 파일 하나만 3,000줄이 넘습니다. 설계 근거를 개발진이 밝혀뒀습니다.

**[MaterializedViewRewriter.java#L106-L110](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/transformation/materialization/MaterializedViewRewriter.java#L106-L110)**

```java
 * SPJG materialized view rewriter, based on
 * 《Optimizing Queries Using Materialized Views: A Practical, Scalable Solution》
 *
 *  This rewriter is for single table or multi table join query rewrite
 */
```

▸ **읽는 법** — 학술 논문 한 편을 근거로 구현했다고 밝히고 있습니다. 마지막 줄이 범위입니다 — **한 테이블짜리 조회뿐 아니라 여러 테이블을 잇는 조회도** 변환 대상입니다.

### 3-2. 조회와 미리계산표가 정확히 같지 않아도 활용한다

**[MaterializedViewRewriter.java#L129-L139](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/transformation/materialization/MaterializedViewRewriter.java#L129-L139)**

```java
    public enum MatchMode {
        // all tables and join types match
        COMPLETE,
        // all tables match but join types do not
        PARTIAL,
        // all join types match but query has more tables
        QUERY_DELTA,
        // all join types match but view has more tables
        VIEW_DELTA,
        NOT_MATCH
    }
```

▸ **읽는 법** — 다섯 가지 일치 방식입니다. 주석을 그대로 읽으면 — `COMPLETE`(테이블과 연결 방식이 모두 일치), `PARTIAL`(테이블은 같은데 연결 방식이 다름), **`QUERY_DELTA`(조회 쪽 테이블이 더 많음)**, **`VIEW_DELTA`(미리계산표 쪽 테이블이 더 많음)**.

**뒤의 두 가지가 핵심입니다.** 조회가 미리계산표보다 테이블을 더 쓰더라도, **일치하는 부분만 미리계산표로 갈아끼우고 나머지는 원본에서 읽습니다.** 4-2에서 실제로 확인했습니다.

### 3-3. "미리계산표를 쓰는 방법"과 "안 쓰는 방법"을 비용으로 겨룬다

**[QueryOptimizer.java#L996-L999](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L996-L999)**

```java
        if (mvRewriteStrategy.enableCBOBasedMvRewrite && mvRewriteStrategy.enableMultiTableRewrite) {
            context.getRuleSet().addSingleTableMvRewriteRule();
            context.getRuleSet().addMultiTableMvRewriteRule();
        }
```

▸ **읽는 법** — 이 코드가 있는 곳이 **여러 실행 방법의 비용을 비교하는 단계**입니다. 거기에 미리계산표 활용 규칙을 등록합니다. 즉 **"미리계산표를 쓰는 계획"이 다른 후보들과 함께 비용으로 겨루고, 이기면 채택**됩니다. 무조건 쓰는 것이 아닙니다.

### 3-4. 대신 조회 계획 수립 시간에 상한을 둔다

**[SessionVariable.java#L1791-L1792](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java#L1791-L1792)**

```java
    @VariableMgr.VarAttr(name = OPTIMIZER_MATERIALIZED_VIEW_TIMELIMIT)
    private long optimizerMaterializedViewTimeLimitMillis = 1000;
```

▸ **읽는 법** — 미리계산표 후보를 따져보는 데 쓸 수 있는 시간이 **1초로 제한**돼 있습니다. 이런 상한이 필요하다는 것 자체가 **자동 변환의 비용**을 말해줍니다 — 미리계산표가 많아지면 조회 계획을 세우는 시간이 늘어납니다.

이 밖에 관련 설정이 18개 이상 있고, 이 조회에서 쓸 미리계산표를 **이름으로 한정하는 설정**(`query_including_mv_names` / `query_excluding_mv_names`)도 있습니다. 자동 변환이 오작동할 때 범위를 좁히는 수단입니다.

## 4. 실제로 돌려서 확인한 것

**시험 조건**: Trino 처리 서버 1대 / StarRocks 처리 서버 1대, TPC-H 표준 데이터 최소 규모(약 6만 건), 두 제품이 **같은 데이터 파일**을 봅니다. **양쪽에 정의가 완전히 같은 미리계산표**를 만들고(둘 다 갱신 후 15,000건, 상태 정상) 조회 계획을 비교했습니다. 실행 시간은 재지 않았습니다.

> 시험용으로 만든 미리계산표와 테이블은 **모두 삭제했습니다.**

### 4-1. 미리계산표 이름을 쓰지 않은 조회 — 한쪽만 바뀐다

원본 테이블을 대상으로 쓴 조회를 던졌습니다.

| 엔진 | 무엇을 읽었나 |
|---|---|
| Trino 483 | 원본 테이블 `lineitem` |
| StarRocks 4.0.14 | **미리계산표 `mv_order_sum`** |

설정으로 자동 변환을 끄자 StarRocks도 원본을 읽었습니다 — **원인이 자동 변환임을 확정**했습니다.

### 4-2. 자동 변환의 범위가 넓다

정확히 같은 조회만 바뀌는 것이 아니었습니다.

| 조회 | 미리계산표를 쓰려면 필요한 것 | 결과 |
|---|---|---|
| 미리계산표와 동일한 집계 | 그대로 일치 | ✅ 미리계산표 사용 |
| 조건이 추가된 집계 | 조건을 미리계산표에 적용 + 합계 재집계 | ✅ 미리계산표 사용 |
| 전체 건수 세기 | 저장된 건수들을 더하기 | ✅ 미리계산표 사용 |
| **두 테이블을 잇는 조회** | **한쪽 가지만 미리계산표로 교체** | ✅ 미리계산표 + 원본 테이블 |

마지막이 특히 강력합니다. 미리계산표는 한 테이블만 집계한 것인데, 두 테이블을 잇는 조회에서 **해당 테이블 쪽만 미리계산표로 갈아끼우고 나머지는 원본에서 읽었습니다.** 3-2의 `QUERY_DELTA` 방식입니다.

**결과는 정확했습니다.** 자동 변환 켬/끔/Trino 대조군 세 경우가 소수점까지 같았습니다.

### 4-3. 원본이 바뀐 뒤의 동작이 정반대다

작은 원본 테이블에 미리계산표를 걸고 갱신한 뒤, 원본에 한 건을 추가했습니다.

**Trino**

| 미리계산표 설정 | 원본 변경 후 |
|---|---|
| 허용 지연 시간 미지정(기본) | **여전히 미리계산표를 읽음** |
| 허용 지연 시간을 0초로 지정 | 정의를 펼쳐 **원본을 읽음** |

상태 조회에서는 첫 번째 경우도 **"낡음(STALE)"으로 표시됩니다.** 그런데도 미리계산표를 읽습니다 — 2-3의 무제한 허용 지연 때문입니다.

> **운영상 주의**: **모니터링에서 "낡음"을 보고 "그럼 원본을 읽고 있겠지"라고 넘기면 틀립니다.** 허용 지연 시간을 명시하지 않은 미리계산표는 갱신할 때까지 낡은 답을 계속 제공합니다.

**StarRocks**

| 단계 | 무엇을 읽었나 |
|---|---|
| 갱신 직후 | 미리계산표 |
| 원본 변경 후 (변경을 인식한 뒤) | **원본 테이블** — 미리계산표를 쓰지 않음 |

**StarRocks는 낡았다고 판단하면 자동 변환을 포기하고 원본으로 돌아갑니다.**

> **투명성을 위한 기록**: 이 시험의 중간 단계에서 StarRocks가 옛 값을 돌려준 구간이 있었는데, 원인을 추적하니 **미리계산표가 아니라 외부 데이터 목록 캐시** 때문이었습니다. 캐시를 갱신하자 즉시 원본을 읽고 정확한 값을 냈습니다. 두 원인을 섞어 해석하지 않도록 실험 기록에 별도로 적었습니다.

## 5. 실무에서 의미 있는 차이

### (1) 미리계산표를 운영 수단으로 쓸 수 있는가

| 상황 | Trino | StarRocks |
|---|---|---|
| 미리계산표를 새로 만들면 | **조회문을 고쳐야** 이득이 생김 | 기존 조회가 자동으로 빨라짐 |
| 미리계산표를 지우면 | 참조하던 조회가 **깨짐** | 원본으로 조용히 돌아감 |
| 미리계산표 정의를 바꾸면 | 참조 조회를 **전부 점검**해야 함 | 안 맞으면 원본으로 돌아감 |
| BI 도구가 만든 조회 | 적용 불가 | 그대로 이득 |

**BI·애드혹 조회가 많고 조회문을 통제할 수 없는 환경이라면 이 차이가 결정적입니다.** Trino에서는 미리계산표를 만들어도 활용할 방법이 없습니다.

반대로 **조회문이 코드로 관리되고 수가 적다면 차이가 작습니다** — Trino에서도 미리계산표 이름을 직접 쓰면 같은 이득을 얻습니다.

### (2) 조회 계획의 예측 가능성

| | Trino | StarRocks |
|---|---|---|
| 같은 조회문의 실행 방식 | 항상 같음 | **미리계산표 유무에 따라 달라짐** |
| 조회 계획 수립 시간 | 미리계산표와 무관 | 미리계산표가 많을수록 늘어남(상한 1초) |
| 범위를 좁히는 수단 | — | 미리계산표를 이름으로 한정 |

**자동 변환은 공짜가 아닙니다.** 응답 시간을 보장해야 하는 업무에서는 "같은 조회가 어제와 다르게 실행된다"는 것이 부담이 될 수 있습니다. StarRocks가 시간 상한과 이름 한정 설정을 둔 것이 그 방증입니다.

### (3) 신선도 정책 — 둘 다 자기 방식에서는 타당하다

| | Trino | StarRocks |
|---|---|---|
| 접근 방식 | 사용자가 **이름을 직접 적었다** | 사용자는 **원본 테이블을 적었다** |
| 낡은 결과를 줘도 되는가 | 사용자가 요약표를 선택한 것이므로 **허용 가능** | 결과가 달라지면 **오류** |
| 기본 동작 | 계속 사용 (허용 지연 무제한) | 사용 안 함 |

**투명하게 바꿔주는 쪽은 신선도를 양보할 수 없고, 이름을 직접 적는 쪽은 양보할 수 있습니다.** 원리상 필연적인 차이입니다.

다만 Trino 쪽에는 실무적 함정이 있습니다(4-3) — **상태 표시와 실제 동작이 어긋나 보입니다.** 정확성이 중요한 미리계산표에는 허용 지연 시간을 반드시 명시해야 합니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **자동 변환으로 얼마나 빨라지는가** | 시험 데이터가 6만 건이라 미리계산표를 읽는 이득을 측정할 수 없습니다 | 메모리 24GB 이상 장비 + 100배 이상 데이터 |
| **자동 변환이 조회 계획 수립 시간에 미치는 영향** | 미리계산표를 하나만 만들어 시험했습니다. 개수를 늘려가며 재야 합니다 | 미리계산표 다수 생성 후 반복 측정 |
| **원본이 일부만 바뀐 경우의 부분 활용** | StarRocks 소스에 해당 기능이 있으나, 시험용 테이블이 나뉘어 저장돼 있지 않아 그 경로를 타지 못했습니다 | 나눠 저장한 테이블로 별도 시험 |
| **미리계산표 위에 미리계산표를 만드는 경우** | 확인하지 않았습니다(설정상 3단계까지 지원) | 별도 시험 |
| **StarRocks 자체 저장소 기반 미리계산표** | 전부 공용 파일 형식(Iceberg) 기준으로만 확인했습니다. 자체 저장소에서만 되는 갱신 방식이 따로 있습니다 | 자체 저장소 시험 별도 설계 |
| **미리계산표의 유지 비용** | 자동 변환의 이득만 봤고, 갱신에 드는 시간·저장 공간은 보지 않았습니다 | 갱신 부하 측정 |

**이번 보고는 "자동으로 바꿔주는가와 그 범위"이며, "얼마나 빨라지는가"가 아닙니다.**
