## 한 장 요약

앞선 일곱 편은 **"어떻게 실행할지 정하는 단계"**(실행 계획 수립)를 다뤘습니다. 이번부터는 **"실제로 실행하는 단계"** 입니다. 그 첫 문서로, 데이터를 메모리에 어떤 모양으로 담아 나르는지 비교했습니다.

| | Trino | StarRocks |
|---|---|---|
| 언어 | Java | 실행부는 C++ |
| 한 묶음의 크기 기준 | **용량**(1~16MB), 건수는 자동 조절 | **건수 고정**(4,096건) |
| 크기를 사람이 조절 | **불가** | **가능**(설정값) |
| 컬럼 표현 종류 | 11종 (+ 압축 형태 2종) | 53종 |
| 특별 취급하는 것 | **압축된 데이터**(같은 값 반복, 사전 방식) | **빈 값·고정값** |
| CPU 벡터 명령 직접 사용 | 14개 파일 (저장·파일 해독에 한정) | 45개 파일 (연산 전반) |
| 관련 코드 규모 | 약 13,700줄 | 약 16,400줄 |

**결론: 같은 방식(컬럼 단위 묶음 처리)을 각자의 언어에 맞게 구현했습니다. 규모는 대등하고, 이번 시험 조건에서는 우열을 판정할 수 없습니다. 다만 널리 퍼진 "Java라서 CPU 벡터 명령을 못 쓴다"는 통념은 483 기준으로 사실이 아닙니다.**

## 1. 왜 이걸 봤나

두 제품 모두 데이터를 **한 건씩이 아니라 수천 건 묶음으로, 컬럼 단위로** 처리합니다. 이 묶음의 모양이 뒤따르는 모든 처리 방식을 제약합니다 — 테이블을 잇는 방법도, 계산식을 평가하는 방법도 전부 이 위에 얹힙니다.

운영 관점에서 걸리는 것은 둘입니다.

- **메모리 사용량이 예측 가능한가** — 묶음 크기를 무엇으로 정하느냐에 달렸습니다
- **성능이 아쉬울 때 조절할 여지가 있는가**

그리고 이 항목은 **제품 선정 자리에서 "C++이라 빠르다 / Java라 느리다"는 말이 나오는 지점**이기도 합니다. 실제로 코드가 어떤지 확인했습니다.

---

## 2. Trino의 방식 — "용량을 목표로 잡고 건수는 알아서 맞춘다"

### 2-1. 한 묶음은 컬럼 배열과 건수로 이뤄진다

**[Page.java#L50-L52](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/Page.java#L50-L52)**

```java
    private final Block[] blocks;
    private final int positionCount;
    private volatile long sizeInBytes = -1;
```

▸ **읽는 법** — `blocks` 가 컬럼들, `positionCount` 가 건수입니다. 주목할 것은 세 번째 `sizeInBytes`(**용량**)를 따로 기억해둔다는 점입니다. **Trino에서 용량은 부수적인 값이 아니라 1급 관심사입니다.**

### 2-2. 압축된 데이터를 "컬럼의 종류"로 다룬다

**[Block.java#L21-L24](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/block/Block.java#L21-L24)**

```java
public sealed interface Block
        permits DictionaryBlock,
                RunLengthEncodedBlock,
                ValueBlock
```

▸ **읽는 법** — 컬럼의 종류가 **딱 세 갈래로 봉인**돼 있습니다. `DictionaryBlock`(**사전 방식으로 압축된 컬럼**), `RunLengthEncodedBlock`(**같은 값이 반복되는 컬럼**), `ValueBlock`(그냥 값이 들어 있는 컬럼).

**압축 형태가 컬럼의 종류 자체입니다.** 덕분에 모든 처리 단계가 "이 컬럼은 압축돼 있을 수 있다"를 반드시 마주하게 되고, 압축을 풀지 않고 처리하는 최적화를 안전하게 할 수 있습니다.

`ValueBlock` 의 실제 구현은 **11종**입니다. 특징은 **자료형이 아니라 메모리에 놓이는 모양으로 나눴다**는 점입니다 — 예를 들어 정수(bigint)와 실수(double)가 **같은 종류**를 씁니다. 둘 다 8바이트짜리이기 때문입니다.

### 2-3. 묶음 크기를 실행 중에 스스로 조절한다

**[PageProcessor.java#L220-L231](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/operator/project/PageProcessor.java#L220-L231)**

```java
        private void updateBatchSize(int positionCount, long pageSize)
        {
            // if we produced a large page, halve the batch size for the next call
            if (positionCount > 1 && pageSize > MAX_PAGE_SIZE_IN_BYTES) {
                projectBatchSize = projectBatchSize / 2;
            }

            // if we produced a small page, double the batch size for the next call
            if (pageSize < MIN_PAGE_SIZE_IN_BYTES && projectBatchSize < MAX_BATCH_SIZE) {
                projectBatchSize = projectBatchSize * 2;
            }
        }
```

▸ **읽는 법** — 개발진 주석이 그대로 설명합니다. **"묶음이 너무 커지면 다음번엔 건수를 절반으로, 너무 작으면 두 배로."** 목표는 용량이고 건수는 그것을 맞추는 수단입니다.

기준값은 소스에 고정돼 있습니다 — 목표 용량 4MB~16MB, 건수 상한 8,192건.

**왜 용량 기준인가**: Trino는 컬럼이 몇 개인지 모르는 남의 데이터를 상대합니다. 어떤 표는 컬럼이 3개, 어떤 표는 300개입니다. **"4,096건"이라는 약속으로는 메모리 사용량을 통제할 수 없습니다.**

**대신 사람이 조절할 수 있는 설정이 없습니다.** 엔진이 알아서 합니다.

## 3. StarRocks의 방식 — "건수를 고정하고, 빈 값을 특별 취급한다"

### 3-1. 한 묶음은 컬럼 벡터로 이뤄진다

**[chunk.h#L93-L94](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/column/chunk.h#L93-L94)**

```cpp
    size_t num_columns() const { return _columns.size(); }
    size_t num_rows() const { return _columns.empty() ? 0 : _columns[0]->size(); }
```

▸ **읽는 법** — 건수를 별도로 들고 있지 않고 **첫 컬럼의 길이로 구합니다.** 용량을 미리 계산해 기억해두는 곳도 없습니다. Trino가 용량을 따로 관리하는 것(2-1)과 대비됩니다.

### 3-2. 묶음 크기가 건수로 고정돼 있고, 사람이 바꿀 수 있다

**[config.h#L854](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/common/config.h#L854)**

```cpp
CONF_Int32(vector_chunk_size, "4096");
```

▸ **읽는 법** — **4,096건 고정**입니다. Trino처럼 실행 중에 조절하는 장치가 없습니다. 대신 이 값은 **조회 단위 설정으로도 노출돼 있어 사람이 바꿀 수 있습니다.** 실행부 코드에서 이 값을 참조하는 곳이 246군데로, 처리 전체의 기본 단위입니다.

4-2에서 이 설정을 바꿔 실제로 효과가 있음을 확인했습니다.

### 3-3. 빈 값(NULL)을 "감싸는 컬럼"으로 다룬다

**[nullable_column.h#L362-L364](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/column/nullable_column.h#L362-L364)**

```cpp
    ColumnPtr _data_column;
    NullColumnPtr _null_column;
    mutable bool _has_null;
```

▸ **읽는 법** — 실제 값이 든 컬럼(`_data_column`)과 **빈 값 여부를 표시하는 별도 컬럼**(`_null_column`)을 함께 들고 다닙니다. 세 번째 `_has_null` 은 "빈 값이 하나라도 있는가"를 미리 기억해둔 것으로, **없으면 검사를 통째로 건너뛰는 빠른 경로**를 만듭니다.

한 걸음 더 나간 장치도 있습니다.

**[adaptive_nullable_column.h#L64-L70](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/column/adaptive_nullable_column.h#L64-L70)**

```cpp
    enum class State {
        kUninitialized,
        kNull,
        kConstant,
        kNotConstant,
        kMaterialized,
    };
```

▸ **읽는 법** — 데이터를 읽어 들이는 동안 **빈 값 표시를 아예 만들지 않고 상태만 기억**해둡니다. 전부 비었거나(`kNull`) 전부 같은 값이면(`kConstant`) 표시가 필요 없기 때문입니다. 실제로 섞여 있을 때만(`kNotConstant`) 그때 만듭니다.

**Trino에는 이런 장치가 없습니다.** 반대로 **StarRocks에는 압축 형태를 컬럼 종류로 두는 장치가 없습니다**(2-2). **서로 다른 것을 특별 취급하기로 한 것입니다.**

### 3-4. 컬럼 종류가 53가지인 것은 언어 때문이다

StarRocks의 컬럼 종류는 **53가지**입니다. Trino의 11종보다 훨씬 잘게 나뉜 것처럼 보이지만, **담을 수 있는 것의 범위는 비슷합니다.**

차이는 자료형 정보를 어디에 두느냐입니다.

| | Trino | StarRocks |
|---|---|---|
| 나누는 기준 | 메모리에 놓이는 모양 | **자료형별로 따로** |
| 정수와 실수 | **같은 종류**를 씀 | 각각 별도 |
| 자료형 정보 | 별도 객체가 보관 | **컬럼 종류 자체에 들어 있음** |

**이것은 취향이 아니라 언어의 제약입니다.** Java에서 자료형마다 컬럼 종류를 만들면 실행 시점 최적화가 깨져 오히려 느려집니다. C++은 반대로 자료형마다 코드를 따로 만들어도 비용이 들지 않습니다.

**따라서 "Trino가 덜 세분화됐으니 느리다"고 읽으면 안 됩니다.** 각자의 실행 환경에서 빠른 형태를 고른 것입니다.

## 4. 실제로 돌려서 확인한 것

**시험 조건**: Trino 처리 서버 1대 / StarRocks 처리 서버 1대, TPC-H 표준 데이터 최소 규모(약 6만 건).

> **이 항목은 원래 실제 실행으로 확인할 수 있는 범위가 좁습니다.** 컬럼이 메모리에 어떻게 놓이는지, CPU 벡터 명령이 실제로 도는지는 실행 계획에도 성능 기록에도 드러나지 않습니다. 확인할 수 있었던 것은 **묶음 크기 설정과 그 효과**까지입니다.

### 4-1. 조절 손잡이의 성격이 다르다

| 제품 | 노출된 설정 | 값 | 성격 |
|---|---|---|---|
| StarRocks | `chunk_size` | 4,096건 | **처리 전체의 기본 묶음 크기** |
| Trino | `filter_and_project_min_output_page_row_count` | 256건 | 특정 처리 단계 출력의 **하한** |
| Trino | `filter_and_project_min_output_page_size` | 500kB | 같은 것의 용량 기준 |

**Trino에는 묶음 크기 자체를 정하는 설정이 없습니다.** 소스에 고정된 값 + 실행 중 자동 조절입니다(2-3).

### 4-2. 묶음 크기는 실제로 메모리를 좌우한다

StarRocks의 `chunk_size` 를 바꿔가며 같은 조회의 **메모리 할당량**을 읽었습니다(각 2회 측정, 편차 0.5% 미만). **시간이 아니라 메모리를 신호로 쓴 이유는, 이 시험 환경에서는 실행 시간으로 결론을 내지 않기 때문입니다.**

| 묶음 크기 | 메모리 할당량 |
|---|---|
| 64건 | 3.74 MB |
| **4,096건 (기본)** | **3.17 MB** |
| 32,768건 | 7.08 MB |

- 기본값의 8배로 키우자 할당량이 **2.2배**로 늘었습니다
- 64건으로 줄이자 **오히려 늘었습니다** — 묶음 하나당 고정 비용이 있는데 묶음 수가 64배가 되기 때문입니다

**결과값은 세 설정에서 모두 같았고 Trino와도 같았습니다.** 묶음 크기는 성능 설정이지 결과를 바꾸는 값이 아닙니다.

> **다만 어느 값이 빠른지는 판정하지 않았습니다.** 시간을 재지 않았습니다.

### 4-3. 성능 기록에는 묶음 개수가 드러나지 않는다

| 제품 | 처리 단계별로 보이는 것 |
|---|---|
| Trino | `Input: 60175 rows (587.64kB)` — **건수와 용량을 함께** |
| StarRocks | `OutputRows: 60.175K` + 소요 시간 + 메모리 |

**양쪽 다 묶음 개수를 직접 보여주는 지표는 없습니다.** 여기서도 2-1의 성격이 비칩니다 — Trino는 용량을 함께 보여주고, StarRocks는 건수와 시간을 보여줍니다.

## 5. 실무에서 의미 있는 차이

### (1) 메모리 사용량의 예측 가능성

| | Trino | StarRocks |
|---|---|---|
| 묶음 크기 기준 | **용량**(4~16MB 목표) | **건수**(4,096건) |
| 컬럼이 아주 많은 표에서 | 자동으로 건수를 줄임 | 건수는 그대로 — **메모리가 늘어남** |
| 조절 | 불가(자동) | **가능**(설정값) |

**컬럼이 수백 개인 넓은 표를 다룬다면 StarRocks에서는 `chunk_size` 를 낮춰야 할 수 있습니다.** 반대로 컬럼이 적고 건수가 많은 표라면 올려보는 것이 튜닝 수단입니다(4-2에서 설정이 실제로 작동함을 확인).

Trino는 알아서 맞춰주지만, **잘못 맞췄을 때 사람이 고칠 방법이 없습니다.**

### (2) "C++이라 빠르다"는 말을 어디까지 받아들일 것인가

**널리 퍼진 "Java라서 CPU 벡터 명령(SIMD)을 못 쓴다"는 통념은 483 기준으로 사실이 아닙니다.**

| | Trino | StarRocks |
|---|---|---|
| 벡터 명령을 쓰는 파일 수 | **14개** | **45개** |
| 쓰는 곳 | 데이터 저장·전송, 파일 해독 | **계산식·컬럼 처리·저장소 전반** |
| 계산 자체는 | 실행 시점 코드 생성 + 자동 최적화에 위임 | **직접 작성** |

**차이는 "쓰느냐"가 아니라 "어디까지 직접 쓰느냐"입니다.** Trino는 데이터를 주고받는 경계에만 손으로 쓴 벡터 코드를 두고, 실제 계산은 Java 실행 환경의 자동 최적화에 맡깁니다. StarRocks는 조건 검사·해시 계산·계산식까지 직접 씁니다.

**그 차이가 실제 속도로 얼마나 나타나는지는 이번에 재지 않았습니다.** 코드 표면적만 보고 성능을 단정하면 안 됩니다.

### (3) 서로 다른 것을 특별 취급하기로 했다

| 특별 취급 대상 | Trino | StarRocks |
|---|---|---|
| 압축된 데이터(사전 방식, 반복 값) | **컬럼 종류로 승격** | 없음 |
| 빈 값·고정값 | 일반 처리 | **감싸는 컬럼 + 상태 5단계** |

**어느 쪽이 낫다기보다, 각자 자주 마주치는 데이터에 맞춰 최적화한 것으로 읽힙니다.** Trino는 여러 저장소에서 오는 압축된 데이터를, StarRocks는 자체 저장소에서 흔한 빈 값 패턴을 각각 겨냥했습니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **실제 처리 속도** | 시험 데이터가 6만 건으로 너무 작고, 시험 장비 메모리(7.6GB)가 부족합니다 | 메모리 24GB 이상 장비 + 100배 이상 데이터 |
| **CPU 벡터 명령이 실제로 도는지** | 코드에 있다는 것과 실행 시점에 실제로 쓰인다는 것은 다릅니다. CPU 수준 측정이 필요합니다 | 프로파일링 도구 |
| **Java 자동 최적화의 실효** | Trino가 만들어내는 코드가 실제로 벡터화되는지 확인하려면 실행 환경 로그가 필요합니다 | JVM 컴파일 로그 분석 |
| **묶음 크기의 최적값** | 4-2는 메모리만 봤습니다. 어느 값이 빠른지는 재지 않았습니다 | 위와 같음 |
| **컬럼 내부 메모리 배치** | 실행 계획·성능 기록 어디에도 드러나지 않습니다. 코드 비교로만 확인했습니다 | 메모리 덤프 분석 |
| **StarRocks 자체 저장소** | 전부 공용 파일 형식 기준으로만 확인했습니다. 자체 저장소는 묶음을 만드는 경로가 다릅니다 | 자체 저장소 시험 별도 설계 |

**이번 보고는 "어떤 모양으로 담아 나르는가"이며, "어느 쪽이 더 빠른가"가 아닙니다.**

특히 두 번째 항목이 중요합니다 — **"코드에 벡터 명령이 몇 개 있다"는 것은 성능 지표가 아닙니다.** 이번 보고에서 확인한 것은 *두 제품이 벡터 명령을 쓰는 범위가 다르다*는 사실까지입니다.
