# [보고] Trino vs StarRocks 기술 검토 종합 보고

> 작성일: 2026-09-07 | 대상 버전: **Trino 483**, **StarRocks 4.0.14**
> 검토 산출물: 기술 문서 31편 · 실험 기록 18편 · 항목별 보고서 9편
>
> **이 보고서에는 소스코드를 넣지 않았습니다.** 모든 근거는 해당 기술 문서로 링크했고,
> 각 문서 안에 실제 코드와 GitHub 원문 링크가 있습니다.
> 전체 목록은 [8. 근거 문서](#8-근거-문서)에 있습니다.

## 요약

두 제품을 **소스코드 수준에서 31개 항목**으로 나눠 비교하고, 그중 상당수를 **실제 시험 환경에서 돌려** 확인했습니다.

**핵심 결론은 한 문장입니다.**

> **두 제품의 거의 모든 차이는 단 하나의 설계 결정에서 갈라져 나옵니다 — 데이터를 자기가 보관하는가.**

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 성격 | 데이터를 **보관하지 않는** 조회 엔진 | 데이터를 **보관하는** 데이터베이스 |
| 붙일 수 있는 데이터 소스 | **27종**(+관계형 DB 15종), 추가 개발 가능 | 10종, 제품을 고쳐야 추가 |
| 반복 조회 가속(미리계산표 자동 활용) | 없음 | **있음** |
| 공용 형식 데이터 수정(UPDATE/DELETE/MERGE) | **가능** | 불가(넣기만 가능) |
| 통계 관리 | 사람이 실행 | **자동** |
| 장시간 작업 장애 복구 | **진행분을 살림** | 전체 재실행 |

**확인된 우위는 StarRocks 12개 · Trino 10개로 비슷했고, "차이 없음"으로 끝난 항목이 10개였습니다.**

**따라서 이 검토의 결론은 "어느 쪽이 낫다"가 아닙니다.** 선택은 아래 세 질문의 답으로 결정됩니다.

> 1. 우리 데이터가 **한 시스템 안에 사는가, 여러 시스템에 흩어져 있는가**
> 2. 우리가 그 데이터를 **고쳐 쓰는가, 읽기만 하는가**
> 3. 우리에게 필요한 것이 **반복 조회의 속도인가, 붙일 수 있는 소스의 폭인가**

세 답이 한 방향이면 선택은 정해져 있고, 갈리면 **[5-2의 함께 쓰는 구성](#5-2-함께-쓰는-구성)** 이 현실적인 답입니다.

> ⚠ **가장 중요한 한계를 먼저 밝힙니다. 이 검토는 "어느 쪽이 빠른가"에 답하지 않습니다.**
> 시험 장비의 메모리 제약으로 **실행 시간을 한 번도 재지 못했습니다.** 자세한 내용은 [6. 이 검토의 한계](#6-이-검토의-한계).

## 1. 검토 개요

| 구분 | 내용 |
|---|---|
| 목적 | 두 제품의 차이를 **기능 목록이 아니라 설계 결정 수준에서** 파악 |
| 방법 | 소스코드 분석 + 동일 조건 시험 환경에서 실측 |
| 시험 환경 | 두 제품을 **같은 데이터 저장소(Iceberg)** 에 붙이고 같은 조회 실행 |
| 산출물 | 기술 문서 31편, 실험 기록 18편, 항목별 보고서 9편 |
| 비교 축 | SQL 해석 · 최적화 · 실행 엔진 · 데이터 교환 · 연결 확장성 · 운영 · 저장 계층 · 코드베이스 |

**기능 목록 대조 방식을 택하지 않은 이유**가 있습니다.

- **되는 것끼리도 되는 범위가 어긋납니다.** 이번 검토에서 가장 자주 나온 형태입니다([4-3](#4-3-어느-쪽도-상위집합이-아닌-것-6개))
- **"왜 그런지"를 모르면 예측할 수 없습니다.** 지금 없는 기능이 다음 버전에 생길지, 구조상 못 만드는지가 갈립니다

## 2. 핵심 결론 — 하나의 갈림길

그림 한 장으로 줄이면 이렇습니다.

```
  Trino                                    StarRocks
  ─────────────────────────────            ─────────────────────────────
  ┌───────────────┐                        ┌───────────────┐
  │   조회 엔진    │                        │   조회 엔진    │
  ├───────────────┤                        ├───────────────┤
  │ ═══ 경계 ═══  │  ← 확장점 (16종)       │   저장 엔진    │  ← 경계 없음
  ├───────────────┤                        ├───────────────┤
  │   저장 엔진    │  ← 남의 것             │   디스크       │  ← 자기 것
  │   (없음)      │                        └───────────────┘
  └───────────────┘
```

**경계를 만들어 그 뒤를 남에게 맡긴 쪽**과 **경계를 없애 전부 자기가 하는 쪽**입니다.

## 3. 아키텍처 구성도

### 3-1. Trino — 두 종류의 프로세스와, 그 밖의 모든 것

```
        SQL (JDBC / HTTP)
             │
             ▼
┌────────────────────────────────────┐
│  Coordinator  (Java 프로세스 1대)    │   ※ 이중화 계층 없음
│  ┌──────────────────────────────┐  │
│  │ 파싱 → 분석 → 최적화 → 배치   │  │
│  └──────────────────────────────┘  │
│  보관하는 것: 실행 중인 조회의 상태만 │
└────────────────────────────────────┘
             │  조회 계획 전달
             ▼
┌────────────────────────────────────┐
│  Worker  (Java 프로세스 N대)         │
│  ┌──────────────────────────────┐  │
│  │  실행 (읽기·조인·집계·정렬)    │  │
│  └──────────────────────────────┘  │
│  보관하는 것: 없음 (디스크 불필요)   │
└────────────────────────────────────┘
      │  Worker ↔ Worker : HTTP (받는 쪽이 가져감)
      │
   ═══╪════════ 확장점 경계 ═══════════════════════
      │
      ▼  플러그인 파일 하나로 붙음
┌──────────────┬──────────────┬──────────────┐
│  Iceberg     │  PostgreSQL  │  Kafka  …    │  ← 27종 (+관계형 DB 15종)
└──────────────┴──────────────┴──────────────┘
      │              │              │
      ▼              ▼              ▼
  오브젝트        외부 DB        메시지 큐        ← 데이터는 전부 남의 것
  스토리지
```

▸ **그림 읽는 법** — 굵은 가로선(`═══ 확장점 경계 ═══`)이 이 보고서의 주인공입니다. **선 아래는 Trino 코드가 아닙니다.** 플러그인이 담당하고, 제3자가 직접 만들어 붙일 수도 있습니다.

세 가지를 눈여겨보십시오.

- **Worker에 디스크가 없어도 됩니다.** 그래서 캐시가 기본 꺼짐입니다 → [캐시 계층](../B-3-01-캐시-계층.md)
- **Coordinator를 이중화하는 계층이 아예 없습니다.** 보관할 관리 정보가 없기 때문입니다 → [고가용성](../B-4-01-고가용성과-장애-복구.md)
- **Worker끼리는 받는 쪽이 가져가는 방식**으로 데이터를 주고받습니다 → [데이터 전송 계층](../A-4-01-셔플-전송-계층.md)

### 3-2. StarRocks — 두 종류의 프로세스가 모든 것을 나눠 가짐

```
        SQL (MySQL 프로토콜)
             │
             ▼
┌─────────────────────────────────────────────────┐
│  FE  (Java 프로세스 · 3대 이상 권장)              │
│  ┌───────────────────────────────────────────┐  │
│  │ 파싱 → 분석 → 최적화 → 배치                │  │
│  ├───────────────────────────────────────────┤  │
│  │ 관리 정보 (테이블·스키마·트랜잭션)         │  │
│  │ 자동 통계 수집 · 미리계산표 관리            │  │
│  └───────────────────────────────────────────┘  │
│                                                 │
│   LEADER ◄──복제──► FOLLOWER ◄──복제──► OBSERVER │
│      쓰기          선거 참여          읽기 확장   │
└─────────────────────────────────────────────────┘
             │  조회 계획 전달 · 제어
             ▼
┌─────────────────────────────────────────────────┐
│  BE  (C++ 프로세스 N대)                          │
│  ┌───────────────────────────────────────────┐  │
│  │  실행 (읽기·조인·집계·정렬)                │  │
│  ├───────────────────────────────────────────┤  │
│  │  저장 엔진                                 │  │
│  │   데이터 조각 → 적재 묶음 → 컬럼 파일       │  │
│  │   색인 4종 (범위·존재·비트맵·부분문자열)    │  │
│  │   자동 파일 정리 · 캐시                     │  │
│  └───────────────────────────────────────────┘  │
│  보관하는 것: 데이터 그 자체 (로컬 디스크)        │
└─────────────────────────────────────────────────┘
      │  BE ↔ BE : 보내는 쪽이 밀어넣음
      │
      └─► (외부 소스는 목록에 든 10종만: Iceberg·Hive·JDBC …)
```

▸ **그림 읽는 법** — **경계선이 없습니다.** FE와 BE는 하나의 제품을 둘로 쪼갠 것이지 확장점이 아닙니다. 새 데이터 소스를 붙이려면 **두 언어와 그 사이 통신 규약 세 곳을 모두 고치고 제품을 다시 빌드**해야 합니다 → [연결 확장성](../A-5-01-커넥터-인터페이스와-추가-난이도.md)

그리고 **BE 상자 안에 조회 엔진과 저장 엔진이 함께 있습니다.** 이것이 이 보고서 전체의 열쇠입니다.
저장 계층의 구조는 [저장 형식과 색인](../C-1-02-스토리지-포맷과-인덱스.md), 자동 정리는 [파일 정리](../C-1-03-compaction과-shared-data.md)에 있습니다.

### 3-3. 같은 조회가 어떻게 흐르는가

같은 조회(`지역별 매출 합계`)를 두 제품이 어떻게 처리하는지 나란히 놓았습니다.

```
  Trino                                  StarRocks
  ──────────────────────────             ──────────────────────────
  ① 조회 계획 수립                        ① 조회 계획 수립
     · 통계를 저장소에 "물어봄"               · 통계를 자기 것에서 "꺼냄"
     · 미리계산표는 이름을 써야 씀            · 미리계산표를 자동으로 갈아끼움
        │                                       │
  ② 조건을 저장소에 넘김                  ② 조건을 읽기 단계에 붙임
     · "이거 처리해 줄 수 있나?"              · 묻지 않고 그냥 붙임
     · 저장소가 책임진 건 계획에서 삭제       · 쓸 수 있는 형태를 이미 앎
        │                                       │
  ③ Worker 가 원격 저장소에서 읽음        ③ BE 가 자기 디스크에서 읽음
     · 네트워크 왕복                          · 색인으로 먼저 걸러냄
     · 캐시는 설정해야 켜짐                   · 캐시 기본 켜짐
        │                                       │
  ④ Worker ↔ Worker 로 재분배             ④ BE ↔ BE 로 재분배
        │                                       │
  ⑤ 결과 반환                            ⑤ 결과 반환
```

▸ **그림 읽는 법** — ①②③에서 **StarRocks는 "이미 알고 있어서" 한 단계씩 건너뜁니다.** 물어볼 필요가 없고, 색인이 있고, 캐시가 켜져 있습니다. 전부 데이터를 자기가 보관하기 때문입니다.

**반대로 ②의 Trino 쪽 "물어봄"이 27종의 데이터 소스를 붙일 수 있게 하는 바로 그 장치입니다.** 같은 구조가 한쪽에서는 비용이고 한쪽에서는 능력입니다.

### 3-4. 경계가 만든 결과 — 기능이 어느 쪽에 살고 있는가

같은 기능들이 두 제품에서 **어느 위치에 놓여 있는지**를 겹쳐 그렸습니다.

```
                    Trino                    │              StarRocks
 ───────────────────────────────────────────┼──────────────────────────────────
                                            │
  Coordinator ┌─────────────────────┐       │   FE ┌──────────────────────────┐
              │ 파싱·분석·최적화     │       │      │ 파싱·분석·최적화          │
              │ 접근제어 (84 지점)   │       │      │ 접근제어 (31 지점)        │
              │ 데이터 흐름 추적     │       │      │ ★ 통계 자동수집·관리      │
              └─────────────────────┘       │      │ ★ 미리계산표 자동 활용     │
                                            │      │ ★ 관리 정보 이중화        │
                                            │      └──────────────────────────┘
  Worker      ┌─────────────────────┐       │   BE ┌──────────────────────────┐
              │ 실행                 │       │      │ 실행                     │
              │ (디스크 없어도 됨)   │       │      │ ★ 저장 엔진 (테이블 4종)  │
              └─────────────────────┘       │      │ ★ 색인 4종+              │
                                            │      │ ★ 자동 파일 정리          │
   ═══════ 확장점 경계 (16종) ═══════        │      │ ★ 캐시 (기본 켜짐)       │
                                            │      │ ★ 실시간 적재 (Kafka 구독)│
  플러그인    ┌─────────────────────┐        │      │ ★ CPU 실격리             │
              │ ★ 공용 형식 쓰기·정리│        │      └──────────────────────────┘
              │ ★ 통계 보관          │        │
              │ ★ 미리계산표 보관     │        │      (경계 없음 — 외부 소스 10종 고정)
              │ (27종이 각자 구현)   │        │
              └─────────────────────┘        │

  ★ = 그 제품에서 우위가 확인된 기능
```

▸ **그림 읽는 법** — **★ 표시의 위치를 보십시오.**

StarRocks의 ★는 **전부 제품 안**에 있습니다. 그래서 자동으로 동작하고 서로 맞물려 최적화됩니다.

Trino의 ★는 **경계 아래 플러그인 쪽**에 있습니다. 그래서 **플러그인 품질에 따라 성능이 달라지고**, 통계·미리계산표처럼 엔진이 소유해야 가능한 기능은 만들 수 없습니다.

**그런데 바로 그 위치 때문에 Trino의 ★는 27종에 각각 존재합니다.** 공용 형식을 고치고 정리하는 기능이 그 예입니다 — 남의 저장소를 빌려 쓰니 정리 책임까지 져야 했고, 그래서 완비돼 있습니다 → [공용 형식 쓰기](../A-5-04-쓰기와-테이블-포맷-트랜잭션.md)

### 3-5. 자원을 다루는 방식

```
  메모리
  ──────────────────────────────────────────────────────────────
  Trino    ┌────────────────────────────┐  전체 100%
           │ 조회에 배정 (최대 30%)      │
           ├────────────────────────────┤
           │ ░░ 비워 둠 (30%) ░░         │ ← 정리 작업·버퍼·플러그인 몫
           ├────────────────────────────┤
           │ 나머지                      │
           └────────────────────────────┘
           계산 대상: 조회만

  StarRocks┌────────────────────────────┐  전체 100%
           │ 사용 (90%)                  │
           │  조회 + 적재 + 파일 정리    │ ← 보관 작업까지 같은 예산 안에서
           │  + 복제 + 캐시              │
           ├────────────────────────────┤
           │ ░ 10% ░                     │
           └────────────────────────────┘
           계산 대상: 제품이 하는 모든 일
```

▸ **그림 읽는 법** — Trino는 **조회가 쓰는 메모리만 계산하고 30%를 넉넉히 비웁니다.** 보관 작업이 없으니 셀 것도 없습니다. StarRocks는 **90%를 쓰되 적재·정리·복제까지 같은 예산 안에서 다툽니다.** 자원 계획이 더 어려운 대신 그 전부를 제품이 조율합니다 → [메모리 관리](../B-1-01-메모리-관리와-spill.md)

```
  CPU 격리
  ──────────────────────────────────────────────────────────────
  Trino      조회 목록을 1초마다 훑어봄 → 한도 초과면 실패 처리
             ┌──┐ ┌──┐ ┌──┐        ← 1초 안에 끝난 조회는 그냥 통과
             └──┘ └──┘ └──┘           (실측 확인)
             스레드는 OS 가 나눔

  StarRocks  BE 가 스레드를 소유 → 데이터 읽는 도중에 중단시킴
             ████████▌ 중단          ← 짧은 조회도 못 빠져나감
             CPU 배정 + 가중치로 실제 분배            (실측 확인)
```

▸ **그림 읽는 법** — **스레드를 누가 소유하는가의 차이입니다.** Trino의 Worker는 실행만 하므로 OS에 맡기고 입장만 통제합니다. StarRocks의 BE는 데이터를 들고 있으니 읽는 흐름 자체에 개입할 수 있습니다 → [자원 격리](../B-2-01-리소스-격리.md)

### 3-6. 장애가 났을 때

```
  ① 조율 노드가 죽었을 때
  ──────────────────────────────────────────────────────────────
  Trino      Coordinator ✗
             └─► 진행 중이던 조회 전부 소실. 이중화 계층 없음
                 (앞단 게이트웨이로 보완하는 것이 일반적)

  StarRocks  FE(LEADER) ✗
             └─► FOLLOWER 중 하나가 자동 승격
                 관리 정보는 이어짐. 단 진행 중이던 조회는 소실

  ② 실행 노드가 죽었을 때
  ──────────────────────────────────────────────────────────────
  Trino      Worker ✗
             기본        └─► 조회 실패 → 처음부터 재실행
             복원 기능 켬 └─► 죽은 작업만 다시 → ★ 진행분 유지

  StarRocks  BE ✗
             └─► 조회 전체 재실행 (최대 2회)
                 ※ 데이터는 복제본이 있어 소실되지 않음

  ③ 파일 읽기 중 결함이 났을 때
  ──────────────────────────────────────────────────────────────
  Trino      읽기 코드가 별도 계층  → 조회 하나 실패
  StarRocks  읽기 코드가 저장 계층  → ★ 데이터 보관 프로세스 자체가 죽음
```

▸ **그림 읽는 법** — ①에서는 StarRocks가, ②에서는 Trino가 앞섭니다. **서로 다른 층을 보호하고 있습니다** — StarRocks는 관리 정보를, Trino는 진행 중인 작업을.

③이 특히 중요합니다. **Trino는 실행과 저장이 분리돼 있어 결함의 파급이 조회 하나에 그칩니다.** StarRocks는 같은 프로세스가 데이터를 들고 있어 파급이 큽니다. **보관하는 대가입니다.**

### 5-2. 함께 쓰는 구성

**두 제품을 같은 데이터 저장소에 붙이는 것은 실제로 잘 동작합니다** — 이번 검토의 시험 환경이 그 증거입니다.

```
                    ┌──────────────────┐
                    │  공용 데이터 저장소│
                    │  (Iceberg)        │
                    └────────┬─────────┘
                  ┌──────────┴──────────┐
                  ▼                     ▼
        ┌───────────────────┐  ┌───────────────────┐
        │      Trino        │  │    StarRocks      │
        ├───────────────────┤  ├───────────────────┤
        │ ✔ 여러 소스 조인   │  │ ✔ 반복 집계 가속   │
        │ ✔ 수정·삭제·병합   │  │ ✔ 대시보드 조회    │
        │ ✔ 파일 정리·이력   │  │ ✔ 성능 분석       │
        │ ✔ 장시간 배치      │  │                   │
        │ ✔ 계보·감사        │  │ (+ 자체 저장소에   │
        │                   │  │   실시간 적재)     │
        └───────────────────┘  └───────────────────┘

        ⚠ 통계는 공유되지 않음 → 양쪽에서 각각 수집
        ⚠ StarRocks 만으로 운영 금지 → 정리 수단이 없어 파일이 쌓임
```

▸ **그림 읽는 법** — **Trino가 쓰기·정리를, StarRocks가 읽기 가속을 맡는 구성**입니다. 두 제품의 강점이 겹치지 않기 때문에 성립합니다([3-4](#3-4-경계가-만든-결과--기능이-어느-쪽에-살고-있는가)).

경고 두 가지가 실무에서 실제로 걸립니다. 특히 두 번째는 **StarRocks로 공용 형식에 데이터를 넣을 수는 있으나 고치거나 정리할 수 없기** 때문입니다.

### 5-3. 선택 흐름도

```
        질문 1                    질문 2                   질문 3
   데이터가 한 시스템에      그 데이터를 고쳐        필요한 것이 반복 조회
   사는가, 흩어져 있는가?      쓰는가, 읽기만?          속도인가, 소스의 폭인가?
        │                         │                         │
        ├── 한 곳 ──┐             ├── 고쳐 씀 ──┐           ├── 속도 ──┐
        │           ▼             │             ▼           │          ▼
        │      StarRocks          │        (자체 저장소면)   │     StarRocks
        │                         │          StarRocks      │
        │                         │        (공용 형식이면)   │
        │                         │          Trino          │
        └── 흩어짐 ─┐             └── 읽기만 ──┐            └── 폭 ────┐
                    ▼                          ▼                       ▼
                 Trino                   어느 쪽도 가능              Trino

   세 답이 한 방향이면 → 선택은 정해져 있습니다
   갈리면            → 5-2 의 함께 쓰는 구성
```

Trino에서 StarRocks로 SQL을 옮길 때 **조용히 결과가 달라지는 것부터** 확인해야 합니다.

| 순위 | 항목 | 왜 위험한가 | 근거 |
|---|---|---|---|
| **1** | **문자열 이어붙이기 연산자** | 오류가 아니라 **조용히 빈 값**이 됨 | [A-1-01](../A-1-01-문법-정의와-방언-커버리지.md) |
| 2 | 근사 집계 함수 | 이름은 대응되나 **값이 약 2.7% 다름** | [A-1-03](../A-1-03-함수-등록과-확장.md) |
| 3 | 시간대 포함 시각 컬럼 | 구분되지 않음. 값 자체는 맞음 | [A-1-02](../A-1-02-타입-체계.md) |

## 6. 이 검토의 한계

**보고서의 신뢰는 무엇을 확인하지 못했는지를 밝히는 데서 나옵니다.** 가장 중요한 것부터 적습니다.

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **어느 쪽이 실제로 빠른가** | **실행 시간을 한 번도 재지 않았습니다.** 시험 데이터가 약 6만 건으로 너무 작고, 큰 데이터로 재려면 메모리가 부족했습니다(한도와 실제 용량이 거의 같고 여유 공간이 없음) | 메모리 24GB 이상 장비 |
| **여러 대로 묶었을 때의 동작** | 각 제품 **1대씩**으로만 구성했습니다. [3-1·3-2·3-6](#3-아키텍처-구성도) 그림의 N대 부분은 **코드를 읽어 그린 것**이고 동작을 확인하지 못했습니다 | 3대 이상 구성 |
| **데이터 전송 계층 전체** | 위와 같은 이유로 **실측이 하나도 없습니다** | 위와 같음 |
| **자원 격리가 설정대로 CPU를 나누는가** | 이 항목의 핵심 주장인데 1대에서는 확인 불가 | 위와 같음 |
| **한 대가 죽어도 계속되는가** | 이 항목의 핵심 질문인데 1대에서는 확인 불가 | 위와 같음 |
| **여러 시스템 연합 조회** | 시험 환경에 데이터 소스가 하나뿐이었습니다 | 다중 소스 구성 |
| **외부 정책 엔진 연동** | 정책 서버가 없었습니다 | 별도 구성 |
| **실시간 적재 경로** | Kafka가 없었습니다 | 별도 구성 |
| **StarRocks 저장·컴퓨트 분리 구성** | [3-2](#3-2-starrocks--두-종류의-프로세스가-모든-것을-나눠-가짐) 그림은 기본 구성 기준입니다. 분리 구성은 재구성이 필요해 확인하지 못했습니다 | 클러스터 재구성 |
| **제품 개발 활동·출시 주기** | 소스를 최신본만 내려받아 이력이 없습니다 | 전체 이력 복제 |

**미해결 과제 하나**: StarRocks 이전 버전에서 관찰된 데이터 보관 프로세스 사망 현상이 **특정 CPU 아키텍처 한정인지 확인하지 못했습니다.** 디스크 여유가 부족해 두 버전을 함께 둘 수 없었습니다.

**이 보고서는 "두 제품이 무엇을 어떻게 하는가와 그 이유"이며, "어느 쪽이 더 빠른가"가 아닙니다.**
[4-1과 4-2의 표는 길이가 비슷하고](#4-확인된-격차), [4-4의 "차이 없음" 목록도 그만큼 깁니다](#4-4-차이-없음으로-끝난-것-10개). **성능 비교 없이 우열을 말할 수 없다는 것이 이 검토의 정직한 결론입니다.**

## 7. 검토 과정의 자기 정정

**검토 신뢰성의 근거로 기록을 남깁니다.** 처음 세운 계획의 전제가 **일곱 번 틀렸고**, 코드를 읽어 내린 판단이 **실제 시험에 두 번 뒤집혔습니다.**

### 7-1. 계획 단계의 전제가 틀린 것 (7건)

| 처음 전제 | 실제 | 근거 |
|---|---|---|
| 문법 정의가 특정 위치에 있다 | 최신 버전에서 **다른 모듈로 분리**됨 | [A-1-01](../A-1-01-문법-정의와-방언-커버리지.md) |
| 두 제품의 실행 방식이 서로 대비된다 | **성립하지 않음.** 둘 다 같은 방식으로 수렴 | [A-3-02](../A-3-02-실행-모델과-스케줄링.md) |
| Trino 미리계산표는 두 형식 지원 | **한 형식은 실제로 구현돼 있지 않음** | [A-2-06](../A-2-06-MV-쿼리-재작성.md) |
| StarRocks 문자열 최적화는 Trino에 없는 기능 | 맞지만 **공용 형식에서는 StarRocks 자신도 기본으로 안 씀** | [A-3-05](../A-3-05-표현식-평가와-딕셔너리.md) |
| StarRocks 자원 격리는 OS 기능 기반 | **아님.** CPU 배정 + 가중치 방식 | [B-2-01](../B-2-01-리소스-격리.md) |
| 캐시는 StarRocks만, **Trino는 없음** | **Trino에 분산 파일 캐시가 있음.** 없는 것은 결과 캐시뿐 | [B-3-01](../B-3-01-캐시-계층.md) |
| StarRocks는 자체 권한 관리만 | **외부 정책 엔진 통합이 있음** | [B-5-01](../B-5-01-보안과-권한-모델.md) |

### 7-2. 코드 독해가 실제 시험에 뒤집힌 것 (2건)

| 잘못 읽은 것 | 시험이 바로잡은 것 | 근거 |
|---|---|---|
| "설정 기준값 때문에 StarRocks가 단순한 실행 순서를 만든다" | 원인은 **통계 부족**이었음. 통계가 완전하면 균형 잡힌 순서가 나옴 | [A-2-01](../A-2-01-조인-순서-결정.md) |
| "StarRocks는 함수를 감싼 조건을 파일 건너뛰기에 못 쓴다" | **특정 함수에서는 완전히 걸러냄.** 문제는 함수 종류의 범위였음 | [A-5-02](../A-5-02-커넥터-푸시다운.md) |

### 7-3. 측정 설계에서 빠질 뻔한 함정 (2건)

- 읽은 양을 재려고 **건수 세기**를 썼다가 StarRocks의 최적화에 걸려 비교가 성립하지 않았습니다
- 두 제품의 지표를 짝지을 때 **필터 적용 전후가 다른 값**을 잘못 맞출 뻔했습니다

→ 둘 다 [A-5-02](../A-5-02-커넥터-푸시다운.md)

**이 기록의 뜻은 하나입니다 — 소스코드만 읽고 내린 결론은 상당한 확률로 틀립니다.** 그래서 이번 검토는 가능한 항목마다 실제로 돌려 확인했고, 돌리지 못한 항목은 [6절](#6-이-검토의-한계)에 남김없이 적었습니다.
