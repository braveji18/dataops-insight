# 종합 결론 — Trino 483 vs StarRocks 4.0.14

> 이 문서는 본문 **31편**과 증거 파일 **18편**의 결론을 모아 **워크로드별 선택 기준**으로 재정리한 것이다.
> 개별 근거는 각 문서에 있고, 여기서는 **결론과 그 사이의 연결**만 다룬다.
> 기준 버전: **Trino 483** / **StarRocks 4.0.14**
> 일자: 2026-09-04

---

## 1. 한 문장

**두 엔진의 거의 모든 차이는 하나의 결정에서 갈라져 나온다 — 스토리지를 소유하는가.**

Trino 는 소유하지 않기로 하고 **경계(SPI)를 만들어 그 뒤를 남에게 맡겼다.**
StarRocks 는 소유하기로 하고 **경계를 없애 전부 자기가 한다.**

31편을 쓰는 동안 이 구도가 **축을 가리지 않고 반복해서 나타났다.** 아래 표가 그 반복이다.

| 축 | 같은 결정이 어떻게 나타났는가 |
|---|---|
| `A-1-02` 타입 | Trino 타입은 SPI 에 있어 확장 가능 / StarRocks 는 FE 열거형 + BE C++ 짝 |
| `A-1-03` 함수 | 애노테이션 붙은 Java 메서드(플러그인 가능) / `functions.py` 가 FE·BE 코드를 동시 생성 |
| `A-2-06` MV | 커넥터가 MV 를 소유해 옵티마이저가 손대지 못한다 / 자기 스토리지라 재작성 전용 18,000줄 |
| `A-2-07` 통계 | 테이블에 돌려줘 다른 엔진과 공유 / 자기 안에 쌓아 더 많이 담는다 |
| `A-4-02` 셔플 | 상태가 없어 FTE 로 진행분을 살린다 / 데이터가 로컬이라 재실행이 합리적 |
| `A-5-01` 커넥터 | `trino-spi` 만 구현 / FE + BE + Thrift |
| `A-5-04` 쓰기 | Iceberg 가 유일한 저장 수단이라 MERGE·유지보수까지 완비 / 네이티브 테이블이 있어 외부 쓰기 유인이 약하다 |
| `B-1-01` 메모리 | 쿼리만 회계하고 30% 를 비운다 / 적재·compaction·복제까지 세고 90% 를 쓴다 |
| `B-2-01` 격리 | 스레드를 OS 에 맡겨 입장 통제만 / 스레드를 소유해 CPU 를 실제로 나눈다 |
| `B-3-01` 캐시 | 워커에 디스크가 없을 수 있어 기본 꺼짐 / BE 에 디스크가 있으니 기본 켜짐 |
| `B-4-01` HA | 메타데이터가 없어 그 층이 없다 / 복제 저널 + 자동 선거 |
| `B-6-01` 관측 | 쿼리 밖(계보)에 투자 / 쿼리 안(리더 내부 카운터)에 투자 |
| `C-1` 전체 | 대응물 없음 | 테이블 모델·인덱스·compaction·적재 |
| `D-01` 빌드 | Maven 하나 / Maven + CMake + Python 코드 생성 |

**따라서 제품 선택은 기능 목록 대조가 아니라 이 결정이 자기 상황에 맞는지를 묻는 일이다.**

## 2. 명확한 격차 (측정으로 확인된 것)

우열이 분명한 항목만 모았다. **나머지는 3절에서 "대등"으로 따로 다룬다.**

### 2-1. StarRocks 가 명확히 앞서는 곳

| 항목 | 근거 | 크기 |
|---|---|---|
| **MV 쿼리 재작성** | `A-2-06` | 재작성 전용 18,000줄 대 **규칙 0개.** Trino 는 MV 이름을 직접 써야 한다 |
| **통계 자동 수집** | `A-2-07` | 백그라운드 데몬이 **쿼리를 관찰해 필요한 컬럼을 스스로 고른다**(실측). Trino 는 사람이 `ANALYZE` |
| **테이블 모델** | `C-1-01` | 같은 입력에 네 가지 결과. **`UPDATE` 와 부분 컬럼 갱신은 `PRIMARY KEY` 만**이고 Iceberg 에 대체 수단이 없다 |
| **인덱스 종류** | `C-1-02` | 비트맵·n-gram(+실험 단계의 전문·벡터). `LIKE '%…%'` 는 Iceberg 통계로 전혀 걸러지지 않는다 |
| **자동 compaction** | `C-1-03` | BE 가 3종을 자동으로 돌린다. Trino 는 사람이 `EXECUTE optimize` 를 불러야 한다 |
| **적재 경로** | `C-1-04` | Stream/Broker/**Routine Load** — Kafka 상시 구독을 DB 가 소유한다 |
| **리소스 격리 강제력** | `B-2-01` | BE 가 스캔 도중 쿼리를 중단시킨다(실측). Trino 는 1초 폴링이라 짧은 쿼리가 빠져나간다(실측) |
| **캐시 기본 켜짐** | `B-3-01` | 설정 없이 적중한다(실측). Trino 는 디렉토리를 지정해야 켜진다 |
| **CTE 재사용** | `A-2-05` | 능력 자체가 Trino 에 없다(다만 이 랩에서 자동 선택은 확인 못 함) |
| **spill 범위** | `A-3-03` | 12계열 대 4계열. 다만 **양쪽 다 기본 꺼짐** |
| **메타데이터 HA** | `B-4-01` | BDB JE 복제 + LEADER/FOLLOWER/OBSERVER 자동 선거. Trino 는 이 층이 없다 |
| **쿼리 안 관측** | `B-6-01` | Parquet 리더 내부까지 계측되고 **끝난 쿼리를 SQL 로 사후 조회**할 수 있다 |

### 2-2. Trino 가 명확히 앞서는 곳

| 항목 | 근거 | 크기 |
|---|---|---|
| **커넥터 확장성** | `A-5-01`·`C-2-01` | SPI **16종**, 플러그인 JAR 로 배포. StarRocks 는 `ConnectorType` 열거형 + FE·BE 재빌드 |
| **커넥터 다양성** | `C-2-02` | 27개(+JDBC 계열 15). 관계형 DB **15:1**, 관측 데이터·SaaS·스트리밍 읽기는 대응물 없음 |
| **Iceberg 쓰기** | `A-5-04` | **StarRocks 는 INSERT/CTAS 만 된다.** UPDATE·DELETE·MERGE 가 각각 다른 방식으로 막혀 있고 유지보수 명령이 없다 |
| **장수 쿼리 내결함성** | `A-4-02`·`B-4-01` | FTE 가 태스크 단위로 재시도해 진행분을 살린다. StarRocks 는 쿼리 전체 재실행 최대 2회 |
| **함수 추가 비용** | `A-1-03` | 애노테이션 하나 + 플러그인 JAR. StarRocks 는 ID 부여 + C++ 구현 + 양쪽 재빌드 |
| **접근제어 세밀함** | `B-5-01` | 검사 지점 **84 대 31**. OPA 연동은 Trino 만 |
| **컬럼 수준 계보** | `B-6-01` | 엔진이 직접 계산해 이벤트로 내보낸다. StarRocks 에 없다 |
| **결함의 폭발 반경** | `A-5-03` | 리더 결함이 Trino 는 쿼리 실패, StarRocks 는 **BE 프로세스 사망**(그것도 데이터를 든 프로세스) |
| **타입 표현력(시간대·UUID)** | `A-1-02` | Iceberg `timestamptz` 를 구분하고 `UUID` 를 읽는다. StarRocks 는 전자를 합치고 후자는 **조회에서 실패** |
| **DECIMAL 정밀도** | `A-1-02` | **반대다.** StarRocks 76 대 Trino 38. 단 Iceberg 상한이 38이라 외부 테이블에서는 무의미 |

### 2-3. 어느 쪽도 상위집합이 아닌 것

**이 연구에서 가장 자주 나온 형태다.** "둘 다 되는데 되는 범위가 어긋난다."

| 항목 | 근거 |
|---|---|
| **함수 술어 프루닝** | `A-5-02` — Trino 는 `year`/`date_trunc`, StarRocks 는 `date_format` 을 벗긴다. **서로 반대 방향으로 못 한다** |
| **서브쿼리 언네스팅** | `A-2-05` — 15종 중 12종 동일, **2종이 정반대** |
| **윈도우 최적화** | `A-2-05` — 최적화하는 쿼리 모양이 어긋나 하나씩 이긴다 |
| **런타임 필터** | `A-3-04` — StarRocks 만 TopN·집계 필터, Trino 만 파일/행 필터 분리 |
| **조인 순서 탐색** | `A-2-01` — 5~8개는 Trino 가 넓게, 9~50개는 StarRocks 만 리오더 |
| **예약어** | `A-1-01` — StarRocks 에만 99개, Trino 에만 27개 |

## 3. 대등한 것 — 이 연구의 중요한 결과

**"차이가 없다"는 것도 결과다.** 다음 항목들은 실측에서 판별되지 않았거나 동등했다.

| 항목 | 근거 |
|---|---|
| 플랜 내부 푸시다운(술어 전이, outer join 단순화, LIMIT·TopN 관통) | `A-2-04` — 실측 6항목 전부 동등 |
| 파티션 프루닝(맨 컬럼 술어) | `A-5-02` — **165행 / 1파일로 완전히 일치** |
| 파일 리더 호환성 | `A-5-03` — 복합 타입·압축 4종·Iceberg 삭제 파일 전부 결과 일치 |
| 스키마 진화 | `A-5-04` — ADD/DROP/RENAME 이 상호운용된다(양쪽이 서로의 변경을 본다) |
| 시간 여행·메타데이터 테이블 | `A-5-04` — 스냅샷 7개를 양쪽이 똑같이 센다 |
| 데이터 표현 모델 | `A-3-01` — 같은 컬럼너 배치 모델, 규모 대등 |
| 실행 모델 | `A-3-02` — **`plan/01` 의 대비가 성립하지 않는다.** 둘 다 다단계 피드백 큐로 수렴 |
| 파서 오류 처리 | `A-1-01` — 양쪽 다 SLL → LL 2단계 |
| 메모리 유효 바닥 | `B-1-01` — 16MB 대 18MB, 같은 자릿수 |
| min/max·블룸필터 계층 | `C-1-02` — Iceberg 매니페스트와 ZoneMap 이 대등 |

**특히 `A-2-04`·`A-3-01`·`A-3-02` 는 "다를 것"이라 예상하고 들어가 "같다"로 끝난 축들이다.** 계획서의 대비가 실제로는 성립하지 않았다.

## 4. 워크로드별 선택 기준

### 4-1. 결정 표

| 상황 | 선택 | 결정적 근거 |
|---|---|---|
| **서로 다른 시스템을 한 쿼리로 조인해야 한다** | **Trino** | 커넥터 27개 대 10. 대체 수단 없음 (`C-2-02`) |
| **Iceberg 를 고쳐 써야 한다** (CDC upsert, GDPR 삭제) | **Trino** | StarRocks 는 Iceberg 에 UPDATE·DELETE·MERGE 를 못 한다 (`A-5-04`) |
| **수십 분 이상 도는 ETL** | **Trino** | FTE 만이 진행분을 살린다 (`A-4-02`·`B-4-01`) |
| **BI 대시보드 · 애드혹 반복 조회** | **StarRocks** | MV 자동 재작성 + 캐시 기본 켜짐 + 자동 통계 (`A-2-06`·`B-3-01`·`A-2-07`) |
| **잦은 upsert 가 있는 서비스 데이터** | **StarRocks** | `PRIMARY KEY` 모델 + 부분 컬럼 갱신 (`C-1-01`) |
| **Kafka → 테이블 파이프라인** | **StarRocks** | Routine Load 가 구성 요소를 하나 줄인다 (`C-1-04`) |
| **`LIKE '%…%'` 검색이 잦다** | **StarRocks** | n-gram 인덱스. Iceberg 통계로는 전혀 안 걸린다 (`C-1-02`) |
| **운영 인력이 적다** | **StarRocks** | 자동 통계·자동 compaction·캐시 기본 켜짐. 단 자원 계획은 더 어렵다 |
| **여러 엔진(Spark 등)이 같은 레이크를 쓴다** | **Trino** | 통계가 테이블에 남아 공유된다 (`A-2-07`) |
| **정책을 Rego 로 통일한다** | **Trino** | OPA 연동은 Trino 만 (`B-5-01`) |
| **거버넌스·규제 대응(컬럼 계보)** | **Trino** | 엔진이 직접 계산한다 (`B-6-01`) |
| **엔진을 고쳐 쓸 계획이 있다** | **Trino** | SPI 로 대부분 해결, 단일 언어 빌드 (`C-2-01`·`D-01`) |
| **초 단위 대화형 분석이 목표** | **StarRocks** | BRPC push·낮은 양자·C++ 실행 엔진. **다만 실행 시간을 재지 못했다**(5절) |

### 4-2. 함께 쓰는 구성

두 엔진을 같은 Iceberg 카탈로그에 붙이는 것은 **실제로 잘 동작한다** — 이 연구의 랩이 그 증거다. 역할을 나누면 이렇다.

| 작업 | 담당 |
|---|---|
| 적재(append), 조회, 시간 여행 | 양쪽 다 |
| **행 수정·삭제, MERGE upsert** | **Trino 만** (`A-5-04`) |
| **파일 병합, 스냅샷 만료, 고아 파일 제거** | **Trino 만** (`A-5-04`·`C-1-03`) |
| **반복 집계 가속(MV 재작성)** | **StarRocks** (`A-2-06`) |
| 감사·컬럼 계보 | Trino (`B-6-01`) |
| 성능 분석 | StarRocks 프로파일 (`B-6-01`) |

**주의 두 가지.**

1. **통계는 공유되지 않는다.** 양쪽에서 각각 `ANALYZE` 를 돌려야 한다 (`A-2-07`)
2. **StarRocks 만으로 Iceberg 를 운영하지 말 것.** 적재는 되지만 정리할 수단이 없어 파일이 쌓인다 (`A-5-04`)

### 4-3. 이전(migration) 체크리스트

Trino → StarRocks 로 SQL 을 옮길 때 **오류로 드러나지 않는 것부터** 확인한다.

| 순위 | 항목 | 왜 |
|---|---|---|
| **1** | **`\|\|` 연산자** | 오류가 아니라 **조용히 NULL** 이 된다. `'a' \|\| 'b'` → `NULL` (`A-1-01`) |
| 2 | 근사 집계 함수 | 이름은 대응되나 **값이 다르다**(15432 vs 15022) (`A-1-03`) |
| 3 | Iceberg `timestamptz` 컬럼 | 스키마로 구분되지 않는다. 값은 맞다 (`A-1-02`) |
| 4 | 날짜 함수를 감싼 술어 | 프루닝이 조용히 사라진다. 쿼리는 성공한다 (`A-5-02`) |
| 5 | 예약어 99개 | 오류로 드러난다. `text`·`key`·`json`·`range`·`default` 등 |
| 6 | 상관 서브쿼리 | 계획 실패가 오류로 드러난다. 전수 확인 필요 (`A-2-05`) |
| 7 | Iceberg `UUID` 컬럼 | `DESC` 는 성공하고 **조회에서 실패**한다 (`A-1-02`·`A-5-03`) |

**`sql_dialect='trino'` 를 일괄 이전 수단으로 기대하지 말 것** — trino-parser **385** 기준 부분 지원이고 함수 대응표가 약 100건이다 (`A-1-01`).

## 5. 이 연구가 답하지 못한 것

**가장 중요한 한계부터 적는다.**

### 5-1. 실행 시간을 한 번도 재지 못했다

**"어느 쪽이 빠른가"에 이 연구는 답하지 않는다.**

랩이 TPC-H **SF 0.01**(lineitem 60,175행)이고, `perf` 프로파일(SF 1)은 이 호스트에서 불가능하다 — 컨테이너 한도 15.3GB 대 RAM 15.6GB, **swap 0**(`plan/02` 6-2절).

따라서 아래 항목은 전부 미검증이다.

- 두 옵티마이저가 고른 플랜 중 어느 쪽이 실제로 빨랐는가 (`A-2-01`~`A-2-03`)
- C++ 벡터화와 JVM 바이트코드 생성의 실제 처리량 차이 (`A-3-01`·`A-3-05`)
- 해시 조인 구현 6종과 2종의 성능 차 (`A-3-03`)
- spill 이 걸렸을 때의 성능 (`A-3-03`·`B-1-01`)
- 캐시·인덱스의 실제 이득 (`B-3-01`·`C-1-02`)

### 5-2. 노드가 1대씩이라 다중 노드 항목이 전부 빠졌다

Trino worker 1 / StarRocks BE 1 이다. 다음이 미검증이다.

- **셔플 전송 계층 전체** (`A-4-01`·`A-4-02` — 두 문서에 실측이 하나도 없다)
- StarRocks broadcast 게이트의 `beNum` 항 (`A-2-02`)
- 리소스 그룹이 **가중치대로 CPU 를 나누는가** (`B-2-01` — 이 축의 핵심 주장)
- **한 노드가 죽어도 나머지로 계속하는가** (`B-4-01` — 이 축의 핵심 질문)
- FTE 의 태스크 단위 재시도 (`A-4-02`)
- FE FOLLOWER 승격 (`B-4-01`)

## 6. 이 연구가 스스로 고친 것

**계획서(`plan/01`)의 전제가 일곱 번 틀렸다.** 기록으로 남긴다 — 소스코드 비교에서 **선입견이 얼마나 자주 개입하는지**의 표본이다.

| # | `plan/01` 의 전제 | 실제 | 문서 |
|---|---|---|---|
| 1 | 문법이 `core/trino-parser` 에 있다 | 483 에서 **`core/trino-grammar`** 로 분리됨 | `A-1-01` |
| 2 | "협력적 멀티태스킹 대 논블로킹 폴러" | **성립하지 않는다.** 둘 다 다단계 피드백 큐로 수렴 | `A-3-02` |
| 3 | Trino MV 는 커넥터(Iceberg/Hive) 한정 | **Hive 커넥터는 MV 를 구현하지 않는다** | `A-2-06` |
| 4 | StarRocks 전역 딕셔너리는 Trino 대응물 부재 | 맞지만 **레이크 테이블에서는 StarRocks 자신도 기본으로 안 쓴다** | `A-3-05` |
| 5 | StarRocks 는 **BE cgroup** 실격리 | **cgroup 이 아니다.** CPU 친화도 바인딩 + 가중 vruntime + 코어 대여 | `B-2-01` |
| 6 | 캐시는 StarRocks 만, **Trino 는 부재** | **Trino 483 에 Alluxio 기반 분산 파일 캐시가 있다.** 없는 것은 결과 캐시뿐 | `B-3-01` |
| 7 | StarRocks 는 **내장 RBAC** | **Apache Ranger 통합이 있다**(Hive 서비스 정의 재사용 포함) | `B-5-01` |

**그리고 코드 독해가 실측에 두 번 뒤집혔다.**

| 잘못 읽은 것 | 실측이 바로잡은 것 | 문서 |
|---|---|---|
| "임계값 때문에 StarRocks 가 left-deep 플랜을 만든다" | 원인은 **통계 부족**이었다. 통계가 완전하면 bushy 가 나온다 | `A-2-01` 4절 |
| "StarRocks 커넥터가 함수 술어를 못 민다" | **`date_format` 에서는 완전히 프루닝한다.** 문제는 옵티마이저 규칙의 함수 커버리지 | `A-5-02` 4-4 |

**측정 설계에서도 두 번 함정에 빠질 뻔했다.**

- `count(*)` 로 스캔량을 재려 했다 → StarRocks 의 메타데이터 최적화에 걸려 비교가 성립하지 않는다 (`A-5-02` 4-1)
- StarRocks 의 `OutputRows` 를 Trino 의 `Input rows` 와 짝지었다 → 전자는 필터 **이후**다. 짝은 `RawRowsRead` (`A-5-02` 4-1)

## 7. 마지막

**이 연구의 결론은 "어느 쪽이 낫다"가 아니다.**

측정으로 확인된 명확한 격차는 2절의 두 표에 있고, **그 두 표는 길이가 비슷하다.** 그리고 3절의 "대등" 목록도 그만큼 길다. 예상과 달리 **두 엔진은 많은 곳에서 같은 답에 도달해 있었다.**

갈리는 곳은 거의 전부 **1절의 한 문장**으로 설명된다. 그러므로 선택의 질문은 이렇게 좁혀진다.

> **우리 데이터가 한 시스템 안에 사는가, 여러 시스템에 흩어져 있는가.**
> **우리가 그 데이터를 고쳐 쓰는가, 읽기만 하는가.**
> **우리에게 필요한 것이 반복 조회의 속도인가, 붙일 수 있는 소스의 폭인가.**

세 질문의 답이 한 방향이면 선택은 이미 정해져 있다. 갈리면 **4-2 의 함께 쓰는 구성**이 현실적인 답이다.
