## 1. 비교 관점

`C-1-01` 이 "행을 어떻게 합칠 것인가"였다면, 여기는 **"바이트를 어떻게 배치하고 무엇으로 찾을 것인가"** 다.

Trino 에는 자기 스토리지 포맷이 없다. 그러나 **"찾는 것"까지 없는 것은 아니다** — Parquet/ORC 의 통계와 블룸필터, Iceberg 의 매니페스트 통계를 쓴다. 그래서 이 문서의 비교는 "있다/없다"가 아니라 **"얼마나 많은 종류를, 누가 만드는가"** 가 된다.

결론부터: **자동으로 붙는 것은 비슷하고, 사용자가 선언하는 것에서 격차가 크다.** 그리고 StarRocks 의 화려한 인덱스 목록 중 **둘(GIN·VECTOR)은 4.0.14 에서 실험 기능이라 기본 비활성**이다 — 실측으로 확인했다.

## 2. StarRocks 구현

### 2-1. 저장 계층이 3단이다

| 단위 | 뜻 |
|---|---|
| **Tablet** | 분산·복제의 단위. 파티션 × 버킷 하나가 태블릿 하나 |
| **Rowset** | 한 번의 적재(트랜잭션)가 만든 데이터 묶음 |
| **Segment** | 실제 컬럼 파일. rowset 안에 여러 개 |

`be/src/storage/` 에 `rowset/`, `rowset_merger.*`, `segment_flush_executor.*`, `tablet_*` 이 있고, `rowset/` 안에 세그먼트 읽기·쓰기와 인덱스 구현이 모여 있다.

**Iceberg 와 대응시키면 이렇다.**

| StarRocks | Iceberg |
|---|---|
| Tablet | (없음 — 파일이 어느 노드에 있는지 개념이 없다) |
| Rowset | 스냅샷이 추가한 파일 집합 |
| Segment | 데이터 파일 (Parquet/ORC) |

**Tablet 에 대응물이 없다는 점이 핵심이다.** Iceberg 는 "이 파일이 어느 노드 것"이라는 개념을 갖지 않는다. 그래서 `B-3-01` 5-3 에서 본 대로 Trino 는 캐시를 위해 스플릿 배정을 인위적으로 고정해야 한다.

### 2-2. 나누는 축이 두 개다 — 파티션과 버킷

```sql
PARTITION BY RANGE(ts) (PARTITION p1 VALUES LESS THAN ('2026-02-01'), ...)
DISTRIBUTED BY HASH(id) BUCKETS 3
```

- **파티션** — 잘라내기(pruning)용. 보통 시간
- **버킷** — 분산과 조인용. 해시

Iceberg 는 **파티션 하나뿐**이다(변환 함수로 `bucket(N, col)` 을 쓸 수 있지만 그것도 파티션 스펙의 일부다). StarRocks 는 두 축을 명시적으로 분리했고, **버킷이 조인 전략과 직접 연결된다** — `A-2-02` 5-1 의 `COLOCATE` / `BUCKET_SHUFFLE` 분배 방식이 이 버킷을 쓴다.

### 2-3. 자동으로 붙는 인덱스

| 인덱스 | 구현 | 성격 |
|---|---|---|
| **Prefix (short key)** | `storage/short_key_index.cpp` | 정렬 키 앞부분으로 블록을 찾는다 |
| **ZoneMap** | `storage/rowset/zone_map_index.cpp` | 블록별 min/max/null — `A-5-02` 의 그 통계 |
| **Bloom filter** | `storage/rowset/bloom_filter_index_*` | 테이블 속성 `bloom_filter_columns` 로 지정 |

Prefix 와 ZoneMap 은 **선언 없이 붙는다.**

### 2-4. 선언하는 인덱스는 4종

```antlr
indexType
    : USING (BITMAP | GIN | NGRAMBF | VECTOR)
```
— `fe/fe-core/src/main/antlr/StarRocks.g4:577-578`

| 종류 | 용도 | 구현 |
|---|---|---|
| `BITMAP` | 저카디널리티 등호 필터 | `storage/rowset/bitmap_index_*` |
| `NGRAMBF` | `LIKE '%...%'` 가속 | n-gram 블룸필터 |
| `GIN` | **전문 역색인** | `storage/index/inverted/clucene` (CLucene) |
| `VECTOR` | **벡터 근사 최근접 탐색** | `storage/index/vector/tenann` (TenANN) |

**`GIN` 과 `VECTOR` 는 Trino 진영에 대응물이 아예 없다.** 전문 검색과 벡터 검색을 SQL 엔진 안에서 한다는 발상 자체가 스토리지를 소유해야 가능하다.

다만 4절에서 보듯 **둘 다 4.0.14 에서 실험 기능**이다.

## 3. Trino 쪽의 대응물

**"인덱스가 없다"는 부정확하다.** 파일 포맷과 테이블 포맷이 제공하는 것을 쓴다.

| 계층 | 무엇이 있는가 |
|---|---|
| **Iceberg 매니페스트** | 파일별 컬럼 min/max, null 개수 → **파일 단위 프루닝**(`A-5-02` 4-5 에서 75/80 으로 확인) |
| **Iceberg 파티션 스펙** | 변환 함수(`month`, `bucket`, `truncate`)로 파티션 프루닝 |
| **Parquet 블룸필터** | `BloomFilterStore.java` — 읽기 지원 |
| **Parquet/ORC 통계** | row group / stripe 단위 min/max |
| **Iceberg Puffin** | `IcebergThetaSketchForStats.java` — NDV 스케치(`A-2-07`) |

쓰기 시 블룸필터도 지정할 수 있다.

```java
public static final String ORC_BLOOM_FILTER_COLUMNS_PROPERTY = "orc_bloom_filter_columns";
public static final String ORC_BLOOM_FILTER_FPP_PROPERTY = "orc_bloom_filter_fpp";
public static final String PARQUET_BLOOM_FILTER_COLUMNS_PROPERTY = "parquet_bloom_filter_columns";
```
— `plugin/trino-iceberg/.../IcebergTableProperties.java:75-77`

**즉 min/max·블룸필터 계층은 대등하다.** 없는 것은 **비트맵·n-gram·전문·벡터** 네 가지, 그리고 **정렬 키 기반 prefix 인덱스**다.

Iceberg 에도 정렬 순서(`sort_order`)는 있어 파일 안을 정렬해 둘 수 있으나, **그 정렬을 이용하는 전용 인덱스 구조는 없다** — min/max 가 좁아지는 간접 효과만 얻는다.

## 4. 실측

### 4-1. 인덱스 선언은 실제로 된다

```sql
CREATE TABLE t_idx (
  id BIGINT, cat VARCHAR(20), txt VARCHAR(200), ts DATETIME,
  INDEX idx_cat (cat) USING BITMAP,
  INDEX idx_txt (txt) USING NGRAMBF ('gram_num'='4','bloom_filter_fpp'='0.05')
) DUPLICATE KEY(id)
PARTITION BY RANGE(ts) (PARTITION p1 VALUES LESS THAN ('2026-02-01'),
                        PARTITION p2 VALUES LESS THAN ('2026-03-01'))
DISTRIBUTED BY HASH(id) BUCKETS 3
PROPERTIES('replication_num'='1','bloom_filter_columns'='cat');
```

`SHOW INDEX FROM t_idx` 결과다.

| Key_name | Column | Index_type |
|---|---|---|
| `idx_cat` | `cat` | `BITMAP` |
| `idx_txt` | `txt` | `NGRAMBF("bloom_filter_fpp" = "0.05", "case_sensitive" = "true", "gram_num" = "4")` |

**파티션 2개 × 버킷 3개**도 함께 만들어졌다(`SHOW PARTITIONS` → `p1`, `p2`). 한 문장에 **인덱스 2종 + 블룸필터 + 파티션 + 버킷**을 다 넣을 수 있다.

### 4-2. GIN 과 VECTOR 는 기본 비활성이다

```
ERROR 1064: The inverted index is disabled, enable it by setting
FE config `enable_experimental_gin` to true.
```

```
ERROR 1064: The vector index is disabled, enable it by setting
FE config `enable_experimental_vector` to true.
```

**둘 다 실험 기능으로 잠겨 있다.** 이 사실을 확인하지 않았다면 "StarRocks 는 전문 검색과 벡터 검색을 지원한다"고 쓸 뻔했다 — **틀린 서술은 아니지만 운영에 쓸 수 있다는 인상을 준다.**

### 4-3. 재지 못한 것

**인덱스가 실제로 얼마나 걷어내는지 재지 않았다.** 데이터를 채우고 프로파일로 `BitmapIndexFilterRows` 같은 카운터를 봐야 하는데, 이 문서 범위를 넘는다고 판단했다.

`A-5-02` 에서 **Iceberg 쪽 min/max 프루닝은 실측**했다(`o_orderkey < 1000` 에서 80→75 파일). 두 엔진의 같은 계층은 그 문서가 다룬다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| 저장 단위 | 스냅샷 → 데이터 파일 | **Tablet → Rowset → Segment** |
| 노드 소속 | **없음** | Tablet 이 노드에 속한다 |
| 나누는 축 | 파티션(변환 함수 포함) | **파티션 + 버킷 2축** |
| min/max | Iceberg 매니페스트 + 파일 내부 통계 | ZoneMap |
| 블룸필터 | Parquet/ORC (읽기·쓰기 지원) | `bloom_filter_columns` |
| 정렬 키 인덱스 | 없음(정렬 순서만) | **Prefix(short key) 인덱스** |
| 비트맵 | **없음** | `USING BITMAP` |
| n-gram | **없음** | `USING NGRAMBF` |
| 전문 검색 | **없음** | `USING GIN` — **실험 기능, 기본 꺼짐** |
| 벡터 검색 | **없음** | `USING VECTOR` — **실험 기능, 기본 꺼짐** |
| NDV 스케치 | **Iceberg Puffin**(`A-2-07`) | 자체 통계 테이블 |

### 5-2. Tablet 이 만드는 차이

**Tablet 은 "데이터가 노드에 속한다"는 개념**이고, 여기서 세 가지가 파생된다.

1. **조인에서 셔플을 생략할 수 있다** — 같은 키로 버킷팅한 두 테이블은 셔플 없이 조인한다(`A-2-02` 의 `COLOCATE`/`BUCKET_SHUFFLE`)
2. **캐시 배정 문제가 없다** — `B-3-01` 5-3 에서 Trino 가 인위적으로 만들어야 했던 것
3. **노드를 늘리면 데이터를 옮겨야 한다** — 대가다. Trino 워커는 그냥 늘리면 된다

**즉 Tablet 은 성능과 탄력성을 맞바꾼 설계다.**

### 5-3. 인덱스 종류가 많다는 것의 이면

StarRocks 의 인덱스 목록은 화려하지만, 실측이 두 가지를 보여준다.

- **둘은 실험 기능이다**(GIN, VECTOR). 운영에서 쓰려면 FE 설정을 바꿔야 하고, 그것은 곧 **아직 안정성을 보장하지 않는다**는 뜻이다
- **나머지도 사용자가 선택해야 한다.** 어느 컬럼에 비트맵을 걸지, n-gram 을 걸지는 워크로드를 알아야 정한다. **잘못 걸면 저장 공간과 적재 시간만 늘어난다**

Trino 쪽은 선택지가 적은 대신 **고민할 것도 적다.** min/max 는 자동이고 블룸필터만 정하면 된다.

**"인덱스가 많다"를 곧바로 우위로 읽으면 안 된다.** 운영 인력이 그것을 설계할 수 있어야 이득이 된다.

### 5-4. 그러나 없는 것은 정말 없다

공정하게 말해, **비트맵·n-gram·전문·벡터는 Trino 진영에서 흉내 낼 수 없다.**

- 저카디널리티 등호 필터를 자주 쓴다면 비트맵 인덱스의 이득이 크다
- `LIKE '%foo%'` 는 Iceberg 통계로 전혀 걸러지지 않는다. n-gram 블룸필터만이 답이다
- 전문 검색·벡터 검색은 Trino 에서 **다른 시스템(Elasticsearch, 벡터 DB)을 붙여** 해결해야 한다 — 커넥터로 연결은 되지만 같은 테이블 안에서 하는 것과는 다르다

## 6. 결론

**자동 계층은 대등하고, 선언 인덱스에서 격차가 크다. 다만 그중 둘은 아직 실험 기능이다.**

- **min/max·블룸필터**: 양쪽 다 있다. `A-5-02` 에서 Iceberg 쪽 파일 프루닝을 실측했다
- **StarRocks 만**: Prefix 인덱스, 비트맵, n-gram, (실험) 전문, (실험) 벡터
- **구조**: StarRocks 는 Tablet/Rowset/Segment 3단 + 파티션·버킷 2축. Iceberg 는 스냅샷/파일 + 파티션 1축
- **Tablet 의 존재**가 셔플 생략과 캐시 배정 이점을 낳고, 대신 노드 증감 시 데이터 이동 비용을 만든다

**실무 결론**

1. **`LIKE '%...%'` 검색이 잦다면 StarRocks 의 n-gram 인덱스가 유일한 답이다.** Iceberg 통계로는 전혀 걸러지지 않는다
2. **전문 검색·벡터 검색을 SQL 엔진 안에서 하려는 계획이라면 4.0.14 에서는 실험 기능임을 감안하라.** FE 설정을 바꿔야 하고 안정성 보장이 없다
3. **조인 대상을 같은 키로 버킷팅해 두면 StarRocks 가 셔플을 생략한다.** 설계 시점에 정해야 하는 결정이다
4. **인덱스를 많이 걸수록 좋은 것이 아니다.** 저장 공간과 적재 시간이 늘고, 워크로드를 모르면 헛돈다
5. **Trino 쪽에서는 파티션 설계와 정렬 순서가 사실상 유일한 튜닝 수단이다.** 그만큼 파티션을 잘 잡는 것이 중요하다

### 아직 답하지 않은 것

- **인덱스의 실효** — 비트맵·n-gram 이 실제로 얼마나 걷어내는지 재지 않았다. 데이터를 채우고 프로파일 카운터를 봐야 한다
- **인덱스의 비용** — 저장 공간 증가와 적재 지연을 측정하지 않았다
- **Prefix 인덱스** — 정렬 키 설계가 조회에 미치는 영향을 확인하지 않았다. StarRocks 튜닝의 핵심 중 하나인데 다루지 못했다
- **버킷 수 선택** — `BUCKETS 3` 으로만 시험했다. 적정 버킷 수 산정은 다루지 않았다
- **GIN·VECTOR 를 켰을 때의 동작** — 실험 플래그를 켜지 않았다. 랩을 불안정하게 만들 위험이 있다고 판단했다
- **Trino 블룸필터의 실효** — `parquet_bloom_filter_columns` 를 시험하지 않았다. `A-5-02` 4-5 에서 min/max 만 확인했다
- **compaction 이 인덱스를 어떻게 다루는가** — `C-1-03`
