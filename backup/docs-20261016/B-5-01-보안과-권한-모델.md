# B-5 운영 (5) — 보안과 권한 모델

> 비교 축: `plan/01-비교항목-정리.md` B-5 "Access Control SPI + Ranger/OPA vs 내장 RBAC"
> 기준 버전: **Trino 483** / **StarRocks 4.0.14**
> 런타임 증거: 4절 (StarRocks RBAC 강제 확인). Trino 쪽은 랩에 접근제어가 구성돼 있지 않아 미검증
> 일자: 2026-09-04

> ### ⚠ `plan/01` 전제 보완
> `plan/01` 은 StarRocks 쪽을 **"내장 RBAC"** 으로만 적었다. **Apache Ranger 통합이 있다.**
> `fe/fe-core/.../authorization/ranger/` 에 `RangerStarRocksAccessController` 와
> **`RangerHiveAccessController`** 까지 들어 있다 — 외부 정책 엔진 연동이 Trino 만의 것이 아니다.
> 다만 **OPA 대응물은 없다**(전체 검색 0건). 3절 참조.

---

## 1. 비교 관점

권한 모델은 세 질문으로 나뉜다.

1. **누구인가** — 인증
2. **무엇을 할 수 있는가** — 인가, 그리고 그 판단을 **누가** 하는가
3. **얼마나 잘게 나뉘는가** — 테이블 단위인가, 행·열 단위인가

결론부터: **판단 주체의 위치가 다르다.** Trino 는 인가 판단을 **SPI 뒤로 완전히 밀어냈고**(내장 정책도 플러그인이다), StarRocks 는 **FE 안에 RBAC 을 갖고 있으면서 외부 엔진도 붙일 수 있다.** 검사 지점의 세밀함은 **Trino 가 2.7배** 많다(84 vs 31).

---

## 2. Trino 구현

### 2-1. 인가가 전부 SPI 다

`core/trino-spi/src/main/java/io/trino/spi/security/` 에 26개 파일이 있고, 중심은 `SystemAccessControl` 이다. **`default` 검사 메서드가 84개**다.

검사 지점이 그만큼 잘게 나뉜다는 뜻이다 — 카탈로그·스키마·테이블·컬럼·뷰·MV·함수·프로시저·세션 프로퍼티·시스템 정보·쿼리 조회/종료·역할·사용자 가장(impersonation)까지.

행·열 보안도 SPI 항목이다.

```java
default List<ViewExpression> getRowFilters(SystemSecurityContext context, CatalogSchemaTableName tableName)
```
— `core/trino-spi/.../security/SystemAccessControl.java:1067`

```java
default Map<ColumnSchema, ViewExpression> getColumnMasks(SystemSecurityContext context, CatalogSchemaTableName tableName, List<ColumnSchema> columns)
```
— `SystemAccessControl.java:1128`

**반환 타입이 `ViewExpression` 이라는 점이 중요하다.** 정책이 "허용/거부" 불리언이 아니라 **SQL 표현식**이고, 옵티마이저가 그것을 쿼리에 합성한다. 열 마스킹은 컬럼을 표현식으로 바꾸고, 행 필터는 술어로 붙는다.

### 2-2. 정책 엔진이 플러그인이다

| 플러그인 | 내용 |
|---|---|
| `plugin/trino-ranger` | Apache Ranger 연동 |
| `plugin/trino-opa` | **Open Policy Agent 연동** |
| (내장) 파일 기반 | 규칙 JSON |

**OPA 연동이 Trino 쪽에만 있다.** 정책을 Rego 로 쓰고 외부 서비스가 판단한다 — 쿠버네티스 등 다른 인프라와 정책 언어를 통일하려는 조직에 의미가 있다.

### 2-3. 인증도 다층이다

`core/trino-main/.../server/security/` 에 `KerberosAuthenticator`, `PasswordAuthenticator`, `CertificateAuthenticator`, `HeaderAuthenticator`, `AbstractBearerAuthenticator`(JWT/OAuth2) 가 있고, 설정이 **순서 있는 목록**이다.

```java
@Config("http-server.authentication.type")
@ConfigDescription("Ordered list of authentication types")
```
— `core/trino-main/.../server/security/SecurityConfig.java:58-59`

**여러 방식을 순서대로 시도한다.** `PasswordAuthenticator` 와 `HeaderAuthenticator` 는 SPI 라 플러그인으로 확장된다.

## 3. StarRocks 구현

### 3-1. RBAC 이 FE 안에 있다

`fe/fe-core/.../authorization/` 에 39개 파일. `AuthorizationMgr`, `PrivilegeCollectionV2`, `PrivilegeType`, `ObjectType` 과 객체별 `*PEntryObject`(카탈로그·DB·테이블·함수·MV·리소스그룹·파이프·정책) 가 있다.

**메타데이터의 일부로 저장되고 저널로 복제된다**(`B-4-01` 2-1). 즉 권한이 클러스터 상태다 — Trino 처럼 외부 설정 파일이나 서비스에 의존하지 않는다.

`AccessController` 의 검사 메서드는 **31개**다. Trino 의 84개와 비교하면 **덜 잘게 나뉜다.**

### 3-2. 외부 정책 엔진도 붙는다 — Ranger

```java
public abstract class ExternalAccessController implements AccessController {
```
— `fe/fe-core/.../authorization/ExternalAccessController.java:16`

구현이 `authorization/ranger/` 에 있다.

| 파일 | 역할 |
|---|---|
| `RangerAccessController.java` | 공통 |
| `starrocks/RangerStarRocksAccessController.java` | StarRocks 서비스 정의로 판단 |
| **`hive/RangerHiveAccessController.java`** | **Hive 서비스 정의를 그대로 재사용** |

세 번째가 실무적으로 중요하다. **이미 Hive/Ranger 로 관리하던 정책을 StarRocks 가 그대로 읽는다.** 기존 레이크 권한 체계를 다시 만들지 않아도 된다.

**OPA 대응물은 없다.** `fe-core` 전체에서 OPA 를 대소문자 무시로 검색해 0건이다.

### 3-3. 행·열 보안은 정책 엔진에서 온다

```java
Map<String, Expr> maskingExprMap = Authorizer.getColumnMaskingPolicy(context, tableName, validColumns);
Expr rowAccessExpr = Authorizer.getRowAccessPolicy(context, tableName);
```
— `fe/fe-core/.../authorization/SecurityPolicyRewriteRule.java:57-58`

Trino 와 **똑같은 발상**이다 — 정책을 표현식으로 받아 쿼리에 합성한다(마스킹은 select 항목 치환, 행 접근은 술어).

다만 **정책을 만드는 SQL 문장이 없다.** 문법에서 `POLICY`/`POLICIES` 는 비예약어 목록에만 나오고 `CREATE MASKING POLICY` 같은 문장이 없다. 즉 **행·열 정책은 Ranger 를 통해서만 들어온다.**

### 3-4. 인증

`fe/fe-core/.../authentication/` 에 `PlainPasswordAuthenticationProvider`, `LDAPAuthProvider`, `JWTAuthenticationProvider`, `OAuth2AuthenticationProvider` 가 있고, 그룹 제공자도 파일/LDAP 두 가지다(`FileGroupProvider`, `LDAPGroupProvider`).

**MySQL 프로토콜을 쓰기 때문에** 기존 MySQL 클라이언트·BI 도구의 인증 방식을 그대로 쓸 수 있다는 부수 효과가 있다(`A-1-01` 의 MySQL 호환 지향과 같은 뿌리).

## 4. 실측

### 4-1. StarRocks RBAC 은 실제로 강제된다

```sql
CREATE USER probe_user IDENTIFIED BY '...';
SET CATALOG iceberg;
GRANT SELECT ON TABLE bench.nation TO USER probe_user;
```

그 사용자로 직접 접속해 두 테이블을 조회했다.

| 대상 | 결과 |
|---|---|
| `iceberg.bench.nation` (부여됨) | **25** |
| `iceberg.bench.lineitem` (미부여) | ✗ 거부 |

```
ERROR 5203 (42000): Access denied; you need (at least one of) the SELECT privilege(s)
on TABLE lineitem for this operation. Please ask the admin to grant permission(s) or
try activating existing roles using <set [default] role>.
Current role(s): NONE. Inactivated role(s): NONE.
```

**오류가 진단 정보를 담고 있다** — 필요한 권한, 대상, 그리고 **현재 활성 역할과 비활성 역할**까지. "역할은 있는데 활성화하지 않았다"는 흔한 상황을 바로 짚어 준다.

부여 전에는 같은 사용자가 `nation` 조회도 거부됐다. **기본이 거부**임이 확인된다.

### 4-2. Trino 쪽은 검증하지 못했다

랩의 코디네이터에 `access-control.properties` 가 **없다.** 즉 기본값(`allow-all`)이라 **권한 검사 자체가 일어나지 않는다.**

이는 랩 구성의 한계이지 Trino 의 특성이 아니다. `plan/02` 의 랩 설계가 기능 비교를 목적으로 해 접근제어를 구성하지 않았다.

**따라서 2절은 전부 코드 독해다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 인가 판단 위치 | **전부 SPI** — 내장 정책도 플러그인 | **FE 내장 RBAC** + 외부 연동 선택 |
| 권한 저장 | 설정 파일 / 외부 서비스 | **메타데이터**(저널로 복제) |
| 검사 지점 수 | **84** | 31 |
| 외부 정책 엔진 | **Ranger + OPA** | **Ranger** (Hive 서비스 정의 재사용 포함) |
| 행 필터 / 열 마스킹 | SPI 항목, `ViewExpression` 합성 | 같은 방식 — 단 **정책 생성 SQL 없음**(Ranger 경유) |
| 인증 | Kerberos/LDAP/JWT/OAuth2/인증서/헤더, **순서 있는 다중** + SPI | 암호/LDAP/JWT/OAuth2 |
| 랩 기본값 | `allow-all`(설정 없으면 검사 없음) | **거부**(실측) |

### 5-2. 권한이 어디에 사는가

**Trino 의 권한은 클러스터 밖에 산다.** 설정 파일이거나 Ranger/OPA 서비스다. 클러스터를 새로 띄워도 권한은 그대로 따라온다 — `B-4-01` 3-1 에서 본 "코디네이터 이중화 대신 클러스터 이중화" 전략과 잘 맞는다.

**StarRocks 의 권한은 클러스터 안에 산다.** 메타데이터의 일부이고 FE 저널로 복제된다. 클러스터가 곧 권한 경계다.

**이 차이가 다중 클러스터 운영에서 드러난다.** Trino 는 여러 클러스터에 같은 정책을 자연스럽게 적용하고, StarRocks 는 클러스터마다 권한을 따로 관리하거나 Ranger 로 밀어내야 한다.

### 5-3. 84 대 31 — 세밀함의 대가

Trino 의 검사 지점이 2.7배 많은 것은 **커넥터 다양성 때문**이다(`A-5-01`·`C-2-01`). 카탈로그마다 성격이 다르고 프로시저·테이블 함수·언어 함수까지 있으니 검사할 동작이 그만큼 많다.

StarRocks 는 대상이 좁아(10종 커넥터 + 네이티브 테이블) 31개로 덮인다.

**세밀함이 항상 이득은 아니다.** 검사 지점이 많다는 것은 **정책을 그만큼 많이 써야 한다**는 뜻이기도 하다. 다만 "이 동작만 막고 싶다"가 되는 것은 Trino 쪽이다.

### 5-4. Ranger Hive 재사용이 뜻하는 것

`RangerHiveAccessController` 는 StarRocks 가 **레이크하우스 생태계에 후발로 들어왔다는 사실**을 그대로 보여준다. 이미 Hive/Ranger 로 관리되던 데이터를 읽으러 왔으니, **기존 정책을 그대로 존중하는 것이 채택의 전제**다.

Trino 도 같은 문제를 갖지만 답이 다르다 — Ranger 플러그인을 두되 **커넥터별로 정책을 매핑**한다. 그리고 OPA 라는 다른 선택지를 함께 제공한다.

### 5-5. 기본값이 반대다

**Trino 는 설정하지 않으면 검사하지 않는다.** `access-control.properties` 가 없으면 `allow-all` 이다(4-2 에서 랩이 그 상태였다).

**StarRocks 는 설정하지 않아도 거부한다.** 새 사용자는 아무 권한이 없다(4-1).

`B-3-01` 5-2 의 캐시 기본값과 **방향이 반대**라는 점이 흥미롭다 — 캐시는 StarRocks 가 켜 두고 Trino 가 꺼 두는데, 권한은 StarRocks 가 잠가 두고 Trino 가 열어 둔다. 각자 **"운영자가 반드시 결정해야 하는 것"** 을 다르게 본 결과다.

## 6. 결론

**동등하지 않다 — 다만 격차가 아니라 위치의 차이에 가깝다.**

- **판단 주체**: Trino 는 전부 SPI 뒤(내장 정책도 플러그인), StarRocks 는 FE 내장 + 외부 선택
- **외부 정책 엔진**: 양쪽 다 **Ranger 를 지원한다.** `plan/01` 의 "내장 RBAC 뿐"은 정정이 필요하다. **OPA 는 Trino 만**
- **세밀함**: 검사 지점 84 vs 31. 커넥터 다양성 차이에서 나온다
- **행·열 보안**: 발상이 같다(표현식 합성). StarRocks 는 **정책 생성 SQL 이 없어 Ranger 가 사실상 필수**
- **기본값**: Trino 는 열려 있고 StarRocks 는 잠겨 있다(실측)

**실무 결론**

1. **Trino 를 운영에 쓴다면 `access-control.properties` 설정 여부를 가장 먼저 확인하라.** 없으면 아무나 무엇이든 할 수 있다
2. **기존 Hive/Ranger 정책이 있다면 StarRocks 의 `RangerHiveAccessController` 가 이전 비용을 크게 줄인다.** 정책을 다시 만들 필요가 없다
3. **행·열 수준 보안이 요건이면 StarRocks 는 Ranger 가 사실상 필수다.** 내장 RBAC 만으로는 테이블 단위까지다
4. **정책을 Rego 로 통일하려는 조직이라면 OPA 를 지원하는 Trino 가 유일한 선택이다**
5. **다중 클러스터를 운영한다면 Trino 쪽이 유리하다.** 권한이 클러스터 밖에 있어 자연스럽게 공유된다

### 아직 답하지 않은 것

- **Trino 쪽 실측 전무** — 랩에 접근제어가 구성돼 있지 않다. 2절은 전부 코드 독해다
- **Ranger 연동의 실제 동작** — 양쪽 다 Ranger 서버가 없어 확인하지 못했다. 특히 `RangerHiveAccessController` 가 Hive 정책을 얼마나 충실히 해석하는지 모른다
- **행 필터·열 마스킹의 실측** — 정책 엔진이 없어 시험하지 못했다
- **성능 영향** — 검사 지점이 84개라는 것은 계획 시점 오버헤드를 뜻할 수 있다. 재지 않았다
- **감사 로그** — 누가 무엇을 했는지 기록하는 계층은 `B-6-01`
- **전송 구간 암호화** — Trino 는 HTTP 위라 TLS 가 자연스럽지만(`A-4-01`), StarRocks 의 FE-BE / BE-BE BRPC 구간은 확인하지 않았다
