## 1. 비교 관점

셔플은 분산 쿼리에서 **유일하게 노드 경계를 넘는 지점**이다. 여기서 실패하면 쿼리가 죽고, 여기서 막히면 상류 전체가 멈춘다.

세 가지를 본다.

1. **전송 프로토콜** — 무엇으로 보내는가
2. **누가 주도하는가** — 받는 쪽이 가져가는가(pull), 보내는 쪽이 밀어넣는가(push)
3. **막혔을 때 어떻게 세우는가** — 배압 기법

결론부터: **Trino 는 HTTP pull, StarRocks 는 BRPC push 다.** 그리고 이 선택이 배압 구현을 결정한다 — pull 에서는 배압이 프로토콜에 공짜로 딸려 오고, push 에서는 **응답을 일부러 붙잡아** 만들어야 한다.

---

## 2. 검증 가능성 — 먼저 밝힌다

**이 문서에는 실측이 없다.**

현재 랩은 Trino worker 1대 / StarRocks BE 1대다. 셔플은 노드가 둘 이상일 때만 네트워크를 탄다. 1노드에서는 로컬 교환으로 끝나므로, **전송 계층을 지나가는 경로 자체가 생기지 않는다.**

`docs/00-목차.md` 의 "검증 가능성의 한계"에 따라 이 문서는 **코드 비교와 설계 차이까지만** 쓰고 성능 결론을 내지 않는다. 아래 모든 서술은 소스 독해다.

## 3. Trino 구현

### 3-1. HTTP 위에서 받는 쪽이 가져간다

교환 클라이언트가 상류 태스크의 출력 버퍼에 **HTTP GET 을 건다.**

```java
import io.airlift.http.client.HttpClient;
```
— `core/trino-main/.../operator/HttpPageBufferClient.java:26`

```java
import static io.airlift.http.client.Request.Builder.prepareDelete;
import static io.airlift.http.client.Request.Builder.prepareGet;
```
— `HttpPageBufferClient.java:69-70`

`sendGetResults()`(`:354`)가 GET 을 보내고, 다 쓴 페이지는 `prepareDelete` 로 지운다. **받는 쪽이 주도한다.**

응답 본문의 형식은 전용 미디어 타입으로 못박혀 있다.

```java
if (!mediaTypeMatches(contentType.orElseThrow(), TRINO_PAGES_TYPE)) {
    throw new PageTransportErrorException(fromUri(uri), format("Expected %s response from server but got %s", TRINO_PAGES_TYPE, contentType.orElseThrow()));
}
```
— `HttpPageBufferClient.java:708-709`

즉 **HTTP 는 운반 수단이고 내용물은 직렬화된 `Page`** 다(`A-3-01` 의 그 `Page`). 범용 JSON 이 아니다.

### 3-2. 배압은 프로토콜에 딸려 온다

```java
private DataSize maxBufferSize = DataSize.of(32, Unit.MEGABYTE);
private int concurrentRequestMultiplier = 3;
private Duration maxErrorDuration = new Duration(1, TimeUnit.MINUTES);
private DataSize maxResponseSize = new HttpClientConfig().getMaxResponseContentLength();
private int clientThreads = 25;
```
— `core/trino-main/.../operator/DirectExchangeClientConfig.java:33-37`

받는 쪽 버퍼가 **32MB** 를 채우면 **GET 을 더 보내지 않는다.** 그러면 상류의 출력 버퍼(`sink.max-buffer-size`, 역시 **32MB** — `TaskManagerConfig.java:72`)가 차고, 그 위의 연산자가 멈춘다.

**배압을 위한 별도 장치가 없다.** "안 물어보면 안 온다"가 곧 배압이다. pull 모델의 구조적 이점이다.

`concurrentRequestMultiplier = 3` 은 반대 방향 조절이다 — 버퍼에 여유가 있으면 여러 상류에 동시에 GET 을 건다.

### 3-3. HTTP 를 쓴 대가

- **오버헤드** — 요청마다 헤더가 붙고, 페이지를 모아 응답으로 만드는 왕복이 생긴다
- **폴링 지연** — 데이터가 준비되기 전에 GET 이 도착하면 롱폴링으로 기다린다
- **얻는 것** — 재시도·타임아웃·오류 분류가 HTTP 계층의 성숙한 도구로 처리된다. `maxErrorDuration = 1분` 동안 재시도하다 포기하는 정책이 한 줄이다

이 선택은 `A-3-02`(실행 모델)에서 본 Trino 의 일관된 태도와 같다 — **성숙한 범용 계층 위에 올리고, 그 비용을 감수한다.**

## 4. StarRocks 구현

### 4-1. BRPC 위에서 보내는 쪽이 밀어넣는다

```cpp
#include "service/brpc.h"
#include "util/brpc_stub_cache.h"
```
— `be/src/runtime/data_stream_sender.cpp:58-59`

`DataStreamSender::Channel` 이 목적지마다 BRPC 스텁을 들고 `transmit_chunk` RPC 를 **보낸다.**

```cpp
Status send_chunk_request(PTransmitChunkParams* params, const butil::IOBuf& attachment);
```
— `data_stream_sender.cpp:117`

주목할 것은 **`attachment`** 다. BRPC 의 attachment 는 protobuf 직렬화를 거치지 않고 붙는 바이트 덩어리다. 즉 **메타데이터만 protobuf 로 보내고 실제 청크 데이터는 인코딩 없이 실어 보낸다.** protobuf 인코딩 비용을 피하는 설계다.

수신측은 `DataStreamMgr` 이 fragment instance id 로 `DataStreamRecvr` 을 찾고, `SenderQueue` 가 청크를 쌓는다.

### 4-2. 배압은 "응답을 붙잡아" 만든다

push 모델에는 "안 물어보면 안 온다"가 없다. StarRocks 는 **RPC 응답을 일부러 늦춘다.**

```cpp
if (closure != nullptr) {
    COUNTER_UPDATE(metrics.closure_block_timer, MonotonicNanos() - queue_enter_time);
    // When the execution thread is blocked and the Chunk queue exceeds the memory limit,
    // the execution thread will hold done and will not return, block brpc from sending packets,
    // and the execution thread will call run() to let brpc continue to send packets,
    // and there will be memory release
```
— `be/src/runtime/sender_queue.cpp:167-172`

주석이 기법을 그대로 설명한다 — **큐가 메모리 한도를 넘으면 `done`(closure)을 붙들고 반환하지 않는다.** 송신측 RPC 가 완료되지 않으니 다음 청크를 보내지 못한다. 소비가 진행되면 `closure->Run()` 을 불러 풀어 준다.

`closure_block_timer` 라는 전용 카운터까지 있다 — **배압으로 얼마나 막혔는지를 프로파일에서 볼 수 있다.** Trino 쪽에는 대응하는 단일 지표가 없다(버퍼 사용량으로 간접 판단한다).

버퍼 한도는 교환 노드마다다.

```cpp
CONF_mInt32(exchg_node_buffer_size_bytes, "10485760");
```
— `be/src/common/config.h:285`

**10MB** 다. Trino 의 32MB 와는 세는 단위가 다르므로 직접 비교하면 안 된다 — Trino 는 *교환 클라이언트 하나*가 여러 상류로부터 받는 총량이고, StarRocks 는 *교환 노드 하나*의 큐 한도다.

### 4-3. RPC 계층에도 별도 방어선이 있다

```cpp
// Maximum size of a single message body in all protocols.
CONF_Int64(brpc_max_body_size, "2147483648");
// Max unwritten bytes in each socket, if the limit is reached, Socket.Write fails with EOVERCROWDED.
CONF_Int64(brpc_socket_max_unwritten_bytes, "1073741824");
// brpc connection types, "single", "pooled", "short".
CONF_String_enum(brpc_connection_type, "single", "single,pooled,short");
// If the amount of data to be sent by a single channel of brpc exceeds brpc_socket_max_unwritten_bytes
// it will cause rpc to report an error. We add configuration to ignore rpc overload.
// This may cause process memory usage to rise.
// In the future we need to count the memory on each channel of the rpc. To do application layer rpc flow limiting.
CONF_mBool(brpc_query_ignore_overcrowded, "false");
CONF_mBool(brpc_load_ignore_overcrowded, "true");
```
— `be/src/common/config.h:808-819`

**소켓당 미전송 1GB 한도**를 넘으면 RPC 가 `EOVERCROWDED` 로 실패한다. 그리고 `ignore_overcrowded` 로 그 오류를 무시할 수 있는데, 주석이 대가를 밝힌다 — *"This may cause process memory usage to rise."*

**기본값이 갈린다** — 쿼리는 `false`(무시하지 않음, 즉 실패시킴), 적재는 `true`(무시하고 진행). 적재는 실패 비용이 크니 메모리를 더 쓰더라도 밀고 나가겠다는 판단이다.

마지막 주석이 솔직하다 — *"In the future we need to count the memory on each channel of the rpc. To do application layer rpc flow limiting."* **현재 RPC 계층 흐름 제어가 완성되지 않았음을 개발진이 스스로 적어 두었다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 프로토콜 | **HTTP**(airlift http-client) | **BRPC**(protobuf + attachment) |
| 방향 | **pull** — 받는 쪽이 GET | **push** — 보내는 쪽이 RPC |
| 페이로드 | `TRINO_PAGES_TYPE` 미디어 타입, 직렬화된 `Page` | protobuf 메타 + **attachment 에 청크 바이트** |
| 수신 버퍼 | 교환 클라이언트당 **32MB** | 교환 노드당 **10MB** |
| 송신 버퍼 | 태스크당 **32MB**(`sink.max-buffer-size`) | BRPC 소켓당 미전송 **1GB** |
| 배압 | **프로토콜에 내장** — GET 을 멈추면 끝 | **응답 보류** — closure 를 붙잡아 송신을 막음 |
| 배압 관측 | 버퍼 사용량으로 간접 | `closure_block_timer` **전용 카운터** |
| 과부하 시 | 상류가 자연스럽게 멈춤 | `EOVERCROWDED` 로 **RPC 실패**(쿼리 기본) 또는 무시(적재 기본) |
| 정리 | 사용한 페이지를 `DELETE` | RPC 완료로 암묵 |

### 5-2. pull 과 push 는 각각 무엇을 사는가

**pull(Trino)** — 배압이 공짜다. 받는 쪽이 자기 사정만 알면 되고, 보내는 쪽은 버퍼에 쌓아 두기만 하면 된다. 대신 **왕복이 생긴다.** 데이터가 준비돼 있어도 GET 이 와야 나간다.

**push(StarRocks)** — 지연이 낮다. 준비되는 즉시 나간다. 대신 **배압을 직접 만들어야 하고**, 4-3 에서 본 대로 그 흐름 제어가 아직 완결되지 않았다.

이 트레이드오프는 두 제품의 목표 워크로드와 맞아떨어진다. StarRocks 는 **저지연 대화형 분석**을 겨냥하므로 왕복 한 번이 아깝고, Trino 는 **장시간 배치·페더레이션**이 주 무대라 왕복보다 안정성이 중요하다.

### 5-3. 프로토콜 선택이 언어 선택의 결과이기도 하다

Trino 가 HTTP 를 쓴 것은 JVM 생태계에서 가장 잘 검증된 계층이기 때문이다. airlift 의 http-client 는 Trino 팀이 직접 만든 것이라 통제도 된다.

StarRocks 가 BRPC 를 쓴 것도 같은 논리다 — C++ 진영에서 가장 성숙한 RPC 프레임워크이고, **attachment 라는 인코딩 우회 경로**가 있다. 청크를 protobuf 로 인코딩했다면 `A-3-01` 에서 본 컬럼 표현의 이점이 통신 구간에서 사라졌을 것이다.

**즉 두 엔진 모두 "자기 언어권에서 가장 성숙한 것"을 골랐고, 그 결과가 pull/push 차이로 나타났다.** 어느 쪽이 우월한 선택이라고 말할 근거가 이 자료에는 없다.

## 6. 결론

**동등하지 않다 — 다만 우열이 아니라 지연과 안정성의 교환이다.**

- **Trino**: HTTP pull. 배압이 프로토콜에 내장돼 별도 장치가 필요 없다. 왕복 비용을 치른다
- **StarRocks**: BRPC push. attachment 로 청크를 인코딩 없이 실어 보내 지연이 낮다. 배압을 응답 보류로 직접 구현했고, RPC 계층 흐름 제어는 **개발진 주석 기준 미완성**이다

**실무 결론**

1. **셔플이 많은 대형 쿼리에서 StarRocks 는 `exchg_node_buffer_size_bytes`(10MB) 를 확인할 만하다.** 기본값이 작고, 넘치면 배압으로 막힌다. `closure_block_timer` 로 확인할 수 있다
2. **StarRocks 에서 `brpc_query_ignore_overcrowded=true` 로 바꾸는 것은 신중해야 한다.** 소스 주석이 메모리 상승을 경고한다
3. **Trino 에서 셔플이 병목이면 `exchange.max-buffer-size` 와 `sink.max-buffer-size` 를 함께 올려야 한다.** 둘 중 하나만 올리면 다른 쪽이 새 병목이 된다

### 아직 답하지 않은 것

- **모든 것이 코드 독해다.** 실측이 하나도 없다. 다중 노드 랩이 필요하다(`plan/02` 6-3절)
- **처리량·지연 비교** — 재지 않았다. HTTP 왕복 비용이 실제로 얼마인지, attachment 의 인코딩 우회 이득이 얼마인지 모른다
- **오류 상황** — 노드가 셔플 중에 죽었을 때의 동작을 확인하지 않았다. `B-4-01` 에서 다룬다
- **암호화·인증** — Trino 는 HTTP 위라 TLS 가 자연스럽고, StarRocks 의 BRPC 구간은 확인하지 않았다. `B-5-01` 의 주제에 가깝다
- **셔플 파티셔닝과 디스크 스풀** — `A-4-02`
