## 1. 비교 관점

여기서부터는 **비교가 아니라 부재와 대체 수단**이다. `plan/01` C 절의 성격 그대로다.

Trino 에게 테이블은 **커넥터가 정의한 무엇**이다. Iceberg 테이블은 한 종류이고, 스키마와 파티셔닝만 정할 수 있다. **"같은 키의 행이 또 들어오면 어떻게 할지"를 테이블 정의에 넣을 수단이 없다.**

StarRocks 는 그것을 **네 가지 모델**로 나눠 두었다. 이 선택이 조회 결과 자체를 바꾼다.

이 문서가 답할 질문은 둘이다.

1. **네 모델이 실제로 무엇을 다르게 하는가**
2. **Trino 진영에서 같은 요구를 어떻게 푸는가**

## 2. StarRocks 구현

### 2-1. 모델은 열거형 네 개다

```java
public enum KeysType {
    PRIMARY_KEYS,
    DUP_KEYS,
    UNIQUE_KEYS,
    AGG_KEYS;
```
— `fe/fe-core/.../catalog/KeysType.java:39-43`

```java
    public boolean isAggregationFamily() {
        switch (this) {
            case AGG_KEYS:
            case UNIQUE_KEYS:
                return true;
```
— `KeysType.java:45-49`

**`UNIQUE` 가 집계 계열로 분류된다는 점이 구조를 드러낸다.** `UNIQUE` 는 사실상 "모든 값 컬럼이 `REPLACE` 인 `AGGREGATE`"다. 즉 세 모델(`DUP`/`UNIQUE`/`AGG`)이 한 뿌리이고, **`PRIMARY_KEYS` 만 다른 계열**이다.

### 2-2. `PRIMARY KEY` 는 별도 기계다

`be/src/storage/` 에 이 모델 전용 파일이 몰려 있다.

| 파일 | 역할 |
|---|---|
| `persistent_index.cpp` / `.h` | **키 → 행 위치 매핑을 디스크에 유지** |
| `persistent_index_compaction_manager.*` | 그 인덱스의 병합 관리 |
| `persistent_index_load_executor.*` | 기동 시 인덱스 적재 |
| `del_vector.cpp` / `.h` | **삭제 벡터** — 어떤 행이 지워졌는지 비트맵 |
| `local_primary_key_compaction_conflict_resolver.*` | compaction 중 충돌 해소 |
| `local_primary_key_recover.*` | 인덱스 손상 복구 |

**여섯 갈래의 전용 코드가 붙어 있다.** 다른 세 모델은 이것을 쓰지 않는다.

동작 원리의 차이는 이렇다.

- `UNIQUE`/`AGG` — **읽을 때 합친다**(merge-on-read). 같은 키의 여러 버전이 파일에 남아 있고, 조회 시 정렬·병합한다
- `PRIMARY KEY` — **쓸 때 정한다**(delete-and-insert). 지속 인덱스로 이전 행을 찾아 삭제 벡터에 표시하고 새 행을 넣는다. **조회 시 병합이 없다**

즉 `PRIMARY KEY` 는 **쓰기 비용을 더 치르고 읽기를 빠르게** 하는 선택이다. 그 대가로 인덱스를 메모리·디스크에 유지해야 한다(`B-1-01` 3-1 의 `MemTracker` 항목과 연결된다).

### 2-3. 지속 인덱스가 기본이다

```
"enable_persistent_index" = "true"
```
— `SHOW CREATE TABLE` 출력 (4-4)

인덱스를 메모리에만 두면 테이블이 커질수록 메모리를 잡아먹는다. 디스크에 유지하는 것이 기본값이 된 것은 **대용량 PK 테이블을 상정한 결정**이다.

## 3. Trino 쪽의 대체 수단

Trino 에는 테이블 모델이 없다. 같은 요구를 어떻게 푸는지 정리한다.

| 요구 | StarRocks | Trino + Iceberg |
|---|---|---|
| 중복 그대로 보존 | `DUPLICATE` | **기본 동작** — 그냥 INSERT |
| 같은 키는 최신만 | `UNIQUE` / `PRIMARY KEY` | **`MERGE INTO`** 를 쓸 때마다 실행 |
| 키별 합계/최대 등 사전 집계 | `AGGREGATE` | **MV** 또는 조회 시 집계 |
| 행 수정 | `PRIMARY KEY` 의 `UPDATE` | `UPDATE` / `MERGE`(삭제 파일 생성) |
| 특정 컬럼만 수정 | **부분 컬럼 갱신** | **없음** — 행 전체를 다시 쓴다 |

**핵심 차이는 "언제 정하는가"다.**

- StarRocks 는 **테이블을 만들 때** 규칙을 정하고, 그 뒤의 모든 적재가 자동으로 그 규칙을 따른다
- Trino 는 **쓸 때마다** 규칙을 SQL 로 표현한다(`MERGE INTO ... WHEN MATCHED THEN UPDATE`)

Trino 쪽이 유연하고(같은 테이블에 다른 규칙을 적용할 수 있다) StarRocks 쪽이 안전하다(적재 경로가 여럿이어도 규칙이 깨지지 않는다).

**부분 컬럼 갱신만은 대체 수단이 없다.** Iceberg 는 파일이 불변이라 한 컬럼을 바꾸려면 행 전체를 다시 써야 한다.

## 4. 실측

전문은 `docs/evidence/C-1/20260904-table-model-probes.md`.

네 테이블에 **완전히 같은 입력**을 넣었다.

```sql
INSERT INTO <t> VALUES (1,10,'a'),(1,20,'b'),(2,5,'c');
INSERT INTO <t> VALUES (1,7,'z');
```

### 4-1. 같은 입력, 네 가지 결과

| 모델 | 결과 |
|---|---|
| `DUPLICATE` | `(1,7,z) (1,10,a) (1,20,b) (2,5,c)` — **4행 전부 보존** |
| `UNIQUE` | `(1,7,z) (2,5,c)` — 마지막 쓰기가 이긴다 |
| `PRIMARY KEY` | `(1,7,z) (2,5,c)` — 마지막 쓰기가 이긴다 |
| `AGGREGATE` | **`(1,37,z)`** `(2,5,c)` — `v` 는 SUM(10+20+7), `s` 는 REPLACE |

**`AGGREGATE` 의 37 이 이 표의 요점이다.** 원본 행이 남지 않는다 — 적재 시점에 합쳐지고 되돌릴 수 없다.

### 4-2. `UNIQUE` 와 `PRIMARY KEY` 를 가르는 것

조회 결과가 같으므로 다른 축이 필요했다.

| 모델 | `UPDATE ... SET` | `DELETE` |
|---|---|---|
| `DUPLICATE` | ✗ `table t_dup does not support update` | ✅ |
| `UNIQUE` | ✗ `table t_uni does not support update` | ✅ |
| **`PRIMARY KEY`** | **✅** | ✅ |
| `AGGREGATE` | ✗ `table t_agg does not support update` | ✅ |

**`UPDATE` 를 지원하는 것은 `PRIMARY KEY` 뿐이다.** 2-2 의 구조와 정확히 맞는다 — 지속 인덱스가 있어야 "이 키의 현재 행이 어디 있는지"를 알고 고칠 수 있다.

### 4-3. 부분 컬럼 갱신 — Iceberg 에 없는 것

```sql
INSERT INTO t_pk VALUES (3,1,'x'),(4,2,'y');
SET partial_update_mode='column';
INSERT INTO t_pk (k,v) VALUES (3,555);      -- s 는 지정하지 않는다
```

| k | v | s |
|---|---|---|
| 3 | **555** | **x** |

**`s` 가 `'x'` 로 남았다.** 지정하지 않은 컬럼은 건드리지 않는다.

`A-5-04` 에서 StarRocks 가 Iceberg 에 `UPDATE` 조차 못 하는 것을 확인했는데, **네이티브 테이블에서는 컬럼 단위 갱신까지 된다.** 격차가 이렇게 크다.

### 4-4. 지속 인덱스

`SHOW CREATE TABLE t_pk` 가 `"enable_persistent_index" = "true"` 를 보고한다. 지정하지 않았는데도 켜져 있다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| 테이블 종류 | **1종** | **4종** |
| 중복 규칙 위치 | 쓰는 문장(`MERGE`) | **테이블 정의** |
| 사전 집계 | 없음(MV 로 대체) | **`AGGREGATE` 모델** |
| 행 수정 | `UPDATE`/`MERGE`(삭제 파일) | **`PRIMARY KEY` 만** |
| 부분 컬럼 갱신 | **없음** | **있음** |
| 최신 행 찾기 | 삭제 파일과 병합 | **지속 인덱스**(PK) / 읽기 시 병합(UNIQUE·AGG) |
| 전용 코드 | 커넥터 안 | `be/src/storage/` 6갈래 + FE |

### 5-2. 왜 StarRocks 에만 있는가

**테이블 모델은 스토리지를 소유해야만 만들 수 있다.**

`AGGREGATE` 를 생각해 보면 분명하다 — 적재 시점에 값을 합쳐 버리려면 **쓰기 경로를 통제해야** 한다. Trino 는 쓰기 경로가 커넥터마다 다르고, 애초에 Iceberg 파일 포맷이 "같은 키를 합친다"는 개념을 갖고 있지 않다.

`PRIMARY KEY` 도 마찬가지다. 지속 인덱스는 **BE 가 데이터 파일과 인덱스를 함께 관리해야** 성립한다. 상태 없는 워커에는 둘 곳이 없다.

`A-5-01` 이후 반복돼 온 구도의 가장 선명한 사례다 — **소유하면 할 수 있고, 소유하지 않으면 SPI 로도 만들 수 없다.**

### 5-3. 모델 선택은 되돌리기 어렵다

**테이블을 만들 때 정하고 바꿀 수 없다.** 그리고 `AGGREGATE` 는 원본을 버리므로, 나중에 "원본 행이 필요하다"가 되면 **데이터가 이미 없다.**

Trino 쪽 유연성이 여기서 의미를 갖는다 — Iceberg 테이블은 언제든 다르게 읽고 다르게 병합할 수 있다. **StarRocks 의 모델은 성능을 위해 선택지를 미리 버리는 거래다.**

### 5-4. 다른 축과의 연결

이 문서의 사실은 여러 곳에서 다시 쓰인다.

| 사실 | 어디서 다시 나오는가 |
|---|---|
| `PRIMARY KEY` 만 `UPDATE` 가능 | `A-5-04` — "StarRocks 로 고치려면 네이티브로 옮겨라"의 근거 |
| `AGGREGATE` 의 사전 집계 | `A-2-06` — MV 와 역할이 겹친다. 어느 쪽을 쓸지가 설계 결정 |
| 지속 인덱스의 메모리·디스크 소비 | `B-1-01` — BE 메모리 회계 항목 |
| 모델별 compaction 전략 | `C-1-03` |
| `BITMAP`/`HLL` 컬럼 타입 | `A-1-02` — `AGGREGATE` 모델에서 진가를 발휘한다 |

## 6. 결론

**비교 대상이 아니다 — Trino 에 대응물이 없다.**

- **네 모델이 같은 입력에 네 가지 결과를 낸다**(실측). 중복 보존 / 최신만 / 최신만 / 사전 집계
- **`UPDATE` 를 지원하는 것은 `PRIMARY KEY` 뿐**이고, 그것만 **부분 컬럼 갱신**까지 된다
- **Trino 의 대체 수단은 `MERGE INTO`** 다. 유연하지만 쓸 때마다 규칙을 표현해야 하고, **부분 컬럼 갱신은 아예 불가능**하다
- 이 기능들은 **스토리지를 소유해야만 만들 수 있다.** SPI 로 흉내 낼 수 없는 종류의 격차다

**실무 결론**

1. **잦은 upsert 가 있는 워크로드(CDC 반영, 주문 상태 갱신)라면 StarRocks `PRIMARY KEY` 모델이 명확히 유리하다.** Trino + Iceberg 로 하려면 `MERGE INTO` 를 반복해야 하고 삭제 파일이 쌓인다
2. **부분 컬럼 갱신이 필요하면 선택지가 하나다.** 대체 수단이 없다
3. **`AGGREGATE` 모델은 신중히 고르라.** 원본이 사라진다. 되돌릴 수 없는 결정이다
4. **모델을 고를 때 `UPDATE` 필요 여부를 먼저 물어라.** `UNIQUE` 와 `PRIMARY KEY` 는 조회 결과가 같아 보이지만 `UPDATE` 지원이 갈린다(실측)
5. **StarRocks 를 조회 가속기로만 쓴다면 이 모델들은 쓰지 않게 된다.** 외부 Iceberg 를 읽는 구성에서는 해당 없음이다

### 아직 답하지 않은 것

- **성능** — 어느 모델이 얼마나 빠른지 재지 않았다. 특히 `PRIMARY KEY` 의 쓰기 비용과 `UNIQUE` 의 읽기 병합 비용을 비교해야 실무 선택에 쓸 수 있다(`perf` 프로파일 필요)
- **다중 복제·다중 버킷** — `replication_num=1`, `BUCKETS 1` 로만 시험했다. `PRIMARY KEY` 인덱스가 버킷에 어떻게 분산되는지 모른다
- **`AGGREGATE` 의 다른 집계 함수** — `SUM`/`REPLACE` 만 봤다. `MIN`/`MAX`/`BITMAP_UNION`/`HLL_UNION` 은 시험하지 않았다
- **지속 인덱스의 크기와 메모리 영향** — `B-1-01` 과 이어지는 질문인데 측정하지 않았다
- **모델 변경 가능 여부** — 만든 뒤 바꿀 수 있는지 확인하지 않았다(문서상 불가로 알려져 있으나 검증하지 않음)
- **스토리지 포맷과 인덱스** — `C-1-02`
