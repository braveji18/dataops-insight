## 1. 비교 관점

`A-4-01` 이 "무엇으로 보내는가"였다면 여기는 **"어떻게 나누고, 넘치면 어디에 두는가"** 다.

1. **파티셔닝 종류** — 데이터를 어떤 규칙으로 나눠 보내는가
2. **셔플 데이터가 메모리를 넘으면** — 디스크로 흘리는가, 죽는가
3. **셔플 중 노드가 죽으면** — 다시 만들 수 있는가

세 번째가 이 문서의 핵심이다. Trino 의 **Fault-Tolerant Execution(FTE)** 은 셔플을 **파일로 물질화**해 노드 사망을 태스크 단위 재시도로 흡수한다. StarRocks 에는 대응물이 없다.

결론부터: **파티셔닝 종류는 비슷하고, 스풀과 내결함성에서 갈린다.** Trino 는 셔플을 외부 저장소에 쓰는 경로를 SPI 로 열어 뒀고, StarRocks 의 셔플은 **메모리 스트리밍 전용**이다. 다만 StarRocks 도 **로컬 교환 한 종류에는 스필이 있다.**

## 2. 파티셔닝 종류

### 2-1. 목록

| Trino `SystemPartitioning` | StarRocks `TPartitionType` |
|---|---|
| `SINGLE` — 한 노드로 모음 | `UNPARTITIONED` |
| `FIXED` — 해시로 고정 개수에 분배 | `HASH_PARTITIONED` |
| `SOURCE` — 소스 분할을 그대로 유지 | (스캔 노드가 담당) |
| `ARBITRARY` — 아무 데나(라운드로빈) | `RANDOM` |
| `COORDINATOR_ONLY` — 코디네이터에서만 | (FE 는 실행하지 않음) |
| — | `RANGE_PARTITIONED` — 정렬된 범위 분할 |
| — | `BUCKET_SHUFFLE_HASH_PARTITIONED` — 저장 버킷을 이용 |
| — | `HYBRID_HASH_PARTITIONED` — 일부는 해시, 나머지는 broadcast/random |

Trino 는 위 시스템 파티셔닝 외에 **커넥터가 정의한 파티셔닝**을 쓸 수 있다(`ConnectorPartitioningHandle`, `applyPartitioning`). 즉 목록이 닫혀 있지 않다.

### 2-2. 갈리는 두 항목

**`BUCKET_SHUFFLE_HASH_PARTITIONED`** — 이미 그렇게 나눠 저장해 둔 버킷을 이용해 한쪽만 셔플하는 방식이다. `A-2-02` 5-1 에서 다룬 `JoinNode.DistributionMode` 6종의 그 항목이고, **스토리지를 소유하기 때문에 가능하다.**

```
// unordered partition on a set of exprs
// (only use in bucket shuffle join)
BUCKET_SHUFFLE_HASH_PARTITIONED,

// Part of the data is hashed, and the other part is broadcast or randomly sent
HYBRID_HASH_PARTITIONED
```
— `gensrc/thrift/Partitions.thrift:55-60`

**`HYBRID_HASH_PARTITIONED`** — 주석대로 데이터의 일부는 해시로, 나머지는 broadcast 또는 random 으로 보낸다. 데이터 쏠림(skew)에 대응하는 장치다. **Trino 의 시스템 파티셔닝에는 대응물이 없다.**

반대로 **`COORDINATOR_ONLY`** 는 Trino 에만 있다. 코디네이터에서만 돌아야 하는 연산(일부 DDL, 시스템 테이블)을 위한 것으로, StarRocks 는 FE 가 쿼리를 실행하지 않으므로 개념 자체가 필요 없다.

버킷 함수도 명시돼 있다.

```
enum TBucketFunction {
  NATIVE,
  MURMUR3_X86_32
}
```
— `Partitions.thrift:70-73`

`MURMUR3_X86_32` 는 Iceberg/Spark 의 버킷 변환과 맞추기 위한 것이다 — 외부 테이블의 버킷을 그대로 활용하려는 의도로 읽힌다.

## 3. 셔플이 메모리를 넘을 때

### 3-1. Trino — 두 가지 모드가 있다

**기본(`retry-policy=NONE`)에서 셔플은 메모리 스트리밍**이다. `A-4-01` 3-2 에서 본 32MB 버퍼가 차면 배압으로 상류를 세운다. 디스크로 흘리지 않는다.

**FTE(`retry-policy=TASK` 또는 `QUERY`)를 켜면 완전히 달라진다.**

```java
@Config("retry-policy")
```
— `core/trino-main/.../execution/QueryManagerConfig.java:617`

```java
public enum RetryPolicy
{
    TASK(RetryMode.RETRIES_ENABLED),
    QUERY(RetryMode.RETRIES_ENABLED),
    NONE(RetryMode.NO_RETRIES),
```
— `core/trino-main/.../operator/RetryPolicy.java:18-23`

FTE 에서는 셔플 데이터가 **외부 저장소에 파일로 쓰인다.** 그 저장소 인터페이스가 SPI 다.

`core/trino-spi/src/main/java/io/trino/spi/exchange/` — `Exchange`, `ExchangeManager`, `ExchangeSink`, `ExchangeSource`, `ExchangeSourceHandle` 등 **14개 인터페이스**. 구현체는 플러그인이다.

| 플러그인 | 대상 |
|---|---|
| `plugin/trino-exchange-filesystem` | 로컬 디스크 / S3 / GCS / Azure |
| `plugin/trino-exchange-hdfs` | HDFS |

설정은 이렇다.

```java
private DataSize maxPageStorageSize = DataSize.of(16, MEGABYTE);
private int exchangeSinkBufferPoolMinSize = 10;
private int exchangeSinkBuffersPerPartition = 2;
private DataSize exchangeSinkMaxFileSize = DataSize.of(1, GIGABYTE);
private int exchangeSourceConcurrentReaders = 4;
private int exchangeSourceMaxFilesPerReader = 25;
private int maxOutputPartitionCount = 50;
```
— `plugin/trino-exchange-filesystem/.../FileSystemExchangeConfig.java:40-46`

**`exchangeSinkMaxFileSize = 1GB`** 와 **`maxOutputPartitionCount = 50`** 이 규모를 말해 준다. 셔플 결과가 파일로 남으므로 메모리 한도와 무관해지고, **태스크가 죽으면 그 태스크만 다시 돌린다.**

### 3-2. StarRocks — 원격 셔플에는 스필이 없다

`be/src/exec/spill/` 에 스필 기반이 있고 `A-3-03` 에서 본 대로 **12계열 연산자**가 스필한다. 그런데 **원격 교환은 그 목록에 없다.**

`be/src/exec/pipeline/exchange/` 에서 스필을 언급하는 파일을 찾으면 이렇다.

| 파일 | 성격 |
|---|---|
| `spillable_multi_cast_local_exchange.cpp` | **로컬** 멀티캐스트 교환 |
| `mem_limited_chunk_queue.cpp` / `.h` | 위가 쓰는 메모리 한도 큐 |
| `multi_cast_local_exchange.h` | 위의 인터페이스 |

`exchange_sink_operator` / `exchange_source_operator`(원격 셔플)에는 없다.

**`multi_cast_local_exchange` 는 CTE 재사용의 실행 장치다.** `A-2-05` 에서 "CTE 재사용은 StarRocks 만 가능하다"고 결론지었는데, 그 재사용된 결과를 여러 소비자에게 나눠 주는 것이 이 연산자이고, **그것이 메모리를 넘으면 디스크로 흘린다.** 즉 스필이 붙은 곳은 셔플이 아니라 **중간 결과 물질화** 쪽이다.

정리하면 **StarRocks 의 원격 셔플은 메모리 스트리밍 전용**이고, 넘치면 `A-4-01` 4-2 의 배압으로 상류를 세우거나 `EOVERCROWDED` 로 실패한다.

### 3-3. 노드가 죽으면

| | 동작 |
|---|---|
| Trino (기본) | 쿼리 실패 |
| Trino (FTE) | **셔플 파일이 외부 저장소에 있으므로 죽은 태스크만 재시도**한다 |
| StarRocks | 쿼리 전체 재실행 — `Config.max_query_retry_time = 2`(`fe/fe-core/.../common/Config.java:1678`) |

StarRocks 의 재시도는 **쿼리 단위**다. 중간 결과가 남아 있지 않으므로 처음부터 다시 돈다. 그리고 `A-5-03` 3-3 에서 본 대로, 죽은 BE 는 자동으로 블랙리스트에 오르므로 재시도는 남은 노드에서 이뤄진다.

**이 차이는 쿼리가 길수록 커진다.** 10분짜리 쿼리가 9분째에 노드를 잃으면 Trino FTE 는 그 태스크만 다시 돌리고 StarRocks 는 9분을 버린다. `B-4-01` 에서 다시 다룬다.

## 4. 실측

**없다.** `A-4-01` 2절과 같은 이유다 — 1노드에서는 원격 셔플 경로가 생기지 않는다.

FTE 는 노드가 여럿이 아니어도 켤 수는 있으나, **"죽은 태스크만 재시도한다"를 확인하려면 죽일 노드가 있어야 한다.** 현재 랩에서는 판별력이 없다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 파티셔닝 종류 | 시스템 5종 + **커넥터 정의 가능** | **6종 고정**(Thrift 열거형) |
| 스토리지 활용 파티셔닝 | 커넥터가 제공하면 가능 | `BUCKET_SHUFFLE` — **1급 시민** |
| 쏠림 대응 파티셔닝 | 없음 | **`HYBRID_HASH_PARTITIONED`** |
| 기본 셔플 | 메모리 스트리밍 | 메모리 스트리밍 |
| 셔플 스풀 | **FTE 켜면 외부 저장소로 물질화**(SPI 14종 + 플러그인 2개) | **없음**(원격 셔플) |
| 로컬 교환 스풀 | — | **있음** — `spillable_multi_cast_local_exchange`(CTE 재사용) |
| 노드 사망 | FTE 면 **태스크 단위 재시도** | 쿼리 전체 재실행(최대 2회) |

### 5-2. 파티셔닝 목록이 닫혀 있는가

`A-5-01`·`A-5-02` 의 구도가 여기서도 그대로 반복된다.

- Trino 의 파티셔닝은 **SPI 로 열려 있다.** 커넥터가 "내 데이터는 이미 이렇게 나뉘어 있다"고 알려 주면 옵티마이저가 셔플을 생략한다
- StarRocks 의 파티셔닝은 **Thrift 열거형 6개로 닫혀 있다.** 대신 그중 둘(`BUCKET_SHUFFLE`, `HYBRID_HASH`)이 **자기 스토리지를 전제로 한 고급 기능**이다

**닫힌 목록이 손해만은 아니다.** `HYBRID_HASH_PARTITIONED` 같은 쏠림 대응은 엔진이 실행 계층까지 통제해야 만들 수 있고, Trino 에는 없다.

### 5-3. FTE 는 무엇을 사고 무엇을 파는가

FTE 는 셔플을 파일로 쓴다. **얻는 것**은 내결함성이고 **파는 것**은 지연이다 — 메모리에서 바로 넘길 것을 디스크나 S3 에 썼다가 다시 읽는다.

Trino 가 이것을 **기본이 아니라 선택**으로 둔 이유가 여기 있다(`retry-policy=NONE` 이 기본). 짧은 대화형 쿼리에는 손해이고, **장수 ETL 에는 결정적**이다.

StarRocks 가 대응물을 만들지 않은 것도 같은 계산으로 읽힌다 — 주 무대가 **초 단위 대화형 분석**이라 파일 왕복을 넣을 이유가 없다. `A-4-01` 5-2 에서 본 pull/push 선택과 방향이 같다.

### 5-4. 그러나 "장수 쿼리"는 StarRocks 에서도 늘고 있다

StarRocks 가 MV 자동 갱신(`A-2-06`)과 적재(`C-1-04`)를 자기 안에서 처리하는 이상, 분 단위·시간 단위로 도는 작업이 존재한다. 그 작업들이 노드 사망에 어떻게 대응하는지는 **셔플 계층이 아니라 다른 장치**로 처리될 것이다 — `B-4-01` 의 주제다.

## 6. 결론

**파티셔닝은 서로 다른 방향으로 풍부하고, 스풀·내결함성에서는 Trino 가 명확히 앞선다.**

- **파티셔닝**: Trino 는 커넥터가 확장할 수 있고, StarRocks 는 6종 고정이되 **스토리지 기반 버킷 셔플과 쏠림 대응 하이브리드**를 갖는다. 우열이 아니다
- **셔플 스풀**: Trino 는 FTE 로 외부 저장소에 물질화한다(SPI + 플러그인 2종). **StarRocks 의 원격 셔플에는 없다**
- **로컬 교환**: StarRocks 도 CTE 재사용용 멀티캐스트 교환에는 스필이 있다. 셔플이 아니라 중간 결과 쪽이다
- **노드 사망**: Trino FTE 는 태스크 단위 재시도, StarRocks 는 쿼리 전체 재실행(최대 2회)

**실무 결론**

1. **수십 분 이상 도는 ETL 을 SQL 엔진에서 돌린다면 Trino FTE 가 사실상 유일한 선택이다.** StarRocks 는 그 길이의 쿼리가 노드를 잃으면 처음부터 다시 돈다
2. **FTE 를 기본으로 켜지 말 것.** 대화형 쿼리에는 파일 왕복이 손해다. Trino 도 기본은 `NONE` 이다
3. **StarRocks 에서 셔플이 큰 쿼리는 메모리로 감당되는 크기여야 한다.** 넘치면 흘릴 곳이 없다
4. **조인 대상 테이블을 같은 키로 버킷팅해 두면 StarRocks 쪽이 유리하다** — `BUCKET_SHUFFLE` 로 셔플 자체를 줄인다(`A-2-02` 5-1)

### 아직 답하지 않은 것

- **전부 코드 독해다.** 실측이 없다. 다중 노드 랩이 필요하다(`plan/02` 6-3절)
- **FTE 의 실제 비용** — 파일 왕복이 지연을 얼마나 늘리는지 재지 않았다
- **`HYBRID_HASH_PARTITIONED` 가 언제 선택되는가** — 옵티마이저가 쏠림을 어떻게 감지해 이 방식을 고르는지 확인하지 않았다
- **`BUCKET_SHUFFLE` 의 실효** — 랩 테이블이 버킷팅돼 있지 않아 `A-2-02` 에서도 판별하지 못했다
- **커넥터 정의 파티셔닝의 실제 사용처** — Trino 의 `applyPartitioning` 을 구현한 커넥터가 3개뿐이다(`A-5-02` 2-2). 실제로 얼마나 쓰이는지 모른다
- **노드 사망 시나리오 전반** — `B-4-01`
