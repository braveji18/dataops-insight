## 1. 비교 관점

A-2-04의 푸시다운은 **계획 시점**에 알 수 있는 조건을 아래로 내리는 것이었다. 런타임 필터는 다르다 — **실행 중에야 알 수 있는 값 집합**을 아래로 보낸다.

전형적인 형태는 이렇다. `lineitem ⋈ orders WHERE o_orderdate < '1993-01-01'` 에서 orders 쪽이 2,283건으로 줄어든다면, **그 2,283개의 주문번호 집합**을 lineitem 스캔에 넘겨 6만 건을 미리 걸러낼 수 있다. 이 집합은 orders 를 실제로 읽어봐야 알 수 있으므로 계획 시점에는 만들 수 없다.

두 엔진 다 이 기능을 갖고 있고 **기본으로 켜져 있다.** 비교할 것은 셋이다.

1. **무엇을 보내는가** — 값 목록인가, 범위인가, 블룸 필터인가
2. **어디까지 보내는가** — 같은 노드 안인가, 다른 노드까지인가
3. **얼마나 기다리는가** — 필터가 준비될 때까지 스캔이 기다리는가

**결론부터: 기능 자체는 대등하고 둘 다 기본 켜짐이다. 갈리는 것은 (가) 크기 임계값의 축과 개수, (나) 로컬/원격 구분을 플랜에 드러내는가, (다) 관측 경로다.**

## 2. Trino 구현 — Dynamic Filtering

### 2-1. 기본 켜짐, 그리고 두 층으로 나뉜다

`works/trino/core/trino-main/src/main/java/io/trino/execution/DynamicFilterConfig.java:58-60`:

```java
    private boolean enableDynamicFiltering = true;
    private boolean enableDynamicRowFiltering = true;
    private double dynamicRowFilterSelectivityThreshold = 0.7;
```

**두 가지가 별도로 존재한다.**

- `enableDynamicFiltering` — **스플릿·파일 단위** 필터. 읽을 파일 자체를 건너뛴다
- `enableDynamicRowFiltering` — **행 단위** 필터. 읽은 뒤 행을 거른다. `selectivityThreshold = 0.7` 은 "필터가 30% 이상 걸러낼 때만 적용한다"는 뜻이다

**두 번째 층은 StarRocks 에 대응하는 별도 설정이 없다** — StarRocks 는 행 단위 적용이 기본 동작에 포함돼 있다.

### 2-2. 크기 임계값이 6개 — 조인 분배 방식에 따라 두 벌

`DynamicFilterConfig.java:61-69`:

```java
    private int maxDistinctValuesPerDriver = 50_000;
    private DataSize maxSizePerDriver = DataSize.of(4, MEGABYTE);
    private int rangeRowLimitPerDriver = 100_000;
    private DataSize maxSizePerOperator = DataSize.of(5, MEGABYTE);
    private int partitionedMaxDistinctValuesPerDriver = 20_000;
    private DataSize partitionedMaxSizePerDriver = DataSize.of(200, KILOBYTE);
    private int partitionedRangeRowLimitPerDriver = 30_000;
```

**broadcast 조인용과 partitioned(shuffle) 조인용 값이 따로다.**

| 축 | broadcast | partitioned |
|---|---|---|
| 서로 다른 값 개수 | 50,000 | **20,000** |
| 크기 | 4MB | **200KB** |
| 범위로 축약하는 행 수 상한 | 100,000 | **30,000** |

**shuffle 조인 쪽 임계값이 훨씬 빡빡하다.** 이유는 분명하다 — shuffle 조인에서는 필터를 다른 노드로 보내야 하므로 네트워크 비용이 붙는다.

그리고 `rangeRowLimitPerDriver` 라는 축이 있다는 점이 중요하다. **값 개수가 많아지면 개별 값 목록 대신 [최소, 최대] 범위로 축약한다.** 정확도를 낮추는 대신 크기를 줄이는 것이다.

필터 전체의 상한도 따로 있다 — `maxSizePerFilter = 10MB` (`:69`).

### 2-3. A-2-04에서 이미 관찰됐다

A-2-04·A-2-05의 여러 실측 플랜에 `dynamicFilters = {...}` 가 계속 등장했다.

```
ScanFilter[table = iceberg:bench.lineitem$data@…, dynamicFilters = {l_orderkey = #df_236}]
```

**Trino 는 기본 `EXPLAIN` 에 동적 필터를 표시한다.** `#df_236` 은 필터 식별자다.

## 3. StarRocks 구현 — Runtime Filter

### 3-1. 기본 켜짐, 설정이 12개 이상

`fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java`:

```java
    private boolean enableGlobalRuntimeFilter = true;      // :1873
    private boolean enableTopNRuntimeFilter = true;        // :1876
    private long globalRuntimeFilterBuildMaxSize = 64L * 1024L * 1024L;   // :1885 (64MB)
    private long globalRuntimeFilterBuildMinSize = 128L * 1024L;          // :1888 (128KB)
    private long globalRuntimeFilterProbeMinSize = 100L * 1024L;          // :1890 (100KB)
    private int globalRuntimeFilterWaitTimeout = 20;                      // :1894 (20ms)
    private float runtimeFilterEarlyReturnSelectivity = 0.05f;            // :1898
```

여기에 `runtime_filter_scan_wait_time`(기본 20ms, `:1229`), `global_runtime_filter_rpc_timeout`, `runtime_filter_on_exchange_node`, `enable_join_runtime_filter_push_down` 등이 더 있다.

**Trino 에 없는 축 둘이 눈에 띈다.**

- **`globalRuntimeFilterBuildMinSize`(하한)** — 빌드측이 **너무 작으면** 만들지 않는다. Trino 는 상한만 둔다
- **`enableTopNRuntimeFilter`** — 조인이 아니라 **정렬+상한(TopN)에서 생성하는 필터**. 상위 N건의 경계값을 스캔에 넘겨 그보다 나쁜 행을 미리 버린다. **Trino 에 대응물이 없다**

`runtimeFilterEarlyReturnSelectivity = 0.05` 는 "필터가 95% 이상 걸러내면 조기 반환한다"는 최적화다.

### 3-2. 실행 계층이 별도 모듈이다

BE 쪽 구현이 `be/src/exprs/` 와 `be/src/runtime/` 에 나뉘어 있다.

| 파일 | 역할 |
|---|---|
| `exprs/runtime_filter.{h,cpp}` | 필터 자료구조 |
| `exprs/runtime_filter_bank.{h,cpp}` | 필터 보관·조회 |
| `exprs/runtime_filter_layout.{h,cpp}` | 배치 |
| `exprs/agg_in_runtime_filter.h` | **집계에서 만드는 IN 필터** |
| `runtime/runtime_filter_worker.{h,cpp}` | **노드 간 필터 전송 전담 워커** |
| `runtime/runtime_filter_cache.{h,cpp}` | 필터 캐시 |

**`runtime_filter_worker` 가 따로 있다는 점이 특징이다** — 필터를 노드 사이로 보내는 일을 전담 스레드가 맡는다. Trino 는 코디네이터의 `DynamicFilterService` 가 수집·배포를 담당한다.

`agg_in_runtime_filter` 는 **집계 결과로 필터를 만드는 경로**로, 조인 외의 생성 지점이 있다는 뜻이다.

### 3-3. 로컬 필터와 원격 필터를 구분한다

`EXPLAIN VERBOSE` 가 이것을 그대로 보여준다(4-2).

```
build runtime filters:
- filter_id = 0, build_expr = (17: o_orderkey), remote = false
```

`remote` 가 **false 면 같은 노드 안에서만, true 면 다른 노드로도** 보낸다. broadcast 조인은 빌드측이 이미 모든 노드에 복제돼 있으므로 로컬로 충분하고, shuffle 조인은 원격이 필요하다.

## 4. 실측

전체 절차·조건은 `docs/evidence/A-3/20260904-runtime-filter-probes.md`.

### 4-1. 양쪽 다 만든다 — 그런데 보이는 곳이 다르다

```sql
SELECT count(*) FROM lineitem JOIN orders ON l_orderkey = o_orderkey
WHERE o_orderdate < DATE '1993-01-01';
```

| 엔진 | 생성 | 어디에 보이는가 |
|---|---|---|
| Trino 483 | ✅ | **기본 `EXPLAIN`** — `dynamicFilters = {l_orderkey = #df_343}` |
| StarRocks 4.0.14 | ✅ | **`EXPLAIN VERBOSE` 에서만** — `build runtime filters: - filter_id = 0, …` |

**기본 `EXPLAIN` 만 보면 StarRocks 가 런타임 필터를 안 만드는 것처럼 보인다.** 실제로는 만든다. 진단할 때 알고 있어야 하는 차이다.

### 4-2. StarRocks 는 조인 분배에 따라 필터 범위를 바꾼다

| 조인 분배 | 런타임 필터 |
|---|---|
| `INNER JOIN (BROADCAST)` (기본) | `remote = **false**` |
| `INNER JOIN (PARTITIONED)` (`[shuffle]` 힌트) | `remote = **true**` |

**같은 쿼리에서 조인 방식만 바꿨는데 필터의 전파 범위가 따라 바뀌었다.** 3-3의 설계가 그대로 확인된다.

Trino 도 내부적으로는 broadcast/partitioned 를 구분해 임계값을 다르게 쓰지만(2-2), **플랜에는 그 구분이 드러나지 않는다.**

### 4-3. 임계값의 적용 지점은 확정하지 못했다

3-1의 `globalRuntimeFilterBuildMinSize`(128KB)에 따르면, 빌드측이 2,283건 × 12바이트 ≈ **27KB** 인 이 쿼리는 필터를 만들지 않아야 한다. **그런데 만들었다.**

임계값을 1로 낮춰도 변화가 없었다. **즉 이 경로에서는 그 설정이 발화 지점이 아니다.**

**코드에서 읽은 임계값이 실제로 어디에 적용되는지 확정하지 못했다.** 이것을 "미확인"으로 남긴다 — 코드 독해만으로 동작을 단정하면 안 된다는 사례가 이 저장소에서 세 번째다(A-2-03 5-3, A-2-05, 여기).

### 4-4. 필터의 실제 효과는 측정 불가

데이터가 6만 건이라 필터 유무로 읽는 양이 유의미하게 달라지지 않는다. **양쪽 다 "생성됐다"까지만 확인했고 "얼마나 걸렀는가"는 재지 못했다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 기본값 | 켜짐 | 켜짐 |
| 적용 층 | **파일/스플릿 층 + 행 층(별도 설정)** | 통합 |
| 크기 임계값 | **상한만** (6개, broadcast/shuffle 두 벌) | **상한 + 하한** |
| 빌드측이 너무 작을 때 | 만든다 | 이론상 만들지 않음 — **실측에서는 만들었다(4-3)** |
| 값이 많을 때 | **범위로 축약**(`rangeRowLimit`) | 블룸 필터 계열 |
| 조인 외 생성 지점 | 없음 | **TopN 필터**, **집계 IN 필터** |
| 로컬/원격 구분 | 내부적으로 구분, 플랜에 미표시 | **플랜에 표시**(`remote = true/false`) |
| 전송 담당 | 코디네이터의 `DynamicFilterService` | **전담 워커**(`runtime_filter_worker`) |
| 대기 시간 | `dynamic_filtering_wait_timeout` | `global_runtime_filter_wait_timeout` 20ms, `runtime_filter_scan_wait_time` 20ms |
| 관측 | **기본 `EXPLAIN`** | `EXPLAIN VERBOSE` |

### 5-2. 임계값의 축이 다른 이유

**Trino 는 상한만 둔다.** 필터가 너무 커지면 네트워크와 메모리를 낭비하므로 막는다. 작은 필터는 만들어도 손해가 없다는 판단이다.

**StarRocks 는 하한도 둔다.** 필터를 만들고 전파하는 것 자체에 고정 비용이 있으니, 이득이 그보다 작으면 만들지 말자는 판단이다.

**두 판단 다 타당하고, 어느 쪽이 옳은지는 데이터에 달렸다.** 다만 4-3에서 본 대로 **StarRocks 의 하한이 실제로 어디에 적용되는지는 확인하지 못했다.**

### 5-3. 조인 외의 생성 지점

StarRocks 의 `enableTopNRuntimeFilter` 와 `agg_in_runtime_filter` 는 **조인이 아닌 곳에서 필터를 만든다.**

- **TopN 필터** — `ORDER BY x LIMIT 10` 에서 이미 찾은 10번째 값을 스캔에 넘긴다. 그보다 나쁜 행은 읽자마자 버릴 수 있다
- **집계 IN 필터** — 집계 결과의 그룹 키 집합을 필터로 쓴다

**Trino 에는 둘 다 대응물이 없다.** A-2-05 4-3에서 본 "Trino 는 순위 필터를 만나면 윈도우를 `TopNRanking` 으로 바꾼다"가 계획 시점의 최적화라면, StarRocks 의 TopN 런타임 필터는 **실행 시점의 최적화**다. **접근하는 층이 다르다.**

### 5-4. 관측 경로 차이가 운영에 걸린다

`EXPLAIN` 만 보고 "StarRocks 는 런타임 필터를 안 만드네"라고 판단하면 틀린다(4-1). 진단할 때는 `EXPLAIN VERBOSE` 를 써야 한다.

반대로 Trino 는 기본 `EXPLAIN` 에 `dynamicFilters` 를 보여주지만, **로컬/원격 구분과 필터의 종류(값 목록인지 범위인지)는 보여주지 않는다.** 그것을 보려면 쿼리 실행 후의 통계를 봐야 한다.

**양쪽 다 완전하지 않고, 보여주는 것이 다르다.**

## 6. 결론

**기능은 대등하고 둘 다 기본 켜짐이다. 차이는 임계값의 축, 조인 외 생성 지점, 그리고 관측 경로다.**

- **크기 임계값** — Trino 는 상한만(6개, 조인 분배별로 두 벌), StarRocks 는 상한과 하한 둘 다. **다만 하한의 실제 적용 지점은 확인하지 못했다**
- **StarRocks 만 가진 것** — TopN 에서 만드는 필터, 집계에서 만드는 필터, 전송 전담 워커, 플랜에 드러나는 로컬/원격 구분
- **Trino 만 가진 것** — 파일 단위 필터와 행 단위 필터를 **별도 설정으로 분리**한 구조(`enable_dynamic_row_filtering` + 선택도 임계 0.7)
- **관측 경로가 다르다** — Trino 는 기본 `EXPLAIN`, StarRocks 는 `EXPLAIN VERBOSE`

### 아직 답하지 않은 것

- **필터가 실제로 얼마나 걸러내는가** — 데이터 6만 건에서는 측정 불가(`perf` 프로파일 필요, `plan/02` 6-2절)
- **다중 노드에서의 원격 필터 전파** — worker/BE 1대라 `remote = true` 가 실제로 네트워크를 타지 않는다. 전송 지연·타임아웃 동작을 볼 수 없다
- **StarRocks 빌드측 최소 크기 임계의 적용 지점** — 4-3. 코드에는 있으나 이 쿼리에서 발화하지 않았다
- **대기 시간 동작** — 빌드가 늦을 때 프로브가 기다리다 포기하는 경로를 재현하지 못했다
- **필터 종류(값 목록 / 범위 / 블룸)의 선택 기준** — 코드 표면만 봤고 실제 선택을 관찰하지 못했다
- **Trino 행 단위 필터의 선택도 임계(0.7)** — 발화 여부를 확인하지 못했다
