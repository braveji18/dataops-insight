## 1. 비교 관점

함수는 두 가지를 동시에 드러낸다.

1. **엔진의 실행 구조** — Trino 는 전부 JVM 이고, StarRocks 는 FE(Java)와 BE(C++)로 나뉘어 있다. 함수 하나를 추가하려면 이 경계를 반드시 통과해야 하므로, 함수 등록 방식은 이원 구조의 비용을 가장 선명하게 보여준다
2. **확장의 개방성** — 외부인이 함수를 넣을 수 있는가, 넣으려면 무엇을 해야 하는가

결론부터: **내장 함수 개수는 StarRocks 가 많고(637 vs 442), 새 함수를 넣는 비용은 Trino 가 압도적으로 낮다.** 상반돼 보이지만 같은 원인에서 나온다 — StarRocks 는 함수를 엔진 코어에 직접 넣고, Trino 는 SPI 뒤에 두었다.

## 2. Trino 구현

### 2-1. 함수 = 애노테이션 붙은 Java 메서드

```java
@Description("Absolute value")
@ScalarFunction
@SqlType(StandardTypes.BIGINT)
public static long abs(@SqlType(StandardTypes.BIGINT) long num)
{
    checkCondition(num != Long.MIN_VALUE, NUMERIC_VALUE_OUT_OF_RANGE, "Value -9223372036854775808 is out of range for abs(bigint)");
    return Math.abs(num);
}
```
— `core/trino-main/.../operator/scalar/MathFunctions.java:134-141`

등록표도, ID 도, 별도 선언도 없다. **메서드 시그니처가 곧 함수 시그니처**이고 리플렉션으로 읽힌다. 오버로드는 같은 이름의 메서드를 하나 더 쓰면 된다.

애노테이션 자체는 SPI 에 있다.

```java
public @interface ScalarFunction
{
    String value() default "";
    String[] alias() default {};
    boolean hidden() default false;
    boolean deterministic() default true;
    boolean neverFails() default false;
}
```
— `core/trino-spi/.../function/ScalarFunction.java`

`alias`, `deterministic` 같은 속성이 애노테이션에 있다는 점이 중요하다. 옵티마이저가 필요로 하는 메타데이터(결정성 여부 → 공통부분식 제거·상수 접기 가능 여부)가 **구현과 같은 자리에 선언**된다.

**(a) 플러그인 JAR** — `Plugin` 인터페이스의 기본 메서드다.

`@ScalarFunction` 이 붙은 클래스를 반환하면 끝이다. **엔진을 다시 빌드하지 않는다.**

**(b) 커넥터가 제공하는 함수** — 커넥터도 함수를 노출할 수 있다.

```java

```
— `core/trino-spi/.../connector/ConnectorMetadata.java:1111`

**(c) SQL / 외부 언어 UDF** — `CREATE FUNCTION` 이 문법에 있다.

— `SqlBase.g4:133`

언어 엔진도 SPI 다(`LanguageFunctionEngine`), 구현체로 `plugin/trino-functions-python` 이 들어 있다. 커넥터가 UDF 정의를 저장·조회한다(`createLanguageFunction` / `getLanguageFunctions`, `ConnectorMetadata.java:1151-1181`).

- 표의 항목 수는 **932개**다

## 4. 실측 — 내장 함수 개수

살아 있는 두 엔진에 직접 물었다.

| 엔진 | 질의 | 결과 |
|---|---|---|
| Trino 483 | `SHOW FUNCTIONS` 의 고유 함수명 | **442** |
| StarRocks 4.0.14 | `SHOW BUILTIN FUNCTIONS` | **637** |

**StarRocks 가 1.4배 많다.** MySQL 호환을 목표로 삼았으니(`A-1-01` 5절) 자연스러운 결과다.

방언 모드 실측(`A-1-01` 4-4)에서 본 것을 여기서 다시 짚는다.

| 설정 | `approx_distinct(l_orderkey)` |
|---|---|
| Trino 483 | `15432` |
| StarRocks 기본 | 오류 (`No matching function`) |
| StarRocks `sql_dialect='trino'` | `15022`, 컬럼명이 `approx_count_distinct(...)` 로 바뀜 |

`connector/parser/trino/Trino2SRFunctionCallTransformer` 에 **약 100건**의 이름 대응이 손으로 등록돼 있다. 637개 내장 함수 중 100건이므로, **방언 모드의 함수 커버리지는 이름 대응 표의 크기가 상한**이다. 그리고 대응은 이름만 옮기고 구현은 각자의 것을 쓰므로, 근사 집계처럼 값이 달라질 수 있다.

## 5. 설계 차이와 그 원인

### 5-1. 함수 하나를 추가하는 데 드는 일

| 단계 | Trino | StarRocks |
|---|---|---|
| 구현 | Java 메서드 1개 | **BE 에 C++ 함수** 구현 |
| 등록 | 애노테이션 (`@ScalarFunction`) | `functions.py` 에 **ID 를 직접 붙여** 한 줄 추가 |
| 타입 선언 | `@SqlType` 애노테이션 | 같은 줄의 반환/인자 타입 문자열 |
| 빌드 | 해당 모듈 | **FE(Maven) + BE(CMake) 양쪽** |
| 배포 | **플러그인 JAR 로 가능 — 엔진 재빌드 불필요** | 엔진 재빌드·재배포 |

**차이의 크기가 종류의 차이로 넘어간다.** Trino 에서는 외부인이 함수 라이브러리를 만들어 배포할 수 있고, StarRocks 에서는 upstream 에 기여하는 것 외에 방법이 없다(UDF 는 별개 경로다).

이 비대칭은 `A-5-01` 에서 다룰 커넥터 추가 난이도와 **정확히 같은 구조**다. 원인도 같다 — SPI 뒤에 두었는가, 코어에 직접 넣었는가.

### 5-2. UDF 경로는 오히려 대등하다

내장 함수와 달리 UDF 는 양쪽 다 갖췄다.

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| SQL UDF | `CREATE FUNCTION` (SQL routines) | `CREATE FUNCTION ... RETURNS expression` |
| Java UDF | 플러그인 JAR | `CREATE FUNCTION ... ("type"="StarRocks_JAR")` |
| Python UDF | `plugin/trino-functions-python` (언어 엔진 SPI) | `("type"="StarRocks_PYTHON")` |
| 저장 위치 | 커넥터(`createLanguageFunction`) | FE 메타데이터 (`GLOBAL` 지원) |

성격이 다르다. Trino 는 UDF 정의를 **커넥터에 저장**해 카탈로그 단위로 관리하고, StarRocks 는 **FE 메타데이터**에 두며 전역 함수를 지원한다. 스토리지를 소유하는 쪽과 아닌 쪽의 차이가 여기서도 반복된다.

### 5-3. 함수 개수가 많은 것이 곧 유리하지 않다

637 vs 442 는 이전 방향에 따라 다르게 읽힌다.

- **Trino → StarRocks**: 이름이 대응되면 대체로 옮겨진다. 다만 `approx_distinct` 처럼 **이름이 다른데 의미가 비슷한** 함수가 함정이다. 방언 모드가 이름만 바꿔주고 값은 달라진다
- **StarRocks → Trino**: MySQL 계열 함수(`date_format` 의 포맷 문자열 등)가 Trino 에 없거나 규격이 달라 다시 써야 한다. 대응 도구도 없다

즉 개수는 **MySQL 생태계와의 거리**를 재는 값이지, 표현력의 우열이 아니다.

## 6. 결론

**동등하지 않다 — 개수는 StarRocks 가, 확장성은 Trino 가 앞선다. 원인은 같다.**

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 내장 함수 수 (실측) | 442 | **637** |
| 함수 정의 형태 | 애노테이션 붙은 Java 메서드 | Python 표의 한 줄 + BE C++ 심볼 |
| 함수 ID | 없음 (시그니처로 식별) | **사람이 붙이는 숫자 ID** (932건) |
| FE/BE 계약 | 해당 없음 (단일 JVM) | `functions.py` → FE Java + BE C++ **동시 생성** |
| 외부 함수 추가 | **플러그인 JAR — 재빌드 불필요** | upstream 기여 + 양쪽 재빌드 |
| 커넥터 제공 함수 | 지원 (`ConnectorMetadata.getFunctions`) | 없음 |
| UDF 언어 | SQL / Java / Python | SQL / Java / Python |
| 전역 UDF | 카탈로그 단위 | **`CREATE GLOBAL FUNCTION`** |
| 상대 방언 함수 대응 | 없음 | 약 100건 (이름만, 구현은 각자) |

**실무 결론**

1. **사내 전용 함수를 많이 쓴다면 Trino 쪽이 유지비가 낮다.** 플러그인 JAR 로 분리해 엔진 업그레이드와 독립적으로 관리할 수 있다. StarRocks 에서는 UDF(jar/Python)로 우회하거나 upstream 을 따라가야 한다
2. **이전 시 함수 대조는 이름이 아니라 값으로 해야 한다.** `approx_distinct` → `approx_count_distinct` 는 이름이 대응되지만 값이 2.7% 달랐다. 근사 집계·날짜 포맷·문자열 함수가 특히 위험하다
3. **`sql_dialect='trino'` 를 함수 호환 수단으로 기대하면 안 된다.** 대응표가 약 100건이고 손으로 관리된다

### 아직 답하지 않은 것

- **함수 이름 전수 대조** — 442 vs 637 의 교집합·차집합을 내지 않았다. 두 엔진이 살아 있으므로 `SHOW FUNCTIONS` 출력을 맞대면 기계적으로 가능하다. 이 문서 범위를 넘어 별도 작업으로 남긴다
- **같은 이름 함수의 의미 차이** — 이름이 같아도 NULL 처리, 반올림, 날짜 포맷 규격이 다를 수 있다. 표본 없이는 주장할 수 없다
- **UDF 성능** — Java/Python UDF 의 호출 오버헤드는 측정하지 않았다. StarRocks 는 C++ BE 에서 JVM/Python 을 호출해야 하므로 구조적으로 불리할 수 있으나, `perf` 프로파일이 필요하다(`plan/02` 6-2절)
- **집계·윈도우·테이블 함수** — 이 문서는 스칼라 함수 중심이다. `@AggregationFunction` 과 StarRocks 의 `AggregateFunction`/`TableFunction` 등록 경로는 다루지 않았다
