## 1. 비교 관점

타입 체계는 SQL 을 옮길 때 **가장 늦게 드러나는 차이**다. 문법 차이는 파싱에서 즉시 실패하지만, 타입 차이는 값이 조용히 뭉개진 뒤에야 알게 된다.

이 랩은 두 엔진이 **완전히 같은 Iceberg 테이블**을 읽으므로, 타입 비교에 특히 유리하다. 같은 파일·같은 스키마를 놓고 양쪽이 그것을 무엇이라 부르는지 직접 대조할 수 있다.

세 가지를 본다.

1. 각자 무엇을 표현할 수 있는가 (타입 목록과 정밀도 한계)
2. **같은 Iceberg 스키마를 각자 무엇으로 매핑하는가** — 이 축의 핵심
3. 매핑이 어긋날 때 어디서 드러나는가

결론부터: **표현력의 총량은 우열을 가릴 수 없다.** StarRocks 는 DECIMAL 정밀도가 두 배(76 vs 38)고 분석용 전용 타입(BITMAP/HLL/PERCENTILE)을 갖는 반면, Trino 는 시간대·UUID·IP·중첩 타입을 표준에 맞게 구분한다. 그러나 **Iceberg 를 읽는 순간 비대칭이 생긴다** — StarRocks 쪽에서 타입 정보가 좁아지는 방향으로만 손실된다.

## 2. Trino 구현

### 2-1. 타입이 SPI 에 있다

타입 정의는 `core/trino-spi/src/main/java/io/trino/spi/type/` 에 있다(90개 파일). **SPI 라는 위치 자체가 설계 의도**다 — 플러그인이 타입을 추가할 수 있고, 커넥터가 같은 타입 어휘로 대화한다.

내장 타입 등록은 한 곳에 모여 있다.

```java
addType(BOOLEAN);
addType(BIGINT);
addType(INTEGER);
addType(SMALLINT);
addType(TINYINT);
addType(DOUBLE);
addType(REAL);
```
— `core/trino-main/.../metadata/TypeRegistry.java` 발췌

등록되는 타입을 성격별로 묶으면 이렇다.

| 갈래 | 타입 |
|---|---|
| 수치 | `BOOLEAN` `TINYINT` `SMALLINT` `INTEGER` `BIGINT` `REAL` `DOUBLE` `DECIMAL(p,s)` |
| 문자/이진 | `VARCHAR(n)` `CHAR(n)` `VARBINARY` |
| 시간 | `DATE` `TIME(p)` `TIME(p) WITH TIME ZONE` `TIMESTAMP(p)` `TIMESTAMP(p) WITH TIME ZONE` `INTERVAL` 2종 |
| 중첩 | `ARRAY` `MAP` `ROW` |
| 반정형 | `JSON` `JSON_2016` `VARIANT` |
| 도메인 | `UUID` `IPADDRESS` |
| 근사 집계 상태 | `HYPERLOGLOG` `P4HYPERLOGLOG` `SETDIGEST` `QDIGEST` `TDIGEST` |

### 2-2. 정밀도 한계

```java
public static final int MAX_PRECISION = 38;
public static final int MAX_SHORT_PRECISION = 18;
```
— `core/trino-spi/.../type/Decimals.java:46-47`

18자리 이하는 `long` 한 개(short decimal), 그 위는 `Int128`(long decimal)로 물리 표현이 갈린다. 상한은 **38**.

```java
public static final int MAX_PRECISION = 12;

public static final int MAX_SHORT_PRECISION = 6;
public static final int DEFAULT_PRECISION = 3; // TODO: should be 6 per SQL spec
```
— `core/trino-spi/.../type/TimestampType.java:35-38`

`TIMESTAMP(p)` 는 **p 를 0~12 까지 파라미터로 받는다.** 즉 타입 자체가 정밀도를 들고 다닌다.

### 2-3. 시간대가 타입에 들어 있다

`TIMESTAMP(p)` 와 `TIMESTAMP(p) WITH TIME ZONE` 은 **별개의 타입**이다. 값마다 시간대를 실어 나르므로(`LongTimestampWithTimeZone`), 세션 설정과 무관하게 의미가 고정된다.

## 3. StarRocks 구현

### 3-1. 타입이 FE 카탈로그에 있다

```java
INVALID_TYPE NULL_TYPE BOOLEAN TINYINT SMALLINT INT BIGINT LARGEINT FLOAT DOUBLE
DATE DATETIME CHAR VARCHAR DECIMALV2 HLL TIME BITMAP PERCENTILE
DECIMAL32 DECIMAL64 DECIMAL128 DECIMAL256 JSON FUNCTION BINARY VARBINARY UNKNOWN_TYPE
```
— `fe/fe-core/.../catalog/PrimitiveType.java` 열거 상수

중첩 타입은 별도 클래스다 — `ArrayType`, `MapType`, `StructType`(+`StructField`).

Trino 에 없는 것: `LARGEINT`(128비트 정수), `BITMAP`, `HLL`, `PERCENTILE`.
Trino 에 있고 여기 없는 것: `UUID`, `IPADDRESS`, `VARIANT`, `INTERVAL`, `TIMESTAMP WITH TIME ZONE`, `TIME WITH TIME ZONE`, `QDIGEST`/`TDIGEST`.

`BITMAP`/`HLL`/`PERCENTILE` 은 Trino 의 `HYPERLOGLOG`/`QDIGEST` 와 같은 갈래(집계 상태를 값으로 저장)지만, StarRocks 쪽은 **테이블 컬럼 타입으로 정착시켜 사전집계 테이블 모델과 엮인다.** 그 연결은 `C-1-01`(테이블 모델)에서 다룬다.

### 3-2. DECIMAL — 물리 폭이 네 단계, 상한은 76

```java
public static int getMaxPrecisionOfDecimal(PrimitiveType t) {
    switch (t) {
        case DECIMALV2:
            return 27;
        case DECIMAL32:
            return 9;
        case DECIMAL64:
            return 18;
        case DECIMAL128:
            return 38;
        case DECIMAL256:
            return 76;
```
— `fe/fe-core/.../catalog/PrimitiveType.java:325-336`

Trino 가 18/38 두 단계로 나눈 것을 StarRocks 는 9/18/38/76 네 단계로 나눴다. **상한이 76 으로 Trino(38)의 두 배**다. 사용자가 쓰는 이름은 `DECIMAL(p,s)` 하나이고, 정밀도를 보고 물리 타입이 자동 선택된다.

### 3-3. 시간대가 타입에 없다

`TIMESTAMP WITH TIME ZONE` 에 해당하는 타입이 없다. 시간대는 **세션 변수 `time_zone` 하나로** 처리된다. 4-2 에서 이것이 Iceberg 읽기에서 어떻게 나타나는지 본다.

## 4. 실측 — 같은 Iceberg 테이블을 양쪽에서 본다

전문은 `docs/evidence/A-1/20260903-parser-dialect-and-type-mapping.md` 판별 3.

Trino 로 테이블을 만들고 양쪽에서 스키마와 값을 읽었다.

```sql
CREATE TABLE bench.typeprobe (
  ts_ntz timestamp(6),
  ts_tz  timestamp(6) with time zone,
  d      decimal(38,4),
  u      uuid,
  b      varbinary
);
```

### 4-1. 타입 표면이 좁아진다

| 컬럼 | Trino `DESCRIBE` | StarRocks `DESC` |
|---|---|---|
| `ts_ntz` | `timestamp(6)` | `DATETIME` |
| `ts_tz` | `timestamp(6) with time zone` | **`DATETIME`** |
| `d` | `decimal(38,4)` | `DECIMAL(38,4)` |
| `u` | `uuid` | `VARBINARY` |
| `b` | `varbinary` | `VARBINARY` |

**`ts_ntz` 와 `ts_tz` 가 StarRocks 에서 같은 이름이 된다.** 스키마만 보고는 어느 쪽이 시간대 보정 대상인지 알 수 없다.

### 4-2. 그러나 값의 의미는 지켜진다

세션 `time_zone` 만 바꿔 같은 행을 다시 읽었다.

| `time_zone` | `ts_ntz` | `ts_tz` |
|---|---|---|
| `Etc/UTC` | 2026-01-02 03:04:05.123456 | 2026-01-01 18:04:05.123456 |
| `Asia/Seoul` | 2026-01-02 03:04:05.123456 | **2026-01-02 03:04:05.123456** |

`ts_tz` 만 +9시간 이동했다. StarRocks 는 Iceberg 의 `adjust-to-UTC` 플래그를 **읽기 경로에서 반영하고 있다.**

**따라서 "StarRocks 는 시간대를 잃는다"는 서술은 틀렸다.** 잃는 것은 타입 표면이다. 정확히 말하면:

- 값은 맞다
- 그러나 **스키마로는 두 컬럼을 구분할 수 없다**
- 그리고 StarRocks 쪽에서 테이블을 만들 때 그 구분을 **표현할 수단이 없다**

### 4-3. UUID 는 조회 시점에 실패한다

```
ERROR 1064 (HY000): parquet column reader: not supported convert from parquet
`FIXED_LEN_BYTE_ARRAY` to `VARBINARY`: ... BE:10001
```

`DESC` 는 성공한다(`VARBINARY` 라고 답한다). 실패는 **값을 읽을 때** 난다.

원인을 좁히기 위해 같은 `VARBINARY` 인 `b` 컬럼(`X'0102'`)을 읽어봤다 — `hex(b) = 0102` 로 정상이다. 따라서 문제는 VARBINARY 가 아니라 **Parquet `FIXED_LEN_BYTE_ARRAY` → VARBINARY 경로의 부재**다.

## 5. 설계 차이와 그 원인

### 5-1. 같은 자리의 코드 두 줄

Iceberg 타입을 자기 타입으로 옮기는 곳이다.

Trino:

```java
case TIMESTAMP -> ((Types.TimestampType) type).shouldAdjustToUTC() ? TIMESTAMP_TZ_MICROS : TIMESTAMP_MICROS;
case TIMESTAMP_NANO -> ((Types.TimestampNanoType) type).shouldAdjustToUTC() ? TIMESTAMP_TZ_NANOS : TIMESTAMP_NANOS;
```
— `plugin/trino-iceberg/.../TypeConverter.java:89-90`

StarRocks:

```java
case TIMESTAMP:
    primitiveType = PrimitiveType.DATETIME;
    break;
```
— `fe/fe-core/.../connector/ColumnTypeConverter.java:667-669`

**같은 정보(`shouldAdjustToUTC`)가 한쪽에서는 분기 조건이고 다른 쪽에서는 읽히지 않는다.** 이것은 구현의 게으름이 아니라 **받을 그릇이 없기 때문**이다. StarRocks 의 `PrimitiveType` 에 대응 타입이 없으니 분기할 이유도 없다. 4-2 에서 본 시간대 보정은 이 표 아래쪽, 값을 읽는 단계에서 따로 처리된다.

같은 파일에서 DECIMAL 도 갈린다.

```java
if (precision <= 9) {
    return ScalarType.createDecimalV3Type(PrimitiveType.DECIMAL32, precision, scale);
} else if (precision <= 18) {
    return ScalarType.createDecimalV3Type(PrimitiveType.DECIMAL64, precision, scale);
} else {
    return ScalarType.createDecimalV3Type(PrimitiveType.DECIMAL128, precision, scale);
}
```
— `ColumnTypeConverter.java:675-681`

`DECIMAL256` 이 없다. Iceberg DECIMAL 의 상한이 38 이므로 **정보 손실은 아니다.** 3-2 에서 본 76자리는 StarRocks 자체 테이블에서만 쓰인다.

`UUID`, `FIXED` 처리도 대조된다.

| Iceberg 타입 | Trino | StarRocks |
|---|---|---|
| `UUID` | `UUID` (전용 타입) | `VARBINARY` → **읽기 실패** |
| `FIXED` | `VARBINARY` | `UNKNOWN_TYPE` |
| `BINARY` | `VARBINARY` | `VARBINARY` (정상) |
| `VARIANT` | `VARIANT` | 분기 없음 |
| `GEOMETRY` | `GEOMETRY` (CRS 검증 포함) | 분기 없음 |
| `TIMESTAMP_NANO` | `TIMESTAMP(9)` / `TIMESTAMP(9) WITH TIME ZONE` | 분기 없음 |

### 5-2. 타입 손실의 방향은 한쪽이다

Iceberg 를 매개로 놓고 보면 손실이 **항상 StarRocks 쪽에서만** 난다. 이유는 두 가지다.

**첫째, 설계 기준점.** `A-1-01` 에서 본 대로 StarRocks 는 MySQL 호환을 기준으로 삼았다. MySQL 에는 `TIMESTAMP WITH TIME ZONE` 도 `UUID` 도 없다. Iceberg/ANSI 는 있다. Trino 의 타입 어휘가 Iceberg 와 가까운 것은 우연이 아니라 **둘 다 ANSI 를 기준점으로 삼았기 때문**이다.

**둘째, 타입 체계의 위치.** Trino 의 타입은 `trino-spi` 에 있고 커넥터가 그 어휘로 말한다. 커넥터가 새 타입을 필요로 하면 SPI 에 추가하는 경로가 열려 있다. StarRocks 의 타입은 FE 카탈로그의 `PrimitiveType` 열거형이고, **BE 의 C++ 타입과 짝을 맞춰야 하므로 추가 비용이 크다.** 이 비대칭은 `A-5-01`(커넥터 추가 난이도)에서 다루는 FE/BE 이원 구조와 같은 뿌리다.

### 5-3. UUID 실패는 타입 문제가 아니라 이원 구조 문제다

4-3 의 실패를 다시 보면, FE 는 "이 컬럼은 VARBINARY 다"라고 **정상적으로 답한다.** 거부는 BE 의 Parquet 리더가 한다. 즉 **FE 의 타입 매핑 표와 BE 리더의 지원 범위가 어긋나 있고, 그 어긋남이 조회 시점에야 드러난다.**

Trino 에는 이 실패 유형이 구조적으로 생기기 어렵다. 타입 매핑과 리더가 같은 JVM 안의 같은 커넥터 모듈에 있어, 매핑을 추가하면 리더도 같은 코드베이스에서 따라간다.

이 관찰은 `A-5-03`(파일 리더)의 증거(`evidence/A-5/20260820-...`)와 성격이 같다 — 그쪽은 BE 프로세스가 죽었고 여기서는 오류로 끝났지만, **원인의 위치는 둘 다 FE/BE 경계**다.

## 6. 결론

**동등하지 않다 — 표현력의 총량이 아니라 어휘의 방향이 다르다.**

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 타입 정의 위치 | `trino-spi` (플러그인 확장 가능) | FE `PrimitiveType` 열거형 (+ BE C++ 짝) |
| DECIMAL 상한 | 38 (물리 2단계: 18/38) | **76** (물리 4단계: 9/18/38/76) |
| TIMESTAMP 정밀도 | `TIMESTAMP(p)`, p=0~12 | `DATETIME` (파라미터 없음) |
| 시간대 | **타입에 포함** (`WITH TIME ZONE`) | 세션 변수 `time_zone` |
| 한쪽만 가진 것 | `UUID` `IPADDRESS` `VARIANT` `INTERVAL` `QDIGEST`/`TDIGEST` | `LARGEINT` `BITMAP` `HLL` `PERCENTILE` |
| 중첩 타입 | `ARRAY` `MAP` `ROW` | `ARRAY` `MAP` `STRUCT` |
| Iceberg `timestamptz` | 전용 타입으로 구분 | `DATETIME` 로 합쳐짐 (값 의미는 유지) |
| Iceberg `UUID` | 정상 | **조회 실패** (BE 리더 미지원) |

**실무 결론**

1. **StarRocks 를 Iceberg 조회에 쓸 때는 스키마를 그대로 믿으면 안 된다.** `DESC` 가 성공해도 조회가 실패할 수 있고(UUID), 같은 `DATETIME` 이라도 시간대 보정 여부가 다를 수 있다. 이전 시 컬럼 단위 조회 확인이 필요하다
2. **시간대가 섞인 데이터를 다룬다면 이 차이는 설계 제약이다.** StarRocks 에서는 "이 컬럼이 UTC 기준인가"를 스키마로 표현할 수 없으므로 명명 규칙이나 문서로 관리해야 한다
3. **38자리를 넘는 DECIMAL 이 필요하면 StarRocks 쪽이 유일한 선택지다.** 단 Iceberg 를 매개로 하면 38 이 상한이므로, StarRocks 네이티브 테이블에서만 의미가 있다

### 아직 답하지 않은 것

- **ORC / Avro** — 4-3 의 UUID 실패는 Parquet 리더에서 확인했다. 다른 포맷에서 같은지 확인하지 않았다
- **중첩 타입의 세부 대조** — `ROW` vs `STRUCT` 의 필드명 대소문자, 익명 필드, 깊은 중첩에서의 동작을 확인하지 않았다
- **암묵 캐스트 규칙** — 같은 타입 이름이라도 연산 시 승격 규칙이 다르면 결과가 갈린다. `DECIMAL` 산술의 결과 정밀도 규칙이 대표적이며, 이 문서에서 다루지 않았다
- **StarRocks 네이티브 테이블의 타입 동작** — 이 문서는 Iceberg 를 매개로만 비교했다. `C-1-01`(테이블 모델)에서 `BITMAP`/`HLL` 이 실제로 어떻게 쓰이는지 다룬다
