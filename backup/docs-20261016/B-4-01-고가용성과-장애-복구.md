## 1. 비교 관점

장애 복구는 세 층으로 나뉜다.

1. **메타데이터** — 카탈로그·스키마가 사라지면 클러스터가 아니다
2. **제어 평면** — 쿼리를 받고 조율하는 노드가 죽으면
3. **실행 평면** — 계산 중인 노드가 죽으면

**세 층에서 두 엔진의 강약이 정반대로 나온다.** StarRocks 는 1층이 튼튼하고 3층이 약하다. Trino 는 1층이 아예 없고(스토리지가 없으니) 3층에 FTE 라는 정교한 장치가 있다. 2층은 **양쪽 다 약하다.**

---

## 2. 메타데이터 (1층)

### 2-1. StarRocks — 복제된 저널

FE 는 메타데이터를 **BDB JE 기반 복제 저널**로 관리한다.

```java
public enum FrontendNodeType {
    LEADER,
    FOLLOWER,
    OBSERVER,
    INIT,
    UNKNOWN
}
```
— `fe/fe-core/.../ha/FrontendNodeType.java`

`ha/` 패키지에 `BDBHA`, `BDBStateChangeListener`, `HAProtocol`, `LeaderInfo`, `StateChangeExecutor` 가 있고, `journal/bdbje/` 에 저널 구현이 있다.

- **LEADER** — 쓰기를 받고 저널을 만든다
- **FOLLOWER** — 저널을 복제받고 **선거에 참여한다.** LEADER 가 죽으면 그중 하나가 승격된다
- **OBSERVER** — 복제만 받고 선거에 참여하지 않는다. 읽기 확장용

즉 **FE 는 과반수 기반 자동 장애 조치를 갖춘 복제 상태 기계**다. 체크포인트도 있다(`CheckpointWorker`, `GlobalStateCheckpointWorker`).

### 2-2. Trino — 이 층이 없다

Trino 는 **메타데이터를 소유하지 않는다.** 스키마와 테이블 정의는 전부 커넥터 뒤(Hive Metastore, Iceberg 카탈로그, PostgreSQL…)에 있다.

**따라서 "Trino 의 메타데이터 HA" 라는 질문 자체가 성립하지 않는다.** 그 책임은 카탈로그 쪽으로 넘어간다 — 랩에서는 HMS + PostgreSQL 이 그 역할을 하고, 그것의 이중화는 Trino 의 관심사가 아니다.

**이것은 약점이 아니라 다른 설계다.** 다만 운영 관점에서 **책임 소재가 클러스터 밖으로 나간다**는 뜻이므로, 별도 팀·별도 절차가 필요하다.

## 3. 제어 평면 (2층)

### 3-1. Trino — 코디네이터가 단일 지점이다

공식 문서가 구조를 명시한다.

```
A Trino cluster consists of several Trino [nodes](trino-concept-node) - one
[coordinator](trino-concept-coordinator) and zero or more
[workers](trino-concept-worker).
```
— `docs/src/main/sphinx/overview/concepts.md:36-38`

**"one coordinator"** 다. 설정도 불리언 하나다.

```java
private boolean coordinator = true;
```
— `core/trino-main/.../server/ServerConfig.java:27`

코디네이터가 죽으면 **진행 중인 모든 쿼리가 사라진다.** 이 저장소의 클론에는 이중화 장치가 없다.

대체 수단은 **Trino Gateway**(별도 프로젝트, `C-2-02`)다. 클러스터를 여러 개 두고 그 앞에 게이트웨이를 세워 라우팅한다. 즉 **코디네이터를 이중화하는 것이 아니라 클러스터를 이중화한다.**

### 3-2. StarRocks — FE 는 이중화되지만 쿼리는 살아남지 않는다

2-1 의 FOLLOWER 승격이 제어 평면 HA 를 제공한다. **다만 승격은 메타데이터를 잇는 것이지 진행 중이던 쿼리를 잇는 것이 아니다.** 죽은 FE 가 조율하던 쿼리는 사라진다.

**따라서 2층에서 "진행 중인 쿼리"만 놓고 보면 양쪽 다 잃는다.** 차이는 **클러스터가 새 쿼리를 받을 수 있게 되기까지의 시간**이다 — StarRocks 는 자동 선거로 수초~수십초, Trino 는 새 코디네이터를 띄우거나 게이트웨이가 다른 클러스터로 돌릴 때까지다.

## 4. 실행 평면 (3층)

### 4-1. Trino — FTE 가 있고, 기본은 꺼져 있다

`A-4-02` 3-1 에서 다룬 내용이다. 핵심만 옮긴다.

```java
public enum RetryPolicy
{
    TASK(RetryMode.RETRIES_ENABLED),
    QUERY(RetryMode.RETRIES_ENABLED),
    NONE(RetryMode.NO_RETRIES),
```
— `core/trino-main/.../operator/RetryPolicy.java:18-23`

`TASK` 모드에서는 셔플 결과가 외부 저장소에 파일로 남으므로 **죽은 태스크만 다시 돌린다.** 진행된 작업이 보존된다.

`B-1-01` 2-2 에서 본 `LeastWastedEffortTaskLowMemoryKiller` 가 이 위에 선다 — **"버리는 작업량이 가장 적은 태스크"를 고르는 것은 태스크 재시도가 가능해야 의미가 있다.**

기본값은 `NONE` 이다. 대화형 쿼리에는 파일 왕복이 손해이기 때문이다.

### 4-2. StarRocks — 쿼리 전체 재실행

```java
int retryTime = Config.max_query_retry_time;
```
— `fe/fe-core/.../qe/StmtExecutor.java:863`

```java
public static int max_query_retry_time = 2;
```
— `fe/fe-core/.../common/Config.java:1678`

**최대 2회, 쿼리 단위**다. 중간 결과가 남지 않으므로 처음부터 다시 돈다.

그리고 죽은 BE 는 명단에서 빠진다.

```java
public static void addToBlocklist(Long backendID) {
    HOST_BLACKLIST.add(backendID);
}
```
— `fe/fe-core/.../qe/SimpleScheduler.java:172-174`

호출부 5곳이 전부 실행 경로다(`ExecutionDAG:643`, `ResultReceiver:138,147`, `DefaultCoordinator:777`, `FragmentInstanceExecState:410`). **즉 재시도는 살아 있는 노드에서 이뤄진다.**

`A-5-03` 3-3 에서 지적한 위험이 여기서 구체화된다 — 문제가 특정 파일이나 쿼리 패턴에 있으면 **재시도할 때마다 다음 BE 가 차례로 죽고**, 블랙리스트는 빼기만 하므로 남는 노드가 없어진다.

## 5. 실측

전문은 `docs/evidence/B/20260904-node-failure-probes.md`.

실행 노드를 실제로 정지시켰다. **워커/BE 가 1대뿐이라 "나머지로 계속하는가"는 판별할 수 없고**, 확인한 것은 **실패 방식과 복구 시간**이다.

### 5-1. Trino — 62초 기다린 뒤 실패

```
Query ... failed: Encountered too many errors talking to a worker node. The node
may have crashed or be under too much load. This is probably a transient issue,
so please retry your query in a few minutes.
(... - 15 failures, failure duration 62.25s, total failed request time 67.25s)
```

**62.25초 동안 15번 재시도했다.** 이 숫자가 코드와 정확히 맞는다 — `A-4-01` 3-2 의 `maxErrorDuration = 1분` 이다.

**오류 메시지에 판단이 들어 있다** — *"This is probably a transient issue"*. Trino 는 노드 사망을 **일시적 장애로 가정하고 오래 기다린다.**

### 5-2. StarRocks — 즉시 실패

```
ERROR 1064 (HY000) at line 1: Failed to find backend to execute
```

**기다리지 않는다.** FE 가 실행 가능한 BE 목록을 항상 들고 있어 계획 단계에서 곧장 거부한다.

이 메시지는 `A-5-03` 의 4.0.1 크래시에서 사용자가 본 것과 **완전히 같다.** 즉 **BE 가 죽은 원인이 무엇이든 사용자에게는 구분되지 않는다.**

### 5-3. 복구

| | 결과 |
|---|---|
| Trino | 워커 재기동 후 자동 복귀(`system.runtime.nodes` active=2) |
| StarRocks | **19초** 후 정상. `SHOW BACKEND BLACKLIST` 는 비어 있음 |

정상 종료(`docker compose stop`)라 블랙리스트에 등록되지 않았다. 비정상 종료 시 동작은 확인하지 못했다.

## 6. 설계 차이와 그 원인

### 6-1. 요약 — 층마다 강약이 반대다

| 층 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| **메타데이터** | 소유하지 않음 — 커넥터 책임 | **BDB JE 복제 저널 + LEADER/FOLLOWER/OBSERVER 자동 선거** |
| **제어 평면** | **코디네이터 1대**(문서 명시). 대체 수단은 Trino Gateway | FE 이중화. 단 진행 중 쿼리는 잃는다 |
| **실행 평면** | **FTE — 태스크 단위 재시도**(기본 꺼짐) | 쿼리 전체 재실행 **최대 2회** + BE 자동 블랙리스트 |
| 노드 사망 감지 | 교환 클라이언트의 재시도 실패 — **62초** | FE 노드 목록 — **즉시** |
| 사망 가정 | **일시적 장애** | 영구 장애 |

### 6-2. 왜 강약이 정반대인가

**StarRocks 는 상태를 소유한다.** 태블릿과 메타데이터가 클러스터 안에 있으니 **잃으면 안 된다.** 그래서 1층에 복제 저널과 선거를 넣었다. 반대로 계산 중간 결과는 어차피 데이터가 로컬에 있어 다시 읽으면 되므로, **재실행이 합리적인 선택**이다.

**Trino 는 상태가 없다.** 잃을 메타데이터가 없으니 1층이 필요 없다. 그러나 **계산은 원격 저장소에서 데이터를 끌어와야 하므로 다시 하는 비용이 크다.** 그래서 3층에 FTE 를 넣었다.

**즉 각자 "잃으면 아까운 것"을 지키도록 설계했다.** 우열이 아니다.

### 6-3. 62초 대 즉시 — 어느 쪽이 옳은가

가정이 다를 뿐 둘 다 근거가 있다.

- **Trino 의 62초**는 GC 정지·일시적 네트워크 문제를 넘기려는 것이다. 워커가 상태 없이 교체 가능하다는 전제에서, 잠깐 느린 노드를 죽은 것으로 취급하면 손해가 크다
- **StarRocks 의 즉시 실패**는 FE 가 하트비트로 노드 상태를 이미 알고 있기 때문에 가능하다. 기다릴 이유가 없다

**실무에서는 Trino 쪽 62초가 더 자주 문제가 된다.** 대화형 쿼리가 1분간 멈춰 있다 실패하면 사용자는 "행 걸렸다"고 인식한다. `exchange.max-error-duration` 을 줄이는 것이 조정 수단이다.

### 6-4. 장수 쿼리에서 격차가 벌어진다

`plan/01` 이 이 축을 **"장수 ETL 쿼리에서 갈리는 지점"** 이라고 적은 것이 정확하다.

| 쿼리 길이 | 노드 사망 시 손실 |
|---|---|
| 수 초 | 양쪽 다 무시할 만하다. 다시 돌리면 된다 |
| 수 분 | StarRocks 는 처음부터. Trino 는 기본 설정이면 마찬가지 |
| **수십 분~시간** | StarRocks 는 **전부 버린다**(2회 재시도도 전부 다시). **Trino FTE 만이 진행분을 살린다** |

그리고 **길수록 노드를 잃을 확률 자체가 높아진다.** 이 구간에서는 FTE 가 선택이 아니라 요건에 가깝다.

### 6-5. BE 사망의 무게가 워커 사망보다 크다

`A-5-03` 5-3 에서 짚은 것을 다시 적는다. **Trino 워커는 상태가 없어 죽어도 다시 띄우면 그만이지만, StarRocks BE 는 태블릿을 들고 있다.** 죽은 BE 가 갖고 있던 데이터는 복제본이 있어야 접근 가능하고, 복귀하면 따라잡기(clone)가 필요하다 — `B-1-01` 3-1 의 `MemTracker::Type` 에 `CLONE` 이 있는 이유다.

**즉 StarRocks 에서 BE 다중화는 성능이 아니라 가용성 요건이다.**

## 7. 결론

**동등하지 않다 — 층마다 강약이 정반대다.**

- **메타데이터**: StarRocks 가 복제 저널과 자동 선거를 갖췄다. Trino 는 이 층이 없고 책임이 카탈로그로 넘어간다
- **제어 평면**: **양쪽 다 약하다.** Trino 는 코디네이터 1대(문서 명시), StarRocks 는 FE 를 이중화하지만 진행 중 쿼리는 잃는다
- **실행 평면**: **Trino FTE 만이 진행분을 살린다.** StarRocks 는 쿼리 전체 재실행 최대 2회
- **감지**: Trino 62초(일시적 장애 가정) vs StarRocks 즉시(영구 장애 가정) — 실측 확인

**실무 결론**

1. **수십 분 이상 도는 ETL 이 있다면 Trino FTE 가 사실상 유일한 답이다.** StarRocks 에서는 그 길이의 쿼리를 SQL 엔진에 맡기지 말고 잘게 쪼개는 편이 낫다
2. **StarRocks 에서 BE 다중화는 선택이 아니다.** BE 는 데이터를 들고 있고, 리더 결함으로 프로세스가 죽을 수 있으며(`A-5-03`), FE 는 죽은 BE 를 명단에서 빼기만 한다
3. **Trino 의 코디네이터 이중화는 클러스터 밖에서 해결해야 한다** — Trino Gateway + 다중 클러스터(`C-2-02`)
4. **Trino 에서 노드 사망이 잦다면 `exchange.max-error-duration` 을 줄여라.** 기본 1분은 대화형 쿼리에 길다
5. **StarRocks 의 `Failed to find backend to execute` 는 원인을 구분하지 않는다.** 리더 결함으로 죽었는지 네트워크 문제인지 알 수 없으므로, BE 로그를 함께 봐야 한다

### 아직 답하지 않은 것

- **이 축의 핵심 질문이 미검증이다** — 워커/BE 1대라 **"한 대가 죽어도 나머지로 계속하는가"** 를 확인하지 못했다. FTE 의 태스크 단위 재시도도 마찬가지다. 다중 노드 랩이 필요하다(`plan/02` 6-3절)
- **FE 장애 조치** — FE 1대라 FOLLOWER 승격을 확인하지 못했다
- **비정상 종료** — `docker compose stop`(정상 종료)만 시험했다. SIGKILL 이나 프로세스 크래시에서 블랙리스트 동작이 다를 수 있다
- **연쇄 사망** — `A-5-03` 3-3 과 4-2 에서 지적한 "재시도할 때마다 다음 BE 가 죽는" 시나리오를 재현하지 못했다
- **FTE 의 실제 비용과 이득** — 파일 왕복이 늘리는 지연도, 재시도로 아끼는 시간도 재지 않았다
- **복제본 수와 데이터 가용성** — StarRocks 네이티브 테이블의 복제 정책은 `C-1` 의 주제다
