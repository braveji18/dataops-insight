## 1. 비교 관점

이 문서는 **연구 전체의 마지막 각도**다. 앞선 27편이 "무엇을 어떻게 하는가"를 봤다면, 여기는 **"그 코드를 다루는 것이 어떤 일인가"** 를 본다.

두 가지를 본다.

1. **규모와 그 분포** — 어디에 코드가 몰려 있는가
2. **기여 난이도** — 무엇을 바꾸려면 어디까지 알아야 하는가

**먼저 밝힐 한계가 있다.** `works/` 는 **얕은 클론**이라 커밋 이력과 릴리스 주기를 볼 수 없다. `plan/01` 이 이 축에 "커밋 활동, 릴리스 주기"를 넣었으나 **그 부분은 답하지 못한다.**

```
trino     50b0b50b [maven-release-plugin] prepare release 483
starrocks 7c18dd9d [BugFix] ... (backport #77404) ...
```

각각 커밋 하나씩만 있다.

## 2. 규모

### 2-1. 계측

`src/main` 과 `src/test` 를 나눠 셌다.

| 영역 | 파일 | 줄 |
|---|---|---|
| **Trino** Java (main) | 7,572 | **1,169,458** |
| **Trino** Java (test) | 3,561 | 831,798 |
| **StarRocks FE** Java (main) | 3,642 | **755,539** |
| **StarRocks FE** Java (test) | 1,565 | 478,004 |
| **StarRocks BE** C++ (src) | 2,747 | **633,327** |
| **StarRocks BE** C++ (test) | 628 | 296,820 |

본체만 합치면 **Trino 1,169,458 / StarRocks 1,388,866**(FE + BE). **StarRocks 쪽이 19% 크다.**

**단순 비교가 위험한 이유가 둘 있다.**

1. **언어가 다르다.** 같은 일을 C++ 로 쓰면 Java 보다 줄이 늘어나기 쉽다(헤더 분리 등)
2. **제품 경계가 다르다.** StarRocks 는 스토리지·적재·compaction 을 포함하고(`C-1`), Trino 는 그것이 없는 대신 커넥터 27개를 포함한다(`C-2-02`)

### 2-2. 어디에 몰려 있는가 — Trino

| 영역 | 줄 | 비중 |
|---|---|---|
| `core/` | 567,770 | 55% |
| **`plugin/`** | **308,781** | **30%** |
| `lib/` | 151,660 | 15% |

**플러그인이 전체의 30%다.** `C-2-01`·`C-2-02` 의 결론이 숫자로 확인된다 — **커넥터 생태계가 코드베이스의 3분의 1을 차지한다.**

`lib/` 15% 는 파일 리더(`A-5-03`)와 문법(`A-1-01`) 등 공용 라이브러리다.

**즉 Trino 코어 엔진 자체는 567,770줄이고, 나머지 44%는 "붙이는 것들"이다.**

### 2-3. 어디에 몰려 있는가 — StarRocks

최상위 디렉토리가 제품 경계를 보여준다.

```
be/ bin/ build-support/ community/ conf/ contrib/ docker/ docs/ extra/ fe/
format-sdk/ fs_brokers/ gensrc/ images/ java-extensions/ licenses/ test/
thirdparty/ tools/ webroot/
```

Trino 는 7개(`client core docs lib plugin service testing`)다.

**`gensrc/`, `thirdparty/`, `fs_brokers/`, `java-extensions/`, `format-sdk/`, `webroot/` 가 StarRocks 에만 있다** — `D-01` 에서 본 이중 빌드와 59개 네이티브 의존성, 그리고 FE 가 웹 UI 를 직접 제공한다는 사실이 디렉토리로 드러난다.

FE 755,539 대 BE 633,327 로 **거의 반반**이다. `A-5-01` 이 "FE/BE 양쪽을 수정해야 한다"고 결론지은 구조가 규모에서도 대칭이다.

### 2-4. 테스트 비중

| | 테스트 / 본체 |
|---|---|
| Trino | **71%** |
| StarRocks FE | 63% |
| StarRocks BE | 47% |

**BE 쪽 47%가 눈에 띈다.** `A-5-03` 에서 본 대로 **BE 의 결함은 프로세스 사망으로 이어지는데**, 테스트 비중은 가장 낮다. 인과를 주장할 근거는 없지만 **기록할 값어치가 있는 대조**다.

## 3. 기여 난이도

### 3-1. 무엇을 바꾸려면 어디까지 알아야 하는가

앞선 문서들의 결론을 모으면 표가 된다.

| 하고 싶은 일 | Trino | StarRocks |
|---|---|---|
| 커넥터 추가 | **`trino-spi` 만**, 플러그인 JAR (`A-5-01`) | `ConnectorType` 열거형 + FE + BE + Thrift |
| 스칼라 함수 추가 | **애노테이션 붙은 Java 메서드**, 플러그인 가능 (`A-1-03`) | `functions.py` ID 부여 + BE C++ + 양쪽 재빌드 |
| 타입 추가 | `trino-spi` 의 `Type` (`A-1-02`) | `PrimitiveType` 열거형 + BE C++ 짝 |
| 접근제어 정책 | **SPI** (`B-5-01`) | `AccessController` 구현(내부) 또는 Ranger |
| 관측 대상 추가 | **`EventListener` SPI** (`B-6-01`) | `AuditPlugin`(감사 한정) |
| 셔플 저장소 교체 | **`ExchangeManager` SPI** (`A-4-02`) | 불가 |
| 리소스 그룹 정책 | **SPI** (`B-2-01`) | 불가(SQL 객체로 고정) |
| 옵티마이저 규칙 추가 | 코어 수정 | 코어 수정 |
| 실행 연산자 추가 | 코어 수정 | **FE + BE 코어 수정** |

**경계가 분명하다.** Trino 에서 "SPI 로 되는가"의 답이 예이면 **엔진을 몰라도 된다.** 아니면 `core/` 567,770줄을 상대해야 한다.

StarRocks 에서는 **거의 모든 항목이 코어 수정**이고, 그것은 곧 FE(Java)와 BE(C++) 양쪽 + `gensrc` 코드 생성 + 이중 빌드(`D-01`)를 뜻한다.

### 3-2. SPI 안정성이 실제로 주는 것

`C-2-01` 2-3 에서 본 `@Unstable` 애노테이션(26곳)과 `D-01` 3-1 의 `trino-plugin-reader` 가 짝이다.

**"바뀌지 않는다"는 약속이 있어야 외부 개발이 성립한다.** 플러그인을 만든 사람은 Trino 가 483 에서 484 로 올라가도 자기 코드가 도는지 예측할 수 있어야 한다.

StarRocks 에는 이 계약이 없다 — **필요가 없다.** 외부 코드가 붙을 자리가 없으니 내부 구조를 자유롭게 바꿀 수 있다. **이것은 장점이기도 하다** — `A-3-05` 의 JIT, `C-1-02` 의 벡터 인덱스 같은 것을 만들려면 내부를 크게 흔들어야 한다.

### 3-3. 답하지 못하는 부분

`plan/01` 이 이 축에 넣은 **"커밋 활동, 릴리스 주기"** 는 얕은 클론이라 볼 수 없다.

다만 **간접 신호는 하나 있다.** StarRocks 쪽 HEAD 커밋 메시지다.

```
[BugFix] Also disable the query cache when a SortNode builds the TOPN_FILTER
(backport #77404) (backport #77429) (#77525)
```

**`backport` 가 두 번 겹쳐 있고 PR 번호가 77,000번대다.** 4.0.14 라는 패치 버전 자체와 함께, **활발한 유지보수 브랜치가 돌고 있다**는 신호로 읽을 수는 있다. 그러나 **이것으로 활동량을 비교하는 것은 부당하다** — Trino 쪽은 릴리스 준비 커밋 하나만 잡혔을 뿐이다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 본체 규모 | 1,169,458줄 (Java) | **1,388,866줄** (FE 755,539 + BE 633,327) |
| 최상위 디렉토리 | 7 | **20** |
| 코드 분포 | core 55% / **plugin 30%** / lib 15% | FE 54% / BE 46% |
| 테스트 비중 | **71%** | FE 63% / **BE 47%** |
| 외부 기여 경로 | **SPI 16종** | 사실상 upstream 기여만 |
| 안정성 계약 | `@Unstable` + `plugin-reader` 검증 | 없음(필요 없음) |

### 5-2. 규모의 19% 차이는 무엇인가

**StarRocks 가 더 큰 이유는 "더 많은 일을 하기 때문"** 이다. 스토리지 엔진(`C-1`), 적재 파이프라인(`C-1-04`), compaction(`C-1-03`), 리소스 스케줄러(`B-2-01`), 메타데이터 복제(`B-4-01`) — 전부 Trino 에 없는 것이다.

반대로 Trino 는 **커넥터 27개와 파일 리더 두 벌**(`A-5-03`)을 갖고 있고, 그것이 44%다.

**즉 규모 비교는 "누가 더 복잡한가"가 아니라 "어디까지를 제품으로 보는가"의 반영이다.**

### 5-3. 플러그인 30%가 뜻하는 것

Trino 코드베이스의 30%가 플러그인이라는 것은 **코어 팀이 그 전부를 유지보수하지 않아도 된다**는 뜻이기도 하다. `C-2-02` 5-2 에서 본 `loki`, `faker`, `ai-functions` 같은 커넥터는 필요한 사람이 만들어 넣은 것이다.

**동시에 위험이기도 하다.** `A-5-02` 2-2 에서 확인한 대로 커넥터마다 푸시다운 구현 범위가 크게 다르다 — 코어 팀이 관리하지 않으니 품질이 균일할 수 없다.

### 5-4. BE 테스트 47%

3절에서 짚은 대조를 다시 적는다.

- **BE 는 결함의 대가가 가장 크다** — 프로세스 사망, 그것도 데이터를 들고 있는 프로세스(`A-5-03` 5-3)
- **BE 는 테스트 비중이 가장 낮다** — 47%
- **BE 는 언어가 C++ 이라 실수의 여지가 가장 크다** — 경계 검사가 없다

**인과를 주장하지 않는다.** C++ 테스트는 Java 보다 줄당 밀도가 높을 수 있고, SQL regression(`test/sql/`)이 BE 를 간접 검증하기도 한다. 다만 `evidence/A-5/20260820-...` 의 실제 크래시가 이 영역에서 나왔다는 사실과 함께 놓고 볼 값어치가 있다.

### 5-5. 이 축의 결론이 다른 축을 설명한다

이 연구에서 반복된 구도를 마지막으로 정리하면 이렇다.

**Trino 는 "경계를 만들고 그 뒤를 남에게 맡긴다."**
→ SPI 16종(`C-2-01`), 커넥터 27개(`C-2-02`), 플러그인 30%, 안정성 계약, 단일 언어 빌드(`D-01`)
→ 대가: 커넥터마다 능력이 다르고(`A-5-02`), 스토리지가 없어 못 하는 것이 있다(`C-1`, `A-2-06`)

**StarRocks 는 "경계를 없애고 전부 소유한다."**
→ 스토리지·적재·compaction·스케줄러·메타데이터 복제, C++ 실행 엔진
→ 대가: 확장이 upstream 기여뿐이고(`A-5-01`), 이중 빌드이며(`D-01`), 결함의 폭발 반경이 크다(`A-5-03`)

## 6. 결론

**규모는 비슷하고(19% 차), 그 안의 구성이 정반대다.**

- **Trino**: 코어 55% + **플러그인 30%** + 라이브러리 15%. 테스트가 본체의 71%
- **StarRocks**: FE 54% + BE 46%. 최상위 디렉토리 20개가 제품 경계의 넓이를 보여준다
- **기여 난이도**: Trino 는 "SPI 로 되는가"가 경계선이고, StarRocks 는 거의 모든 것이 코어 수정 + 이중 빌드
- **답하지 못한 것**: 얕은 클론이라 **커밋 활동과 릴리스 주기를 비교할 수 없다**

**실무 결론**

1. **엔진을 고쳐 쓸 계획이 있다면 Trino 가 압도적으로 싸다.** 대부분 플러그인으로 해결되고, 안 되는 경우에도 단일 언어다
2. **고쳐 쓸 계획이 없다면 이 축은 선택에 영향을 주지 않는다.** 규모도 기여 난이도도 운영자에게는 보이지 않는다
3. **StarRocks 에 버그를 발견하면 FE/BE 중 어디인지부터 가려야 한다.** 오류 메시지에 `BE:10001` 같은 표시가 있는지가 첫 단서다(`A-5-03`·`B-2-01` 에서 실제로 그렇게 썼다)
4. **커넥터 품질은 개별 확인이 필요하다.** Trino 의 플러그인 30%는 코어 팀이 다 관리하지 않는다

### 아직 답하지 않은 것

- **커밋 활동·릴리스 주기** — 얕은 클론이라 볼 수 없다. `plan/01` 이 이 축에 넣은 항목인데 답하지 못했다. 전체 클론을 받으면 가능하다
- **기여자 수와 분포** — 같은 이유로 불가
- **이슈·PR 처리 속도** — GitHub API 가 필요하고 이 연구의 범위 밖이다
- **줄 수의 질** — 주석·빈 줄을 걸러내지 않았고, 생성 코드도 클론에 없어 제외됐다. **절대값보다 비율로 읽어야 한다**
- **BE 테스트 비중이 낮은 것의 의미** — 5-4 에서 인과를 주장하지 않았다. SQL regression 의 간접 커버리지를 평가하지 못했다
- **문서화 수준** — `docs/` 를 비교하지 않았다. StarRocks 는 다국어 문서를 저장소에 갖고 있다(`docs/ja/` 등을 조사 중 확인했다)
