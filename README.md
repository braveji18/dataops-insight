# dataops-insight

## 프로젝트 개요
- 오픈소스 trino 와 StarRocks를 소스코드에서 기능을 비교하는 프로젝트입니다.
- trino git url : https://github.com/trinodb/trino.git
- StarRocks  git url : https://github.com/StarRocks/starrocks.git


## 디렉토리 구조

- works : trino와 starrocks를 소스코드를 다운받아서 코드 분석을 위한 디렉토리
- plan :  trino 와 starrocks을 비교하기 위한 계획 문서를 저장하는 디렉토리
- scripts : 비교 작업을 진행하는 코드를 저장하는 디렉토리
  - scripts/testenv : 두 엔진을 동일 조건으로 띄우는 테스트 환경(lakehouse-lab)
- docs : 비교 결과를 저장하는 디렉토리
  - docs/00-목차.md : 산출 문서 목록과 진행 상태
  - docs/evidence : 실제 쿼리로 확인한 검증 증거
  - docs/report : 경영·관리자 보고용으로 다시 쓴 문서


## 테스트 환경

소스코드 분석 결과를 실제 쿼리로 검증하기 위한 로컬 Docker 랩.
Trino(coordinator+worker)와 StarRocks(FE+BE)가 **동일한 Iceberg 카탈로그**(Hive Metastore + MinIO)를 공유한다.

```bash
cd scripts/testenv
bin/up.sh                                          # 기동 + 시드 + 상태 점검
bin/q.sh trino "SELECT count(*) FROM lineitem"
bin/q.sh sr    "SELECT count(*) FROM lineitem"
```

- 사용법: `scripts/testenv/README.md`
- 설계 근거와 한계: `plan/02-테스트환경-설계.md`
- 버전 기준선: `scripts/testenv/versions.env` (works/ 클론 태그와 반드시 일치)

AI로 작업할 때는 skill `lakehouse-lab` 과 agent `dual-engine-runner` 가 이 환경을 다룬다.


## 보고용 문서 작성 (exec-report)

`docs/` 본문은 소스 경로와 라인 번호가 촘촘히 박힌 **검증용 문서**다. 그대로는 비전문가가 읽지 못한다.
같은 내용을 **읽는 사람이 판단할 수 있는 형태**로 옮기는 절차를 skill `exec-report` 로 고정해 두었다.

산출물은 `docs/report/<번호>-<제목>-보고.md`, 진행 상태는 `docs/00-목차.md` 의 "보고용 문서" 절이 관리한다.

### 원칙

1. **요약이 아니라 번역이다.** 분량을 줄이는 게 목적이 아니라 *용어와 근거 제시 방식*을 바꾸는 것이다. 근거(코드)는 오히려 늘어난다
2. **모든 기능 설명에 실제 코드와 GitHub 영구 링크를 붙인다.** "그렇다더라"가 아니라 "여기 있습니다"여야 보고가 성립한다
3. **확인하지 못한 것을 반드시 별도 절로 적는다.** 보고서의 신뢰는 여기서 나온다. 특히 "어느 쪽이 빠른가"를 재지 않았으면 명시한다
4. **정정 이력을 숨기지 않는다.** 틀렸다가 고친 항목은 경위를 짧게 남긴다
5. **측정하지 않은 것에서 우열을 말하지 않는다**

### 절차 7단계

| 단계 | 하는 일 | 왜 |
|---|---|---|
| 1 | `plan/01` 의 해당 축 질문과 원본을 대조해 **빠진 항목부터 원본에 보강** | 보고서에만 있고 원본에 없는 내용을 만들지 않는다 |
| 2 | 인용할 코드 확정 (`grep -n` 으로 라인 번호). **부정 주장은 반드시 검색으로 확인** | "~기능이 없다"를 확인 없이 썼다가 틀린 적이 있다 |
| 3 | GitHub 영구 링크 생성 — 브랜치가 아니라 **비교 기준 태그** | `versions.env` / `works/` 클론 태그와 일치해야 한다 |
| 4 | 코드 기준값을 **읽는 사람의 단위로 환산**하고, 환산했다는 사실을 밝힌다 | 코드를 직접 연 사람이 숫자 차이를 알 수 있어야 한다 |
| 5 | 코드 블록마다 **▸ 읽는 법** 한 문단 | 코드만 있으면 비전문가에게는 장식이다 |
| 6 | 발췌 정확성을 **스크립트로 대조** | "이 코드가 원문 그대로냐"는 질문이 반드시 나온다 |
| 7 | `docs/00-목차.md` 상태 갱신 후 커밋 | |

### 보고서 뼈대

`.claude/skills/exec-report/references/template.md` 에 있다.

| 절 | 내용 |
|---|---|
| 한 장 요약 | 비교표 + 한 문장 결론 — 이것만 읽어도 되게 |
| 1. 왜 이걸 봤나 | 실무에서 왜 중요한지 (기술 배경 아님) |
| 2~3. 각 제품의 방식 | 설명 → **코드** → 읽는 법 |
| 4. 실제로 돌려서 확인한 것 | 실측 결과, 정정 이력. 없으면 "안 했다"고 명시 |
| 5. 실무에서 의미 있는 차이 | 운영자 관점 2~3가지 — 보고의 알맹이 |
| 6. 확인하지 못한 것 | 항목 / 이유 / 필요한 것. **생략 금지** |
| 7. 참고 | 원본 문서, 실험 기록, 소스 링크 |

### 발췌 대조

```bash
python3 .claude/skills/exec-report/scripts/verify-code-blocks.py docs/report/01-조인-순서-결정-보고.md
```

링크의 라인 범위와 바로 뒤 코드 블록을 `works/` 클론과 문자 단위로 비교한다.
가독성을 위해 줄인 발췌는 불일치로 잡히는데 이는 정상이며, 대신 **무엇을 줄였는지 블록에 표기**한다.
표기 없는 불일치는 고쳐야 할 오류다.

### 겪은 실패

| 실패 | 어떻게 드러났나 | 예방 |
|---|---|---|
| 부정 주장을 확인 없이 씀 | "Trino에 통계 없음 분기가 없다" → 실제로는 있었고 동작만 달랐다 | 2단계 grep 확인 |
| 코드 기준값을 그대로 옮김 | 단위가 섞여 있어 단계 구간이 3줄 틀림 | 4단계 환산 |
| 코드 독해만으로 원인을 단정 | "임계값 때문에 플랜이 다르다" → 실제 원인은 통계 부족이었다 | 실측 후 작성, 정정 이력 보존 |
| 발췌를 원문처럼 제시 | — | 6단계 대조 + 생략 표기 |

**이 프로젝트에서 실측이 코드 독해를 두 번 뒤집었다.** 실측 없이 쓴 보고서는 그 사실을 함께 알려야 한다.
