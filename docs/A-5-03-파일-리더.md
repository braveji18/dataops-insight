## 1. 비교 관점

레이크하우스에서 두 엔진이 하는 일의 대부분은 **같은 Parquet 파일을 읽는 것**이다. 그런데 리더는 각자 독립적으로, 서로 다른 언어로 구현돼 있다. 그래서 두 질문이 생긴다.

1. **결과가 정말 같은가** — 독립 구현 두 개가 같은 파일을 같게 해석하는가
2. **틀렸을 때 무엇이 죽는가** — 리더의 결함은 어디까지 번지는가

두 번째가 이 문서의 핵심이다. `A-5-01` 이 "커넥터를 새로 만드는 비용"을 봤다면, 여기서는 **이미 있는 커넥터가 고장 났을 때의 대가**를 본다.

결론부터: **정상 경로는 완전히 동등하다.** 복합 타입·압축 코덱·Iceberg 삭제 파일 어디서도 결과가 갈리지 않았다. 갈리는 곳은 **지원 범위의 가장자리**와 **결함의 폭발 반경**이고, 후자는 되돌릴 수 없는 구조적 차이다.

## 2. Trino 구현

### 2-1. 리더가 독립 라이브러리 모듈이다

| 모듈 | 파일 | 줄 |
|---|---|---|
| `lib/trino-parquet` | 174 | 36,255 |
| `lib/trino-orc` | 171 | 30,498 |
| `lib/trino-hive-formats` | 150 | 21,801 |

**`plugin/` 이 아니라 `lib/` 에 있다.** 커넥터(iceberg, hive, delta-lake, hudi)가 공유하는 공용 라이브러리라는 뜻이다. Iceberg 커넥터의 결함이 아니라 리더의 결함이면 네 커넥터에 동시에 영향을 준다 — 반대로 고치면 동시에 고쳐진다.

### 2-2. 외부 라이브러리는 포맷 정의만 쓴다

```xml
<artifactId>parquet-column</artifactId>
<artifactId>parquet-common</artifactId>
<artifactId>parquet-encoding</artifactId>
<artifactId>parquet-format-structures</artifactId>
```
— `lib/trino-parquet/pom.xml` 발췌

ORC 쪽은 더 얇다.

```xml
<artifactId>orc-format</artifactId>
```
— `lib/trino-orc/pom.xml` 발췌

`orc-format` 은 protobuf 정의뿐이다. **읽는 코드는 30,498줄 전부 자체 구현**이다. Parquet 도 마찬가지로 parquet-mr 의 인코딩·포맷 구조체만 빌려 쓰고 컬럼 읽기는 직접 한다.

### 2-3. 실패는 예외다

```java
public class ParquetCorruptionException
        extends IOException
```
— `lib/trino-parquet/.../ParquetCorruptionException.java:22-23`

`IOException` 이다. 리더가 던지면 커넥터가 `TrinoException` 으로 감싸고, **쿼리가 실패하고 끝난다.** 워커 프로세스는 그대로 산다. JVM 이므로 배열 범위를 벗어나도 `ArrayIndexOutOfBoundsException` 이지 세그멘테이션 폴트가 아니다.

**이것이 이 문서에서 가장 중요한 한 줄이다.** 성능의 대가로 얻은 안전이다 — `A-3-01` 에서 본 대로 Trino 는 JVM 위에서 돌고, 그 경계 검사 비용을 치르는 대신 **리더의 버그가 프로세스를 죽이지 못한다.**

## 3. StarRocks 구현

### 3-1. 리더는 BE 안의 C++ 이다

| 디렉토리 | 파일 | 줄 |
|---|---|---|
| `be/src/formats/parquet` | 60 | 16,569 |
| `be/src/formats/orc` | 24 | 5,100 |
| `be/src/formats/csv` | 41 | 4,020 |
| `be/src/formats/json` | 10 | 1,227 |

**Parquet 은 자체 구현, ORC 는 래핑이다.** ORC 쪽이 5,100줄뿐인 이유는 Apache ORC C++ 라이브러리를 감싸기 때문이다.

```cpp
#include "orc/OrcFile.hh"
```

Parquet 은 반대다. Arrow/parquet-cpp 를 의존성으로 갖고 있지만(`thirdparty/vars.sh` 의 `apache-arrow-19.0.1`), **읽기 경로에서는 쓰지 않는다.** `<parquet/api/reader.h>` 를 포함하는 파일을 세어 보면 전부 쓰기 쪽이다.

| 파일 | 성격 |
|---|---|
| `chunk_writer.h` / `file_writer.h` / `parquet_file_writer.h` / `column_chunk_writer.h` / `level_builder.h` | **쓰기** — Arrow 사용 |
| `column_reader.cpp` / `page_reader.cpp` / `group_reader.cpp` / `encoding*.h` / `metadata.cpp` / `column_converter.cpp` | **읽기** — 자체 구현 |

즉 **쓰기는 검증된 라이브러리에 맡기고 읽기는 직접 썼다.** 읽기가 성능의 핵심 경로이기 때문이다. 같은 이유로 Trino 도 읽기를 직접 썼다 — **두 엔진의 판단이 일치하는 드문 지점**이다.

### 3-2. 실패는 프로세스 사망일 수 있다

`evidence/A-5/20260820-...` 의 4.0.1 크래시 스택이다.

```
*** SIGSEGV (@0x0) received by PID 7 ...
  starrocks::parquet::Int32ToDateConverter::convert(...)
  starrocks::parquet::StatisticsHelper::decode_value_into_column(...)
  starrocks::parquet::RawColumnReader::_row_group_zone_map_filter(...)
  starrocks::parquet::ScalarColumnReader::row_group_zone_map_filter(...)
  starrocks::parquet::PredicateFilterEvaluator::visit_for_rowgroup_zonemap<...>(...)
  starrocks::parquet::FileReader::_filter_group(...)
  starrocks::parquet::FileReader::init(...)
  starrocks::HdfsParquetScanner::do_open(...)
  starrocks::connector::HiveDataSource::open(...)
```

`Int32ToDateConverter` 는 4.0.14 에도 그대로 있다(`be/src/formats/parquet/column_converter.cpp:58`). 결함은 고쳐졌고 클래스는 남았다.

**주목할 것은 이 스택이 "읽기 전"이라는 점이다.** `FileReader::init` → `_filter_group` — 아직 데이터를 읽지도 않고 **row group 통계에 술어를 적용하는 단계**에서 죽었다. `A-5-02` 4-5 에서 본 "StarRocks 는 80개를 전부 스케줄한 뒤 리더 안에서 거른다"는 그 경로다.

### 3-3. 죽으면 FE 가 그 BE 를 명단에서 뺀다

BE 가 사라지면 FE 가 자동으로 블랙리스트에 올린다.

```java
public static void addToBlocklist(Long backendID) {
    HOST_BLACKLIST.add(backendID);
}
```
— `fe/fe-core/.../qe/SimpleScheduler.java:172-174`

호출부는 5곳이고 전부 실행 경로다 — `ExecutionDAG:643`, `ResultReceiver:138,147`, `DefaultCoordinator:777`, `FragmentInstanceExecState:410`. **즉 "RPC 가 실패하면 그 노드를 뺀다"** 가 기본 동작이다.

**이 자동 동작이 양날이다.**

- **완충 효과** — 한 BE 가 죽어도 나머지로 계속 서비스한다. 죽은 노드로 계속 보내지 않는다
- **연쇄 위험** — 문제가 특정 파일이나 특정 쿼리 패턴에 있다면, 그 쿼리를 재시도할 때마다 **다음 BE 가 차례로 죽는다.** 블랙리스트는 노드를 빼기만 하므로 결국 남는 노드가 없어진다. 랩(BE 1대)에서 정확히 그 결말을 봤다 — `Failed to find backend to execute`

이 항목은 `B-4-01`(고가용성) 에서 다시 다룬다.

## 4. 실측

전문은 `docs/evidence/A-5/20260904-file-reader-compat-probes.md`.

### 4-1. 복합 타입 — 완전히 일치

Trino 로 쓰고 양쪽에서 읽었다.

| 값 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `ARRAY[1,2,3]` | `[1, 2, 3]` | `[1,2,3]` |
| `MAP(['x','y'],[10,20])` | `{x=10, y=20}` | `{"x":10,"y":20}` |
| `ROW(7,'seven')` | `{a=7, b=seven}` | `{"a":7,"b":"seven"}` |
| 빈 배열 / 빈 맵 | `[]` / `{}` | `[]` / `{}` |
| `ROW(NULL,NULL)` | `{a=NULL, b=NULL}` | `{"a":null,"b":null}` |
| `TIMESTAMP '...123456'` | `2026-01-02 03:04:05.123456` | 동일 |
| `DECIMAL '-0.000001'` | `-0.000001` | 동일 |

표기법만 다르고 **값은 전부 같다.** 빈 컬렉션과 NULL 필드까지 맞았다.

### 4-2. 압축 코덱 — 4종 동등

ZSTD / GZIP / SNAPPY / NONE 전부 양쪽 25행으로 일치했다. LZ4 는 **Trino 가 쓰기를 거부**해(`Compression codec LZ4 not supported for Parquet`) 판별되지 않았다 — 읽기 문제가 아니다.

### 4-3. Iceberg v2 삭제 파일 — 동등

Trino 로 `DELETE FROM bench.del WHERE o_orderkey % 7 = 0`(2,142행)을 실행하면 원본을 다시 쓰지 않고 삭제 파일을 남긴다.

| 엔진 | `count(*)` |
|---|---|
| Trino 483 | **12,858** |
| StarRocks 4.0.14 | **12,858** |

StarRocks 프로파일에 `DeleteFilesPerScan` / `DeleteFileBuildTime` 카운터가 따로 있어 전용 경로가 있음을 알 수 있다.

### 4-4. 가장자리에서 갈린다 — UUID

`A-1-02` 4-3 에서 확인한 것이다.

| 단계 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 스키마 조회 | `uuid` | `VARBINARY` — **성공** |
| 값 조회 | 정상 | **실패** — `not supported convert from parquet FIXED_LEN_BYTE_ARRAY to VARBINARY` |

`X'0102'` 로 넣은 다른 VARBINARY 컬럼은 정상이다. 즉 **FE 의 타입 매핑표와 BE 리더의 지원 범위가 어긋나 있고, 어긋남이 조회 시점에야 드러난다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 위치 | `lib/` 공용 라이브러리 (커넥터 4종이 공유) | BE 프로세스 안(`be/src/formats/`) |
| 언어 | Java | C++ |
| Parquet 읽기 | 자체 36,255줄 (parquet-mr 의 포맷·인코딩만 사용) | 자체 16,569줄 (Arrow 는 **쓰기에만**) |
| ORC 읽기 | 자체 30,498줄 (`orc-format` 만 사용) | Apache ORC C++ 래핑 (5,100줄) |
| 결함 시 | **예외 → 쿼리 실패, 워커 생존** | **SIGSEGV 가능 → BE 사망** |
| 사망 후 | 해당 없음 | FE 가 자동 블랙리스트 (`SimpleScheduler:172`) |
| 지원 범위 이탈 | 타입 매핑 단계에서 드러남 | **스키마는 성공, 조회에서 실패** |

### 5-2. 두 엔진이 같은 판단을 한 지점

**읽기 리더를 직접 쓴 것**은 양쪽이 같다. Trino 는 parquet-mr 을 쓰지 않았고, StarRocks 는 Arrow 를 읽기에 쓰지 않았다. 이유도 같다 — **읽기가 성능의 주 경로이고, 범용 라이브러리는 각 엔진의 메모리 표현(Trino `Block`, StarRocks `Column`)으로 직접 채워 넣지 못하기 때문**이다. 범용 리더를 쓰면 중간 표현을 한 번 더 거쳐야 한다(`A-3-01` 참조).

**갈린 것은 ORC 다.** StarRocks 는 Apache ORC C++ 를 감쌌다. ORC 가 StarRocks 사용자층에서 주 포맷이 아니라는 판단으로 읽힌다.

### 5-3. 폭발 반경은 되돌릴 수 없는 대가다

`A-5-01` 은 "커넥터를 새로 붙이는 비용"에서 Trino 가 유리하다고 결론지었다. 이 문서는 **이미 붙어 있는 커넥터의 운영 위험**에서도 같은 방향임을 보인다. 원인은 하나다 — **어디서 도는가.**

| | 리더 결함 하나가 미치는 범위 |
|---|---|
| Trino | 그 쿼리 하나. 워커는 다음 쿼리를 정상 처리한다 |
| StarRocks | **BE 프로세스 전체.** 그 BE 가 처리 중이던 **다른 모든 쿼리**가 함께 죽고, 그 BE 의 로컬 데이터도 잠시 접근 불가가 된다 |

StarRocks 쪽 피해가 더 큰 이유는 언어 때문만이 아니다. **BE 는 스토리지도 함께 들고 있다**(`C-1`). Trino 의 워커는 상태가 없어 죽어도 다시 띄우면 그만이지만, StarRocks BE 는 태블릿을 들고 있으므로 사망의 의미가 다르다.

**공정하게 볼 것** — 이 위험은 **실제로 발생했을 때의 크기**이지 발생 확률이 아니다. 4절 실측에서 정상 경로는 전부 동등했고, 4.0.1 의 결함은 4.0.14 에서 고쳐졌다. **"StarRocks 리더가 불안정하다"는 결론은 이 자료로 지지되지 않는다.** 지지되는 것은 "같은 확률의 결함이 더 큰 피해를 낳는다"이다.

### 5-4. 가장자리 이탈이 늦게 드러나는 문제

4-4 의 UUID 는 폭발 반경과는 다른 종류의 문제다. **FE 와 BE 가 서로 다른 표를 들고 있어서** 생긴다.

- FE `ColumnTypeConverter` : Iceberg `UUID` → `VARBINARY` (매핑 있음)
- BE Parquet 리더 : `FIXED_LEN_BYTE_ARRAY` → `VARBINARY` (변환 없음)

`A-1-03` 에서 본 함수 등록 구조(`functions.py` 하나가 FE Java 와 BE C++ 를 **동시에** 생성)와 대비된다. 함수는 단일 원본에서 생성해 어긋날 수 없게 만들었는데, **타입 매핑에는 그런 장치가 없다.**

Trino 에는 이 실패 유형이 구조적으로 생기기 어렵다 — 타입 매핑(`TypeConverter`)과 리더가 같은 JVM 안, 같은 저장소, 같은 빌드에 있다.

## 6. 결론

**정상 경로는 동등하다. 대가는 결함이 났을 때 나타난다.**

- **호환성**: 복합 타입·코덱·Iceberg 삭제 파일 전부 일치했다. 서로 다른 언어의 독립 구현치고는 상호운용이 잘 지켜지고 있다
- **폭발 반경**: 같은 종류의 리더 결함이 Trino 에서는 쿼리 실패로, StarRocks 에서는 BE 프로세스 사망으로 끝난다. 게다가 BE 는 스토리지를 들고 있어 사망의 의미가 더 크다
- **지원 범위 이탈**: StarRocks 는 FE 매핑표와 BE 리더의 지원 범위가 어긋날 수 있고, **스키마 조회로는 발견되지 않는다**

**실무 결론**

1. **StarRocks 로 외부 레이크를 읽을 때는 컬럼 단위 조회 확인이 필요하다.** `DESC` 성공은 조회 성공을 보장하지 않는다. 신규 테이블을 붙일 때 전 컬럼 `SELECT` 를 한 번 돌려 보는 절차를 권한다
2. **BE 를 여러 대 두는 것은 성능이 아니라 안전 문제다.** 리더 결함으로 BE 가 죽으면 FE 가 자동으로 빼는데, 뺄 노드가 남아 있어야 의미가 있다
3. **다만 "리더가 불안정하다"고 일반화하지 말 것.** 실측에서 정상 경로는 전부 동등했다

### 아직 답하지 않은 것

- **ORC / Avro / CSV** — Parquet 만 봤다. StarRocks 가 ORC 를 래핑한다는 사실이 호환성에 어떤 영향을 주는지 확인하지 않았다
- **손상 파일** — 파일을 인위적으로 깨뜨려 양쪽 반응을 비교하지 않았다. 이 랩에서 가능하지만 위험 대비 이득이 작다고 판단했다
- **4.0.1 크래시 재현** — 디스크 부족으로 못 했다(`plan/02` 6-1절). **arm64 한정 여부가 미확인으로 남아 있다**
- **읽기 성능** — 두 리더의 처리량을 비교하지 않았다. `perf` 프로파일이 필요하다
- **등가 삭제 파일(equality delete)** — Trino 가 만들지 않아 판별하지 못했다. Flink 로 쓴 테이블이 필요하다
- **BE 다중 노드에서의 연쇄 사망** — 3-3 의 "차례로 죽는다"는 코드 독해다. BE 1대 랩에서는 확인할 수 없다
