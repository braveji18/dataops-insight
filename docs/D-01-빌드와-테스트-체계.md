## 1. 비교 관점

빌드와 테스트는 **기여 비용을 결정한다.** `A-5-01`·`A-1-03`·`C-2-01` 이 반복해서 "StarRocks 는 FE 와 BE 양쪽을 건드려야 한다"고 결론지었는데, **그 말이 실제로 무엇을 뜻하는지**를 여기서 구체화한다.

두 가지를 본다.

1. **한 번 빌드하는 데 무엇이 필요한가**
2. **바꾼 것이 맞는지 어떻게 확인하는가**

## 2. 빌드

### 2-1. Trino — Maven 하나

| 항목 | 값 |
|---|---|
| 빌드 도구 | Maven |
| `pom.xml` 개수 | **116** |
| 최상위 모듈 | **111** |
| 언어 | Java 하나 |

`mvn install` 하나로 끝난다. 네이티브 의존성이 없다.

**모듈 111개는 많아 보이지만 단일 도구 아래 있다.** 하나를 고치면 그 모듈만 다시 빌드하면 되고, IDE 가 전체 구조를 이해한다.

### 2-2. StarRocks — Maven + CMake + Python 코드 생성

| 항목 | 값 |
|---|---|
| 빌드 도구 | **Maven(FE) + CMake(BE)** |
| `pom.xml` 개수 | 27 |
| `CMakeLists.txt` 개수 | **42** |
| 진입점 | `build.sh` (BUILD_FE / BUILD_BE 플래그로 분기) |
| 언어 | **Java + C++ (+ Python 코드 생성, Thrift, protobuf)** |

`build.sh` 가 `BUILD_FE` / `BUILD_BE` 를 나눠 처리한다(`build.sh:165-265`). 즉 **두 빌드가 별개**이고, 한쪽만 빌드할 수 있다.

**그리고 세 번째 계층이 있다** — `gensrc/`.

`A-1-03` 3-2 에서 본 것이다.

```python
    FE_PATH = "../../fe/fe-core/target/generated-sources/build"
    BE_PATH = "../build/gen_cpp"
```
— `gensrc/script/gen_functions.py:268-269`

**Python 스크립트가 FE 의 Java 코드와 BE 의 C++ 코드를 함께 생성한다.** Thrift 와 protobuf 정의도 `gensrc/` 에 있다(`gensrc/thrift/`, `gensrc/proto/` — `A-4-01`·`A-4-02` 에서 인용했다).

즉 **빌드 순서에 의존성이 있다**: gensrc → FE, gensrc → BE.

### 2-3. 외부 의존성의 무게

```
thirdparty/vars.sh 의 다운로드 항목: 59개
```

BE 를 빌드하려면 **59개 C++ 라이브러리를 받아 컴파일해야 한다** — Arrow 19.0.1, Apache ORC, brpc, CLucene, TenANN 등(`A-4-01`·`A-5-03`·`C-1-02` 에서 각각 마주쳤다).

그래서 `build-in-docker.sh` 와 `docker-dev.sh` 가 함께 제공된다. **개발 환경을 컨테이너로 고정하지 않으면 재현이 어렵다**는 신호다.

Trino 는 Maven 이 JAR 을 받아 오면 끝이다.

## 3. 테스트

### 3-1. Trino

| 계층 | 규모 |
|---|---|
| 단위·통합 테스트 | Java **3,561파일 / 831,798줄** |
| Product Test | `testing/trino-product-tests` **227파일** |
| 내결함성 테스트 | `testing/trino-faulttolerant-tests` |
| 벤치마크 | `testing/trino-benchmark-queries`, `trino-benchto-benchmarks` |
| 플러그인 검증 | `testing/trino-plugin-reader` |

**테스트 코드가 본체의 71%** 다(831,798 / 1,169,458).

`trino-product-tests-launcher` 가 따로 있는 것이 특징이다 — **실제 Hadoop/Hive/Kerberos 환경을 컨테이너로 띄워** 통합 테스트를 돌린다. `trino-plugin-reader` 는 **플러그인이 SPI 계약을 지키는지 검증**하는 도구로, `C-2-01` 에서 본 SPI 안정성 정책의 실행 장치다.

### 3-2. StarRocks

| 계층 | 규모 |
|---|---|
| FE 단위 테스트 | Java **1,565파일 / 478,004줄** |
| BE 단위 테스트 | C++ **628파일 / 296,820줄** (gtest) |
| SQL regression | `test/sql/` **213개 디렉토리 / 89개 `.sql`** |
| 실행 스크립트 | `run-fe-ut.sh`, `run-be-ut.sh`, `run-java-exts-ut.sh` |

**테스트를 돌리는 스크립트가 세 개로 나뉘어 있다.** FE / BE / Java 확장이 각각이다. 빌드가 이중이니 테스트도 이중이다.

`test/sql/` 의 디렉토리 이름이 성격을 보여준다 — `test_multilane_operator_missing_runtime_filter`, `test_information_schema`, `test_warehouse` 등. **실제 SQL 을 던지고 결과를 비교하는 회귀 테스트**다.

## 4. 실측

**없다.** 두 프로젝트를 빌드해 보지 않았다.

이 랩은 **공식 배포 이미지**를 쓴다(`scripts/testenv/versions.env`). 소스 빌드는 다른 종류의 작업이고, 특히 StarRocks BE 는 59개 C++ 의존성 때문에 시간과 디스크가 크게 든다 — `plan/02` 6-1절에서 확인한 대로 **이 호스트는 이미 디스크 여유가 빠듯하다.**

따라서 2·3절은 전부 파일 구성 조사다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 빌드 도구 | **Maven 하나** | **Maven + CMake + Python 코드 생성** |
| 모듈/빌드 파일 | pom 116개, 모듈 111 | pom 27 + CMakeLists 42 |
| 언어 | Java | **Java + C++** (+ Thrift/protobuf/Python) |
| 외부 네이티브 의존성 | 없음 | **59개** |
| 개발 환경 | 로컬 JDK | **컨테이너 권장**(`build-in-docker.sh`) |
| 테스트 실행 | Maven | **스크립트 3개**(FE/BE/exts) |
| 통합 테스트 | Product Test 227파일 + 런처 | SQL regression 213 디렉토리 |
| 테스트/본체 비율 | **71%** | FE 63% / BE 47% |

### 5-2. 이중 빌드가 만드는 것

`A-1-03` 5-1 의 표를 다시 보면, 함수 하나를 추가하는 데 **"FE(Maven) + BE(CMake) 양쪽"** 이 필요했다. 이 문서가 그 말의 무게를 구체화한다.

- 개발자는 **Java 와 C++ 을 둘 다** 다뤄야 한다
- 빌드 환경을 **컨테이너로 고정**하지 않으면 재현이 어렵다
- 바꾼 것을 확인하려면 **테스트를 두 번 돌린다**(`run-fe-ut.sh`, `run-be-ut.sh`)
- `gensrc` 를 건드리면 **양쪽을 다시 빌드**해야 한다

**진입 장벽이 높다는 것은 곧 기여자 풀이 좁다는 뜻**이고, 이는 `C-2-02` 5-2 에서 본 "커넥터 27 대 10" 의 배경이기도 하다.

### 5-3. 그러나 이중 구조는 선택이 아니라 결과다

**공정하게 볼 지점이다.** StarRocks 가 이중 빌드를 택한 것이 아니라, **C++ 실행 엔진을 갖기로 한 결정의 결과**다.

`A-3-01`·`A-3-05` 에서 본 SIMD 벡터화와 LLVM JIT, `C-1-02` 의 벡터 인덱스는 JVM 위에서 같은 방식으로 만들 수 없다. **성능을 위해 C++ 을 택했고 그 대가가 빌드 복잡도**다.

Trino 도 같은 거래의 반대편에 있다 — 단일 언어의 단순함을 얻고 `A-3-01` 에서 본 만큼의 SIMD 활용 폭을 포기했다.

### 5-4. 테스트 전략의 차이

**Trino 의 Product Test 는 "환경까지 재현"한다.** 런처가 Hadoop·Hive·Kerberos 컨테이너를 띄운다. 커넥터가 수십 개이고 각각 외부 시스템과 대화하므로, **모의 객체로는 검증이 안 되기 때문**이다.

**StarRocks 의 SQL regression 은 "결과를 고정"한다.** 자기 엔진 안에서 SQL 을 돌리고 출력을 비교한다. 외부 시스템 의존이 적으니 이 방식으로 충분하다.

**즉 테스트 전략도 제품 경계를 따라간다** — 이 연구에서 계속 반복돼 온 구도다.

### 5-5. `trino-plugin-reader` 가 뜻하는 것

`C-2-01` 2-3 에서 본 `@Unstable` 애노테이션과 짝이다. **SPI 를 공개 계약으로 다루려면 계약 위반을 자동으로 잡아야 한다.**

StarRocks 에는 이런 도구가 필요 없다 — 확장점이 없으니 지킬 계약도 없다.

## 6. 결론

**동등하지 않다 — 기여 비용이 크게 다르고, 그것은 언어 선택의 귀결이다.**

- **Trino**: Maven 하나, Java 하나. 테스트가 본체의 71%이고 Product Test 가 외부 환경까지 컨테이너로 재현한다
- **StarRocks**: Maven + CMake + Python 코드 생성. **59개 C++ 의존성**, 컨테이너 빌드 권장, 테스트 스크립트 3개
- **이 차이는 결함이 아니라 C++ 실행 엔진을 갖기로 한 결정의 대가**다

**실무 결론**

1. **upstream 기여를 계획한다면 진입 비용을 감안하라.** StarRocks 는 Java·C++·CMake·Thrift 를 함께 다뤄야 하고, 빌드 환경을 컨테이너로 고정해야 한다
2. **사내 포크를 유지할 계획이라면 Trino 쪽이 압도적으로 싸다.** 대부분의 필요는 플러그인으로 해결되고(`C-2-01`), 포크 자체가 필요 없을 수 있다
3. **StarRocks 를 소스에서 빌드할 일이 있다면 디스크와 시간을 넉넉히 잡아라.** 59개 네이티브 의존성을 컴파일한다
4. **버그를 재현해 보고할 때도 비용이 다르다.** Trino 는 테스트 하나를 추가하면 되고, StarRocks 는 FE/BE 중 어디인지부터 가려야 한다

### 아직 답하지 않은 것

- **실제 빌드 시간과 자원** — 두 프로젝트를 빌드해 보지 않았다. "무겁다"는 파일 구성에서 추론한 것이다
- **증분 빌드의 실제 편의** — Trino 의 모듈 111개가 실제로 얼마나 빠르게 증분 빌드되는지 모른다
- **테스트 실행 시간** — 전체 테스트를 돌리는 데 얼마나 걸리는지 확인하지 않았다
- **CI 구성** — `.github/workflows` 를 보지 않았다. 실제 검증 파이프라인이 어떻게 도는지 모른다
- **테스트 커버리지의 질** — 줄 수는 셌지만 무엇을 덮는지는 판단하지 않았다
- **코드 규모와 기여 활동** — `D-02`
