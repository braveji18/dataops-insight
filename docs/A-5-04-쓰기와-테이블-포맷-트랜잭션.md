# A-5 커넥터 (4) — 쓰기와 테이블 포맷 트랜잭션

> 비교 축: `plan/01-비교항목-정리.md` A-5 "INSERT/CTAS/MERGE/DELETE/UPDATE, Iceberg·Delta 트랜잭션 지원 수준"
> 기준 버전: **Trino 483** / **StarRocks 4.0.14**
> 런타임 증거: `docs/evidence/A-5/20260904-iceberg-write-capability-probes.md`
> 선행 문서: `docs/A-5-01`~`A-5-03`
> 일자: 2026-09-04

---

## 1. 비교 관점

`A-5-02`·`A-5-03` 에서 **읽기는 거의 동등**했다. 이 문서는 반대쪽을 본다.

레이크하우스에서 쓰기는 읽기보다 훨씬 어렵다. 파일을 만드는 것만이 아니라 **메타데이터를 원자적으로 갱신**해야 하고, 동시 쓰기가 충돌하면 재시도해야 하며, 행을 지우거나 고치려면 삭제 파일이라는 별도 장치를 다뤄야 한다.

두 엔진의 위치가 여기서 갈린다.

- Trino 는 스토리지를 갖지 않으므로 **Iceberg 가 유일한 저장 수단**이다. 못 하면 대안이 없다
- StarRocks 는 **자기 네이티브 테이블이 있다.** 외부 포맷에 쓰지 못해도 "우리 테이블로 옮겨 쓰라"는 답이 있다

결론부터: **쓰기에서 격차가 크다.** 추가(INSERT/CTAS)와 스키마 진화는 동등하지만, **행을 수정하는 문장(UPDATE/DELETE/MERGE)을 StarRocks 는 Iceberg 에 실행하지 못한다.** 유지보수 명령도 없다. 다만 **읽기 쪽 시간 여행·메타데이터 테이블은 완전히 동등**하다.

---

## 2. Trino 구현

### 2-1. 쓰기가 SPI 의 1급 시민이다

`ConnectorMetadata` 의 쓰기 표면은 읽기만큼 넓다 — `beginInsert`/`finishInsert`, `beginMerge`/`finishMerge`, `applyDelete`/`executeDelete`, `applyUpdate`, `beginCreateTable`/`finishCreateTable`, `beginStatisticsCollection` 등.

특히 **`MERGE` 가 SPI 수준의 개념**이다. `UPDATE`·`DELETE` 도 내부적으로 merge 로 내려간다. 커넥터는 "행 수정"이라는 하나의 원시 연산만 구현하면 세 문장을 모두 얻는다.

### 2-2. 유지보수가 테이블 프로시저로 노출돼 있다

```
OPTIMIZE  OPTIMIZE_MANIFESTS  DROP_EXTENDED_STATS  ROLLBACK_TO_SNAPSHOT
EXPIRE_SNAPSHOTS  REMOVE_ORPHAN_FILES  ADD_FILES  ADD_FILES_FROM_TABLE
```
— `plugin/trino-iceberg/.../procedure/IcebergTableProcedureId.java`

`ALTER TABLE <t> EXECUTE optimize` 로 부른다. **Iceberg 운영에 필요한 작업이 SQL 문장으로 다 나와 있다** — 작은 파일 병합, 매니페스트 정리, 스냅샷 만료, 고아 파일 제거, 외부 파일 등록, 스냅샷 롤백.

이것은 "있으면 좋은 기능"이 아니라 **필수**다. Iceberg 테이블은 쓰기를 반복하면 작은 파일과 스냅샷이 쌓여 반드시 정리해야 한다. Trino 를 쓰기 엔진으로 삼으면 그 정리도 Trino 안에서 끝난다.

## 3. StarRocks 구현

### 3-1. 문장 단계에서 카탈로그 이름만 보고 막는다

```java
if (!operation.equals("ALTER") && catalog.getType().equalsIgnoreCase("iceberg")) {
    throw new SemanticException("Table of iceberg catalog doesn't support [%s]", operation);
}
```
— `fe/fe-core/.../sql/common/MetaUtils.java:91-93`

**커넥터에게 물어보지 않는다.** 카탈로그 타입 문자열이 `iceberg` 이고 연산이 `ALTER` 가 아니면 곧장 거부다. `DeleteAnalyzer.java:201` 이 `"DELETE"` 로 이것을 호출한다.

`A-5-02` 에서 본 구조가 여기서도 반복된다 — **StarRocks 는 커넥터에게 능력을 묻지 않는다.** 읽기에서는 그 판단을 엔진이 대신 했고, 쓰기에서는 아예 목록으로 막았다.

### 3-2. UPDATE 는 다른 경로로 막힌다

```java
if (!table.supportsUpdate()) {
    throw unsupportedException("table " + table.getName() + " does not support update");
}
```
— `fe/fe-core/.../sql/analyzer/UpdateAnalyzer.java:89-91`

이쪽은 테이블 객체에 물어본다. **같은 성격의 거부가 두 가지 방식으로 구현돼 있다** — 하나는 카탈로그 이름 하드코딩, 하나는 능력 질의. 일관되지 않다.

`MERGE` 는 세 번째다 — **문법에 없다.** 파서에서 구문 오류로 떨어진다.

### 3-3. 기계는 이미 있다

`IcebergMetadata` 안에 삭제 파일을 다루는 코드가 이미 있다.

```java
public void deleteFile(DeleteFile file) {
```
— `fe/fe-core/.../connector/iceberg/IcebergMetadata.java:1817`

`addAppliedDeleteFiles(Set<DeleteFile> o)`(`:1850`), `finishSink(...)`(`:1535`) 도 있다. **삭제 파일을 쓸 수 있는 기계는 갖춰져 있고 SQL 문장이 연결돼 있지 않다.** 읽기 쪽은 이미 연결돼 있다 — `A-5-03` 4-3 에서 Trino 가 만든 삭제 파일을 StarRocks 가 정확히 읽어냈다.

즉 **"읽을 수는 있는데 쓸 수는 없다"** 가 현재 상태다.

### 3-4. 유지보수 명령이 없다

`ALTER TABLE ... COMPACT` 는 `This connector does not support ...` 로 거부된다. 스냅샷 만료·고아 파일 제거에 해당하는 문장도 없다.

**StarRocks 자기 테이블에는 compaction 이 있다**(`C-1-03`). 외부 Iceberg 테이블에는 적용되지 않는다.

## 4. 실측

전문은 `docs/evidence/A-5/20260904-iceberg-write-capability-probes.md`.

Trino 로 만든 Iceberg 테이블 하나에 양쪽에서 번갈아 문장을 던졌다.

### 4-1. DML

| 문장 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `INSERT INTO ... SELECT` | **성공** | **성공** |
| `CREATE TABLE ... AS SELECT` | **성공** | **성공** |
| `UPDATE ... SET ... WHERE` | **성공** | ✗ `table w1 does not support update` |
| `DELETE FROM ... WHERE` | **성공** | ✗ `Table of iceberg catalog doesn't support [DELETE]` |
| `MERGE INTO ...` | **성공** | ✗ 구문 오류 |

### 4-2. 스키마 진화 — 동등하고, 상호운용된다

| 문장 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `ADD COLUMN` / `DROP COLUMN` / `RENAME COLUMN` | 성공 | **성공** |

**교차 확인이 이 절의 요점이다.** StarRocks 로 `n_name` → `n_nm` 을, Trino 로 `n_comment` → `n_cmt` 를 각각 바꾼 뒤 양쪽에서 스키마를 읽었다.

| | 결과 |
|---|---|
| Trino `DESCRIBE` | `n_nationkey, n_nm, n_regionkey, n_cmt` |
| StarRocks `DESC` | `n_nationkey, n_nm, n_regionkey, n_cmt` |

**서로가 바꾼 것을 서로가 본다.** Iceberg 메타데이터를 통한 스키마 진화 상호운용이 실제로 동작한다.

### 4-3. 스냅샷 — 읽기는 완전히 동등

| 기능 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `FOR VERSION AS OF <snapshot_id>` | **25** | **25** |
| 메타데이터 테이블 (`$snapshots`) | **7** | **7** |
| 파일 병합 (`OPTIMIZE` / `COMPACT`) | 성공 | ✗ 미지원 |

스냅샷 7개를 양쪽이 똑같이 세고, 첫 스냅샷으로 되돌아간 조회도 25행으로 일치했다. **시간 여행은 판별되지 않는다 — 동등하다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| INSERT / CTAS | ✅ | ✅ |
| UPDATE / DELETE / MERGE | ✅ | **✗ 전부** |
| 스키마 진화 | ✅ | ✅ (상호운용 확인) |
| 시간 여행 / 메타데이터 테이블 | ✅ | ✅ |
| 유지보수(병합·스냅샷 정리·고아 파일) | **프로시저 8종** | ✗ |
| 거부 방식 | 해당 없음 | 카탈로그 이름 하드코딩 / 테이블 능력 질의 / 문법 부재 — **셋이 제각각** |
| 삭제 파일 | 쓰고 읽는다 | **읽기만** — 쓰는 기계는 있으나 문장이 없다 |

### 5-2. 격차의 원인은 제품의 무게중심이다

**Trino 에게 Iceberg 는 유일한 저장 수단이다.** 스토리지가 없으니 "Trino 로 데이터를 고친다"는 곧 "Iceberg 를 고친다"이다. 그래서 MERGE 를 SPI 원시 연산으로 두고, 유지보수까지 SQL 로 노출했다.

**StarRocks 에게 Iceberg 는 읽어오는 곳이다.** 무게중심은 네이티브 테이블(`C-1`)에 있고, 거기에는 Primary Key 모델·compaction·트랜잭션이 다 있다. 외부 Iceberg 에 UPDATE 를 붙일 유인이 상대적으로 약하다.

`A-2-06`(MV 재작성)에서 본 구도의 거울상이다. 그쪽은 StarRocks 가 자기 스토리지를 소유하기 때문에 **압도적으로 앞섰고**, 여기서는 같은 이유로 **뒤진다.**

### 5-3. 그러나 거부 방식의 불일치는 설명되지 않는다

세 문장이 세 가지 방식으로 막히는 것은 설계가 아니라 **누적**으로 보인다.

- `DELETE` — `MetaUtils.checkNotSupportCatalog` 의 카탈로그 이름 하드코딩
- `UPDATE` — `table.supportsUpdate()` 능력 질의
- `MERGE` — 문법 부재

특히 `checkNotSupportCatalog` 는 **커넥터 종류가 늘어날 때마다 조건절이 늘어나는 구조**다. `A-5-01` 이 지적한 "붙일 수 있는 소스가 열거형에 박혀 있다"와 같은 성격이고, `A-5-02` 의 "커넥터에게 묻지 않는다"와도 같다. **세 문서가 같은 뿌리를 서로 다른 각도에서 보고 있다.**

### 5-4. 운영자 관점 — 누가 쓰기 엔진인가

이 절이 실무의 알맹이다. 두 엔진을 같은 Iceberg 카탈로그에 붙였을 때 **쓰기 역할을 나눠야 한다.**

| 작업 | 가능한 엔진 |
|---|---|
| 적재(append) | 양쪽 |
| 테이블 생성 / 스키마 변경 | 양쪽 |
| 행 수정·삭제, MERGE 기반 upsert | **Trino 만** |
| 파일 병합, 스냅샷 만료, 고아 파일 제거 | **Trino 만** |
| 조회 / 시간 여행 | 양쪽 |

**StarRocks 만 두고 Iceberg 를 운영할 수는 없다.** 쓰기가 반복되면 작은 파일이 쌓이는데 정리할 수단이 없기 때문이다. 정리를 Spark 나 Flink 같은 다른 도구에 맡기든지, Trino 를 함께 두든지 해야 한다.

반대로 **StarRocks 를 조회 가속기로 두는 구성은 자연스럽다.** 읽기는 전부 동등하고(`A-5-02`·`A-5-03`), 그 위에 MV 재작성(`A-2-06`)과 자동 통계(`A-2-07`) 같은 StarRocks 의 강점이 얹힌다.

## 6. 결론

**동등하지 않다 — 쓰기에서 Trino 가 명확히 앞선다.**

- **추가와 스키마 진화는 동등**하고 상호운용도 확인됐다
- **행 수정(UPDATE/DELETE/MERGE)은 StarRocks 가 Iceberg 에 하지 못한다.** 삭제 파일을 **읽을 수는 있으나 쓰지 못한다**
- **유지보수 명령이 없다.** Trino 는 프로시저 8종, StarRocks 는 0
- **읽기 쪽 스냅샷 기능(시간 여행, 메타데이터 테이블)은 완전히 동등**

**실무 결론**

1. **Iceberg 를 고쳐 쓰는 워크로드라면 Trino 가 필요하다.** CDC upsert, GDPR 삭제, 지연 도착 데이터 정정이 여기 해당한다
2. **StarRocks 만으로 Iceberg 를 운영하지 말 것.** 적재는 되지만 정리 수단이 없다. 파일이 쌓이면 읽기 성능이 서서히 나빠지는데 손댈 문장이 없다
3. **두 엔진을 함께 쓴다면 역할을 나누는 것이 자연스럽다** — 쓰기·정리는 Trino, 조회 가속은 StarRocks. `A-2-06`·`A-2-07` 의 결론과 방향이 맞는다
4. **StarRocks 로 데이터를 고쳐야 한다면 네이티브 테이블로 옮기는 것이 정공법이다**(`C-1-01`·`C-1-04`)

### 아직 답하지 않은 것

- **동시 쓰기와 충돌 처리** — 양쪽에서 동시에 커밋할 때 무엇이 일어나는지 확인하지 않았다. Iceberg 는 낙관적 동시성이라 재시도 정책이 중요한데, 도구가 단일 세션이라 재현하지 못했다
- **트랜잭션 격리 수준** — 두 엔진 모두 `START TRANSACTION`/`BEGIN` 구문은 받는다. 다중 문장 트랜잭션이 Iceberg 에서 실제로 어떻게 동작하는지 확인하지 않았다
- **Delta Lake / Hudi / Paimon** — 랩에 카탈로그가 없다. Iceberg 결론을 다른 포맷으로 옮기면 안 된다
- **쓰기 성능** — 재지 않았다. `perf` 프로파일 필요
- **StarRocks 네이티브 테이블의 쓰기** — 이 문서는 외부 Iceberg 만 다뤘다. Primary Key 모델의 upsert 는 `C-1-01`·`C-1-04`
- **StarRocks 의 Iceberg 쓰기 로드맵** — 3-3 에서 본 대로 기계는 있다. 어느 버전에서 연결될지는 이 저장소의 얕은 클론으로 판단할 수 없다
