## 읽는 법

- **파일명 규칙**: `docs/<축>-<순번>-<제목>.md` (예: `A-2-01-조인-순서-결정.md`)
- **증거 파일**: `docs/evidence/<축>/<YYYYMMDD>-<probe>.md` — 본문의 주장을 실제 쿼리로 검증한 기록
- **문서 형식**: `plan/01` 5절 (비교 관점 → Trino 구현 → StarRocks 구현 → 설계 차이 → 영향 → 결론)

### 상태 표기

| 표기 | 뜻 |
|---|---|
| ✅ | 완료 (코드 인용 + 결론) |
| 🔬 | 완료 + **런타임 증거** 있음 |
| ⬜ | 미착수 |
| 🚧 | 현재 랩 구성으로 **검증 불가** — 코드 비교까지만 가능 |

### 검증 가능성의 한계 (전 축 공통)

현재 랩(`scripts/testenv/`)은 **Trino worker 1대 / StarRocks BE 1대, TPC-H SF 0.01** 이다. 따라서:

- **다중 노드에 반응하는 항목**은 검증 불가다. StarRocks의 broadcast 게이트(`beNum`), Trino의 `taskCountEstimator`, 셔플 전략, 리소스 격리가 모두 여기 해당한다
- **실행 시간 비교**는 전 축에서 불가하다. `perf` 프로파일(RAM 24GB + swap)이 필요하다 — `plan/02` 6-2절
- 위 두 경우 문서는 **코드 비교 + 설계 차이까지만** 쓰고, 성능 결론을 내지 않는다

## 진행 순서

`plan/01` 5절의 권장 순서를 따른다: **A-2 → A-3 → A-5 → B-2 → C-1**.

**A-1(3/3)과 A-2(7/7)가 끝났고, A-3 는 1/5 진행됐다.** 남은 A-3 중에서는 **A-3-04(런타임 필터)** 가 현재 랩에서 `EXPLAIN` 으로 바로 판별 가능해 비용이 가장 낮다 — A-2-04·A-2-05 실측에서 Trino `dynamicFilters` 가 이미 플랜에 보였다. **A-3-05(표현식·딕셔너리)** 는 A-3-01 5-4에서 남긴 질문(누가 인코딩을 타입으로 승격시켰는가)의 직접적인 후속이다.

보고용 문서는 `report/03`(A-2-03 대응)까지 마쳤다. **A-2-04 ~ A-3-01 대응 5건이 남아 있다** — 본문을 더 쓰기 전에 이쪽을 먼저 따라잡는 편이 낫다.

> `report/03` 작성 중 원본 `A-2-03` 2-5의 "Trino 자신은 통계를 수집하지 않는다" 서술이 부정확함을 발견해 보강했다(쓰기 시점 수집은 존재하고, 없는 것은 배경 자동 수집이다). **보고서를 쓰는 과정이 원본을 검증하는 장치로도 작동한다** — exec-report 스킬 1단계가 노리는 효과다.
