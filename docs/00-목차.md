> 이 파일은 `plan/01-비교항목-정리.md` 에 정리된 비교 축을 **실제로 산출한 문서 단위로 분해한 목차**다.
> 무엇을 비교할 것인지는 `plan/01` 이 관리하고, 무엇이 끝났는지는 이 파일이 관리한다.

> 기준 버전: **Trino 483** / **StarRocks 4.0.14** (`scripts/testenv/versions.env` 에 적힌 값과 `works/` 에 클론한 태그가 일치한다)
> 최종 갱신: 2026-10-30

## 읽는 법

- **파일명 규칙**: `docs/<축>-<순번>-<제목>.md` 형식을 따른다. 예를 들어 `A-2-01-조인-순서-결정.md` 와 같다
- **증거 파일**: `docs/evidence/<축>/<YYYYMMDD>-<probe>.md` 에 둔다. 본문에서 제시한 주장을 실제 쿼리로 검증한 기록이다
- **문서 형식**: `plan/01` 5절을 따른다. 비교 관점에서 시작해 Trino 구현, StarRocks 구현, 설계 차이, 영향, 결론 순서로 쓴다

### 상태 표기

| 표기 | 뜻 |
|---|---|
| ✅ | 완료했다 (코드 인용과 결론을 갖추었다) |
| 🔬 | 완료했고 **런타임 증거**도 있다 |
| ⬜ | 아직 착수하지 않았다 |
| 🚧 | 현재 랩 구성으로는 **검증할 수 없다.** 코드 비교까지만 가능하다 |

### 검증 가능성의 한계 (전 축에 공통으로 적용된다)

현재 랩(`scripts/testenv/`)은 **Trino worker 1대와 StarRocks BE 1대로 구성되어 있고, 데이터는 TPC-H SF 0.01** 이다. 따라서 다음과 같은 한계가 있다.

- **다중 노드에 반응하는 항목**은 검증할 수 없다. StarRocks 의 broadcast 게이트(`beNum`), Trino 의 `taskCountEstimator`, 셔플 전략, 리소스 격리가 모두 여기에 해당한다
- **실행 시간 비교**는 전 축에서 불가능하다. `perf` 프로파일(RAM 24GB 와 swap 이 필요하다)을 띄울 수 없기 때문이며, 자세한 사정은 `plan/02` 6-2절에 적어 두었다
- 위 두 경우에 해당하는 문서는 **코드 비교와 설계 차이까지만** 서술하고, 성능에 관한 결론은 내리지 않는다

**블로그 작성 규칙**

- 글 하나가 답하는 질문을 **한 문장**으로 적고, 결론을 글의 첫 세 줄 안에 둔다
- 버전과 커밋을 상단에 명시한다 (`483` / `50b0b50b`, `4.0.14` / `7c18dd9d`)

- 측정값에는 환경(호스트, CPU, 데이터 규모)을 붙이고, **실행 시간을 재지 못했다는 사실을 매 편에 적는다**
- 문체는 `~습니다` 로 통일하고, 번역투(`~을 통해`, `~에 대한`, `~의 경우`, `~되어지다`)와 엠대시를 쓰지 않는다
- **코드만 읽고 내린 판단이 실측에 뒤집힌 사례를 숨기지 않고 글에 남긴다.** 글의 신뢰가 거기서 나온다
