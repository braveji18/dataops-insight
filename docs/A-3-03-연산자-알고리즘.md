## 1. 비교 관점

A-3-01이 데이터의 모양, A-3-02가 실행 단위의 스케줄링이었다면 이 문서는 **연산자 안쪽**이다. 세 가지를 본다.

1. **해시 조인의 조회표를 몇 가지 방식으로 만드는가**
2. **메모리가 부족할 때 어느 연산자가 디스크로 내려갈 수 있는가**(spill)
3. **정렬을 어떻게 구현하는가**

**결론부터: 이 축은 A-3-01의 구도가 그대로 반복된다 — StarRocks 는 특수화된 구현을 여러 벌 만들고(조회표 6종, spill 연산자 12종), Trino 는 적은 수의 구현에 런타임 코드 생성을 얹는다. 다만 spill 범위는 StarRocks 가 뚜렷하게 넓다.**

## 2. Trino 구현

### 2-1. 해시 조회표는 2가지 — 그리고 나머지는 코드 생성

`works/trino/core/trino-main/src/main/java/io/trino/operator/join/JoinHashSupplier.java:91-94`:

```java
        this.pagesHash = switch (getPagesHashType(addresses, singleBigintJoinChannel)) {
            case BIGINT -> new BigintPagesHash(addresses, pagesHashStrategy, positionLinksFactoryBuilder, hashArraySizeSupplier, pages, singleBigintJoinChannel.getAsInt());
            case DEFAULT -> new DefaultPagesHash(addresses, pagesHashStrategy, positionLinksFactoryBuilder, hashArraySizeSupplier);
        };
```

**두 갈래뿐이다.**

- `BIGINT` — 조인 키가 **8바이트 정수 하나**일 때의 특수 구현
- `DEFAULT` — 그 외 전부

그 외의 타입별 최적화는 **바이트코드 생성**이 맡는다. `pagesHashStrategy` 가 그것으로, `JoinCompiler` 가 조인 키 조합마다 비교·해시 코드를 만들어낸다. **클래스를 늘리는 대신 클래스를 만들어내는 방식**이고, A-3-01 5-3에서 본 언어 제약(자료형별 클래스를 늘리면 JIT 인라이닝이 깨진다)의 귀결이다.

`operator/join/` 아래 파일은 25개 남짓이고, 중첩 루프 조인(`NestedLoopJoinOperator`)이 따로 있다.

### 2-2. spill 가능한 연산자는 4계열

`io/trino/operator/` 에서 `Spiller` 를 참조하는 연산자는 넷이다.

| 파일 | 연산자 |
|---|---|
| `HashAggregationOperator.java` | 해시 집계 |
| `OrderByOperator.java` | 정렬 |
| `WindowOperator.java` | 윈도우 함수 |
| `OperatorFactories.java` | 조인(spilling lookup join 조립부) |

집계의 spill 은 별도 빌더로 분리돼 있다 — `operator/aggregation/builder/` 에 4개 클래스:

```
HashAggregationBuilder.java          (인터페이스)
InMemoryHashAggregationBuilder.java  (메모리 안)
SpillableHashAggregationBuilder.java (디스크로 내림)
MergingHashAggregationBuilder.java   (내린 것을 다시 합침)
```

`SpillableHashAggregationBuilder.java:68-69, 104-105` 가 두 개의 한도를 든다:

```java
    private final long memoryLimitForMerge;
    private final long memoryLimitForMergeWithMemory;
```

**"합칠 때 쓸 메모리"와 "메모리에 남은 것과 함께 합칠 때 쓸 메모리"를 구분한다.** 다시 읽어 들이며 합치는 단계의 메모리까지 별도 한도로 관리하는 구조다. 세션 속성 `aggregation_operator_unspill_memory_limit` 이 여기에 대응한다.

### 2-3. spill 은 기본 꺼져 있다

`FeaturesConfig.java:110`:

```java
    private boolean spillEnabled;
```

**초기값이 없다 — 즉 기본 `false`.** 세션 속성 `spill_enabled` 로 켠다. 진단용으로 `force_spilling_join` 도 있다(`SystemSessionProperties.java:215`).

**메모리가 부족하면 기본 동작은 spill 이 아니라 쿼리 실패다.** 이 선택의 배경은 B-1-01에서 다룬다.

### 2-4. 정렬 — 비교기를 컴파일한다

`operator/PagesIndex.java` 가 정렬 대상을 담고, 비교기는 **런타임에 생성**된다 — `:40, 86, 138`:

```java
import io.trino.sql.gen.OrderingCompiler;
...
    private final OrderingCompiler orderingCompiler;
...
        private static final OrderingCompiler ORDERING_COMPILER = new OrderingCompiler(TYPE_OPERATORS);
```

**정렬 키의 타입·개수·방향 조합마다 전용 비교기 바이트코드를 만든다.** 2-1의 조인 해시 전략과 같은 방식이다.

`OrderByOperator` 가 전체 정렬을, `GroupedTopN*Builder` 계열(5개 클래스)이 그룹별 상위 N건을 담당한다 — A-2-05 2-4에서 본 `TopNRanking` 의 실행 측 구현이다.

## 3. StarRocks 구현

### 3-1. 해시 조회표가 6종 — 키의 성질마다 전용 구현

`works/starrocks/be/src/exec/join/join_hash_map_method.h`:

| 라인 | 클래스 | 겨냥하는 상황 |
|---|---|---|
| `:54` | `BucketChainedJoinHashMap` | 일반적인 버킷 체이닝 |
| `:119` | `LinearChainedJoinHashMap` | 선형 체이닝 |
| `:202` | `LinearChainedAsofJoinHashMap` | ASOF 조인(시간 근접 조인) |
| `:250` | `DirectMappingJoinHashMap` | **키를 배열 첨자로 직접 쓸 수 있을 때** |
| `:301` | `RangeDirectMappingJoinHashMap` | 키가 좁은 범위의 정수일 때 |
| `:379` | `DenseRangeDirectMappingJoinHashMap` | 위와 같되 조밀할 때 |

**`DirectMapping` 계열이 핵심이다.** 조인 키가 예컨대 1~100 범위의 정수라면 해시를 계산하지 않고 **배열 첨자로 바로 찾는다.** Trino 의 `BigintPagesHash` 도 정수 특수화이지만 해시 계산은 한다.

여기에 매칭 결과의 성질까지 미리 분류한다 — `join_hash_table_descriptor.h:35`:

```cpp
enum class JoinMatchFlag { NORMAL, ALL_NOT_MATCH, ALL_MATCH_ONE, MOST_MATCH_ONE };
```

**"모두 매칭 안 됨", "모두 정확히 하나씩 매칭", "대부분 하나씩 매칭"** 을 구분해 프로브 루프를 갈아 끼운다. 외래키 조인처럼 대부분 1:1 인 경우를 겨냥한 최적화다.

`exec/join/` 전체가 3,400줄 남짓이다.

### 3-2. spill 가능한 연산자가 12계열

`be/src/exec/` 아래 `spillable_*` 파일이 이만큼 있다.

| 계열 | 파일 |
|---|---|
| 집계 (블로킹) | `spillable_aggregate_blocking_sink/source_operator` |
| 집계 (중복 제거) | `spillable_aggregate_distinct_blocking_operator` |
| 집계 (파티션 단위) | `spillable_partitionwise_aggregate_operator`, `spillable_partitionwise_distinct_operator` |
| 해시 조인 | `spillable_hash_join_build/probe_operator` |
| **중첩 루프 조인** | `spillable_nljoin_build/probe_operator` |
| 정렬 | `spillable_chunks_sorter_full_sort`, `spillable_partition_sort_sink_operator` |
| **다중 소비 교환** | `spillable_multi_cast_local_exchange` |

**Trino 의 4계열보다 넓다.** 특히 두 가지가 Trino 에 없다.

- **중첩 루프 조인의 spill** — 등가 조건이 없는 조인에서 메모리가 터지는 것을 막는다
- **다중 소비 교환의 spill** — A-2-05 3-3에서 본 CTE 재사용(`MultiCastDataSinks`)의 중간 결과를 디스크로 내릴 수 있다. **CTE 재사용 기능 자체가 Trino 에 없으므로 대응물이 있을 수 없다**

spill 전용 하부 구조도 별도 디렉토리다 — `be/src/exec/spill/` 에 블록 관리자(파일/로그/하이브리드 3종), 입력 스트림, 메모리 테이블, 연산자 메모리 자원 관리자가 들어 있다.

### 3-3. spill 도 기본은 꺼져 있다

`fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java:1601, 1625`:

```java
    private boolean enableSpill = false;
...
    private String spillMode = "auto";
```

**Trino 와 같다 — 기본 꺼짐.** 다만 `spill_mode` 라는 축이 하나 더 있어, 켰을 때 언제 내릴지(`auto` / `force`)를 고를 수 있다.

### 3-4. 정렬 — 컬럼 단위 정렬과 병합 경로 분리

`be/src/exec/sorting/` 의 파일 구성이 설계를 드러낸다.

```
sort_column.cpp     compare_column.cpp   sort_permute.cpp   sort_helper.h
merge.cpp  merge_column.cpp  merge_cascade.cpp  merge_path.cpp
```

두 갈래로 나뉜다.

- **정렬** — `sort_column`(컬럼 단위 정렬), `sort_permute`(순열을 만들어 재배치). 값을 옮기지 않고 **순서 배열만 만든 뒤 마지막에 한 번 재배치**하는 방식이다
- **병합** — `merge_cascade`(다단 병합), `merge_path`(병합 경로 분할). 후자는 **병합을 여러 스레드로 나누기 위한 기법**이다

Trino 가 비교기 하나를 컴파일해 범용 정렬에 넣는 것과 달리, **StarRocks 는 컬럼 단위 정렬과 병렬 병합을 각각 별도 알고리즘으로 구현했다.**

## 4. 실측

**이 축은 현재 랩에서 판별할 수 있는 것이 거의 없다.**

- **해시 조회표 종류** — 어느 구현이 선택됐는지는 플랜에도 프로파일에도 나오지 않는다
- **spill** — 데이터가 6만 건이라 어느 연산자도 메모리 한도에 닿지 않는다. 양쪽 다 기본 꺼짐이기도 하다
- **정렬 구현** — 결과만 같고 내부는 드러나지 않는다

확인한 것은 **설정의 존재와 기본값**뿐이다.

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| spill 기본값 | `spill_enabled` = **false** | `enable_spill` = **false** |
| 추가 축 | `force_spilling_join`(진단용) | `spill_mode` = `auto` |

**이 문서는 코드 비교까지만 쓴다.** 성능 결론을 내지 않는다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino | StarRocks |
|---|---|---|
| 해시 조회표 구현 | **2종** + 바이트코드 생성 | **6종** + 매칭 성질 4분류 |
| 정수 키 최적화 | 전용 클래스(해시는 계산) | **배열 첨자 직접 접근**(해시 없음) |
| spill 가능 연산자 | **4계열** | **12계열** |
| spill 기본값 | 꺼짐 | 꺼짐 |
| 중첩 루프 조인 spill | 없음 | 있음 |
| 다중 소비 교환 spill | 해당 기능 자체가 없음 | 있음 |
| 정렬 | 비교기 **컴파일** + 범용 정렬 | 컬럼 단위 정렬 + 병렬 병합 **전용 구현** |
| 그룹별 상위 N | `GroupedTopN*` 5개 클래스 | `PARTITION-TOP-N` 연산자 |

### 5-2. "구현을 늘리는가, 만들어내는가"

A-3-01 5-3의 구도가 연산자 층에서 반복된다.

- **StarRocks** — 키의 성질(정수/좁은 범위/조밀함)마다 **클래스를 따로 만든다.** C++ 템플릿이라 단형화가 공짜다
- **Trino** — 특수 케이스 하나(bigint)만 클래스로 두고, 나머지는 **런타임에 바이트코드를 생성**한다. 클래스를 늘리면 JIT 이 인라이닝을 포기하기 때문이다

**두 방식 다 "타입별 전용 코드"라는 같은 목표에 도달한다.** 차이는 그 코드가 컴파일 시점에 만들어지느냐 실행 시점에 만들어지느냐다. 후자는 첫 실행에 컴파일 비용이 붙지만, 실제 데이터 분포를 보고 결정할 여지가 있다.

### 5-3. spill 범위 차이는 무엇을 뜻하는가

**12계열 대 4계열은 "메모리가 부족할 때 살아남는 쿼리의 범위"다.**

Trino 에서 중첩 루프 조인(등가 조건이 없는 조인)이 메모리를 넘기면 **spill 할 방법이 없어 쿼리가 실패한다.** StarRocks 에는 그 경로가 있다.

다만 **양쪽 다 기본이 꺼져 있다**(2-3, 3-3)는 점이 중요하다. spill 은 성능을 크게 떨어뜨리므로 "느려도 끝나는 것"이 "빠르게 실패하는 것"보다 나을 때만 켠다. **기본값이 같다는 것은 두 엔진이 이 판단을 공유한다는 뜻이다.**

`plan/01` B-1 이 이 주제를 따로 두고 있으므로, **한도 계층과 OOM 정책은 B-1-01** 에서 다룬다.

### 5-4. 정렬에서 갈리는 지점

Trino 의 정렬은 **비교기가 빠르면 전체가 빠르다**는 구조다. 그래서 비교기를 컴파일한다.

StarRocks 는 다르게 접근한다 — `sort_permute` 는 값을 옮기지 않고 **순서만 계산한 뒤 마지막에 한 번 재배치**한다. 컬럼너 배치에서는 이 편이 메모리 접근이 유리하다. 그리고 `merge_path` 는 **병합 자체를 여러 스레드로 쪼갠다.**

**A-3-01의 "컬럼을 자료형별로 나눠 두면 단형화된 코드를 쓸 수 있다"가 여기서 실익으로 나타난다** — 컬럼 단위 정렬은 컬럼의 실제 타입을 컴파일 시점에 알아야 효율적이다.

## 6. 결론

**같은 알고리즘 계열을 각자의 언어 강점에 맞춰 구현했다. 이 랩에서는 우열을 판정할 수 없다.**

- **해시 조인** — StarRocks 가 키 성질별 전용 구현 6종 + 매칭 성질 4분류로 더 잘게 나눴고, 특히 **좁은 범위 정수 키에서 해시 계산 자체를 없애는 경로**가 있다. Trino 는 2종 + 바이트코드 생성으로 같은 목표에 접근한다
- **spill** — **StarRocks 가 뚜렷하게 넓다**(12계열 대 4계열). 중첩 루프 조인과 다중 소비 교환은 Trino 에 대응물이 없다. 다만 **양쪽 다 기본 꺼짐**이라 평시 동작에는 차이가 없다
- **정렬** — Trino 는 비교기를 컴파일하고, StarRocks 는 컬럼 단위 정렬과 병렬 병합을 전용 구현한다

### 아직 답하지 않은 것

- **실측 전부** — 데이터 6만 건에서는 어느 연산자도 메모리 한도에 닿지 않고, 어느 해시 구현이 선택됐는지도 노출되지 않는다
- **어느 해시 구현이 실제로 빠른가** — `DirectMapping` 이 이론상 유리하지만 재지 않았다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **바이트코드 생성의 컴파일 비용** — Trino 의 첫 실행 지연이 얼마인지 측정하지 않았다. A-3-05의 주제와 겹친다
- **spill 이 실제로 걸렸을 때의 성능** — 양쪽 다 켜고 메모리를 좁혀 재는 실험이 필요하다. 현재 호스트(RAM 7.6GB)로는 어렵다
- **메모리 한도 계층과 OOM 정책** — **B-1-01**
- **StarRocks 네이티브 테이블에서의 조인** — 버킷팅된 테이블은 조인 경로가 다르다(colocate/bucket shuffle). **C-1-02**
