## 1. 비교 관점

두 엔진 다 **컬럼너 배치 처리**다. 행 하나씩이 아니라 수천 행 묶음을 컬럼 단위로 들고 다닌다. 여기까지는 같다.

갈리는 지점은 세 개다.

1. **묶음의 크기를 무엇으로 정하는가** — 행 수인가 바이트인가, 고정인가 적응인가
2. **컬럼을 몇 종류로 표현하는가** — 물리 레이아웃별로 통합하는가, 타입별로 나누는가
3. **벡터화를 누구에게 맡기는가** — JIT 에 맡기는가, 인트린식을 직접 쓰는가

이 문서가 A-3 의 첫 문서인 이유는, **여기서 정해진 표현이 뒤따르는 모든 연산자 구현을 제약하기 때문**이다.
해시 조인이 어떻게 생겼는지(A-3-03), 표현식을 어떻게 평가하는지(A-3-05)는 전부 이 계층 위에 얹힌다.

결론부터: **규모는 대등하다(블록 13,754줄 vs 컬럼 16,364줄). 차이는 "Java 로 할 수 있는 것"과 "C++ 로 할 수 있는 것"의 경계에서 나온다.**

## 2. Trino 구현

### 2-1. Page = 블록 배열 + 행 수

`works/trino/core/trino-spi/src/main/java/io/trino/spi/Page.java:50-52`:

```java
private final Block[] blocks;
private final int positionCount;
private volatile long sizeInBytes = -1;
```

**Page 는 스키마를 들고 있지 않다.** 블록 배열과 행 수뿐이고, 각 블록이 어떤 컬럼인지는 플랜의 심볼 순서로 정해진다.
`sizeInBytes` 를 `volatile` 로 캐시하는 것에서 보이듯, **바이트 크기가 1급 관심사**다.

### 2-2. Block 은 봉인된 3분류

`core/trino-spi/src/main/java/io/trino/spi/block/Block.java:21-24`:

```java
public sealed interface Block
        permits DictionaryBlock,
                RunLengthEncodedBlock,
                ValueBlock
```

**딕셔너리와 RLE 가 타입 시스템의 1급 시민이다.** 인코딩된 데이터가 "특수한 컬럼"이 아니라 블록 종류 자체다.
`ValueBlock` 이 실제 값을 담은 블록의 상위 타입이고, 구현이 **11개** 있다.

| 블록 | 담는 것 |
|---|---|
| `ByteArrayBlock` / `ShortArrayBlock` / `IntArrayBlock` / `LongArrayBlock` | 고정 폭 1/2/4/8바이트 |
| `Fixed12Block` / `Int128ArrayBlock` | 12바이트 / 16바이트 |
| `VariableWidthBlock` | 가변 길이(문자열 등) |
| `ArrayBlock` / `MapBlock` / `RowBlock` | 복합 타입 |
| `VariantBlock` | VARIANT |

**핵심은 "타입이 아니라 물리 레이아웃으로 나눈다"는 점이다.** `BIGINT` 와 `DOUBLE` 이 같은 `LongArrayBlock` 을 쓴다 —
`spi/type/DoubleType.java:114` 가 `doubleToLongBits` 로 변환해 넣는다. 논리 타입 정보는 `Type` 객체가 따로 들고 있다.

블록 패키지 전체는 파일 **64개, 13,754줄**이다.

### 2-3. 배치 크기 — 바이트 예산을 목표로 행 수를 적응시킨다

Trino 에는 "행 몇 개짜리 배치"라는 고정값이 없다. 대신 **상한과 목표 바이트**가 있다.

| 상수 | 값 | 위치 |
|---|---|---|
| `MAX_BATCH_SIZE` | 8192 행 | `operator/project/PageProcessor.java:55` |
| `MAX_PAGE_SIZE_IN_BYTES` | 16 MB | `:56` |
| `MIN_PAGE_SIZE_IN_BYTES` | 4 MB | `:57` |
| `DEFAULT_MAX_PAGE_SIZE_IN_BYTES` | 1 MB | `spi/block/PageBuilderStatus.java:22` |

그리고 **런타임에 배치 크기를 스스로 바꾼다** — `PageProcessor.java:220-231`:

```java
private void updateBatchSize(int positionCount, long pageSize)
{
    // if we produced a large page, halve the batch size for the next call
    if (positionCount > 1 && pageSize > MAX_PAGE_SIZE_IN_BYTES) {
        projectBatchSize = projectBatchSize / 2;
    }

    // if we produced a small page, double the batch size for the next call
    if (pageSize < MIN_PAGE_SIZE_IN_BYTES && projectBatchSize < MAX_BATCH_SIZE) {
        projectBatchSize = projectBatchSize * 2;
    }
}
```

**바이트가 목표이고 행 수는 그것을 맞추는 수단이다.** 컬럼 폭이 제각각인 페더레이션 환경에서
"행 4096개"가 어떤 때는 40KB, 어떤 때는 400MB 가 되는 문제를 이렇게 피한다.

세션 속성으로 노출된 것은 filter/project 출력의 **하한** 둘뿐이다 — `FeaturesConfig.java:118-119`:

```java
private DataSize filterAndProjectMinOutputPageSize = DataSize.of(500, KILOBYTE);
private int filterAndProjectMinOutputPageRowCount = 256;
```

### 2-4. NULL 과 메모리 회계

블록은 불변(immutable)이고, `getRegion`/`copyRegion` 으로 잘라 쓴다. 같은 배열을 여러 블록이 공유할 수 있으므로
메모리 회계가 두 갈래다 — `Block.java:50`, `:61`:

```java
long getSizeInBytes();          // 논리 크기
long getRetainedSizeInBytes();  // 실제 붙잡고 있는 크기
```

`Page.retainedBytesForEachPart(visitor)` 로 **공유된 부분을 중복 계산하지 않고** 합산한다.
`DictionaryBlock` 하나가 큰 사전을 참조할 때 이 구분이 없으면 메모리 회계가 크게 틀린다.

### 2-5. 벡터화 — "JIT 에 맡긴다"는 말은 이제 정확하지 않다

Trino 483 은 **Java Vector API(`jdk.incubator.vector`)를 실제로 쓴다.** 다만 범위가 좁다.

전체 트리에서 `jdk.incubator.vector` 를 참조하는 파일은 **14개**이고, 벤치마크를 빼면 실제 용도는 둘이다.

| 용도 | 파일 |
|---|---|
| **블록 직렬화 시 NULL 압축·확장** | `spi/block/{Byte,Short,Int,Long}ArrayBlockEncoding.java` (4개) |
| **Parquet 비트 언패킹** | `parquet/reader/decoders/VectorIntBitUnpackers.java`, `parquet/reader/flat/VectorBitPackingUtils.java` |

CPU 지원 여부는 런타임에 판별한다 — `io/trino/simd/BlockEncodingSimdSupport.java` 가 `/proc/cpuinfo` 플래그를 읽어
`SimdCapability` 8종(`COMPRESS_/EXPAND_` × `BYTE/SHORT/INT/LONG`)의 가용성을 정하고, 없으면 스칼라 경로로 떨어진다.

**즉 SIMD 는 "직렬화와 파일 디코딩 경계"에만 있고, 연산자와 표현식 평가에는 없다.**
그쪽은 바이트코드 생성(`sql/gen/`, 56파일 **9,383줄**)이 담당하며 실제 벡터화는 JIT 의 자동 벡터화에 맡긴다 — A-3-05의 주제다.

## 3. StarRocks 구현

### 3-1. Chunk = 컬럼 벡터 + 스키마 + slot 매핑

`works/starrocks/be/src/column/chunk.h`:

```cpp
size_t num_columns() const { return _columns.size(); }
size_t num_rows() const { return _columns.empty() ? 0 : _columns[0]->size(); }
void set_slot_id_to_index(SlotId slot_id, size_t idx) { _slot_id_to_index[slot_id] = idx; }
```

Trino 의 Page 와 달리 **Chunk 는 스키마와 slot id → 인덱스 해시맵을 들고 다닌다**(`:155-159`).
연산자가 "이 slot 의 컬럼"을 이름으로 찾을 수 있다는 뜻이고, 대신 청크마다 그 맵을 유지하는 비용이 붙는다.

### 3-2. Column 은 타입별 템플릿 인스턴스

`be/src/column/column.h:41`:

```cpp
class Column : public Cow<Column> {
```

컬럼 방문자(`column_visitor.h`)가 열거하는 구체 타입이 **53종**이다. 목록을 보면 성격이 드러난다.

```
NullableColumn  ConstColumn  ArrayColumn  MapColumn  StructColumn
BinaryColumn  LargeBinaryColumn  JsonColumn
Int8Column  UInt8Column  Int16Column  ...  Int128Column  DoubleColumn  FloatColumn
DateColumn  TimestampColumn  Decimal32/64/128/256Column
HyperLogLogColumn  BitmapColumn  PercentileColumn
FixedLengthColumn<int96_t>  FixedLengthColumnBase<int64_t>  ...
ArrayViewColumn  ColumnView
```

**Trino 가 물리 레이아웃으로 통합한 자리를, StarRocks 는 타입별 템플릿 인스턴스로 펼쳤다.**
`BIGINT` 와 `DOUBLE` 이 각각 `Int64Column` / `DoubleColumn` 으로 별개다.

이것은 언어 차이에서 직접 나온다. C++ 템플릿은 컴파일 시점에 단형화(monomorphize)되므로 타입마다 클래스를
만들어도 가상 호출이 늘지 않는다. Java 에서 같은 짓을 하면 호출 지점이 megamorphic 해져 JIT 인라이닝이 깨진다.

컬럼 패키지 전체는 파일 **69개, 16,364줄**이다.

### 3-3. NULL 과 상수는 감싸는 컬럼이다

Trino 가 블록 안에 `boolean[] valueIsNull` 을 두는 대신, StarRocks 는 **컬럼을 감싼다** — `nullable_column.h:362-364`:

```cpp
ColumnPtr _data_column;
NullColumnPtr _null_column;
mutable bool _has_null;
```

`_null_column` 은 행당 1바이트짜리 `UInt8Column` 이고, `_has_null`(`:82`)이 빠른 경로를 만든다.
`ConstColumn` 도 같은 방식의 래퍼다.

여기에 `AdaptiveNullableColumn` 이 따로 있다(`adaptive_nullable_column.h:64-70`):

```cpp
enum class State {
    kUninitialized,
    kNull,
    kConstant,
    kNotConstant,
    kMaterialized,
};
```

**적재 중에는 NULL 마스크를 만들지 않고 상태만 들고 있다가, 실제로 섞이면 그때 물질화한다.**
JSON/CSV/Avro 스캐너가 쓴다(`exec/json_scanner.cpp:267`). Trino 에 대응물이 없다.

**딕셔너리·RLE 컬럼 타입은 없다.** `be/src/column/` 에 `DictColumn`/`RleColumn` 같은 클래스가 존재하지 않는다.
저카디널리티 문자열의 딕셔너리 최적화는 이 계층이 아니라 실행 계층의 별도 기능이다 — A-3-05.

### 3-4. 소유권 모델 — Copy-on-Write 참조 카운트

`column.h:41` 의 `Cow<Column>` 이 핵심이다. 컬럼은 **참조 카운트 기반 COW 객체**다 — `column.h:482-483`:

```cpp
MutablePtr res = ptr->try_mutate(); /// Now use_count is 2.
ptr.reset();                        /// Reset use_count to 1.
```

참조자가 하나뿐이면 제자리에서 고치고, 여럿이면 복사한다. `ChunkPtr` 는 `std::shared_ptr<Chunk>` 다(`vectorized_fwd.h:112`).

Trino 의 블록은 **불변이고 GC 가 수거한다.** 같은 결과("공유하되 안전하게")를 서로 다른 수단으로 얻는다 —
한쪽은 참조 카운트, 한쪽은 가비지 컬렉터.

메모리 회계는 양쪽이 놀랍도록 비슷하게 갈라져 있다 — `column.h:438-441`:

```cpp
virtual size_t memory_usage() const { return container_memory_usage() + reference_memory_usage(); }
```

Trino 의 `getSizeInBytes` / `getRetainedSizeInBytes` 와 같은 문제의식이다.

### 3-5. 배치 크기 — 행 수 고정, 세션에서 조절

`be/src/common/config.h:854`:

```
CONF_Int32(vector_chunk_size, "4096");
```

세션 변수로도 있다 — `qe/SessionVariable.java:1431-1432`:

```java
@VariableMgr.VarAttr(name = CHUNK_SIZE, flag = VariableMgr.INVISIBLE)
private int chunkSize = 4096;
```

**행 수 고정값이고, 적응 로직이 없다.** BE 코드에서 `state->chunk_size()` 또는 `config::vector_chunk_size` 를
참조하는 지점이 **246곳**으로, 실행 전체의 기본 단위다.

`INVISIBLE` 플래그가 붙어 `SHOW VARIABLES` 목록에는 안 나오지만 `SELECT @@chunk_size` / `SET chunk_size` 는 동작한다(4-1).

### 3-6. 벡터화 — 인트린식을 직접 쓴다

`be/src/simd/` 에 전용 디렉토리가 있다 — 파일 10개, **2,221줄**.

```
selector.h  mulselector.h  gather.h  expand.{h,cpp}  delta_decode.h
batch_run_counter.h  simd.h  simd_utils.h  multi_version.h
```

AVX/SSE 인트린식(`__m256i`, `_mm256_*`)을 쓰는 파일은 트리 전체에서 **45개**이고 영역이 넓다.

| 영역 | 파일 수 |
|---|---|
| `util/` | 9 |
| `simd/` | 8 |
| **`exprs/`** | 8 |
| **`column/`** | 5 |
| `storage/` | 3 (+ `storage/rowset/` 1) |
| `formats/parquet`, `formats/orc` | 3 |
| 기타 | 8 |

`column/` 아래 5개는 `column_helper.cpp`, `binary_column.cpp`, `array_column.cpp`, `map_column.cpp`, `column_hash.h` —
**필터 적용, 문자열 처리, 해시 계산 같은 핵심 경로**다.

`multi_version.h` 는 같은 함수를 SSE·AVX2·AVX512 로 여러 벌 컴파일해 런타임에 고르는 장치다.

## 4. 실측

전체 절차·조건은 `docs/evidence/A-3/20260904-batch-unit-probes.md`.

**이 축은 런타임으로 볼 수 있는 것이 적다.** 블록·컬럼의 메모리 배치는 플랜에도 프로파일에도 드러나지 않는다.
확인한 것은 배치 단위의 노브와 그 효과까지다.

### 4-1. 노출된 노브의 축이 다르다

| 엔진 | 노브 | 값 | 성격 |
|---|---|---|---|
| StarRocks | `chunk_size` | 4096 행 | **실행 전체의 기본 배치** |
| Trino | `filter_and_project_min_output_page_row_count` | 256 행 | filter/project 출력의 **하한** |
| Trino | `filter_and_project_min_output_page_size` | 500 kB | 같은 것의 바이트 축 |

Trino 에는 배치 크기 자체를 정하는 세션 속성이 없다 — 코드 상수 + 런타임 적응이다(2-3).

### 4-2. 청크는 실제 메모리 단위다

`chunk_size` 를 바꾸고 같은 쿼리의 `QueryAllocatedMemoryUsage` 를 읽었다(각 2회, 편차 0.5% 미만).

| `chunk_size` | 할당 메모리 |
|---|---|
| 64 | 3.745 / 3.733 MB |
| **4096** (기본) | **3.172 / 3.169 MB** |
| 32768 | 7.076 / 7.077 MB |

- 8배로 키우면 할당량이 **2.2배**
- 64로 줄이면 오히려 **늘었다** — 청크당 고정 비용 × 청크 수

**결과는 세 설정에서 모두 같았고 Trino 와도 같았다.** 배치 크기는 성능 노브이지 의미를 바꾸지 않는다.

> **시간은 재지 않았다.** 어느 `chunk_size` 가 빠른지는 이 랩에서 판정하지 않는다(`plan/02` 6-2절).

### 4-3. 배치 단위는 관측 지표로 노출되지 않는다

| 엔진 | 프로파일에 보이는 단위 |
|---|---|
| Trino 483 | `Input: 60175 rows (587.64kB)` — **행과 바이트를 함께** |
| StarRocks 4.0.14 | `OutputRows: 60.175K` + 타이머 + `InstanceAllocatedMemoryUsage` |

**페이지·청크 개수를 보여주는 카운터는 어느 쪽에도 없다.** StarRocks 프로파일의 `GroupChunkRead` 는
Parquet row group 타이머이지 실행 청크와 무관하다(`pipeline_profile_level=2` 로 올려도 같다).

여기서도 2-1의 성격이 비친다 — **Trino 는 바이트를 함께 보여주고, StarRocks 는 행과 시간을 보여준다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino | StarRocks |
|---|---|---|
| 배치 이름 | `Page` | `Chunk` |
| 배치가 들고 있는 것 | 블록 배열 + 행 수 + 캐시된 바이트 크기 | 컬럼 벡터 + **스키마 + slot id 맵** |
| 배치 크기 기준 | **바이트 예산**(1/4/16MB), 행 수는 수단 | **행 수 고정**(4096) |
| 배치 크기 적응 | **런타임 배증/반감** (상한 8192행) | 없음 |
| 사용자 노브 | 없음(연산자 출력 하한 둘만) | `chunk_size` 세션 변수 |
| 컬럼 구현 수 | **11** (+ 래퍼 2) | **53** (템플릿 인스턴스 포함) |
| 분류 기준 | **물리 레이아웃** (BIGINT·DOUBLE 이 같은 블록) | **타입** (각각 별도 클래스) |
| 딕셔너리·RLE | **블록 타입으로 존재**(`sealed` 3분류의 둘) | 컬럼 타입 없음 — 실행 계층 별도 기능 |
| NULL | 블록 안의 `boolean[]`(없으면 생략) | **감싸는 `NullableColumn`** + `_has_null` + 적응 상태 5종 |
| 소유권 | 불변 + GC | **COW 참조 카운트** |
| 메모리 회계 | `getSizeInBytes` / `getRetainedSizeInBytes` + 중복 제거 방문자 | `container_memory_usage` + `reference_memory_usage` |
| SIMD | Vector API **14파일**, 직렬화·Parquet 디코딩 한정 | 인트린식 **45파일**, `exprs`/`column`/`storage` 핵심 경로 |
| 코드 규모 | 블록 패키지 64파일 13,754줄 | 컬럼 패키지 69파일 16,364줄 |

### 5-2. 배치 기준이 바이트냐 행이냐

A-2-02에서 본 구도가 여기서 반복된다 — **Trino 는 바이트를, StarRocks 는 행 수를 센다.**

이유도 같다. **Trino 는 컬럼 폭을 모르는 데이터를 상대한다.** 커넥터가 50개 넘고, 어떤 테이블은 컬럼이 3개
어떤 테이블은 300개다. "행 4096개"라는 약속은 그런 환경에서 메모리 사용량을 통제하지 못한다. 그래서 바이트를
목표로 두고 행 수를 런타임에 조절한다.

**StarRocks 는 자기 스토리지의 스키마를 안다.** 행 수를 고정해도 메모리가 폭발하지 않고, 고정값이면
컴파일 시점에 버퍼 크기를 정할 수 있어 C++ 최적화에 유리하다.

**대신 튜닝 손잡이가 반대다.** StarRocks 는 사용자가 `chunk_size` 를 돌릴 수 있고 실제로 효과가 있다(4-2).
Trino 는 돌릴 것이 없고 엔진이 알아서 한다. 어느 쪽이 나은지는 상황에 달렸다 —
자동 조절은 대부분의 경우 옳지만, **틀렸을 때 고칠 방법이 없다.**

### 5-3. 컬럼 종류 11 vs 53 — 언어가 만든 차이

숫자만 보면 StarRocks 가 훨씬 잘게 나눈 것 같지만, **표현 가능한 것의 범위는 비슷하다.**
차이는 "타입을 어디에 담는가"다.

- **Trino**: 물리 레이아웃별 블록 11종 + 논리 타입은 `Type` 객체가 별도로 보유.
  `DoubleType.java:114` 가 `doubleToLongBits` 로 변환해 `LongArrayBlockBuilder` 에 넣는다
- **StarRocks**: `FixedLengthColumn<T>` 를 타입마다 인스턴스화. 타입 정보가 C++ 타입 자체에 들어 있다

**이것은 취향이 아니라 언어 제약의 귀결이다.** Java 에서 타입마다 블록 클래스를 만들면 `Block.getLong()` 호출
지점이 megamorphic 해져 JIT 이 인라이닝을 포기한다. C++ 템플릿은 반대로 인스턴스마다 코드를 따로 만들어
가상 호출조차 없앨 수 있다.

**그래서 "Trino 가 덜 세분화됐다"는 성능 결론으로 읽으면 안 된다.** 각자의 런타임에서 빠른 형태를 고른 것이다.

### 5-4. 인코딩을 타입 시스템에 넣을 것인가

이 축에서는 반대로 **Trino 쪽이 더 명시적**이다.

`Block` 이 `permits DictionaryBlock, RunLengthEncodedBlock, ValueBlock` 으로 봉인돼 있다는 것은,
**모든 연산자가 "이 블록이 딕셔너리일 수 있다"를 타입 수준에서 마주하게 만든다는 뜻**이다.
덕분에 딕셔너리 블록을 받은 연산자가 사전만 처리하고 인덱스를 그대로 넘기는 최적화를 안전하게 할 수 있다.

StarRocks 의 Chunk 계층에는 딕셔너리 컬럼 타입이 없다. 저카디널리티 딕셔너리 최적화는 존재하지만
**컬럼 표현이 아니라 실행 계획 수준의 별도 기능**이고(A-3-05), 그래서 적용 조건이 더 좁을 수 있다.

반대로 StarRocks 는 **NULL 과 상수를 래퍼 컬럼으로** 두어 같은 이점을 그쪽에서 얻는다.
`AdaptiveNullableColumn` 의 5단 상태(3-3)는 Trino 에 대응물이 없는, 한 걸음 더 나간 최적화다.

**즉 "무엇을 타입으로 승격시켰는가"가 다르다** — Trino 는 인코딩을, StarRocks 는 NULL·상수를.

### 5-5. 벡터화 — 통념을 정정해야 한다

"Trino 는 Java 라서 SIMD 를 못 쓴다"는 서술은 **483 기준으로 틀렸다.** Vector API 를 실제로 쓴다(2-5).

정확한 서술은 이렇다.

| | Trino | StarRocks |
|---|---|---|
| SIMD 사용 파일 수 | 14 (벤치마크 포함) | 45 |
| 쓰는 곳 | **직렬화 NULL 압축·확장, Parquet 비트 언패킹** | `exprs/`, `column/`, `storage/`, `util/` — **연산 경로 전반** |
| CPU 판별 | 런타임(`/proc/cpuinfo` 플래그 → `SimdCapability` 8종) | 컴파일 다중 버전(`multi_version.h`) + 런타임 디스패치 |
| 연산자·표현식 평가 | **바이트코드 생성 + JIT 자동 벡터화**(9,383줄) | **인트린식 직접 작성** |

**차이는 "SIMD 를 쓰느냐"가 아니라 "어디까지 직접 쓰느냐"다.** Trino 는 데이터 경계(직렬화·파일 디코딩)에만
손으로 쓴 SIMD 를 두고, 연산 자체는 JIT 에 맡긴다. StarRocks 는 필터·해시·표현식까지 직접 쓴다.

이것도 언어 제약이다 — Java Vector API 는 아직 incubator 이고, `module-info.java:20` 에
`requires jdk.incubator.vector` 를 넣어야 쓸 수 있다. 커넥터 플러그인이 이것을 쓰게 만들 수는 없다.

**성능 차이의 크기는 이 랩에서 측정하지 않았다.** 코드 표면적만으로 결론을 내면 안 된다.

## 6. 결론

**같은 컬럼너 배치 모델을 각자의 언어에 맞게 구현했다. 규모는 대등하고, 우열은 이 랩에서 판정할 수 없다.**

- **배치 기준이 다르다.** Trino 는 바이트 예산(1~16MB)을 목표로 행 수를 **런타임에 조절**하고, StarRocks 는
  행 수(4096)를 **고정**한다. A-2-02의 "바이트 대 행 수" 구도가 실행 계층에서 반복된다
- **컬럼 종류 11 대 53 은 언어 제약의 귀결이다.** Java 는 megamorphic 호출을 피하려고 물리 레이아웃으로
  통합했고, C++ 은 템플릿 단형화가 공짜라 타입별로 펼쳤다. 표현 범위는 비슷하다
- **타입으로 승격시킨 대상이 다르다.** Trino 는 딕셔너리·RLE 를 `sealed` 블록 3분류에 넣었고,
  StarRocks 는 NULL·상수를 래퍼 컬럼으로 두고 `AdaptiveNullableColumn` 까지 갔다
- **"Java 라서 SIMD 를 못 쓴다"는 483 기준으로 틀렸다.** Vector API 를 쓰지만 **직렬화와 Parquet 디코딩에 한정**되고,
  연산 경로는 바이트코드 생성 + JIT 에 맡긴다. StarRocks 는 45개 파일에서 인트린식을 직접 쓴다

**운영 관점**

| 상황 | 판단 |
|---|---|
| 컬럼이 아주 넓은 테이블(수백 컬럼)을 다룬다 | Trino 의 바이트 기준 적응이 유리한 구조다. StarRocks 는 `chunk_size` 를 낮춰야 할 수 있다 |
| 행이 좁고 많은 테이블을 다룬다 | StarRocks 는 `chunk_size` 를 올려볼 수 있다(4-2에서 노브가 살아 있음을 확인) |
| 메모리 사용량이 예측 가능해야 한다 | Trino 는 바이트 예산이 명시돼 있다. StarRocks 는 행 수 × 컬럼 폭이라 스키마에 따라 달라진다 |
| 배치 크기를 직접 튜닝하고 싶다 | **StarRocks 만 가능하다.** Trino 에는 노브가 없다 |

### 아직 답하지 않은 것

- **실행 시간과 처리량** — 전 항목 미측정. 벡터화 구현 차이가 실제로 얼마나 벌어지는지는 이 문서로 말할 수 없다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **SIMD 가 실제로 실행되는지** — CPU 카운터 수집이 필요하다. 코드에 있다는 것과 도는 것은 다르다
- **JIT 자동 벡터화의 실효** — Trino 의 바이트코드 생성 결과가 실제로 벡터화되는지는 JVM 로그(`-XX:+PrintCompilation` 등)가 필요하다
- **`chunk_size` / 배치 크기의 최적값** — 4-2는 메모리 신호만 봤다. 어느 값이 빠른지는 재지 않았다
- **StarRocks 네이티브 테이블의 청크 생성 경로** — 전부 Iceberg 외부 테이블로만 확인했다. 세그먼트 → 청크 경로는 C-1-02
- **딕셔너리 최적화의 실제 적용 범위** — Trino 의 `DictionaryBlock` 전파와 StarRocks 의 저카디널리티 전역 딕셔너리 비교는 **A-3-05**
- **복합 타입(ARRAY/MAP/ROW)의 표현 비교** — `ArrayBlock`/`MapBlock`/`RowBlock` vs `ArrayColumn`/`MapColumn`/`StructColumn` 을 표면적으로만 대조했다
