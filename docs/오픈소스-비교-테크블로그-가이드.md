# 오픈소스 2종 비교 테크 블로그 작성 가이드

Oct 16, 2026 · @JI YONG GI

## 이 가이드가 다루는 것

두 오픈소스를 **문서와 코드까지** 읽고 비교하는 블로그 글 한 편을, 기획부터 발행까지 6단계로 만드는 방법입니다. 한 편당 작업량은 보통 3\~5일(하루 2\~3시간 기준)이며, 가장 오래 걸리는 단계는 코드 읽기(2단계·3단계)입니다.

좋은 비교 글의 조건은 세 가지입니다.

- **질문이 하나다**: "A vs B"가 아니라 "이런 상황에서 A와 B 중 무엇을 고를까"에 답한다.
- **근거가 코드에 있다**: 공식 문서의 주장을 그대로 옮기지 않고, 실제 구현과 실행 결과로 확인한다.
- **재현할 수 있다**: 독자가 같은 커밋, 같은 명령으로 같은 결과를 얻을 수 있다.

독자는 "둘 중 하나를 골라야 하는 개발자"로 고정합니다. 입문자용 소개와 선택 가이드를 한 글에 섞으면 둘 다 약해집니다.

## 1단계 · 비교 대상과 질문 정하기 (반나절)

글의 성패는 여기서 70%가 결정됩니다. 두 프로젝트와 비교 축을 먼저 고정하고, 나머지 단계는 그 축을 채우는 작업으로 만듭니다.

**프로젝트 선정 기준**

- 같은 문제를 푸는가: 예) Vite vs Turbopack(번들러), Prisma vs Drizzle(ORM), Zod vs Valibot(스키마 검증). 범주가 다르면 비교가 아니라 소개가 됩니다.
- 둘 다 살아 있는가: 최근 90일 내 릴리스, 열린 이슈에 메인테이너 응답이 있는지 확인합니다.
- 코드를 읽을 수 있는 규모인가: 핵심 경로가 수천 줄 안에 들어오는 프로젝트가 적당합니다. 수십만 줄짜리는 모듈 하나로 범위를 좁힙니다.

**비교 축 설계**: 축은 4\~6개로 제한하고, 각 축마다 "무엇을 확인하면 답이 나오는가"를 미리 적습니다.

| 축 | 확인할 질문 | 확인 방법 |
| --- | --- | --- |
| 설계 철학 | 왜 이렇게 만들었나, 무엇을 포기했나 | README·설계 문서·초기 이슈/RFC |
| 핵심 동작 방식 | 요청 하나가 어떤 경로로 처리되나 | 코드 추적 (3단계) |
| API·DX | 같은 작업을 몇 줄로, 얼마나 직관적으로 하나 | 동일 예제 직접 작성 |
| 성능·자원 | 지연, 처리량, 메모리, 빌드 시간 중 글 주제에 맞는 1\~2개 | 재현 가능한 벤치마크 |
| 생태계·운영 | 플러그인, 타입 지원, 디버깅, 마이그레이션 | 문서·이슈 트래커·릴리스 노트 |
| 유지보수 건강도 | 릴리스 주기, 기여자 수, 이슈 처리 속도 | GitHub Insights, 체인지로그 |

축을 정했으면 글의 **한 문장 질문**을 적어 둡니다. 예) "중간 규모 Next.js 프로젝트에서 ORM을 Prisma에서 Drizzle로 바꿀 가치가 있는가." 이후 모든 조사는 이 문장에 답하는 데만 씁니다.

## 2단계 · 기술 문서 읽기 (프로젝트당 반나절)

문서는 "저자가 주장하는 것"을 모으는 단계입니다. 여기서 모은 주장은 3단계에서 코드로 검증할 **가설 목록**이 됩니다. 읽는 순서를 지키면 시간이 절반으로 줄어듭니다.

1. **README와 "Why X?" 페이지**: 프로젝트가 스스로를 어떻게 자리매김하는지, 어떤 경쟁 프로젝트를 의식하는지 적습니다.
2. **아키텍처·설계 문서**: `docs/architecture`, `DESIGN.md`, `CONTRIBUTING.md`의 "코드 구조" 절. 없으면 메인테이너의 블로그 글이나 컨퍼런스 발표를 찾습니다.
3. **RFC·ADR·설계 이슈**: `rfcs/` 디렉터리, "RFC" 라벨 이슈, 논쟁이 길었던 PR. 트레이드오프가 가장 솔직하게 적힌 곳입니다.
4. **체인지로그와 마이그레이션 가이드**: 최근 3개 메이저/마이너 버전. 무엇을 깨뜨렸고 왜 바꿨는지가 설계 철학의 변화를 보여 줍니다.
5. **API 레퍼런스**: 1단계에서 정한 "동일 예제"를 작성하는 데 필요한 부분만 읽습니다. 전체를 읽지 않습니다.

**메모 규칙**: 프로젝트마다 메모 파일 하나(`notes/A.md`, `notes/B.md`)를 두고, 문장마다 출처 URL과 문서 버전(또는 커밋 해시)을 붙입니다. 이렇게 적어 둡니다.

```markdown
- [주장] 쿼리 빌더는 런타임 오버헤드 없이 SQL을 생성한다
  - 출처: docs/overview.md @ v0.33.0
  - 검증 방법: 생성된 SQL과 호출 스택을 3단계에서 확인
  - 결과: (3단계에서 채움)
```

주장·출처·검증 방법·결과 네 칸을 처음부터 비워 두는 것이 핵심입니다. 비워 둔 칸이 3단계의 할 일 목록이 됩니다.

## 3단계 · 코드 읽기 (프로젝트당 1일)

코드 읽기의 목표는 저장소 전체를 이해하는 것이 아니라, **1단계에서 정한 질문에 답하는 경로 하나를 끝까지 따라가는 것**입니다. 두 프로젝트에서 같은 경로를 따라가야 비교가 성립합니다.

**준비: 버전 고정**

```bash
git clone https://github.com/org/project-a && cd project-a
git checkout v1.4.2          # 글에 적을 태그 또는 커밋 해시
git log -1 --format='%H %ad' # 메모에 기록
```

이 해시를 글의 상단에 명시합니다. 독자가 다른 버전을 보고 "내 코드와 다르다"고 하는 상황을 막습니다.

**읽는 순서**

1. **저장소 지도 그리기 (30분)**: `tree -L 2`로 디렉터리 구조를 보고, `package.json`/`Cargo.toml`/`go.mod`에서 의존성과 빌드 구조를 읽습니다. 가장 큰 디렉터리 3개와 그 역할을 메모합니다.
2. **진입점 찾기 (30분)**: CLI면 `main`/`bin`, 라이브러리면 `index`/`lib`의 공개 export. 사용자가 호출하는 최상위 함수 하나를 고릅니다.
3. **핵심 경로 추적 (2\~3시간)**: 그 함수에서 시작해 "동일 예제"가 실행될 때 거치는 함수를 순서대로 따라갑니다. 에디터의 Go to Definition과 디버거 브레이크포인트를 같이 씁니다. 거쳐 간 파일·함수 이름을 호출 순서대로 적어 두면 그대로 글의 다이어그램 재료가 됩니다.
4. **테스트 읽기 (1시간)**: 핵심 경로의 테스트 파일은 "저자가 보장하려는 동작"의 목록입니다. 테스트가 없는 분기는 글에서 "보장되지 않음"으로 적을 수 있는 근거입니다.
5. **벤치마크 확인 (30분)**: `bench/`, `benchmarks/`, `*_bench.*`가 있으면 무엇을 측정하는지만 봅니다. 저자가 어떤 성능을 중시하는지 드러납니다.
6. **직접 실행 (1\~2시간)**: 동일 예제를 두 프로젝트에서 실행하고, 로그·생성물·프로파일을 저장합니다. 2단계 메모의 "결과" 칸을 여기서 채웁니다.

**도구**

- 호출 추적: 언어별 디버거, `strace`/`dtrace`, Node는 `--cpu-prof`, Python은 `cProfile`, Rust는 `cargo flamegraph`.
- 코드 탐색: `rg`(ripgrep), Sourcegraph, 에디터의 Call Hierarchy.
- 변경 이력: `git log -S '<함수명>'`으로 그 함수가 언제 왜 바뀌었는지, `git blame`으로 연결된 PR을 찾습니다.
- 규모 측정: `tokei` 또는 `cloc`으로 언어별 라인 수. 글에 "핵심 모듈 약 2,400줄" 같은 숫자를 쓸 수 있습니다.

**코드 읽기에서 자주 하는 실수**

- 전체를 읽으려다 지쳐서 핵심 경로를 못 끝낸다 → 경로 하나만 끝까지.
- 문서의 설명을 코드 확인 없이 옮긴다 → 2단계 메모의 "결과" 칸이 비어 있으면 글에 쓰지 않는다.
- 두 프로젝트에서 다른 예제를 실행한다 → 입력·출력·측정 항목을 완전히 동일하게 맞춘다.

## 4단계 · 비교표와 근거 정리 (반나절)

글을 쓰기 전에 비교표를 먼저 완성합니다. 표의 모든 칸이 2단계·3단계 메모의 "결과"로 채워지면 글은 표를 풀어 쓰는 일이 됩니다. 칸이 비면 그 축은 글에서 빼거나 "확인하지 못함"으로 솔직하게 적습니다.

**비교표 형식**: 축마다 사실(코드·문서·측정값)과 해석을 분리합니다.

| 축 | A — 사실 | B — 사실 | 해석 (어떤 상황에 유리한가) | 근거 링크 |
| --- | --- | --- | --- | --- |
| 핵심 동작 | 컴파일 시 SQL 문자열 생성, 런타임 호출 스택 4단계 | 런타임 AST 조립, 호출 스택 11단계 | 콜드 스타트가 중요한 서버리스면 A | `src/compiler.ts#L120`, 프로파일 캡처 |
| 타입 안전성 | 스키마에서 타입 추론, 조인 결과 타입 보장 | 수동 제네릭 필요 | 대형 스키마면 A, 작은 프로젝트면 차이 미미 | 테스트 `types.test.ts` |

실제 값은 예시입니다. 핵심은 "사실" 칸에 형용사(빠르다, 깔끔하다)가 없고 숫자·파일 경로·동작만 있다는 점입니다.

**근거 관리 규칙**

- 코드 인용은 GitHub의 영구 링크(permalink: 커밋 해시가 포함된 URL)로 남깁니다. 브랜치 링크는 나중에 깨집니다.
- 인용 코드는 30줄 이하, 핵심 함수 하나만. 나머지는 링크로 대신합니다.
- 측정값에는 환경(OS, CPU, 런타임 버전, 반복 횟수)을 반드시 붙입니다.
- 문서의 주장과 코드가 다르면 그 자체가 글의 가장 좋은 소재입니다. 이슈를 찾아 경위를 확인하고, 없으면 글에서 "문서와 구현이 다르다"고 적습니다.

**재현 가능한 실험 패키지**: 벤치마크나 비교 예제는 별도 저장소로 공개합니다. 최소 구성은 다음과 같습니다.

```text
compare-a-vs-b/
├── README.md        # 실행 방법, 환경, 측정 결과 요약
├── a/               # A용 동일 예제 + 의존성 잠금 파일
├── b/               # B용 동일 예제 + 의존성 잠금 파일
├── bench.sh         # 두 쪽을 같은 조건으로 실행
└── results/         # 원본 측정 로그 (CSV 또는 JSON)
```

독자가 이 저장소를 클론해 `bench.sh`만 실행하면 글의 숫자를 재현할 수 있어야 합니다. 글의 신뢰도는 이 저장소가 만듭니다.

## 5단계 · 글 구조와 작성 (1일)

결론을 맨 앞에 두고, 비교표를 중심에 놓고, 코드 추적을 그 근거로 붙이는 구조가 가장 잘 읽힙니다. 분량은 한국어 기준 4,000\~7,000자, 코드 블록 5\~8개가 적당합니다.

**추천 목차**

1. **한 문장 결론** (3줄 이내): "X 상황이면 A, Y 상황이면 B." 글 전체를 읽지 않아도 답을 가져갈 수 있게 합니다.
2. **비교 범위와 버전**: 두 프로젝트의 버전·커밋 해시, 테스트 환경, 다루지 않는 범위.
3. **두 프로젝트가 푸는 문제** (각 2\~3문단): 설계 철학과 포기한 것. 2단계의 RFC·ADR에서 가져옵니다.
4. **핵심 동작 비교** (글의 중심, 40%): 동일 예제가 두 프로젝트 안에서 어떻게 처리되는지 호출 경로 다이어그램 + 핵심 함수 코드 인용. 3단계 추적 결과입니다.
5. **축별 비교** (표 + 축마다 1\~2문단): 4단계 비교표를 그대로 싣고, 해석만 풀어 씁니다.
6. **측정 결과**: 벤치마크 수치, 환경, 재현 저장소 링크. 그래프는 1\~2개.
7. **언제 무엇을 고를까**: 결론을 시나리오별로 다시 풀어 씁니다. "우리 팀이라면"으로 끝내도 좋습니다.
8. **확인하지 못한 것과 출처**: 비워 둔 축, 가정, 참고 링크 전체.

**문단 작성 원칙**

- 문단의 첫 문장이 그 문단의 결론입니다. "살펴보겠습니다"로 시작하지 않습니다.
- 주장 하나에 근거 하나를 붙입니다: 코드 링크, 측정값, 문서 인용 중 하나.
- "더 빠르다"가 아니라 "같은 입력에서 42ms vs 118ms (10회 중앙값)"처럼 씁니다.
- 한 쪽을 깎아내리는 표현은 뺍니다. 트레이드오프로 서술하면 양쪽 커뮤니티 모두가 글을 공유합니다.

**코드 스니펫**: 파일 경로와 줄 번호를 캡션으로 붙이고, 추적 경로의 핵심 분기만 남깁니다. 생략한 부분은 `// ...`로 표시합니다.

```ts
// src/query/compiler.ts#L120-L138 @ a1b2c3d
export function compile(node: QueryNode): SQL {
  // 조인은 컴파일 시점에 평탄화된다 — 런타임 재귀 없음
  const parts = flatten(node)
  // ...
  return join(parts, ' ')
}
```

**다이어그램**: 호출 경로는 상자와 화살표로 그린 시퀀스 또는 플로차트 하나면 충분합니다. 두 프로젝트를 같은 레이아웃·같은 단계 수로 나란히 그리면 차이가 한눈에 보입니다. Mermaid, Excalidraw, D2 중 블로그 플랫폼이 렌더링하는 것을 씁니다.

## 5-1 · 자연스러운 한글로 쓰기

비교 글이 어색하게 읽히는 원인의 대부분은 영어 문서를 머릿속에서 직역한 **번역투**와, 격식을 차리려다 붙은 **군더더기**입니다. 초안을 쓴 뒤 아래 네 가지를 순서대로 점검하면 문장이 20\~30% 짧아지고 읽는 속도가 빨라집니다.

**1. 번역투 걷어내기**: 영어 전치사와 관계절을 그대로 옮긴 표현이 가장 흔합니다.

| 자주 나오는 번역투 | 고친 문장 |
| --- | --- |
| 이 도구를 통해 분석을 수행할 수 있다 | 이 도구로 분석할 수 있다 |
| 성능에 대한 측정 결과 | 성능 측정 결과 |
| 캐시의 경우 메모리에 저장된다 | 캐시는 메모리에 저장한다 |
| 가장 빠른 라이브러리 중 하나이다 | 손꼽히게 빠르다 / 측정값으로 쓴다 |
| 컴파일 시점에 처리되어진다 | 컴파일 시점에 처리한다 |
| 쿼리를 실행함에 있어서 | 쿼리를 실행할 때 |
| A와 함께 사용할 경우 | A와 같이 쓰면 |
| 모든 요청들이 핸들러들로 전달된다 | 모든 요청이 핸들러로 전달된다 |

`~을 통해`, `~에 대한`, `~에 있어서`, `~의 경우`, `~중 하나`, `~라는 사실`, `~되어지다`(이중 피동), 불필요한 복수형 `~들`, 조사 `의` 남발이 대표적입니다. 영어 원문이 수동태여도 한국어에서는 능동으로 바꾸는 편이 자연스럽습니다.

**2. 주어·서술어 호응 맞추기**: 기술 글은 주어를 생략하다가 "누가 무엇을 하는지" 잃기 쉽습니다. "요청이 들어오면 파싱 후 실행된다"는 누가 파싱하는지 없습니다. "라우터가 요청을 파싱하고 핸들러가 실행한다"처럼 주체를 씁니다. 한 문장에 동작이 둘 이상이면 문장을 나눕니다.

**3. 명사화·군더더기 줄이기**: "분석을 수행한다"는 "분석한다", "적용이 가능하다"는 "적용할 수 있다", "\~라고 할 수 있다"는 그냥 "\~이다"로 씁니다. "결론적으로", "시사하는 바가 크다", "살펴보도록 하겠습니다" 같은 상투어는 삭제해도 뜻이 바뀌지 않습니다.

**4. 문장 부호와 외래어**: 한국어에는 쌍반점(;)이 없고 쉼표도 영어보다 적게 씁니다. 연결 어미(\~하고, \~하면) 뒤 쉼표는 대부분 뺍니다. 기술 용어는 처음 한 번만 원어를 병기하고("지연 평가(lazy evaluation)") 이후 한 가지 표기로 통일합니다. 영어를 그대로 두는 편이 나은 용어(API, ORM, 커밋 해시)는 억지로 번역하지 않습니다.

**점검 방법**: 초안을 소리 내어 읽으면 번역투는 대부분 귀에 걸립니다. 추가로 Grep으로 `통해|에 대한|에 있어|의 경우|되어지|중 하나`를 검색해 남은 것을 고칩니다. 문체는 글 전체에서 하나("\~한다" 또는 "\~합니다")로 고정합니다.

참고: [카카오엔터프라이즈 테크니컬 라이팅 10계명 정리](https://ditoday.com/바쁜-개발자를-위한-테크니컬-라이팅-10계명/), [한글 기술 문서 번역 스타일 정리](https://wikidocs.net/381075), 김정선 『내 문장이 그렇게 이상한가요?』([독서록](https://brunch.co.kr/@gnugeun/134))

## 6단계 · 검수와 발행 (반나절)

발행 전 검수에서 가장 많이 걸리는 것은 "버전이 바뀌어 사실이 아니게 된 문장"입니다. 초안을 쓰는 동안 새 릴리스가 나왔는지 마지막으로 확인합니다.

**사실 확인**

- 글의 모든 코드 링크를 다시 열어 봅니다. 영구 링크(커밋 해시 포함)인지, 줄 번호가 맞는지.
- 측정값은 재현 저장소에서 한 번 더 실행해 글의 숫자와 일치하는지 확인합니다.
- 두 프로젝트의 최신 릴리스 노트를 확인하고, 글이 다루는 버전 이후에 바뀐 점이 있으면 "v1.5에서 달라짐" 주석을 답니다.

**라이선스와 저작권**

- 코드 인용 시 프로젝트 라이선스(MIT, Apache-2.0, GPL 등)와 저작권 표시를 글 하단에 적습니다. 30줄 이하 발췌에 출처를 명시하면 대부분의 오픈소스 라이선스에서 문제가 없습니다.
- 프로젝트 로고·마스코트는 상표인 경우가 많으니 쓰지 않거나 브랜드 가이드를 확인합니다.
- 다른 블로그·문서의 문장은 인용 표시와 링크 없이 옮기지 않습니다.

**커뮤니티 피드백**: 발행 전에 양쪽 프로젝트의 Discord·Discussions에 초안 링크를 공유하고 사실 오류를 지적받습니다. 메인테이너가 답하면 글에 "검토해 주신 분"으로 적고, 반영한 내용은 수정 이력에 남깁니다. 이 과정이 글의 신뢰도와 확산을 동시에 만듭니다.

**플랫폼 선택**

| 플랫폼 | 적합한 경우 | 주의점 |
| --- | --- | --- |
| 자체 블로그 (Astro, Hugo, Next.js 등) | 코드 하이라이트·다이어그램 렌더링을 직접 제어하고 싶을 때 | 초기 설정에 하루 소요, SEO·RSS 직접 구성 |
| velog, Medium, dev.to | 빠르게 올리고 노출을 얻고 싶을 때 | Mermaid 미지원 플랫폼은 다이어그램을 이미지로 변환 |
| GitHub 저장소 README + 블로그 요약 | 재현 저장소가 글의 중심일 때 | 긴 글은 README보다 블로그가 읽기 편함 |

**발행 후**: 두 프로젝트의 다음 메이저 릴리스가 나오면 글 상단에 "이 글은 vX 기준, vY에서 ○○가 달라졌습니다"를 추가합니다. 비교 글은 업데이트할수록 검색 유입이 오래갑니다.

## 작업 체크리스트와 템플릿

한 편을 쓸 때마다 아래 체크리스트를 복사해 씁니다. 전부 체크되기 전에는 발행하지 않습니다.

**체크리스트**

- [ ] 글이 답하는 질문을 한 문장으로 적었다
- [ ] 비교 축 4\~6개와 각 축의 확인 방법을 정했다
- [ ] 두 프로젝트의 버전(태그·커밋 해시)을 고정하고 글에 명시했다
- [ ] 프로젝트별 메모 파일에 주장·출처·검증 방법·결과를 기록했다
- [ ] 동일 예제를 두 프로젝트에서 실행하고 핵심 경로를 끝까지 추적했다
- [ ] 비교표의 "사실" 칸에 형용사가 없다
- [ ] 모든 코드 인용이 영구 링크이고 30줄 이하다
- [ ] 측정값에 환경과 반복 횟수를 붙였다
- [ ] 재현 저장소를 공개했고 `bench.sh` 한 번으로 숫자가 나온다
- [ ] 결론이 글의 첫 3줄 안에 있다
- [ ] 초안을 소리 내어 읽고 번역투(\~을 통해, \~에 대한, \~의 경우, \~되어지다)를 걷어냈으며 문체를 하나로 통일했다
- [ ] 라이선스·저작권 표시를 하단에 적었다
- [ ] 양쪽 커뮤니티 중 최소 한 곳에서 사실 검토를 받았다
- [ ] 최신 릴리스를 확인하고 달라진 점을 주석으로 달았다
