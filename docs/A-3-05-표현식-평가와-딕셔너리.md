## 1. 비교 관점

A-3-01 5-4에서 이렇게 남겼다 — **"무엇을 타입으로 승격시켰는가가 다르다. Trino 는 인코딩을, StarRocks 는 NULL·상수를."** 이 문서가 그 질문의 후속이다.

두 가지를 본다.

1. **`a + b * 2 > 100` 같은 식을 어떻게 실행 코드로 바꾸는가** — 바이트코드 생성인가, LLVM JIT 인가
2. **문자열 딕셔너리를 어떻게 활용하는가** — A-3-01의 `DictionaryBlock` 이 실제로 어디서 값을 하는가

**결론부터: 표현식 평가는 두 엔진 다 "실행 시점 코드 생성"에 도달했다 — Trino 는 항상, StarRocks 는 선택적으로. 딕셔너리는 접근하는 층이 전혀 다르고, StarRocks 의 전역 딕셔너리는 이 랩에서 발동하지 않았다.**

## 2. Trino 구현

### 2-1. 표현식은 바이트코드로 컴파일된다 — 항상

`works/trino/core/trino-main/src/main/java/io/trino/sql/gen/` 에 파일 **56개, 9,383줄**이 있다. 여기가 표현식을 Java 바이트코드로 바꾸는 곳이다.

`sql/gen/PageFunctionCompiler.java:123-131`:

```java
    public PageFunctionCompiler(FunctionManager functionManager, Metadata metadata, TypeManager typeManager, int expressionCacheSize)
    ...
        if (expressionCacheSize > 0) {
            projectionCache = buildNonEvictableCache(
                    CacheBuilder.newBuilder()
```

**컴파일 결과를 캐시한다.** 같은 모양의 표현식이 다시 나오면 재사용한다. 캐시 크기가 0이면 캐시 없이 매번 컴파일한다.

이것이 A-3-01 5-3, A-3-03 5-2에서 반복해 본 구도의 정점이다 — **Java 에서 타입별 전용 코드를 얻는 유일한 방법이 실행 시점 코드 생성**이고, Trino 는 표현식·조인 해시 전략·정렬 비교기를 전부 이 방식으로 만든다.

**켜고 끄는 설정이 없다.** 항상 컴파일한다.

### 2-2. 딕셔너리를 표현식 층에서 활용한다

`operator/project/` 에 딕셔너리 전용 클래스가 둘 있다.

```
DictionaryAwarePageProjection.java
DictionaryAwarePageFilter.java
```

핵심은 `DictionaryAwarePageProjection.java:123-140`:

```java
        if (lastInputDictionary == dictionary.get()) {
...
        boolean shouldProcessDictionary = dictionary.get().getPositionCount() <= blockPositionsCount || lastInputDictionary == null || lastDictionaryUsageCount >= lastInputDictionary.getPositionCount();
...
        lastInputDictionary = dictionary.get();
...
            return projection.project(session, SourcePage.create(lastInputDictionary), SelectedPositions.positionsRange(0, lastInputDictionary.getPositionCount()));
```

**요지는 셋이다.**

- **같은 사전이 다시 오면 이전 결과를 그대로 쓴다**(`lastInputDictionary == dictionary.get()`)
- **사전 크기가 실제 행 수보다 작을 때만** 사전을 처리한다(`shouldProcessDictionary`). 사전이 행보다 크면 이득이 없다
- 사전을 처리한다는 것은 **사전의 고유값들에만 표현식을 적용하고 인덱스는 그대로 두는 것**이다

`upper(l_returnflag)` 를 6만 행이 아니라 **고유값 3개에만** 적용한다는 뜻이다.

**이것이 A-3-01 2-2의 `sealed interface Block permits DictionaryBlock, …` 이 값을 하는 자리다.** 딕셔너리가 블록 타입이라서 표현식 층이 그것을 알아보고 최적화할 수 있다.

### 2-3. 사전은 파일에서 온다

Trino 의 `DictionaryBlock` 은 **Parquet/ORC 파일이 이미 딕셔너리 인코딩으로 저장한 컬럼**을 읽을 때 자연스럽게 만들어진다. 엔진이 별도로 사전을 수집하거나 관리하지 않는다.

즉 **적용 범위가 "파일이 딕셔너리 인코딩된 경우"로 한정되고, 그 대신 어떤 커넥터든 동작한다.**

## 3. StarRocks 구현

### 3-1. 표현식은 벡터화된 C++ 이고, JIT 은 선택이다

기본 경로는 `be/src/exprs/` 의 **미리 컴파일된 벡터화 함수들**이다. A-3-01 3-6에서 본 대로 이 디렉토리의 8개 파일이 SIMD 인트린식을 직접 쓴다.

그 위에 LLVM JIT 이 얹혀 있다 — `be/src/exprs/jit/`:

```
jit_engine.{h,cpp}   ir_helper.{h,cpp}   jit_expr.{h,cpp}
```

**켜고 끄는 설정이 있다** — `qe/SessionVariable.java:2881-2882`:

```java
    @VarAttr(name = JIT_LEVEL)
    private int jitLevel = 1;
```

**단계값이다.** 기본 1 은 "일부만" 정도로 읽히고, 소스를 더 봐야 각 단계의 의미가 확정된다 — **이 문서에서는 확인하지 않았다.**

**대비가 분명하다** — Trino 는 코드 생성이 유일한 경로이고 끌 수 없다. StarRocks 는 미리 컴파일된 함수가 기본이고 JIT 은 그 위의 선택적 가속이다. **C++ 은 미리 컴파일된 코드가 이미 충분히 빠르기 때문에 JIT 이 필수가 아니다.**

### 3-2. 저카디널리티 전역 딕셔너리 — 옵티마이저가 개입한다

Trino 가 표현식 층에서 딕셔너리를 다루는 것과 달리, **StarRocks 는 실행 계획 수립 단계에서 딕셔너리를 도입한다.**

FE 쪽에 전용 패키지가 있다 — `fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/tree/lowcardinality/`:

```
LowCardinalityRewriteRule.java
DecodeCollector.java   DecodeContext.java   DecodeInfo.java   DecodeRewriter.java
```

BE 쪽에는 전용 연산자가 있다 — `be/src/exec/dict_decode_node.{h,cpp}`.

**동작 요지**: 문자열 컬럼의 고유값이 적으면 **문자열 대신 정수 코드로 조인·집계·정렬을 수행하고, 마지막에 한 번만 문자열로 되돌린다.** 그 되돌리는 지점이 `DictDecodeNode` 다.

**Trino 의 방식과 결정적으로 다르다.**

| | Trino | StarRocks |
|---|---|---|
| 개입 층 | **표현식 평가** (실행 중) | **실행 계획 수립** (계획 시점) |
| 사전의 출처 | 파일이 이미 갖고 있는 것 | **엔진이 수집·관리하는 전역 사전** |
| 적용 범위 | 표현식 적용 대상 | **조인·집계·정렬 전 구간** |
| 플랜에 드러나는가 | 아니오 | 예 (`DictDecodeNode`) |

### 3-3. 설정과 임계값

`qe/SessionVariable.java:1805-1814`:

```java
    private boolean enableLowCardinalityOptimize = true;         // :1805
    private boolean enableLowCardinalityOptimizeForJoin = true;  // :1808
    private boolean useLowCardinalityOptimizeV2 = true;          // :1811
    private boolean useLowCardinalityOptimizeOnLake = false;     // :1814
```

**마지막 값이 이 랩에서 결정적이다 — `low_cardinality_optimize_on_lake` 가 기본 `false`.** 즉 **데이터레이크(Iceberg 등) 테이블에는 기본적으로 적용되지 않는다.**

고유값 임계는 FE Config 에 있다 — `common/Config.java:2414`:

```java

```

**고유값 255개 이하**여야 대상이 된다. 그리고 사전 수집 대상 컬럼 수 상한이 `statistic_dict_columns = 100000`(`:2396`)이다.

**사전은 통계 수집 계층이 관리한다** — A-2-07에서 본 `_statistics_` 체계의 일부다. `sql/optimizer/statistics/` 에 `CacheDictManager`, `IDictManager`, `ColumnDict` 가 있는 것이 그 근거다.

## 4. 실측

### 4-1. StarRocks 의 전역 딕셔너리는 이 랩에서 발동하지 않는다

```sql
SELECT l_returnflag, count(*) FROM iceberg.bench.lineitem GROUP BY l_returnflag;
```

`l_returnflag` 는 고유값 **3개**로 저카디널리티 최적화의 교과서적 대상이다. 그런데:

| 설정 | 플랜에 `DictDecodeNode` 가 있는가 |
|---|---|
| 기본값 | **없음** |
| `SET low_cardinality_optimize_on_lake = true` | **여전히 없음** |

**두 겹의 이유가 있다.**

1. 3-3의 `useLowCardinalityOptimizeOnLake = false` — 데이터레이크 테이블은 기본 대상이 아니다
2. 켜도 발동하지 않은 것은 **전역 사전이 수집돼 있지 않기 때문**으로 보인다. 사전 수집은 자체 스토리지(OLAP) 테이블 경로에 붙어 있고, 이 랩의 테이블은 전부 Iceberg 외부 테이블이다

**따라서 이 기능은 "StarRocks 자체 저장소에서만 확인할 수 있다."** 두 번째 이유는 추정이며 **확정하지 않았다.**

### 4-2. Trino 의 딕셔너리 처리도 관측되지 않는다

Trino 의 `DictionaryAwarePageProjection` 은 **플랜에도 프로파일에도 드러나지 않는다.** `EXPLAIN ANALYZE` 에 관련 지표가 없다.

시드 테이블의 Parquet 파일이 `l_returnflag` 를 딕셔너리 인코딩으로 저장했는지조차 이 랩에서 확인하지 못했다.

### 4-3. 표현식 컴파일도 관측되지 않는다

Trino 의 바이트코드 컴파일과 StarRocks 의 JIT 모두 **첫 실행 지연으로만 간접 관찰이 가능한데**, 이 랩의 쿼리는 전부 수십 ms 라 컴파일 비용과 실행 비용을 분리할 수 없다.

**이 문서는 코드 비교까지만 쓴다.** 성능 결론을 내지 않는다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 표현식 실행 코드 | **바이트코드 생성**(항상, 56파일 9,383줄) | 미리 컴파일된 벡터화 함수 + **LLVM JIT(선택)** |
| 끌 수 있는가 | 없음 | `jit_level` 단계값(기본 1) |
| 컴파일 결과 캐시 | 있음(`PageFunctionCompiler`) | JIT 쪽 확인하지 않음 |
| 딕셔너리 개입 층 | **표현식 평가**(실행 중) | **실행 계획 수립**(계획 시점) |
| 사전의 출처 | **파일이 갖고 있는 것** | **엔진이 수집한 전역 사전** |
| 적용 범위 | 표현식 대상 컬럼 | **조인·집계·정렬 전 구간** |
| 플랜 가시성 | 없음 | `DictDecodeNode` |
| 고유값 임계 | 사전 크기 < 행 수(동적) | **255개**(`low_cardinality_threshold`) |
| 데이터레이크 테이블 | 커넥터 무관하게 동작 | **기본 미적용**(`..._on_lake = false`) |

### 5-2. 왜 개입 층이 다른가

**Trino 는 사전을 만들 수 없다.** 데이터는 남의 저장소에 있고, 어떤 컬럼이 저카디널리티인지 알려면 통계가 필요한데 그 통계는 커넥터가 준다(A-2-07). 그래서 **파일이 이미 딕셔너리 인코딩해 준 경우에만, 그것도 실행 중에 알아채서** 활용한다.

**대신 어떤 커넥터든 동작한다.** 사전을 관리하지 않으므로 관리 비용도 없다.

**StarRocks 는 자체 저장소의 사전을 갖고 있다.** 어떤 컬럼이 255개 이하인지 통계로 알고, 사전을 수집·캐시한다. 그래서 **계획 시점에 "이 컬럼은 정수로 다루자"고 결정**할 수 있고, 그 결정이 조인·집계·정렬 전 구간에 걸린다.

**적용 범위가 훨씬 넓은 대신 자기 저장소에 묶인다.** 4-1이 그 대가다 — 외부 테이블에서는 기본으로 꺼져 있다.

**A-2-06(MV), A-2-07(통계)에서 본 것과 같은 축이다 — 자기 것으로 가져오면 더 할 수 있고, 남의 것을 존중하면 더 넓게 동작한다.**

### 5-3. JIT 이 필수인가 선택인가

**Java 에서 코드 생성은 선택이 아니다.** 인터프리터 방식 표현식 평가는 가상 호출이 매 행마다 발생해 실용적이지 않다. Trino 가 9,383줄을 들여 바이트코드 생성기를 만든 것은 그 때문이다.

**C++ 에서는 선택이다.** 미리 컴파일된 벡터화 함수가 이미 SIMD 를 쓰고(A-3-01 3-6) 가상 호출도 컬럼 단위로 한 번만 일어난다. JIT 이 더 벌어주는 것은 **여러 연산을 한 루프로 융합(fusion)하는 부분**이고, 그것이 항상 이득은 아니라서 `jit_level` 이라는 단계값을 둔다.

**따라서 "StarRocks 는 JIT 을 쓰니 더 빠르다"고 읽으면 안 된다.** JIT 이 기본 1단계에 머무는 것 자체가 "무조건 이득이 아니다"의 방증이다.

## 6. 결론

**표현식 평가는 같은 목적지에 다른 경로로 도달했다. 딕셔너리는 개입 층이 달라 적용 범위와 제약이 갈린다.**

- **표현식** — Trino 는 바이트코드 생성이 유일한 경로이고 끌 수 없다. StarRocks 는 미리 컴파일된 벡터화 함수가 기본이고 LLVM JIT 은 단계값으로 조절하는 선택적 가속이다. **언어 제약의 귀결이지 성능 우열이 아니다**
- **딕셔너리** — Trino 는 **실행 중 표현식 층**에서, StarRocks 는 **계획 시점**에 개입한다. 후자가 적용 범위가 훨씬 넓지만(조인·집계·정렬 전 구간) **자체 저장소에 묶인다**
- **이 랩에서는 StarRocks 의 전역 딕셔너리가 발동하지 않았다.** `low_cardinality_optimize_on_lake` 가 기본 꺼짐이고, 켜도 사전이 없었다. **`plan/01` 이 "Trino 대응물 부재"라고 적은 이 기능은, 데이터레이크 테이블에서는 StarRocks 자신도 기본으로 쓰지 않는다**

### 아직 답하지 않은 것

- **전역 딕셔너리의 실제 동작과 이득** — StarRocks 자체 저장소(OLAP) 테이블이 필요하다. `seed.sh --with-native` 로 만들 수 있으나 별도 설계가 필요하다(**C-1-02** 와 함께)
- **4-1의 두 번째 원인** — "사전이 수집되지 않아서"는 추정이다. 확정하지 않았다
- **`jit_level` 각 단계의 의미** — 소스를 더 봐야 한다
- **컴파일 비용** — Trino 의 첫 실행 지연, StarRocks 의 JIT 컴파일 지연을 재지 않았다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **Trino 딕셔너리 처리의 실제 발동 여부** — 플랜·프로파일 어디에도 드러나지 않아 확인하지 못했다
- **표현식 평가 성능 자체** — 두 방식의 처리량 차이는 이 랩에서 측정 불가
