## 1. 비교 관점

`A-2-04` 는 **옵티마이저가 커넥터에게 무엇을 넘기는가**를 봤다. 결론은 "Trino 는 협상하고 StarRocks 는 통보한다"였다.

이 문서는 그 **다음 두 칸**을 본다.

1. **넘어간 술어로 커넥터가 실제로 얼마나 걷어내는가** — 계획의 모양이 아니라 읽은 파일·행의 수
2. **커넥터마다 능력이 다른가** — Trino 의 협상 구조는 커넥터별 편차를 허용한다. 그 편차가 실제로 얼마나 큰가

결론부터: **맨 컬럼 술어에서는 두 엔진의 프루닝 결과가 완전히 같다.** 갈리는 곳은 술어가 함수로 감싸였을 때이고, 그 차이는 **커넥터의 능력이 아니라 옵티마이저 재작성 규칙의 함수 커버리지**에서 나온다. 그리고 **어느 쪽도 상대의 상위집합이 아니다.**

한편 **능력의 편차는 Trino 쪽이 압도적으로 크다.** 같은 Trino 안에서도 커넥터에 따라 조인 푸시다운이 되고 안 되고가 갈린다.

## 2. Trino 구현

### 2-1. 협상 메서드가 11개, 전부 선택 구현이다

`ConnectorMetadata` 에서 커넥터가 "이건 내가 받겠다"고 답할 수 있는 지점이다.

| 메서드 | 무엇을 넘기는가 |
|---|---|
| `applyFilter` | 술어 |
| `applyProjection` | 투영·표현식 |
| `applyLimit` | LIMIT |
| `applyTopN` | ORDER BY + LIMIT |
| `applyAggregation` | 집계 |
| `applyJoin` | 조인 |
| `applySample` | 샘플링 |
| `applyPartitioning` | 파티셔닝 |
| `applyTableFunction` | 테이블 함수 |
| `applyDelete` / `applyUpdate` | DML |
| `applyTableScanRedirect` | 스캔 대상 바꿔치기 |

전부 `default` 구현이 `Optional.empty()` 다 — **구현하지 않으면 "못 받는다"가 되고 엔진이 알아서 처리한다.**

핵심은 반환 타입이다.

```java
private final T handle;
private final TupleDomain<ColumnHandle> remainingFilter;
private final Optional<ConnectorExpression> remainingExpression;
private final boolean precalculateStatistics;
```
— `core/trino-spi/.../connector/ConstraintApplicationResult.java:26-29`

`remainingFilter` 가 이 구조의 전부다. **커넥터가 "이만큼은 내가 처리했고 나머지는 네가 해라"라고 답한다.** 엔진은 그만큼을 계획에서 지운다.

SPI 주석은 이 협상이 반복 호출됨을 전제한다.

```java
* Connectors can indicate whether they don't support predicate pushdown or that the action had no effect
* by returning {@link Optional#empty()}. Connectors should expect this method to be called multiple times
* during the optimization of a given query.
```
— `ConnectorMetadata.java:1414-1416`

### 2-2. 커넥터마다 구현 범위가 다르다

플러그인 트리에서 각 메서드를 실제로 구현한 커넥터를 셌다.

| 메서드 | 구현 커넥터 |
|---|---|
| `applyFilter` | **18** — jdbc(공용), elasticsearch, opensearch, tpch, hudi, bigquery, lakehouse, delta-lake, iceberg, kafka, redis, prometheus, jmx, pinot, cassandra, thrift, hive, mongodb |
| `applyProjection` | 10 |
| `applyLimit` | 10 |
| `applyAggregation` | **3** — jdbc(공용), lakehouse, pinot |
| `applyTopN` | **2** — jdbc(공용), lakehouse |
| `applyJoin` | **1** — jdbc(공용) |
| `applySample` | 3 |
| `applyTableScanRedirect` | 2 |

**"1개"라는 숫자를 그대로 읽으면 안 된다.** `applyJoin` 의 유일한 구현은 `trino-base-jdbc` 의 `DefaultJdbcMetadata` 인데, **JDBC 계열 커넥터 15개가 이것을 상속한다**(clickhouse, mysql, postgresql, oracle, sqlserver, snowflake, redshift, mariadb, singlestore, duckdb, druid, exasol, ignite 등). 즉 조인 푸시다운은 "커넥터 1개"가 아니라 **"관계형 DB 커넥터 전부"** 다.

반대로 **Iceberg·Hive·Delta 같은 레이크 커넥터는 조인·집계·TopN 푸시다운을 구현하지 않는다.** 밀어봐야 밀 곳이 없기 때문이다 — 파일 뒤에 SQL 엔진이 없다.

### 2-3. JDBC 계열은 방언마다 다시 갈린다

`JdbcClient` 인터페이스가 방언별 능력 선언 지점을 따로 둔다.

```java
default boolean supportsAggregationPushdown(ConnectorSession session, JdbcTableHandle table, List<AggregateFunction> aggregates, Map<String, ColumnHandle> assignments, List<List<ColumnHandle>> groupingSets)
```
— `plugin/trino-base-jdbc/.../JdbcClient.java:93`

```java
boolean supportsTopN(ConnectorSession session, JdbcTableHandle handle, List<JdbcSortItem> sortOrder);

/**
 * Reports whether result cardinality and ordering is guaranteed when {@link #supportsTopN(ConnectorSession, JdbcTableHandle, List)} returns true.
 */
boolean isTopNGuaranteed(ConnectorSession session);
```
— `JdbcClient.java:165-170`

`supportsTopN` 을 오버라이드한 방언 클라이언트가 **11개**다(mysql, postgresql, sqlserver, oracle 계열, clickhouse, snowflake, redshift, mariadb, singlestore, ignite, exasol). `isTopNGuaranteed` 가 따로 있는 이유는 **정렬 규칙이 DB마다 달라(대소문자·콜레이션) 밀어도 순서를 보장 못 하는 경우가 있기 때문**이다. 이 정도로 세밀하게 나뉜다.

**요약하면 Trino 의 푸시다운 능력은 3층으로 갈린다** — 커넥터가 메서드를 구현했는가 → JDBC 라면 방언이 지원하는가 → 그 특정 함수·정렬을 변환할 수 있는가.

## 3. StarRocks 구현

### 3-1. 커넥터는 "받겠다"고 답하지 않는다

`ConnectorMetadata` 에 `apply*` 에 해당하는 협상 메서드가 없다. 대신 술어가 **인자로 들어간다.**

```java
default Statistics getTableStatistics(OptimizerContext session,
                                      Table table,
                                      Map<ColumnRefOperator, Column> columns,
                                      List<PartitionKey> partitionKeys,
                                      ScalarOperator predicate,
                                      long limit,
                                      TableVersionRange tableVersionRange) {
    return Statistics.builder().build();
}
```
— `fe/fe-core/.../connector/ConnectorMetadata.java:206-214`

바로 위 주석이 용도를 밝힌다 — `predicate` 는 *"used to filter metadata for iceberg, etc"*, `limit` 은 *"scan limit if needed"*. **메타데이터를 걸러 통계를 좁히는 데 쓰라는 것이지, 술어를 가져가라는 게 아니다.**

`getRemoteFiles` 의 주석도 같다.

```java
* 1. Get the remote files information from hdfs or s3 according to table or partition.
* 2. Get file scan tasks for iceberg/deltalake metadata by query predicate.
```
— `ConnectorMetadata.java:155-157`

**커넥터는 술어를 "프루닝에만" 쓴다.** 계획에서 술어가 사라지는 일은 없다 — `A-2-04` 3-4에서 확인한 그대로다. 반환 값에 `remainingFilter` 에 해당하는 것이 없으니 구조적으로 불가능하다.

`ConnectorMetadata` 의 `default` 메서드는 50개다(351줄). Trino 의 `ConnectorMetadata` 는 156개(1,866줄) — **표면적이 3.7배 차이 난다.** 다만 이건 커넥터가 할 일이 적다는 뜻이 아니라, **엔진이 대신 하기 때문에 물어볼 것이 적다는 뜻**이다.

### 3-2. 소스별 술어 변환기는 있다

"엔진이 다 한다"고 해서 소스별 코드가 없는 것은 아니다. 술어를 각 포맷의 표현식으로 옮기는 변환기가 커넥터마다 있다.

| 커넥터 | 변환기 |
|---|---|
| Iceberg | `iceberg/ScalarOperatorToIcebergExpr.java` (494줄) |
| Delta Lake | `delta/ScalarOperationToDeltaLakeExpr.java` |
| Paimon | `paimon/PaimonPredicateConverter.java` |
| Kudu | `kudu/KuduPredicateConverter.java` |
| Elasticsearch | `elasticsearch/QueryConverter.java` + `QueryBuilders.java` |
| Hive | `hive/HiveMetadata.java` · `HiveConnectorScanRangeSource.java` 안 |
| JDBC / ODPS | 옵티마이저의 `PushDownPredicateToExternalTableScanRule` (공용 화이트리스트) |

**`ConnectorType` 열거형은 10종**이다 — `ES HIVE ICEBERG JDBC HUDI DELTALAKE PAIMON ODPS KUDU UNIFIED`(`A-5-01` 3-2).

다만 `A-2-04` 3-5 에서 본 대로 **JDBC 계열은 대상 DB 종류와 무관하게 같은 화이트리스트**를 쓴다. Trino 가 방언별로 `supportsTopN` 을 따로 두는 것과 정확히 대비된다.

### 3-3. 변환기가 함수를 받지 않는다

Iceberg 변환기의 컬럼명 추출기다.

```java
private static class ExtractColumnName extends ScalarOperatorVisitor<String, Void> {

    @Override
    public String visit(ScalarOperator scalarOperator, Void context) {
        return null;
    }
```
— `ScalarOperatorToIcebergExpr.java:465-470`

기본 방문 메서드가 `null` 이고, 오버라이드된 것은 **컬럼 참조 / CAST / 서브필드 셋뿐**이다. 함수 호출(`CallOperator`)은 여기서 떨어진다.

떨어지면 술어가 통째로 버려진다.

```java
public Expression visitBinaryPredicate(BinaryPredicateOperator operator, IcebergContext context) {
    String columnName = getColumnName(operator.getChild(0));
    if (columnName == null) {
        return null;
    }
```
— `ScalarOperatorToIcebergExpr.java:189-193`

**즉 `year(o_orderdate) = 1995` 는 Iceberg 매니페스트까지 도달하지 못한다.** 4절에서 그 결과를 잰다.

### 3-4. 대신 옵티마이저가 함수를 벗긴다

그러나 이것은 구조적 한계가 아니다. 함수를 벗겨 맨 컬럼 술어로 바꾸는 규칙이 따로 있다.

```java
 * substr(cast(t as varchar), 1, 10) >= '2023-03-27' -> `t` >= '2023-03-27'
 * substring(cast(t as varchar), 1, 10) >= '2023-03-27' -> `t` >= '2023-03-27'
 * replace(substring(cast(t as varchar), 1, 10), "-", "") >= '20230327' -> `t` >= '20230327'
 *
 * if it is datetime
 * date_format(t, '%Y-%m-%d') >=/< '2023-03-27' -> t >=/< '2023-03-27'
 * date_format(t, '%Y-%m-%d') >/<= '2023-03-27' -> t >=/< days_add('2023-03-27', 1)
 */
public class SimplifiedDateColumnPredicateRule extends BottomUpScalarOperatorRewriteRule {
```
— `sql/optimizer/rewrite/scalar/SimplifiedDateColumnPredicateRule.java:44-52`

**다루는 함수는 `date_format` / `substr` / `substring` / `replace` 다. `year` 와 `date_trunc` 는 없다.**

Trino 에도 정확히 같은 성격의 규칙이 있다 — `UnwrapYearInComparison.java`, `UnwrapDateTruncInComparison.java`, `UnwrapCastInComparison.java`. **다루는 함수 목록만 다르다.**

## 4. 실측 — 읽은 파일과 행

전문은 `docs/evidence/A-5/20260904-connector-pruning-probes.md`.

Trino 로 파티션 Iceberg 테이블(`orders` 15,000행 → 80개월 파티션 = 80파일)을 만들고 양쪽에서 읽었다.

### 4-1. 측정 단위를 맞추는 것이 먼저였다

두 함정을 먼저 넘어야 했다.

- **`count(*)` 를 쓰면 안 된다.** StarRocks 가 메타데이터만 읽고 끝낸다(`A-2-04` 3-7). `sum(o_totalprice)` 로 통일했다
- **StarRocks 의 `OutputRows` 는 필터 통과 후 값이다.** Trino 의 `Input rows`(필터 이전)와 짝이 아니다. 짝은 `RawRowsRead` 다. 초안에서 이걸 혼동해 "15,000 대 255" 라는 잘못된 표를 만들 뻔했다

### 4-2. 결과

| 술어 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 없음 (기준선) | 15,000행 / 80파일 | 15,000행 / 80파일 |
| `o_orderdate >= '1995-01-01' AND < '1995-02-01'` | **165행 / 1파일** | **165행 / 1파일** |
| `year(o_orderdate) = 1995` | **2,204행 / 12파일** | 15,000행 / 80파일 ✗ |
| `date_trunc('month', o_orderdate) = '1995-01-01'` | **165행 / 1파일** | 15,000행 / 80파일 ✗ |
| 문자열 포맷 함수 * | 15,000행 / 80파일 ✗ | **165행 / 1파일** |
| `o_orderkey < 1000` (비파티션) | 14,269행 / **75파일** | 14,269행 / **80파일** |

\* Trino `format_datetime(CAST(o_orderdate AS timestamp), 'yyyy-MM-dd')` / StarRocks `date_format(o_orderdate, '%Y-%m-%d')`.

**결과값은 모든 행에서 일치했다.** 갈린 것은 읽은 양뿐이다.

### 4-3. 맨 컬럼이면 완전히 같다

두 번째 행이 이 문서의 기준선이다. **술어가 맨 컬럼에 걸리면 커넥터 단계 프루닝은 완전히 동등하다** — 165행 / 1파일. Iceberg 매니페스트를 읽고 파티션을 걸러내는 능력 자체에는 차이가 없다.

### 4-4. 함수가 끼면 갈리고, 방향이 서로 반대다

- StarRocks 는 `year` / `date_trunc` 에서 프루닝하지 못한다 — **15,000행 전부**
- Trino 는 문자열 포맷 함수에서 프루닝하지 못한다 — **15,000행 전부**

**어느 쪽도 상대의 상위집합이 아니다.** 그리고 StarRocks 가 `date_format` 에서는 **165행 / 1파일**로 맨 컬럼과 완전히 같은 결과를 낸다는 사실이 원인을 확정한다 — 커넥터가 못 하는 게 아니라 **옵티마이저가 함수를 벗겨주지 않으면 못 하는 것**이고, 벗겨주는 함수 목록이 다르다.

### 4-5. 비파티션 컬럼 — 제거 시점만 다르다

`o_orderkey < 1000` 에서 두 엔진 모두 **14,269행**을 읽었다. 15,000 중 5%만 줄었는데, `o_orderkey` 가 파일 안에서 정렬돼 있지 않아 min/max 통계가 거의 무력하기 때문이다.

파일 수만 다르다 — Trino **75**, StarRocks **80**. Trino 는 매니페스트 통계로 5개를 계획 시점에 뺐고, StarRocks 는 80개를 전부 스케줄한 뒤 리더 안에서 걸렀다. **읽은 행이 같으므로 결과는 동등하다.** 파일이 수만 개인 환경에서는 스케줄링 비용 차이가 생길 수 있으나 여기서 측정하지 않았다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 커넥터가 답하는 방식 | `apply*` 11종, `remainingFilter` 로 협상 | 답하지 않음 — 술어를 인자로 받아 프루닝에만 사용 |
| `ConnectorMetadata` 표면 | 156개 default 메서드 / 1,866줄 | 50개 / 351줄 |
| 커넥터 간 능력 편차 | **크다** — `applyFilter` 18개 vs `applyJoin` 1개(JDBC 공용) | **없다** — 엔진이 일괄 처리 |
| 방언별 편차 | `supportsTopN` 등 방언 클라이언트 11개가 재정의 | 없음 — JDBC 는 공용 화이트리스트 |
| 소스별 술어 변환기 | 커넥터마다 | Iceberg / Delta / Paimon / Kudu / ES / Hive |
| 함수 술어 벗기기 | `Unwrap*InComparison` 3종 | `SimplifiedDateColumnPredicateRule` 1종 |
| 파티션 프루닝 결과(맨 컬럼) | **동등** | **동등** |

### 5-2. 편차의 크기가 곧 설계 의도다

Trino 의 능력이 커넥터마다 다른 것은 결함이 아니라 **필연**이다. 뒤에 있는 것이 파일일 수도 있고 PostgreSQL 일 수도 있으니, "조인을 밀 수 있는가"의 답이 같을 수 없다. 그래서 **물어보는 구조**(`applyJoin` → `Optional.empty()`)를 만들었다.

StarRocks 는 뒤에 오는 소스가 10종으로 고정돼 있고 대부분 레이크 포맷이다. **물어볼 필요가 없으니 묻지 않는 구조**를 택했고, 그 대가로 JDBC 처럼 "밀면 이득인" 소스에서도 공용 화이트리스트로만 처리한다.

`A-5-01` 의 결론(SPI 뒤인가 코어 안인가)이 여기서 그대로 반복된다.

### 5-3. 그러나 이번 실측의 차이는 커넥터 탓이 아니다

**주의해서 읽어야 할 지점이다.** 4-4 의 차이를 "Trino 커넥터가 더 똑똑하다"로 읽으면 틀린다.

- 커넥터가 받은 것이 **맨 컬럼 술어면 양쪽 다 완벽하게 프루닝한다**(4-3)
- 함수를 벗기는 일은 **옵티마이저**가 한다 — Trino `UnwrapYearInComparison`, StarRocks `SimplifiedDateColumnPredicateRule`
- 두 규칙의 **함수 커버리지가 다를 뿐**이고, 어느 쪽도 상대를 포함하지 않는다

즉 이 차이는 `A-5`(커넥터)가 아니라 `A-2`(옵티마이저) 쪽 성격의 차이인데, **드러나는 곳이 커넥터 프루닝이라 여기서 잡혔다.** 실측 없이 코드만 봤다면 `ScalarOperatorToIcebergExpr` 의 `return null` 만 보고 "StarRocks 커넥터가 함수 술어를 못 민다"고 쓸 뻔했다. `date_format` 측정이 그것을 막았다.

### 5-4. 운영자 관점

두 엔진 모두 **"쓰는 함수가 목록에 있는가"** 로 결과가 갈린다. 목록 밖의 함수를 쓰면 조용히 전체 스캔이 되고, **쿼리는 성공하며 결과도 맞다.** 느려질 뿐이다.

확인 방법은 양쪽이 다르다.

| | 확인 수단 |
|---|---|
| Trino | `EXPLAIN ANALYZE` 의 `Splits:` 와 `Input: N rows` |
| StarRocks | `ANALYZE PROFILE FROM '<id>', 0` 의 `ScanRanges` 와 `RawRowsRead` |

StarRocks 는 `EXPLAIN` 만으로는 알 수 없다 — `PREDICATES` 에 술어가 찍혀 있어도 그것이 매니페스트까지 갔다는 뜻이 아니기 때문이다. `enable_profile=true` 를 켜고 프로파일을 봐야 한다. **관측 비용이 한 단계 더 든다**(`B-6-01` 과 같은 뿌리).

## 6. 결론

**커넥터 프루닝 능력 자체는 대등하다. 편차의 구조가 다르다.**

- **맨 컬럼 술어**: 완전히 동등하다. 파티션 프루닝 165행/1파일로 일치
- **함수 술어**: 서로 다른 함수 집합에서만 동작하고 **어느 쪽도 상대를 포함하지 않는다.** 원인은 커넥터가 아니라 옵티마이저의 재작성 규칙 커버리지
- **커넥터 간 편차**: Trino 는 크고(조인 푸시다운은 JDBC 계열만, 방언별로 또 갈림) StarRocks 는 없다. 이는 붙는 소스의 다양성 차이에서 나온 필연이다
- **비파티션 컬럼**: 읽는 양은 같고 파일 제거 시점만 다르다(계획 시점 vs 리더 안)

**실무 결론**

1. **어느 엔진이 낫다고 말할 수 없다.** 확인할 것은 "우리가 쓰는 날짜 함수가 그 엔진의 벗기기 목록에 있는가"이고, 없으면 **맨 컬럼 범위 술어로 고쳐 쓰면 양쪽 다 해결된다**
2. **관계형 DB 를 조인해 써야 한다면 Trino 다.** `applyJoin`·`applyAggregation`·`applyTopN` 이 JDBC 계열 15개 커넥터에 다 있고 방언별로 세밀하게 나뉜다. StarRocks 는 공용 화이트리스트뿐이다
3. **프루닝이 실제로 걸렸는지 반드시 확인하라.** 안 걸려도 쿼리는 성공하고 결과도 맞다. StarRocks 는 `EXPLAIN` 으로 부족하고 프로파일이 필요하다

### 아직 답하지 않은 것

- **실행 시간** — SF 0.01 이라 재지 않았다. "80파일 vs 1파일"이 실제로 몇 배 차이인지는 `perf` 프로파일이 필요하다(`plan/02` 6-2절)
- **다른 파티션 변환** — `month` 만 봤다. `bucket`, `truncate`, `day`, `year` 변환은 확인하지 않았다
- **Iceberg 외 커넥터** — Hive / Delta / Paimon / JDBC 는 코드로만 봤다. 랩에 해당 카탈로그가 없다
- **ORC** — Parquet 만 봤다
- **파일 수가 많은 환경** — 4-5 의 "계획 시점 vs 리더 안" 차이는 파일 80개에서 무의미하다. 수만 개일 때 유의미해지는지 확인하지 않았다
- **집계·조인 푸시다운의 실측** — 2-2 의 표는 코드 조사다. JDBC 카탈로그가 없어 실제로 원격 SQL 이 어떻게 나가는지 보지 못했다
