> 재등장 항목: A-2-04 5-2(푸시다운 판단 주체), A-2-06 5-2(MV 소유권), A-2-07 5-2(통계 소유권)의 뿌리

## 1. 비교 관점

앞의 여러 문서에서 같은 문장이 반복해 나왔다 — **"Trino 는 커넥터에게 물어보고, StarRocks 는 엔진이 직접 판단한다."** 푸시다운(A-2-04), MV(A-2-06), 통계(A-2-07)가 전부 그랬다.

이 문서는 그 구도의 **뿌리**를 본다. 새 데이터 소스를 붙이려면 무엇을 해야 하는가.

세 가지를 본다.

1. **확장점이 어디에 있는가** — 안정된 인터페이스 뒤인가, 엔진 코드 안인가
2. **몇 개의 언어·프로세스를 건드려야 하는가**
3. **결과적으로 붙어 있는 데이터 소스가 몇 개인가**

**결론부터: 이것이 두 엔진의 가장 큰 구조적 차이다. Trino 는 플러그인 61개가 엔진 코드를 한 줄도 건드리지 않고 붙어 있고, StarRocks 는 커넥터 10종이 FE(Java)와 BE(C++) 양쪽에 걸쳐 엔진 코드 안에 들어 있다.**

## 2. Trino 구현

### 2-1. 확장점이 별도 모듈로 분리돼 있다

`works/trino/core/trino-spi/` — 파일 **558개, 73,858줄**의 독립 모듈이다. 커넥터 개발자는 **이 모듈만 의존**하고 엔진 본체(`trino-main`)를 참조하지 않는다.

이것이 **버전 호환성의 근거**다. SPI 는 별도로 버전이 관리되고 호환성 정책이 적용된다.

### 2-2. 커넥터가 구현할 것은 인터페이스 몇 개다

`core/trino-spi/src/main/java/io/trino/spi/connector/Connector.java` (263줄)가 진입점이고, 실제 일은 넷으로 나뉜다.

| 인터페이스 | 줄 수 | 역할 |
|---|---|---|
| `ConnectorMetadata` | **1,866** | 테이블 목록, 스키마, 통계, 푸시다운 협상, 쓰기 |
| `ConnectorSplitManager` | **44** | 읽을 단위(split) 나누기 |
| `ConnectorPageSourceProvider` | **83** | split 하나를 읽어 `Page` 로 만들기 |
| `Connector` | 263 | 위 셋을 묶어 제공 |

**`ConnectorMetadata` 가 1,866줄로 크지만, 그 대부분이 `default` 구현이다.** A-2-04 2-4, A-2-06 2-1, A-2-07 2-1에서 본 대로 `applyFilter`·`createMaterializedView`·`getTableStatistics` 모두 "지원 안 함"을 돌려주는 기본 구현을 갖는다.

**즉 최소 구현은 아주 작고, 능력을 더 신고할수록 성능이 좋아진다.** 이 구조가 A-2-04의 "협상" 모델을 만든다.

### 2-3. 플러그인이 61개, 그중 커넥터가 28개

`works/trino/plugin/` 아래 `trino-*` 디렉토리가 **61개**다. 그중 `getConnectorFactories` 를 구현한 것(= 커넥터)이 **28개**다.

```
ai-functions  base-jdbc  bigquery  blackhole  cassandra  datasketches  delta-lake
elasticsearch  example-http  faker  google-sheets  hive  hudi  iceberg  jmx  kafka
lakehouse  loki  memory  mongodb  opensearch  pinot  prometheus  redis  redshift
thrift  tpcds  tpch
```

**`base-jdbc` 하나에 관계형 DB 커넥터 여러 개가 얹혀 있다.** 별도 플러그인으로 존재하는 것만 봐도 이만큼이다.

```
clickhouse  druid  duckdb  exasol  ignite  mariadb  mysql  oracle
postgresql  singlestore  snowflake  sqlserver
```

나머지 플러그인은 **커넥터가 아닌 확장점**이다 — 이벤트 리스너(`http-event-listener`, `kafka-event-listener`, `openlineage`), 접근 제어(`ranger`, `opa`), 인증(`password-authenticators`, `ldap-group-provider`), 리소스 그룹(`resource-group-managers`), 함수(`functions-python`, `geospatial`, `ml`, `ai-functions`), 교환(`exchange-filesystem`, `exchange-hdfs`, `spooling-filesystem`).

**"커넥터 SPI"가 아니라 "플러그인 SPI"라는 것이 여기서 드러난다** — C-2-01의 주제다.

## 3. StarRocks 구현

### 3-1. 커넥터가 엔진 코드 안에 있고, FE·BE 양쪽에 걸친다

**FE(Java)** — `fe/fe-core/src/main/java/com/starrocks/connector/` 아래 하위 패키지 **21개**:

```
config  delta  elasticsearch  exception  hadoop  hive  hudi  iceberg
informationschema  jdbc  kudu  metadata  metastore  odps  paimon  parser
partitiontraits  share  statistics  trino  unified
```

**BE(C++)** — `be/src/connector/` 아래:

```
es_connector  file_connector  hive_connector  iceberg_connector
jdbc_connector  lake_connector  mysql_connector  binlog_connector
```

**같은 데이터 소스가 두 프로세스, 두 언어에 나뉘어 구현돼 있다.**

### 3-2. 붙일 수 있는 소스가 열거형에 박혀 있다

`fe/fe-core/src/main/java/com/starrocks/connector/ConnectorType.java:36-45`:

```java
    ES("es", ElasticsearchConnector.class, EsConfig.class),
    HIVE("hive", HiveConnector.class, null),
    ICEBERG("iceberg", IcebergConnector.class, null),
    JDBC("jdbc", JDBCConnector.class, null),
    HUDI("hudi", HudiConnector.class, null),
    DELTALAKE("deltalake", DeltaLakeConnector.class, null),
    PAIMON("paimon", PaimonConnector.class, null),
    ODPS("odps", OdpsConnector.class, null),
    KUDU("kudu", KuduConnector.class, null),
    UNIFIED("unified", UnifiedConnector.class, null);
```

**10종이고, 새로 붙이려면 이 열거형에 항목을 추가해야 한다.** 플러그인을 떨어뜨려 넣는 경로가 없다.

`JDBC` 하나가 관계형 DB 여러 종을 포괄하므로 실제 지원 소스는 이보다 많지만, **엔진 코드를 고치지 않고는 늘릴 수 없다**는 점이 핵심이다.

### 3-3. 스캔 노드 타입도 프로토콜에 박혀 있다

FE 와 BE 는 Thrift 로 실행 계획을 주고받는다. 그 정의에 **스캔 노드 종류가 열거돼 있다** — `gensrc/thrift/PlanNodes.thrift`:

```
OLAP_SCAN_NODE   MYSQL_SCAN_NODE   CSV_SCAN_NODE   SCHEMA_SCAN_NODE
META_SCAN_NODE   KUDU_SCAN_NODE    FILE_SCAN_NODE  ES_SCAN_NODE
ES_HTTP_SCAN_NODE  HDFS_SCAN_NODE  JDBC_SCAN_NODE  LAKE_SCAN_NODE
STREAM_SCAN_NODE   LAKE_META_SCAN_NODE  …
```

**즉 새 소스를 붙이려면 최소 네 곳을 건드려야 한다.**

1. FE 의 `ConnectorType` 열거형과 커넥터 구현(Java)
2. FE 의 논리·물리 스캔 오퍼레이터(A-2-04 3-4에서 본 `PushDownPredicateScanRule` 의 `SUPPORT` 집합 17종이 그 흔적이다)
3. **Thrift 프로토콜 정의**
4. BE 의 `DataSourceProvider` / `DataSource` 구현(C++)

### 3-4. BE 쪽 인터페이스

`be/src/connector/connector.h:126-137, 204-220`:

```cpp

    virtual DataSourcePtr create_data_source(const TScanRange& scan_range) = 0;
...
class Connector {
```

248줄짜리 헤더다. **Trino 의 `ConnectorPageSourceProvider`(83줄)에 대응하는 위치**이고, 크기도 비슷하다. **문제는 크기가 아니라 여기가 엔진 코드 안이라는 점이다.**

## 4. 실측

**이 축은 실측이 성립하지 않는다.** "커넥터를 하나 새로 만들어 본다"가 유일한 실측인데, 그것은 이 저장소의 범위를 넘는다.

간접 증거로 **양쪽에 붙어 있는 소스의 수**를 셌다.

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 별도 배포 단위 | 플러그인 **61개** | 없음(엔진에 내장) |
| 그중 커넥터 | **28개** (+ `base-jdbc` 위의 관계형 DB 12종) | **10종** (`ConnectorType` 열거형) |
| 확장점 모듈 | `trino-spi` **558파일 73,858줄** — 독립 모듈 | 없음 — 엔진 코드 |
| 건드려야 할 언어 | **Java 하나** | **Java + C++ + Thrift** |
| 건드려야 할 프로세스 | 없음(플러그인 로딩) | **FE + BE** |

랩에서 확인한 것은 하나다 — **양쪽 다 같은 Iceberg 카탈로그를 붙였고 같은 데이터를 읽었다**(전 문서의 실측이 그 증거다). **붙는 것 자체는 문제가 아니다. 새로 붙이는 비용이 다르다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino | StarRocks |
|---|---|---|
| 확장점 위치 | **별도 모듈**(`trino-spi`) | 엔진 코드 안 |
| 배포 단위 | 플러그인 JAR — 떨어뜨려 넣으면 됨 | 없음 — 엔진 빌드에 포함 |
| 건드릴 언어 | Java | **Java + C++ + Thrift** |
| 소스 목록 | 열려 있음 | **열거형에 고정** |
| 최소 구현 | 인터페이스 3~4개, 대부분 `default` 있음 | FE 오퍼레이터 + BE DataSource + Thrift |
| 성능 최적화 신고 | **선택적**(`applyFilter` 등을 구현할수록 좋아짐) | 엔진이 판단 — 신고 개념 없음 |
| 제3자 확장 | **가능** | 사실상 불가(포크 필요) |

### 5-2. 이 차이가 앞 문서들을 설명한다

지금까지 관찰한 것들이 전부 여기서 따라 나온다.

| 관찰 | 어디서 | 뿌리 |
|---|---|---|
| 푸시다운 가능 여부를 커넥터가 답한다 | A-2-04 2-4 | **엔진이 소스를 모르기 때문** |
| 프루닝에 쓸 술어 형태가 엔진에 하드코딩돼 있다 | A-2-04 3-2 | **엔진이 소스를 알기 때문** |
| MV 를 커넥터가 소유한다 | A-2-06 2-1 | 같음 |
| 통계를 커넥터가 준다 | A-2-07 2-1 | 같음 |
| 통계를 테이블 포맷에 남긴다 | A-2-07 2-3 | **엔진이 통계를 보관할 자리가 없다** |
| 저카디널리티 딕셔너리가 데이터레이크에 기본 미적용 | A-3-05 3-3 | **엔진이 사전을 관리하려면 자기 저장소가 필요** |

**"Trino 는 남의 데이터를 읽는 엔진이고 StarRocks 는 자기 데이터를 읽는 엔진"이라는 한 문장이 이 표 전체를 만든다.**

### 5-3. 각자가 치르는 대가

**Trino 의 대가**

- 커넥터가 능력을 신고하지 않으면 **최적화가 통째로 사라진다**(A-2-04 5-2)
- 통계를 신뢰할 수 없어 **모르면 멈추는** 보수적 설계를 택해야 한다(A-2-03 2-7)
- MV·딕셔너리처럼 **엔진이 데이터를 소유해야 가능한 기능**을 만들 수 없다(A-2-06, A-3-05)
- 커넥터 품질 편차가 성능 편차로 직결된다

**StarRocks 의 대가**

- 새 소스를 붙이려면 **엔진을 포크해야 한다.** 제3자 생태계가 성립하지 않는다
- 소스가 늘 때마다 **FE·BE·Thrift 세 곳이 함께 늘어난다** — A-2-04 3-4의 `SUPPORT` 집합 17종, `PlanNodes.thrift` 의 스캔 노드 15종이 그 부담의 흔적이다
- C++ 쪽 결함이 프로세스를 통째로 죽인다(**A-5-03**)

### 5-4. "SPI 안정성"의 실질

`plan/01` 이 이 축을 "SPI 안정성 vs 내부 구조 직접 수정"이라고 적었다. **483 에서 확인한 바로는 정확한 서술이다.**

다만 SPI 가 안정적이라는 것이 **변하지 않는다는 뜻은 아니다.** A-3-01 2-2에서 본 `Block` 의 `sealed` 선언, A-2-07의 `SourcePage` 도입(과거 `LazyBlock` 대체) 등 SPI 는 계속 바뀐다. **안정성의 실질은 "바뀔 때 호환성 정책을 따른다"와 "엔진 본체와 분리돼 있어 바뀌는 범위가 명시된다"** 쪽이다.

## 6. 결론

**이것이 두 엔진의 가장 큰 구조적 차이이고, 앞의 여러 문서에서 관찰한 차이들의 공통 뿌리다.**

- **Trino** — `trino-spi`(558파일 73,858줄)라는 **독립 모듈** 뒤에 확장점을 뒀다. 플러그인 61개(커넥터 28개 + 관계형 DB 12종)가 엔진 코드를 건드리지 않고 붙어 있다. **제3자가 커넥터를 만들 수 있다**
- **StarRocks** — 커넥터가 **엔진 코드 안에 있고 FE(Java)·BE(C++)·Thrift 세 곳에 걸친다.** `ConnectorType` 열거형에 10종이 고정돼 있고, 새로 붙이려면 엔진을 고쳐야 한다
- **그 대가로 StarRocks 는 데이터를 "자기 것"으로 다룰 수 있다** — 통계 자동 수집(A-2-07), MV 자동 재작성(A-2-06), 전역 딕셔너리(A-3-05)가 전부 그 위에 선다

**선택 기준은 명확하다.** 붙여야 할 데이터 소스가 다양하고 계속 늘어난다면 Trino, 소스가 고정돼 있고 그 위에서 최대 성능을 뽑아야 한다면 StarRocks 다.

### 아직 답하지 않은 것

- **실제 커넥터 개발 난이도** — 새 커넥터를 만들어 보지 않았다. 줄 수와 건드릴 곳의 수는 대리 지표일 뿐이다
- **SPI 버전 호환성 정책의 실제 강도** — 릴리스 간 SPI 변경 이력을 보지 않았다(얕은 클론이라 어렵다)
- **StarRocks 의 `UNIFIED` 커넥터** — 여러 포맷을 묶는 커넥터인데 구조를 확인하지 않았다
- **StarRocks 의 `connector/trino` 패키지** — 이름으로 보아 Trino 방언·함수 호환 계층인데 확인하지 않았다(A-1-01 관련)
- **커넥터별 지원 범위 차이** — 어느 커넥터가 무엇까지 구현했는지는 **A-5-02**
- **C++ 커넥터 결함의 영향** — **A-5-03**
