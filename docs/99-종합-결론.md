# 종합 결론: Trino 483 과 StarRocks 4.0.14

> 이 문서는 본문 **31편**과 증거 파일 **18편**의 결론을 모아 **워크로드별 선택 기준**으로 재정리한 것이다.
> 개별 근거는 각 문서에 있으므로, 여기서는 **결론과 결론 사이의 연결 관계만** 다룬다.
> 기준 버전: **Trino 483** / **StarRocks 4.0.14**
> 일자: 2026-09-04

---

## 1. 한 문장으로 정리한 결론

**두 엔진의 거의 모든 차이는 스토리지를 소유하는지 여부라는 하나의 결정에서 갈라져 나온다.**

Trino 는 스토리지를 소유하지 않기로 결정하고 **SPI 라는 경계를 만들어 그 뒤쪽을 외부에 맡겼다.**
StarRocks 는 스토리지를 소유하기로 결정하고 **경계를 없애 전부 직접 처리한다.**

31편을 쓰는 동안 이 구도가 **축을 가리지 않고 반복해서 나타났다.** 아래 표가 그 반복을 정리한 것이다.

| 축 | 같은 결정이 어떻게 나타났는가 |
|---|---|
| `A-1-02` 타입 | Trino 의 타입은 SPI 에 있어서 확장할 수 있고, StarRocks 는 FE 열거형과 BE 의 C++ 구현이 짝을 이룬다 |
| `A-1-03` 함수 | 애노테이션을 붙인 Java 메서드로 플러그인을 만들 수 있고, StarRocks 는 `functions.py` 가 FE 와 BE 의 코드를 동시에 생성한다 |
| `A-2-06` MV | 커넥터가 MV 를 소유하므로 옵티마이저가 개입할 수 없고, StarRocks 는 자기 스토리지이므로 재작성 전용 코드를 18,000줄 갖추었다 |
| `A-2-07` 통계 | 테이블 포맷에 반환해 다른 엔진과 공유하는 쪽과, 자기 안에 쌓아 더 많은 정보를 담는 쪽으로 갈린다 |
| `A-4-02` 셔플 | 상태가 없으므로 FTE 로 진행분을 보존하는 쪽과, 데이터가 로컬에 있으므로 재실행이 합리적인 쪽으로 갈린다 |
| `A-5-01` 커넥터 | `trino-spi` 만 구현하면 되는 쪽과 FE, BE, Thrift 세 곳을 모두 고쳐야 하는 쪽으로 갈린다 |
| `A-5-04` 쓰기 | Iceberg 가 유일한 저장 수단이므로 MERGE 와 유지보수 명령까지 완비한 쪽과, 네이티브 테이블이 있어서 외부에 쓸 유인이 약한 쪽으로 갈린다 |
| `B-1-01` 메모리 | 쿼리만 회계하고 30% 를 비워 두는 쪽과, 적재와 compaction 과 복제까지 회계하고 90% 를 사용하는 쪽으로 갈린다 |
| `B-2-01` 격리 | 스레드를 OS 에 맡겨 입장만 통제하는 쪽과, 스레드를 직접 소유해 CPU 를 실제로 나누는 쪽으로 갈린다 |
| `B-3-01` 캐시 | 워커에 디스크가 없을 수도 있어서 기본값이 꺼짐이고, BE 에는 디스크가 있으므로 기본값이 켜짐이다 |
| `B-4-01` HA | 메타데이터를 보관하지 않으므로 그 계층 자체가 없고, StarRocks 는 복제 저널과 자동 선거를 갖추었다 |
| `B-6-01` 관측 | 쿼리 밖의 계보에 투자한 쪽과, 쿼리 안의 리더 내부 카운터에 투자한 쪽으로 갈린다 |
| `C-1` 전체 | Trino 에는 대응물이 없다. 테이블 모델과 인덱스, compaction, 적재가 모두 StarRocks 에만 있다 |
| `D-01` 빌드 | Maven 하나만 쓰는 쪽과 Maven 과 CMake 에 Python 코드 생성까지 더한 쪽으로 갈린다 |

**따라서 제품을 선택하는 일은 기능 목록을 대조하는 작업이 아니라, 이 결정이 자기 상황에 맞는지를 묻는 작업이다.**

## 2. 명확한 격차 (측정으로 확인한 것)

우열이 분명한 항목만 모았다. **나머지는 3절에서 "대등한 것"으로 따로 다룬다.**

### 2-1. StarRocks 가 명확히 앞서는 곳

| 항목 | 근거 | 격차의 크기 |
|---|---|---|
| **MV 쿼리 재작성** | `A-2-06` | 재작성 전용 코드가 18,000줄인 쪽과 **규칙이 0개인 쪽이다.** Trino 에서는 MV 이름을 직접 적어야 한다 |
| **통계 자동 수집** | `A-2-07` | 백그라운드 데몬이 **쿼리를 관찰해 필요한 컬럼을 스스로 고른다**(실측). Trino 에서는 사람이 `ANALYZE` 를 실행해야 한다 |

| **캐시 기본 켜짐** | `B-3-01` | 설정하지 않아도 적중한다(실측). Trino 에서는 디렉토리를 지정해야 켜진다 |
| **CTE 재사용** | `A-2-05` | Trino 에는 이 기능 자체가 없다. 다만 이 랩에서 자동 선택이 동작하는지는 확인하지 못했다 |
| **spill 범위** | `A-3-03` | 12계열과 4계열로 갈린다. 다만 **양쪽 모두 기본값이 꺼짐이다** |

### 2-2. Trino 가 명확히 앞서는 곳

| 항목 | 근거 | 격차의 크기 |
|---|---|---|
| **커넥터 확장성** | `A-5-01`, `C-2-01` | SPI 가 **16종**이고 플러그인 JAR 로 배포한다. StarRocks 에서는 `ConnectorType` 열거형을 고치고 FE 와 BE 를 다시 빌드해야 한다 |
| **커넥터 다양성** | `C-2-02` | 27개에 JDBC 계열 15개를 더한다. 관계형 데이터베이스는 **15 대 1** 이고, 관측 데이터와 SaaS, 스트리밍 읽기에는 대응물이 없다 |
| **Iceberg 쓰기** | `A-5-04` | **StarRocks 는 `INSERT` 와 CTAS 만 가능하다.** `UPDATE`·`DELETE`·`MERGE` 가 각각 다른 방식으로 막혀 있고 유지보수 명령도 없다 |
| **장수 쿼리의 내결함성** | `A-4-02`, `B-4-01` | FTE 가 태스크 단위로 재시도해 진행분을 보존한다. StarRocks 는 쿼리 전체를 최대 2회 재실행한다 |
| **함수 추가 비용** | `A-1-03` | 애노테이션 하나와 플러그인 JAR 로 끝난다. StarRocks 에서는 ID 를 부여하고 C++ 로 구현한 뒤 양쪽을 다시 빌드해야 한다 |
| **접근제어의 세밀함** | `B-5-01` | 검사 지점이 **84개와 31개**로 다르다. OPA 연동은 Trino 에만 있다 |
| **컬럼 수준 계보** | `B-6-01` | 엔진이 직접 계산해 이벤트로 내보낸다. StarRocks 에는 없다 |
| **결함이 미치는 영향 범위** | `A-5-03` | 리더에 결함이 발생하면 Trino 는 쿼리가 실패하고, StarRocks 는 **BE 프로세스가 중단된다.** 그것도 데이터를 보유한 프로세스다 |
| **타입 표현력 (시간대와 UUID)** | `A-1-02` | Iceberg 의 `timestamptz` 를 구분하고 `UUID` 를 읽는다. StarRocks 는 전자를 합쳐 버리고 후자는 **조회에서 실패한다** |
| **DECIMAL 정밀도** | `A-1-02` | **이 항목만 반대다.** StarRocks 가 76 이고 Trino 가 38 이다. 다만 Iceberg 의 상한이 38 이므로 외부 테이블에서는 의미가 없다 |

### 2-3. 어느 쪽도 상위집합이 아닌 것

**이 연구에서 가장 자주 나온 형태다.** 양쪽 모두 가능하지만 가능한 범위가 서로 어긋난다.

| 항목 | 근거 |
|---|---|
| **함수 술어 프루닝** | `A-5-02`: Trino 는 `year` 와 `date_trunc` 를, StarRocks 는 `date_format` 을 벗겨 낸다. **서로 반대 방향으로 처리하지 못한다** |
| **서브쿼리 언네스팅** | `A-2-05`: 15종 가운데 12종이 동일하고 **2종이 정반대다** |
| **윈도우 최적화** | `A-2-05`: 최적화하는 쿼리 모양이 어긋나서 각각 하나씩 우위를 가진다 |
| **런타임 필터** | `A-3-04`: TopN 과 집계 필터는 StarRocks 에만 있고, 파일 필터와 행 필터를 분리하는 것은 Trino 에만 있다 |
| **조인 순서 탐색** | `A-2-01`: 5개에서 8개까지는 Trino 가 더 넓게 탐색하고, 9개에서 50개까지는 StarRocks 만 순서를 바꾼다 |
| **예약어** | `A-1-01`: StarRocks 에만 99개가 있고 Trino 에만 27개가 있다 |

## 3. 대등한 것: 이 연구의 중요한 결과

**차이가 없다는 사실도 하나의 결과다.** 다음 항목들은 실측에서 차이가 판별되지 않았거나 완전히 동등하게 나왔다.

| 항목 | 근거 |
|---|---|
| 플랜 내부 푸시다운 (술어 전이, outer join 단순화, LIMIT·TopN 관통) | `A-2-04`: 실측한 6항목이 전부 동등했다 |
| 파티션 프루닝 (맨 앞 컬럼에 걸린 술어) | `A-5-02`: **165행과 1파일로 완전히 일치했다** |
| 파일 리더 호환성 | `A-5-03`: 복합 타입과 압축 코덱 4종, Iceberg 삭제 파일에서 결과가 전부 일치했다 |
| 스키마 진화 | `A-5-04`: `ADD`·`DROP`·`RENAME` 이 상호운용된다. 양쪽이 서로의 변경을 모두 인식한다 |
| 시간 여행과 메타데이터 테이블 | `A-5-04`: 스냅샷 7개를 양쪽이 똑같이 센다 |
| 데이터 표현 모델 | `A-3-01`: 같은 컬럼너 배치 모델을 쓰고 규모도 대등하다 |
| 실행 모델 | `A-3-02`: **`plan/01` 이 설정한 대비가 성립하지 않는다.** 양쪽 모두 다단계 피드백 큐로 수렴했다 |
| 파서의 오류 처리 | `A-1-01`: 양쪽 모두 SLL 에서 LL 로 넘어가는 2단계 방식을 쓴다 |
| 메모리의 유효 바닥 | `B-1-01`: 16MB 와 18MB 로 같은 자릿수다 |
| min/max 와 블룸필터 계층 | `C-1-02`: Iceberg 매니페스트와 ZoneMap 이 대등하다 |

**특히 `A-2-04`, `A-3-01`, `A-3-02` 는 다를 것이라고 예상하고 착수했으나 같다는 결론으로 끝난 축들이다.** 계획서가 설정한 대비가 실제로는 성립하지 않았다.

## 4. 워크로드별 선택 기준

### 4-1. 결정 표

| 상황 | 선택 | 결정적 근거 |
|---|---|---|
| **서로 다른 시스템을 한 쿼리로 조인해야 한다** | **Trino** | 커넥터가 27개와 10개로 다르고 대체 수단이 없다 (`C-2-02`) |
| **Iceberg 를 고쳐 써야 한다** (CDC upsert, GDPR 삭제) | **Trino** | StarRocks 는 Iceberg 에 `UPDATE`·`DELETE`·`MERGE` 를 수행하지 못한다 (`A-5-04`) |
| **수십 분 이상 실행되는 ETL 이 있다** | **Trino** | FTE 만이 진행분을 보존한다 (`A-4-02`, `B-4-01`) |
| **BI 대시보드와 애드혹 반복 조회가 주된 용도다** | **StarRocks** | MV 자동 재작성과 기본으로 켜진 캐시, 자동 통계를 모두 갖추었다 (`A-2-06`, `B-3-01`, `A-2-07`) |
| **upsert 가 잦은 서비스 데이터를 다룬다** | **StarRocks** | `PRIMARY KEY` 모델과 부분 컬럼 갱신을 지원한다 (`C-1-01`) |
| **Kafka 에서 테이블로 들어가는 파이프라인이 필요하다** | **StarRocks** | Routine Load 가 구성 요소를 하나 줄여 준다 (`C-1-04`) |
| **`LIKE '%…%'` 검색이 잦다** | **StarRocks** | n-gram 인덱스가 있다. Iceberg 통계로는 전혀 걸러지지 않는다 (`C-1-02`) |
| **운영 인력이 적다** | **StarRocks** | 자동 통계와 자동 compaction, 기본으로 켜진 캐시가 있다. 다만 자원 계획을 세우는 일은 더 어렵다 |
| **Spark 를 포함한 여러 엔진이 같은 레이크를 사용한다** | **Trino** | 통계가 테이블에 남아서 공유된다 (`A-2-07`) |
| **정책을 Rego 로 통일해 관리한다** | **Trino** | OPA 연동은 Trino 에만 있다 (`B-5-01`) |
| **거버넌스와 규제에 대응해야 한다** (컬럼 계보) | **Trino** | 엔진이 직접 계산해 준다 (`B-6-01`) |
| **엔진을 직접 고쳐 쓸 계획이 있다** | **Trino** | SPI 로 대부분 해결되고 빌드도 단일 언어로 이루어진다 (`C-2-01`, `D-01`) |
| **초 단위 대화형 분석이 목표다** | **StarRocks** | BRPC push 와 낮은 양자, C++ 실행 엔진을 갖추었다. **다만 실행 시간을 재지 못했다** (5절) |

### 4-2. 두 엔진을 함께 쓰는 구성

두 엔진을 같은 Iceberg 카탈로그에 연결하는 방식은 **실제로 잘 동작한다.** 이 연구의 랩 자체가 그 증거다. 역할을 나누면 다음과 같다.

| 작업 | 담당 |
|---|---|
| 적재(append), 조회, 시간 여행 | 양쪽 모두 가능하다 |
| **행 수정과 삭제, MERGE upsert** | **Trino 만 가능하다** (`A-5-04`) |
| **파일 병합, 스냅샷 만료, 고아 파일 제거** | **Trino 만 가능하다** (`A-5-04`, `C-1-03`) |
| **반복 집계 가속 (MV 재작성)** | **StarRocks 가 담당한다** (`A-2-06`) |
| 감사와 컬럼 계보 | Trino 가 담당한다 (`B-6-01`) |
| 성능 분석 | StarRocks 의 프로파일을 사용한다 (`B-6-01`) |

**주의할 점이 두 가지 있다.**

1. **통계는 공유되지 않는다.** 양쪽에서 각각 `ANALYZE` 를 실행해야 한다 (`A-2-07`)
2. **StarRocks 만으로 Iceberg 를 운영하지 않아야 한다.** 적재는 가능하지만 정리할 수단이 없어서 파일이 계속 쌓인다 (`A-5-04`)

### 4-3. 이전(migration) 체크리스트

Trino 에서 StarRocks 로 SQL 을 옮길 때에는 **오류로 드러나지 않는 항목부터** 확인해야 한다.

| 순위 | 항목 | 확인해야 하는 이유 |
|---|---|---|
| **1** | **`\|\|` 연산자** | 오류가 발생하지 않고 **아무 경고 없이 NULL** 이 된다. `'a' \|\| 'b'` 가 `NULL` 로 평가된다 (`A-1-01`) |
| 2 | 근사 집계 함수 | 이름은 대응되지만 **값이 다르게 나온다** (15432 와 15022) (`A-1-03`) |
| 3 | Iceberg 의 `timestamptz` 컬럼 | 스키마에서 구분되지 않는다. 값 자체는 올바르다 (`A-1-02`) |
| 4 | 날짜 함수로 감싼 술어 | 프루닝이 아무 표시 없이 사라진다. 쿼리는 성공한다 (`A-5-02`) |
| 5 | 예약어 99개 | 오류로 드러난다. `text`, `key`, `json`, `range`, `default` 등이 해당한다 |
| 6 | 상관 서브쿼리 | 계획 실패가 오류로 드러난다. 전수로 확인해야 한다 (`A-2-05`) |
| 7 | Iceberg 의 `UUID` 컬럼 | `DESC` 는 성공하지만 **조회에서 실패한다** (`A-1-02`, `A-5-03`) |

**`sql_dialect='trino'` 를 일괄 이전 수단으로 기대하지 않아야 한다.** trino-parser **385** 를 기준으로 삼은 부분 지원이고 함수 대응표도 약 100건에 머문다 (`A-1-01`).

## 5. 이 연구가 답하지 못한 것

**가장 중요한 한계부터 적는다.**

### 5-1. 실행 시간을 한 번도 재지 못했다

**어느 쪽이 빠른지에 이 연구는 답하지 않는다.**

랩이 TPC-H **SF 0.01**(lineitem 60,175행)이고, SF 1 을 사용하는 `perf` 프로파일은 이 호스트에서 띄울 수 없다. 컨테이너 한도가 15.3GB 인데 RAM 이 15.6GB 이고 **swap 이 0** 이기 때문이다 (`plan/02` 6-2절).

따라서 아래 항목은 전부 검증하지 못했다.

- 두 옵티마이저가 고른 플랜 가운데 어느 쪽이 실제로 빨랐는가 (`A-2-01` 부터 `A-2-03` 까지)
- C++ 벡터화와 JVM 바이트코드 생성 사이에 실제 처리량 차이가 얼마나 되는가 (`A-3-01`, `A-3-05`)
- 해시 조인 구현이 6종인 쪽과 2종인 쪽 사이에 성능 차이가 있는가 (`A-3-03`)
- spill 이 발생했을 때 성능이 어떻게 변하는가 (`A-3-03`, `B-1-01`)
- 캐시와 인덱스가 실제로 얼마나 이득을 주는가 (`B-3-01`, `C-1-02`)

### 5-2. 노드가 1대씩이라 다중 노드 항목이 전부 빠졌다

Trino worker 가 1대이고 StarRocks BE 도 1대다. 다음 항목을 검증하지 못했다.

- **셔플 전송 계층 전체** (`A-4-01`, `A-4-02`: 두 문서에 실측 결과가 하나도 없다)
- StarRocks 의 broadcast 게이트에 들어가는 `beNum` 항 (`A-2-02`)
- 리소스 그룹이 **가중치대로 CPU 를 나누어 주는가** (`B-2-01` 축의 핵심 주장이다)
- **한 노드가 중단되어도 나머지 노드로 계속 처리하는가** (`B-4-01` 축의 핵심 질문이다)
- FTE 의 태스크 단위 재시도 (`A-4-02`)
- FE FOLLOWER 의 승격 (`B-4-01`)

### 5-3. 랩 구성이 닿지 않은 영역

| 영역 | 검증하지 못한 이유 |
|---|---|
| 연합 질의 | 카탈로그가 Iceberg 하나뿐이다 (`C-2-02`) |
| Ranger 와 OPA 연동 | 정책 서버가 없다 (`B-5-01`) |
| Trino 파일 캐시 | 구성하지 않았다 (`B-3-01`) |
| Trino 리소스 그룹 | 구성하지 않았다 (`B-2-01`) |
| Stream Load, Broker Load, Routine Load | Kafka 와 브로커가 없다 (`C-1-04`) |
| StarRocks 의 shared-data 모드 | 클러스터를 다시 구성해야 한다 (`C-1-03`) |
| 커밋 활동과 릴리스 주기 | `works/` 를 **얕은 클론**으로 받았다 (`D-02`) |
| 두 프로젝트의 빌드 | 시간과 디스크가 부족하다 (`D-01`) |

### 5-4. 아직 재현하지 못한 과제

**StarRocks 4.0.1 에서 발생한 BE SIGSEGV 가 arm64 환경에만 해당하는지 확인하지 못했다**(`evidence/A-5/20260820-…`). 디스크 여유가 부족해서 4.0.1 이미지를 함께 둘 수 없었다. 재개 절차는 `plan/02` 6-1절에 적어 두었다.

## 6. 이 연구가 스스로 고친 것

**계획서(`plan/01`)의 전제가 일곱 번 틀렸다.** 기록으로 남긴다. 소스코드를 비교하는 작업에 **선입견이 얼마나 자주 개입하는지** 보여 주는 표본이기 때문이다.

| # | `plan/01` 의 전제 | 실제 확인한 내용 | 문서 |
|---|---|---|---|
| 1 | 문법이 `core/trino-parser` 에 있다 | 483 에서 **`core/trino-grammar`** 로 분리되었다 | `A-1-01` |
| 2 | 협력적 멀티태스킹과 논블로킹 폴러로 대비된다 | **성립하지 않는다.** 양쪽 모두 다단계 피드백 큐로 수렴했다 | `A-3-02` |
| 3 | Trino 의 MV 는 Iceberg 와 Hive 커넥터에 한정된다 | **Hive 커넥터는 MV 를 구현하지 않는다** | `A-2-06` |
| 4 | StarRocks 의 전역 딕셔너리는 Trino 에 대응물이 없다 | 맞는 설명이지만 **레이크 테이블에서는 StarRocks 자신도 기본으로 사용하지 않는다** | `A-3-05` |
| 5 | StarRocks 는 **BE cgroup** 으로 실제 격리를 수행한다 | **cgroup 을 쓰지 않는다.** CPU 친화도 바인딩과 가중 vruntime, 코어 대여로 구현되어 있다 | `B-2-01` |
| 6 | 캐시는 StarRocks 에만 있고 **Trino 에는 없다** | **Trino 483 에 Alluxio 기반 분산 파일 캐시가 있다.** 없는 것은 결과 캐시뿐이다 | `B-3-01` |
| 7 | StarRocks 는 **내장 RBAC** 만 제공한다 | **Apache Ranger 통합이 있다.** Hive 서비스 정의를 재사용하는 방식까지 지원한다 | `B-5-01` |

**그리고 코드만 읽고 내린 판단이 실측에 두 번 뒤집혔다.**

| 잘못 읽은 내용 | 실측이 바로잡은 내용 | 문서 |
|---|---|---|
| 임계값 때문에 StarRocks 가 left-deep 플랜을 만든다 | 원인은 **통계 부족**이었다. 통계가 완전하면 bushy 플랜이 나온다 | `A-2-01` 4절 |
| StarRocks 커넥터는 함수 술어를 밀어 내리지 못한다 | **`date_format` 에서는 완전히 프루닝한다.** 문제는 옵티마이저 규칙이 다루는 함수의 범위였다 | `A-5-02` 4-4절 |

**측정을 설계하는 과정에서도 두 번 오류를 범할 뻔했다.**

- `count(*)` 로 스캔량을 재려고 했다. StarRocks 의 메타데이터 최적화에 걸려서 비교가 성립하지 않는다 (`A-5-02` 4-1절)
- StarRocks 의 `OutputRows` 를 Trino 의 `Input rows` 와 짝지었다. 전자는 필터를 적용한 **이후**의 값이므로, 올바른 짝은 `RawRowsRead` 다 (`A-5-02` 4-1절)

## 7. 마지막으로

**이 연구의 결론은 어느 쪽이 더 낫다는 것이 아니다.**

측정으로 확인한 명확한 격차는 2절의 두 표에 있고, **그 두 표의 길이는 서로 비슷하다.** 그리고 3절의 대등한 항목 목록도 그만큼 길다. 예상과 달리 **두 엔진은 많은 영역에서 같은 답에 도달해 있었다.**

갈리는 곳은 거의 전부 **1절의 한 문장**으로 설명된다. 그러므로 선택의 질문은 다음과 같이 좁혀진다.

> **우리 데이터가 한 시스템 안에 있는가, 여러 시스템에 흩어져 있는가.**
> **우리가 그 데이터를 고쳐 쓰는가, 읽기만 하는가.**
> **우리에게 필요한 것이 반복 조회의 속도인가, 연결할 수 있는 소스의 폭인가.**

세 질문의 답이 한 방향으로 모이면 선택은 이미 정해져 있다. 답이 갈린다면 **4-2절의 함께 쓰는 구성**이 현실적인 답이 된다.
