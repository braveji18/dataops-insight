## 1. 비교 관점

`A-5-04` 에서 **외부 Iceberg 에 대한 쓰기**를 비교했다. 여기는 **StarRocks 가 자기 테이블에 데이터를 넣는 방식**이다 — Trino 에 대응물이 없는 영역이다.

세 가지를 본다.

1. **어떤 경로로 들어오는가** — SQL 만인가, 다른 통로가 있는가
2. **트랜잭션이 어떻게 끝나는가** — 커밋과 가시성이 같은 것인가
3. **Trino 진영은 같은 요구를 어떻게 푸는가**

결론부터: **StarRocks 는 SQL 밖에 적재 경로를 여럿 두었고, 커밋과 가시성을 분리했다.** Trino 는 적재라는 개념 자체가 없다 — `INSERT` 문이 전부이고, 스트리밍 적재는 다른 시스템의 일이다.

## 2. StarRocks 구현

### 2-1. 적재 경로가 SQL 밖에 있다

`fe/fe-core/.../load/` 아래 디렉토리가 경로를 보여준다.

| 디렉토리 | 방식 |
|---|---|
| `load/streamload/` | **Stream Load** — HTTP PUT 으로 파일을 밀어 넣는다. SQL 이 아니다 |
| `load/loadv2/` | **Broker Load** — `LOAD LABEL ...` 문장으로 외부 저장소에서 비동기 적재 |
| `load/routineload/` | **Routine Load** — Kafka 등에서 **계속 읽어 들이는 상시 작업** |
| (+ `INSERT INTO`) | 일반 SQL |

`A-1-01` 5-1 의 문장 카테고리 목록에 `StreamLoad Statement`, `Routine Statement`, `Load Statement`, `Pipe Statement` 가 따로 있던 것이 이것이다.

**`Routine Load` 가 성격을 가장 잘 보여준다.** Kafka 토픽을 구독해 계속 적재하는 **상시 작업을 데이터베이스가 소유한다.** 시작·정지·재개·변경이 전부 SQL 문장이다(`createRoutineLoadStatement`, `pauseRoutineLoadStatement`, `resumeRoutineLoadStatement`, `stopRoutineLoadStatement`).

즉 **StarRocks 는 "데이터를 가져오는 일"까지 제품 경계 안에 넣었다.**

### 2-2. 트랜잭션이 5단계다

```java
public enum TransactionStatus {
    UNKNOWN(0),
    PREPARE(1),
    COMMITTED(2),
    VISIBLE(3),
    ABORTED(4),
    PREPARED(5);
```
— `fe/fe-core/.../transaction/TransactionStatus.java:25-31`

**`COMMITTED` 와 `VISIBLE` 이 나뉘어 있는 것이 이 절의 핵심이다.**

- `COMMITTED` — FE 가 "이 트랜잭션은 성공했다"고 확정한 상태. 되돌리지 않는다
- `VISIBLE` — **모든 복제본이 새 버전을 적용해 조회에 보이는 상태**

그 사이가 **publish version** 단계다.

```java
                    transactionState.setTransactionStatus(TransactionStatus.VISIBLE);
```
— `fe/fe-core/.../transaction/DatabaseTransactionMgr.java:1350`

```java
        info.add(TimeUtils.longToTimeString(txnState.getPublishVersionTime()));
```
— `DatabaseTransactionMgr.java:792`

**왜 나눴는가.** 데이터가 여러 BE 에 복제돼 있기 때문이다. FE 가 커밋을 확정한 뒤, 각 BE 가 그 버전을 실제로 적용해야 조회 결과에 나타난다. 그 시차를 상태로 표현한 것이다.

**MVCC 는 이 버전 번호로 성립한다.** 조회는 "현재 보이는 버전"을 읽고, 적재 중인 버전은 보지 않는다. 그래서 **적재와 조회가 서로를 막지 않는다.**

관리자는 트랜잭션이 한 번에 하나만 진행 중임을 전제한다.

```java
                    // there should be at most 1 txn in PREPARE/COMMITTED/VISIBLE status
```
— `DatabaseTransactionMgr.java:222`

### 2-3. 라벨이 멱등성을 준다

`BEGIN WORK? (WITH LABEL label=identifier)?`(`A-4-01` 관련 조사에서 확인한 문법)와 적재 작업의 `LABEL` 이 같은 장치다.

**같은 라벨로 다시 적재하면 중복되지 않는다.** 네트워크 오류로 재시도해야 하는 스트리밍 적재에서 필수적인 장치다 — 클라이언트가 "이번 배치의 라벨은 `batch-2026-09-04-001`" 이라고 정해 두면, 재시도가 안전해진다.

Trino/Iceberg 에는 이 개념이 없다. 재시도 안전성은 애플리케이션이 책임진다.

## 3. Trino 쪽

**적재라는 개념이 없다.** 데이터를 넣는 수단은 `INSERT` / `CREATE TABLE AS` / `MERGE` 세 SQL 문장뿐이고, 전부 **쿼리와 같은 실행 경로**를 탄다.

| 요구 | StarRocks | Trino |
|---|---|---|
| 파일 밀어 넣기 | **Stream Load**(HTTP) | 없음 — 파일을 저장소에 두고 `INSERT ... SELECT` 하거나 Iceberg `ADD_FILES` 프로시저 |
| 외부 저장소에서 대량 적재 | **Broker Load**(비동기) | `INSERT ... SELECT` (동기) |
| Kafka 상시 구독 | **Routine Load** | **없음** — Flink/Spark 등 외부 도구 |
| 재시도 멱등성 | **라벨** | 없음 |
| 트랜잭션 가시성 | `COMMITTED` → `VISIBLE` 2단계 | Iceberg 스냅샷 커밋(원자적) |

**`ADD_FILES` 프로시저**(`A-5-04` 2-2)가 Stream Load 와 가장 가까운 대체 수단이다 — 이미 저장소에 있는 파일을 테이블에 등록한다. 다만 **파일을 올리는 일은 Trino 밖**이다.

**Kafka 상시 구독에는 대체 수단이 없다.** Trino 에 Kafka 커넥터가 있지만 그것은 **읽기**용이고, "계속 읽어서 테이블에 쌓는" 작업은 Flink 나 Spark Streaming 이 한다.

## 4. 실측

### 4-1. 모든 쓰기가 적재 작업으로 기록된다

`information_schema.loads` 에 남은 이력이다.

| JOB_ID | LABEL | STATE | TYPE |
|---|---|---|---|
| 29702 | `delete_01a06ca0-...` | FINISHED | INSERT |
| 29701 | `delete_01a06ca0-...` | FINISHED | INSERT |
| 29700 | `insert_01a06c9f-...` | FINISHED | INSERT |

**`DELETE` 의 TYPE 이 `INSERT` 다.** 삭제도 "삭제 표시를 적재하는" 트랜잭션으로 처리된다. 실제 정리는 compaction 이 나중에 한다(`C-1-03`).

라벨이 자동 생성돼 있다(`delete_<uuid>`, `insert_<uuid>`). **사용자가 지정하지 않으면 엔진이 만든다.**

`loads` 뷰의 컬럼은 `ID, LABEL, PROFILE_ID, DB_NAME, TABLE_NAME, USER, WAREHOUSE, STATE, PROGRESS, TYPE, PRIORITY, SCAN_ROWS, SCAN_BYTES, FILTERED_ROWS, ...` 다 — **`FILTERED_ROWS` 가 있다는 점이 적재 전용 관점을 보여준다**(형식 오류로 걸러진 행 수).

### 4-2. 트랜잭션 상태

```
SHOW PROC '/transactions/native_probe'
→ running 0 / finished 18
```

C-1-01·C-1-02 실험에서 만든 18개 트랜잭션이 전부 끝나 있다. **진행 중인 트랜잭션을 잡아 `COMMITTED`/`VISIBLE` 을 구분해 보이지는 못했다** — 랩 규모에서는 두 상태 사이가 순식간이다.

### 4-3. 재지 못한 것

**Stream Load / Broker Load / Routine Load 를 실행하지 못했다.** Kafka 도 브로커도 랩에 없다. 2-1 은 코드와 문법 독해다.

**라벨 멱등성도 시험하지 못했다.**

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| 적재 경로 | SQL 3종(`INSERT`/`CTAS`/`MERGE`) | **SQL + Stream/Broker/Routine Load + Pipe** |
| 스트리밍 구독 | **없음**(외부 도구) | **Routine Load** — DB 가 소유 |
| 재시도 멱등성 | 없음(애플리케이션 책임) | **라벨** |
| 트랜잭션 상태 | 스냅샷 커밋(원자적) | **PREPARE → COMMITTED → VISIBLE** |
| 가시성 지연 | 없음(커밋 = 가시) | **publish version 단계 존재** |
| MVCC | Iceberg 스냅샷 | **버전 번호** |
| 적재 관측 | 쿼리 이력과 동일 | **`information_schema.loads` 전용 뷰**(`FILTERED_ROWS` 등) |

### 5-2. "적재를 소유한다"는 결정

StarRocks 가 Routine Load 를 갖는 것은 **데이터베이스가 파이프라인의 일부가 되겠다**는 선언이다. Kafka → 테이블 경로에 Flink 를 두지 않아도 된다.

**얻는 것**: 구성 요소가 줄고, 적재 상태를 SQL 로 관측·제어한다.
**파는 것**: 적재 부하가 **쿼리와 같은 프로세스**에서 발생한다. `B-1-01` 3-1 의 `MemTracker::Type` 에 `LOAD` 가 있고, `A-4-01` 4-3 에서 본 `brpc_load_ignore_overcrowded` 가 **적재만 기본 `true`** 인 것도 이 때문이다 — 적재는 실패 비용이 크니 메모리를 더 쓰더라도 밀고 나간다.

**즉 적재를 소유한 대가가 여러 축에서 반복해 나타난다.** 메모리 회계(`B-1-01`), 셔플 흐름 제어(`A-4-01`), compaction 부하(`C-1-03`)가 전부 같은 뿌리다.

### 5-3. 커밋과 가시성을 나눈 이유

Iceberg 는 **메타데이터 파일 하나를 원자적으로 교체**하면 커밋이 끝난다. 데이터 파일은 이미 저장소에 있고 모두가 같은 것을 본다. **분리할 이유가 없다.**

StarRocks 는 데이터가 **여러 BE 에 복제**돼 있다. FE 가 커밋을 확정해도 각 BE 가 버전을 적용해야 조회에 반영된다. **분리하지 않을 수 없다.**

**이 차이는 복제를 소유하는 대가다.** 그리고 운영 관점의 함의가 있다 — **적재가 "끝났다"고 해서 즉시 조회되는 것이 아니다.** publish 가 늦어지면 커밋된 데이터가 아직 안 보일 수 있다.

### 5-4. `FILTERED_ROWS` 가 말해 주는 것

`information_schema.loads` 에 걸러진 행 수 컬럼이 있다는 것은 **적재 중 형식 오류를 허용하는 설계**를 뜻한다. 대량 적재에서 일부 행이 깨져 있어도 전체를 실패시키지 않고 넘어가는 것 — 실무에서 매우 중요한 동작이다.

Trino 의 `INSERT ... SELECT` 는 **한 행이라도 실패하면 쿼리가 실패**한다. 데이터 정제를 앞단에서 끝내 두어야 한다.

## 6. 결론

**비교가 아니라 부재다 — Trino 에는 적재 계층이 없다.**

- **경로**: StarRocks 는 SQL 밖에 Stream/Broker/Routine Load 를 두었다. 특히 **Routine Load 는 Kafka 상시 구독을 DB 가 소유**하는 것으로, Trino 진영에서는 Flink/Spark 의 몫이다
- **트랜잭션**: `COMMITTED` 와 `VISIBLE` 이 나뉘어 있다. 복제를 소유하기 때문에 생긴 구조다
- **멱등성**: 라벨로 재시도 안전성을 준다. Iceberg 에는 대응물이 없다
- **오류 허용**: `FILTERED_ROWS` — 일부 행이 깨져도 적재가 진행된다. Trino 는 전체 실패
- **대가**: 적재 부하가 쿼리와 같은 프로세스에서 발생하고, 그 영향이 여러 축에서 반복해 나타난다

**실무 결론**

1. **Kafka → 테이블 파이프라인을 단순화하고 싶다면 StarRocks Routine Load 가 구성 요소를 하나 줄여 준다.** Trino 진영에서는 Flink/Spark 가 필요하다
2. **적재 재시도가 잦은 환경이라면 라벨을 반드시 활용하라.** 지정하지 않으면 엔진이 자동 생성하는데, 그것으로는 클라이언트 재시도의 중복을 막지 못한다
3. **"적재 완료"와 "조회 가능"이 다를 수 있음을 감안하라.** `COMMITTED` 와 `VISIBLE` 사이에 publish version 단계가 있다
4. **더러운 데이터를 넣어야 한다면 StarRocks 쪽이 편하다.** Trino 는 한 행만 깨져도 전체가 실패하므로 앞단 정제가 필수다
5. **적재 부하를 쿼리 용량 계획에 포함하라** — `B-1-01`·`B-2-01`·`C-1-03` 이 같은 결론을 반복한다

### 아직 답하지 않은 것

- **Stream / Broker / Routine Load 전부 미실행.** Kafka 도 브로커도 랩에 없다. 2-1 은 코드와 문법 독해다
- **라벨 멱등성 미검증**
- **`COMMITTED` → `VISIBLE` 지연** — 랩 규모에서는 순식간이라 관찰하지 못했다. 복제 3개·대용량에서 얼마나 걸리는지가 실무 관심사인데 답하지 못했다
- **적재 중 조회 격리** — MVCC 가 실제로 적재와 조회를 분리하는지 동시 실행으로 확인하지 않았다
- **`FILTERED_ROWS` 의 동작** — 깨진 데이터를 넣어 보지 않았다. 허용 비율 설정(`max_filter_ratio`)도 확인하지 않았다
- **적재 성능** — 처리량을 재지 않았다. `perf` 프로파일이 필요하다
- **Pipe** — 문법에 `Pipe Statement` 가 있으나 다루지 않았다
