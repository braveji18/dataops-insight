# `'a' || 'b'`가 NULL이 됩니다: SQL을 옮길 때 조용히 깨지는 것들

> 비교 기준: Trino **483** (`50b0b50b`) · StarRocks **4.0.14** (`7c18dd9d`) · 2026-10-16 기준

## 결론부터

**오류로 드러나는 차이는 위험하지 않습니다. 위험한 것은 쿼리가 성공하고 값만 틀리는 경우입니다.**

Trino에서 StarRocks로 SQL을 옮길 때 확인해야 할 항목을 위험도 순으로 정리했습니다. 상위 네 개는 **아무 경고 없이 결과가 달라지거나 성능이 조용히 나빠집니다.**

| 순위 | 항목 | 어떻게 드러나는가 |
|---|---|---|
| **1** | **`||` 연산자** | **오류 없이 `NULL`이 됩니다.** `'a' \|\| 'b'`가 `NULL`로 평가됩니다 |
| 2 | 근사 집계 함수 | 이름은 대응되지만 **값이 약 2.7% 다릅니다** (15,432 대 15,022) |
| 3 | Iceberg `timestamptz` 컬럼 | 스키마에서 구분되지 않습니다. **값 자체는 맞습니다** |
| 4 | 날짜 함수로 감싼 술어 | **프루닝이 아무 표시 없이 사라집니다.** 쿼리는 성공합니다 |
| 5 | 예약어 99개 | 오류로 드러납니다 |
| 6 | 상관 서브쿼리 | 계획 실패가 오류로 드러납니다. 전수 확인이 필요합니다 |
| 7 | Iceberg `UUID` 컬럼 | `DESC`는 성공하고 **조회에서 실패합니다** |

**그리고 `sql_dialect='trino'` 호환 모드를 일괄 이전 수단으로 기대하면 안 됩니다.** trino-parser **385**를 기준으로 삼은 부분 지원이고, 함수 대응표가 약 100건에 머뭅니다.

## 2. 1순위: `||` 연산자

### 2-1. 같은 SQL, 다른 답, 오류 없음

| 엔진 / 설정 | `'a' \|\| 'b'` | `1 \|\| 0` | `0 \|\| 0` |
|---|---|---|---|
| Trino 483 | `ab` | 파싱 오류 | 해당 없음 |
| StarRocks 4.0.14 (기본) | **`NULL`** | `1` | `0` |
| StarRocks (`sql_mode='PIPES_AS_CONCAT'`) | `ab` | 미확인 | 미확인 |

`1 || 0 = 1`이므로 **StarRocks 기본값에서 `||`는 논리 OR입니다.** 문자열은 boolean 캐스트에 실패해 `NULL`이 됩니다.

**이것이 전체 비교에서 가장 위험한 항목입니다.** 다른 차이는 오류로 즉시 드러나지만 이것은 쿼리가 성공하고 값만 틀립니다. `sql_mode`를 바꾸면 원래 의미로 돌아오므로 **원인이 렉서 분기임도 확정됩니다.**

### 2-2. 어떻게 대응할까

세 가지 선택지가 있습니다.

1. **`sql_mode='PIPES_AS_CONCAT'`을 설정합니다.** 가장 간단하지만 세션이나 사용자 단위로 빠짐없이 적용되는지 확인해야 합니다.
2. **`||`를 `concat()`으로 모두 바꿉니다.** 양쪽에서 같은 의미이므로 가장 안전합니다.
3. **이전 전에 전수 검색합니다.** 쿼리 저장소에서 `||`를 찾아 목록을 만듭니다. **이 항목만은 자동 검증이 불가능하므로 목록이 필요합니다.**

## 3. 2순위: 이름이 대응되는데 값이 다른 함수

```sql
SELECT approx_distinct(l_orderkey) FROM lineitem;
```

| 설정 | 결과 |
|---|---|
| Trino 483 | **15,432** |
| StarRocks 기본 | 오류 (`No matching function`) |
| StarRocks `sql_dialect='trino'` | **15,022**, 컬럼명이 `approx_count_distinct(...)`로 바뀝니다 |

**이름만 치환되고 알고리즘은 각자의 것입니다.** 근사 집계라 값이 2.7% 어긋났습니다. 참값은 15,000이고 Trino는 +2.9%, StarRocks는 +0.15% 오차입니다. 어느 쪽이 정확하다는 뜻이 아니라 **HLL과 Theta 스케치의 구현 차이**입니다.

**호환 모드의 커버리지 상한을 짚어 둡니다.** 이름 대응이 약 **100건** 손으로 등록되어 있습니다. StarRocks의 내장 함수가 637개이므로, **방언 모드의 함수 커버리지는 이 대응표의 크기가 상한입니다.**

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 내장 함수 수 (실측) | 442개 | **637개** |

**개수가 많은 것이 곧 유리한 것은 아닙니다.** 이전 방향에 따라 다르게 읽힙니다.

- **Trino에서 StarRocks로**: 이름이 대응되면 대체로 옮겨집니다. 다만 `approx_distinct`처럼 **이름이 다른데 의미가 비슷한** 함수가 함정입니다.
- **StarRocks에서 Trino로**: MySQL 계열 함수(`date_format`의 포맷 문자열 등)가 Trino에 없거나 규격이 달라 다시 써야 합니다. **대응 도구도 없습니다.**

즉 함수 개수는 **MySQL 생태계와의 거리**를 재는 값이지 표현력의 우열이 아닙니다.

## 4. 3순위: 시간대 타입은 값은 맞고 스키마가 좁아집니다

Trino로 테이블을 만들고 양쪽에서 스키마와 값을 읽었습니다.

```sql
CREATE TABLE bench.typeprobe (
  ts_ntz timestamp(6),
  ts_tz  timestamp(6) with time zone,
  d      decimal(38,4),
  u      uuid,
  b      varbinary
);
```

| 컬럼 | Trino `DESCRIBE` | StarRocks `DESC` |
|---|---|---|
| `ts_ntz` | `timestamp(6)` | `DATETIME` |
| `ts_tz` | `timestamp(6) with time zone` | **`DATETIME`** |
| `d` | `decimal(38,4)` | `DECIMAL(38,4)` |
| `u` | `uuid` | `VARBINARY` |
| `b` | `varbinary` | `VARBINARY` |

**`ts_ntz`와 `ts_tz`가 StarRocks에서 같은 이름이 됩니다.** 스키마만 보고는 어느 쪽이 시간대 보정 대상인지 알 수 없습니다.

**그러나 값의 의미는 지켜집니다.** 세션 `time_zone`만 바꿔 같은 행을 다시 읽었습니다.

| `time_zone` | `ts_ntz` | `ts_tz` |
|---|---|---|
| `Etc/UTC` | 2026-01-02 03:04:05.123456 | 2026-01-01 18:04:05.123456 |
| `Asia/Seoul` | 2026-01-02 03:04:05.123456 | **2026-01-02 03:04:05.123456** |

**`ts_tz`만 9시간 이동했습니다.** StarRocks는 Iceberg의 `adjust-to-UTC` 플래그를 읽기 경로에서 반영하고 있습니다.

**따라서 "StarRocks는 시간대를 잃는다"는 서술은 틀렸습니다.** 정확히 말하면 이렇습니다.

- **값은 맞습니다.**
- 그러나 **스키마로는 두 컬럼을 구분할 수 없습니다.**
- 그리고 StarRocks 쪽에서 테이블을 만들 때 **그 구분을 표현할 수단이 없습니다.**

**DECIMAL은 이 비교에서 유일하게 반대 방향인 항목입니다.** StarRocks가 76자리, Trino가 38자리입니다. 다만 Iceberg의 상한이 38이므로 **외부 테이블에서는 실익이 없습니다.**

## 5. 4순위: 프루닝이 아무 표시 없이 사라집니다

**이 항목은 결과가 맞는데 성능만 나빠지므로 가장 발견하기 어렵습니다.**

파티션 Iceberg 테이블(`orders` 15,000행, 80개월 파티션 = 80파일)에 같은 의미의 술어를 여러 모양으로 던졌습니다.

| 술어 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `o_orderdate >= '1995-01-01' AND < '1995-02-01'` | **165행 / 1파일** | **165행 / 1파일** |
| `year(o_orderdate) = 1995` | 2,204행 / 12파일 | **15,000행 / 80파일** |
| `date_trunc('month', o_orderdate) = '1995-01-01'` | 165행 / 1파일 | **15,000행 / 80파일** |
| `date_format(o_orderdate, '%Y-%m-%d')` 계열 | **15,000행 / 80파일** | 165행 / 1파일 |

**결과값은 모든 행에서 일치했습니다. 갈린 것은 읽은 양뿐입니다.**

**맨 앞 컬럼에 직접 걸린 술어는 완전히 동등합니다.** 함수가 끼면 갈리고, **방향이 서로 반대입니다.** StarRocks는 `year`와 `date_trunc`에서 프루닝하지 못하고, Trino는 문자열 포맷 함수에서 프루닝하지 못합니다. 어느 쪽도 상대의 상위집합이 아닙니다.

**대응 방법은 하나입니다. 날짜 함수로 감싸지 말고 범위 술어로 쓰는 것입니다.** `year(d) = 1995`보다 `d >= '1995-01-01' AND d < '1996-01-01'`이 양쪽 모두에서 프루닝됩니다.

**그리고 `EXPLAIN`으로 끝내면 안 됩니다.** 술어가 플랜에 찍혀 있어도 프루닝이 걸렸다는 뜻이 아닙니다. StarRocks에서는 프로파일을 켜고 `RawRowsRead`를 확인해야 합니다.

**측정 설계의 함정 두 개도 기록해 둡니다.** `count(*)`로 스캔량을 재면 StarRocks가 메타데이터만 읽고 끝내므로 비교가 성립하지 않습니다. 그리고 StarRocks의 `OutputRows`는 필터 통과 **후** 값이므로 Trino의 `Input rows`와 짝이 아닙니다. 올바른 짝은 `RawRowsRead`입니다.

## 6. 5순위: 예약어 99개

`SELECT 1 AS <word>`를 양쪽에 던졌습니다.

| 단어 | Trino | StarRocks |
|---|---|---|
| `text` / `key` / `json` / `range` / `partition` | 전부 통과합니다 | 전부 오류입니다 |

두 목록을 기계적으로 비교했습니다.

| | 개수 |
|---|---|
| Trino 예약어 | 83개 |
| StarRocks 예약어 | 155개 |
| **StarRocks에만 예약** (Trino에서는 식별자로 쓸 수 있습니다) | **99개** |
| Trino에만 예약 | 27개 |

**StarRocks에만 예약된 99개에 실무에서 컬럼명으로 흔한 단어가 대거 들어 있습니다.** 두 부류가 눈에 띕니다.

- **타입 이름 전체**입니다. `INT`, `VARCHAR`, `DECIMAL`, `JSON`, `TEXT`, `DOUBLE`, `ARRAY` 등입니다. **Trino는 타입 이름을 예약하지 않습니다.**
- **윈도우 함수 이름**입니다. `LAG`, `LEAD`, `ROW_NUMBER`, `DENSE_RANK`, `NTILE`, `FIRST_VALUE`, `LAST_VALUE`입니다.

반대로 Trino에만 예약된 27개는 ANSI 구문 키워드(`UNNEST`, `NATURAL`, `RECURSIVE`, `EXCEPT`, `ROLLUP`, `JSON_TABLE` 등)입니다. StarRocks가 그 구문을 지원하지 않거나 다르게 처리하기 때문에 예약할 필요가 없는 쪽에 가깝습니다.

**이 항목은 오류로 드러나므로 위험도가 낮습니다.** 다만 양이 많아서 이전 작업량에 직접 영향을 줍니다. 컬럼명에 백틱을 두르거나 이름을 바꾸어야 합니다.

## 7. 6순위: 상관 서브쿼리는 전수로 확인해야 합니다

**양쪽 모두 디코릴레이션에 실패하면 쿼리를 거부합니다.** "재작성 못 하면 행마다 돌린다"는 대안 경로가 양쪽 모두 없습니다. 15종을 던져 지원 매트릭스를 만들었습니다.

| 모양 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 스칼라 / EXISTS / NOT EXISTS / IN / NOT IN / 중첩 / OR / 윈도우 필터 (12종) | 가능합니다 | 가능합니다 |
| 상관 + `LIMIT 1` | 실패 | 실패 |
| **상관 + `ORDER BY … LIMIT 1`** | **가능합니다** | **실패** |
| **상관 EXISTS 안에 집계 + `HAVING`** | **실패** | **가능합니다** |

**15종 가운데 12종이 같고 1종은 공통으로 실패하며 2종이 정반대입니다.** 우열이 없습니다.

거부 메시지는 각각 `Given correlated subquery is not supported`와 `Not support the subquery!`입니다. **오류로 드러나므로 안전하지만, 어느 모양이 막히는지 미리 알 수 없으므로 전수 확인이 필요합니다.**

**의미론은 동등합니다.** 스칼라 서브쿼리가 여러 행을 돌려줄 때 양쪽 모두 실행 중에 오류를 냅니다. 대응 행이 없는 상관 `count`를 0으로 판정하는 것도 같고, 결과값도 같았습니다(15,000과 27,987).

**디코릴레이션 결과의 표현만 다릅니다.**

| 쿼리 | Trino | StarRocks |
|---|---|---|
| 상관 EXISTS | `InnerJoin` + 서브쿼리측 집계 | **`LEFT SEMI JOIN`** |
| 상관 NOT EXISTS | `LeftJoin` + 서브쿼리측 집계 | **`LEFT ANTI JOIN`** |
| 상관 NOT IN | `LeftJoin[filter = (… IS NULL OR …)]` | **`NULL AWARE LEFT ANTI JOIN`** |

**StarRocks는 semi/anti 전용 조인 연산자를 갖고 있고 Trino는 없습니다.** Trino는 outer join과 필터 조합으로 같은 의미를 만듭니다. **어느 쪽이 빠른지는 측정하지 않았습니다.**

### 7-1. 윈도우 함수는 쓰는 모양에 따라 유리한 엔진이 바뀝니다

| 쿼리 모양 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `row_number() <= 3` 필터 | `TopNRanking(limit 3)`, 윈도우가 사라집니다 | `PARTITION-TOP-N(3)` → 셔플 → `SORT` → `ANALYTIC` |
| `row_number() OVER(ORDER BY x)` + 바깥 `LIMIT 5` | **`TopNRanking(limit 5)`**, 전역 정렬이 없습니다 | **`SORT`(60,175행 전량)** → `ANALYTIC limit: 5` |
| `… ORDER BY rk LIMIT 5` | `TopN(5)` → **`Window`(전량)** → 스캔 | `TOP-N(5)` → `ANALYTIC` → **`TOP-N(5)`** → 스캔 |
| 같은 `PARTITION BY`/`ORDER BY` 윈도우 함수 2개 | **`Window` 노드 1개** | `ANALYTIC` 노드 2개 (정렬은 1개 공유) |

**두 번째와 세 번째가 정확히 뒤집혀 있습니다.** Trino는 맨 `LIMIT` 모양을, StarRocks는 `ORDER BY 순위컬럼 LIMIT` 모양을 최적화합니다.

**즉 같은 의미의 쿼리를 어떻게 쓰느냐에 따라 유리한 엔진이 바뀝니다.** 이전할 때 윈도우 쿼리는 플랜을 직접 확인하는 편이 안전합니다.

## 8. 7순위: UUID는 조회 시점에 실패합니다

```
ERROR 1064 (HY000): parquet column reader: not supported convert from parquet
`FIXED_LEN_BYTE_ARRAY` to `VARBINARY`: ... BE:10001
```

**`DESC`는 성공합니다.** `VARBINARY`라고 답합니다. **실패는 값을 읽을 때 납니다.**

원인을 좁히기 위해 같은 `VARBINARY`인 다른 컬럼(`X'0102'`)을 읽어 보았습니다. `hex(b) = 0102`로 정상입니다. 따라서 문제는 `VARBINARY`가 아니라 **Parquet `FIXED_LEN_BYTE_ARRAY`에서 `VARBINARY`로 가는 경로의 부재**입니다.

**이 유형은 FE와 BE가 서로 다른 표를 들고 있어서 생깁니다.** FE의 타입 변환기에는 매핑이 있는데 BE의 Parquet 리더에는 그 변환이 없습니다. 함수 등록은 `functions.py` 하나가 FE Java와 BE C++를 동시에 생성하므로 어긋날 수 없게 만들어 두었는데, **타입 매핑에는 그런 장치가 없습니다.**

**실행 항목**: StarRocks로 외부 레이크를 읽을 때는 **신규 테이블마다 전 컬럼 `SELECT`를 한 번 돌려야 합니다.** `DESC` 성공이 조회 성공을 보장하지 않습니다.

---

## 9. 양쪽이 같은 곳

**파서의 오류 처리 방식이 같습니다.** 양쪽 모두 SLL에서 LL로 넘어가는 2단계 방식을 씁니다. 빠른 경로로 먼저 파싱하고 실패하면 느리지만 정확한 경로로 다시 시도합니다.

**문법이 덮는 범위는 3배 다릅니다.**

| | 최상위 `statement` 분기 수 | 성격 |
|---|---|---|
| Trino `SqlBase.g4` | **91종** | 쿼리, DDL, 세션, 접근제어 |
| StarRocks `StarRocks.g4` | **249종** | 위 + 클러스터·적재·백업·플러그인 운영 전반 |

[SqlBase.g4](https://github.com/trinodb/trino/blob/483/core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4) · [StarRocks.g4](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocks.g4)

**StarRocks 문법이 넓은 것은 운영 명령을 SQL로 노출하기 때문입니다.** 적재, 백업, 리소스 그룹, 보안 통합이 전부 문법에 들어 있습니다. Trino는 그것들을 설정 파일과 플러그인에 둡니다.

**여기서 계획 단계의 전제 하나를 고쳤습니다.** 문법이 `core/trino-parser`에 있다고 적었는데, **483에서 `core/trino-grammar`로 분리되었습니다.**

---

## 10. 이전 작업 순서

위험도와 작업량을 함께 고려한 순서입니다.

1. **`||`를 전수 검색합니다.** `concat()`으로 바꾸거나 `sql_mode`를 설정합니다. **이 항목만은 자동 검증이 불가능합니다.**
2. **근사 집계 함수를 목록화합니다.** 값이 달라지므로 허용 오차를 정해야 합니다.
3. **날짜 함수로 감싼 술어를 범위 술어로 바꿉니다.** 양쪽 모두에서 프루닝됩니다.
4. **예약어 99개를 검색해 컬럼명을 확인합니다.** 오류로 드러나므로 기계적으로 처리할 수 있습니다.
5. **상관 서브쿼리와 윈도우 쿼리를 전수 실행합니다.** 계획 실패가 오류로 드러납니다.
6. **신규 테이블마다 전 컬럼 `SELECT`를 돌립니다.** 타입 지원 범위 이탈을 잡습니다.
7. **`timestamptz` 컬럼을 문서화합니다.** 값은 맞지만 스키마로 구분되지 않으므로 사람이 알고 있어야 합니다.

**호환 모드(`sql_dialect='trino'`)는 이전 작업을 줄여 주지만 대체하지 못합니다.** trino-parser 385 기준의 부분 지원이고 함수 대응표가 약 100건입니다. **이름만 옮기고 구현은 각자의 것을 쓰므로 값이 달라질 수 있습니다.**

## 11. 확인하지 못한 것

| 항목 | 이유 |
|---|---|
| 전체 함수 대응표 | 637개와 442개를 전수 대조하지 않았습니다. 실측은 `approx_distinct` 한 건입니다 |
| MySQL 방언 전수 검증 | 예약어는 기계 비교했으나 구문 차이는 표본 5개만 확인했습니다 |
| 호환 모드의 구문 커버리지 | 함수 대응표 크기(약 100건)는 셌지만 구문 지원 범위는 측정하지 않았습니다 |
| semi/anti 조인 연산자의 성능 | Trino의 outer join + 필터 조합과 비교하지 않았습니다 |
| 윈도우 최적화 차이의 실제 비용 | 플랜 모양만 대조했고 실행 시간은 재지 않았습니다 |
| StarRocks에서 Trino로 가는 방향 | 이 비교는 Trino에서 StarRocks로 가는 경로만 다뤘습니다. 역방향 도구는 없습니다 |
| 복합 타입의 이전 | `ARRAY`, `MAP`, `ROW`의 표기와 함수 차이를 확인하지 않았습니다 |

**이 글의 결론은 "확인해야 할 목록"까지입니다.** 각 항목이 실제 쿼리 집합에서 몇 건 걸릴지는 그 쿼리 집합을 보아야 알 수 있습니다.
