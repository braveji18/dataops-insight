# 경계를 만든 값은 얼마인가: 커넥터와 확장성

> 비교 기준: Trino **483** (`50b0b50b`) · StarRocks **4.0.14** (`7c18dd9d`) · 2026-10-16 기준
> 랩 구성: 같은 Iceberg 카탈로그, Trino worker 1대 / StarRocks BE 1대, TPC-H SF 0.01
> 다루지 않는 것: 커넥터를 직접 만들어 보는 것, 연합 질의 실측(카탈로그가 하나뿐이었습니다), 실행 시간 비교

## 결론부터

**경계를 만든 값은 세 가지로 돌아왔습니다.** 붙일 수 있는 데이터 소스의 수(27종 대 10종), Iceberg를 고쳐 쓸 수 있는 능력, 그리고 결함이 미치는 범위입니다.

**그리고 치른 비용도 분명합니다.** 커넥터마다 능력이 달라서 "커넥터가 있다"가 "잘 동작한다"를 뜻하지 않습니다. 푸시다운 협상 메서드를 11종 두었지만 `applyFilter`를 구현한 커넥터가 18개, `applyAggregation`은 3개, `applyJoin`은 1개입니다.

**읽기 경로는 대등했습니다.** 같은 Iceberg 테이블에서 복합 타입과 압축 코덱 4종, 삭제 파일까지 결과가 전부 일치했습니다. 파티션 프루닝도 맨 앞 컬럼 술어에서는 165행과 1파일로 완전히 같았습니다. **갈린 것은 쓰기와, 함수가 끼었을 때의 프루닝, 그리고 결함이 났을 때입니다.**

## 2. 경계가 코드에 있는 모습

### 2-1. 확장점이 16종인 쪽과 3종인 쪽

Trino의 `core/trino-spi`는 파일 **558개, 73,858줄**짜리 독립 모듈입니다. 커넥터 개발자는 이 모듈만 의존하고 엔진 본체를 참조하지 않습니다. 확장점은 커넥터만이 아닙니다.

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 확장점 수 | **16종** | **3종** (그중 구현된 것은 1종) |
| 확장점 위치 | 별도 모듈 (`trino-spi`) | 엔진 코드 안 |
| 배포 단위 | 플러그인 JAR | 없습니다. 엔진 빌드에 포함됩니다 |
| 안정성 계약 | `@Unstable` 애노테이션 26곳 + 플러그인 검증 도구 | 없습니다 (필요가 없습니다) |
| 제3자 확장 | 가능합니다 | 사실상 포크가 필요합니다 |

Trino는 데이터와 표현, 계산, 보안, 운영, 실행 기반을 전부 열었습니다. **`plugin/` 아래에 플러그인이 61개 있고 그중 커넥터가 28개입니다.** 나머지는 이벤트 리스너, 접근 제어, 인증, 리소스 그룹, 함수, 교환 관리자입니다. 즉 "커넥터 SPI"가 아니라 "플러그인 SPI"입니다.

StarRocks도 플러그인 메커니즘 자체는 갖추었습니다. 동적 로딩과 클래스로더 격리까지 있습니다. **범위가 좁을 뿐입니다.** 감사와 적재, 저장 세 종류이고 구현된 것은 감사 하나입니다.

**StarRocks에 이 계층이 없는 것은 결함이 아니라 필요가 없기 때문입니다.** 외부 코드가 붙을 자리가 없으니 내부 구조를 자유롭게 바꿀 수 있습니다. **이것은 장점이기도 합니다.** LLVM JIT이나 벡터 인덱스 같은 것을 만들려면 내부를 크게 흔들어야 합니다.

### 2-2. 커넥터를 추가하려면 몇 곳을 고쳐야 하는가

Trino에서 커넥터가 구현할 것은 인터페이스 넷이고, `ConnectorMetadata`가 1,866줄로 가장 크지만 **대부분이 `default` 구현**입니다. `applyFilter`와 `createMaterializedView`, `getTableStatistics`가 모두 "지원하지 않음"을 돌려주는 기본 구현을 가지고 있습니다. **최소 구현은 아주 작고, 능력을 더 신고할수록 최적화가 늘어납니다.**

StarRocks는 **붙일 수 있는 소스가 열거형에 적혀 있습니다.**

```java
// fe/fe-core/src/main/java/com/starrocks/connector/ConnectorType.java#L36-L45 @ 4.0.14
    ES("es", ElasticsearchConnector.class, EsConfig.class),
    HIVE("hive", HiveConnector.class, null),
    ICEBERG("iceberg", IcebergConnector.class, null),
    JDBC("jdbc", JDBCConnector.class, null),
    HUDI("hudi", HudiConnector.class, null),
    DELTALAKE("deltalake", DeltaLakeConnector.class, null),
    PAIMON("paimon", PaimonConnector.class, null),
    ODPS("odps", OdpsConnector.class, null),
    KUDU("kudu", KuduConnector.class, null),
    UNIFIED("unified", UnifiedConnector.class, null);
```

[ConnectorType.java#L36-L45](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/connector/ConnectorType.java#L36-L45)

**10종이고 플러그인을 떨어뜨려 넣는 경로가 없습니다.** 새로 붙이려면 네 곳을 함께 고쳐야 합니다.

1. FE의 `ConnectorType` 열거형과 커넥터 구현(Java)
2. FE의 논리·물리 스캔 오퍼레이터
3. **Thrift 프로토콜 정의**(`gensrc/thrift/PlanNodes.thrift`의 스캔 노드 열거)
4. BE의 `DataSourceProvider` / `DataSource` 구현(C++)

```cpp
// be/src/connector/connector.h#L126-L137 @ 4.0.14
class DataSourceProvider {
...
    virtual DataSourcePtr create_data_source(const TScanRange& scan_range) = 0;
```

[connector.h#L126-L137](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/connector/connector.h#L126-L137)

248줄짜리 헤더입니다. **Trino의 `ConnectorPageSourceProvider`(83줄)에 대응하는 위치이고 크기도 비슷합니다. 문제는 크기가 아니라 여기가 엔진 코드 안이라는 점입니다.**

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 건드려야 할 언어 | **Java 하나** | **Java + C++ + Thrift** |
| 건드려야 할 프로세스 | 없습니다 (플러그인 로딩입니다) | **FE + BE** |
| 성능 최적화 신고 | 선택적입니다 (구현할수록 좋아집니다) | 신고 개념이 없습니다. 엔진이 판단합니다 |

### 2-3. 기여 난이도가 경계선 하나로 갈립니다

| 하고 싶은 일 | Trino | StarRocks |
|---|---|---|
| 커넥터 추가 | `trino-spi`만, 플러그인 JAR | 열거형 + FE + BE + Thrift |
| 스칼라 함수 추가 | **애노테이션 붙은 Java 메서드**, 플러그인 가능합니다 | `functions.py` ID 부여 + BE C++ + 양쪽 재빌드 |
| 타입 추가 | `trino-spi`의 `Type` | `PrimitiveType` 열거형 + BE C++ 짝 |
| 접근제어 정책 | SPI | 내부 구현 또는 Ranger |
| 관측 대상 추가 | `EventListener` SPI | `AuditPlugin`(감사 한정) |
| 셔플 저장소 교체 | `ExchangeManager` SPI | 불가능합니다 |
| 리소스 그룹 정책 | SPI | 불가능합니다 (SQL 객체로 고정되어 있습니다) |
| 옵티마이저 규칙 추가 | 코어 수정 | 코어 수정 |
| 실행 연산자 추가 | 코어 수정 | **FE + BE 코어 수정** |

**경계가 분명합니다.** Trino에서 "SPI로 되는가"의 답이 예이면 **엔진을 몰라도 됩니다.** 아니면 `core/` 567,770줄을 상대해야 합니다. StarRocks에서는 거의 모든 항목이 코어 수정이고, 그것은 곧 FE(Java)와 BE(C++) 양쪽에 코드 생성과 이중 빌드를 뜻합니다.

### 2-4. 규모가 그 구조를 그대로 보여줍니다

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 본체 규모 | 1,169,458줄 (Java) | **1,388,866줄** (FE 755,539 + BE 633,327) |
| 최상위 디렉토리 | 7개 | **20개** |
| 코드 분포 | core 55% / **plugin 30%** / lib 15% | FE 54% / BE 46% |
| 테스트 비중 | **71%** | FE 63% / **BE 47%** |

**StarRocks가 19% 큰 이유는 더 많은 일을 하기 때문입니다.** 스토리지 엔진, 적재 파이프라인, compaction, 리소스 스케줄러, 메타데이터 복제가 전부 Trino에 없는 것입니다. 반대로 Trino는 커넥터 27개와 파일 리더 두 벌을 갖고 있고 그것이 44%입니다. **즉 규모 비교는 "누가 더 복잡한가"가 아니라 "어디까지를 제품으로 보는가"의 반영입니다.**

**플러그인이 30%라는 것은 코어 팀이 그 전부를 유지보수하지 않아도 된다는 뜻**이기도 하고, **동시에 위험**이기도 합니다. 커넥터마다 푸시다운 구현 범위가 크게 다른 것이 그 결과입니다.

**BE 테스트 비중 47%는 기록할 값어치가 있는 대조입니다.** BE는 결함의 대가가 가장 크고(프로세스 사망), 언어가 C++이라 실수의 여지가 가장 큰데, 테스트 비중은 가장 낮습니다. **인과를 주장하지는 않습니다.** C++ 테스트는 Java보다 줄당 밀도가 높을 수 있고 SQL regression이 BE를 간접 검증하기도 합니다.

## 3. 측정 결과: 읽기는 대등합니다

환경: macOS arm64 Docker Desktop 14 CPU / 25GB, `functional` 프로파일, TPC-H SF 0.01.

### 3-1. 파일 리더 호환성이 전부 일치했습니다

복합 타입, 압축 코덱 4종, Iceberg 삭제 파일을 왕복시켰습니다. **결과가 전부 일치했습니다.** 서로 다른 언어의 독립 구현치고는 상호운용이 잘 지켜지고 있습니다.

읽기 리더를 직접 쓴 것도 양쪽이 같은 판단입니다. Trino는 parquet-mr을 쓰지 않았고(자체 36,255줄), StarRocks는 Arrow를 읽기에 쓰지 않았습니다(자체 16,569줄). **이유도 같습니다.** 읽기가 성능의 주 경로이고, 범용 라이브러리는 각 엔진의 메모리 표현(`Block`과 `Column`)으로 직접 채워 넣지 못하기 때문입니다. 갈린 것은 ORC뿐입니다. StarRocks는 Apache ORC C++를 감쌌습니다.

### 3-2. 파티션 프루닝: 맨 앞 컬럼이면 완전히 같습니다

| 술어 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 없음 (기준선) | 15,000행 / 80파일 | 15,000행 / 80파일 |
| `o_orderdate >= '1995-01-01' AND < '1995-02-01'` | **165행 / 1파일** | **165행 / 1파일** |
| `year(o_orderdate) = 1995` | **2,204행 / 12파일** | 15,000행 / 80파일 (실패) |
| `date_trunc('month', o_orderdate) = '1995-01-01'` | **165행 / 1파일** | 15,000행 / 80파일 (실패) |
| 문자열 포맷 함수 (`date_format` 계열) | 15,000행 / 80파일 (실패) | **165행 / 1파일** |
| `o_orderkey < 1000` (비파티션) | 14,269행 / **75파일** | 14,269행 / **80파일** |

**결과값은 모든 행에서 일치했습니다. 갈린 것은 읽은 양뿐입니다.**

**함수가 끼면 갈리고 방향이 서로 반대입니다.** StarRocks는 `year`와 `date_trunc`에서 프루닝하지 못하고, Trino는 문자열 포맷 함수에서 프루닝하지 못합니다. **어느 쪽도 상대의 상위집합이 아닙니다.**

**그리고 이 측정이 코드만 읽고 내린 판단을 뒤집었습니다.** 처음에는 "StarRocks 커넥터는 함수 술어를 밀어 내리지 못한다"고 적었습니다. 그런데 `date_format`에서는 165행과 1파일로 맨 앞 컬럼과 완전히 같은 결과를 냅니다. **커넥터가 못 하는 것이 아니라 옵티마이저가 함수를 벗겨 주지 않으면 못 하는 것이고, 벗겨 주는 함수 목록이 다를 뿐입니다.**

마지막 행은 제거 시점의 차이입니다. Trino는 매니페스트 통계로 5개 파일을 계획 시점에 뺐고, StarRocks는 80개를 전부 스케줄한 뒤 리더 안에서 걸렀습니다. **읽은 행이 같으므로 결과는 동등합니다.** 파일이 수만 개인 환경에서는 스케줄링 비용 차이가 생길 수 있으나 측정하지 않았습니다.

**측정 설계의 함정 두 개를 기록해 둡니다.** 첫째로 `count(*)`를 쓰면 안 됩니다. StarRocks가 메타데이터만 읽고 끝냅니다. 둘째로 StarRocks의 `OutputRows`는 필터 통과 **후** 값이므로 Trino의 `Input rows`(필터 이전)와 짝이 아닙니다. 올바른 짝은 `RawRowsRead`입니다. **초안에서 이것을 혼동해 "15,000 대 255"라는 잘못된 표를 만들 뻔했습니다.**

## 4. 측정 결과: 쓰기에서 갈립니다

Trino로 만든 Iceberg 테이블 하나에 양쪽에서 번갈아 문장을 던졌습니다.

### 4-1. DML

| 문장 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `INSERT INTO ... SELECT` | 성공합니다 | 성공합니다 |
| `CREATE TABLE ... AS SELECT` | 성공합니다 | 성공합니다 |
| `UPDATE ... SET ... WHERE` | 성공합니다 | 실패: `table w1 does not support update` |
| `DELETE FROM ... WHERE` | 성공합니다 | 실패: `Table of iceberg catalog doesn't support [DELETE]` |
| `MERGE INTO ...` | 성공합니다 | 실패: 구문 오류 |

**StarRocks는 Iceberg에 `INSERT`와 CTAS만 가능합니다.** 삭제 파일을 **읽을 수는 있으나 쓰지 못합니다.** 유지보수 명령도 없습니다. Trino는 파일 병합과 스냅샷 만료, 고아 파일 제거를 프로시저 8종으로 노출합니다.

**거부 방식이 셋 다 제각각이라는 점도 기록해 둡니다.** `DELETE`는 카탈로그 이름 하드코딩으로, `UPDATE`는 테이블 능력 질의로, `MERGE`는 문법 부재로 막힙니다. 설계가 아니라 누적으로 보입니다.

### 4-2. 스키마 진화와 시간 여행은 동등하고 상호운용됩니다

| 문장 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `ADD` / `DROP` / `RENAME COLUMN` | 성공합니다 | 성공합니다 |
| `FOR VERSION AS OF <snapshot_id>` | 25행 | 25행 |
| 메타데이터 테이블 (`$snapshots`) | 7개 | 7개 |

**교차 확인이 이 절의 요점입니다.** StarRocks로 `n_name`을 `n_nm`으로, Trino로 `n_comment`를 `n_cmt`로 각각 바꾼 뒤 양쪽에서 스키마를 읽었습니다.

| | 결과 |
|---|---|
| Trino `DESCRIBE` | `n_nationkey, n_nm, n_regionkey, n_cmt` |
| StarRocks `DESC` | `n_nationkey, n_nm, n_regionkey, n_cmt` |

**서로가 바꾼 것을 서로가 봅니다.** Iceberg 메타데이터를 통한 스키마 진화 상호운용이 실제로 동작합니다.

### 4-3. 격차의 원인은 제품의 무게중심입니다

**Trino에게 Iceberg는 유일한 저장 수단입니다.** 스토리지가 없으니 "Trino로 데이터를 고친다"는 곧 "Iceberg를 고친다"입니다. 그래서 MERGE를 SPI 원시 연산으로 두고 유지보수까지 SQL로 노출했습니다.

**StarRocks에게 Iceberg는 읽어 오는 곳입니다.** 무게중심은 네이티브 테이블에 있고, 거기에는 `PRIMARY KEY` 모델과 compaction, 트랜잭션이 다 있습니다([5편](05-스토리지-한쪽에만-있는-계층.md)). 외부 Iceberg에 `UPDATE`를 붙일 유인이 상대적으로 약합니다.

**MV 재작성에서 본 구도의 거울상입니다.** 그쪽은 StarRocks가 자기 스토리지를 소유하기 때문에 압도적으로 앞섰고, 여기서는 **같은 이유로 뒤집니다.**

## 5. 결함이 났을 때의 범위

### 5-1. 같은 결함이 다른 크기의 피해를 냅니다

| | 리더 결함 하나가 미치는 범위 |
|---|---|
| Trino | 그 쿼리 하나입니다. 워커는 다음 쿼리를 정상 처리합니다 |
| StarRocks | **BE 프로세스 전체입니다.** 그 BE가 처리 중이던 다른 모든 쿼리가 함께 죽고, 그 BE의 로컬 데이터도 잠시 접근할 수 없게 됩니다 |

이 연구 과정에서 실제로 겪은 일입니다. StarRocks 4.0.1 BE는 Trino가 쓴 Iceberg Parquet의 DATE 컬럼에 술어를 걸면 row-group zone-map 필터 경로에서 SIGSEGV로 죽었습니다. 그래서 비교 버전을 4.0.14로 올렸습니다.

**StarRocks 쪽 피해가 더 큰 이유는 언어 때문만이 아닙니다.** BE는 스토리지도 함께 들고 있습니다. Trino 워커는 상태가 없어 죽어도 다시 띄우면 그만이지만, StarRocks BE는 태블릿을 들고 있으므로 사망의 의미가 다릅니다.

**공정하게 볼 점이 있습니다.** 이 위험은 발생했을 때의 크기이지 발생 확률이 아닙니다. 3-1의 실측에서 정상 경로는 전부 동등했고, 4.0.1의 결함은 4.0.14에서 고쳐졌습니다. **"StarRocks 리더가 불안정하다"는 결론은 이 자료로 지지되지 않습니다.** 지지되는 것은 "같은 확률의 결함이 더 큰 피해를 낳는다"입니다.

### 5-2. 지원 범위 이탈이 늦게 드러납니다

Iceberg `UUID` 컬럼에서 **`DESC`는 성공하고 조회에서 실패합니다.** FE와 BE가 서로 다른 표를 들고 있기 때문입니다. FE의 타입 변환기는 `UUID`를 `VARBINARY`로 매핑하는데, BE의 Parquet 리더에는 그 변환이 없습니다.

함수 등록 구조와 대비됩니다. 함수는 `functions.py` 하나가 FE Java와 BE C++를 **동시에** 생성하므로 어긋날 수 없게 만들어 두었는데, **타입 매핑에는 그런 장치가 없습니다.**

Trino에는 이 실패 유형이 구조적으로 생기기 어렵습니다. 타입 매핑과 리더가 같은 JVM 안, 같은 저장소, 같은 빌드에 있습니다.

**실행 항목**: StarRocks로 외부 레이크를 읽을 때는 **컬럼 단위 조회 확인이 필요합니다.** `DESC` 성공은 조회 성공을 보장하지 않습니다. 신규 테이블을 붙일 때 전 컬럼 `SELECT`를 한 번 돌려 보는 절차를 권합니다.

## 6. 다양성과 그 대가

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 커넥터 수 | **27종** (+ JDBC 계열 15종) | **10종** (열거형) |
| 레이크 포맷 | hive / iceberg / delta / hudi / lakehouse | **+ Paimon** |
| 관계형 DB | **15종**, 방언별 최적화 | 1종, 공용 화이트리스트 |
| 관측 데이터 | prometheus, loki, jmx | 없습니다 |
| SaaS | bigquery, google-sheets, snowflake | ODPS |
| 스트리밍 읽기 | kafka | 없습니다 |

**레이크 포맷은 StarRocks가 오히려 촘촘합니다**(Paimon). 그 밖의 모든 갈래에서 Trino가 넓고, **관계형 데이터베이스는 15 대 1**입니다. 방언별 푸시다운 최적화까지 감안하면 격차가 개수 비율보다 큽니다.

### 6-1. 왜 개수가 벌어졌는가

**SPI가 있으니 코어 팀이 아닌 사람도 만들 수 있었습니다.** `loki`(로그 집계), `faker`(테스트 데이터 생성), `ai-functions`, `datasketches` 같은 커넥터는 **코어 로드맵에서 나올 만한 것이 아닙니다.** 필요한 사람이 만들어 넣은 것입니다. StarRocks의 10종은 전부 "분석 대상이 될 만한 데이터 저장소"이고, 로드맵에서 나온 목록의 모양입니다.

### 6-2. 다양성의 대가

**커넥터마다 능력이 다릅니다.** `applyFilter`는 18개가 구현했지만 `applyAggregation`은 3개, `applyJoin`은 1개(JDBC 공용)입니다.

**즉 "커넥터가 있다"가 "잘 동작한다"를 뜻하지 않습니다.** 사용자는 쓰려는 커넥터의 실제 구현 범위를 확인해야 하고, 그 정보는 커넥터 문서에 흩어져 있습니다.

StarRocks는 10종에서 동작이 일관됩니다. 엔진이 전부 처리하므로 커넥터에 따라 달라질 여지가 적습니다.

### 6-3. 그리고 이 축의 무게는 요건에 따라 0이 됩니다

**연합 질의가 요건이면 Trino 외에 선택지가 없습니다. 요건이 아니면 이 축의 격차는 의미가 없습니다.** Iceberg만 본다면 커넥터 27개는 아무 이득이 아닙니다.

## 7. 언제 무엇을 고를까

| 상황 | 선택 | 이유 |
|---|---|---|
| 서로 다른 시스템을 한 쿼리로 조인합니다 | **Trino** | 27종 대 10종이고 대체 수단이 없습니다 |
| 관계형 데이터베이스를 자주 조인합니다 | **Trino** | 15 대 1이고 방언별 최적화까지 있습니다 |
| Iceberg를 고쳐 써야 합니다 (CDC upsert, 개인정보 삭제) | **Trino** | StarRocks는 `UPDATE`·`DELETE`·`MERGE`가 전부 막혀 있습니다 |
| Iceberg 파일 정리가 필요합니다 | **Trino** | 유지보수 프로시저 8종 대 0종입니다 |
| 커넥터를 직접 만들어야 합니다 | **Trino** | StarRocks는 upstream 기여 외에 길이 없습니다 |
| 사내 전용 함수와 타입이 많습니다 | **Trino** | 애노테이션 하나와 플러그인 JAR로 끝납니다 |
| 결함의 파급을 줄여야 합니다 | **Trino** | 리더 결함이 쿼리 하나로 끝납니다 |
| 데이터 소스가 고정되어 있고 성능을 최대로 뽑아야 합니다 | **StarRocks** | 10종에서 동작이 일관되고 엔진이 전부 최적화합니다 |
| 커넥터 품질 편차를 감당할 인력이 없습니다 | **StarRocks** | 커넥터마다 능력을 확인할 필요가 없습니다 |
| Paimon을 읽어야 합니다 | **StarRocks** | 레이크 포맷은 이쪽이 촘촘합니다 |

### 두 엔진을 함께 쓸 때의 쓰기 역할 분담

| 작업 | 가능한 엔진 |
|---|---|
| 적재(append), 테이블 생성, 스키마 변경 | 양쪽입니다 |
| 조회, 시간 여행 | 양쪽입니다 |
| **행 수정과 삭제, MERGE upsert** | **Trino만 가능합니다** |
| **파일 병합, 스냅샷 만료, 고아 파일 제거** | **Trino만 가능합니다** |

**StarRocks만 두고 Iceberg를 운영할 수는 없습니다.** 쓰기가 반복되면 작은 파일이 쌓이는데 정리할 수단이 없습니다. 정리를 Spark나 Flink 같은 다른 도구에 맡기든지, Trino를 함께 두든지 해야 합니다.

**반대로 StarRocks를 조회 가속기로 두는 구성은 자연스럽습니다.** 읽기는 전부 동등하고, 그 위에 MV 재작성과 자동 통계 같은 StarRocks의 강점이 얹힙니다.

## 8. 확인하지 못한 것

| 항목 | 이유 |
|---|---|
| **실제 커넥터 개발 난이도** | 새 커넥터를 만들어 보지 않았습니다. **줄 수와 건드릴 곳의 수는 대리 지표일 뿐입니다** |
| 플러그인 개발 | 플러그인을 만들어 보지 않았습니다 |
| SPI 버전 호환성 정책의 실제 강도 | `@Unstable`이 26곳에 있다는 것은 알지만 릴리스 간 실제 변경 빈도를 보지 않았습니다(얕은 클론입니다) |
| 플러그인 품질 편차 | 61개 가운데 어느 것이 잘 관리되는지 판단할 근거가 없습니다 |
| 연합 질의 | 카탈로그가 Iceberg 하나뿐이었습니다 |
| 커밋 활동과 릴리스 주기 | 얕은 클론이라 이력이 없습니다 |
| 파일이 수만 개일 때의 스케줄링 비용 | 3-2의 75파일 대 80파일 차이가 실제로 영향을 주는 규모를 측정하지 않았습니다 |
| StarRocks 4.0.1 SIGSEGV의 재현 조건 | arm64 한정인지 확인하지 못했습니다. 두 버전 이미지를 함께 둘 디스크 여유가 없었습니다 |
| BE 테스트 비중 47%의 의미 | 2-4에서 인과를 주장하지 않았습니다. SQL regression의 간접 커버리지를 평가하지 못했습니다 |

**이 글에서 코드만 읽고 내린 판단이 한 번 뒤집혔습니다.** "StarRocks 커넥터는 함수 술어를 밀어 내리지 못한다"고 적었으나 `date_format`에서는 완전히 프루닝했습니다(3-2). 원인은 커넥터가 아니라 옵티마이저 규칙이 다루는 함수의 범위였습니다.
