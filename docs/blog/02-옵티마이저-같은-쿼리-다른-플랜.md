# 같은 쿼리에 다른 플랜이 나옵니다: 두 옵티마이저를 코드와 실측으로 비교했습니다

> 비교 기준: Trino **483** (`50b0b50b`) · StarRocks **4.0.14** (`7c18dd9d`) · 2026-10-16 기준
> 랩 구성: 같은 Iceberg 카탈로그(Hive Metastore 4.0.1 + MinIO), Trino worker 1대 / StarRocks BE 1대, TPC-H SF 0.01
> 다루지 않는 것: 실행 시간 비교, 다중 노드 셔플, 버킷팅된 테이블의 조인
> 시리즈: [1편 · 전체 결론](01-스토리지를-소유하는가.md)

## 결론부터

**조인이 8개 이하이고 통계를 직접 관리할 수 있다면 두 옵티마이저는 같은 플랜을 만듭니다. 갈리는 지점은 세 곳입니다.** 조인이 9개를 넘어가는 구간, 통계가 부실한 상태, 그리고 반복 집계를 미리 계산해 둔 경우입니다.

- **조인 9개 이상**: StarRocks만 순서를 재배치합니다. Trino는 평탄화를 멈춰 작성된 순서를 그대로 씁니다.
- **통계가 부실할 때**: Trino는 리오더를 포기하고, StarRocks는 left-deep 재배치까지는 합니다.
- **MV 재작성**: StarRocks는 전용 코드 18,000줄을 갖추었고 Trino에는 규칙이 하나도 없습니다.

나머지는 대부분 대등했습니다. 6테이블 조인 쿼리에서 두 엔진이 **완전히 같은 조인 트리**를 만들었고, 플랜 내부 푸시다운은 실측 6항목이 전부 동등했습니다.

## 1. 비교 범위와 버전

TPC-H Q5 형태의 6테이블 쿼리(inner 조인 5개)를 두 엔진에 같은 문자열로 넣고, 플랜과 중간 카디널리티 추정을 대조했습니다. 설정값을 한 번에 하나만 움직여 플랜이 바뀌는 지점을 찾는 방식입니다.

| 항목 | 내용 |
|---|---|
| 비교 대상 | Trino 483 / StarRocks 4.0.14 |
| 측정 환경 | macOS arm64, Docker Desktop 14 CPU / 25GB, `functional` 프로파일 |
| 데이터 | TPC-H SF 0.01, `bench.lineitem` 60,175행, Iceberg 외부 테이블 |
| 비교 방법 | `EXPLAIN` / `EXPLAIN COSTS` / `EXPLAIN VERBOSE` 대조, 세션 변수 단일 변경 |

**한 가지 한정을 먼저 밝힙니다.** 랩 테이블이 모두 Iceberg이므로 StarRocks 쪽에서는 **스캔 연산자의 비용이 0으로 계산됩니다.** `CostModel`이 `visitPhysicalIcebergScan`을 재정의하지 않기 때문입니다. 따라서 "두 비용 모델을 같은 조건에서 비교했다"고 말할 수 없습니다. 조인 순서에 미치는 영향은 제한적이라고 볼 근거가 있지만(스캔 비용은 순서와 무관하게 상수에 가깝습니다), 해석할 때 감안해야 합니다.

## 2. 두 옵티마이저의 구조

**Trino는 판단을 파이프라인의 독립된 칸에 모아 둡니다.** 조인 리오더는 `IterativeOptimizer`가 돌리는 규칙 하나이고, `PlanOptimizers`가 이 최적화기를 **43번** 생성합니다. 규칙은 `iterative/rule/` 아래에 **232개**가 있습니다. 조인 리오더 규칙에는 `// Because ReorderJoins runs only once,`라는 주석이 붙어 있습니다. 한 번만 돕니다.

**StarRocks는 Cascades 구조이고 판단을 탐색 안에 녹입니다.** `Memo`와 `GroupExpression`, 태스크 기반 탐색(`OptimizeGroupTask`, `EnforceAndCostTask`)으로 이루어집니다. 조인 분배 방식을 정하는 전용 규칙이 없고, 비용 계산 태스크 안에서 물리 속성으로 결정됩니다.

이 구도가 축마다 반복해서 나타났습니다. 전자는 읽고 추적하기 쉽고, 후자는 다른 결정과 함께 비용으로 저울질됩니다.

## 3. 핵심 동작 비교

### 3-1. 조인 순서: 한도 하나 대 4단계 전환

Trino는 **부분집합 분할 전수 열거**를 합니다. `generatePartitions()`가 `powerSet`으로 모든 이분할을 만들고, 0번 원소를 포함하는 부분집합만 남겨 대칭 중복을 제거합니다. 재귀적으로 하위 그룹에도 같은 열거를 적용하므로 **bushy 트리가 자연스럽게 나옵니다.** left-deep으로 제한하지 않습니다.

자르는 지점은 **개수 한도 하나**입니다.

```java
// core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L51 @ 483
private int maxReorderedJoins = 8;
```

[OptimizerConfig.java#L51](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L51)

한도를 넘으면 조인 트리를 평탄화하지 않고 넘는 부분을 원래 순서로 남깁니다. 한도 이하에서 탐색 강도를 낮추는 중간 단계는 없습니다. 시간 안전장치는 `optimizer_timeout`이 별도로 담당하며, 초과하면 플랜을 포기하고 예외를 던집니다.

StarRocks는 **조인 개수를 세어 경로를 가릅니다.**

```java
// fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L956-L972 @ 4.0.14
int innerCrossJoinNode = Utils.countJoinNodeSize(tree, JoinOperator.innerCrossJoinSet());
if (!sessionVariable.isDisableJoinReorder() && innerCrossJoinNode < sessionVariable.getCboMaxReorderNode()) {
    if (innerCrossJoinNode > sessionVariable.getCboMaxReorderNodeUseExhaustive()) {
        new ReorderJoinRule().transform(tree, context);              // 휴리스틱 경로
        context.getRuleSet().addJoinCommutativityWithoutInnerRule();
    } else {
        context.getRuleSet().addJoinTransformationRules();           // memo 전수 탐색 경로
    }
}
```

[QueryOptimizer.java#L955-L973](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L955-L973)

휴리스틱 경로에서는 알고리즘 셋을 **동시에 후보로** 넣습니다. Left-deep은 항상, DP는 테이블 10개 이하일 때, Greedy는 16개 이하일 때 들어가고, 세 결과를 모두 memo에 넣어 비용으로 고릅니다. 하나를 고르는 것이 아니라 후보를 늘리는 구조입니다. DP의 기본값 10에는 근거가 주석으로 붙어 있습니다. `// 10 table join reorder takes more than 100ms`입니다.

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 전수 탐색 한계 | 조인 **8개** | 조인 **4개** |
| 리오더 가능 최대 | 8개 (넘으면 평탄화 중단) | **50개** (그 사이는 휴리스틱) |
| 탐색 방식 | DP 전수 열거 단일 | 규모별 4단계 전환 |
| outer join 재배치 | 하지 않습니다 (`INNER`만 적용) | 합니다 (`enable_outer_join_reorder` 기본 true) |

**기준값의 단위가 섞여 있다는 점을 짚어 둡니다.** StarRocks의 `4`와 `50`은 **조인 노드 개수**이고, `10`과 `16`은 **테이블(atom) 개수**입니다. 테이블 수로 환산하면 단계가 `≤5 / 6~10 / 11~16 / 17~50 / ≥51`이 됩니다. 같은 파일 안에서 두 단위가 섞이므로 설정값을 조정할 때 혼동하기 쉽습니다.

### 3-2. 통계가 없을 때: 포기하는 쪽과 최소한을 하는 쪽

StarRocks는 통계가 없는 컬럼이 하나라도 있으면 DP와 greedy를 건너뜁니다.

```java
// fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/join/ReorderJoinRule.java#L250-L253 @ 4.0.14
// If there is no statistical information, the DP and greedy reorder algorithm are disabled,
// and the query plan degenerates to the left deep tree
if (Utils.hasUnknownColumnsStats(innerJoinRoot) && ...) { continue; }
```

[ReorderJoinRule.java#L247-L267](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/join/ReorderJoinRule.java#L247-L267)

Trino에도 대응하는 분기가 있지만 **행동이 다릅니다.** 열거 도중 비용을 알 수 없는 분할이 하나라도 나오면 그 그룹 전체에 `UNKNOWN_COST_RESULT`를 넣고 즉시 반환합니다. 그 결과 규칙이 발화하지 않고 **쿼리에 작성된 조인 순서가 그대로 남습니다.**

| 통계가 부실할 때 | 결과 |
|---|---|
| Trino | 리오더 **자체를 포기**합니다. 작성된 순서를 유지합니다 |
| StarRocks | DP와 greedy만 포기하고 **left-deep 재배치는 수행합니다** |

둘 다 "비용을 믿을 수 없으면 탐색하지 않는다"는 원칙은 같습니다. 다만 StarRocks는 그 상태에서도 최소한의 재배치를 하고 Trino는 손을 뗍니다.

### 3-3. 비용 모델: 4-튜플을 끝까지 들고 가는 쪽과 즉시 접는 쪽

Trino의 비용은 네 축입니다. `cpuCost`, `maxMemory`, `maxMemoryWhenOutputting`, `networkCost`입니다. 이 4-튜플은 끝까지 유지되고, **하나의 숫자로 접히는 곳은 비교 시점 한 곳뿐**입니다.

```java
// core/trino-main/src/main/java/io/trino/cost/CostComparator.java#L63-L69 @ 483
double leftCost = left.getCpuCost() * cpuWeight
        + left.getMaxMemory() * memoryWeight
        + left.getNetworkCost() * networkWeight;
```

[CostComparator.java#L63-L69](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/cost/CostComparator.java#L63-L69)

가중치는 `OptimizerConfig`에 **75 / 10 / 15**로 있고, 설정으로 바꿀 수 있습니다. 미상 성분이 있으면 `checkArgument`가 비교 자체를 거부합니다. 3-2의 "리오더 포기"가 여기서 나옵니다.

StarRocks의 비용은 세 축이고, **연산자 하나를 계산할 때마다 스칼라로 접힙니다.**

```java
// fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/CostModel.java#L129-L136 @ 4.0.14
public static double getRealCost(CostEstimate costEstimate) {
    double cpuCostWeight = 0.5;
    double memoryCostWeight = 2;
    double networkCostWeight = 1.5;
    ...
}
```

[CostModel.java#L129-L136](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/CostModel.java#L129-L136)

**가중치가 메서드 안의 지역 변수입니다.** 설정도 세션 변수도 아니고, 소스를 고치지 않으면 바꿀 수 없습니다.

두 모델의 가중치를 나란히 놓으면 축의 비중이 사실상 반대입니다.

| 축 | Trino (설정 가능) | StarRocks (소스 고정) |
|---|---|---|
| CPU | **75** | 0.5 |
| 메모리 | 10 | **2** |
| 네트워크 | 15 | **1.5** |

비율로 보면 Trino는 CPU를 메모리의 7.5배로 보고, StarRocks는 메모리를 CPU의 4배로 봅니다. 스칼라화를 즉시 하는 대가로 StarRocks는 **가지치기**를 얻습니다. 누계가 상한을 넘으면 즉시 버리고 더 싼 플랜을 찾으면 상한을 낮추는 branch-and-bound이고, 스칼라 하나이기 때문에 가능합니다.

조인 비용에는 StarRocks에만 있는 모델이 하나 더 있습니다. `HashJoinCostModel`이 해시 테이블이 10만 행을 넘어가면 **로그 스케일로 프로브 단가를 올립니다.** 캐시 미스를 모델에 넣은 것이고, 셔플 경로에서는 병렬도로 그 페널티를 깎아 줍니다. Trino는 바이트만 세고 해시 테이블이 캐시에 들어가는지는 보지 않습니다.

### 3-4. 조인 분배: 바이트를 보는 게이트와 행 수를 보는 게이트

broadcast를 후보로 허용할지 판단하는 게이트가 서로 다른 것을 재고 있습니다.

```java
// core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java#L82-L96 @ 483
double buildSideSizeInBytes = buildSideStatsEstimate.getOutputSizeInBytes(buildSide.getOutputSymbols());
return buildSideSizeInBytes <= joinMaxBroadcastTableSize.toBytes()
        || getSourceTablesSizeInBytes(buildSide, ...) <= joinMaxBroadcastTableSize.toBytes();
```

[DetermineJoinDistributionType.java#L82-L96](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java#L82-L96)

판단 대상이 **빌드측뿐**이고, 단위는 **바이트**(기본 100MB)이며, 두 항의 OR입니다. 프로브측 크기는 게이트에 들어오지 않습니다.

StarRocks는 양측 상대 크기와 BE 수를 함께 봅니다.

```java
// fe/fe-core/src/main/java/com/starrocks/sql/optimizer/task/EnforceAndCostTask.java#L321-L328 @ 4.0.14
if (leftOutputSize < rightOutputSize * beNum * sv.getBroadcastRightTableScaleFactor()
        && rightChildStats.getOutputRowCount() > sv.getBroadcastRowCountLimit()) {
    return false;
}
return true;
```

[EnforceAndCostTask.java#L321-L328](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/task/EnforceAndCostTask.java#L321-L328)

거부 조건이 **AND 두 개**입니다. 오른쪽이 왼쪽에 비해 충분히 작지 않고, 동시에 오른쪽이 절대적으로도 크면(기본 1,500만 행) 거부합니다. 뒤집으면 **오른쪽이 왼쪽보다 훨씬 작으면 행 수 제한을 아예 보지 않습니다.** 소스 주석이 의도를 밝히고 있습니다. 큰 왼쪽 테이블을 셔플하느니 오른쪽을 복제하는 편이 낫다는 판단입니다.

`beNum`이 곱해지는 것도 특징입니다. **BE가 많을수록 broadcast가 관대해집니다.** 복제 비용이 노드 수에 비례해 커지는데도 그렇습니다. 이 식은 복제 총량이 아니라 "왼쪽을 셔플하는 비용과의 상대 비교"로 읽어야 합니다.

| | Trino | StarRocks |
|---|---|---|
| 게이트 판단 대상 | 빌드측만 | 양측 상대 크기 + BE 수 |
| 게이트 단위 | **바이트** (기본 100MB) | **행 수** (기본 1,500만) |
| 게이트 형태 | 출력 크기 **OR** 소스 크기 | 상대 크기 **AND** 행 수 |
| 통계 없을 때 | 크기 휴리스틱으로 하강(8배 규칙) | broadcast 거부, 셔플로 |
| 분배 모드 수 | 2종 + 별도 단계의 셔플 회피 | 6종 (colocate, bucket shuffle 포함) |

바이트와 행 수의 차이는 **넓은 테이블에서 벌어집니다.** 같은 행 수라도 컬럼 수와 타입에 따라 전송량이 크게 달라집니다. 게이트 축이 각자의 위치에서 자연스럽다는 점도 짚을 값어치가 있습니다. Trino는 커넥터가 주는 통계에 의존하는데 바이트 크기는 파일 기반 커넥터가 비교적 잘 제공하고, StarRocks는 자체 스토리지의 행 수 통계를 신뢰할 수 있습니다.

## 4. 측정 결과

환경: macOS arm64 Docker Desktop 14 CPU / 25GB, `functional` 프로파일, TPC-H SF 0.01, Trino worker 1대 / StarRocks BE 1대. **실행 시간은 재지 않았습니다.**

### 4-1. 통계가 완전하면 두 엔진이 같은 트리를 만듭니다

TPC-H Q5 형태의 6테이블 쿼리입니다. 조인 5개는 StarRocks의 임계값 4를 넘고 Trino의 한도 8은 넘지 않는 구간입니다.

| 엔진 | 조인 트리 (통계 FULL, 기본 설정) |
|---|---|
| Trino 483 | `(lineitem ⋈ (supplier ⋈ (nation ⋈ region))) ⋈ (orders ⋈ customer)` |
| StarRocks 4.0.14 | **동일** |

결과값도 모든 경우에 양쪽이 일치했습니다(5행, revenue 소수점까지).

**이 측정은 코드만 읽고 내린 판단 하나를 뒤집었습니다.** 처음에는 "임계값 4가 StarRocks를 left-deep으로 만든다"고 적었습니다. 통계 상태와 임계값을 교차시켜 보니 원인 귀속이 틀렸습니다.

| StarRocks 통계 상태 | 임계값 4 (기본) | 임계값 10 |
|---|---|---|
| FULL (전 컬럼) | **bushy** | bushy |
| `DROP STATS nation` | **left-deep** | bushy |

**통계를 지우자 left-deep 트리가 그대로 재현되었고, `ANALYZE`로 복구하자 bushy로 돌아왔습니다.** 임계값이 탐색 경로를 가르는 것은 맞지만, 관찰된 트리 모양을 가른 것은 통계 가용성이었습니다.

대칭 실험으로 Trino 쪽 NDV를 지워 보았습니다. **Trino는 리오더를 포기하지 않았습니다.** Iceberg는 매니페스트에 행 수가 항상 있어서 NDV만 지워도 행 수 추정이 살아 있기 때문입니다. 3-2의 코드 경로 자체는 유효하지만 이 커넥터에서는 도달하기 어렵습니다.

### 4-2. 추정이 갈리는 지점은 다중 등가절 하나입니다

트리가 같으므로 노드별 카디널리티 추정을 직접 대조할 수 있었습니다.

| 조인 노드 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| nation ⋈ region (ASIA) | 5 | 5 |
| supplier ⋈ (…) | 20 | 20 |
| lineitem ⋈ (…) | 12,035 | 12,035 |
| orders ⋈ customer | 15,000 | 15,111 |
| **최상위 (등가절 2개)** | **5,448** | **10,896** |

**중간 노드는 전부 일치하고, 등가절이 2개인 최상위 조인에서만 정확히 2배 벌어집니다.** 다중 등가절의 상관 가정이 다르기 때문입니다. 손잡이를 돌려 확인했습니다. 최상위 조인의 실제 행 수는 **647**입니다.

| 엔진 / 설정 | 추정 | 실제 대비 |
|---|---|---|
| Trino `factor=0` (완전 상관) | 12,182 | 18.8× |
| StarRocks 기본 (`cbo_use_correlated_join_estimate=true`) | 10,896 | 16.8× |
| **Trino 기본 (`factor=0.25`)** | **5,448** | 8.4× |
| Trino `factor=0.5` | 2,436 | 3.8× |
| StarRocks `correlated=false` | 484 | 0.75× |
| **Trino `factor=1` (완전 독립)** | **609** | **0.94×** |

**양쪽 기본값 모두 한 자릿수에서 두 자릿수 배로 과대추정합니다.** Q5의 두 등가절은 실제로 독립적이라 완전 독립 가정이 정답에 가깝습니다. 어느 쪽 기본값이 낫다고 일반화하면 안 됩니다. FK 체인처럼 등가절이 실제로 상관된 스키마에서는 방향이 반대가 됩니다.

그리고 **이 설정 하나가 조인 순서까지 바꿉니다.** Trino `factor=1`에서는 최상위 조인의 등가절 조합이 달라졌고, StarRocks `correlated=false`에서는 트리가 right-deep으로 바뀌었습니다.

### 4-3. 분배 게이트의 경계값

| 쿼리 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `lineitem ⋈ supplier` (빌드 81행) | REPLICATED | BROADCAST |
| `lineitem ⋈ orders` (빌드 15,000행) | **REPLICATED** | **PARTITIONED** |

두 번째 행에서 결론이 갈렸습니다. **게이트 차이가 아닙니다.** StarRocks에 `[broadcast]` 힌트를 주면 broadcast 플랜이 나오므로 후보로는 허용되어 있었고, 비용 모델이 셔플을 골랐습니다.

원인을 세션 변수 하나로 확정했습니다. **BE 1대에서는 SHUFFLE 교환의 네트워크 비용이 0으로 계산됩니다.** `SET enable_local_shuffle_agg = false`로 이 조건을 깨자 조인이 BROADCAST로 뒤집혔고, 대조군(`lineitem ⋈ supplier`)은 움직이지 않았습니다. **즉 위 표의 StarRocks 열은 랩 구성이 만든 결과이지 일반적 성향이 아닙니다.** BE가 2대 이상이면 이 경로를 타지 않습니다.

게이트 경계값도 각각 확인했습니다.

- **Trino**: `join_max_broadcast_table_size`를 낮추자 경계가 **500B~1kB 사이**에서 나타났습니다. supplier 81행 × bigint 8바이트 = **648바이트**로, 조인 키 하나만 투영한 크기와 정확히 일치합니다.
- **StarRocks**: `broadcast_row_limit`을 **1**로 낮춰도 broadcast가 유지되었습니다(81 > 1인데도). AND 조건이 성립하지 않기 때문입니다. **0**으로 두자 그제서야 PARTITIONED가 되었습니다.

**운영자가 알아야 할 비대칭입니다.** Trino의 손잡이는 빌드측 크기 하나만 걸러내므로 예측이 쉽습니다. StarRocks의 `broadcast_row_limit`은 **값을 낮춰도 broadcast가 사라지지 않습니다.** 전면적으로 끄려면 0으로 두어야 합니다.

### 4-4. MV 재작성: 한쪽만 바뀝니다

양쪽에 같은 정의의 MV를 만들고(둘 다 갱신 후 15,000행), **MV 이름을 쓰지 않은 쿼리**를 던졌습니다.

```sql
SELECT l_orderkey, sum(l_extendedprice) FROM iceberg.bench.lineitem GROUP BY l_orderkey;
```

| 엔진 | 스캔 대상 |
|---|---|
| Trino 483 | `TableScan[table = iceberg:bench.lineitem$data@…]` 원본입니다 |
| StarRocks 4.0.14 | `0:OlapScanNode TABLE: mv_order_sum` MV입니다 |

`SET enable_materialized_view_rewrite = false`로 StarRocks도 원본으로 돌아갑니다. 원인이 확정됩니다.

재작성의 폭이 정확 일치를 훨씬 넘습니다. 술어를 MV 스캔에 밀어넣는 경우, `count(*)`를 `sum(c)`로 롤업하는 경우, 그리고 **조인의 한쪽 가지만 MV로 갈아끼우는 경우**까지 동작했습니다.

```
5:HASH JOIN  (INNER JOIN, BUCKET_SHUFFLE)
├─ 0:OlapScanNode    TABLE: mv_order_sum
└─ 3:IcebergScanNode TABLE: bench.orders
```

MV는 `lineitem` 단독 집계인데 조인 쿼리에서 lineitem 가지만 MV로 바꾸고 orders는 원본에서 읽었습니다. 결과는 재작성 ON/OFF/Trino 대조군 셋이 소수점까지 같았습니다.

Trino 쪽에 재작성 규칙이 없는 것은 **코드로 확인되는 사실**입니다. MV 관련 SPI는 모두 정의와 갱신용이고(`createMaterializedView`, `refreshMaterializedView` 등), 쿼리를 MV와 대조해 바꾸는 SPI가 없습니다. `iterative/rule/`에도 MV 관련 규칙이 하나도 없습니다. MV를 어떻게 읽을지는 옵티마이저가 아니라 **분석기**가 정하고, 진입 조건이 `metadata.getMaterializedView(session, name)`입니다. 여기서 `name`은 **쿼리가 적은 이름**입니다. 원본 테이블을 대상으로 쓴 쿼리는 이 분기에 들어오지 않습니다.

반대쪽에는 전용 패키지가 파일 35개, **18,000줄**로 있습니다. 본체 클래스 주석이 근거 논문을 밝힙니다.

```java
// fe/.../rule/transformation/materialization/MaterializedViewRewriter.java#L106-L110 @ 4.0.14
/*
 * SPJG materialized view rewriter, based on
 * 《Optimizing Queries Using Materialized Views: A Practical, Scalable Solution》
 *
 *  This rewriter is for single table or multi table join query rewrite
 */
```

[MaterializedViewRewriter.java#L106-L110](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/transformation/materialization/MaterializedViewRewriter.java#L106-L110)

### 4-5. 신선도 처리가 정반대입니다

작은 테이블에 MV를 걸고 갱신한 뒤 원본에 1행을 넣었습니다.

| 엔진 | 원본 변경 후 |
|---|---|
| **Trino** (`GRACE PERIOD` 미지정, 기본) | **여전히 MV를 읽습니다.** 메타데이터 테이블은 `STALE`로 보고하는데 읽기는 MV입니다 |
| Trino (`GRACE PERIOD INTERVAL '0' SECOND`) | 정의를 펼쳐 원본을 읽습니다 |
| **StarRocks** | 낡았다고 판단하면 **재작성을 포기하고 원본으로 돌아갑니다** |

Trino 쪽 기본값이 무제한 grace period이기 때문입니다. 코드에 `// Unlimited grace period`라는 주석과 함께 `return true`가 있습니다. **원본이 아무리 바뀌어도 갱신 전까지 스토리지 테이블을 읽습니다.**

### 4-6. 통계: 자동으로, 그것도 골라서 수집합니다

probe를 진행하는 동안 **실행하지 않은 수집 작업**이 StarRocks 이력에 나타났습니다.

```
27494  iceberg.bench  statprobe   l_suppkey,l_shipdate   FULL  ONCE  SUCCESS  2026-09-04 01:55:34
27499  iceberg.bench  statprobe2  l_suppkey              FULL  ONCE  SUCCESS  2026-09-04 01:56:34
```

**수집된 컬럼 목록이 술어에 쓴 컬럼과 정확히 일치했습니다.** `statprobe2`에는 `WHERE l_suppkey > 99` 하나만 던졌고 수집된 컬럼도 `l_suppkey` 하나입니다. 테이블 생성부터 수집까지 약 1분이 걸렸습니다. 근거가 `_statistics_.predicate_columns`에 남아 있고, 쓰인 방식(`normal,predicate,group_by`)까지 기록됩니다. **Trino에는 이 개념 자체가 없습니다.**

그리고 **두 엔진의 통계는 공유되지 않습니다.** 같은 테이블을 StarRocks에서 보면 외부 컬럼 통계 행 수가 0이고, `EXPLAIN COSTS`의 컬럼 통계가 `UNKNOWN`입니다. 행 수는 Iceberg 메타데이터에서 읽지만 Trino가 Puffin에 써 둔 NDV는 읽지 않습니다. 같은 카탈로그, 같은 파일, 같은 스냅샷인데 각자 자기 통계만 믿습니다.

통계 표현력도 확인했습니다.

| 컬럼 | 참 NDV | StarRocks | Trino | StarRocks min/max | Trino low/high |
|---|---|---|---|---|---|
| `l_orderkey` | 15,000 | 15,022 (+0.15%) | 14,819 (−1.2%) | 1 / 60000 | 1 / 60000 |
| `l_suppkey` | 100 | 100 | 100 | 1 / 100 | 1 / 100 |
| `l_returnflag` | 3 | 3 | 3 | **A / R** | **(빈칸)** |

**`l_returnflag`의 min/max가 Trino에는 없습니다.** Trino의 컬럼 통계는 4필드이고 범위가 `DoubleRange`라서 문자열 min/max를 담을 수 없습니다. 히스토그램과 다중 컬럼 결합 NDV는 개념 자체가 없습니다. 다만 StarRocks의 히스토그램도 이 랩에서는 쓸 수 없었습니다. Iceberg 외부 테이블에는 적용되지 않습니다.

### 4-7. CTE 재사용: 능력은 한쪽에만 있고, 자동 선택은 확인하지 못했습니다

```sql
WITH t AS (SELECT l_orderkey, sum(l_extendedprice) s FROM lineitem GROUP BY l_orderkey)
SELECT count(*) FROM t a JOIN t b ON a.l_orderkey = b.l_orderkey WHERE a.s > b.s;
```

| 엔진 / 설정 | lineitem 스캔 수 |
|---|---|
| Trino 483 | 2 |
| StarRocks 4.0.14 (기본) | 2 |
| StarRocks (`SET cbo_cte_reuse_rate = 0`) | **1** + `MultiCastDataSinks` |

**기본 설정의 StarRocks도 인라인을 골랐습니다.** SF 0.01에서는 lineitem 재계산이 재사용보다 싸기 때문입니다. 참조를 3회로 늘려도 마찬가지였습니다. **이 랩에서 확인된 것은 "능력이 있다"까지입니다.** 비용 모델이 자동으로 재사용을 고르는 규모는 확인하지 못했습니다.

## 5. 축별 정리

| 축 | Trino 483 | StarRocks 4.0.14 | 어떤 상황에 갈리는가 |
|---|---|---|---|
| 조인 순서 탐색 | 8개까지 전수, 넘으면 포기 | 4단계 전환, 50개까지 | 조인 9개 이상이면 StarRocks만 재배치합니다 |
| 통계 부실 시 | 리오더 포기 | left-deep 재배치 | 통계 없는 외부 카탈로그 |
| 비용 축 | 4-튜플, 가중치 75/10/15 (설정 가능) | 3-튜플, 0.5/2/1.5 (소스 고정) | 메모리가 빡빡한 플랜 |
| 조인 비용 모델 | 바이트 기반 | 캐시 미스를 로그로 반영 | 해시 테이블 10만 행 초과 |
| 분배 게이트 | 빌드측 바이트 | 양측 비율 + 행 수 + BE 수 | 넓은 테이블, BE 증설 |
| MV 재작성 | **없습니다** | 18,000줄, 매칭 모드 5종 | 반복 집계 워크로드 |
| 통계 수집 | 사람이 `ANALYZE` | 데몬이 쿼리를 관찰해 자동 | 테이블이 많고 운영 인력이 적을 때 |
| 통계 저장 위치 | 테이블 포맷(Puffin) | 엔진 내부 DB | 여러 엔진이 같은 레이크를 쓸 때 |
| CTE 재사용 | 없습니다 | 있습니다 | 같은 서브쿼리를 여러 번 참조할 때 |
| 플랜 내부 푸시다운 | 실측 6항목 동등 | 동등 | 차이가 없었습니다 |
| 운영 개입 단위 | 세션 속성(쿼리 전체) | SQL 힌트(조인 하나) | 문제 쿼리 한 건 응급 대응 |

**힌트의 유무를 따로 짚어 둡니다.** StarRocks는 SQL 문법에 힌트가 있고, `[broadcast]`·`[shuffle]`·`[bucket]`·`[colocate]`·`[skew]`·`[unreorder]`가 조인 하나에 걸립니다. Trino의 SQL 문법에는 힌트가 없습니다. 조인 순서에 대해서는 `join_reordering_strategy=NONE`으로 전체를 끄는 것이 유일한 수단입니다. 문제 쿼리 한 건만 손보고 싶을 때 차이가 큽니다. 다만 힌트는 쿼리 본문에 남으므로 통계나 데이터 분포가 바뀐 뒤에도 계속 강제된다는 부작용이 있습니다.

4-3에서 `[broadcast]` 힌트로 플랜을 뒤집어 "게이트는 열려 있고 비용 모델이 고른 것"을 판별했듯이, **힌트는 튜닝 수단이자 진단 수단**입니다.

## 6. 언제 무엇을 고를까

| 상황 | 선택 | 이유 |
|---|---|---|
| 조인이 10개를 넘는 BI 쿼리가 많습니다 | StarRocks | Trino는 8개를 넘으면 리오더를 포기합니다 |
| 같은 집계를 반복해서 읽습니다 | StarRocks | MV 재작성이 투명하게 동작합니다. Trino에서는 쿼리가 MV 이름을 알아야 합니다 |
| 테이블이 많고 통계 관리 인력이 없습니다 | StarRocks | 자동 수집이 술어 컬럼을 골라 수집합니다 |
| 통계를 Spark 등 다른 엔진과 공유해야 합니다 | Trino | 통계가 테이블 포맷에 남습니다 |
| 비용 모델 가중치를 조정해야 합니다 | Trino | 설정으로 바꿉니다. StarRocks는 소스를 고쳐야 합니다 |
| 문제 쿼리 한 건을 응급 대응해야 합니다 | StarRocks | 힌트가 조인 하나에 걸립니다 |
| 조인 8개 이하이고 통계를 직접 관리합니다 | 어느 쪽도 가능합니다 | 4-1에서 같은 트리가 나왔습니다 |

**두 엔진을 함께 쓴다면 `ANALYZE`를 양쪽에서 각각 돌려야 합니다.** 한쪽만 돌리면 다른 쪽은 통계 없는 상태로 플랜을 짭니다. 벤치마크에서 두 엔진을 비교할 때 특히 함정입니다.

## 7. 확인하지 못한 것

| 항목 | 이유 |
|---|---|
| **어느 쪽 플랜이 실제로 빨랐는가** | 실행 시간을 재지 않았습니다. SF 0.01에서는 의미가 없습니다 |
| 다중 BE에서의 분배 결정 | StarRocks 게이트에 `beNum`이 곱해지므로 BE 1대 결과를 확장 해석할 수 없습니다 |
| 조인 9개 이상 구간의 실제 플랜 품질 | 비교 쿼리를 만들지 않았습니다 |
| outer join 재배치의 영향 | TPC-H Q5는 전부 inner join입니다 |
| 넓은 테이블에서 바이트와 행 수 게이트의 차이 | TPC-H로는 드러나지 않습니다. 컬럼이 많은 테이블이 필요합니다 |
| CTE 재사용이 자동으로 선택되는 규모 | SF 0.01에서는 비용 모델이 인라인을 골랐습니다 |
| 버킷팅된 테이블의 셔플 회피 비교 | 랩의 Iceberg 시드 테이블이 버킷팅되어 있지 않습니다 |
| StarRocks 스캔 비용 0의 영향 범위 | Iceberg 테이블만 썼습니다. 내부 OLAP 테이블로 재측정하면 이 항이 살아납니다 |
| 통계 표현력 차이가 플랜을 얼마나 바꾸는가 | 문자열 min/max와 히스토그램의 효과를 측정하지 못했습니다 |

**이 글에서 두 번 틀렸습니다.** "임계값 때문에 StarRocks가 left-deep을 만든다"고 읽었으나 원인은 통계였고(4-1), "기본 설정에서 StarRocks가 셔플을 선호한다"고 읽었으나 랩의 BE 1대 구성이 만든 결과였습니다(4-3). 둘 다 **코드만 읽고 내린 판단이 실측에 뒤집힌 경우**입니다.
