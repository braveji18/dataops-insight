# 같은 입력에 네 가지 결과가 나옵니다: StarRocks에만 있는 스토리지 계층

> 비교 기준: Trino **483** (`50b0b50b`) · StarRocks **4.0.14** (`7c18dd9d`) · 2026-10-16 기준
> 랩 구성: 같은 Iceberg 카탈로그, Trino worker 1대 / StarRocks BE 1대(`shared_nothing` 모드)
> 다루지 않는 것: StarRocks shared-data 모드, Kafka 적재 경로 실행, 인덱스의 실제 이득, 실행 시간 비교
> 시리즈: [1편 · 전체 결론](01-스토리지를-소유하는가.md) · [2편 · 옵티마이저](02-옵티마이저-같은-쿼리-다른-플랜.md) · [3편 · 실행 엔진](03-실행-엔진-JVM과-C++.md) · [4편 · 운영](04-운영-메모리-격리-장애.md)

## 결론부터

**이 글은 비교가 아니라 부재를 다룹니다.** 테이블 모델, 선언 인덱스, 자동 compaction, 적재 파이프라인은 모두 StarRocks에만 있고 Trino에는 대응물이 없습니다. **그리고 SPI로도 만들 수 없습니다.** 스토리지를 소유해야만 성립하는 기능들이기 때문입니다.

**다만 "있다"가 곧 "쓰면 이득"은 아닙니다.** 이 계층은 세 가지를 요구합니다.

- **테이블 모델은 되돌리기 어렵습니다.** 테이블을 만들 때 정하고 바꿀 수 없으며, `AGGREGATE` 모델은 원본 행을 버립니다.
- **인덱스는 워크로드를 알아야 설계할 수 있습니다.** 잘못 걸면 저장 공간과 적재 시간만 늘어납니다. 그리고 네 종류 가운데 둘은 실험 기능입니다.
- **자동 compaction은 예측 가능성과 맞바꾼 것입니다.** 언제 돌지 모르고 쿼리와 자원을 다툽니다.

**필요한 쪽에는 대체 수단이 없습니다.** `UPDATE`가 필요한데 Iceberg를 쓴다면 Trino를 거쳐야 하고, `LIKE '%…%'` 검색이 잦다면 n-gram 인덱스가 유일한 답입니다.

## 2. 테이블 모델: 같은 입력, 네 가지 결과

### 2-1. 중복 규칙이 테이블 정의에 있습니다

StarRocks의 테이블은 **네 종류**이고, 같은 키가 들어왔을 때 무엇을 할지가 **테이블 정의에 적혀 있습니다.**

```java
// fe/fe-core/src/main/java/com/starrocks/catalog/KeysType.java#L39-L43 @ 4.0.14
public enum KeysType {
    PRIMARY_KEYS,
    DUP_KEYS,
    UNIQUE_KEYS,
    AGG_KEYS;
```

[KeysType.java#L39-L43](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/catalog/KeysType.java#L39-L43)

**`UNIQUE`가 집계 계열로 분류된다는 점이 구조를 드러냅니다.** 같은 파일의 `isAggregationFamily()`가 `AGG_KEYS`와 `UNIQUE_KEYS`를 함께 참으로 돌려줍니다. `UNIQUE`는 사실상 "모든 값 컬럼이 `REPLACE`인 `AGGREGATE`"입니다. 즉 세 모델이 한 뿌리이고 **`PRIMARY_KEYS`만 다른 계열입니다.**

네 테이블에 완전히 같은 입력을 넣었습니다.

```sql
INSERT INTO <t> VALUES (1,10,'a'),(1,20,'b'),(2,5,'c');
INSERT INTO <t> VALUES (1,7,'z');
```

| 모델 | 결과 |
|---|---|
| `DUPLICATE` | `(1,7,z) (1,10,a) (1,20,b) (2,5,c)` 4행 전부 보존합니다 |
| `UNIQUE` | `(1,7,z) (2,5,c)` 마지막 쓰기가 이깁니다 |
| `PRIMARY KEY` | `(1,7,z) (2,5,c)` 마지막 쓰기가 이깁니다 |
| `AGGREGATE` | **`(1,37,z)`** `(2,5,c)` `v`는 SUM(10+20+7), `s`는 REPLACE입니다 |

**`AGGREGATE`의 37이 이 표의 요점입니다.** 원본 행이 남지 않습니다. 적재 시점에 합쳐지고 되돌릴 수 없습니다.

Trino + Iceberg에서는 테이블 종류가 **1종**이고, 중복 규칙을 **쓰는 문장**(`MERGE`)에 적습니다. 같은 데이터로 다르게 병합하는 것이 언제든 가능한 대신, 적재 시점에 미리 합쳐 두는 것은 불가능합니다.

### 2-2. `UPDATE`를 지원하는 것은 한 모델뿐입니다

`UNIQUE`와 `PRIMARY KEY`는 조회 결과가 같아서 다른 축으로 판별했습니다.

| 모델 | `UPDATE ... SET` | `DELETE` |
|---|---|---|
| `DUPLICATE` | 실패: `table t_dup does not support update` | 가능합니다 |
| `UNIQUE` | 실패: `table t_uni does not support update` | 가능합니다 |
| **`PRIMARY KEY`** | **가능합니다** | 가능합니다 |
| `AGGREGATE` | 실패: `table t_agg does not support update` | 가능합니다 |

**`UPDATE`를 지원하는 것은 `PRIMARY KEY`뿐입니다.** 지속 인덱스가 있어야 "이 키의 현재 행이 어디 있는지"를 알고 고칠 수 있기 때문입니다. `SHOW CREATE TABLE`이 `"enable_persistent_index" = "true"`를 보고하는데, 지정하지 않았는데도 켜져 있습니다.

### 2-3. 부분 컬럼 갱신: Iceberg에 없는 것

```sql
INSERT INTO t_pk VALUES (3,1,'x'),(4,2,'y');
SET partial_update_mode='column';
INSERT INTO t_pk (k,v) VALUES (3,555);      -- s는 지정하지 않습니다
```

| k | v | s |
|---|---|---|
| 3 | **555** | **x** |

**`s`가 `'x'`로 남았습니다.** 지정하지 않은 컬럼은 건드리지 않습니다.

**격차의 크기를 짚어 둡니다.** StarRocks는 Iceberg 테이블에 `UPDATE`조차 못 하는데([6편](06-커넥터와-확장성-경계의-값.md)), 자기 네이티브 테이블에서는 **컬럼 단위 갱신까지** 됩니다.

### 2-4. 왜 StarRocks에만 있는가

**테이블 모델은 스토리지를 소유해야만 만들 수 있습니다.**

`AGGREGATE`를 생각해 보면 분명합니다. 적재 시점에 값을 합쳐 버리려면 **쓰기 경로를 통제해야** 합니다. Trino는 쓰기 경로가 커넥터마다 다르고, 애초에 Iceberg 파일 포맷이 "같은 키를 합친다"는 개념을 갖고 있지 않습니다.

`PRIMARY KEY`도 마찬가지입니다. 지속 인덱스는 **BE가 데이터 파일과 인덱스를 함께 관리해야** 성립합니다. 상태 없는 워커에는 둘 곳이 없습니다.

**이것이 "소유하면 할 수 있고, 소유하지 않으면 SPI로도 만들 수 없다"의 가장 선명한 사례입니다.**

### 2-5. 그리고 모델 선택은 되돌리기 어렵습니다

**테이블을 만들 때 정하고 바꿀 수 없습니다.** 특히 `AGGREGATE`는 원본을 버리므로, 나중에 "원본 행이 필요하다"가 되면 **데이터가 이미 없습니다.**

Trino 쪽 유연성이 여기서 의미를 갖습니다. Iceberg 테이블은 언제든 다르게 읽고 다르게 병합할 수 있습니다. **StarRocks의 모델은 성능을 위해 선택지를 미리 버리는 거래입니다.**

## 3. 저장 구조와 인덱스

### 3-1. Tablet이 있는 쪽과 없는 쪽

| 관점 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| 저장 단위 | 스냅샷 → 데이터 파일 | **Tablet → Rowset → Segment** |
| 노드 소속 | **없습니다** | Tablet이 노드에 속합니다 |
| 나누는 축 | 파티션(변환 함수 포함) | **파티션 + 버킷 2축** |

**Tablet은 "데이터가 노드에 속한다"는 개념**이고, 여기서 세 가지가 파생됩니다.

1. **조인에서 셔플을 생략할 수 있습니다.** 같은 키로 버킷팅한 두 테이블은 셔플 없이 조인합니다.
2. **캐시 배정 문제가 없습니다.** Trino가 `CacheSplitAffinityProvider`로 인위적으로 만들어야 했던 것입니다([4편](04-운영-메모리-격리-장애.md) 4-3).
3. **노드를 늘리면 데이터를 옮겨야 합니다.** 대가입니다. Trino 워커는 그냥 늘리면 됩니다.

**즉 Tablet은 성능과 탄력성을 맞바꾼 설계입니다.**

### 3-2. 자동 계층은 대등하고 선언 인덱스에서 갈립니다

| 인덱스 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| min/max | Iceberg 매니페스트 + 파일 내부 통계 | ZoneMap |
| 블룸필터 | Parquet/ORC (읽기·쓰기 지원) | `bloom_filter_columns` |
| 정렬 키 인덱스 | 없습니다 (정렬 순서만 있습니다) | **Prefix(short key) 인덱스** |
| 비트맵 | **없습니다** | `USING BITMAP` |
| n-gram | **없습니다** | `USING NGRAMBF` |
| 전문 검색 | **없습니다** | `USING GIN`: **실험 기능이고 기본 꺼짐입니다** |
| 벡터 검색 | **없습니다** | `USING VECTOR`: **실험 기능이고 기본 꺼짐입니다** |

**min/max와 블룸필터 계층은 대등합니다.** Iceberg 매니페스트와 ZoneMap이 같은 일을 하고, 실제로 파일 프루닝을 측정했을 때 양쪽이 165행과 1파일로 완전히 일치했습니다.

**갈리는 것은 선언 인덱스입니다. 그리고 없는 것은 정말 없습니다.**

- 저카디널리티 등호 필터를 자주 쓴다면 비트맵 인덱스의 이득이 큽니다.
- **`LIKE '%foo%'`는 Iceberg 통계로 전혀 걸러지지 않습니다.** n-gram 블룸필터만이 답입니다.
- 전문 검색과 벡터 검색은 Trino에서 **다른 시스템을 붙여** 해결해야 합니다. 커넥터로 연결은 되지만 같은 테이블 안에서 하는 것과는 다릅니다.

### 3-3. "인덱스가 많다"를 곧바로 우위로 읽으면 안 됩니다

두 가지를 함께 보아야 합니다.

**첫째로 둘은 실험 기능입니다.** GIN과 VECTOR는 운영에서 쓰려면 FE 설정을 바꿔야 하고, 그것은 곧 **아직 안정성을 보장하지 않는다**는 뜻입니다.

**둘째로 나머지도 사용자가 선택해야 합니다.** 어느 컬럼에 비트맵을 걸지, n-gram을 걸지는 워크로드를 알아야 정합니다. **잘못 걸면 저장 공간과 적재 시간만 늘어납니다.**

Trino 쪽은 선택지가 적은 대신 **고민할 것도 적습니다.** min/max는 자동이고 블룸필터만 정하면 됩니다. 대신 **파티션 설계와 정렬 순서가 사실상 유일한 튜닝 수단**이므로 파티션을 잘 잡는 것이 그만큼 중요해집니다.

## 4. compaction: 자동인 쪽과 사람이 부르는 쪽

| 관점 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| 파일 정리 | **사람이나 스케줄러가 실행합니다** (`EXECUTE optimize`) | **BE가 자동으로 합니다** |
| 종류 | 1종 (+ 매니페스트·스냅샷·고아 파일은 별도 프로시저) | **3종** (cumulative / base / update) |
| 확인 주기 | 없습니다 | 1초 / 60초 / 10초 |
| 자원 | 쿼리와 같은 클러스터(쿼리로 실행합니다) | **쿼리와 같은 프로세스**(상시) |
| 저장 계층 구현 | 커넥터 하나 | **두 벌** (`storage/` + `storage/lake/` 103파일) |

### 4-1. 자동이 항상 나은 것은 아닙니다

StarRocks의 자동 compaction은 **운영자가 신경 쓰지 않아도 조회 성능이 유지된다**는 큰 장점이 있습니다. 그러나 대가가 있습니다.

- **언제 돌지 모릅니다.** 적재가 몰린 직후 compaction이 함께 돌면 그 시간대 쿼리가 느려집니다.
- **쿼리와 자원을 다툽니다.** 디스크당 스레드 1개로 묶어 두었지만 I/O는 공유합니다.
- **끌 수 없습니다.** 정확히는 설정으로 조일 수 있으나, 끄면 파일이 무한히 쌓입니다.

Trino 쪽은 반대입니다. **정리 시점을 완전히 통제할 수 있고**(새벽에 몰아서), 대신 **아무도 하지 않으면 아무 일도 일어나지 않습니다.**

**실행 항목이 양쪽에 각각 있습니다.** Trino + Iceberg를 쓴다면 `EXECUTE optimize`를 도는 스케줄을 반드시 만들어야 하고, StarRocks를 쓴다면 compaction 몫을 자원 계획에 포함해야 합니다. 적재가 몰리는 시간대에 쿼리가 느려지면 이것을 먼저 의심해야 합니다.

### 4-2. 저장 계층이 두 벌로 존재합니다

`storage/`와 `storage/lake/`에 같은 개념의 파일이 나란히 있습니다. **두 모드(shared-nothing과 shared-data)가 코드를 크게 공유하지 않는다**는 뜻입니다.

이는 **두 모드의 기능이 어긋날 수 있는 지점**입니다. 예를 들어 `cloud_native_index_compaction_task.cpp`는 lake 쪽에만 있습니다. shared-data 전용 최적화이거나, 아직 shared-nothing에 없는 것이거나 둘 중 하나입니다. **얕은 클론으로는 판단할 수 없었습니다.**

`shared_data` 모드의 StarRocks는 배치 형태가 Trino와 거의 같아집니다. 데이터는 객체 스토리지에 두고 계산 노드는 캐시를 가진 상태 없는 노드가 됩니다. 코드를 보면 **태블릿 개념은 유지하고 저장 위치만 옮기는** 설계로 읽힙니다. 콜로케이트 조인 같은 이점을 남기려는 것입니다. **다만 랩이 `shared_nothing`이라 검증하지 못했습니다.**

## 5. 적재와 트랜잭션: Trino에는 이 계층이 없습니다

| 관점 | Trino 483 + Iceberg | StarRocks 4.0.14 |
|---|---|---|
| 적재 경로 | SQL 3종 (`INSERT` / `CTAS` / `MERGE`) | **SQL + Stream/Broker/Routine Load + Pipe** |
| 스트리밍 구독 | **없습니다** (외부 도구가 필요합니다) | **Routine Load**, 데이터베이스가 소유합니다 |
| 재시도 멱등성 | 없습니다 (애플리케이션 책임입니다) | **라벨** |
| 트랜잭션 상태 | 스냅샷 커밋(원자적) | **PREPARE → COMMITTED → VISIBLE** |
| 오류 허용 | 한 행만 깨져도 전체가 실패합니다 | **`FILTERED_ROWS`**, 걸러내고 진행합니다 |
| 적재 관측 | 쿼리 이력과 같습니다 | **`information_schema.loads` 전용 뷰** |

### 5-1. 적재를 소유한다는 결정

StarRocks가 Routine Load를 갖는 것은 **데이터베이스가 파이프라인의 일부가 되겠다**는 선언입니다. Kafka에서 테이블로 가는 경로에 Flink를 두지 않아도 됩니다.

**얻는 것**은 구성 요소가 줄고 적재 상태를 SQL로 관측하고 제어할 수 있다는 점입니다. **파는 것**은 적재 부하가 **쿼리와 같은 프로세스**에서 발생한다는 점입니다. `MemTracker::Type`에 `LOAD`가 있고, 셔플 흐름 제어에서 `brpc_load_ignore_overcrowded`가 **적재만 기본 `true`**인 것도 이 때문입니다. 적재는 실패 비용이 크니 메모리를 더 쓰더라도 밀고 나갑니다.

**적재를 소유한 대가가 여러 축에서 반복해 나타납니다.** 메모리 회계, 셔플 흐름 제어, compaction 부하가 전부 같은 뿌리입니다.

### 5-2. 커밋과 가시성이 나뉘어 있습니다

Iceberg는 **메타데이터 파일 하나를 원자적으로 교체**하면 커밋이 끝납니다. 데이터 파일은 이미 저장소에 있고 모두가 같은 것을 봅니다. 분리할 이유가 없습니다.

StarRocks는 데이터가 **여러 BE에 복제**되어 있습니다. FE가 커밋을 확정해도 각 BE가 버전을 적용해야 조회에 반영됩니다. 분리하지 않을 수 없습니다.

**운영 관점의 함의가 있습니다. 적재가 "끝났다"고 해서 즉시 조회되는 것이 아닙니다.** publish가 늦어지면 커밋된 데이터가 아직 안 보일 수 있습니다.

### 5-3. 측정: 모든 쓰기가 적재 작업으로 기록됩니다

`information_schema.loads`에 남은 이력입니다.

| JOB_ID | LABEL | STATE | TYPE |
|---|---|---|---|
| 29702 | `delete_01a06ca0-...` | FINISHED | **INSERT** |
| 29701 | `delete_01a06ca0-...` | FINISHED | **INSERT** |
| 29700 | `insert_01a06c9f-...` | FINISHED | INSERT |

**`DELETE`의 TYPE이 `INSERT`입니다.** 삭제도 "삭제 표시를 적재하는" 트랜잭션으로 처리되고, 실제 정리는 compaction이 나중에 합니다. 라벨은 사용자가 지정하지 않으면 엔진이 자동 생성합니다.

**다만 그 자동 라벨로는 클라이언트 재시도의 중복을 막지 못합니다.** 재시도가 잦은 환경이라면 라벨을 직접 지정해야 합니다.

`COMMITTED`와 `VISIBLE`을 구분해 보이지는 못했습니다. 랩 규모에서는 두 상태 사이가 순식간입니다.

### 5-4. `FILTERED_ROWS`가 말해 주는 것

적재 이력에 걸러진 행 수 컬럼이 있다는 것은 **적재 중 형식 오류를 허용하는 설계**를 뜻합니다. 대량 적재에서 일부 행이 깨져 있어도 전체를 실패시키지 않습니다. 실무에서 중요한 동작입니다.

Trino의 `INSERT ... SELECT`는 **한 행이라도 실패하면 쿼리가 실패합니다.** 데이터 정제를 앞단에서 끝내 두어야 합니다.

## 6. 언제 무엇을 고를까

| 상황 | 선택 | 이유 |
|---|---|---|
| upsert가 잦은 서비스 데이터를 다룹니다 | **StarRocks** | `PRIMARY KEY` 모델과 부분 컬럼 갱신을 지원합니다 |
| 사전 집계로 조회를 가속하고 싶습니다 | **StarRocks** | `AGGREGATE` 모델이 적재 시점에 합칩니다 |
| `LIKE '%…%'` 검색이 잦습니다 | **StarRocks** | n-gram 인덱스가 유일한 답입니다 |
| 저카디널리티 등호 필터가 많습니다 | **StarRocks** | 비트맵 인덱스의 이득이 큽니다 |
| Kafka에서 테이블로 가는 파이프라인이 필요합니다 | **StarRocks** | Routine Load가 구성 요소를 하나 줄여 줍니다 |
| 더러운 데이터를 넣어야 합니다 | **StarRocks** | `FILTERED_ROWS`로 걸러내고 진행합니다 |
| 파일 정리를 신경 쓰고 싶지 않습니다 | **StarRocks** | BE가 자동으로 3종을 수행합니다 |
| 같은 데이터를 여러 방식으로 병합해야 합니다 | **Trino + Iceberg** | 모델에 묶이지 않습니다 |
| 정리 작업 시점을 완전히 통제해야 합니다 | **Trino + Iceberg** | `EXECUTE optimize`를 원하는 때 부릅니다 |
| 노드를 자주 늘리고 줄입니다 | **Trino + Iceberg** | Tablet이 없어 데이터 이동이 필요 없습니다 |
| 전문 검색과 벡터 검색을 SQL 안에서 하려 합니다 | **보류** | StarRocks 4.0.14에서는 실험 기능입니다 |

### 설계 시점에 정해야 하는 것

이 계층의 결정은 대부분 **나중에 바꾸기 어렵습니다.** 테이블을 만들기 전에 정해야 하는 항목을 모았습니다.

1. **테이블 모델**: 바꿀 수 없습니다. `AGGREGATE`는 원본을 버립니다.
2. **버킷 키**: 조인 대상을 같은 키로 버킷팅해 두면 StarRocks가 셔플을 생략합니다.
3. **인덱스**: 워크로드를 모르면 헛돕니다. 저장 공간과 적재 시간이 늘어납니다.
4. **파티션**: Trino 쪽에서는 사실상 유일한 튜닝 수단입니다.
5. **`PRIMARY KEY` 모델의 compaction 부담**: 전용 `update_compaction`이 따로 도는 것이 그 증거입니다.

## 7. 확인하지 못한 것

| 항목 | 이유 |
|---|---|
| **인덱스의 실제 이득** | 비트맵과 n-gram이 얼마나 걷어내는지 재지 않았습니다. 데이터를 채우고 프로파일 카운터를 보아야 합니다 |
| 인덱스의 비용 | 저장 공간 증가와 적재 지연을 측정하지 않았습니다 |
| **compaction이 도는 것** | 삽입량이 임계값(rowset 5개)에 못 미쳤습니다. 대량 적재를 반복해야 합니다 |
| compaction이 쿼리에 미치는 영향 | 적재와 조회를 동시에 걸어야 합니다 |
| **shared-data 모드 전부** | 랩이 `shared_nothing`이고 모드 전환은 클러스터 재구성이 필요합니다 |
| 두 저장 계층의 기능 격차 | 4-2의 우려를 확인하지 못했습니다 |
| **Stream / Broker / Routine Load 전부** | Kafka도 브로커도 랩에 없습니다. 5절의 적재 경로는 코드와 문법 독해입니다 |
| 라벨 멱등성 | 시험하지 못했습니다 |
| `COMMITTED`와 `VISIBLE`의 구분 | 랩 규모에서는 두 상태 사이가 순식간입니다 |
| `EXECUTE optimize`의 비용 | 실행은 확인했으나 대용량에서의 소요 시간과 자원은 재지 않았습니다 |
| compaction이 인덱스를 어떻게 다루는가 | 병합 시 인덱스가 재생성되는지 확인하지 않았습니다 |

**이 글의 결론은 "있다"와 "그 대가"까지입니다.** 인덱스와 compaction이 실제로 얼마나 이득을 주는지는 더 큰 데이터로 다시 재야 합니다.
