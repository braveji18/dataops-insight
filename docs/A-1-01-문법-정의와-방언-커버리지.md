## 1. 비교 관점

두 엔진 모두 ANTLR4 로 SQL 을 파싱한다. 도구가 같으므로 비교는 "무엇을 쓰는가"가 아니라 **어떤 SQL 을 받아들이도록 설계했는가**로 좁혀진다.

세 가지를 본다.

1. **방언의 기준점** — ANSI SQL 인가 MySQL 인가. 이건 취향이 아니라 같은 SQL 이 다른 뜻이 되는 지점을 만든다
2. **문법이 덮는 범위** — 쿼리만인가, 클러스터 운영까지인가
3. **상대 방언을 얼마나 받아주는가** — 이전 비용과 직결된다

결론부터: **Trino 는 ANSI SQL 을 기준으로 삼고 그 위에 확장을 얹었다. StarRocks 는 MySQL 호환을 기준으로 삼았고, 그 대가로 `||` 같은 기본 연산자의 의미가 갈린다.** 그리고 StarRocks 는 Trino 파서를 **의존성으로 통째 내장해** 방언 모드를 제공한다 — 반대 방향은 없다.

## 3. StarRocks 구현

### 3-1. 위치 — 렉서와 파서가 분리돼 있다

| | 경로 |
|---|---|
| 파서 문법 | `fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocks.g4` (3,246줄) |
| 렉서 문법 | `fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocksLex.g4` (629줄) |
| 분석기 | `fe/fe-core/src/main/java/com/starrocks/sql/analyzer/` (98개 파일, 36,761줄) |

`fe/fe-core/src/main/antlr/` 아래에도 같은 이름의 `.g4` 두 개가 보이지만 **심볼릭 링크**다(빌드 플러그인이 보는 경로). 실체는 하나다.

### 3-2. 렉서가 세션 설정을 읽는다

StarRocks 렉서는 상태를 갖는다.

```antlr
lexer grammar StarRocksLex;
@members {

    sqlMode = newSqlMode;
}
}
```
— `StarRocksLex.g4:16-22`

그리고 `||` 의 토큰 타입을 실행 중에 바꾼다.

```antlr
LOGICAL_OR: '||' {setType((sqlMode & com.starrocks.qe.SqlModeHelper.MODE_PIPES_AS_CONCAT) == 0 ? LOGICAL_OR : StarRocksParser.CONCAT);};
```
— `StarRocksLex.g4:532`

기본값은 `PIPES_AS_CONCAT` 을 **포함하지 않는다.**

```java
/* When a new session is create, its sql mode is set to MODE_DEFAULT */
public static final long MODE_DEFAULT = 32L;
/* Bits for different SQL MODE modes, you can add custom SQL MODE here */
public static final long MODE_REAL_AS_FLOAT = 1L;
public static final long MODE_PIPES_AS_CONCAT = 1L << 1;
```
— `SqlModeHelper.java:58-62`

`32 = 1 << 5` 는 `MODE_ONLY_FULL_GROUP_BY` 하나다. `MODE_PIPES_AS_CONCAT`(`1 << 1 = 2`)과 겹치지 않으므로 **기본 상태에서 `||` 는 논리 OR** 이다. 4절에서 실측한다.

대소문자 무시는 ANTLR 옵션이 아니라 직접 만든 입력 스트림으로 처리한다 — 문자를 읽을 때마다 대문자로 올린다.

```java
public int LA(int i) {
    int result = stream.LA(i);
    switch (result) {
        case 0:
        case IntStream.EOF:
            return result;
        default:
            return Character.toUpperCase(result);
    }
}
```
— `CaseInsensitiveStream.java:39-49`

결과는 Trino 와 같다. 다만 렉서 규칙을 모두 대문자 리터럴(`ACCESS: 'ACCESS';`)로 적어야 한다는 제약이 따라온다.

### 3-3. 힌트를 전용 채널로 보낸다

```antlr
OPTIMIZER_HINT
    : '/*+' .*? '*/' -> channel(2)
    ;
```
— `StarRocksLex.g4:616-618`

일반 주석은 `channel(HIDDEN)` 이지만 옵티마이저 힌트만 **채널 2** 로 간다. `HintCollector` / `HintFactory` 가 이 채널을 따로 읽는다. `A-2-01` 5-1절에서 다룬 `[broadcast]`·`SET_VAR` 힌트가 여기서 들어온다 — 즉 **힌트가 문법 수준의 1급 시민**이다. Trino 에는 대응물이 없고, 세션 프로퍼티로 대신한다.

## 4. 실측

전문은 `docs/evidence/A-1/20260903-parser-dialect-and-type-mapping.md`.

### 4-1. `||` — 같은 SQL, 다른 답, 오류 없음

| 엔진 / 설정 | `'a' \|\| 'b'` | `1 \|\| 0` | `0 \|\| 0` |
|---|---|---|---|
| Trino 483 | `ab` | 파싱 오류 | — |
| StarRocks 4.0.14 (기본) | **`NULL`** | `1` | `0` |
| StarRocks (`sql_mode='PIPES_AS_CONCAT'`) | `ab` | — | — |

`1 || 0 = 1` 이므로 논리 OR 이 맞다. 문자열은 boolean 캐스트에 실패해 `NULL` 이 된다.

**이것이 A-1 전체에서 가장 위험한 항목이다.** 다른 차이는 오류로 즉시 드러나지만, 이건 쿼리가 성공하고 값만 틀린다. `sql_mode` 를 바꾸면 원래 의미로 돌아오므로 원인이 렉서 분기임도 확정된다.

### 4-2. 예약어 — 표본 5개 전부 갈렸다

`SELECT 1 AS <word>` 를 양쪽에 던졌다.

| 단어 | Trino | StarRocks |
|---|---|---|
| `text` / `key` / `json` / `range` / `partition` | 전부 OK | 전부 오류 |

## 5. 설계 차이와 그 원인

### 5-1. 문법이 덮는 범위가 3배 다르다

최상위 `statement` 규칙의 분기 수다.

| | 분기 수 | 성격 |
|---|---|---|
| Trino `SqlBase.g4` | **91** | 쿼리, DDL, 세션, 접근제어 |
| StarRocks `StarRocks.g4` | **249** | 위 + 클러스터·적재·백업·플러그인 운영 전반 |

StarRocks 문법의 카테고리 주석을 그대로 옮기면 이유가 보인다.

```
Query / Database / Table / View / Partition / Index / Task / Materialized View /
Catalog / DML / Routine / StreamLoad / Admin / Cluster Management / Analyze /
Profile / Resource Group / External Resource / UDF / Load / Show / authz /
Security Integration / Group Provider / Backup Restore / Sql BlackList And WhiteList /
Backend BlackList / Compute Node BlackList / Data Cache management / Export /
Plugin / File / Set / Storage Volume / Pipe / Compaction / FailPoint / prepare_stmt /
Dictionary / Plan advisor / Warehouse / CNGroup / Transaction / Translate /
SQL Plan Management / Unsupported
```

`Cluster Management`, `Backup Restore`, `Compaction`, `Backend BlackList`, `Storage Volume` 은 **스토리지와 클러스터를 직접 소유하는 엔진에서만 나올 수 있는 항목**이다. Trino 는 스토리지를 갖지 않으므로 이 영역이 통째로 비어 있고, 대신 커넥터와 외부 도구가 맡는다.

즉 문법 규모 차이는 SQL 표현력의 차이가 아니라 **제품 경계의 차이**다. 이 관찰은 `A-5-01`(커넥터 추가 난이도)과 `C-1`(스토리지 계층)에서 다시 쓰인다.

## 6. 결론

**동등하지 않다 — 기준 방언이 다르고, 그 차이는 이전 비용으로 나타난다.**

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 기준 방언 | ANSI SQL | MySQL 호환 |
| `\|\|` | 항상 문자열 결합 | 기본 논리 OR (`sql_mode` 로 전환) |
| 예약어 | 83개, ANSI 대조표로 문서화 | 155개 (타입명·윈도우 함수명 포함) |
| 문법 범위 | 91개 문장 — 쿼리·DDL 중심 | 249개 문장 — 클러스터 운영 포함 |
| 대소문자 무시 | ANTLR `caseInsensitive` 옵션 | 자체 `CaseInsensitiveStream` |
| 힌트 | 문법에 없음 (세션 프로퍼티로 대체) | 전용 렉서 채널(2) + `HintCollector` |
| 상대 방언 수용 | 없음 | `sql_dialect='trino'` (trino-parser **385** 내장, 부분 지원, 자동 되돌림) |

**우열이 아니라 지향의 차이다.** Trino 는 표준 준수를, StarRocks 는 MySQL 생태계 호환을 택했다. 각각 얻은 것과 잃은 것이 대칭이다.

**이전 작업에 쓸 실무 결론**

1. Trino → StarRocks 이전에서 **`||` 를 먼저 훑어야 한다.** 오류가 나지 않고 값만 틀리므로 테스트가 잡아주지 못할 수 있다. 이전 전에 `sql_mode` 에 `PIPES_AS_CONCAT` 을 넣어두는 편이 안전하다
2. 예약어 99개는 오류로 드러나므로 위험도는 낮지만 건수가 많다. `text`, `key`, `json`, `range`, `default` 같은 컬럼명은 일괄 백틱 처리가 필요하다
3. `sql_dialect='trino'` 는 **일괄 이전 수단이 아니다.** 385 문법 기준의 부분 지원이고, 함수는 약 100건만 이름 대응되며, 근사 집계처럼 값이 달라지는 경우도 있다. 이전 초기의 완충재로 보는 편이 맞다

### 아직 답하지 않은 것

- **함수 커버리지 전체 비교** — 4-4 는 표본 1건이다. 이름·시그니처·의미 수준의 대조는 `A-1-03` 에서 다룬다
- **타입 표현력** — 예약어에 타입명이 들어간 이유이자 이전의 다른 축이다. `A-1-02` 에서 다룬다
- **`sql_dialect='trino'` 의 실제 커버리지 비율** — TPC-DS 같은 쿼리 집합을 통째로 던져 통과율을 재야 한다. 이 랩에서 가능하지만 이 문서 범위를 넘는다
- **`MODE_ANSI_QUOTES` 등 다른 sql_mode 비트의 영향** — `||` 하나만 확인했다
