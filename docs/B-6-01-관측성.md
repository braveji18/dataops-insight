## 1. 비교 관점

관측성은 이 비교 연구에서 **가장 실증적으로 검증된 축**이다. 열여섯 편의 문서를 쓰는 동안 두 엔진의 관측 수단을 계속 써 왔고, **어디서 막히고 어디서 잘 보였는지가 그대로 기록에 남아 있다.**

두 방향으로 나눠 본다.

1. **쿼리 밖에서 보는 것** — 누가 무엇을 실행했는가(감사·계보·집계 통계)
2. **쿼리 안을 보는 것** — 왜 느렸는가(연산자 단위 계측)

결론부터: **1번은 Trino, 2번은 StarRocks 가 앞선다.** Trino 의 `EventListener` 는 **컬럼 수준 계보**까지 담고, StarRocks 의 Query Profile 은 **엔진 내부 카운터를 SQL 로 꺼내 준다.** 그리고 이 문서의 결론은 실측 경험에서 나온다 — **StarRocks 쪽이 없었으면 `A-5-02`·`A-5-03`·`B-2-01` 의 판별이 불가능했다.**

### 2-3. 쿼리 안을 보는 것 — `EXPLAIN ANALYZE`

연산자 단위 계측은 `EXPLAIN ANALYZE` 로 나온다. 이 연구에서 실제로 쓴 출력이다.

```
└─ ScanFilterProject[table = iceberg:bench.o_part$data@..., filterPredicate = (o_orderkey < bigint '1000')]
       Input: 14269 rows (169.36kB), Filtered: 98.21%, Physical input: 225.41kB,
       Physical input time: 309.58ms, Splits: 75, Splits generation wait time: 8.08ms
```

**필요한 것이 대부분 한 줄에 있다** — 읽은 행, 필터 제거율, 물리 입력 바이트와 시간, 스플릿 수. `A-5-02` 의 프루닝 판별이 이 한 줄로 됐다.

한계는 **쿼리를 다시 돌려야 한다**는 것이다. 이미 끝난 쿼리의 연산자 상세는 Web UI 의 JSON 으로 가야 하고, **SQL 로는 꺼낼 수 없다.**

## 3. StarRocks 구현

### 3-1. 감사 로그 — 플러그인

`plugin/AuditPlugin.java`, `plugin/AuditEvent.java`, `qe/AuditLogBuilder.java`, `qe/AuditEventProcessor.java`. `AuditEvent` 의 감사 필드(`@AuditField`)는 **46개**다.

Trino 의 `QueryCompletedEvent` 와 성격이 다르다 — **평면적인 필드 목록**이다. 쿼리 시간, 스캔 행 수, 반환 행 수, 리소스 그룹, 상태 코드 등이 나란히 있고, **계보나 옵티마이저 통계 같은 구조적 정보는 없다.**

`AuditEncryptionChecker` 가 따로 있어 민감한 문장을 가리는 장치가 있다.

### 3-2. Query Profile — 쿼리 안을 보는 것

이 축에서 StarRocks 의 결정적 강점이다.

```sql
SET enable_profile = true;
-- 쿼리 실행
SHOW PROFILELIST;                       -- 최근 쿼리 목록
ANALYZE PROFILE FROM '<query_id>';      -- 전체 프로파일
ANALYZE PROFILE FROM '<query_id>', 0;   -- 노드 0의 상세
```

문법이 SQL 이다(`ShowProfilelistStmt.java`, `AnalyzeProfileStmt.java`). **이미 끝난 쿼리의 연산자 카운터를 SQL 로 꺼낼 수 있다** — Trino 가 못 하는 것이다.

**`enable_profile` 은 기본 꺼짐이지만 긴 쿼리는 자동으로 남는다.**

```java
@VariableMgr.VarAttr(name = BIG_QUERY_PROFILE_THRESHOLD)
private String bigQueryProfileThreshold = "30s";
```
— `fe/fe-core/.../qe/SessionVariable.java:1578-1579`

`ConnectContext.isProfileEnabled()`(991-1002)가 `enable_profile` 이 꺼져 있어도 **실행 시간이 이 임계값을 넘으면 참**을 돌려준다. 즉 **30초 넘게 걸린 쿼리는 사후에 볼 수 있고, 30초 미만 쿼리는 미리 켜 두지 않으면 볼 수 없다.**

무엇이 나오는지가 이 문서의 핵심이다. 이 연구에서 실제로 쓴 카운터들이다.

### 3-3. 지표 — 무엇이 수집되고, 무엇으로 성능 저하를 찾는가

> **이 절은 2026-10-30 에 보강했다.** 초판은 두 줄이었고 "Prometheus 형식 수집기가 있다"까지만 적었다. 지표 이름과 개수는 아래 파일을 직접 세어 확인했으며, **런타임 수집은 하지 않았다**(랩 컨테이너가 내려가 있고, 떠 있는 다른 프로젝트 컨테이너는 이 문서의 기준 버전과 다르다). 따라서 **지표가 존재한다는 것까지가 확인된 범위이고, 실제 값과 수집 주기는 미확인이다.**

#### 3-3-3. 장단점

**Trino 지표의 강점**

1. **실행 엔진 내부가 드러난다.** `getBlockedDrivers`·`getBlockedSplits`·`getWaitingSplits` 는 **"일이 밀려 있는지"를 직접 보여주는 지표**다. StarRocks 에 대응물이 없어서, StarRocks 에서 같은 질문에 답하려면 쿼리별 프로파일(3-2)을 켜야 한다.
2. **대기 시간과 실행 시간을 분리해 센다.** `getQueuedTime` 과 `getExecutionTime` 이 따로 있어 **"느린 것이 대기 때문인가 실행 때문인가"** 가 지표 단계에서 갈린다.
3. **자원 부족 실패가 별도 분류다.** `getInsufficientResourcesFailures` 와 `getQueriesKilledDueToOutOfMemory` 가 따로 있어 용량 문제를 다른 실패와 섞지 않는다.
4. **SQL 로 조회할 수 있는 창구가 있다.** `system.runtime.queries`·`tasks`·`nodes` 는 지표 수집기 없이도 즉시 쓸 수 있다.
5. **지표가 기능 클래스에 붙어 있어** 새 기능이 들어오면 지표가 함께 들어온다.

**Trino 지표의 약점**

1. **스토리지 상태 지표가 없다.** 소유하지 않으므로 당연하지만, **파일이 쌓이는지, 작은 파일이 많아졌는지를 엔진 지표로는 알 수 없다.** `A-5-04`·`C-1-03` 에서 본 대로 Iceberg 정리는 사람이 돌려야 하는데, **언제 돌려야 하는지를 지표가 알려주지 않는다.**
2. **지연 분위가 지표에 없다.** `TimeStat` 이 분포를 갖지만 StarRocks 처럼 **P95·P99 가 이름 있는 지표로 노출되지 않는다.** 대시보드에서 바로 쓰려면 수집 측에서 계산해야 한다.
3. **이름이 MBean 경로라 길고 변하기 쉽다.** 클래스 이름이 바뀌면 지표 이름도 바뀐다.
4. **캐시 지표가 커넥터에 흩어져 있다.** `B-3-01` 에서 Trino 파일 캐시 적중을 확인하지 못한 이유가 여기에도 걸린다.

**StarRocks 지표의 강점**

1. **스토리지 건강도가 지표로 나온다.** `max_tablet_compaction_score` 가 **"이 클러스터가 지금 건강한가"를 한 숫자로 보여주고**, `tablet_max_compaction_score` 는 **BE 라벨로 어느 노드가 문제인지까지 좁혀 준다**(`MetricRepo:949-956`). 이것이 다음 절의 핵심이다.
2. **지연 분위가 이름 있는 지표다.** mean/median/P75/P95/P98/P99/P999 7종이 그대로 나온다.
3. **대기열이 지표로 분해돼 있다.** `query_queue_pending` 과 슬롯 수준(`slot_pending`/`slot_running`)까지 있어 **`B-2-01` 의 리소스 그룹 동작을 지표로 추적할 수 있다.**
4. **적재와 트랜잭션, 복제가 지표로 덮인다.** `C-1-04` 에서 본 "적재를 소유한다"는 결정이 지표에서도 나타난다. `routine_load_paused` 는 **Kafka 구독이 멈춘 것을 바로 알려주는 지표**다.
5. **잠금 경합 히스토그램이 있다.** FE 메타데이터 잠금이 병목인지 판별할 수 있다.
6. **이름이 안정적이다.** `starrocks_fe_*` 접두어와 고정 문자열이라 대시보드가 버전 간에 덜 깨진다.

**StarRocks 지표의 약점**

1. **실행 단계의 밀림을 보여주는 지표가 없다.** 드라이버·스플릿·블록 상태 지표가 없어서, **쿼리가 느릴 때 "어디서 막혔는가"를 지표로는 좁히지 못한다.** 프로파일을 켜야 하고, 그것은 3-2·4-3 의 네 단계 비용으로 돌아온다.
2. **대기와 실행이 분리되지 않는다.** `query_latency` 는 총 시간이다. 대기열 지표는 따로 있지만 **지연 자체를 분해한 지표가 아니다.**
3. **쿼리 spill 지표가 없다.** spill 지표는 **적재 경로만 8종**(`load_spill_*`) 있고, `A-3-03`·`B-1-01` 에서 본 **쿼리 실행 spill 12계열에 대응하는 지표를 찾지 못했다.** 즉 **적재가 디스크로 흘리는 것은 지표로 보이지만, 쿼리가 흘리는 것은 보이지 않는다.** 켜 놓고 운영할 때 쿼리 spill 총량을 추적하려면 프로파일로 가야 한다. Trino 는 `SpillerStats.getTotalSpilledBytes` 로 쿼리 spill 총량을 바로 본다.
4. **지표가 SQL 로 나오지 않는다.** Trino 의 `system.runtime.*` 같은 창구가 없어 **수집기를 붙이기 전에는 지표를 볼 수 없다.**
5. **중앙 레지스트리라 지표 추가가 한 파일에 몰린다.** `MetricRepo` 가 1,300줄 넘게 커졌다.

#### 3-3-4. 클러스터 성능 저하를 확인하는 지표

**이 절이 운영에서 가장 자주 쓰인다.** 증상별로 먼저 볼 지표를 적는다.

| 증상 | Trino 483 에서 볼 것 | StarRocks 4.0.14 에서 볼 것 |
|---|---|---|
| **쿼리가 시작되지 않는다** | `getQueuedTime` 증가 + `TimeSharingTaskExecutor.getWaitingSplits` 증가 | **`query_queue_pending`** 증가 + `query_queue_slot_pending` |
| **쿼리가 중간에 멈춰 있다** | **`getBlockedDrivers` / `getBlockedSplits` 비율** 상승. `SplitSchedulerStats.getSplitQueuesFull` 과 함께 본다 | 지표로 좁힐 수 없다. **프로파일의 `closure_block_timer`**(`A-4-01`)를 봐야 한다 |
| **읽기가 느려졌다** | `getWallInputBytesRate` 하락. 커넥터 캐시 MBean | **`query_cache_hit_ratio` / `cache_miss_ratio` 하락**, `datacache_disk_used_bytes` 가 한도에 붙었는지, **`read_time_ms` / `io_time_weigthed`** 증가 |
| **점점 느려진다 (수 일 단위)** | 엔진 지표로는 보이지 않는다. **Iceberg 파일 수를 따로 세야 한다**(`C-1-03`) | **`max_tablet_compaction_score` 상승**이 1순위(클러스터 전체 최대). 어느 BE 인지는 **`tablet_max_compaction_score` 의 `backend` 라벨**로 좁히고, `max_tablet_rowset_num` 과 함께 본다 |
| **적재 중에만 조회가 느리다** | 해당 없음 (적재 계층이 없다) | **`base_compaction_task_byte_per_second` 하락** + `cumulative_compaction_request_total` 증가. `B-1-01` 5-3 의 "적재·compaction 이 쿼리 메모리를 먹는다"가 이 조합으로 드러난다 |
| **메모리가 부족하다** | **`getQueriesKilledDueToOutOfMemory` / `getTasksKilledDueToOutOfMemory`** 증가, `getClusterTotalMemoryReservation` 이 한도에 붙음, `getNumberOfLeakedQueries` | `memory_usage` 와 `MemTracker` 계열. **쿼리 밖 소비(LOAD·COMPACTION)를 함께 봐야 한다** |
| **디스크로 흘리고 있다** | **`SpillerStats.getTotalSpilledBytes` / `SpillSpaceTracker.getCurrentBytes`** — 쿼리 spill | 적재는 **`load_spill_local_bytes_write_total`** 로 보인다. **쿼리 spill 은 지표가 없어 프로파일(`SPILL_PROCESS` 노드)로 가야 한다** |
| **노드가 빠졌다** | **`HeartbeatFailureDetector.getActiveCount` 감소 / `getFailedCount` 증가**, `getTotalAvailableProcessors` 감소 | `report_queue_size` 적체. `SHOW BACKENDS` 로 확인하는 편이 빠르다 |
| **실패가 늘었다** | `getUserErrorFailures`(사용자 책임)와 **`getInsufficientResourcesFailures`**(용량 책임)를 **반드시 나눠 본다** | `query_err_rate` + **`query_internal_err`**(엔진 책임)와 `query_analysis_err`(SQL 책임)를 나눠 본다 |
| **계획 수립이 느리다** | **`system.runtime.optimizer_rule_stats`** 로 규칙별 시간 | **대응물이 없다**(5-1). 프로파일의 플랜 단계 시간으로 간접 추정 |
| **메타데이터가 병목이다** | 커넥터 MBean (메타데이터 캐시 적중) | **`HISTO_SLOW_LOCK_WAIT_TIME_MS` 상승**, `edit_log_write` / `edit_log_size_bytes` 급증, **`max_journal_id` 증가 속도** |
| **Kafka 적재가 밀린다** | 해당 없음 | **`routine_load_paused`**(즉시 조치 필요), `routine_load_error_rows`, `RoutineLoadLagTimeMetricMgr` |
| **클러스터가 읽기 전용이 됐다** | 해당 없음 | **`safe_mode`** |

**두 엔진에서 "성능 저하"의 1순위 지표가 다르다는 점이 이 표의 요점이다.**

- **Trino 는 실행 밀림(`BlockedDrivers`)과 대기(`QueuedTime`)** 가 1순위다. 스토리지를 소유하지 않으니 **엔진이 느려지는 원인도 엔진 안에 있거나 원격 스토리지에 있고, 후자는 엔진 지표에 안 나온다.**
- **StarRocks 는 `max_tablet_compaction_score`** 가 1순위다. **조회가 점점 느려지는 가장 흔한 원인이 파일 누적이고, 그것을 한 숫자로 보여준다.** 반대로 실행 단계의 밀림은 지표로 못 본다.

**양쪽 모두 못 보는 것도 적는다.** 두 엔진의 지표 어디에도 **"이 쿼리가 왜 이 플랜을 골랐는가"** 는 없다. 그것은 `A-2-07`(통계)과 `A-2-03`(비용 모델)의 영역이고, 지표가 아니라 `EXPLAIN` 과 프로파일로 간다.

> **미확인 사항을 명시한다.** (가) 위 지표들의 **실제 값과 수집 주기를 런타임으로 확인하지 않았다.** (나) StarRocks 의 **쿼리 spill** 지표 부재는 `be/src/` 전체에서 `METRIC_DEFINE.*spill` 을 검색한 결과이고(적재 spill 8종만 나왔다), **다른 이름으로 존재할 가능성을 배제하지 못했다.** (다) Trino 쪽 `@Managed` 100개 이상은 **파일 수**이고 지표 개수가 아니다 — 한 파일에 여러 지표가 있다. (라) **두 엔진의 지표를 실제 Prometheus·Grafana 에 붙여 비교하지 않았다.**

### 3-4. 분산 추적 — 양쪽 다 OpenTelemetry 지만 범위가 다르다

Trino 는 서버 모듈에 `TracingModule` 을 기본으로 올리고(`Server.java:103`), `io/trino/tracing/` 에 `TracingMetadata`·`TracingConnectorMetadata`·`TracingAccessControl` 같은 래퍼를 둔다. **쿼리 처리 중의 메타데이터 조회와 권한 검사가 span 으로 남는다.**

StarRocks 는 FE 에 `TraceManager` 와 `otlp_exporter_grpc_endpoint`(기본 빈 값 = 끔, `Config.java:3227-3228`), BE 에 `jaeger_endpoint` 가 있다. 그런데 FE 에서 `TraceManager` 를 쓰는 곳은 `AlterJobV2`·`PublishVersionTask`·`DatabaseTransactionMgr`·`TransactionState` 뿐이다. **추적 대상이 쿼리가 아니라 적재·트랜잭션·스키마 변경 경로다.**

## 4. 실측 — 이 연구 자체가 실측이다

별도 증거 파일을 만들지 않는다. **A-2 부터 B-5 까지 열여섯 편의 실측이 곧 이 축의 데이터다.** 그중 관측 수단 때문에 결론이 갈린 사례를 모은다.

### 4-1. StarRocks 쪽이 없었으면 못 했을 판별

**`A-5-02` 커넥터 프루닝** — Trino 는 `EXPLAIN ANALYZE` 한 줄에 `Input: 14269 rows ... Splits: 75` 가 나온다. StarRocks 의 `EXPLAIN` 에는 `cardinality=250`(추정치)뿐이라 **비교가 성립하지 않았다.** `ANALYZE PROFILE FROM '<id>', 0` 으로 `RawRowsRead: 14269`, `ScanRanges: 80` 을 꺼내고서야 판별됐다.

이 과정에서 **함정도 있었다.** `OutputRows` 를 Trino 의 `Input rows` 와 짝지었다가 "15,000 대 255" 라는 틀린 표를 만들 뻔했다. `OutputRows` 는 필터 이후이고 짝은 `RawRowsRead` 다. **카운터가 많다는 것은 잘못 고를 여지도 많다는 뜻이다.**

**`B-3-01` 캐시 적중** — `FooterCacheReadCount: 1` / `FooterCacheWriteCount: 0` 으로 두 번째 실행이 캐시에서 읽었음을 확인했다. **Trino 쪽은 대응 카운터를 SQL 로 꺼낼 수 없어 같은 확인을 하지 못했다.**

### 4-2. Trino 쪽이 더 나았던 지점

**`B-1-01` 메모리 오류** — Trino 는 오류 메시지에 `Top Consumers: {PagePartitioner=856B}` 를 붙인다. **어느 연산자가 먹었는지 오류가 직접 말해 준다.** StarRocks 는 BE 와 fragment 만 알려 주고 소비 연산자는 알려주지 않는다.

**`A-5-02` 플랜 확인** — Trino 는 `EXPLAIN` 만으로 `TableScan[... constraint on [o_orderdate]]` 와 `filterPredicate` 유무가 보여, **술어가 커넥터에 흡수됐는지를 한 번에 판단**할 수 있었다. StarRocks 는 `EXPLAIN` 의 `PREDICATES` 에 술어가 찍혀 있어도 그것이 매니페스트까지 갔다는 뜻이 아니라, **반드시 프로파일을 봐야 했다.**

### 4-3. 관측 비용의 차이

| | 판별에 필요한 절차 |
|---|---|
| Trino | `EXPLAIN ANALYZE <쿼리>` — **한 번** |
| StarRocks | `SET enable_profile=true` → 쿼리 → `SHOW PROFILELIST` → `ANALYZE PROFILE FROM '<id>', <node>` — **네 단계** |

**StarRocks 쪽 정보가 더 깊지만 꺼내는 비용이 크다.** 그리고 `enable_profile` 은 기본 꺼짐이라 **30초 미만의 쿼리는 문제가 난 뒤에 다시 재현해야 한다.** 30초를 넘긴 쿼리는 자동으로 남는다(3-2).

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 쿼리 이벤트 | **`EventListener` SPI 34클래스** — 플러그인으로 내보냄 | `AuditPlugin` + `AuditEvent` **46필드**(평면) |
| 컬럼 계보 | **있음**(`ColumnLineageInfo`) | 없음 |
| 옵티마이저 관측 | **`system.runtime.optimizer_rule_stats`** + `QueryPlanOptimizerStatistics` | 없음 |
| 연산자 계측 | `EXPLAIN ANALYZE`(재실행 필요) | **`ANALYZE PROFILE`(사후 조회 가능)** |
| 리더 내부 계측 | 없음 | **있음** — `PageReadTime`, `GroupChunkRead`, `RawRowsRead` 등 |
| 기본 활성 | `EXPLAIN ANALYZE` 는 즉시 | **`enable_profile` 기본 꺼짐**, 단 **30초 넘는 쿼리는 자동 수집** |
| 오류 진단 | **소비 연산자 명시**(`Top Consumers`) | 위치와 해결 방법 명시 |
| 지표 노출 | JMX + **OpenMetrics(Prometheus 호환)** | FE·BE `/metrics`, Prometheus 형식 |
| 지표 선언 | 기능 클래스의 **`@Managed`**(파일 100개 이상) | 중앙 레지스트리 (FE 210건 + BE 238건) |
| 지표가 강한 영역 | **실행 밀림**(`BlockedDrivers`·`WaitingSplits`), 대기·실행 분리, **쿼리 spill**, 옵티마이저 규칙 | **스토리지 건강도**(`max_tablet_compaction_score`), 지연 분위 7종, 대기열 슬롯, 적재·복제·적재 spill, 잠금 경합 |
| 지표가 없는 영역 | **스토리지 상태 전부**, 지연 분위, 적재 관련 전부 | **실행 밀림 전부**, **쿼리 spill**, 옵티마이저 통계, SQL 조회 창구 |
| 성능 저하 1순위 지표 | `getBlockedDrivers` / `getQueuedTime` | **`max_tablet_compaction_score`** |
| 분산 추적 | OpenTelemetry, **쿼리 경로**(메타데이터·권한 검사) | OpenTelemetry/Jaeger, **적재·트랜잭션 경로** |

### 5-2. 왜 방향이 갈렸나

**Trino 는 "쿼리 밖"에 투자했다.** 수십 개 커넥터를 넘나드는 연합 엔진이라, 운영자의 질문이 **"누가 어떤 데이터에 접근했나"** 인 경우가 많다. 컬럼 계보는 그 질문의 최종형이다.

**StarRocks 는 "쿼리 안"에 투자했다.** 실행 계층(`A-3`)과 스토리지(`C-1`)를 직접 소유하므로 **내부 카운터를 다 갖고 있고**, 저지연 분석이 목표라 "왜 20ms 가 아니라 200ms 인가"에 답해야 한다.

**즉 각자 자기가 답해야 하는 질문에 맞춰 계측했다.** 이 축에서도 `A-5-01` 이후 반복된 구도가 나타난다 — **소유한 만큼 볼 수 있다.**

### 5-3. 그러나 StarRocks 의 관측 비용은 실제 부담이다

4-3 의 네 단계는 사소하지 않다. **30초 미만 쿼리는 문제가 난 뒤 다시 돌려야 한다**는 점이 특히 그렇다 — 재현되지 않는 문제는 볼 수 없다. 저지연 분석이 주 용도인 StarRocks 에서는 **문제 쿼리 대부분이 이 30초 아래에 있다.**

`A-5-02` 6절에서 "StarRocks 는 `EXPLAIN` 만으로는 알 수 없다"고 적었는데, 그것이 이 축의 실무적 결론이다. **프루닝이 걸렸는지, 캐시가 맞았는지, 배압으로 막혔는지 — 전부 프로파일을 켜야 보인다.**

### 5-4. 카운터가 많다는 것의 이면

4-1 에서 `OutputRows` 와 `RawRowsRead` 를 혼동할 뻔한 일은 우연이 아니다. StarRocks 프로파일에는 **비슷한 이름의 카운터가 여럿** 있고 어느 것이 무엇의 짝인지 문서가 아니라 소스를 봐야 알 수 있다.

**Trino 의 `EXPLAIN ANALYZE` 는 항목이 적어 오독의 여지가 적다.** 깊이와 명료함의 교환이다.

## 6. 결론

**동등하지 않다 — 서로 반대 방향으로 깊다.**

- **쿼리 밖**: Trino 가 앞선다. `EventListener` SPI 34클래스, **컬럼 수준 계보**, 옵티마이저 규칙 통계, 내보내기 플러그인 4종
- **쿼리 안**: StarRocks 가 앞선다. **Parquet 리더 내부까지 계측**되고, **끝난 쿼리를 SQL 로 사후 조회**할 수 있다
- **비용**: Trino 는 `EXPLAIN ANALYZE` 한 번, StarRocks 는 네 단계 + 기본 꺼짐(30초 넘는 쿼리만 자동) + 짧은 쿼리는 재현 필요
- **오류 진단**: Trino 는 소비 연산자를, StarRocks 는 위치와 해결책을 말해 준다
- **지표**: 양쪽 다 Prometheus 로 모을 수 있지만 **강한 영역이 반대다.** Trino 는 실행 밀림을, StarRocks 는 스토리지 건강도를 지표로 보여준다. **성능 저하를 찾을 때 먼저 볼 지표가 서로 다르다**(3-3-4)

**실무 결론**

1. **StarRocks 운영에서는 `enable_profile` 과 `big_query_profile_threshold` 정책을 미리 정해 두라.** 기본으로는 30초 넘는 쿼리만 남으므로, "평소 0.2초인데 가끔 3초" 같은 문제는 사고 후에 재현해야 하고, 재현되지 않으면 영원히 못 본다
2. **StarRocks 에서 성능 문제를 볼 때 `EXPLAIN` 으로 끝내지 말 것.** 술어가 플랜에 찍혀 있어도 프루닝이 걸렸다는 뜻이 아니다(`A-5-02`)
3. **거버넌스·규제 대응이 요건이면 Trino 의 컬럼 계보가 큰 차이를 만든다.** 별도 도구 없이 엔진이 직접 계산해 준다
4. **두 엔진을 함께 쓴다면 감사·계보는 Trino 쪽에서, 성능 분석은 StarRocks 쪽에서** 얻는 구성이 자연스럽다
5. **StarRocks 프로파일의 카운터 이름을 짝지을 때 주의하라.** `OutputRows`(필터 후)와 `RawRowsRead`(필터 전)를 혼동하면 결론이 뒤집힌다
6. **StarRocks 를 운영하면 `max_tablet_compaction_score` 경보를 가장 먼저 걸어라.** 조회가 점점 느려지는 가장 흔한 원인이 파일 누적이고, 이 지표 하나가 그것을 보여준다. 경보가 울리면 `tablet_max_compaction_score` 의 `backend` 라벨로 어느 노드인지 좁힌다(3-3-4)
7. **Trino 를 운영하면 `BlockedDrivers` 비율과 `QueuedTime` 을 대시보드 첫 줄에 두라.** 실행 밀림과 대기를 가르는 지표이고, StarRocks 에는 대응물이 없다
8. **실패 지표를 책임 주체로 나눠 보라.** Trino 는 `getUserErrorFailures`(사용자)와 `getInsufficientResourcesFailures`(용량), StarRocks 는 `query_analysis_err`(SQL)와 `query_internal_err`(엔진)로 갈린다. 섞어 보면 용량 문제를 놓친다

### 아직 답하지 않은 것

- **EventListener 의 실측** — 랩에 이벤트 리스너 플러그인이 구성돼 있지 않다. 컬럼 계보가 실제로 얼마나 정확한지 확인하지 못했다
- **StarRocks 감사 로그의 실측** — `AuditEvent` 46필드의 내용을 실제로 보지 않았다
- **30초 자동 프로파일의 실측** — `big_query_profile_threshold` 동작은 코드로만 확인했다
- **분산 추적의 실측** — 양쪽 모두 OTLP 수집기를 붙여 보지 않았다
- **관측 오버헤드** — `enable_profile=true` 가 실행 시간을 얼마나 늘리는지 재지 않았다. StarRocks 가 기본을 꺼 둔 이유가 여기 있을 텐데 근거를 갖지 못했다
- **`optimizer_rule_stats` 의 실용성** — 조회는 했지만 A-2 축 작성에 활용하지 않았다. 되돌아보면 규칙별 비용 비교에 쓸 수 있었다
- **지표 수집 통합** — 양쪽 지표를 실제 Prometheus·Grafana 에 붙여 비교하지 않았다. 3-3 은 **선언된 지표를 코드에서 센 것**이고 런타임 값은 확인하지 않았다
- **StarRocks 의 쿼리 spill 지표 부재** — `be/src/` 전체 검색 결과 적재 spill 8종만 나왔다. **쿼리 spill 이 다른 이름으로 존재할 가능성을 배제하지 못했다**(3-3-3)
- **지표 수집 자체의 비용** — 양쪽 모두 수집 주기와 오버헤드를 재지 않았다
- **성능 저하 증상별 지표의 실효** — 3-3-4 의 표는 **코드에 존재하는 지표로 구성한 것**이고, 실제 장애에서 그 지표가 먼저 움직이는지 확인하지 않았다
- **다중 노드에서의 프로파일** — BE 1대라 노드별 편차(`[min=..., max=...]` 표기)가 의미를 갖지 못했다
