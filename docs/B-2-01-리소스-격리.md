# B-2 운영 (2) — 리소스 격리

> 비교 축: `plan/01-비교항목-정리.md` B-2 "Resource Groups(큐잉 수준) vs Resource Group(BE cgroup 실격리)"
> 기준 버전: **Trino 483** / **StarRocks 4.0.14**
> 런타임 증거: `docs/evidence/B/20260904-resource-isolation-probes.md`
> 선행 문서: `docs/B-1-01-메모리-관리와-spill.md`
> 일자: 2026-09-04

> ### ⚠ `plan/01` 전제 정정
> `plan/01` 은 StarRocks 쪽을 **"BE cgroup 실격리"** 로 적었다. **cgroup 이 아니다.**
> BE 소스에서 cgroup 을 참조하는 곳은 4개 파일뿐이고 전부 *자기 컨테이너의 CPU·메모리 구성을 읽는* 용도다.
> 실제 격리는 **CPU 친화도 바인딩 + 가중 vruntime + 전용 코어 + 그룹 간 코어 대여**로 된 자체 스케줄러다(3절).
> "큐잉 수준 vs 실격리"라는 **방향은 맞다** — 4절 실측이 확인한다.

---

## 1. 비교 관점

여러 사용자·여러 워크로드가 한 클러스터를 쓰면 **한 쿼리가 전체를 마비시키지 않게** 막아야 한다. 두 엔진 모두 "리소스 그룹"이라는 같은 이름의 기능을 갖고 있지만, **강제하는 지점이 다르다.**

1. **어디서 막는가** — 시작 전인가, 실행 중인가
2. **무엇으로 나누는가** — 동시 실행 수인가, CPU 자체인가
3. **누가 설정하는가** — 설정 파일·플러그인인가, SQL 인가

결론부터: **Trino 는 입장 통제(admission control), StarRocks 는 실행 통제다.** Trino 의 리소스 그룹 한도는 "다음 쿼리를 시작할까"만 정하고 이미 도는 쿼리는 건드리지 않는다. StarRocks 는 BE 스캔 안에서 행을 세다가 **실행 중인 쿼리를 중단시킨다.**

## 2. Trino 구현

### 2-1. 리소스 그룹이 SPI 다

`core/trino-spi/src/main/java/io/trino/spi/resourcegroups/` 에 11개 인터페이스가 있고, 구현은 플러그인이다(`plugin/trino-resource-group-managers` — 파일 기반과 DB 기반).

그룹이 제어하는 항목이다.

```java
void setSoftMemoryLimitBytes(long limit);
void setSoftCpuLimit(Duration limit);
void setHardCpuLimit(Duration limit);
void setCpuQuotaGenerationMillisPerSecond(long rate);
void setHardPhysicalDataScanLimitBytes(long limit);
void setPhysicalDataScanQuotaGenerationBytesPerSecond(long rate);
void setSoftConcurrencyLimit(int softConcurrencyLimit);
void setHardConcurrencyLimit(int hardConcurrencyLimit);
void setMaxQueuedQueries(int maxQueuedQueries);
void setSchedulingWeight(int weight);
void setSchedulingPolicy(SchedulingPolicy policy);
```
— `core/trino-spi/.../resourcegroups/ResourceGroup.java:28-104` 발췌

**메모리·CPU·스캔량 한도가 다 있다.** "큐잉만 한다"는 표현은 항목 목록만 보면 부정확해 보인다. 그러나 **강제 방식이 전부 입장 통제**다.

스케줄링 정책은 4종 — `FAIR`, `WEIGHTED`, `WEIGHTED_FAIR`, `QUERY_PRIORITY`. 대기열에서 **다음에 누구를 꺼낼지** 정하는 정책이지, 도는 쿼리끼리 CPU 를 나누는 정책이 아니다.

### 2-2. 강제는 `canRunMore()` 하나다

```java
if ((cpuUsageMillis >= hardCpuLimitMillis) || (memoryUsageBytes > softMemoryLimitBytes) || (physicalInputDataUsageBytes >= hardPhysicalDataScanLimitBytes)) {
    return false;
}

int hardConcurrencyLimit = this.hardConcurrencyLimit;
if (cpuUsageMillis >= softCpuLimitMillis) {
    // TODO: Consider whether CPU limit math should be performed on softConcurrency or hardConcurrency
    // Linear penalty between soft and hard limit
    double penalty = (cpuUsageMillis - softCpuLimitMillis) / (double) (hardCpuLimitMillis - softCpuLimitMillis);
    hardConcurrencyLimit = (int) Math.floor(hardConcurrencyLimit * (1 - penalty));
```
— `core/trino-main/.../execution/resourcegroups/InternalResourceGroup.java:1079-1088`

메서드 이름이 답이다 — **`canRunMore()`**. 한도를 넘은 그룹은 **새 쿼리를 시작하지 못할 뿐**이고, 이미 도는 쿼리는 그대로 완주한다.

soft 와 hard 사이 구간에서는 **동시 실행 수를 선형으로 깎는다.** 부드럽게 조이는 장치다.

### 2-3. 실행 중 강제는 그룹 밖에 있다

Trino 에도 실행 중인 쿼리를 죽이는 한도가 있다 — `query.max-cpu-time`, `query.max-scan-physical-bytes`. 다만 **리소스 그룹 속성이 아니라 쿼리 단위 설정**이고, 강제 방식이 주기 폴링이다.

```java
try {
    enforceScanLimits();
}
catch (Throwable e) {
    log.error(e, "Error enforcing query scan bytes limits");
}
...
}, 1, 1, TimeUnit.SECONDS);
```
— `core/trino-main/.../execution/QueryManager.java:127-140` 발췌

**코디네이터가 1초마다 전체 쿼리를 훑는다.** 그리고 이미 읽은 양을 보고 사후에 실패시킨다.

```java
limitOpt.ifPresent(limit -> {
    DataSize scan = query.getBasicQueryInfo().getQueryStats().getPhysicalInputDataSize();
    if (scan.compareTo(limit) > 0) {
        query.fail(new ExceededScanLimitException(limit));
    }
});
```
— `QueryManager.java:419-424`

**읽는 것을 막는 것이 아니라 읽은 뒤에 실패시킨다.** 4-2 에서 이것이 무엇을 뜻하는지 실측한다.

## 3. StarRocks 구현

### 3-1. 리소스 그룹이 SQL 객체다

`CREATE RESOURCE GROUP` 문장으로 만들고 카탈로그에 저장된다(`fe/fe-core/.../catalog/ResourceGroup.java`). 플러그인도 설정 파일도 필요 없다.

분류 기준과 한도가 한 목록에 있다.

```java
public static final String USER = "user";
public static final String ROLE = "role";
public static final String QUERY_TYPE = "query_type";
public static final String SOURCE_IP = "source_ip";
public static final String DATABASES = "db";
public static final String PLAN_CPU_COST_RANGE = "plan_cpu_cost_range";
public static final String PLAN_MEM_COST_RANGE = "plan_mem_cost_range";
public static final String CPU_CORE_LIMIT = "cpu_core_limit";
public static final String CPU_WEIGHT = "cpu_weight";
public static final String EXCLUSIVE_CPU_CORES = "exclusive_cpu_cores";
public static final String MAX_CPU_CORES = "max_cpu_cores";
public static final String MEM_LIMIT = "mem_limit";
public static final String MEM_POOL = "mem_pool";
public static final String BIG_QUERY_MEM_LIMIT = "big_query_mem_limit";
public static final String BIG_QUERY_SCAN_ROWS_LIMIT = "big_query_scan_rows_limit";
public static final String BIG_QUERY_CPU_SECOND_LIMIT = "big_query_cpu_second_limit";
public static final String CONCURRENCY_LIMIT = "concurrency_limit";
```
— `fe/fe-core/.../catalog/ResourceGroup.java:35-51`

두 가지가 눈에 띈다.

**`PLAN_CPU_COST_RANGE` / `PLAN_MEM_COST_RANGE`** — **옵티마이저가 추정한 비용으로 그룹을 고른다.** 즉 "무거워 보이는 쿼리는 무거운 그룹으로"가 가능하다. Trino 의 `SelectionCriteria`(사용자·소스·쿼리 타입)에는 비용 항목이 없다.

**`BIG_QUERY_*_LIMIT` 3종** — 실행 중 감시용 한도다. 4절에서 실제로 동작함을 확인한다.

### 3-2. 격리는 자체 스케줄러다 — cgroup 이 아니다

**`plan/01` 의 전제를 정정한다.** BE 전체에서 cgroup 을 언급하는 파일은 4개(`exec_env.cpp`, `cpu_info.h/.cpp`, `mem_info.cpp`)뿐이고, 유일한 실사용은 자기 컨테이너 구성을 읽는 것이다.

```cpp
// Disable bind cpus when cgroup has cpu quota but no cpuset.
                              (!CpuInfo::is_cgroup_with_cpu_quota() || CpuInfo::is_cgroup_with_cpuset());
```
— `be/src/runtime/exec_env.cpp:450-452`

실제 격리는 `be/src/exec/workgroup/` 이다.

```cpp
PipelineExecutorSet(const PipelineExecutorSetConfig& conf, std::string name, CpuUtil::CpuIds cpuids,
                    std::vector<CpuUtil::CpuIds> borrowed_cpuids);
```
— `be/src/exec/workgroup/pipeline_executor_set.h:50-51`

**그룹마다 실행기 묶음(드라이버 실행기 + 스캔 실행기 + 커넥터 스캔 실행기)을 따로 두고, 지정된 CPU 에 붙인다.** `A-3-02` 에서 본 파이프라인 실행 구조가 그룹 단위로 복제되는 셈이다.

가중치는 vruntime 으로 돈다.

```cpp
int64_t runtime_ns() const { return _vruntime_ns * cpu_weight(); }
```
— `be/src/exec/workgroup/work_group.h:66`

리눅스 CFS 와 같은 발상이다 — 가중치가 큰 그룹의 가상 시간이 천천히 흐르게 해 CPU 를 더 준다.

**`borrowed_cpuids` 가 cgroup 과 결정적으로 다른 점이다.** 전용 코어를 가진 그룹이 놀고 있으면 다른 그룹이 **빌려 쓴다.** cgroup 의 cpuset 은 이런 대여를 하지 못한다.

## 4. 실측

전문은 `docs/evidence/B/20260904-resource-isolation-probes.md`.

### 4-1. StarRocks — 실행 중인 쿼리를 중단시킨다

```sql
CREATE RESOURCE GROUP rg_probe TO (user='root')
WITH ('cpu_weight'='4','mem_limit'='0.2','concurrency_limit'='2','big_query_scan_rows_limit'='1000');
```

| 쿼리 | 결과 |
|---|---|
| `SELECT count(n_name) FROM nation` (25행) | **25** |
| `SELECT sum(l_quantity) FROM lineitem` (60,175행) | ✗ `exceed big query scan_rows limit: current is 60175 but limit is 1000: BE:10001` |

**오류 출처가 `BE:10001` 이다.** FE 가 계획 단계에서 막은 것이 아니라 **BE 가 스캔하면서 행을 세다가 끊었다.**

`count(*)` 로는 판별되지 않는다 — 메타데이터 최적화로 행을 읽지 않기 때문이다(`A-2-04` 3-7). 측정을 설계할 때 이 함정을 먼저 넘어야 했다.

### 4-2. Trino — 짧은 쿼리는 한도를 빠져나간다

`lineitem` 의 실제 물리 입력은 **1.34MB** 다. 그보다 한참 작은 한도를 걸었다.

| `query_max_scan_physical_bytes` | 결과 |
|---|---|
| 1GB | 1536127.0 |
| 100kB | **1536127.0** (통과) |
| 10kB | **1536127.0** (통과) |
| **1kB** | **1536127.0** (통과) |

**1kB 한도에서도 1.34MB 를 읽고 성공했다.**

버그가 아니라 설계다. 2-3 에서 본 대로 검사가 **1초 주기 폴링**이고, 이 쿼리는 1초 안에 끝난다. **한 번도 검사받지 않았다.**

**이 결과를 "Trino 의 한도가 무용하다"로 읽으면 안 된다.** 이 한도는 *폭주하는 장수 쿼리*를 잡기 위한 것이고, 그런 쿼리는 반드시 1초 이상 돈다. 다만 **짧고 무거운 쿼리가 다수 몰리는 상황에는 무력하다.**

### 4-3. 판별하지 못한 것

**"가중치대로 CPU 가 나뉘는가"는 재지 못했다.** BE 1대 / worker 1대라 경합이 없다. 확인한 것은 *한도가 실행 중에 강제되는가* 뿐이다.

Trino 쪽 리소스 그룹은 랩에 아예 구성돼 있지 않아, **그룹 단위 큐잉 자체를 실측하지 못했다.** 2절은 전부 코드 독해다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 설정 수단 | **플러그인**(파일/DB) + SPI 11종 | **SQL** (`CREATE RESOURCE GROUP`) |
| 분류 기준 | 사용자·소스·쿼리 타입·클라이언트 태그 | 위 + **DB** + **옵티마이저 추정 비용 범위** |
| 강제 지점 | **입장 통제** — `canRunMore()` | **실행 통제** — BE 스캔·연산 중 |
| CPU 나누기 | 대기열 정책 4종(FAIR/WEIGHTED/…) | **CPU 친화도 바인딩 + 가중 vruntime + 전용 코어 + 대여** |
| 실행 중 한도 | 그룹 밖 쿼리 설정, **1초 폴링** | 그룹 속성(`big_query_*`), **즉시** |
| 짧은 쿼리 | **빠져나감**(실측) | 빠져나가지 못함(실측) |
| 격리 기술 | JVM 스레드 풀 공유 | **자체 스케줄러**(cgroup 아님) |

### 5-2. 왜 Trino 는 실행 중에 조이지 않는가

**할 수 없기 때문이 아니라, 할 자리가 없기 때문에 가깝다.**

`A-3-02` 에서 본 대로 Trino 483 의 기본 실행은 드라이버당 스레드다. 스레드는 JVM 이 OS 에 맡기고, Trino 가 "이 스레드는 천천히 돌아라"라고 지시할 수단이 없다. 결국 조절할 수 있는 것은 **몇 개를 동시에 돌릴 것인가** 뿐이다.

그래서 **입장 통제에 정교함이 집중됐다** — soft/hard 이중 한도, 선형 페널티, 대기열 정책 4종, 계층형 그룹.

### 5-3. 왜 StarRocks 는 실행 중에 조일 수 있는가

BE 가 C++ 이고 **자기 스레드를 직접 만들어 CPU 에 붙이기 때문**이다. `PipelineExecutorSet` 이 그룹마다 별도 실행기를 두는 순간, "이 그룹은 코어 4개에서만 돈다"가 성립한다.

**대가는 복잡도다.** 그룹 수만큼 실행기 묶음이 생기고, 코어 대여 로직과 vruntime 회계가 붙는다. `B-1-01` 3-1 에서 본 `MemTracker::Type` 에 `RESOURCE_GROUP_BIG_QUERY` 가 따로 있는 것도 이 구조의 일부다.

이 축에서도 `A-3-01`·`A-5-03` 과 같은 구도가 반복된다 — **런타임을 직접 소유하면 더 세밀하게 통제할 수 있고, 그만큼 복잡해지고 결함의 대가도 커진다.**

### 5-4. 분류 기준에 "추정 비용"이 있다는 것

`PLAN_CPU_COST_RANGE` / `PLAN_MEM_COST_RANGE` 는 다른 축과 이어지는 항목이다. **옵티마이저의 비용 추정이 리소스 격리의 입력이 된다**는 뜻이므로, `A-2-03`(비용 모델)과 `A-2-07`(통계)의 정확도가 곧 격리의 정확도가 된다.

**통계가 없으면 이 분류도 흔들린다.** `A-2-01` 4절에서 통계 부족이 플랜을 바꾼 사례를 보았는데, 같은 일이 여기서는 "무거운 쿼리가 가벼운 그룹으로 들어가는" 형태로 나타날 수 있다. **이 랩에서는 확인하지 못했다.**

Trino 에는 대응물이 없다 — 분류가 **쿼리를 보기 전 정보**(사용자, 소스, 클라이언트 태그)로만 이뤄진다. 대신 흔들릴 일도 없다.

## 6. 결론

**동등하지 않다 — 강제 지점이 근본적으로 다르다.**

- **Trino**: 입장 통제. `canRunMore()` 가 전부이고, 실행 중인 쿼리는 느려지지 않는다. 실행 중 한도는 그룹 밖에 있고 **1초 폴링**이라 짧은 쿼리는 빠져나간다(실측)
- **StarRocks**: 실행 통제. CPU 친화도 바인딩과 가중 vruntime 으로 실제로 CPU 를 나누고, **BE 가 스캔 도중 쿼리를 중단시킨다**(실측). **cgroup 이 아니다** — `plan/01` 전제 정정
- **설정**: Trino 는 플러그인, StarRocks 는 SQL. 운영 편의는 StarRocks 쪽이 낫다
- **분류**: StarRocks 만 **옵티마이저 추정 비용**으로 그룹을 고를 수 있다

**실무 결론**

1. **짧고 무거운 쿼리가 다수 몰리는 워크로드라면 Trino 의 리소스 그룹만으로는 부족하다.** 1초 안에 끝나는 쿼리는 스캔·CPU 한도를 지나친다. 동시 실행 수 제한이 실질적인 유일한 수단이다
2. **StarRocks 는 `big_query_scan_rows_limit` 로 폭주 쿼리를 즉시 끊을 수 있다.** 다만 그 한도를 `count(*)` 로 시험하면 안 된다 — 메타데이터 최적화로 통과한다
3. **StarRocks 에서 그룹을 나눌 때 `exclusive_cpu_cores` 는 신중히.** 코어 대여가 있어 낭비는 덜하지만, 그룹이 많아지면 실행기 묶음도 그만큼 늘어난다
4. **StarRocks 의 비용 기반 분류는 통계에 의존한다.** 통계가 없는 외부 테이블에서는 분류가 흔들릴 수 있다(`A-2-07`)

### 아직 답하지 않은 것

- **경합 상황 전부** — BE 1대 / worker 1대라 "가중치대로 CPU 가 나뉘는가"를 재지 못했다. 이 축의 핵심 주장이 미검증으로 남는다
- **Trino 리소스 그룹의 실측** — 랩에 구성돼 있지 않다. 2절은 전부 코드 독해다
- **코어 대여의 실효** — `borrowed_cpuids` 가 실제로 얼마나 낭비를 줄이는지 모른다
