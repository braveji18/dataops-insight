## 1. 비교 관점

조인 순서 결정은 옵티마이저에서 실행 시간에 가장 크게 영향을 주는 결정이고, 동시에 탐색 공간이 조인 개수에 대해 지수적으로 커지는 부분이다. 따라서 모든 엔진은 **"얼마나 넓게 탐색할 것인가 vs 컴파일에 얼마나 쓸 것인가"** 를 어딘가에서 잘라야 한다. 이 문서는 두 엔진이 그 선을 **어디에, 어떤 방식으로** 긋는지를 본다.

결론부터: 두 엔진은 자르는 방식이 근본적으로 다르다. **Trino는 한도 안에서는 항상 전수 탐색을 하고 한도를 넘으면 리오더 자체를 포기**한다. **StarRocks는 규모에 따라 알고리즘을 갈아끼우며 훨씬 큰 조인까지 처리**한다. 그 결과 조인 5개짜리 평범한 쿼리에서 이미 플랜 모양이 갈린다(4절에서 실측).

## 2. Trino 구현

### 2-1. 위치 — 반복 최적화기 안의 규칙 하나

Trino의 조인 리오더는 독립된 단계가 아니라 `IterativeOptimizer` 가 돌리는 **규칙(Rule)** 이다.

- `works/trino/core/trino-main/src/main/java/io/trino/sql/planner/iterative/IterativeOptimizer.java:66` — 규칙 집합을 받아 memo 위에서 고정점까지 반복
- `works/trino/core/trino-main/src/main/java/io/trino/sql/planner/PlanOptimizers.java:807-817` — `ReorderJoins` 를 담은 `IterativeOptimizer` 인스턴스. 소스의 주석이 `// Because ReorderJoins runs only once,` 로 시작한다 — **한 번만 돈다**
- `PlanOptimizers.java` 는 `IterativeOptimizer` 를 **43번** 생성한다. 즉 최적화 파이프라인 전체가 "규칙 묶음을 순서대로 돌리는" 구조이고, 조인 리오더는 그중 한 칸이다

전체 규칙 수는 `iterative/rule/` 아래 **232개**다.

### 2-2. 탐색 — 부분집합 분할 전수 열거

핵심은 `ReorderJoins.JoinEnumerator` 다.

- `works/trino/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java:285-295` — `generatePartitions()` 가 `powerSet` 으로 **모든 이분할**을 만든다. 0번 원소를 포함하는 부분집합만 남겨 대칭 중복을 제거한다
- `ReorderJoins.java:249-251` — 각 분할마다 `createJoinAccordingToPartitioning()` 으로 플랜을 만들고 비용을 비교한다. 재귀적으로 하위 그룹에도 같은 열거를 적용하므로 **bushy 트리가 자연스럽게 나온다**
- `ReorderJoins.java:129` — `getJoinReorderingStrategy(session) == AUTOMATIC` 일 때만 동작

이것은 전형적인 DP 전수 열거다. **left-deep 으로 제한하지 않는다.**

### 2-3. 자르는 지점 — 개수 한도 하나

- `works/trino/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java:51` — `maxReorderedJoins = 8` (기본값)
- `ReorderJoins.java:582` — `getMaxReorderedJoins()` 를 `JoinNodeFlattener` 에 `joinLimit + 1` 로 넘긴다. 즉 조인 트리를 평탄화할 때 **소스 개수가 한도를 넘으면 더 이상 평탄화하지 않는다** → 넘는 부분은 원래 순서 그대로 남는다
- `OptimizerConfig.java:105-110` — 전략은 `NONE` / `ELIMINATE_CROSS_JOINS` / `AUTOMATIC` 3단. 기본 `AUTOMATIC`
- 시간 안전장치는 별도로 `IterativeOptimizer.java:118, 381-382` 의 `optimizer_timeout` 이 담당한다. 초과 시 플랜을 포기하고 **예외를 던진다**

정리하면 Trino의 조절 손잡이는 **개수 한도 하나 + 전역 타임아웃**이다. 한도 이하에서는 탐색 강도를 낮추는 중간 단계가 없다.

## 3. StarRocks 구현

### 3-1. 위치 — Cascades memo 최적화 진입 직전의 디스패치

StarRocks는 Cascades 구조다(`optimizer/Memo.java`, `GroupExpression.java`, `task/` 아래 `OptimizeGroupTask` / `ApplyRuleTask` / `EnforceAndCostTask` 등 태스크 기반 탐색). 그런데 **조인 리오더는 memo 탐색에 맡기지 않고, memo 최적화 시작 시점에 조인 개수를 세어 경로를 가른다.**

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java:956-972`:

```java
int innerCrossJoinNode = Utils.countJoinNodeSize(tree, JoinOperator.innerCrossJoinSet());
if (!sessionVariable.isDisableJoinReorder() && innerCrossJoinNode < sessionVariable.getCboMaxReorderNode()) {
    if (innerCrossJoinNode > sessionVariable.getCboMaxReorderNodeUseExhaustive()) {
        new ReorderJoinRule().transform(tree, context);              // 휴리스틱 경로
        context.getRuleSet().addJoinCommutativityWithoutInnerRule();
    } else {
        ...
        context.getRuleSet().addJoinTransformationRules();           // memo 전수 탐색 경로
    }
}
```

- **조인 ≤ 4** (`cbo_max_reorder_node_use_exhaustive`): 조인 변환 규칙(교환·결합법칙 등)을 룰셋에 넣고 **Cascades memo가 전수 탐색**하게 둔다
- **조인 > 4**: memo에 맡기지 않고 `ReorderJoinRule` 이 **미리 후보 순서를 계산해 넣은 뒤**, 교환법칙 규칙만 추가한다
- **조인 ≥ 50** (`cbo_max_reorder_node`, INVISIBLE): 리오더를 **아예 하지 않는다**

### 3-2. 휴리스틱 경로 — 알고리즘 여러 개를 동시에 후보로

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/join/ReorderJoinRule.java:247-268`:

| 알고리즘 | 조건 | 파일 |
|---|---|---|
| Left-deep | **항상** | `rule/join/JoinReorderLeftDeep.java` |
| DP | `atomSize ≤ 62` **그리고** `≤ cbo_max_reorder_node_use_dp`(기본 **10**) | `rule/join/JoinReorderDP.java` |
| Greedy | `≤ cbo_max_reorder_node_use_greedy`(기본 **16**) | `rule/join/JoinReorderGreedy.java` |

세 알고리즘의 결과를 **모두 memo에 넣고** 비용으로 고른다. 하나를 고르는 게 아니라 후보를 늘리는 구조다. `rule/join/JoinReorderFactory.java:46-64` 에 같은 디스패치가 `createJoinReorderAdaptive()` 로도 있다.

DP의 `62` 상한은 소스 주석대로 "부분집합 열거에 long 비트마스크를 쓰기 때문"이고, `10` 이라는 기본값에는 근거가 주석으로 붙어 있다 — `// 10 table join reorder takes more than 100ms`.

### 3-3. 통계가 없으면 left-deep 으로 퇴화한다

`ReorderJoinRule.java:250-253`:

```java
// If there is no statistical information, the DP and greedy reorder algorithm are disabled,
// and the query plan degenerates to the left deep tree
if (Utils.hasUnknownColumnsStats(innerJoinRoot) && ...) { continue; }
```

**통계가 없는 컬럼이 하나라도 있으면 DP·greedy를 건너뛰고 left-deep만 남긴다.**

Trino에도 대응하는 분기가 있지만 **행동이 다르다.** `ReorderJoins.java:252-255` 는 열거 도중 비용을 알 수 없는 분할이 하나라도 나오면 그 그룹 전체에 대해 `UNKNOWN_COST_RESULT` 를 memo에 넣고 **즉시 반환한다**(하위 그룹도 `:343-345` 에서 같은 방식으로 전파). `UNKNOWN_COST_RESULT` 는 `:716` 에서 `planNode = Optional.empty()` 로 정의돼 있고, `apply()` 는 플랜이 없으면 `:137-139` 에서 `Result.empty()` 를 돌려준다 — 즉 **규칙이 발화하지 않고 쿼리에 작성된 조인 순서가 그대로 남는다.**

| 통계가 부실할 때 | 결과 |
|---|---|
| Trino | 리오더 **자체를 포기** → 사용자가 쓴 순서 유지 |
| StarRocks | DP·greedy만 포기 → **left-deep 재배치는 수행** |

둘 다 "비용을 믿을 수 없으면 탐색하지 않는다"는 원칙은 같지만, StarRocks는 그 상태에서도 최소한의 재배치를 하고 Trino는 손을 뗀다. **외부 카탈로그처럼 통계가 부실한 환경에서 갈리는 지점**이며, A-5(커넥터)와 교차하는 항목이다. 어느 쪽이 유리한지는 이 문서에서 판정하지 않는다 — 검증하려면 통계 없는 테이블로 실측해야 한다.

### 3-4. 기본값

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java:1752-1767`:

```
cbo_max_reorder_node_use_exhaustive = 4     # 이하면 memo 전수 탐색
cbo_max_reorder_node_use_dp         = 10
cbo_max_reorder_node_use_greedy     = 16
cbo_max_reorder_node                = 50    # 이상이면 리오더 안 함 (INVISIBLE)
```

## 4. 실측 — 조인 5개에서 이미 갈린다

TPC-H Q5 형태의 6테이블(inner 조인 5개) 쿼리를 양쪽에 돌렸다. 조인 5개는 **StarRocks의 임계값 4를 넘고 Trino의 한도 8은 넘지 않는** 구간이다.

| 엔진 | 조인 트리 | 형태 |
|---|---|---|
| Trino 483 | `(lineitem ⋈ (supplier ⋈ (nation ⋈ region))) ⋈ (orders ⋈ customer)` | **bushy** |
| StarRocks 4.0.14 (기본) | `((((lineitem ⋈ orders) ⋈ customer) ⋈ supplier) ⋈ nation) ⋈ region` | **left-deep** |
| StarRocks 4.0.14 (`cbo_max_reorder_node_use_exhaustive=10`) | `(lineitem ⋈ (orders ⋈ customer)) ⋈ (supplier ⋈ (nation ⋈ region))` | **bushy** |

임계값 하나만 4 → 10으로 올리자 StarRocks의 플랜이 left-deep에서 bushy로 바뀌었다. 통계나 카디널리티가 아니라 **3-1의 디스패치가 원인임이 확정된다.** 결과값은 세 경우 모두 동일했다.

재현 절차와 한정은 `docs/evidence/A-2/20260831-join-reorder-algorithm-threshold.md`.

## 5. 설계 차이와 그 원인

| | Trino | StarRocks |
|---|---|---|
| 리오더의 위치 | 반복 최적화기의 규칙 하나, **한 번만** 실행 | Cascades memo 진입 직전의 **명시적 디스패치** |
| 탐색 방식 | 부분집합 분할 전수 열거(DP) 단일 | 규모별 4단계: memo 전수 → DP → greedy → 포기 |
| 전수 탐색 한계 | **8개** | **4개** |
| 리오더 가능 최대 | **8개** (넘으면 평탄화 중단) | **50개** (그 사이는 휴리스틱) |
| 트리 모양 | bushy 허용 | 휴리스틱 경로에서는 사실상 left-deep 편향 |
| 통계 없을 때 | **리오더 포기** → 작성된 순서 유지 | DP·greedy 비활성 → **left-deep 재배치는 수행** |

차이의 뿌리는 **두 엔진이 상정하는 워크로드**에 있다고 보는 것이 자연스럽다.

Trino는 페더레이션 쿼리 엔진이다. 커넥터가 통계를 주지 않는 경우가 흔하고, 조인 대상이 수십 개로 늘어나는 상황보다 "10개 이하 조인을 잘 푸는 것"이 실제 사용 패턴에 가깝다. 그래서 **비용을 믿을 수 있는 범위에서는 최대한 잘 찾고, 그 밖에서는 손을 떼는** 일관된 정책을 택한다 — 개수 한도를 넘을 때도, 통계가 없을 때도 결과는 같다(리오더 안 함).

StarRocks는 자체 스토리지와 통계 수집기를 갖고 있어(`plan/01` C-1) 통계 가용성을 전제할 수 있고, BI 대시보드처럼 조인이 많은 쿼리를 상정한다. 조인 20개짜리 쿼리를 "리오더 없음"으로 두는 것은 받아들이기 어렵다. 그래서 **품질을 단계적으로 낮추더라도 끝까지 뭔가는 하는** 정책을 택한다 — 통계가 없어도 left-deep 재배치는 남긴다.

단, 이 해석은 **코드 구조에서 읽어낸 것이지 실측으로 검증한 것이 아니다.** 검증 가능한 형태로 만들려면 "통계 없는 외부 테이블에서 두 엔진의 플랜이 어떻게 갈리는가"를 측정해야 한다.

## 6. 결론

**동등하지 않고, 우열도 아니다 — 트레이드오프가 반대 방향이다.**

- **조인 5~8개 구간**: Trino가 더 넓게 탐색한다. StarRocks는 이미 휴리스틱이다
- **조인 9~50개 구간**: StarRocks만 리오더한다. Trino는 평탄화를 멈춰 사실상 작성된 순서를 따른다
- **조인 ≤4**: 양쪽 다 전수 탐색. 이 구간에서 플랜이 다르면 원인은 탐색 공간이 아니라 **비용 모델**이다 (A-2 후속 문서 주제)
- **통계가 부실한 환경**: Trino는 리오더를 포기하고 작성된 순서를 쓰며, StarRocks는 left-deep 재배치까지는 한다. 외부 카탈로그 비교(A-5)에서 실측으로 다시 다뤄야 한다

운영 관점에서 손잡이 위치도 다르다. Trino는 `join_reordering_strategy` / `max_reordered_joins` 둘로 조절하고, StarRocks는 알고리즘별 임계값 3개(+ INVISIBLE 상한)를 따로 조절한다. **StarRocks 쪽이 세밀하게 조절 가능하지만, 어느 경로를 타고 있는지 알아야 손댈 수 있다** — 4절처럼 임계값을 바꿔 플랜 변화를 관찰하는 것이 실질적인 진단법이다.

### 아직 답하지 않은 것

- **어느 쪽 플랜이 실제로 빠른가** — 측정하지 않았다. SF 0.01에서는 의미가 없고, `perf` 프로파일이 필요하다(`plan/02` 6-2절, 현재 호스트 자원 부족)
- **조인 분배 방식(broadcast vs shuffle)** — 이번 실측에서는 세 경우 모두 전량 broadcast라 판별되지 않았다. `DetermineJoinDistributionType`(`PlanOptimizers.java:878`) 대 StarRocks의 분배 결정은 별도 문서로 다룬다
- **비용 모델 자체의 비교** — 같은 탐색 공간에서 다른 플랜을 고르는 이유
