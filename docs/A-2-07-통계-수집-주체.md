## 1. 비교 관점

앞의 여섯 문서는 전부 "옵티마이저가 통계를 어떻게 쓰는가"를 다뤘다. 이 문서는 그 **앞단**을 본다 — **그 통계는 누가, 언제, 어디에 만들어 두는가.**

세 가지를 나눠 봐야 한다.

| 질문 | Trino | StarRocks |
|---|---|---|
| 누가 **수집**하는가 | 커넥터 (엔진은 계산만 도와준다) | 엔진(FE)이 직접 |
| 어디에 **저장**하는가 | 테이블 포맷 안(Iceberg Puffin, HMS 등) | 엔진 내부 DB `_statistics_` |
| 언제 **갱신**되는가 | 사람이 `ANALYZE`, 또는 **쓰기 시점** | 위 둘 + **백그라운드 자동 수집** |

이 축이 A-2 의 마지막 항목인 이유가 있다. **앞 여섯 문서에서 "통계가 없으면/틀리면"이라는 단서가 반복해서 붙었는데, 그 단서를 결정하는 것이 바로 이 계층이다.**

결론부터: **모델의 표현력은 StarRocks 가 넓고(문자열 범위·히스토그램·다중 컬럼), 운영 자동화는 StarRocks 가 압도적이다. 대신 Trino 는 통계를 테이블에 남겨 엔진 밖에서도 쓸 수 있게 한다.** 그리고 **두 엔진의 통계는 같은 테이블을 봐도 공유되지 않는다.**

## 2. Trino 구현

### 2-1. 통계는 커넥터가 준다

옵티마이저가 통계를 얻는 창구는 하나다 — `works/trino/core/trino-spi/src/main/java/io/trino/spi/connector/ConnectorMetadata.java:452`:

```java
default TableStatistics getTableStatistics(ConnectorSession session, ConnectorTableHandle tableHandle)
```

수집 쪽도 SPI 다.

| 라인 | 메서드 | 역할 |
|---|---|---|
| `:739` | `getStatisticsCollectionMetadata` | `ANALYZE` 시 **무엇을 계산해 달라고 할지** 커넥터가 지정 |
| `:747` | `beginStatisticsCollection` | 수집 시작 |
| `:755` | `finishStatisticsCollection` | 계산된 값을 커넥터에 **넘겨준다** |
| `:731` | `getStatisticsCollectionMetadataForWrite` | INSERT/CTAS 중 함께 계산할 통계 지정 |

**분업이 명확하다 — 무엇을 모을지와 어디에 둘지는 커넥터가 정하고, 실제 계산(집계 쿼리)은 엔진이 실행한다.**
엔진 쪽 플래너에 `StatisticsAggregationPlanner.java` 가 있어서 `ANALYZE` 를 집계 플랜으로 바꾼다.

엔진에는 **통계 저장소도, 자동 수집 스레드도 없다.** `io.trino.cost` (54파일 **7,056줄**)는 전부 소비 측 — 받은 통계로 추정하는 코드다.

### 2-2. 통계 모델이 4개 필드다

`core/trino-spi/src/main/java/io/trino/spi/statistics/TableStatistics.java:31-32`:

```java
private final Estimate rowCount;
private final Map<ColumnHandle, ColumnStatistics> columnStatistics;
```

`ColumnStatistics.java:26-29`:

```java
private final Estimate nullsFraction;
private final Estimate distinctValuesCount;
private final Estimate dataSize;
private final Optional<DoubleRange> range;
```

**컬럼당 네 개뿐이다.** 그리고 `range` 의 타입이 `DoubleRange` 다 — **숫자 범위만 표현할 수 있다.** 문자열·날짜 컬럼의 최소·최대는 이 모델에 담기지 않는다(4-1의 실측에서 그대로 드러난다).

수집을 요청할 수 있는 종류는 `ColumnStatisticType` 8종이다 — `MIN_VALUE`, `MAX_VALUE`, `NUMBER_OF_DISTINCT_VALUES`, `NUMBER_OF_DISTINCT_VALUES_SUMMARY`, `NUMBER_OF_NON_NULL_VALUES`, `NUMBER_OF_TRUE_VALUES`, `MAX_VALUE_SIZE_IN_BYTES`, `TOTAL_SIZE_IN_BYTES`.

**히스토그램은 없다.** `io/trino/spi/statistics/` 디렉토리에 히스토그램 관련 클래스가 아예 없다. A-2-03에서 본 균등 분포 가정은 이 모델의 귀결이다.

### 2-3. Iceberg 의 경우 — 통계는 테이블 안에 있다

`plugin/trino-iceberg/src/main/java/io/trino/plugin/iceberg/TableStatisticsReader.java`:

- `:227-233` — 행 수와 null 수는 **manifest 요약**에서 (`summary.recordCount()`, `summary.nullCounts()`)
- `:267` — min/max 는 데이터 파일 메트릭에서
- `:90`, `:293` — **NDV 는 Puffin blob** 에서 (`apache-datasketches-theta-v1` 의 `ndv` 속성)

즉 **통계가 Iceberg 테이블 자체에 저장된다.** Trino 를 지워도 통계는 남고, Spark 등 다른 엔진도 같은 것을 읽을 수 있다.

### 2-4. 자동 수집은 "쓰기 시점"에만 있다

Trino 에 백그라운드 수집은 없지만, **쓰기 중 수집**은 기본으로 켜져 있다 — `plugin/trino-iceberg/.../IcebergConfig.java:77`:

```java
private boolean collectExtendedStatisticsOnWrite = true;
```

세션 속성 `collect_extended_statistics_on_write` 로 끌 수 있다. 4-2의 실측에서 **CTAS 만으로 NDV 가 생겼다.**

정리하면 Trino 의 통계 수명주기는 이렇다.

| 시점 | 동작 |
|---|---|
| INSERT / CTAS | 커넥터가 요청한 통계를 함께 계산해 테이블에 기록(기본 켜짐) |
| `ANALYZE` | 사람이 실행 |
| 그 외 | **아무 일도 일어나지 않는다** |
| 통계 삭제 | Iceberg 는 `ALTER TABLE … EXECUTE drop_extended_stats` |

## 3. StarRocks 구현

### 3-1. 통계 수집이 독립된 서브시스템이다

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/statistic/` — 파일 **70개**(하위 패키지 `base`/`columns`/`hyper`/`sample` 포함), **13,830줄**.
여기에 소비·캐시 측인 `sql/optimizer/statistics/` 가 **10,348줄** 더 있다.

| 구성 | 내용 |
|---|---|
| `StatisticAutoCollector` | FE 데몬 스레드 — 자동 수집 |
| `AnalyzeMgr` / `AnalyzeJob` / `AnalyzeStatus` | 수집 작업 관리·이력 |
| `FullStatisticsCollectJob` / `SampleStatisticsCollectJob` / `HyperStatisticsCollectJob` | 전수 / 샘플 / HLL 기반 수집 |
| `ExternalFullStatisticsCollectJob` / `ExternalSampleStatisticsCollectJob` | **외부 카탈로그 전용** |
| `HistogramStatisticsCollectJob` / `ExternalHistogramStatisticsCollectJob` | 히스토그램 |
| `MultiColumnHyperStatisticsCollectJob` | **다중 컬럼 결합 NDV** |
| `columns/` (5파일) | **술어에 쓰인 컬럼 추적** |
| `StatisticsMetaManager` | 통계 저장 테이블 생성·관리 |

### 3-2. 통계는 엔진 안의 진짜 테이블에 쌓인다

`statistic/StatsConstants.java:66-72`:

```java
public static final String STATISTICS_DB_NAME = "_statistics_";
public static final String SAMPLE_STATISTICS_TABLE_NAME = "table_statistic_v1";
public static final String FULL_STATISTICS_TABLE_NAME = "column_statistics";
public static final String EXTERNAL_FULL_STATISTICS_TABLE_NAME = "external_column_statistics";
public static final String HISTOGRAM_STATISTICS_TABLE_NAME = "histogram_statistics";
public static final String EXTERNAL_HISTOGRAM_STATISTICS_TABLE_NAME = "external_histogram_statistics";
public static final String MULTI_COLUMN_STATISTICS_TABLE_NAME = "multi_column_statistics";
```

**SQL 로 조회할 수 있는 일반 테이블이다**(4-1). 스키마도 Trino 의 4필드보다 넓다 — `row_count`, `data_size`, `ndv`(**HLL 스케치 타입**), `null_count`, `min`, `max`(둘 다 `varchar(1048576)`), `update_time`, 그리고 `partition_name` 으로 **파티션 단위** 보관.

`min`/`max` 가 varchar 라는 점이 Trino 의 `DoubleRange` 와 대비된다 — **문자열 컬럼의 범위를 담을 수 있다.**

### 3-3. 자동 수집 — 주기적으로, 그리고 골라서

`StatisticAutoCollector.java:49`:

```java
super("AutoStatistic", Config.statistic_collect_interval_sec * 1000);
```

FE Config 에 통계 항목이 **40개** 있다. 주요 기본값:

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `enable_statistic_collect` | `true` | 자동 수집 전체 |
| `statistic_collect_interval_sec` | `600` (10분) | 스케줄러 주기 |
| `statistic_auto_analyze_start_time` / `end_time` | — | 수집 허용 시간대 |
| `statistic_auto_collect_ratio` | `0.8` | 통계 "건강도" 임계 — 이보다 낮으면 재수집 |
| `statistic_auto_collect_small_table_rows` | `10,000,000` | 소/대 테이블 경계 |
| `statistic_auto_collect_small_table_interval` | `0`초 | 작은 테이블은 제한 없이 |
| `statistic_auto_collect_large_table_interval` | `43,200`초 (12시간) | 큰 테이블은 12시간에 한 번 |
| `statistic_auto_collect_sample_threshold` | `0.3` | 이 비율 이상이면 샘플링으로 전환 |
| `statistic_sample_collect_rows` | `200,000` | 샘플 행 수 |
| `enable_statistic_collect_on_first_load` / `on_update` | `true` | 적재 시 수집 |
| `statistic_auto_collect_histogram_interval` | `3,600`초 | 히스토그램 갱신 주기 |

**"작은 테이블은 자주, 큰 테이블은 12시간에 한 번, 너무 크면 샘플링"** 이라는 정책이 설정으로 표현돼 있다.

### 3-4. 술어에 쓰인 컬럼만 골라 수집한다

가장 특징적인 부분이다. `statistic/columns/PredicateColumnsMgr.java` 가 **옵티마이저를 지나가는 쿼리에서 컬럼이 어떻게 쓰였는지 기록**한다 — `ColumnUsage.java:187-192`:

```java
public enum UseCase {
    NORMAL,
    PREDICATE,
    JOIN,
    GROUP_BY,
    DISTINCT;
}
```

기록은 `_statistics_.predicate_columns` 테이블에 `statistic_predicate_columns_persist_interval_sec`(기본 60초) 주기로 영속화되고, 자동 수집기가 이것을 보고 **통계가 실제로 필요한 컬럼만** 수집한다 (`statistic_auto_collect_predicate_columns_threshold` 기본 32).

4-3의 실측에서 이 동작이 그대로 관찰됐다.

### 3-5. 모델의 표현력

| 항목 | Trino | StarRocks |
|---|---|---|
| 행 수 / null / NDV / 데이터 크기 | ✅ | ✅ |
| 숫자 min·max | ✅ | ✅ |
| **문자열·날짜 min·max** | ❌ (`DoubleRange`) | ✅ (`varchar`) |
| **히스토그램** | ❌ (개념 없음) | ✅ (`histogram_statistics`) |
| **다중 컬럼 결합 NDV** | ❌ | ✅ (`multi_column_statistics`) |
| 파티션 단위 통계 | 커넥터에 위임 | ✅ (`partition_name` 키) |
| NDV 표현 | Theta 스케치(Puffin) | HLL 스케치(`hll` 컬럼 타입) |

다중 컬럼 결합 통계는 A-2-04 3-6에서 이미 등장했다 — `cbo_push_down_aggregate_with_multi_column_stats` 가 그것을 쓴다.

## 4. 실측

전체 절차·조건과 정리 내역은 `docs/evidence/A-2/20260904-statistics-ownership-probes.md`.

### 4-1. 같은 테이블, 다른 통계

`lineitem`(60175행)에 대해 양쪽이 갖고 있는 값:

| 컬럼 | 참 NDV | StarRocks | Trino | StarRocks min/max | Trino low/high |
|---|---|---|---|---|---|
| `l_orderkey` | 15000 | **15022** (+0.15%) | **14819** (−1.2%) | 1 / 60000 | 1 / 60000 |
| `l_suppkey` | 100 | 100 | 100 | 1 / 100 | 1 / 100 |
| `l_shipdate` | — | 2530 | 2518 | 1992-01-04 / 1998-11-29 | 1992-01-04 / 1998-11-29 |
| `l_returnflag` | 3 | 3 | 3 | **A / R** | **(빈칸)** |

- NDV 는 양쪽 다 근사값이고 오차 방향이 다르다 — HLL 대 Theta
- **`l_returnflag` 의 min/max 가 Trino 에는 없다.** 2-2의 `DoubleRange` 제약이 그대로 나타난다

StarRocks 쪽 값은 `_statistics_.external_column_statistics` 를 **SQL 로 직접 조회**해서 얻었다. `ndv` 는 `hll` 타입이라 `hll_cardinality()` 로 풀어야 보인다.

### 4-2. Trino 는 쓰기만으로 통계를 만든다

```sql
CREATE TABLE iceberg.bench.statprobe2 AS SELECT l_orderkey, l_suppkey FROM iceberg.bench.lineitem;
```

`ANALYZE` 를 돌리지 않았는데 `SHOW STATS` 가 NDV 를 보여준다 — `l_orderkey` 14830, `l_suppkey` 100.
2-4의 `collectExtendedStatisticsOnWrite = true` 다.

### 4-3. 통계는 공유되지 않는다

같은 테이블을 StarRocks 에서 보면:

| 확인 | 값 |
|---|---|
| `_statistics_.external_column_statistics` 행 수 | **0** |
| `EXPLAIN COSTS` 의 컬럼 통계 | `l_suppkey-->[99.0, Infinity, 0.0, 1.0, 1.0]` **`UNKNOWN`** |
| 스캔 노드 카디널리티(술어 없음) | **60175** |

**행 수는 Iceberg 메타데이터에서 읽지만, Trino 가 Puffin 에 써 둔 NDV 는 읽지 않는다.**

같은 카탈로그, 같은 파일, 같은 스냅샷인데 **각자 자기 통계만 믿는다.** 두 엔진을 같은 레이크하우스에 붙여 쓴다면 **ANALYZE 를 양쪽에서 따로 돌려야 한다.**

### 4-4. StarRocks 는 자동으로, 그것도 골라서 수집했다

probe 를 진행하는 동안 **내가 실행하지 않은 수집 작업**이 이력에 나타났다.

```
27494  iceberg.bench  statprobe   l_suppkey,l_shipdate   FULL  ONCE  SUCCESS  2026-09-04 01:55:34
27499  iceberg.bench  statprobe2  l_suppkey              FULL  ONCE  SUCCESS  2026-09-04 01:56:34
```

**수집된 컬럼 목록이 내가 술어에 쓴 컬럼과 정확히 일치한다.** `statprobe2` 에는 `WHERE l_suppkey > 99` 하나만 던졌고, 수집된 컬럼도 `l_suppkey` 하나다. 테이블 생성부터 수집까지 약 **1분**.

`_statistics_.predicate_columns` 에 근거가 남아 있다 — `usage` 값이 `normal,predicate,group_by` 처럼 **쓰인 방식까지** 기록된다. 3-4의 `ColumnUsage.UseCase` 다.

**Trino 에는 이 개념 자체가 없다.**

### 4-5. 히스토그램은 이 랩에서 쓸 수 없다

```
StarRocks: ANALYZE TABLE iceberg.bench.lineitem UPDATE HISTOGRAM ON l_shipdate WITH 32 BUCKETS
        → ERROR 1064: Can't create histogram statistics on table type is ICEBERG
Trino    : 문법 없음
```

StarRocks 에 저장 테이블과 수집 잡이 있지만 **Iceberg 외부 테이블에는 적용되지 않는다.** 네이티브 테이블에서의 동작은 확인하지 못했다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino | StarRocks |
|---|---|---|
| 수집 주체 | 커넥터(무엇을·어디에) + 엔진(계산) | **엔진(FE) 전부** |
| 저장 위치 | **테이블 포맷 안**(Iceberg Puffin, HMS) | 엔진 내부 DB `_statistics_` |
| 코드 규모 | 소비 측 `io.trino.cost` 7,056줄. **수집 전용 코드는 커넥터에 분산** | 수집 13,830줄 + 소비·캐시 10,348줄 |
| 자동 수집 | **쓰기 시점만**(커넥터별, 기본 켜짐) | 백그라운드 데몬 + 적재 시 + 갱신 시 |
| 수집 대상 선정 | 사람이 `ANALYZE` 로 지정 | **쿼리 관찰 기반**(술어/조인/group by 컬럼) |
| 설정 항목 수 | 커넥터별 소수 | FE Config **40개** |
| 컬럼 통계 필드 | **4개**, 범위는 `DoubleRange`(숫자만) | 6개+, min/max 는 varchar |
| 히스토그램 | 없음 | 있음(단 Iceberg 외부 테이블 불가) |
| 다중 컬럼 결합 NDV | 없음 | 있음 |
| 다른 엔진과 공유 | **가능** — 통계가 테이블에 있다 | 불가 — 엔진 안에 있다 |

### 5-2. 왜 이렇게 갈렸는가

**Trino 는 남의 테이블을 읽는 엔진이다.** 통계를 자기 안에 쌓으려면 (가) 카탈로그가 50개 넘게 있고 각각 갱신 주기가 다른데 **언제 낡았는지 알 방법이 없고**, (나) 코디네이터가 상태를 갖게 되어 무상태 설계가 깨진다. 그래서 **통계를 테이블에 돌려주는** 길을 골랐다.

이 선택의 이득은 분명하다 — **Trino 가 `ANALYZE` 로 만든 통계를 Spark 도, 다른 Trino 클러스터도 읽는다.** 통계가 데이터의 일부가 된다.

대가도 분명하다 — **테이블 포맷이 표현할 수 있는 것만 담을 수 있다.** Iceberg Puffin 표준에 히스토그램 blob 타입이 없으니 히스토그램도 없다. `DoubleRange` 제약도 "여러 포맷에 공통으로 매핑 가능한 최소 집합"을 고른 결과로 읽힌다.

**StarRocks 는 자기 스토리지를 갖고 있고 FE 가 메타데이터를 소유한다.** 통계를 자기 테이블에 쌓는 것이 자연스럽고, 적재·갱신 시점을 알기 때문에 자동 수집도 가능하다. 외부 카탈로그도 같은 틀에 얹었다(`external_*` 테이블).

**A-2-04(푸시다운 판단 주체), A-2-06(MV 소유권)에서 본 것과 같은 축이다 — 남의 것을 존중하느냐, 내 것으로 가져오느냐.**

### 5-3. "통계가 없을 때"의 의미가 다르다

A-2-01·A-2-03에서 반복해 나온 "통계가 없으면"이라는 단서를, 이제 정확히 말할 수 있다.

| | Trino 에서 통계가 없다는 것 | StarRocks 에서 통계가 없다는 것 |
|---|---|---|
| 어떤 상황 | 커넥터가 통계를 못 주거나, 쓰기 시 수집이 꺼져 있거나, `ANALYZE` 를 안 돌렸다 | 자동 수집이 아직 못 따라잡았거나, 꺼져 있다 |
| 지속되는가 | **사람이 개입할 때까지 계속** | **최대 10분~12시간 뒤 스스로 해소** |
| 진단 | `SHOW STATS FOR <table>` | `SHOW ANALYZE STATUS`, `_statistics_` 조회 |

**운영 부담이 다르다.** Trino 에서는 통계 갱신이 **운영자의 일**이고, 잊으면 계속 나쁜 플랜이 나온다. StarRocks 에서는 대체로 저절로 해결되지만, **언제 수집이 도는지 예측하기 어렵고** 수집 자체가 클러스터 자원을 쓴다.

### 5-4. 두 엔진을 같이 쓸 때

4-3이 실무에 직접 걸린다. **같은 Iceberg 레이크하우스에 Trino 와 StarRocks 를 함께 붙이면 통계를 두 번 관리해야 한다.**

- Trino 의 `ANALYZE` → Puffin. StarRocks 는 못 본다
- StarRocks 의 `ANALYZE` → `_statistics_`. Trino 는 못 본다
- 행 수처럼 **테이블 메타데이터에서 직접 읽는 값만** 자동으로 공유된다

한쪽만 `ANALYZE` 를 돌리면 **다른 쪽은 통계 없는 상태로 플랜을 짠다.** 벤치마크에서 두 엔진을 비교할 때 특히 함정이다 — 이 저장소의 `seed.sh` 가 적재 후 **양쪽 모두** `ANALYZE` 를 돌리는 것도 그래서다 — Trino 는 시드 SQL 안의 `ANALYZE` 로, StarRocks 는 그 뒤에 테이블별로 따로 (`scripts/testenv/bin/seed.sh:45-59`).

### 5-5. 표현력 차이가 실제로 걸리는 곳

| 없는 것 | 어디서 걸리는가 |
|---|---|
| 문자열 min/max (Trino) | `WHERE name > 'M'` 같은 술어의 선택도. A-2-03에서 본 균등 분포 가정조차 적용할 근거가 없다 |
| 히스토그램 (Trino) | 편향 분포에서 선택도가 크게 틀린다. A-2-03 참조 |
| 다중 컬럼 결합 NDV (Trino) | 여러 컬럼 group by 의 결과 행 수 추정, 그리고 A-2-04의 집계 푸시다운 판단 |

**다만 이 차이가 실제 플랜을 얼마나 바꾸는지는 측정하지 않았다.** StarRocks 쪽 히스토그램은 이 랩의 Iceberg 테이블에서 아예 쓸 수 없었다(4-5).

## 6. 결론

**모델 표현력과 운영 자동화는 StarRocks 우위, 통계의 이식성은 Trino 우위다.**

- **수집 주체가 다르다는 것은 결국 "통계가 누구 것인가"의 문제다.** Trino 는 테이블에 돌려주고(다른 엔진도 읽는다), StarRocks 는 자기 안에 쌓는다(더 많은 것을 담을 수 있다)
- **자동화는 비교가 안 된다.** StarRocks 는 백그라운드 데몬이 돌고, **쿼리를 관찰해 통계가 필요한 컬럼을 스스로 고른다**(4-4에서 실제로 관찰됐다). Trino 는 쓰기 시점 수집 외에는 사람이 `ANALYZE` 를 실행해야 한다
- **모델 표현력도 StarRocks 가 넓다.** Trino 의 컬럼 통계는 4필드이고 범위가 `DoubleRange` 라 **문자열 min/max 를 담을 수 없다**(4-1에서 확인). 히스토그램과 다중 컬럼 결합 NDV 는 개념 자체가 없다
- **그리고 두 엔진의 통계는 공유되지 않는다.** 같은 Iceberg 테이블을 보면서도 각자 따로 `ANALYZE` 가 필요하다

**운영 판단**

| 상황 | 판단 |
|---|---|
| 레이크하우스에 여러 엔진(Spark, Trino, …)이 붙어 있다 | Trino 방식이 유리하다. 통계가 테이블에 남아 공유된다 |
| 테이블이 많고 갱신이 잦은데 운영 인력이 적다 | StarRocks 방식이 유리하다. `ANALYZE` 를 잊어도 대체로 해결된다 |
| 통계 수집이 클러스터 자원을 쓰면 곤란하다 | Trino 는 예측 가능(사람이 돌린 때만). StarRocks 는 `statistic_auto_collect_*` 로 시간대·주기를 조여야 한다 |
| Trino 와 StarRocks 를 같이 쓴다 | **양쪽에서 각각 `ANALYZE` 를 돌려야 한다.** 한쪽만 하면 다른 쪽은 통계 없이 플랜을 짠다 |
| 문자열 컬럼 술어가 성능을 좌우한다 | Trino 는 이 통계를 아예 갖지 못한다 |

### 아직 답하지 않은 것

- **통계 수집 자체의 비용** — 전수 vs 샘플 수집의 시간·자원을 재지 않았다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **자동 수집의 트리거 조건** — `statistic_auto_collect_ratio`(0.8), 소/대 테이블 경계, 수집 주기의 상호작용을 통제된 조건에서 확인하지 않았다. 4-4는 우연히 관찰된 사례다
- **히스토그램·다중 컬럼 통계의 실효** — StarRocks 네이티브 테이블에서만 쓸 수 있는 경로가 있고, 이 랩은 전부 Iceberg 외부 테이블이었다
- **표현력 차이가 만드는 플랜 차이의 크기** — 문자열 min/max 부재, 히스토그램 부재가 실제로 어떤 쿼리를 얼마나 망치는지는 측정하지 않았다
- **Hive/Delta 등 다른 커넥터** — Hive 는 HMS 에 통계를 두므로 Trino 쪽 동작이 다를 수 있다. Iceberg 하나로만 확인했다
- **통계 갱신 지연이 만드는 오판** — 원본이 바뀐 뒤 통계가 낡은 동안 어떤 플랜이 나오는지는 A-2-06의 MV 신선도와 비슷한 성격의 별도 주제다
