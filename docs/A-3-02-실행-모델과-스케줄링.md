## 1. 비교 관점

A-3-01이 "데이터를 어떤 묶음으로 담는가"였다면, 이 문서는 **"그 묶음을 누가 언제 처리하는가"** 다.

두 엔진 다 같은 뼈대를 쓴다 — **연산자를 사슬로 엮은 실행 단위**를 만들고, 그 단위를 워커 스레드에 배정한다. 갈리는 지점은 셋이다.

1. **한 실행 단위가 스레드를 얼마나 오래 쥐는가**(양자)
2. **오래 도는 쿼리를 어떻게 뒤로 미루는가**(다단계 큐)
3. **연산자가 진행 불가일 때 어떻게 표현하는가**(블로킹 모델)

**결론부터: 두 엔진의 스케줄러 구조는 놀랄 만큼 비슷하다 — 둘 다 다단계 피드백 큐 계보다. 결정적으로 다른 것은 양자의 크기(1초 대 0.1초)와, Trino 483 이 기본 실행기를 바꿨다는 사실이다.**

> ⚠ **`plan/01` 의 전제 정정.** `plan/01` A-3 은 Trino 를 "협력적 멀티태스킹", StarRocks 를 "논블로킹 스케줄러"로 대비시켰다. **483 기준으로 이 대비는 성립하지 않는다.** Trino 는 기본 실행기를 **드라이버당 스레드(thread-per-driver)** 로 바꿨고(2-1), StarRocks 는 오히려 시분할 다단계 큐를 쓴다(3-2). 축이 바뀐 것이 아니라 **양쪽이 서로의 방향으로 한 걸음씩 옮긴 상태**다.

## 2. Trino 구현

### 2-1. 기본 실행기가 바뀌었다 — 시분할에서 드라이버당 스레드로

`works/trino/core/trino-main/src/main/java/io/trino/execution/executor/` 아래에 실행기가 **둘** 있다.

| 디렉토리 | 실행기 | 방식 |
|---|---|---|
| `timesharing/` | `TimeSharingTaskExecutor` | 스레드 풀 + 5단계 피드백 큐 + 1초 시분할 |
| `dedicated/` | `ThreadPerDriverTaskExecutor` | **드라이버 하나당 스레드 하나** + `FairScheduler` |

기본값은 후자다 — `execution/TaskManagerConfig.java:57`:

```java
    private boolean threadPerDriverSchedulerEnabled = true;
```

`execution/executor/dedicated/ThreadPerDriverTaskExecutor.java:90` 이 스케줄러를 만든다:

```java
new FairScheduler(config.getMaxWorkerThreads(), "SplitRunner-%d", Ticker.systemTicker())
```

워커 스레드 수는 `TaskManagerConfig.java:65` 에서 **CPU 코어 × 2** 다.

**`plan/01` 이 적은 "스레드당 split"은 옛 실행기의 서술이고, 483 의 기본은 "드라이버당 스레드"다.** 두 표현은 비슷해 보이지만 다르다 — 전자는 스레드 풀이 split 을 돌아가며 집어 드는 것이고, 후자는 드라이버가 자기 스레드를 갖는 것이다.

### 2-2. 양자는 1초다

새 스케줄러의 시간 단위 — `execution/executor/scheduler/FairScheduler.java`:

```java
    public static final long QUANTUM_NANOS = TimeUnit.MILLISECONDS.toNanos(1000);
```

옛 실행기도 같은 값이었다 — `timesharing/PrioritizedSplitRunner.java:49`:

```java
    public static final Duration SPLIT_RUN_QUANTA = new Duration(1, TimeUnit.SECONDS);
```

**실행기를 바꾸면서도 양자는 1초로 유지했다.** 이 숫자가 3-2의 StarRocks 값과 정확히 10배 차이 난다.

### 2-3. 옛 실행기의 다단계 큐 — 5단계, 지수적 시간 배분

`timesharing/MultilevelSplitQueue.java:41-42`:

```java
    static final int[] LEVEL_THRESHOLD_SECONDS = {0, 1, 10, 60, 300};
    static final long LEVEL_CONTRIBUTION_CAP = SECONDS.toNanos(30);
```

누적 실행 시간이 1초·10초·1분·5분을 넘을 때마다 아래 단계로 내려간다. **짧은 쿼리가 긴 쿼리에 밀리지 않게 하는 장치**이고, `LEVEL_CONTRIBUTION_CAP` 은 한 번의 실행이 우선순위에 미치는 영향에 상한을 둔다.

이 큐는 새 실행기에서는 쓰이지 않는다 — 새 실행기는 `scheduler/SchedulingGroup` 과 `PriorityQueue` 로 공정성을 다르게 구현한다. **단계 개념 자체가 사라진 것이 아니라 그룹 단위 공정 스케줄링으로 대체됐다.**

### 2-4. 동시 실행 split 수를 실행 중에 조절한다

`timesharing/SplitConcurrencyController.java:40-68`:

```java
    public void update(long nanos, double utilization, int currentConcurrency)
    ...
        if (threadNanosSinceLastAdjustment >= adjustmentIntervalNanos && utilization < TARGET_UTILIZATION && currentConcurrency >= targetConcurrency) {
            targetConcurrency++;
```

**CPU 활용률이 목표보다 낮으면 동시 실행 수를 늘리고, 높으면 줄인다.** A-3-01 2-3에서 본 "배치 크기를 런타임에 조절한다"와 같은 성격의 장치가 스케줄링 층에도 있다.

### 2-5. 연산자는 "지금 진행 가능한가"를 메서드로 답한다

`operator/Operator.java`:

```java
    boolean needsInput();       // :41
    void addInput(Page page);   // :47
    Page getOutput();           // :53
    void finish();              // :88
    boolean isFinished();       // :94
```

그리고 진행 불가 상태는 **`ListenableFuture<Void> isBlocked()`** 로 표현한다. 즉 **"언제 다시 깨워달라"를 미래(future)로 돌려준다.** 드라이버는 그 미래가 완료될 때까지 스레드를 놓는다.

`operator/Driver.java:267` 의 `processForDuration(Duration)` 이 양자만큼 돌리고 반환한다.

## 3. StarRocks 구현

### 3-1. 연산자 인터페이스가 거의 같다

`works/starrocks/be/src/exec/pipeline/operator.h`:

```cpp
    virtual bool has_output() const = 0;    // :99
    virtual bool need_input() const = 0;    // :105
    virtual bool is_finished() const = 0;   // :109
    virtual StatusOr<ChunkPtr> pull_chunk(RuntimeState* state) = 0;      // :122
    virtual Status push_chunk(RuntimeState* state, const ChunkPtr& chunk) = 0;  // :125
```

**Trino 의 `needsInput`/`getOutput`/`addInput`/`isFinished` 와 일대일로 대응한다.** 이름만 다르다.

차이는 **진행 불가를 어떻게 표현하는가**다. Trino 는 미래 객체를 돌려주고(2-5), StarRocks 는 **드라이버의 상태 열거값**으로 표현한다 — `pipeline_driver.h:59-75`:

```cpp
enum DriverState : uint32_t {
    NOT_READY = 0,
    READY = 1,
    RUNNING = 2,
    INPUT_EMPTY = 3,
    OUTPUT_FULL = 4,
    PRECONDITION_BLOCK = 5,
    FINISH = 6,
    CANCELED = 7,
    INTERNAL_ERROR = 8,
    PENDING_FINISH = 9,
    ...
```

**12개 상태**로 "왜 못 가는지"를 구분한다. `INPUT_EMPTY`(입력 없음)와 `OUTPUT_FULL`(출력 막힘)을 나눠 두면 스케줄러가 어느 쪽을 먼저 깨울지 판단할 수 있다. Trino 의 미래 객체는 "언제"만 알려주고 "왜"는 알려주지 않는다.

### 3-2. 다단계 피드백 큐 — 8단계

`pipeline/pipeline_driver_queue.h:128-144`:

```cpp
    static constexpr size_t QUEUE_SIZE = 8;
...
    // The time slice of the i-th level is (i+1)*LEVEL_TIME_SLICE_BASE ns,
    // so when a driver's execution time exceeds 0.2s, 0.6s, 1.2s, 2.0s, 3.0s, 4.2s, 5.6s, 7.4s.
    // it will move to next level.
```

**주석이 단계 경계를 그대로 밝힌다** — 0.2초, 0.6초, 1.2초, 2.0초, 3.0초, 4.2초, 5.6초, 7.4초.

Trino 옛 실행기의 5단계(1초·10초·1분·5분)와 비교하면 **StarRocks 쪽이 단계가 많고 간격이 훨씬 촘촘하다.** Trino 는 5분까지 벌리는데 StarRocks 는 7.4초에서 끝난다.

### 3-3. 양자는 100밀리초 — Trino 의 1/10

`pipeline/pipeline_driver.h:581-586`:

```cpp
    static constexpr int64_t YIELD_MAX_TIME_SPENT_NS = 100'000'000L;
...
    static constexpr int64_t YIELD_PREEMPT_MAX_TIME_SPENT_NS = 5'000'000L;
...
    static constexpr int64_t OVERLOADED_MAX_TIME_SPEND_NS = 150'000'000L;
```

| 상수 | 값 | 뜻 |
|---|---|---|
| `YIELD_MAX_TIME_SPENT_NS` | **100ms** | 기본 양자 |
| `YIELD_PREEMPT_MAX_TIME_SPENT_NS` | **5ms** | 더 급한 드라이버가 대기 중일 때 |
| `OVERLOADED_MAX_TIME_SPEND_NS` | **150ms** | 과부하 상태의 상한 |

**Trino 1초 대 StarRocks 100ms — 10배 차이다.** 그리고 StarRocks 에는 **선점(preempt)** 개념이 있어 5ms 만에도 양보한다.

양보 이유를 프로파일에 따로 센다(`pipeline_driver.h:675-677`) — `_yield_by_time_limit_counter`, `_yield_by_preempt_counter`, `_yield_by_local_wait_counter`. **왜 양보했는지가 관측 지표로 노출된다.**

### 3-4. 스레드 수

`be/src/common/config.h:941`:

```
CONF_Int64(pipeline_exec_thread_pool_thread_num, "0");
```

**0 은 "자동"** 이고 실제로는 CPU 코어 수 기반으로 정해진다. Trino 가 코어 × 2 로 명시한 것과 대비된다 — StarRocks 는 C++ 이라 블로킹 IO 를 별도 스레드 풀로 빼기 때문에 실행 스레드를 코어 수에 맞추는 편이 자연스럽다.

## 4. 실측

**이 축은 이 랩에서 실측할 수 있는 것이 거의 없다.**

스케줄링 동작은 **동시 실행 쿼리가 여럿이고 워커가 여럿일 때** 드러난다. 현재 랩은 worker 1대 / BE 1대이고 데이터가 6만 건이라 **모든 쿼리가 첫 양자 안에 끝난다** — 다단계 큐도, 선점도, 동시성 조절도 발화하지 않는다.

관측 지표만 확인했다.

| 엔진 | 스케줄링 관련 노출 지표 |
|---|---|
| Trino | `EXPLAIN ANALYZE` 의 `Blocked` 시간, `Scheduled` 시간 (A-3-01 4-3에서 확인) |
| StarRocks | 프로파일의 `ScheduleTime`, 그리고 코드상 `_yield_by_*_counter` 3종 |

**A-3-01 4-3에서 본 Trino 출력에 `Blocked 880.58ms (Input: 438.95ms, Output: 0.00ns)` 가 있었다** — 입력 대기와 출력 대기를 나눠 센다. StarRocks 의 양보 사유 카운터와 같은 문제의식이다.

**이 문서는 코드 비교까지만 쓴다.** 성능 결론을 내지 않는다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 기본 실행기 | **드라이버당 스레드** + `FairScheduler` | 스레드 풀 + 다단계 피드백 큐 |
| 옛/대안 실행기 | `TimeSharingTaskExecutor` (5단계 큐) — 설정으로 되돌릴 수 있음 | 없음 |
| **양자** | **1초** | **100ms** (선점 시 5ms) |
| 다단계 큐 | 옛 실행기 5단계 (1초~5분) | **8단계** (0.2초~7.4초) |
| 진행 불가 표현 | `ListenableFuture` — "언제" | **상태 열거 12종** — "왜" |
| 동시성 조절 | 런타임 자동(`SplitConcurrencyController`) | 큐 레벨로 간접 |
| 워커 스레드 | 코어 × 2 (명시) | 자동(0 = 코어 기반) |
| 양보 사유 관측 | 입력/출력 대기 시간 분리 | **양보 사유 카운터 3종** |

### 5-2. 양자 10배 차이가 뜻하는 것

양자가 짧으면 **짧은 쿼리의 응답이 빨라지고**, 길면 **문맥 전환 비용이 줄어든다.** 두 엔진의 선택은 각자의 언어·실행 특성과 맞물린다.

- **Trino(1초)** — JVM 에서 스레드 전환과 그에 딸린 캐시 손실이 상대적으로 비싸다. 그리고 A-3-01에서 본 대로 한 묶음이 최대 16MB 라 **한 번 잡으면 오래 처리할 거리가 있다**
- **StarRocks(100ms)** — 묶음이 4,096건 고정이라 **한 번에 처리하는 양이 작고**, C++ 이라 전환 비용도 낮다. 대신 짧은 양자로 응답성을 얻는다

**A-3-01 의 "용량 기준 대 건수 기준"이 스케줄링 층에서 "긴 양자 대 짧은 양자"로 이어진다.** 두 결정은 독립적이지 않다.

### 5-3. "왜 못 가는지"를 구분하는 것의 값

Trino 의 `isBlocked()` 는 미래 객체 하나를 돌려준다. 스케줄러는 그것이 완료되면 다시 스케줄한다 — 단순하고, Java 의 비동기 관례와 잘 맞는다.

StarRocks 의 12개 상태는 **스케줄러가 판단할 재료를 더 준다.** `OUTPUT_FULL`(하류가 막힘)과 `INPUT_EMPTY`(상류가 안 줌)는 대처가 달라야 한다 — 전자는 하류를 먼저 돌려야 하고, 후자는 상류를 돌려야 한다.

**대가는 결합도다.** 상태가 늘면 연산자 구현이 그 상태를 정확히 보고해야 하고, 새 연산자를 추가할 때 실수할 여지가 커진다. Trino 의 미래 객체는 **연산자가 스케줄러의 내부 사정을 몰라도 되게** 만든다 — 플러그인이 연산자를 제공하는 구조(A-3-01 5-5, C-2-01)에서는 이 단순함이 값을 한다.

### 5-4. Trino 가 실행기를 바꾼 것을 어떻게 읽을 것인가

`threadPerDriverSchedulerEnabled = true` 는 **483 에서 기본이 된 비교적 최근의 변경**으로 보인다. 옛 실행기가 코드에 그대로 남아 있고 설정으로 되돌릴 수 있다는 점이 그 방증이다.

드라이버당 스레드는 **스레드가 싸야** 성립한다. Java 의 가상 스레드(virtual thread)가 실용화되면서 가능해진 선택으로 읽히지만, **이 저장소의 클론만으로는 확정할 수 없다** — `ThreadPerDriverTaskExecutor` 가 가상 스레드를 쓰는지 플랫폼 스레드를 쓰는지 확인하지 않았다.

**따라서 "Trino 가 협력적 멀티태스킹을 버렸다"고 단정하면 안 된다.** 확실한 것은 **기본 실행기가 바뀌었고, `plan/01` 의 대비 구도가 483 에서는 낡았다**는 사실까지다.

## 6. 결론

**구조는 서로 수렴했고, 남은 차이는 상수와 표현 방식이다.**

- **두 엔진 다 다단계 피드백 큐 계보다.** Trino 는 옛 실행기에 5단계, StarRocks 는 현재 8단계. `plan/01` 이 대비시킨 "협력적 멀티태스킹 대 논블로킹 폴러"는 **483/4.0.14 에서는 성립하지 않는다**
- **연산자 인터페이스가 거의 동형이다.** `needsInput`/`getOutput` ↔ `need_input`/`pull_chunk`
- **결정적 차이는 양자다 — 1초 대 100ms, 10배.** 그리고 이것은 A-3-01의 묶음 크기 결정(용량 기준 대 건수 기준)과 짝을 이룬다
- **진행 불가의 표현이 다르다.** Trino 는 "언제 깨워달라"(미래 객체), StarRocks 는 "왜 못 간다"(상태 12종). 후자가 스케줄러에 정보를 더 주고, 전자가 연산자 구현을 단순하게 한다

### 아직 답하지 않은 것

- **실측 전부** — 스케줄링은 동시 쿼리 다수 + 워커 다수에서만 드러난다. 현재 랩(worker 1 / BE 1, 6만 건)에서는 모든 쿼리가 첫 양자 안에 끝난다
- **Trino 가 가상 스레드를 쓰는가** — `ThreadPerDriverTaskExecutor` 의 스레드 생성 경로를 확인하지 않았다. 5-4의 해석은 추정이다
- **양자 크기가 실제 응답 시간에 미치는 영향** — 재지 않았다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **동시성 제어와 리소스 격리의 연결** — StarRocks 의 `WorkGroupDriverQueue`(워크그룹별 큐)와 Trino 의 Resource Groups 는 **B-2-01** 의 주제다
- **spill 이 스케줄링에 미치는 영향** — 메모리가 부족해 디스크로 내릴 때의 드라이버 상태 전이는 **B-1-01**
