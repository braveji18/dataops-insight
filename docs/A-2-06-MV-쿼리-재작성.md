## 1. 비교 관점

MV 는 두 개의 별개 기능으로 이루어진다.

| 기능 | 뜻 | 이걸 없애면 |
|---|---|---|
| **정의·갱신·조회** | MV 를 만들고, 원본 변화를 반영하고, 이름으로 읽는다 | 그냥 "주기적으로 갱신되는 요약 테이블"이 된다 |
| **쿼리 재작성** | 사용자가 **원본 테이블**을 대상으로 쓴 쿼리를 옵티마이저가 MV 로 바꾼다 | 사용자가 MV 의 존재와 이름을 직접 알아야 한다 |

**두 엔진 다 앞쪽은 있다. 뒤쪽은 StarRocks 에만 있다.**

이것이 왜 큰 차이인가는 운영 관점에서 봐야 한다. 재작성이 없으면 MV 는 **애플리케이션이 알아야 하는 물건**이 된다 — 쿼리를 고쳐 MV 를 가리키게 해야 하고, MV 를 지우거나 바꾸면 쿼리도 같이 고쳐야 한다. 재작성이 있으면 MV 는 **인덱스처럼** 투명한 성능 수단이 된다.

결론부터: **이 축은 지금까지 본 것 중 유일하게 "한쪽에만 있는 기능"이다.** 다만 그 대가와 조건도 분명하다.

## 2. Trino 구현

### 2-1. MV 는 커넥터 기능이고, 재작성 규칙은 존재하지 않는다

MV 관련 SPI 는 `works/trino/core/trino-spi/src/main/java/io/trino/spi/connector/ConnectorMetadata.java` 에 있다 — `createMaterializedView`(`:1700`), `dropMaterializedView`(`:1714`), `listMaterializedViews`(`:1723`), `refreshMaterializedView`(`:843`), `beginRefreshMaterializedView`(`:860`), `finishRefreshMaterializedView`(`:874`), `delegateMaterializedViewRefreshToConnector`(`:834`).

**전부 정의·갱신용이다.** 쿼리를 MV 와 대조해 바꾸는 SPI 는 없다.

옵티마이저 쪽도 마찬가지다. `sql/planner/` 에서 `MaterializedView` 를 언급하는 파일은 `RefreshMaterializedViewNode`, `LogicalPlanner`, `RelationPlanner` 등 **갱신과 조회 경로뿐**이고, `iterative/rule/` 에는 MV 관련 규칙이 하나도 없다.

구현한 커넥터는 **3개**다 — `trino-iceberg`, `trino-lakehouse`, `trino-bigquery`(BigQuery 에 위임).

> **보강 (2026-09-04).** `plan/01` A-2 는 Trino 의 MV 를 "커넥터(Iceberg/**Hive**) 한정"으로 적었는데 **483 기준으로 Hive 커넥터 단독은 MV 를 구현하지 않는다** — `plugin/trino-hive/.../HiveMetadata.java` 에 `createMaterializedView`/`getMaterializedView` 가 없다. `trino-lakehouse` 는 Hive·Iceberg·Delta 를 묶은 커넥터이고 MV 는 그 안의 Iceberg 경로가 담당한다. `plan/01` 의 표현은 계획 단계의 추정이었고, 이 문서의 3개 목록이 실제다.

### 2-2. 결정은 옵티마이저가 아니라 분석기가 한다

MV 를 어떻게 읽을지는 `sql/analyzer/StatementAnalyzer.java:2345-2363` 에서 정해진다.

```java
Optional<MaterializedViewDefinition> optionalMaterializedView = metadata.getMaterializedView(session, name);
if (optionalMaterializedView.isPresent()) {
    ...
    if (isMaterializedViewSufficientlyFresh(session, name, materializedViewDefinition)) {
        // If materialized view is sufficiently fresh with respect to its grace period, answer the query using the storage table
        QualifiedName storageName = getMaterializedViewStorageTableName(materializedViewDefinition)...
        return createScopeForMaterializedView(table, name, scope, materializedViewDefinition, Optional.of(tableHandle));
    }
    else if (shouldFailWhenStale(materializedViewDefinition)) {
        throw semanticException(VIEW_IS_STALE, table, "Materialized view '%s' is stale", name);
    }
    // This is a stale materialized view and should be expanded like a logical view
    return createScopeForMaterializedView(table, name, scope, materializedViewDefinition, Optional.empty());
}
```

**진입 조건에 주목해야 한다** — `metadata.getMaterializedView(session, name)`. `name` 은 **쿼리가 적은 이름**이다. 즉 이 코드는 **쿼리가 MV 를 직접 지목했을 때만** 돈다. 원본 테이블을 대상으로 쓴 쿼리는 이 분기에 들어오지 않는다.

분기는 셋이다.

| 조건 | 동작 |
|---|---|
| 충분히 신선 | 스토리지 테이블을 읽는다 |
| 낡았고 `WHEN STALE FAIL` | `VIEW_IS_STALE` 오류 |
| 낡았고 `WHEN STALE INLINE`(기본) | **일반 뷰처럼 정의를 펼친다** |

`WhenStaleBehavior` 의 기본값은 `INLINE` 이다 — `metadata/MaterializedViewDefinition.java:35`.

### 2-3. "충분히 신선"의 기본값이 무제한이다

`StatementAnalyzer.java:2436-2470`:

```java
MaterializedViewFreshness materializedViewFreshness = metadata.getMaterializedViewFreshness(session, name, considerGracePeriod);
MaterializedViewFreshness.Freshness freshness = materializedViewFreshness.getFreshness();

if (freshness == FRESH || freshness == FRESH_WITHIN_GRACE_PERIOD) {
    return true;
}
Optional<Instant> lastKnownFreshTime = materializedViewFreshness.getLastKnownFreshTime();
if (lastKnownFreshTime.isEmpty()) {
    return false;
}
if (materializedViewDefinition.getGracePeriod().isEmpty()) {
    // Unlimited grace period
    return true;                                       // ← 여기
}
if (gracePeriodZero) {
    return false;
}
Duration gracePeriod = materializedViewDefinition.getGracePeriod().get();
Duration staleness = Duration.between(lastKnownFreshTime.get(), session.getStart());
return staleness.compareTo(gracePeriod) <= 0;
```

**`GRACE PERIOD` 를 지정하지 않으면 무제한**이다. 원본이 아무리 바뀌어도 갱신 전까지 스토리지 테이블을 읽는다. 4-3의 실측이 이것을 확인한다.

`Freshness` 는 4값이다 — `FRESH` / `FRESH_WITHIN_GRACE_PERIOD` / `STALE` / `UNKNOWN` (`core/trino-spi/.../MaterializedViewFreshness.java:85-97`).

### 2-4. 갱신은 얕지 않다

재작성이 없다고 해서 MV 기능 자체가 빈약한 것은 아니다.

- `RefreshType` 에 `FULL` / `INCREMENTAL` 이 있고(`core/trino-spi/src/main/java/io/trino/spi/RefreshType.java`), 커넥터가 어느 쪽으로 갱신할지 결정한다
- `delegateMaterializedViewRefreshToConnector` 로 갱신 자체를 커넥터(예: BigQuery)에 통째로 맡길 수 있다
- 실행 계획에 `RefreshMaterializedViewNode` 라는 전용 노드가 있다

**즉 Trino 의 MV 는 "만들고 갱신하고 읽는" 축에서는 정상적인 기능이다. 없는 것은 재작성 하나다.**

## 3. StarRocks 구현

### 3-1. 재작성 전용 패키지가 18,000줄이다

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/transformation/materialization/` — 파일 35개, 하위 패키지 4개, **총 18,000줄**이다.

| 구성 | 내용 |
|---|---|
| `MaterializedViewRewriter.java` (**3,077줄**) | 재작성 본체 |
| `AggregatedMaterializedViewRewriter.java` (1,053줄) | 집계 MV 전용 |
| `MvUtils.java` (1,789줄) / `BestMvSelector.java` (677줄) | 후보 판정·선택 |
| `rule/` (10개) | 옵티마이저에 붙는 규칙 |
| `equivalent/` (13개) | 집계 함수 등가 변환 (`CountRewriteEquivalent`, `BitmapRewriteEquivalent`, `HLLRewriteEquivalent`, `PercentileRewriteEquivalent`, `DateTruncEquivalent`, `TimeSliceRewriteEquivalent` 등) |
| `compensation/` (7개) | 부분 갱신 보정 (`ExternalTableCompensation`, `OlapTableCompensation`, `PartitionRetentionTableCompensation` 등) |
| `common/` (2개) | 집계 롤업 규칙 |

본체의 클래스 주석이 근거 논문을 밝힌다 — `MaterializedViewRewriter.java:106-110`:

```java
/*
 * SPJG materialized view rewriter, based on
 * 《Optimizing Queries Using Materialized Views: A Practical, Scalable Solution》
 *
 *  This rewriter is for single table or multi table join query rewrite
 */
```

즉 **SPJG(Select-Project-Join-Group by) 패턴 매칭**이다. 대상 판정은 `isValidPlan` (`:154-156`)이 `MvUtils.isLogicalSPJ(expression)` 로 한다.

### 3-2. 매칭 모드가 5종이다

`MaterializedViewRewriter.java:129-139`:

```java
public enum MatchMode {
    // all tables and join types match
    COMPLETE,
    // all tables match but join types do not
    PARTIAL,
    // all join types match but query has more tables
    QUERY_DELTA,
    // all join types match but view has more tables
    VIEW_DELTA,
    NOT_MATCH
}
```

**`QUERY_DELTA` 와 `VIEW_DELTA` 가 핵심이다.** 쿼리와 MV 의 테이블 집합이 정확히 같지 않아도 재작성한다 — 쿼리에 테이블이 더 많으면 MV 를 한 가지로 끼워 넣고, MV 에 테이블이 더 많으면 조인 유도 가능성(FK 제약)을 본다.

조인 타입 호환표도 명시돼 있다(`:120-126`) — `INNER` 는 `LEFT/RIGHT SEMI` 로, `LEFT OUTER` 는 `INNER`/`LEFT ANTI` 로 대체 가능하다는 식이다.

### 3-3. 규칙은 RBO 와 CBO 양쪽에 들어간다

규칙 6개가 두 집합으로 묶여 있다 — `rule/RuleSet.java:357-369`:


투입 지점이 **둘**이다.

| 층 | 위치 | 성격 |
|---|---|---|
| **RBO** | `QueryOptimizer.java:463-480` (`doRuleBasedMaterializedViewRewrite`) | 규칙 기반 재작성. 2단계(`Stage1`/`Stage2`, `:605`, `:722`) |
| **CBO** | `QueryOptimizer.java:996-999` (`memoOptimize` 안) | **Cascades 탐색에 MV 규칙을 등록**해 비용으로 비교 |

**즉 "MV 를 쓰는 플랜"과 "안 쓰는 플랜"이 Memo 안에서 비용으로 겨룬다.** A-2-05의 CTE 재사용과 같은 구조다.

여기에 텍스트 매칭 경로(`TextMatchBasedRewriteRule`)와 뷰 기반 경로(`viewBasedMvRuleRewrite`, `:466`)가 따로 있다.

### 3-4. 준비 단계 — 후보 MV 를 먼저 모은다

`QueryOptimizer.java:333-347`:

`MvRewriteStrategy` 는 이번 쿼리에 어떤 재작성을 시도할지 7개 플래그로 정한다(`MvRewriteStrategy.java:67-76`) — `enableMaterializedViewRewrite`, `enableForceRBORewrite`, `mvStrategy`(DEFAULT/MULTI_STAGES), `enableViewBasedRewrite`, `enableSingleTableRewrite`, `enableMultiTableRewrite`, `enableCBOBasedMvRewrite`.

**후보 MV 가 없으면 전부 끈다**(`:99-102`). 옵티마이저 시간을 낭비하지 않기 위한 장치이고, 상한도 있다 — `optimizer_materialized_view_timelimit` 기본 **1000ms**(`qe/SessionVariable.java:1791-1792`).

## 4. 실측

전체 절차·조건과 정리 내역은 `docs/evidence/A-2/20260904-mv-query-rewrite-probes.md`.
양쪽에 **같은 정의의 MV** 를 만들고(둘 다 갱신 후 15000행, 각각 `IS_ACTIVE=true` / `freshness=FRESH`), MV 이름을 쓰지 않은 쿼리를 던졌다.

### 4-1. MV 이름 없는 쿼리 — 한쪽만 바뀐다

```sql
SELECT l_orderkey, sum(l_extendedprice) FROM iceberg.bench.lineitem GROUP BY l_orderkey;
```

| 엔진 | 스캔 대상 |
|---|---|
| Trino 483 | `TableScan[table = iceberg:bench.lineitem$data@…]` — **원본** |
| StarRocks 4.0.14 | `0:OlapScanNode  TABLE: mv_order_sum` — **MV** |

`SET enable_materialized_view_rewrite = false` 로 StarRocks 도 `IcebergScanNode` 로 돌아간다. **원인 확정.**

### 4-2. 재작성의 폭 — 정확 일치를 훨씬 넘는다

| 쿼리 | MV 활용에 필요한 것 | StarRocks 결과 |
|---|---|---|
| `… GROUP BY l_orderkey` | 정확 일치 | MV |
| `sum(l_extendedprice) WHERE l_orderkey < 100` | 술어를 MV 스캔에 밀어넣기 + `sum(s)` 롤업 | MV (`PREDICATES: l_orderkey < 100`) |
| `count(*) FROM lineitem` | `count(*)` → `sum(c)` 롤업 | MV |
| `lineitem ⋈ orders GROUP BY o_orderstatus` | **조인의 한쪽 가지만 치환** | MV ⋈ `IcebergScanNode(orders)` |

마지막이 특히 강하다. MV 는 `lineitem` 단독 집계인데, 조인 쿼리에서 **lineitem 가지만 MV 로 갈아끼우고** orders 는 원본에서 읽었다.

```
5:HASH JOIN  (INNER JOIN, BUCKET_SHUFFLE)
├─ 0:OlapScanNode    TABLE: mv_order_sum
└─ 3:IcebergScanNode TABLE: bench.orders
```

3-2의 `QUERY_DELTA` 모드와 `AggregateJoinPushDownRule` 이 하는 일이다.

**결과는 정확하다.** 재작성 ON / OFF / Trino 대조군 셋이 소수점까지 같았다.

### 4-3. 신선도 처리가 정반대다

작은 원본 테이블(`iceberg.bench.mvsrc`)에 MV 를 걸고 갱신한 뒤, 원본에 1행을 넣었다.

**Trino**

| MV 정의 | 원본 변경 후 플랜 |
|---|---|
| `GRACE PERIOD` 미지정(기본) | `TableScan[…$materialized_view_storage$data@…]` — **여전히 MV 를 읽는다** |
| `GRACE PERIOD INTERVAL '0' SECOND` | `Aggregate` → `TableScan[…mvsrc$data@…]` — **정의를 펼쳐 원본을 읽는다** |

`system.metadata.materialized_views` 의 `freshness` 는 첫 번째 경우에도 `STALE` 로 보고된다. **표시는 STALE 인데 읽기는 MV 를 읽는다** — 2-3의 무제한 grace 때문이다.

**StarRocks**

| 단계 | 플랜 | 결과 |
|---|---|---|
| 갱신 직후 | `OlapScanNode TABLE: mv_src_sum` | 정답 |
| 원본 +1행, 외부 메타데이터 캐시 갱신 전 | `OlapScanNode TABLE: mv_src_sum` | 옛 값 |
| `REFRESH EXTERNAL TABLE` 후 | **`IcebergScanNode TABLE: bench.mvsrc`** | 정답 (Trino 와 일치) |

**StarRocks 는 MV 가 낡았다고 판단하면 재작성을 포기하고 원본으로 돌아간다.**

가운데 단계는 오해하기 쉽다. 그때 옛 값이 나온 것은 **MV 때문이 아니라 외부 카탈로그 메타데이터 캐시** 때문이고, 재작성을 꺼도 같은 값이 나온다. 두 가지를 섞으면 안 된다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| | Trino | StarRocks |
|---|---|---|
| MV 정의·갱신 | 커넥터 SPI (7개 메서드), 구현 커넥터 **3개** | 엔진 내장, 갱신 4종(SYNC/ASYNC/MANUAL/INCREMENTAL) |
| **쿼리 재작성** | **없음** | 전용 패키지 **18,000줄**, 규칙 6개 |
| 재작성 알고리즘 | — | SPJG 패턴 매칭 (Goldstein·Larson 논문), 매칭 모드 5종 |
| 진입 조건 | 쿼리가 **MV 이름을 직접 적었을 때** | 원본 테이블 대상 쿼리 |
| 결정 위치 | **분석기**(`StatementAnalyzer`) | 옵티마이저 RBO 2단계 + **CBO(Memo) 참여** |
| 낡은 MV 처리 | 기본 **무제한 grace — 계속 사용**. `WHEN STALE FAIL` 로 변경 가능 | **재작성 포기, 원본 fallback**. 부분 보정(UNION) 경로 별도 |
| 집계 롤업 | — | `equivalent/` 13종 (count/bitmap/HLL/percentile/date_trunc/time_slice …) |
| 시간 상한 | — | `optimizer_materialized_view_timelimit` 1000ms |
| 세션 손잡이 | `GRACE PERIOD`, `WHEN STALE` (DDL 속성) | 세션 변수 18개 이상 |

### 5-2. 왜 Trino 에는 없는가

세 가지가 겹친다.

**(가) 커넥터 경계.** A-2-04에서 본 구도가 여기서도 반복된다. Trino 의 MV 는 커넥터가 소유한다 — 정의도, 스토리지 테이블도, 신선도 판정도 커넥터가 한다. 엔진이 재작성을 하려면 **모든 커넥터의 MV 정의를 통일된 형태로 읽고 신선도를 신뢰해야** 한다. `getMaterializedViewFreshness` 가 `UNKNOWN` 을 값으로 갖는다는 사실 자체가 이 신뢰가 보장되지 않음을 말한다.

**(나) 중간 결과를 물질화하지 않는다는 성격.** A-2-05의 CTE 재사용 부재와 같은 뿌리다. Trino 는 "저장은 커넥터가, 계산은 엔진이"라는 분업을 유지한다. MV 는 그 분업을 넘는 물건이라 커넥터 쪽에 밀어 넣었고, 그러자 옵티마이저가 손댈 수 없는 곳이 됐다.

**(다) 통계 신뢰도.** 재작성은 "MV 를 쓰는 편이 나은가"를 판단해야 하고, 그러려면 MV 와 원본 양쪽 통계가 필요하다. Trino 의 통계는 커넥터가 준다(A-2-07). StarRocks 는 MV 가 자기 스토리지의 테이블이라 통계를 직접 갖는다.

**즉 이것은 "Trino 팀이 안 만든 기능"이라기보다 페더레이션 아키텍처가 치르는 비용에 가깝다.** 다만 결과는 결과다.

### 5-3. 재작성이 있을 때와 없을 때 — 운영이 갈린다

| | Trino | StarRocks |
|---|---|---|
| MV 를 추가하면 | **쿼리를 고쳐야** 이득이 생긴다 | 기존 쿼리가 자동으로 빨라진다 |
| MV 를 지우면 | 쿼리가 **깨진다**(테이블 없음) | 원본으로 조용히 돌아간다 |
| MV 정의를 바꾸면 | 참조하는 쿼리를 전부 점검해야 한다 | 매칭이 안 되면 원본으로 돌아간다 |
| BI 도구가 생성한 쿼리 | MV 를 쓰게 만들 수 없다 | 그대로 이득을 본다 |
| 예측 가능성 | **높다** — 쓴 대로 실행된다 | 낮다 — 같은 쿼리가 MV 유무에 따라 다른 플랜이 된다 |

마지막 줄이 StarRocks 쪽의 비용이다. 재작성은 **플랜을 예측하기 어렵게** 만들고, 그래서 진단 수단(`query_excluding_mv_names`, `MVRewriteValidator` 추적)이 따로 필요하다. 시간 상한(1000ms)이 붙어 있는 것도 같은 이유다 — 후보 MV 가 많아지면 **컴파일 시간이 늘어난다.**

### 5-4. 신선도 정책의 차이는 필연이다

4-3의 정반대 동작은 실수가 아니라 **접근 경로가 다르기 때문에 그럴 수밖에 없다.**

- **Trino** — 사용자가 MV 이름을 직접 적었다. "요약 테이블을 읽겠다"는 의사 표시다. 따라서 약간 낡아도 빠른 쪽을 주는 것이 기본값으로 합리적이다. 원하지 않으면 `GRACE PERIOD` 로 조인다
- **StarRocks** — 사용자는 원본 테이블을 적었다. 재작성이 결과를 바꾸면 **버그**다. 따라서 낡았으면 쓰면 안 된다

**투명한 재작성은 신선도를 양보할 수 없고, 명시적 접근은 양보할 수 있다.** 같은 원리다.

다만 Trino 쪽에는 실무적 함정이 있다. **`freshness` 가 `STALE` 이라고 보고되는데도 스토리지 테이블을 읽는다**(4-3). 모니터링에서 `STALE` 을 보고 "그럼 원본을 읽고 있겠지"라고 넘기면 틀린다. `GRACE PERIOD` 를 명시하지 않은 MV 는 갱신할 때까지 낡은 답을 계속 준다.

## 6. 결론

**이 축은 StarRocks 우위다. 지금까지 본 A-2 항목 중 유일하게 명확한 기능 격차다.**

- **쿼리 재작성은 Trino 에 없다.** 옵티마이저에 관련 규칙이 하나도 없고, MV 처리는 분석기가 이름을 보고 하는 분기뿐이다. StarRocks 는 전용 패키지 18,000줄로 SPJG 매칭을 구현하고, 규칙을 RBO 와 **Cascades 비용 탐색 양쪽에** 넣는다
- **재작성의 폭도 좁지 않다.** 실측에서 롤업(`count(*)` → `sum(c)`), 술어 밀어넣기, **조인 쿼리의 한쪽 가지만 치환**까지 동작했고 결과는 정확했다
- **단, 대가가 있다.** 플랜 예측 가능성이 낮아지고 컴파일 시간이 늘어난다. StarRocks 가 1000ms 시간 상한과 MV 이름 필터를 둔 이유다
- **신선도 정책은 정반대이고, 둘 다 자기 접근 방식에서는 옳다.** 문제는 Trino 의 기본값(무제한 grace)이 `freshness=STALE` 표시와 어긋나 보인다는 점이다

**선택 기준**

| 상황 | 판단 |
|---|---|
| BI·애드혹 쿼리가 많고 쿼리를 통제할 수 없다 | **StarRocks.** 재작성이 없으면 MV 를 활용할 방법이 없다 |
| 쿼리가 코드로 관리되고 수가 적다 | 차이가 작다. Trino 에서도 MV 이름을 직접 쓰면 같은 이득을 본다 |
| 플랜이 항상 예측 가능해야 한다(SLA 민감) | Trino 쪽 성격이 맞는다. StarRocks 라면 `materialized_view_rewrite_mode` 와 MV 이름 필터로 범위를 좁힌다 |
| 여러 이종 소스를 조인한 결과를 요약해두고 싶다 | 양쪽 다 제약이 있다. Trino 는 MV 를 만들 수 있는 커넥터가 3개뿐이고, StarRocks 는 MV 가 자기 스토리지에 저장된다 |

### 아직 답하지 않은 것

- **실행 시간과 이득 크기** — SF 0.01 에서는 MV 를 읽는 이득을 잴 수 없다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **재작성이 컴파일 시간에 미치는 영향** — MV 개수를 늘려가며 측정해야 한다. 1000ms 상한의 실제 도달 여부도 미확인
- **부분 갱신 UNION 재작성** — `compensation/` 7개 클래스의 경로. 이 랩의 Iceberg 테이블은 파티션이 없어 타지 못했다
- **중첩 MV** — `nested_mv_rewrite_max_level` 기본 3. 시험하지 않았다
- **StarRocks 네이티브 테이블 위의 MV** — SYNC MV 와 증분 갱신은 네이티브 테이블 전용이다. 이 문서는 전부 Iceberg 외부 테이블 대상으로만 확인했다
- **뷰 기반·텍스트 매칭 재작성** — `enable_view_based_mv_rewrite`, `TextMatchBasedRewriteRule` 경로 미시험
- **MV 자체의 갱신 비용과 저장 비용** — 재작성 이득만 봤고 유지 비용은 보지 않았다
