# StarRocks 4.0.1 BE — Iceberg Parquet DATE 술어에서 SIGSEGV

> 비교 축: A-5 커넥터 / 파일 리더 (`plan/01-비교항목-정리.md`)
> 발견 경위: `lakehouse-lab` 환경 구축 중 TPC-H Q1 스모크 테스트
> 일자: 2026-08-20

## 주장(검증하려던 것)

두 엔진이 동일한 Iceberg 테이블에 동일 쿼리(TPC-H Q1)를 실행해 같은 결과를 낸다.

## 판별 쿼리

```sql
-- Trino 가 쓴 Iceberg/Parquet 테이블. DATE 컬럼에 범위 술어를 건다.
SELECT count(*) FROM iceberg.bench.lineitem WHERE l_shipdate <= DATE '1998-09-02'
```

## 결과

| 엔진 | 결과 |
|---|---|
| Trino 483 | 정상 (59307) |
| StarRocks 4.0.1 | **BE 프로세스 SIGSEGV(exit 139)**, 쿼리는 `ERROR 1064: Failed to find backend to execute` |
| StarRocks 4.0.14 | 정상 (59307) |

술어 없는 `SELECT count(*)` 는 4.0.1에서도 정상(60175)이다. 즉 스캔 자체가 아니라 **술어를 Parquet 통계에 적용하는 경로**가 문제다.

## 크래시 스택 (be.out)

```
*** SIGSEGV (@0x0) received by PID 7 ...
  starrocks::parquet::Int32ToDateConverter::convert(...)
  starrocks::parquet::StatisticsHelper::decode_value_into_column(...)
  starrocks::parquet::RawColumnReader::_row_group_zone_map_filter(...)
  starrocks::parquet::ScalarColumnReader::row_group_zone_map_filter(...)
  starrocks::parquet::PredicateFilterEvaluator::visit_for_rowgroup_zonemap<...>(...)
  starrocks::parquet::FileReader::_filter_group(...)
  starrocks::parquet::FileReader::init(...)
  starrocks::HdfsParquetScanner::do_open(...)
  starrocks::connector::HiveDataSource::open(...)
```

row-group zone-map(min/max 통계) 필터가 DATE 컬럼 통계를 디코딩하다 널 포인터를 만진다.

## 시도한 우회

`parquet_statistics_process_more_filter_enable=false` 를 BE 런타임 설정으로 껐으나 **크래시는 그대로**였다. 즉 이 플래그가 감싸는 경로가 아니다.

## 조치

`versions.env` 의 StarRocks를 `4.0.14` 로 올리고 `bin/reset.sh`. 동일 쿼리가 정상 동작했다.

## 부수 발견 — FE의 BE 자동 블랙리스트

BE가 죽으면 FE가 해당 BE를 자동 블랙리스트에 올린다. BE를 되살려도 `SHOW BACKENDS` 는 `Alive=true` 인데 쿼리는 계속 `Failed to find backend to execute` 로 실패한다.

```sql
SHOW BACKEND BLACKLIST;      -- AddBlackListType=AUTO 로 등록돼 있다
DELETE BACKEND BLACKLIST 11001;
```

Trino에는 대응 개념이 없다(워커가 죽으면 쿼리가 실패하고, 노드가 돌아오면 곧바로 스케줄 대상이 된다). **BE 크래시를 FE가 흡수해 클러스터를 보호하는 설계** 자체가 `plan/01` B-4(고가용성) 비교 소재다.

## 판정

- **환경 구축 관점**: StarRocks 4.0 라인에서 이 랩은 4.0.14 이상이어야 한다.
- **비교 관점(잠정)**: StarRocks의 Parquet 리더는 C++ 자체 구현이라 크래시가 **BE 프로세스 전체를 죽인다**. Trino는 Java 리더라 같은 종류의 결함이 나도 쿼리 실패에 그친다. `plan/01` A-5(파일 리더 Java vs C++) / B-4(장애 격리) 문서를 쓸 때 이 사례를 근거로 쓸 수 있다.
- 단, 이 결함이 arm64 빌드 한정인지 x86에서도 재현되는지는 **미확인**이다. 위 판정을 문서에 옮길 때는 이 한정을 반드시 붙일 것.
