## 1. 비교 관점

앞의 두 문서는 각각 **탐색 공간**(어떤 조인 순서를 후보로 만드는가)과 **게이트**(broadcast를 후보로 허용하는가)를 봤다. 둘 다 "후보를 어떻게 만드는가"의 이야기이고, 남은 질문은 하나다 — **후보가 여럿일 때 무엇을 보고 하나를 고르는가.**

A-2-01 6절과 A-2-02 6절이 모두 이 문서를 지목한다. A-2-01의 조인 ≤4 구간(양쪽 다 전수 탐색인데 플랜이 갈린다)과 A-2-02 4-1의 `lineitem ⋈ orders`(게이트는 양쪽 다 통과했는데 결론이 갈린다)는 탐색 공간으로 설명되지 않는다. 남은 원인은 비용 모델뿐이다.

결론부터: **두 엔진은 같은 세 축(CPU / 메모리 / 네트워크)을 쓰지만 축의 가중치가 사실상 반대이고, 축을 누적하는 방식이 다르며, 통계가 없을 때의 행동이 정반대다.** 그리고 이 저장소의 랩 구성(Iceberg 외부 테이블, BE 1대)은 StarRocks 쪽 비용 계산에서 **두 개의 항을 통째로 0으로 만든다** — 지금까지의 A-2 실측을 해석할 때 반드시 감안해야 한다(5절).

## 2. Trino 구현

### 2-1. 비용은 4-튜플이고, 스칼라화는 비교 직전에만 한다

`works/trino/core/trino-main/src/main/java/io/trino/cost/PlanCostEstimate.java:34-38` 이 비용의 정의다.

```java
private final double cpuCost;
private final double maxMemory;
private final double maxMemoryWhenOutputting;
private final double networkCost;
```

세 축이 아니라 **네 개**다. 메모리가 둘로 쪼개져 있는데, `maxMemoryWhenOutputting` 은 "첫 출력 행이 나온 뒤에도 여전히 붙잡고 있는 메모리"다(`:106-112` 의 주석). 이 축이 왜 필요한지는 2-3에서 드러난다.

이 4-튜플은 끝까지 4-튜플로 유지되고, **하나의 숫자로 접히는 곳은 비교 시점 한 곳뿐**이다 — `cost/CostComparator.java:63-69`:

```java
double leftCost = left.getCpuCost() * cpuWeight
        + left.getMaxMemory() * memoryWeight
        + left.getNetworkCost() * networkWeight;
```

가중치는 `sql/planner/OptimizerConfig.java:42-44` 에서 **75 / 10 / 15**. `maxMemoryWhenOutputting` 은 비교식에 등장하지 않는다 — 누적 계산에만 쓰이는 내부 축이다.

`CostComparator.java:59` 가 `checkArgument(!left.hasUnknownComponents() && ...)` 로 **미상 성분이 있으면 비교 자체를 거부**한다. A-2-01 3-3에서 본 "리오더 포기"의 뿌리가 여기다.

### 2-2. 비용의 단위는 바이트이고, 그 바이트는 실행 시 블록 레이아웃이다

모든 항이 `getOutputSizeInBytes()` 로 환원된다. `cost/PlanNodeStatsEstimate.java:89-110`:

```java
// account for "is null" boolean array
outputSize += outputRowCount;
if (type instanceof FixedWidthType fixedType) {
    outputSize += numberOfNonNullRows * fixedType.getFixedSize();
}
else {
    ...
    // account for offsets array
    outputSize += outputRowCount * Integer.BYTES;
}
```

행 수 × 평균 폭이 아니라 **null 비트 배열과 가변길이 타입의 offsets 배열까지 더한다.** 즉 Trino의 "바이트"는 디스크 크기가 아니라 **실행 엔진이 실제로 메모리에 올릴 `Block` 의 크기**다. null 비율이 높거나 varchar가 많은 컬럼에서 이 차이가 커진다.

연산자별 비용은 `cost/CostCalculatorUsingExchanges.java` 의 방문자가 매긴다. 대부분 한 줄이다 — 스캔은 출력 바이트를 CPU로(`:144-147`), 필터·프로젝트도 마찬가지, 집계는 입력 바이트가 CPU이고 출력 바이트가 메모리(`:166-177`).

### 2-3. 누적 — 메모리는 더하지 않고 "생명주기"를 본다

여기가 Trino 비용 모델에서 가장 공들인 부분이다. `CostCalculatorUsingExchanges.java:297-347` 에 누적 규칙이 셋 있다.

| 메서드 | 대상 | 메모리 처리 |
|---|---|---|
| `costForStreaming` (`:317`) | 스트리밍 연산자 | 자식 최대치와 "자식이 출력 중일 때 + 내 메모리" 중 **최댓값** |
| `costForAccumulation` (`:303`) | 집계처럼 다 모아야 하는 연산자 | 위와 같되, 출력 시점에는 **자식이 이미 해제**했다고 보고 내 메모리만 남긴다 |
| `costForLookupJoin` (`:331`) | 조인 | 프로브와 빌드가 **동시에** 최대 메모리를 잡을 수 있다고 보고 둘을 더한 값과, 빌드가 끝나 해제한 뒤의 값 중 최댓값 |

CPU와 네트워크는 단순 합이지만 **메모리는 합이 아니라 max**이고, 그 max를 구하려고 "출력 중 메모리"라는 별도 축을 끌고 다닌다. 모델링하려는 것은 총량이 아니라 **동시 점유 피크**다.

### 2-4. 교환 비용 — 태스크 수가 곱해지는 곳

`cost/CostCalculatorWithEstimatedExchanges.java:176-194`:

```java
public static LocalCostEstimate calculateRemoteRepartitionCost(double inputSizeInBytes) {
    return LocalCostEstimate.of(inputSizeInBytes, 0, inputSizeInBytes);   // cpu + network
}
public static LocalCostEstimate calculateRemoteReplicateCost(double inputSizeInBytes, int destinationTaskCount) {
    return LocalCostEstimate.ofNetwork(inputSizeInBytes * destinationTaskCount);
}
```

복제는 네트워크에 **태스크 수가 곱해지고**, 조인 입력 비용에서도 빌드측에 같은 배수가 붙는다(`:278-297` 의 `buildSizeMultiplier`). 태스크 수는 `cost/TaskCountEstimator.java:65-75` 가 **살아 있는 노드 수**로 준다(`cost_estimation_worker_count` 로 덮어쓸 수 있다).

A-2-02가 본 게이트와 이 비용은 별개다. 게이트는 후보를 만들지 말지를 정하고, 여기서는 만들어진 후보끼리 겨룬다.

교환이 아직 플랜에 없는 단계에서는 교환을 **추정**해 비용에 넣고(`CostCalculatorWithEstimatedExchanges`), `AddExchanges` 이후에는 실제 교환 노드를 세는 계산기로 갈아탄다 — `sql/planner/PlanOptimizers.java:916-917` 에 `// use cost calculator without estimated exchanges after AddExchanges` 라고 적혀 있다. 최적화 단계에 따라 **비용 계산기 자체가 바뀐다.**

### 2-5. 통계 — 컬럼당 5개 값, 히스토그램 없음

`cost/SymbolStatsEstimate.java:37-41` 이 통계의 전부다.

```java
private final double lowValue;
private final double highValue;
private final double nullsFraction;
private final double averageRowSize;
private final double distinctValuesCount;
```

**히스토그램이 없다.** 분포는 [min, max] 구간과 NDV로만 근사하고(`cost/StatisticRange.java`), 조인 카디널리티는 양쪽 구간의 겹침 비율로 NDV를 깎아 추정한다(`cost/JoinStatsRule.java:199-238`).

원천은 커넥터다. `cost/TableScanStatsRule.java:61-71` 이 `tableStatsProvider.getTableStatistics()` 를 부르고, 컬럼 통계가 없으면 `SymbolStatsEstimate.unknown()`(= NaN)을 넣는다. **Trino 자신은 통계를 수집하지 않는다.**

규칙 기반이라는 점도 옵티마이저와 같다 — `cost/StatsCalculatorModule.java` 가 **24개**의 `StatsRule` 을 조합한다.

### 2-6. 다중 술어 — 독립성 가정의 강도를 손잡이로 뺐다

`cost/PlanNodeStatsEstimateMath.java:202-235`:

```java
// For independenceFactor = 0.75 and terms t1, t2, t3
// Combined selectivity = (t1 selectivity) * ((t2 selectivity) ^ 0.75) * ((t3 selectivity) ^ (0.75 * 0.75))
```

선택도가 낮은(=가장 강한) 항부터 정렬해 첫 항은 그대로 쓰고, 이후 항은 지수를 기하급수적으로 죽인다. `independenceFactor = 1` 이면 완전 독립(단순 곱), `0` 이면 완전 상관(가장 강한 항만).

기본값이 용도별로 다르다 — `OptimizerConfig.java:48, 59`:

```
optimizer.join-multi-clause-independence-factor     = 0.25   # 조인 등가 술어
optimizer.filter-conjunction-independence-factor    = 0.75   # 일반 필터 AND
```

**조인 키들끼리는 강하게 상관됐다고 보고(0.25), 일반 필터는 대체로 독립이라고 본다(0.75).** 같은 수식에 계수만 다르게 넣은 구조이고, 둘 다 세션 프로퍼티로 노출돼 있다(`SystemSessionProperties.java:66, 136`).

### 2-7. 추정 불가 술어 — 기본은 "모른다"로 남긴다

`OptimizerConfig.java:58` 의 `defaultFilterFactorEnabled` 는 선언만 있고 초기값이 없다 — **기본 false**. 즉 추정할 수 없는 술어를 만나면 임의의 선택도를 끼워 넣지 않고 `PlanNodeStatsEstimate.unknown()` 을 반환한다(`cost/FilterStatsCalculator.java` 에 `unknown()` 반환 지점이 14곳). 그 NaN은 비용까지 전파되고, 2-1의 `checkArgument` 에 걸려 **비용 기반 결정이 통째로 발화하지 않는다.**

A-2-01 3-3에서 관찰한 "Trino는 리오더를 포기한다"는 규칙 하나의 성질이 아니라 **비용 모델 전체의 일관된 정책**이다.

## 3. StarRocks 구현

### 3-1. 비용은 3-튜플이고, 연산자마다 즉시 스칼라가 된다

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/CostEstimate.java:25-27` — `cpuCost`, `memoryCost`, `networkCost` 셋이다. 생명주기 축이 없다.

스칼라화는 `cost/CostModel.java:129-136`:

```java
public static double getRealCost(CostEstimate costEstimate) {
    double cpuCostWeight = 0.5;
    double memoryCostWeight = 2;
    double networkCostWeight = 1.5;
    ...
}
```

**가중치가 메서드 안의 지역 변수다.** 설정도 세션 변수도 아니고, 소스를 고치지 않으면 바꿀 수 없다.

그리고 이 스칼라화는 **연산자 하나를 계산할 때마다** 일어난다. Cascades 태스크가 `CostModel.calculateCost(groupExpression)` 로 지역 비용을 얻어 누계에 더한다 — `task/EnforceAndCostTask.java:147-148`:

```java
localCost = CostModel.calculateCost(groupExpression);
curTotalCost += localCost;
```

즉 플랜 전체의 비용은 **스칼라 하나**이고, 세 축은 연산자 경계에서 이미 섞여 사라진다. Trino가 마지막까지 4-튜플을 유지하는 것과 정반대다.

이 구조가 주는 것이 있다 — **가지치기**. `EnforceAndCostTask.java:188-190, 368-371` 이 누계가 상한을 넘으면 즉시 버리고, 더 싼 플랜을 찾으면 상한을 낮춘다. 전형적인 branch-and-bound이고, 스칼라 하나이기 때문에 가능하다.

### 3-2. 스캔 — OlapScan과 HiveScan만 비용이 있다

`cost/CostModel.java` 의 `CostEstimator` 가 재정의한 스캔 방문자는 **둘뿐**이다.

- `:171-186` `visitPhysicalOlapScan` → `CostEstimate.of(computeSize, 0, 0)`
- `:188-195` `visitPhysicalHiveScan` → `CostEstimate.of(computeSize, computeSize, computeSize)` — **세 축 모두**에 같은 값

나머지는 `visitOperator` 로 떨어지고, 그것은 `:147-149` 에서 **`CostEstimate.zero()`** 다.

`PhysicalIcebergScanOperator` 는 `PhysicalScanOperator` 를 직접 상속하고(`operator/physical/PhysicalIcebergScanOperator.java:35`) `visitPhysicalIcebergScan` 으로 디스패치되는데(`:91-93`), `OperatorVisitor.java:312-314` 의 기본 구현이 `visitOperator` 로 위임한다. **따라서 Iceberg 테이블 스캔의 비용은 0이다.** Hudi·Delta·Paimon·JDBC·Elasticsearch 스캔도 같다.

통계는 정상적으로 계산된다 — `statistics/StatisticsCalculator.java:540-546` 이 Iceberg 스캔의 행 수와 컬럼 통계를 채운다. **0이 되는 것은 통계가 아니라 스캔 연산자의 비용 항이다.** 따라서 상위 조인·교환 비용은 여전히 통계에 반응하고, 사라지는 것은 "이 테이블을 읽는 값"이라는 항 하나다.

Hive 스캔에 세 축을 모두 매기는 것과 Iceberg 스캔에 아무것도 매기지 않는 것이 한 파일에 공존한다. 이 비대칭이 의도인지 누락인지는 **코드만으로는 판정할 수 없다** — 커밋 이력을 보지 않았고, 이 저장소는 얕은 클론이라 볼 수도 없다.

### 3-3. 조인 — 실행 방식을 아는 전용 비용 모델

Trino가 조인 비용을 "프로브 바이트 + 빌드 바이트 × 배수" 한 줄로 끝내는 데 비해, StarRocks에는 `cost/HashJoinCostModel.java` 라는 별도 클래스가 있다. 클래스 주석(`:35-54`)이 무엇을 모델링하려는지 밝힌다 — broadcast는 해시 테이블 빌드가 병렬화되지 않고, 복제본 때문에 메모리를 더 쓰며, 셔플 조인은 해시 테이블이 1/병렬도 크기라 프로브가 빠르다.

`:86-113`:

```java
case BROADCAST: buildCost = rightOutput;                  probeCost = leftOutput * getAvgProbeCost();
case SHUFFLE:   buildCost = rightOutput / parallelFactor; probeCost = leftOutput * getAvgProbeCost();
```

`getAvgProbeCost()`(`:134-157`)가 이 모델의 핵심이다.

```java
double mapSize = Math.min(1, keySize) * rightStatistics.getOutputRowCount();
cachePenaltyFactor = Math.max(1, Math.log(mapSize / BOTTOM_NUMBER));   // BOTTOM_NUMBER = 100000
```

해시 테이블이 10만 행을 넘어가면 **로그 스케일로 프로브 단가를 올린다.** 캐시 미스를 모델에 넣은 것이고, 셔플 경로에서는 병렬도로 그 페널티를 깎아준다(`:150-151`). 상한은 broadcast 12배, shuffle 3배(`:60-62`).

메모리는 `:115-132` — broadcast면 `rightOutput × beNum`, 아니면 `rightOutput`.

**Trino의 비용 모델에는 대응물이 없다.** Trino는 바이트만 세고, 해시 테이블 크기가 캐시에 들어가는지, 빌드가 병렬화되는지는 보지 않는다.

### 3-4. 교환 — 단일 BE에서 셔플의 네트워크 비용이 0이 된다

`cost/CostModel.java:387-444` 의 `visitPhysicalDistribution` 이 네트워크 비용을 매기는 유일한 자리다(조인 자체는 `:458` 에서 네트워크 0을 준다).

```java
case BROADCAST:
    result = CostEstimate.of(outputSize * aliveBackendNumber,
                             outputSize * beNum,
                             Math.max(outputSize * beNum, 1));
    if (outputSize > sessionVariable.getMaxExecMemByte()) {
        result = result.multiplyBy(BROADCAST_JOIN_MEM_EXCEED_PENALTY);   // ×1000
    }
    break;
case SHUFFLE:
    boolean ignoreNetworkCost = sessionVariable.isEnableLocalShuffleAgg()
            && sessionVariable.isEnablePipelineEngine()
            && ...getClusterInfo().isSingleBackendAndComputeNode();
    double networkCost = ignoreNetworkCost ? 0 : Math.max(outputSize, 1);
    result = CostEstimate.of(outputSize * factor, 0, networkCost * factor);
    break;
```

broadcast는 세 축 모두에 `beNum` 이 곱해지고, 빌드측이 `max_exec_mem_byte` 를 넘으면 **1000배 페널티**(`statistics/StatisticsEstimateCoefficient.java:60`)를 맞는다. 사실상 금지에 가깝다.

셔플 쪽에 붙은 `ignoreNetworkCost` 가 이 문서에서 가장 중요한 발견이다. 세 조건이 모두 참이면 **셔플 교환의 네트워크 비용이 0이 된다.** 그리고 세 조건은 이 저장소의 랩에서 **전부 참이다**:

| 조건 | 기본값 / 랩 상태 | 근거 |
|---|---|---|
| `enable_local_shuffle_agg` | **true** | `qe/SessionVariable.java:1186` |
| `enable_pipeline_engine` | **true** | `qe/SessionVariable.java:1156` |
| BE + CN 합이 **1** | **참** (BE 1대 구성) | `system/SystemInfoService.java:240-242`, `plan/02` D-1 |

주석은 이 경로의 의도를 "단일 BE에서 `ScanNode→LocalShuffle→OnePhaseLocalAgg` 를 만들기 위해서"라고 밝히지만(`:419-422`), **코드는 집계 여부를 보지 않는다.** 조인 앞의 셔플이든 무엇이든 SHUFFLE 타입이면 네트워크가 0이 된다.

### 3-5. 통계 — 히스토그램·다중 컬럼·자동 수집

`statistics/ColumnStatistic.java:39-45` 는 Trino의 5개 값에 더해 **`Histogram histogram`** 을 갖는다. 조인 추정에서도 쓰인다 — `cbo_enable_histogram_join_estimation` 기본 **true**(`qe/SessionVariable.java:2019-2020`).

여기에 `MultiColumnCombinedStatistics`(다중 컬럼 결합 NDV)가 별도로 있다. Trino가 컬럼 간 상관을 **계수 하나로 근사**하는 자리를(2-6) StarRocks는 **실제 통계로 채우려 한다.**

수집 주체도 다르다. `common/Config.java:2242, 2245` 의 `enable_statistic_collect` / `enable_auto_collect_statistics` 가 모두 기본 true — **엔진이 스스로 수집한다.** Trino는 커넥터가 주는 것을 받아 쓸 뿐이다(2-5).

바이트 환산은 훨씬 단순하다. `statistics/Statistics.java:110-128`:

```java

...
```

Trino의 null 배열·offsets 보정이 없는 대신, **통계가 없어도 NaN이 되지 않는다.** 타입 크기로 메꾸고 최소 1바이트를 보장한다. 3-6의 원칙이 여기서 이미 드러난다.

### 3-6. 통계가 없어도 미상 값을 만들지 않는다

`statistics/StatisticsCalculator.java:1202-1226` 이 조인 카디널리티 추정의 미상 처리다.

A-2-01 3-3의 대조가 여기서 완성된다. Trino는 미상을 미상으로 전파해 결정을 멈추고, StarRocks는 미상을 **계수로 메꿔** 결정을 계속한다. 규칙 하나의 차이가 아니라 **통계 계층의 설계 원칙 차이**다.

### 3-7. 다중 술어 — Presto식이 기본, ORCA식이 대안

`StatisticsCalculator.java:1695-1704` 가 두 갈래로 나뉜다.

**기본 경로**(`cbo_use_correlated_join_estimate` = **true**, `qe/SessionVariable.java:1443-1444`)는 `:1711-1736`, 주석이 출처를 밝힌다 — `// The implementation here refers to Presto`. 가장 강한 술어 하나를 "driving predicate"로 고르고 나머지에는 `0.9^(n-1)`(`UNKNOWN_AUXILIARY_FILTER_COEFFICIENT`, `StatisticsEstimateCoefficient.java:19`)를 곱한다.

**대안 경로**는 `:1760-1782`, 주석이 `// This estimate join row count method refers to ORCA` 다. 같은 테이블 쌍에 걸린 술어끼리는 선택도를 내림차순 정렬해 `s^(1/2^i)` 로 감쇠시키고, 다른 테이블 쌍끼리는 독립으로 곱한다.

Trino와 비교하면 형태는 비슷하다(강한 항 우선 + 이후 항 감쇠). 다른 것은 **감쇠의 근거**다. Trino는 지수를 설정값으로 빼서 사용자가 돌리게 했고(2-6), StarRocks는 두 개의 고정된 알고리즘을 두고 INVISIBLE 플래그로 고른다.

## 5. 실측 — 앞 문서의 결과를 다시 읽는다

3절까지는 소스 독해다. 이 절은 그것을 랩에서 판별한 결과이고, **앞 문서의 결론 하나를 정정한다.**

### 5-1. A-2-02 4-1의 원인 — 확정

**가설**: 랩은 BE 1대이므로 3-4의 세 조건이 모두 참이고, 따라서 SHUFFLE 교환의 네트워크 비용이 0이 된다. 남는 것은 CPU 항(가중치 0.5)뿐이다. 반면 broadcast는 `beNum=1` 이라 배수 효과는 없어도 **세 축 모두**에 빌드측 크기가 실려 가중치 합 `0.5+2+1.5 = 4` 를 문다. 즉 단일 BE에서 StarRocks의 비용 모델은 **구조적으로 셔플에 기울어 있다.**

**판별**: 세션 변수 하나로 조건을 깼다.

| 쿼리 | StarRocks 기본 | `enable_local_shuffle_agg=false` |
|---|---|---|
| `lineitem ⋈ orders` (빌드 15000행) | **PARTITIONED** | **BROADCAST** ← 뒤집힘 |
| `lineitem ⋈ supplier` (빌드 100행, 대조군) | BROADCAST | BROADCAST (변화 없음) |

**확정.** 대조군이 움직이지 않았으므로 이 변수가 무차별적으로 broadcast를 만드는 것이 아니라, **비용이 팽팽한 경우에만 결론을 바꾼다.**

Trino가 같은 쿼리에서 REPLICATED를 고른 것도 대칭적으로 설명된다 — 태스크 수가 1이라 복제 배수가 1이고(2-4), 셔플은 프로브측까지 재분배 비용을 물기 때문이다.

**이것은 랩 구성이 만든 결과이지 StarRocks의 일반적 성향이 아니다.** BE가 2대 이상이면 `isSingleBackendAndComputeNode()` 가 거짓이 되어 이 경로를 타지 않는다. 다중 BE 재현은 이 랩으로 불가하다.

### 5-2. 추정이 갈리는 지점은 "다중 등가절"이다

Q5 형태(6테이블)에서 **양쪽의 조인 트리가 동일하게 나왔다** — `(lineitem ⋈ (supplier ⋈ (nation ⋈ region))) ⋈ (orders ⋈ customer)`. 트리가 같으므로 노드별 추정을 직접 대조할 수 있었다.

| 조인 노드 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| nation ⋈ region (ASIA) | 5 | 5 |
| supplier ⋈ (…) | 20 | 20 |
| lineitem ⋈ (…) | 12035 | 12035 |
| orders ⋈ customer | 15000 | 15111 |
| **최상위 (등가절 2개)** | **5448** | **10896** |

중간 노드는 전부 일치하고, **등가절이 2개인 최상위 조인에서만 정확히 2배 벌어진다.** 2-6과 3-7이 예측한 그 지점이다.

손잡이를 돌려 확인했다. 최상위 조인의 **실제** 행 수는 647이다.

| 엔진 / 설정 | 추정 | 실제 대비 |
|---|---|---|
| Trino `factor=0` (완전 상관) | 12182 | 18.8× |

**양쪽 기본값 모두 한 자릿수~두 자릿수 배로 과대추정한다.** Q5의 두 등가절(`l_orderkey=o_orderkey`, `s_nationkey=c_nationkey`)은 실제로 독립적이라 완전 독립 가정이 정답에 가깝다. StarRocks 기본이 가장 멀고, Trino 기본이 2배 가깝다.

**어느 쪽 기본값이 낫다고 일반화하면 안 된다.** FK 체인처럼 등가절이 실제로 상관된 스키마에서는 방향이 반대가 된다. 여기서 확인된 것은 *기본값이 상관을 강하게 가정하며, 그 결과가 이 정도 크기로 나타난다*는 사실이다.

그리고 **이 설정 하나가 조인 순서까지 바꾼다.** Trino `factor=1` 에서는 최상위 조인의 등가절 조합 자체가 달라졌고, StarRocks `correlated=false` 에서는 트리가 right-deep으로 바뀌었다. 카디널리티 추정 → 플랜의 연결 고리가 실측으로 닫힌다.

### 5-3. ★ 정정 — A-2-01 4절의 left-deep은 임계값 때문이 아니었다

같은 랩, 같은 쿼리, 기본 설정에서 **StarRocks가 bushy 플랜을 냈다.** `docs/evidence/A-2/20260831-join-reorder-algorithm-threshold.md` 는 기본이 left-deep이라고 기록했고 원인을 `cbo_max_reorder_node_use_exhaustive` 디스패치로 귀속했는데, 그것이 재현되지 않았다.

A-2-01 3-3이 다른 설명을 준다 — `ReorderJoinRule.java:250-253` 은 통계가 없는 컬럼이 하나라도 있으면 DP·greedy를 건너뛰고 left-deep만 남긴다. 두 변수를 교차시켰다.

| 통계 상태 | 임계값 4 (기본) | 임계값 10 |
|---|---|---|
| **FULL (전 컬럼)** | **bushy** | bushy (같은 트리, 최상위 build/probe만 교체) |
| **`DROP STATS nation`** | **left-deep** — 8월 31일 기록과 정확히 동일 | bushy |

**통계를 지우자 그 left-deep 트리가 그대로 재현됐고, `ANALYZE` 로 복구하자 bushy로 돌아왔다.**

- 8월 31일 실행 당시 StarRocks 쪽 컬럼 통계가 완전하지 않았다고 보는 것이 관찰을 가장 잘 설명한다
- 임계값을 10으로 올렸을 때 bushy가 나온 것도 같은 이유로 설명된다 — 임계값을 넘기면 **memo 전수 탐색 경로**로 가고, 그 경로는 `hasUnknownColumnsStats` 를 보지 않는다
- 즉 **임계값이 경로를 가르는 것은 맞지만**(소스 근거는 그대로 유효하다), 관찰된 left-deep의 원인은 임계값이 아니라 **통계**였다
- **통계가 완전하면 기본 임계값에서도 StarRocks는 bushy를 만든다.** `JoinReorderDP` 가 후보에 들어가고 비용이 그것을 고르기 때문이다(`ReorderJoinRule.java:247-268`)

따라서 A-2-01 5절 표의 "트리 모양: 휴리스틱 경로에서는 사실상 left-deep 편향"은 **틀렸다.** 편향은 알고리즘 디스패치가 아니라 통계 가용성에서 온다. A-2-01 본문을 그렇게 고쳤다.

### 5-4. Trino의 "통계 없으면 리오더 포기"는 Iceberg에서 관찰되지 않는다

대칭 실험으로 `ALTER TABLE iceberg.bench.nation EXECUTE drop_extended_stats` (NDV 제거)를 걸었다. **Trino는 리오더를 포기하지 않았다** — 플랜 모양은 바뀌었지만 여전히 작성된 순서와 다르게 재배치했고, `ANALYZE` 후 원래 플랜으로 정확히 되돌아왔다.

2-7의 조건은 **비용 전체가 미상**이 되는 경우인데, Iceberg는 매니페스트에 행 수가 항상 있어 NDV만 지워도 행 수 추정이 살아 있다. **코드 경로 자체는 유효하지만 이 커넥터에서는 도달하기 어렵다.** 도달 조건을 만들려면 행 수조차 없는 커넥터가 필요하다(A-5 소재).

### 5-5. 지금까지의 A-2 실측 전체에 붙는 한정

3-2가 더 넓게 걸린다. 랩의 테이블은 전부 **Iceberg**이므로:

- **StarRocks** — 모든 스캔의 비용이 **0**. 플랜 비용은 조인·교환·집계 항만으로 결정된다
- **Trino** — 스캔에 출력 바이트만큼 CPU 비용을 매긴다(`CostCalculatorUsingExchanges.java:144-147`)

같은 쿼리를 재는데 **한쪽만 스캔 항을 갖는다.** 조인 순서에 미치는 영향은 제한적이라고 볼 근거가 있다 — 스캔 비용은 어떤 순서를 고르든 같은 테이블 집합에 대해 상수에 가깝기 때문이다. 실제로 5-2에서 두 엔진의 트리가 일치한 것이 그 방증이다. 그러나 **"두 엔진의 비용 모델을 같은 조건에서 비교했다"고 말할 수는 없다.**

StarRocks의 내부 테이블(OLAP)로 같은 비교를 한 번 돌리면 이 항이 살아난다. 다만 `seed.sh --with-native` 가 만드는 테이블은 조인 키로 버킷팅돼 있어 bucket-shuffle/colocate 조인이라는 **제3의 선택지가 생긴다** — 스캔 비용 항만 분리하지는 못한다. 별도 설계가 필요하다.

## 6. 설계 차이와 그 원인

**Trino의 비용 모델은 "적게 추정하고, 추정한 것은 정확하게, 모르면 멈춘다"** 로 요약된다. 통계 항목은 다섯 개뿐이고 히스토그램도 없지만, 그 다섯 개로 계산하는 바이트는 실행 엔진의 실제 메모리 레이아웃까지 반영하며, 메모리 누적은 연산자 생명주기까지 추적한다. 그리고 하나라도 모르면 NaN을 끝까지 전파해 결정을 포기한다.

이것은 A-2-01 5절에서 읽은 것과 같은 태도다. 커넥터가 통계를 줄지 안 줄지 모르는 페더레이션 엔진에서 **"모르는데 아는 척하는 것"의 비용이 크다**는 판단으로 보인다. 대신 사용자가 돌릴 손잡이를 남겨뒀다 — 가중치 3개, 독립성 계수 2개, 기본 필터 계수 on/off, 워커 수 오버라이드.

**StarRocks의 비용 모델은 "많이 추정하고, 실행 특성까지 넣고, 모르면 메꾼다"** 다. 히스토그램과 다중 컬럼 결합 통계를 직접 수집하고, 해시 조인의 캐시 지역성과 병렬도까지 비용에 넣으며, 통계가 없으면 타입 크기와 고정 계수로 메꾸고 계속 간다.

자체 스토리지와 통계 수집기를 가진 엔진에서는 **통계가 있다는 전제가 대체로 맞고**, BE의 실행 특성도 엔진이 다 알고 있으므로 모델에 넣을 수 있다. 반면 그 정교함은 **조절 불가능한 상수로 굳어 있다** — 가중치 세 개는 소스에 박혀 있고, 감쇠 계수와 페널티는 `StatisticsEstimateCoefficient` 의 근거 없는 숫자들이다.

**한쪽은 적게 재고 재는 것은 정밀하며 사용자에게 열어뒀고, 다른 쪽은 많이 재고 실행까지 알지만 닫아뒀다.** 우열이 아니라 각자의 스토리지 소유 여부에서 따라 나오는 귀결로 읽힌다.

단, 이 해석은 **코드 구조에서 읽은 것이고 실측으로 검증되지 않았다.** A-2-01 5절과 같은 한정이 그대로 걸린다.

## 7. 결론

**동등하지 않고, 우열도 판정할 수 없다 — 재는 대상 자체가 다르다.**

- 두 엔진은 같은 세 축을 쓰지만 **지배적인 축이 반대**다. Trino는 처리 바이트(CPU), StarRocks는 메모리와 네트워크. 다만 메모리 항의 정의(피크 vs 합)가 달라 가중치를 직접 비교하는 것은 무의미하다
- **통계가 없을 때의 행동이 정반대**이고, 이것이 A-2-01에서 관찰한 차이의 뿌리다. 규칙 하나의 성질이 아니라 통계 계층 전체의 원칙이다
- StarRocks는 **실행 특성(캐시·병렬도·BE 수)을 비용에 직접 넣는다.** Trino의 비용 모델에는 대응물이 없다
- 조절 가능성은 반대다. **Trino는 가중치·독립성 계수를 설정으로 열어뒀고, StarRocks는 소스 상수로 닫아뒀다.** A-2-01·A-2-02에서 본 "StarRocks 쪽이 손잡이가 많다"는 관찰은 **임계값에 한정된 것**이고, 비용 모델 자체는 반대다
- 런타임 정보를 되먹이는 곳이 다르다 — Trino는 플랜(FTE 한정), StarRocks는 자원 스케줄링

운영 관점에서 실질적인 함의는 하나다. **플랜이 이상할 때 손댈 수 있는 지점이 Trino 쪽이 넓다.** `cpu-cost-weight`, `join_multi_clause_independence_factor`, `cost_estimation_worker_count` 는 모두 문서화된 손잡이다. StarRocks에서 비용 모델이 잘못된 선택을 하면 조인 힌트(`[broadcast]`, `[shuffle]`)로 결과를 덮어쓰는 것 외에 모델 자체를 조정할 방법이 없다.

### 아직 답하지 않은 것

- **다중 BE / 다중 worker** — `beNum`, `parallelFactor`, `taskCountEstimator` 가 모두 노드 수에 반응한다. **5-1의 결과는 BE 1대에서만 성립한다** — 이 랩으로는 확장 불가
- **Iceberg 스캔 비용 0 항의 분리** — 5-5. `--with-native` 테이블은 버킷팅 때문에 조건이 달라져 이 항만 분리하지 못한다. 버킷을 쓰지 않는 네이티브 테이블을 따로 만들어야 한다
- **다른 쿼리 형태에서의 추정 정확도** — 5-2는 Q5 한 건이다. 등가절이 실제로 상관된 쿼리(FK 체인)에서는 기본값의 방향이 유리하게 뒤집힐 것으로 예상되나 재지 않았다
- **어느 쪽 플랜이 실제로 빠른가** — A-2-01부터 계속 남아 있는 항목. SF 0.01에서는 의미가 없고 `perf` 프로파일이 필요한데, 이 호스트(RAM 7.6GB)로는 불가하다(`plan/02` 3절)
