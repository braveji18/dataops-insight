# B-3 운영 (3) — 캐시 계층

> 비교 축: `plan/01-비교항목-정리.md` B-3 "StarRocks Data Cache / Query Cache vs Trino의 부재와 대체 수단"
> 기준 버전: **Trino 483** / **StarRocks 4.0.14**
> 런타임 증거: `docs/evidence/B/20260904-cache-layer-probes.md`
> 선행 문서: `docs/A-2-06-MV-쿼리-재작성.md`, `docs/A-5-03-파일-리더.md`
> 일자: 2026-09-04

> ### ⚠ `plan/01` 전제 정정
> `plan/01` 은 이 축을 **"Trino 의 부재"** 로 적었다. **절반만 맞다.**
> Trino 483 에는 **Alluxio 기반 분산 파일 시스템 캐시**가 있다(`lib/trino-filesystem-cache-alluxio`,
> Hive·Iceberg·Delta 커넥터 지원, 전용 문서 존재). 없는 것은 **쿼리 결과 캐시**뿐이다.
> 실무적으로 갈리는 것은 "있느냐"가 아니라 **"기본으로 켜져 있느냐"** 다(2·3절).

## 1. 비교 관점

레이크하우스 조회는 **같은 파일을 반복해서 읽는다.** 대시보드가 5분마다 같은 집계를 돌리고, 여러 사용자가 같은 최근 파티션을 본다. 캐시가 여기서 가장 크게 듣는다.

세 층으로 나눠 본다.

1. **파일/블록 캐시** — 원격 저장소에서 가져온 바이트를 로컬에 둔다
2. **쿼리 결과 캐시** — 계산 결과 자체를 재사용한다
3. **대체 수단** — 캐시가 없으면 무엇으로 메우는가

결론부터: **1층은 양쪽 다 있고 기본값이 정반대다**(StarRocks 켜짐, Trino 꺼짐). **2층은 StarRocks 에만 있고, 그마저 네이티브 테이블 전용이며 기본 꺼짐**이다. 3층에서 격차가 다시 벌어진다 — `A-2-06` 의 MV 재작성 차이가 그대로 이어진다.

## 2. Trino 구현

### 2-1. 파일 시스템 캐시가 있다

| 위치 | 내용 |
|---|---|
| `lib/trino-filesystem/.../cache/` | `TrinoFileSystemCache`, `CacheFileSystem`, `CacheInputFile`, `CacheKeyProvider`, **`CacheSplitAffinityProvider`** |
| `lib/trino-filesystem-cache-alluxio/` | Alluxio 기반 구현 (9개 파일) |
| `lib/trino-filesystem/.../memory/` | 메모리 캐시 구현 |

문서가 대상 커넥터를 명시한다.

```
Trino includes support for caching these files with the help of the open
source [Alluxio](https://github.com/Alluxio/alluxio) libraries with catalogs
using the following connectors:

* [](/connector/delta-lake)
* [](/connector/hive)
* [](/connector/iceberg)
```
— `docs/src/main/sphinx/object-storage/file-system-cache.md`

**`CacheSplitAffinityProvider` 가 이 설계의 핵심이다.** 같은 파일의 스플릿을 되도록 같은 노드로 보낸다. 그러지 않으면 N 대 워커가 같은 파일을 각자 캐시해 N 배 낭비한다. 문서도 그렇게 설명한다 — *"with preference for using a fixed set of nodes for a given file"*.

**이는 Trino 가 상태 없는 워커를 전제로 하기 때문에 필요한 장치다.** 스토리지를 소유하지 않으니 "이 데이터는 이 노드 것"이라는 자연스러운 배정이 없고, 캐시를 위해 **인위적으로** 만들어야 한다.

### 2-2. 그러나 기본값이 꺼짐이다

```java
private List<String> cacheDirectories = ImmutableList.of();
private List<DataSize> maxCacheSizes = ImmutableList.of();
private Optional<Duration> cacheTTL = Optional.of(Duration.valueOf("7d"));
private List<Integer> maxCacheDiskUsagePercentages = ImmutableList.of();
private DataSize cachePageSize = DataSize.valueOf("1MB");
```
— `lib/trino-filesystem-cache-alluxio/.../AlluxioFileSystemCacheConfig.java:37-41`

**`cacheDirectories` 가 빈 목록이다.** 캐시를 쓰려면 디렉토리를 지정하고 크기를 정해야 한다. 즉 **명시적 운영 결정**이다.

**TTL 이 7일**로 있다는 점이 StarRocks 와 다르다. 용량뿐 아니라 시간으로도 축출한다.

### 2-3. 쿼리 결과 캐시는 없다

`trino/core/` 와 `trino/lib/` 전체에서 `resultcache` / `querycache` 를 대소문자 무시로 검색해 **0건**이다. 문서에도 없다.

**대체 수단은 Materialized View 다.** 그런데 `A-2-06` 에서 확인한 대로 **Trino 에는 MV 자동 재작성 규칙이 0개**다. 즉 사용자가 MV 를 직접 이름으로 조회해야 하고, **원본 테이블을 조회하는 기존 쿼리는 MV 의 혜택을 받지 못한다.**

이 두 사실이 합쳐지면 결론이 분명해진다 — **Trino 에서 "같은 집계를 반복하는 비용"을 줄이는 자동 수단은 파일 캐시가 사실상 전부다.**

## 3. StarRocks 구현

### 3-1. Data Cache 가 기본으로 켜져 있다

```cpp
CONF_Bool(datacache_enable, "true");
CONF_mString(datacache_mem_size, "20%");
CONF_mString(datacache_disk_size, "100%");
CONF_Int64(datacache_block_size, "262144"); // 256K
```
— `be/src/common/config.h:1372-1375`

**설정을 하나도 하지 않아도 돈다.** 메모리 20% 와 디스크 100% 를 캐시로 쓴다. 구현은 `be/src/cache/`(`mem_cache`, `disk_cache`) 2단 구조다.

블록 단위가 **256KB** 로 Trino 의 1MB 보다 작다. 작은 블록은 세밀한 적중을 노리고, 큰 블록은 관리 비용을 줄인다 — 어느 쪽이 낫다고 말할 근거는 없다.

**노드 배정 문제가 없다는 점이 Trino 와 다르다.** StarRocks BE 는 태블릿을 소유하므로(`C-1`) 어느 노드가 어느 데이터를 읽을지가 이미 정해져 있고, 외부 테이블에서도 스캔 범위 배정이 안정적이다. **Trino 가 `CacheSplitAffinityProvider` 로 인위적으로 만든 것을 StarRocks 는 구조적으로 갖고 있다.**

### 3-2. Query Cache 는 별도 계층이다

```java
public static final String ENABLE_QUERY_CACHE = "enable_query_cache";
public static final String QUERY_CACHE_FORCE_POPULATE = "query_cache_force_populate";
public static final String QUERY_CACHE_ENTRY_MAX_BYTES = "query_cache_entry_max_bytes";
public static final String QUERY_CACHE_ENTRY_MAX_ROWS = "query_cache_entry_max_rows";
public static final String QUERY_CACHE_HOT_PARTITION_NUM = "query_cache_hot_partition_num";
```
— `fe/fe-core/.../qe/SessionVariable.java:730-737`

구현은 `be/src/exec/query_cache/` 다. **파일 바이트가 아니라 부분 집계 결과를 파티션 단위로 캐시한다.** `QUERY_CACHE_HOT_PARTITION_NUM` 이 성격을 말해 준다 — **최근 파티션만** 캐시한다. 대시보드처럼 "최근 N 일을 반복 집계"하는 패턴을 겨냥한 것이다.

기본값은 꺼짐이다.

```java
@VarAttr(name = ENABLE_QUERY_CACHE)
private boolean enableQueryCache = false;
```
— `SessionVariable.java:2567-2568`

### 3-3. Query Cache 는 네이티브 테이블 전용이다

`planner/` 아래 스캔 노드 중 query cache 를 다루는 것은 **`OlapScanNode.java` 하나뿐**이다.

```java
int pkHotNum = connectContext.getSessionVariable().getQueryCacheHotPartitionNum();
```
— `fe/fe-core/.../planner/OlapScanNode.java:1314`

`IcebergScanNode.java` 에는 `QueryCache` 언급이 **0건**이다. 4절에서 실측으로 확인한다.

## 4. 실측

전문은 `docs/evidence/B/20260904-cache-layer-probes.md`.

### 4-1. StarRocks 캐시는 아무 설정 없이 돌고 있었다

랩의 BE `/varz` 가 `datacache_enable=true` 를 보고한다. **compose 파일에 캐시 설정이 없는데도 켜져 있다.**

같은 쿼리를 두 번 돌리고 두 번째 프로파일을 봤다.

```
FooterCacheReadCount: 1
FooterCacheReadTimer: 3.125us
FooterCacheWriteCount: 0
PageCacheReadCounter: 1
PageCacheReadDecompressedCounter: 1
PageCacheWriteCounter: 0
```

**읽기 1, 쓰기 0** — 두 번째 실행은 Parquet footer 와 페이지를 캐시에서 가져왔고 새로 채우지 않았다.

### 4-2. Query Cache 는 Iceberg 에 적용되지 않았다

```sql
SET enable_query_cache=true;
SELECT l_returnflag, sum(l_quantity) FROM iceberg.bench.lineitem GROUP BY l_returnflag;
```

결과는 정상이고 세션 변수도 `false -> true` 로 바뀌었다. 그러나 **프로파일에 캐시 연산자가 나타나지 않는다.** 3-3 의 코드와 일치한다.

### 4-3. 재지 못한 것

**Trino 파일 캐시는 랩에 구성돼 있지 않아 실측하지 못했다.** 2절은 코드와 문서 독해다.

**캐시로 인한 속도 이득도 재지 않았다.** SF 0.01 에서는 캐시가 있든 없든 밀리초 단위라 판별력이 없다.

## 5. 설계 차이와 그 원인

### 5-1. 요약

| 관점 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 파일/블록 캐시 | **있음** — Alluxio 기반, Hive·Iceberg·Delta | **있음** — Data Cache (mem + disk 2단) |
| 기본값 | **꺼짐** (`fs.cache.directories` 빈 목록) | **켜짐** (`datacache_enable=true`) |
| 크기 | 명시 지정 필요 | 메모리 20% + 디스크 100% |
| TTL | **7일** | 없음(용량 축출) |
| 블록 단위 | 1MB | 256KB |
| 노드 배정 | **`CacheSplitAffinityProvider`** 로 인위적 고정 | 구조적으로 안정(BE 가 데이터를 소유) |
| 쿼리 결과 캐시 | **없음** | **있음** — 단 **네이티브 테이블 전용**, 기본 꺼짐 |
| 자동 재사용 대체 수단 | MV — **자동 재작성 없음**(`A-2-06`) | MV — **자동 재작성 있음** |

### 5-2. "기본 켜짐"이 뜻하는 것

이 차이는 단순한 기본값 선택이 아니라 **제품이 상정한 배포 형태**에서 나온다.

**StarRocks BE 는 로컬 디스크를 전제한다.** 태블릿을 저장해야 하므로 어차피 디스크가 있고, 그 디스크의 남는 공간을 캐시로 쓰는 것은 추가 비용이 아니다. 그래서 **켜 두는 것이 기본**이다.

**Trino 워커는 디스크를 전제하지 않는다.** 상태 없는 워커라 디스크가 없거나 아주 작을 수 있다(컨테이너 기본 배포). 임의로 디스크를 채우면 안 되므로 **운영자가 명시적으로 열어 줘야 한다.**

즉 `A-5-01` 이후 반복돼 온 구도 — **스토리지를 소유하는가** — 가 캐시 기본값에서도 그대로 나타난다.

### 5-3. 캐시 친화 배정은 상태 없음의 대가다

`CacheSplitAffinityProvider` 는 Trino 가 치르는 비용을 드러낸다. 워커가 상태 없이 아무 스플릿이나 받는 것이 Trino 의 강점(탄력적 확장, 노드 교체 자유)인데, **캐시는 정확히 그 반대를 원한다** — 같은 데이터가 같은 노드로 와야 한다.

그래서 "선호(preference)"라는 절충이 나온다. 강제하면 스케줄링 유연성을 잃고, 안 하면 캐시가 무력해진다.

**StarRocks 에는 이 긴장이 없다.** 대신 노드를 늘리거나 줄일 때 데이터를 옮겨야 하는 다른 비용을 치른다(`C-1`).

### 5-4. 결과 캐시의 부재가 MV 격차와 겹친다

Trino 에는 쿼리 결과 캐시가 없고, MV 자동 재작성도 없다(`A-2-06`). **두 부재가 같은 방향으로 겹친다.**

| 반복되는 집계를 줄이는 수단 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 결과 캐시 | 없음 | 있음(네이티브 전용) |
| MV 자동 재작성 | **없음** | **있음**(재작성 전용 코드 18,000줄) |
| MV 수동 조회 | 가능 | 가능 |
| 파일 캐시 | 있음(기본 꺼짐) | 있음(기본 켜짐) |

**대시보드형 워크로드에서 이 표가 곧 결론이다.** Trino 는 파일 캐시로 I/O 만 줄이고 계산은 매번 다시 한다. StarRocks 는 계산 자체를 건너뛸 수 있다.

`A-2-06`·`A-2-07` 과 이 문서가 같은 결론을 세 각도에서 지지한다 — **반복 조회 가속에서는 StarRocks 가 명확히 앞선다.**

## 6. 결론

**"Trino 에 캐시가 없다"는 틀렸다. 갈리는 것은 층과 기본값이다.**

- **파일 캐시**: 양쪽 다 있다. **Trino 는 기본 꺼짐, StarRocks 는 기본 켜짐**. 이 차이가 실무에서 가장 크다 — 아무 설정 없이 붙이면 한쪽만 캐시가 돈다
- **쿼리 결과 캐시**: **StarRocks 에만 있다.** 다만 네이티브 테이블 전용이고 기본 꺼짐이다(실측 확인)
- **대체 수단**: Trino 는 MV 자동 재작성도 없어(`A-2-06`) 계산 재사용 수단이 사실상 없다
- **구조**: Trino 는 캐시를 위해 스플릿 배정을 인위적으로 고정해야 하고(`CacheSplitAffinityProvider`), StarRocks 는 데이터를 소유해 그 문제가 없다

**실무 결론**

1. **Trino 를 레이크하우스 조회에 쓴다면 파일 캐시를 반드시 켜라.** 기본값이 꺼짐이라 "느리다"는 인상이 설정 누락에서 올 수 있다. `fs.cache.directories` 와 `fs.cache.max-sizes` 를 지정해야 한다
2. **워커에 로컬 디스크가 없으면 Trino 파일 캐시를 쓸 수 없다.** 캐시를 쓸 계획이라면 배포 형태를 먼저 정해야 한다
3. **StarRocks 의 Query Cache 를 외부 Iceberg 에 기대하지 말 것.** 네이티브 테이블 전용이다(실측 확인). 외부 테이블에서 반복 집계를 줄이려면 **MV** 를 써야 한다(`A-2-06`)
4. **StarRocks 는 캐시가 기본 켜짐이므로 디스크 용량 계획에 포함해야 한다.** `datacache_disk_size` 기본값이 **100%** 다

### 아직 답하지 않은 것

- **Trino 파일 캐시의 실측** — 랩에 구성돼 있지 않다. 적중률·성능 이득 모두 미확인
- **캐시로 인한 속도 이득** — 양쪽 다 재지 않았다. SF 0.01 에서는 판별력이 없다(`perf` 프로파일 필요)
- **StarRocks Query Cache 를 네이티브 테이블에서** — 랩 테이블이 전부 외부 Iceberg 라 시험하지 못했다. `C-1-01` 이후 가능하다
- **캐시 무효화** — 원본 파일이 바뀌었을 때 두 캐시가 어떻게 반응하는지 확인하지 않았다. Iceberg 는 파일이 불변이라 상대적으로 단순하지만, Hive 테이블에서는 다를 수 있다
- **1MB vs 256KB 블록 크기의 실효** — 어느 쪽이 유리한지 판단할 근거가 없다
- **`datacache_disk_size = 100%` 의 위험** — 디스크를 다 쓰면 어떻게 되는지 확인하지 않았다. `A-5-03`·`plan/02` 에서 본 대로 이 랩은 디스크 부족으로 한 번 무너진 적이 있다
