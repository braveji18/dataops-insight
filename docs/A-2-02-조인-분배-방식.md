## 1. 비교 관점

조인 순서를 정한 뒤에도 **각 조인을 어떻게 실행할지**가 남는다. 빌드측을 모든 노드에 복제할 것인가(broadcast/replicated), 양쪽을 조인 키로 재분배할 것인가(shuffle/partitioned). 잘못 고르면 네트워크와 메모리를 통째로 낭비하므로, 실무에서 실행 시간 차이가 가장 크게 나는 결정 중 하나다.

앞 문서(A-2-01)의 실측에서는 **SF 0.01 에서 전량 broadcast가 나와 판별되지 않았다.** 이 문서는 임계값을 직접 움직여 판별력을 만든다.

결론부터: 양쪽 다 비용 기반으로 고르지만, **broadcast를 후보로 허용할지 판단하는 게이트의 축이 다르다.** Trino는 빌드측 바이트만 보고, StarRocks는 양측 상대 크기와 BE 수를 본다. 그리고 기본 설정에서 **같은 쿼리에 서로 다른 결론을 낸다.**

## 2. Trino 구현

### 2-1. 위치 — 전용 규칙, AddExchanges 이전

`works/trino/core/trino-main/src/main/java/io/trino/sql/planner/PlanOptimizers.java:878` 에 `DetermineJoinDistributionType` 이 등록돼 있고, 소스에 `// Must run before AddExchanges` 주석이 붙어 있다. 즉 **분배 방식은 교환(Exchange) 노드를 삽입하기 전에 확정**된다.

A-2-01의 `ReorderJoins` 와 마찬가지로 `IterativeOptimizer` 가 돌리는 규칙 하나다.

### 2-2. 결정 — 비용 비교, 실패 시 크기 휴리스틱

`works/trino/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java`:

- `:73-79` — `join_distribution_type` 이 `AUTOMATIC`(기본)이면 `getCostBasedJoin()`, 아니면 사용자가 지정한 방식을 그대로 쓴다
- `:98-112` — 양쪽 분배 방식 후보를 만들고(원본과 좌우를 뒤집은 것까지 **최대 4개**) 비용으로 최소를 고른다
- `:105-107` — 후보 중 **비용에 미상 성분이 하나라도 있으면** 비용 비교를 포기하고 `getSizeBasedJoin()` 으로 내려간다
- `:114-158` — 크기 휴리스틱. 빌드측이 임계값 이하면 REPLICATED, 아니면 한쪽이 다른 쪽보다 **8배**(`SIZE_DIFFERENCE_THRESHOLD`, `:55`) 이상 작으면 그쪽을 빌드측으로 두고 PARTITIONED
- `:185-190` — `RIGHT`/`FULL` 조인은 `mustPartition` — 복제하면 매칭되지 않은 우측 행이 중복되므로 구조적으로 broadcast가 불가능하다

### 2-3. 게이트 — 빌드측만 본다

핵심은 `canReplicate` (`:82-96`)다.

```java
double buildSideSizeInBytes = buildSideStatsEstimate.getOutputSizeInBytes(buildSide.getOutputSymbols());
return buildSideSizeInBytes <= joinMaxBroadcastTableSize.toBytes()
        || getSourceTablesSizeInBytes(buildSide, ...) <= joinMaxBroadcastTableSize.toBytes();
```

- 판단 대상은 **빌드측(오른쪽)뿐**이다. 프로브측 크기는 게이트에 들어오지 않는다
- 두 항의 **OR** 다. 빌드측 **출력 크기**(그 조인에 실제로 필요한 컬럼만) 또는 **소스 테이블 크기** 중 하나만 통과하면 된다
- 단위는 **바이트**. 기본 100MB (`OptimizerConfig.java:46`)
- 이 게이트는 비용 기반 모드에서도 적용된다 — `addJoinsWithDifferentDistributions` (`:160-168`)가 `canReplicate` 가 거짓이면 REPLICATED 후보를 **아예 만들지 않는다**

"출력 크기"라는 점이 실측에서 그대로 확인된다(4절). 테이블이 커도 조인 키 하나만 쓰면 게이트를 통과할 수 있다.

## 3. StarRocks 구현

### 3-1. 위치 — 전용 규칙이 아니라 Cascades 속성 강제 단계

StarRocks에는 분배 방식을 정하는 별도 규칙이 없다. 분배는 **물리 속성(distribution property)** 이고, Cascades가 그룹의 요구 속성을 만족시키는 과정에서 결정된다. 판단이 들어 있는 곳은 `works/starrocks/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/task/EnforceAndCostTask.java` — 즉 **비용 계산 태스크 안**이다.

A-2-01에서 본 구도와 같다. Trino는 파이프라인의 독립된 칸에서, StarRocks는 Cascades 탐색 안에서 결정한다.

### 3-2. 게이트 — 양측 상대 크기 + BE 수 + 행 수

`EnforceAndCostTask.java:298-329`:

```java
// 구조적으로 broadcast 밖에 안 되는 경우는 제한을 보지 않는다
if (JoinHelper.onlyBroadcast(node.getJoinType(), equalOnPredicate, node.getJoinHint())) return true;

if (sv.getBroadcastRowCountLimit() <= 0) return false;          // 전면 비활성
int beNum = Math.max(1, ctx.getAliveBackendNumber());
...
if (leftChildStats == null || rightChildStats == null) return false;   // 통계 없으면 거부

if (leftOutputSize < rightOutputSize * beNum * sv.getBroadcastRightTableScaleFactor()
        && rightChildStats.getOutputRowCount() > sv.getBroadcastRowCountLimit()) {
    return false;
}
return true;
```

거부 조건이 **AND 두 개**다.

| 조건 | 의미 |
|---|---|
| `left < right × beNum × 10` | 오른쪽이 왼쪽에 비해 *충분히 작지 않다* |
| `right 행 수 > 1500만` | 오른쪽이 절대적으로도 크다 |

둘 다 참일 때만 거부한다. 뒤집으면 — **오른쪽이 왼쪽보다 훨씬 작으면 행 수 제한을 아예 보지 않는다.** 소스 주석이 그 의도를 밝히고 있다: `Otherwise, this limit is not considered, which can avoid shuffling large left-hand table data`. 큰 왼쪽 테이블을 셔플하느니 오른쪽을 복제하는 편이 낫다는 판단이다.

`beNum` 이 곱해지는 것도 특징이다. **BE가 많을수록 broadcast가 관대해진다** — 복제 비용이 노드 수에 비례해 커지는데도 그렇다. 이 식은 "복제 총량"이 아니라 "왼쪽을 셔플하는 비용과의 상대 비교"로 읽어야 한다.

### 3-3. 기본값

`works/starrocks/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java:1779-1783`:

```
broadcast_row_limit                 = 15000000
broadcast_right_table_scale_factor  = 10.0     # INVISIBLE
```

단위가 **행 수**다. Trino의 바이트 기준과 대비된다. 행 폭(컬럼 수·타입)이 다르면 같은 행 수라도 전송량이 크게 달라지므로, 이 축의 차이는 넓은 테이블에서 벌어질 수 있다.

## 4. 실측

### 4-1. 기본 설정에서 결론이 갈린다

| 쿼리 | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| `lineitem ⋈ supplier` (빌드 81행) | REPLICATED | BROADCAST |
| `lineitem ⋈ orders` (빌드 15000행) | **REPLICATED** | **PARTITIONED** |

같은 데이터, 같은 쿼리에서 Trino는 복제를, StarRocks는 셔플을 골랐다. **게이트 차이가 아니다** — StarRocks에서 `[broadcast]` 힌트를 주면 broadcast 플랜이 나오므로 후보로는 허용돼 있었고, **비용 모델이 셔플을 골랐다.**

### 4-2. Trino의 게이트는 "빌드측 출력 크기"다

`lineitem ⋈ supplier` 에서 `join_max_broadcast_table_size` 만 바꾸자 경계가 **500B~1kB 사이**에서 나타났다. supplier 81행 × bigint 8바이트 = **648바이트**로, 조인 키 하나만 투영한 크기와 정확히 일치한다. 2-3의 `getOutputSizeInBytes(buildSide.getOutputSymbols())` 가 실제로 그렇게 동작한다는 확인이다.

### 4-3. StarRocks의 행 수 제한은 조건부다

`lineitem ⋈ supplier` 에서 `broadcast_row_limit` 을 **1** 로 낮춰도 broadcast가 유지됐다(81 > 1 인데도). `left < right × beNum × 10` 이 거짓이라 AND가 성립하지 않기 때문이다. **0** 으로 두면 그제서야 PARTITIONED가 됐다 — `<= 0` 조기 반환 경로다.

3-2에서 읽은 탈출구가 실제로 동작한다.

재현 절차와 한정은 `docs/evidence/A-2/20260831-join-distribution-gate.md`.

## 5. 설계 차이와 그 원인

| | Trino | StarRocks |
|---|---|---|
| 결정 위치 | 전용 규칙, AddExchanges 이전 | Cascades 속성 강제(`EnforceAndCostTask`) 내부 |
| 게이트 판단 대상 | **빌드측만** | **양측 상대 크기 + BE 수** |
| 게이트 단위 | **바이트** (기본 100MB) | **행 수** (기본 1500만) |
| 게이트 형태 | 출력 크기 **OR** 소스 크기 | 상대 크기 **AND** 행 수 (둘 다여야 거부) |
| 통계 없을 때 | 크기 휴리스틱으로 하강(8배 규칙) | **broadcast 거부** → 셔플 |
| 클러스터 규모 반영 | 비용 모델의 `taskCountEstimator` | 게이트 식에 `beNum` 직접 등장 |

A-2-01에서 본 구도가 여기서도 반복된다. **Trino는 판단을 파이프라인의 독립된 칸에 모아두고, StarRocks는 Cascades 탐색 안에 녹인다.** 전자는 읽고 추적하기 쉽고, 후자는 다른 결정과 함께 비용으로 저울질된다.

게이트 축의 차이(바이트 vs 행 수)는 각자의 위치에서 자연스럽다. Trino는 커넥터가 주는 통계에 의존하는데 바이트 크기는 파일 기반 커넥터가 비교적 잘 제공한다. StarRocks는 자체 스토리지의 행 수 통계를 신뢰할 수 있다.

통계가 없을 때의 행동도 A-2-01과 같은 방향이다. **Trino는 대체 휴리스틱으로 내려가 어떻게든 고르고, StarRocks는 안전한 쪽(셔플)으로 거부한다.** 다만 A-2-01의 조인 순서에서는 반대였다 — Trino가 포기하고 StarRocks가 left-deep이라도 했다. 즉 "누가 더 보수적인가"는 항목마다 다르며, **한 문장으로 일반화할 수 없다.**

## 6. 결론

**동등하지 않고, 우열도 판정할 수 없다.**

- 게이트만 보면 두 엔진은 서로 다른 것을 재고 있다. 바이트 대 행 수는 **넓은 테이블에서 갈린다** — 같은 행 수라도 전송량이 다르기 때문이다
- StarRocks의 게이트는 클러스터 규모(`beNum`)에 직접 반응한다. **BE를 늘리면 broadcast 성향이 강해진다.** Trino의 게이트는 노드 수와 무관하다(비용 모델이 별도로 반영)
- 기본 설정에서 결론이 갈린 사례(`lineitem ⋈ orders`)의 원인은 게이트가 아니라 **비용 모델**이다. 이것은 A-2 후속 문서의 주제다

운영 관점에서는 **손잡이를 돌렸을 때 무엇이 변하는지가 다르다.** Trino의 `join_max_broadcast_table_size` 는 빌드측 크기 하나만 걸러내므로 예측이 쉽다. StarRocks의 `broadcast_row_limit` 은 오른쪽이 충분히 작으면 무시되므로, **값을 낮춰도 broadcast가 사라지지 않는다** — 4-3에서 실제로 그랬다. 전면적으로 끄려면 0으로 두어야 한다. 이 비대칭은 튜닝할 때 반드시 알고 있어야 한다.

### 아직 답하지 않은 것

- **비용 모델 자체** — 4-1에서 결론이 갈린 진짜 원인. A-2 다음 문서 주제
- **다중 BE / 다중 worker 에서의 재현** — StarRocks 게이트에 `beNum` 이 곱해지므로 BE 1대 결과를 확장 해석할 수 없다. 현재 랩 구성으로는 불가
- **실행 시간** — 어느 선택이 실제로 빨랐는지는 측정하지 않았다(`perf` 프로파일 필요, `plan/02` 6-2절)
- **넓은 테이블에서의 바이트 vs 행 수 차이** — TPC-H 로는 드러나지 않는다. 컬럼이 많은 테이블이 필요하다
