## 한 장 요약

앞선 여섯 편의 보고서에서 "**통계가 없으면**", "**통계가 낡으면**"이라는 단서가 반복해서 붙었습니다. 이번에는 그 앞단을 봤습니다 — **그 통계는 누가, 언제, 어디에 만들어 두는가.**

| | Trino | StarRocks |
|---|---|---|
| 누가 만드나 | 엔진이 계산하고 **저장소가 보관** | **엔진이 전부** 담당 |
| 어디에 두나 | **데이터 파일 안**(다른 제품도 읽을 수 있음) | 엔진 내부 데이터베이스 |
| 자동 수집 | **데이터를 쓸 때만** | **배경에서 주기적으로** |
| 무엇을 수집할지 | 사람이 지정 | **조회를 관찰해 엔진이 선택** |
| 담을 수 있는 통계 | 4종 (문자열 최소·최대값 **불가**) | 6종 이상 + 분포표 + 다중 컬럼 |
| **두 제품이 통계를 공유하나** | **아니오** — 같은 파일을 봐도 각자 따로 수집해야 함 | 좌동 |

**결론: 자동화와 표현력은 StarRocks가 앞섭니다. 대신 Trino는 통계를 데이터와 함께 남겨 다른 제품과 공유할 수 있습니다. 그리고 두 제품을 함께 쓴다면 양쪽에서 각각 통계를 수집해야 합니다.**

---

## 1. 왜 이걸 봤나

통계는 **엔진이 실행 방법을 고르는 유일한 근거**입니다. 앞선 보고서에서 확인한 것들이 전부 여기에 매달려 있습니다.

- 통계가 없으면 Trino는 **순서 재배치를 아예 포기**합니다(3번 보고서)
- 통계가 없으면 StarRocks는 **집계를 앞당기지 않습니다**(4번 보고서)
- 통계 부족이 원인이었던 오판을 실제로 겪었습니다(3번 보고서의 정정 이력)

따라서 운영에서 중요한 질문은 하나입니다 — **통계 관리가 사람의 일인가, 제품의 일인가.**

---

## 2. Trino의 방식 — "저장소에 맡기고, 데이터와 함께 남긴다"

### 2-1. 통계는 저장소 연결 모듈이 준다

**[ConnectorMetadata.java#L452-L455](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/connector/ConnectorMetadata.java#L452-L455)**

```java
    default TableStatistics getTableStatistics(ConnectorSession session, ConnectorTableHandle tableHandle)
    {
        return TableStatistics.empty();
    }
```

▸ **읽는 법** — 엔진이 통계를 얻는 창구는 이 하나뿐입니다. 그리고 **기본 구현이 "빈 통계"를 돌려줍니다** — 연결 모듈이 이 부분을 구현하지 않으면 엔진은 아무것도 모르는 채로 실행 방법을 정해야 합니다.

엔진 안에는 **통계 저장소도, 자동 수집 작업도 없습니다.** 통계를 소비하는 코드(약 7,000줄)만 있습니다.

### 2-2. 컬럼 하나당 담을 수 있는 정보가 4가지다

**[ColumnStatistics.java#L26-L29](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/statistics/ColumnStatistics.java#L26-L29)**

```java
    private final Estimate nullsFraction;
    private final Estimate distinctValuesCount;
    private final Estimate dataSize;
    private final Optional<DoubleRange> range;
```

▸ **읽는 법** — 빈 값의 비율, 서로 다른 값의 개수, 데이터 크기, 그리고 값의 범위. **네 가지가 전부입니다.**

주목할 것은 네 번째의 타입 `DoubleRange` 입니다 — **숫자 범위만 담을 수 있습니다.** 즉 **문자열이나 날짜 컬럼의 최소·최대값을 이 구조에 담을 수 없습니다.** 4-1에서 실제로 그 자리가 비어 있는 것을 확인했습니다.

**값의 분포를 나타내는 분포표(히스토그램)도 없습니다.** 관련 클래스 자체가 존재하지 않습니다.

### 2-3. 통계를 데이터 파일 안에 남긴다

Iceberg 형식의 경우, 서로 다른 값의 개수는 **데이터 파일 옆의 통계 파일**에서 읽어옵니다.

**[TableStatisticsReader.java#L290-L295](https://github.com/trinodb/trino/blob/483/plugin/trino-iceberg/src/main/java/io/trino/plugin/iceberg/TableStatisticsReader.java#L290-L295)**

```java
            for (Entry<Integer, BlobMetadata> entry : thetaBlobsByFieldId.entrySet()) {
                int fieldId = entry.getKey();
                BlobMetadata blobMetadata = entry.getValue();
                String ndv = blobMetadata.properties().get(APACHE_DATASKETCHES_THETA_V1_NDV_PROPERTY);
                if (ndv == null) {
                    log.debug("Blob %s is missing %s property", blobMetadata.type(), APACHE_DATASKETCHES_THETA_V1_NDV_PROPERTY);
```

▸ **읽는 법** — `blobMetadata` 는 Iceberg 표준이 정한 **통계 저장 형식**입니다. 즉 **통계가 데이터의 일부로 저장됩니다.**

**이것이 Trino 방식의 강점입니다** — Trino가 만든 통계를 Spark나 다른 Trino 클러스터도 읽을 수 있습니다. 통계가 특정 제품에 갇히지 않습니다.

### 2-4. 자동 수집은 "데이터를 쓸 때"만 일어난다

**[IcebergConfig.java#L76-L77](https://github.com/trinodb/trino/blob/483/plugin/trino-iceberg/src/main/java/io/trino/plugin/iceberg/IcebergConfig.java#L76-L77)**

```java
    private boolean tableStatisticsEnabled = true;
    private boolean collectExtendedStatisticsOnWrite = true;
```

▸ **읽는 법** — 두 번째 `collectExtendedStatisticsOnWrite` 가 **기본 켜짐**입니다. 데이터를 넣거나 표를 새로 만들 때 통계를 함께 계산해 저장합니다. 4-2에서 확인했습니다 — **표를 만드는 것만으로 통계가 생겼습니다.**

**그러나 이후 데이터가 바뀌어도 통계는 갱신되지 않습니다.** 사람이 `ANALYZE` 를 실행해야 합니다. **배경에서 알아서 갱신하는 기능은 없습니다.**

## 3. StarRocks의 방식 — "엔진이 직접 모으고, 무엇을 모을지도 스스로 정한다"

### 3-1. 통계를 엔진 안의 실제 테이블에 쌓는다

**[StatsConstants.java#L66-L72](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/statistic/StatsConstants.java#L66-L72)**

```java
    public static final String STATISTICS_DB_NAME = "_statistics_";
    public static final String SAMPLE_STATISTICS_TABLE_NAME = "table_statistic_v1";
    public static final String FULL_STATISTICS_TABLE_NAME = "column_statistics";
    public static final String EXTERNAL_FULL_STATISTICS_TABLE_NAME = "external_column_statistics";
    public static final String HISTOGRAM_STATISTICS_TABLE_NAME = "histogram_statistics";
    public static final String EXTERNAL_HISTOGRAM_STATISTICS_TABLE_NAME = "external_histogram_statistics";
    public static final String MULTI_COLUMN_STATISTICS_TABLE_NAME = "multi_column_statistics";
```

▸ **읽는 법** — `_statistics_` 라는 **내부 데이터베이스**를 두고 그 안에 통계 테이블을 만듭니다. 이름을 보면 무엇을 담는지 드러납니다 — 표본 통계, 컬럼 통계, 외부 데이터용 컬럼 통계, **분포표**, 외부 데이터용 분포표, **다중 컬럼 결합 통계**.

**Trino의 4가지(2-2)보다 담을 수 있는 것이 넓습니다.** 특히 분포표와 다중 컬럼 결합 통계는 Trino에 개념 자체가 없습니다. 그리고 이 테이블들은 **일반 SQL로 직접 조회할 수 있습니다**(4-1).

### 3-2. 배경에서 주기적으로 수집한다

**[StatisticAutoCollector.java#L48-L50](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/statistic/StatisticAutoCollector.java#L48-L50)**

```java
    public StatisticAutoCollector() {
        super("AutoStatistic", Config.statistic_collect_interval_sec * 1000);
    }
```

▸ **읽는 법** — `AutoStatistic` 이라는 이름의 **배경 작업**이 일정 주기로 돕니다. 기본 주기는 10분입니다. Trino에는 이 개념 자체가 없습니다.

수집 정책도 설정으로 표현돼 있습니다.

**[Config.java#L2465-L2474](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/common/Config.java#L2465-L2474)**

```java
    @ConfField(mutable = true, comment = "The interval of auto stats for small tables")
    public static long statistic_auto_collect_small_table_interval = 0; // unit: second, default 0

    @ConfField(mutable = true, comment = "The interval of auto collecting histogram statistics")
    public static long statistic_auto_collect_histogram_interval = 3600L * 1; // 1h

    @ConfField(mutable = true, comment = "The interval of auto stats for large tables")
    public static long statistic_auto_collect_large_table_interval = 3600L * 12; // unit: second, default 12h
```

▸ **읽는 법** — **"작은 표는 제한 없이 자주, 큰 표는 12시간에 한 번"** 이라는 정책이 설정으로 표현돼 있습니다. 큰 표와 작은 표를 가르는 기준도 따로 있습니다(50억 바이트 또는 1,000만 건). 통계 관련 설정이 **40개**입니다.

### 3-3. 무엇을 수집할지 조회를 관찰해 스스로 정한다

가장 특징적인 부분입니다. 조회가 지나갈 때마다 **각 컬럼이 어떻게 쓰였는지 기록**합니다.

**[ColumnUsage.java#L187-L192](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/statistic/columns/ColumnUsage.java#L187-L192)**

```java
    public enum UseCase {
        NORMAL,
        PREDICATE,
        JOIN,
        GROUP_BY,
        DISTINCT;

```

▸ **읽는 법** — 단순 참조인지, **조건에 쓰였는지**, 테이블을 잇는 데 쓰였는지, 묶는 기준이었는지, 중복 제거에 쓰였는지를 구분해 기록합니다. 이 기록이 `_statistics_` 안의 표에 쌓이고, 자동 수집기가 그것을 보고 **통계가 실제로 필요한 컬럼만 골라 수집합니다.**

4-3에서 이 동작을 실제로 관찰했습니다.

## 4. 실제로 돌려서 확인한 것

**시험 조건**: Trino 처리 서버 1대 / StarRocks 처리 서버 1대, TPC-H 표준 데이터 최소 규모(약 6만 건), 두 제품이 **같은 데이터 파일**을 봅니다. 설정은 전부 기본값입니다.

> 시험용으로 만든 표와 그 통계는 **모두 삭제했습니다.**

### 4-1. 같은 표에 대해 두 제품이 아는 것이 다르다

StarRocks 쪽은 `_statistics_` 안의 표를 **SQL로 직접 조회**해서, Trino 쪽은 `SHOW STATS` 로 확인했습니다.

| 컬럼 | 실제 값 종류 | StarRocks | Trino | StarRocks 최소/최대 | Trino 최소/최대 |
|---|---|---|---|---|---|
| 주문번호 | 15,000 | 15,022 | 14,819 | 1 / 60000 | 1 / 60000 |
| 공급자번호 | 100 | 100 | 100 | 1 / 100 | 1 / 100 |
| 배송일 | — | 2,530 | 2,518 | 1992-01-04 / 1998-11-29 | 1992-01-04 / 1998-11-29 |
| **반품구분(문자)** | 3 | 3 | 3 | **A / R** | **(빈칸)** |

두 가지가 드러납니다.

- **값 종류 개수는 양쪽 다 근사값이고 오차 방향이 다릅니다.** 서로 다른 근사 계산법을 쓰기 때문입니다. 실제 15,000에 대해 한쪽은 +0.15%, 한쪽은 −1.2%
- **문자 컬럼의 최소·최대값이 Trino에는 없습니다.** 2-2의 "숫자 범위만 담을 수 있는" 구조 때문입니다

### 4-2. Trino는 표를 만드는 것만으로 통계가 생겼다

`ANALYZE` 를 실행하지 않고 표만 새로 만들었는데, 곧바로 값 종류 개수가 조회됐습니다. 2-4의 "쓸 때 자동 수집"이 기본 켜짐이기 때문입니다.

### 4-3. StarRocks가 조회에 쓴 컬럼만 골라 자동 수집하는 장면을 포착했다

**시험 중에 제가 실행하지 않은 수집 작업이 이력에 나타났습니다.**

| 대상 표 | 수집된 컬럼 | 시각 |
|---|---|---|
| 시험표1 | `l_suppkey, l_shipdate` | 01:55:34 |
| 시험표2 | `l_suppkey` | 01:56:34 |

**수집된 컬럼이 제가 조건에 쓴 컬럼과 정확히 일치합니다.** 시험표2에는 `WHERE l_suppkey > 99` 하나만 던졌고, 수집된 컬럼도 그것 하나였습니다. 표를 만든 지 **약 1분 만**이었습니다. 3-3의 기록 장치가 실제로 작동한 것입니다.

> **투명성을 위한 기록**: 이 관찰은 **계획했던 시험이 아니라 다른 시험을 하던 중에 우연히 드러난 것**입니다. 따라서 수집 주기와 조건의 상호작용을 통제된 조건에서 재본 것은 아닙니다.

### 4-4. 두 제품은 통계를 공유하지 않는다

**같은 데이터 파일**을 보고 있는데도 그렇습니다.

| 확인 | 결과 |
|---|---|
| Trino가 표를 만들며 저장한 값 종류 개수 | 주문번호 14,830 · 공급자번호 100 |
| StarRocks의 `_statistics_` 에 있는 해당 표의 통계 | **0건** |
| StarRocks의 실행 계획이 보는 컬럼 통계 | **"모름"** |
| StarRocks가 아는 전체 건수 | **60,175** (파일 목록에서 읽음) |

**전체 건수는 데이터 파일 목록에서 읽지만, 컬럼별 통계는 읽지 않습니다.** Trino가 그 파일 안에 저장해둔 값 종류 개수가 거기 있는데도 StarRocks는 "모름"으로 취급합니다.

### 4-5. 분포표는 이번 환경에서 쓸 수 없었다

StarRocks에 분포표 수집을 요청했더니 거부됐습니다.

```
StarRocks : Can't create histogram statistics on table type is ICEBERG
Trino     : 해당 문법 없음
```

**StarRocks에 기능은 있으나 공용 파일 형식(Iceberg)에는 적용되지 않습니다.** 자체 저장소에서의 동작은 확인하지 못했습니다.

## 5. 실무에서 의미 있는 차이

### (1) 통계 관리가 누구의 일인가

| | Trino | StarRocks |
|---|---|---|
| 통계가 없을 때 | **사람이 개입할 때까지 계속** 없음 | 최대 10분~12시간 뒤 **저절로 해소** |
| 통계가 없으면 벌어지는 일 | 순서 재배치를 **포기** — 조회문에 쓴 순서대로 실행 | 임의 값으로 메꾸고 판단 계속 |
| 운영 부담 | **정기 작업으로 편성 필요** | 작음 |
| 자원 사용 | 사람이 돌린 때만 (예측 가능) | 배경에서 수시로 (설정으로 시간대 제한 가능) |

**Trino를 쓴다면 `ANALYZE` 를 정기 작업으로 반드시 편성해야 합니다.** 통계가 없으면 조금 느려지는 게 아니라 **엔진이 최적화를 아예 시도하지 않습니다.**

반대로 StarRocks는 관리 부담이 작지만, 수집 작업이 **예측하기 어려운 시점에 클러스터 자원을 씁니다.** 응답 시간이 민감한 환경에서는 수집 시간대를 설정으로 제한해야 합니다.

### (2) 두 제품을 함께 쓸 때 — 통계를 두 번 관리해야 한다

**이것이 이번 보고에서 가장 실무에 직접 걸리는 항목입니다.**

같은 데이터 저장소에 두 제품을 함께 붙이면:

- Trino의 `ANALYZE` 결과 → 데이터 파일 안에. **StarRocks는 못 봅니다**
- StarRocks의 `ANALYZE` 결과 → 엔진 내부 DB에. **Trino는 못 봅니다**
- 전체 건수처럼 파일 목록에서 직접 읽는 값만 자동으로 공유됩니다

**한쪽에서만 통계를 수집하면 다른 쪽은 통계 없는 상태로 실행 방법을 정합니다.** 성능 비교 시험을 할 때 특히 함정입니다 — 실제로 이 저장소의 시험 환경 구성 스크립트도 적재 후 **양쪽에서 각각** 통계를 수집하도록 만들어져 있습니다.

### (3) 통계가 데이터와 함께 남는가

| | Trino | StarRocks |
|---|---|---|
| 통계의 위치 | **데이터 파일 안** | 엔진 내부 DB |
| 다른 제품과 공유 | **가능** | 불가 |
| 제품을 교체하면 | 통계가 남음 | 통계가 사라짐 |
| 담을 수 있는 것 | 표준 형식이 허용하는 범위로 제한 | **제약 없음** |

**표현력과 이식성이 맞바꿔져 있습니다.** Trino가 분포표를 못 담는 것도, 문자 컬럼의 최소·최대값을 못 담는 것도, "여러 저장 형식에 공통으로 맞출 수 있는 최소한"을 고른 결과로 읽힙니다.

여러 제품이 같은 데이터를 공유하는 환경이라면 Trino 방식이, 한 제품으로 완결되는 환경이라면 StarRocks 방식이 각각 유리합니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **통계 수집 자체에 드는 비용** | 시간·자원 사용량을 재지 않았습니다 | 메모리 24GB 이상 장비 + 큰 데이터 |
| **자동 수집이 언제 도는지의 규칙** | 4-3은 우연히 관찰된 사례입니다. 통제된 조건에서 재보지 않았습니다 | 조건을 통제한 반복 시험 |
| **분포표·다중 컬럼 통계의 실효** | 이번 환경(공용 파일 형식)에서는 분포표를 만들 수 없었습니다 | StarRocks 자체 저장소 시험 |
| **표현력 차이가 만드는 실제 성능 차이** | 문자 컬럼 최소·최대값이 없어서 어떤 조회가 얼마나 나빠지는지 재지 않았습니다 | 해당 유형 조회의 반복 측정 |
| **다른 저장소 형식** | Iceberg 하나로만 확인했습니다. Hive 형식은 통계를 다른 곳에 두므로 Trino 쪽 동작이 다를 수 있습니다 | 형식별 별도 시험 |

**이번 보고는 "누가 만들고 어디에 두는가"이며, "통계 품질이 성능에 미치는 영향의 크기"가 아닙니다.**
