## 한 장 요약

여러 서버로 나눠 처리하는 시스템에서 두 테이블을 합치려면, **데이터를 서버 간에 옮겨야** 합니다. 방법은 크게 둘입니다.

- **복사 방식** — 작은 쪽을 모든 서버에 통째로 복사해 준다 (네트워크는 적게, 메모리는 서버마다 중복)
- **재분배 방식** — 양쪽을 기준값에 따라 다시 나눠 담는다 (메모리는 절약, 네트워크는 많이)

두 엔진 모두 이 선택을 자동으로 하지만, **"복사 방식을 후보로 쓸지" 판단하는 기준이 서로 다른 것을 재고 있었습니다.**

| | Trino | StarRocks |
|---|---|---|
| 무엇을 재나 | **작은 쪽의 크기만** (바이트) | **양쪽의 상대 크기 + 서버 대수** |
| 기준 단위 | **용량** (기본 100MB) | **건수** (기본 1,500만 건) |
| 기준을 넘으면 | 복사 방식을 후보에서 제외 | 조건이 **둘 다** 맞을 때만 제외 |
| 큰 쪽 크기 반영 | 안 함 | 함 |
| 서버 대수 반영 | 간접 (비용 계산에서) | **직접** (판정식에 대수가 곱해짐) |
| 선택지 종류 | 2가지 + 별도 단계의 최적화 | **6가지를 한 번에** |
| 쿼리 한 줄로 개입 | 불가 (설정으로 전체 변경) | 가능 (SQL 지시어) |

**결론: 우열이 아니라 측정 대상이 다릅니다.** 다만 **같은 데이터·같은 쿼리에서 두 엔진이 다른 선택을 하는 사례를 확인**했고, 그 원인까지 규명했습니다(4절).

## 1. 왜 이걸 봤나

이 선택을 잘못하면 **네트워크와 메모리를 통째로 낭비합니다.** 큰 테이블을 모든 서버에 복사하면 메모리가 터지고, 반대로 작은 테이블까지 굳이 재분배하면 불필요한 네트워크 전송이 발생합니다.

실무에서 **응답 시간 차이가 가장 크게 벌어지는 결정 중 하나**이고, 데이터가 커질수록 영향이 커집니다.

앞선 보고(조인 순서)에서는 테스트 데이터가 작아 이 항목이 판별되지 않았습니다. 이번에는 **설정값을 직접 움직여 경계를 찾아내는 방식**으로 확인했습니다.

## 2. Trino의 방식 — "작은 쪽만 보고 판단한다"

### 2-1. 복사 방식을 쓸 수 있는지 먼저 걸러낸다

**[DetermineJoinDistributionType.java#L89-L95](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java#L89-L95)**

```java
DataSize joinMaxBroadcastTableSize = getJoinMaxBroadcastTableSize(context.getSession());

PlanNode buildSide = joinNode.getRight();
PlanNodeStatsEstimate buildSideStatsEstimate = context.getStatsProvider().getStats(buildSide);
double buildSideSizeInBytes = buildSideStatsEstimate.getOutputSizeInBytes(buildSide.getOutputSymbols());
return buildSideSizeInBytes <= joinMaxBroadcastTableSize.toBytes()
        || getSourceTablesSizeInBytes(buildSide, context.getLookup(), context.getStatsProvider()) <= joinMaxBroadcastTableSize.toBytes();
```

▸ **읽는 법** — `buildSide` 는 "복사될 쪽"입니다. 이 함수는 **그쪽만** 봅니다. 반대편이 아무리 커도 판정에 들어오지 않습니다. 마지막 두 줄이 `||`(또는)로 이어져 있어, **둘 중 하나만 통과해도 허용**됩니다.

### 2-2. 기준값은 용량, 기본 100MB

**[OptimizerConfig.java#L46](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L46)**

```java
private DataSize joinMaxBroadcastTableSize = DataSize.of(100, MEGABYTE);
```

> **주의 — "100MB짜리 테이블까지"가 아닙니다.** 2-1의 `getOutputSizeInBytes(buildSide.getOutputSymbols())` 는 **그 조회에서 실제로 쓰이는 컬럼만** 계산합니다. 컬럼이 100개인 테이블이라도 조회에서 1개만 쓰면 그 1개 분량만 셉니다. 따라서 **테이블 용량이 100MB를 넘어도 복사 방식이 선택될 수 있습니다.** 실측에서 이 동작을 그대로 확인했습니다(4-2).

### 2-3. 통과한 방식들의 비용을 비교해 고른다

**[DetermineJoinDistributionType.java#L161-L168](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java#L161-L168)**

```java
private void addJoinsWithDifferentDistributions(JoinNode joinNode, List<PlanNodeWithCost> possibleJoinNodes, Context context)
{
    if (!mustPartition(joinNode) && canReplicate(joinNode, context)) {
        possibleJoinNodes.add(getJoinNodeWithCost(context, joinNode.withDistributionType(REPLICATED)));
    }
    if (!mustReplicate(joinNode, context)) {
        possibleJoinNodes.add(getJoinNodeWithCost(context, joinNode.withDistributionType(PARTITIONED)));
    }
```

▸ **읽는 법** — 후보를 담는 `possibleJoinNodes` 에 복사 방식(`REPLICATED`)과 재분배 방식(`PARTITIONED`)을 각각 넣습니다. 중요한 건 첫 번째 `if` 입니다. **2-1의 걸러내기(`canReplicate`)를 통과하지 못하면 복사 방식은 후보에 아예 담기지 않습니다.** 비용을 비교할 기회조차 없다는 뜻입니다.

### 2-4. 통계가 없으면 간이 규칙으로 내려간다

**[DetermineJoinDistributionType.java#L105-L107](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java#L105-L107)**

```java
if (possibleJoinNodes.stream().anyMatch(result -> result.getCost().hasUnknownComponents()) || possibleJoinNodes.isEmpty()) {
    return getSizeBasedJoin(joinNode, context);
}
```

▸ **읽는 법** — 후보 중 **비용을 계산할 수 없는 것이 하나라도 있으면**(`hasUnknownComponents`) 비용 비교를 포기하고 크기만 보는 간이 규칙으로 넘어갑니다. 앞선 보고(조인 순서)에서 Trino가 통계가 없을 때 **손을 뗐던 것과 다릅니다** — 여기서는 대체 수단이 준비돼 있습니다.

### 2-5. 구조적으로 복사가 불가능한 경우

**[DetermineJoinDistributionType.java#L185-L190](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/DetermineJoinDistributionType.java#L185-L190)**

```java
private static boolean mustPartition(JoinNode joinNode)
{
    JoinType type = joinNode.getType();
    // With REPLICATED, the unmatched rows from right-side would be duplicated.
    return type == RIGHT || type == FULL;
}
```

▸ **읽는 법** — RIGHT JOIN, FULL JOIN은 복사 방식을 쓰면 **결과가 틀립니다.** 개발진이 남긴 주석이 이유를 밝히고 있습니다: *"복사 방식에서는 짝이 없는 오른쪽 행이 중복된다."* 성능 판단이 아니라 **정확성 제약**입니다.

## 3. StarRocks의 방식 — "양쪽을 비교하고 서버 대수까지 본다"

### 3-1. 거부 조건이 두 개이고, 둘 다 맞아야 거부한다

**[EnforceAndCostTask.java#L321-L328](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/task/EnforceAndCostTask.java#L321-L328)**

```java
double leftOutputSize = leftChildStats.getOutputSize(groupExpression.getChildOutputColumns(curChildIndex - 1));
double rightOutputSize = rightChildStats.getOutputSize(groupExpression.getChildOutputColumns(curChildIndex));

if (leftOutputSize < rightOutputSize * beNum * sv.getBroadcastRightTableScaleFactor()
        && rightChildStats.getOutputRowCount() > sv.getBroadcastRowCountLimit()) {
    return false;
}
return true;
```

▸ **읽는 법** — `return false` 가 "복사 방식 거부"입니다. 그 앞의 `if` 조건이 `&&`(그리고)로 묶인 **두 개**입니다.

| 조건 | 뜻 |
|---|---|
| `leftOutputSize < rightOutputSize × beNum × 10` | 오른쪽이 왼쪽에 비해 **충분히 작지 않다** |
| `rightChildStats.getOutputRowCount() > 1,500만` | 오른쪽이 **절대적으로도 크다** |

**둘 다 맞아야 거부합니다.** 뒤집으면 — **오른쪽이 왼쪽보다 훨씬 작으면 건수 제한을 아예 보지 않습니다.** 큰 쪽을 재분배하느니 작은 쪽을 복사하는 게 낫다는 판단이며, 실측으로 확인했습니다(4-3).

`beNum`(서버 대수)이 곱해지는 것도 특징입니다. **서버를 늘릴수록 복사 방식이 더 관대하게 허용됩니다.**

### 3-2. 기준값은 건수, 기본 1,500만 건

**[SessionVariable.java#L1779-L1783](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java#L1779-L1783)**

```java
@VariableMgr.VarAttr(name = BROADCAST_ROW_LIMIT)
private long broadcastRowCountLimit = 15000000;

@VariableMgr.VarAttr(name = BROADCAST_RIGHT_TABLE_SCALE_FACTOR, flag = VariableMgr.INVISIBLE)
private double broadcastRightTableScaleFactor = 10.0;
```

▸ **읽는 법** — 단위가 **건수**입니다(Trino는 용량). 같은 100만 건이라도 컬럼이 5개인 테이블과 200개인 테이블은 전송량이 수십 배 다르므로, **컬럼이 많은 테이블에서 두 엔진의 판단이 갈릴 수 있습니다.** 아래 `10.0` 은 3-1의 판정식에 곱해지는 값이며, 관리 화면에 노출되지 않는 내부 설정입니다(`INVISIBLE`).

### 3-3. 선택지가 2가지가 아니라 6가지다

**[JoinNode.java#L585-L593](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/planner/JoinNode.java#L585-L593)**

```java
public enum DistributionMode {
    NONE("NONE"),
    BROADCAST("BROADCAST"),
    PARTITIONED("PARTITIONED"),
    // The hash algorithms of the two bucket shuffle ways are different
    LOCAL_HASH_BUCKET("BUCKET_SHUFFLE"),
    SHUFFLE_HASH_BUCKET("BUCKET_SHUFFLE(S)"),
    COLOCATE("COLOCATE"),
    REPLICATED("REPLICATED");
```

▸ **읽는 법** — 앞의 둘이 복사·재분배이고, **`BUCKET_SHUFFLE` 두 종류와 `COLOCATE` 는 "데이터를 이미 그렇게 나눠 저장해 뒀으니 옮기지 않고 그대로 처리한다"** 는 방식입니다. StarRocks가 자체 저장 방식을 통제하기 때문에 가능합니다.

**단, "Trino에는 이 기능이 없다"고 말하면 틀립니다.** 확인해 보니 Trino도 같은 최적화를 하며, 다만 **다른 단계에서 처리**합니다.

**[OptimizerConfig.java#L62](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L62)**

```java
private boolean colocatedJoinsEnabled = true;
```

**[AddExchanges.java#L1021-L1026](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/optimizations/AddExchanges.java#L1021-L1026)**

```java
// if colocated joins are disabled, force redistribute when using a custom partitioning
if (!isColocatedJoinEnabled(session) && hasMultipleSources(left.getNode(), right.getNode())) {
    Partitioning rightPartitioning = left.getProperties().translate(createTranslator(leftToRight)).getNodePartitioning().get();
    right = withDerivedProperties(
            partitionedExchange(idAllocator.getNextId(), REMOTE, right.getNode(), new PartitioningScheme(rightPartitioning, right.getNode().getOutputSymbols())),
            right.getProperties());
```

▸ **읽는 법** — 기본값이 **켜짐(true)** 이고, 주석대로 *"꺼져 있을 때만 강제로 재분배한다"* 는 구조입니다. 즉 **양쪽이 이미 같은 방식으로 나뉘어 있으면 Trino도 그대로 처리합니다.**

**정리하면 기능의 유무가 아니라 배치의 차이입니다.** Trino는 "어떻게 나눌까(2가지)"와 "실제로 옮길 필요가 있나"를 **두 단계로 분리**했고, StarRocks는 6가지를 한 번에 결정합니다.

## 4. 실제로 돌려서 확인한 것

### 4-1. 같은 쿼리에서 두 엔진이 다른 선택을 했다

| 쿼리 | Trino | StarRocks |
|---|---|---|
| 큰 테이블 ⋈ 아주 작은 테이블(81건) | 복사 | 복사 |
| 큰 테이블 ⋈ 중간 테이블(15,000건) | **복사** | **재분배** |

두 번째 줄이 갈렸습니다. **원인을 끝까지 확인했습니다.**

먼저 "StarRocks가 복사 방식을 금지한 것 아니냐"를 배제했습니다 — SQL 지시어로 복사 방식을 강제하니 정상 동작했으므로, **후보로는 허용돼 있었고 비용 계산이 재분배를 고른 것**입니다.

> **후속 확인 (2026-09-03).** 비용 계산의 어느 부분인지까지 규명했습니다. **서버가 1대일 때는 재분배의 네트워크 비용이 0으로 계산됩니다.** 관련 설정 하나를 끄자 이 조회가 복사 방식으로 뒤집혔고, 대조군은 움직이지 않았습니다.
>
> **따라서 위 표의 StarRocks 결과는 테스트 환경이 1대짜리라서 나온 것이며, 제품의 일반적 성향이 아닙니다.** 서버를 늘리면 성립하지 않습니다. 보고 시 이 점을 함께 전달해야 합니다.

### 4-2. Trino의 기준은 "테이블 크기"가 아니라 "쓰는 컬럼의 크기"였다

작은 테이블(81건)을 놓고 기준값만 바꿔가며 경계를 찾았습니다.

| 기준값 설정 | 결과 |
|---|---|
| 100바이트 | 재분배 |
| 500바이트 | 재분배 |
| **1,000바이트** | **복사** |
| 10,000바이트 | 복사 |

경계가 500~1,000바이트 사이입니다. **81건 × 8바이트 = 648바이트**로, 이 조회에서 실제로 쓰는 컬럼 1개 분량과 정확히 일치합니다. 2-2에서 설명한 동작이 수치로 확인된 것입니다.

### 4-3. StarRocks의 건수 제한은 조건부로 무시된다

같은 조회에서 건수 제한만 바꿨습니다.

| 설정 | 결과 | 해석 |
|---|---|---|
| 기본(1,500만) | 복사 | |
| **1** | **복사 유지** | 81건 > 1건인데도 유지 — 3-1의 두 번째 조건만 맞고 첫 번째가 안 맞아 거부되지 않음 |
| 0 | 재분배 | 0 이하면 복사 방식 전면 금지 |

**건수 제한을 아무리 낮춰도 복사 방식이 사라지지 않습니다.** 완전히 끄려면 0으로 두어야 합니다. **튜닝할 때 반드시 알고 있어야 하는 동작**입니다.

## 5. 실무에서 의미 있는 차이

### (1) 넓은 테이블(컬럼이 많은 테이블)에서 판단이 갈린다

| | 기준 | 넓은 테이블에서 |
|---|---|---|
| Trino | 용량 | 컬럼이 많아도 **쓰는 것만** 계산 → 관대 |
| StarRocks | 건수 | 컬럼 수와 무관하게 건수로만 판단 → 전송량 과소평가 가능 |

컬럼이 수백 개인 테이블을 다루는 업무가 있다면 짚어볼 항목입니다. **다만 이번 테스트 데이터(TPC-H)로는 확인하지 못했습니다** — 컬럼이 많은 테이블이 없습니다.

### (2) 서버를 늘렸을 때의 방향이 다르다

StarRocks는 판정식에 **서버 대수가 직접 곱해집니다**(3-1). 서버를 늘릴수록 복사 방식을 더 관대하게 허용합니다. Trino의 걸러내기에는 서버 대수가 들어가지 않습니다.

**즉 증설 후 실행 계획이 바뀌는 양상이 다를 수 있습니다.** 이번 테스트는 각 1대 구성이라 **확인하지 못했습니다.**

### (3) 문제 조회 한 건만 급히 손볼 수 있는가

앞선 보고와 같은 구도입니다.

| | Trino | StarRocks |
|---|---|---|
| 개입 단위 | **조회 전체** (설정) | **조인 하나** (SQL 지시어) |
| 지정 방법 | `join_distribution_type` 설정 변경 | `[broadcast]` `[shuffle]` 등을 조회문에 표기 |

4-1에서 **SQL 지시어로 강제해 원인을 좁힌 것**처럼, 지시어는 튜닝 수단이자 **진단 수단**이기도 합니다. Trino에는 이 진단 방법이 없어 설정을 바꿔 같은 일을 해야 합니다.

---

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **여러 대로 늘렸을 때의 동작** | 각 엔진 1대씩만 구성. 4-1 결과가 1대 구성 때문에 나온 것으로 판명돼 **특히 중요한 한계** | 다중 서버 환경 |
| **어느 쪽 선택이 실제로 더 빨랐나** | 테스트 데이터가 작아 시간 차이가 의미 없음 | 메모리 24GB 이상 서버 |
| **넓은 테이블에서의 용량 vs 건수 차이** | 테스트 데이터에 컬럼 많은 테이블이 없음 | 별도 테이블 설계 |
| **미리 나눠 저장한 데이터의 처리(3-3)** | 테스트 테이블이 그렇게 저장돼 있지 않음 | 버킷 설정된 테이블 |

**이번 보고는 "판단 기준이 어떻게 다른가"까지이며, "어느 쪽이 빠른가"가 아닙니다.**

특히 **4-1의 결과는 1대 구성이 만든 것**이므로, 이 표만 떼어내 "StarRocks는 재분배를 선호한다"고 인용하면 잘못된 결론이 됩니다.
