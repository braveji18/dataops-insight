## 한 장 요약

데이터 플랫폼을 도입할 때 보안 검토에서 반드시 나오는 질문은 세 가지입니다. **"설치 직후에는 누구나 다 볼 수 있는가", "개인정보 컬럼만 가리거나 특정 행만 보여줄 수 있는가", "회사가 이미 쓰는 권한 관리 시스템과 연결되는가"** 입니다. 두 제품은 이 세 질문에 서로 다르게 답합니다.

| | Trino | StarRocks |
|---|---|---|
| 설치 직후 기본 상태 | **데이터는 전부 열려 있음** (다른 사용자 사칭만 막음) | **전부 잠겨 있음** (권한을 줘야 보임, 실측) |
| 권한을 판단하는 주체 | 전부 **교체 가능한 부품**(플러그인) | **제품 안에 내장**, 외부 시스템 연결도 가능 |
| 권한이 저장되는 곳 | 설정 파일 또는 외부 서비스 (**클러스터 밖**) | 제품 내부 메타데이터 (**클러스터 안**) |
| 권한 검사 지점 수 | **84곳** | 31곳 |
| 컬럼 가리기·행 제한 | **기본 제공 규칙 파일만으로 가능** | **외부 시스템(Ranger)을 붙여야 가능** |
| 연결되는 외부 권한 시스템 | Ranger, **OPA** | Ranger (**기존 Hive용 정책을 그대로 재사용** 가능) |

**결론: 우열보다는 "권한이 어디에 사는가"의 차이입니다. Trino는 설치 직후 열려 있으므로 운영 전에 반드시 잠가야 하고, StarRocks는 기본으로 잠겨 있지만 컬럼·행 단위 보안이 필요하면 Ranger 도입이 사실상 필수입니다.**

> **이번 보고에서 바로잡은 내용**: 기술 문서 초판은 Trino의 기본 상태를 "모든 것을 허용(`allow-all`)"이라고 적었습니다. 코드를 다시 확인해 보니 실제 기본값은 **`default`** 라는 별도 설정이며, 데이터는 전부 허용하되 **다른 사용자 사칭과 시스템 정보 변경 두 가지는 막습니다.** 실무적 결론(데이터는 열려 있다)은 바뀌지 않습니다. 또 초판에는 **컬럼·행 단위 보안을 어디까지 기본 기능으로 할 수 있는가**가 빠져 있어 이번에 원본을 보강했습니다.

## 1. 왜 이걸 봤나

권한 체계는 도입 후에 바꾸기 가장 어려운 부분입니다. 운영 중인 사용자와 정책을 옮겨야 하기 때문입니다. 그래서 다음 세 가지를 도입 전에 알아야 합니다.

- **설치하고 아무 설정도 안 했을 때 무엇이 열려 있는가**: 보안 사고의 대부분은 "설정을 안 한 상태"에서 납니다
- **개인정보 컬럼 가리기, 부서별 행 제한을 어떤 비용으로 할 수 있는가**: 규제 대응의 핵심 요건입니다
- **이미 쓰고 있는 권한 관리 시스템(Ranger 등)을 그대로 쓸 수 있는가**: 정책을 두 번 관리하면 반드시 어긋납니다

> 용어 한 줄 설명
> - **Ranger**: 하둡 생태계에서 널리 쓰이는 중앙 권한 관리 서비스입니다. 여러 제품의 권한을 한 화면에서 관리합니다
> - **OPA**(Open Policy Agent): 쿠버네티스 등 인프라 전반에서 쓰이는 범용 정책 판단 서비스입니다
> - **RBAC**: 역할(role)에 권한을 주고 사용자에게 역할을 주는 방식입니다

## 2. Trino의 방식 — "판단은 전부 교체 가능한 부품에 맡긴다"

### 2-1. 권한 검사 지점이 84곳으로 잘게 나뉜다

Trino는 "이 사용자가 이 동작을 해도 되는가"를 묻는 지점을 하나의 약속(인터페이스)으로 정의해 두고, 실제 판단은 플러그인이 합니다. 그 약속에 정의된 검사 항목이 **84개**입니다(`checkCan...` 으로 시작하는 기본 메서드 수를 센 값입니다). 카탈로그·스키마·테이블·컬럼부터 프로시저 호출, 세션 설정 변경, 남의 쿼리 종료, 다른 사용자 사칭까지 각각 따로 묻습니다.

컬럼 단위 검사도 이 약속에 들어 있습니다.

**[SystemAccessControl.java#L513-L530](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/security/SystemAccessControl.java#L513-L530)**

```java
    /**
     * Check if identity is allowed to select from the specified columns in a relation.  The column set can be empty.
     *
     * @throws AccessDeniedException if not allowed
     */
    default void checkCanSelectFromColumns(SystemSecurityContext context, CatalogSchemaTableName table, Optional<String> branch, Set<String> columns)
    {
        checkCanSelectFromColumns(context, table, columns);
    }

    /**
     * @deprecated use {@link #checkCanSelectFromColumns(SystemSecurityContext, CatalogSchemaTableName, Optional, Set)}
     */
    @Deprecated
    default void checkCanSelectFromColumns(SystemSecurityContext context, CatalogSchemaTableName table, Set<String> columns)
    {
        denySelectColumns(table.toString(), columns);
    }
```

▸ **읽는 법**: 메서드 이름 그대로 "이 **컬럼들**을 조회해도 되는가"를 묻습니다. 묻는 단위가 테이블이 아니라 **컬럼 묶음(`Set<String> columns`)** 입니다. 약속 자체의 기본 답은 `denySelectColumns`, 즉 **거부**입니다. 이 거부를 허용으로 바꿔 주는 것은 어떤 플러그인을 끼우느냐에 달려 있습니다(2-4 참조).

### 2-2. 행 제한과 컬럼 가리기를 "SQL 식"으로 받는다

**[SystemAccessControl.java#L1060-L1070](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/security/SystemAccessControl.java#L1060-L1070)**

```java
    /**
     * Get row filters associated with the given table and identity.
     * <p>
     * Each filter must be a scalar SQL expression of boolean type over the columns in the table.
     *
     * @return the list of filters, or empty list if not applicable
     */
    default List<ViewExpression> getRowFilters(SystemSecurityContext context, CatalogSchemaTableName tableName)
    {
        return List.of();
    }
```

▸ **읽는 법**: 개발진 주석이 핵심을 말합니다. "각 필터는 **참/거짓을 내는 SQL 식**이어야 한다." 권한 시스템이 "허용/거부"만 답하는 것이 아니라 `region = 'KR'` 같은 **조건식**을 돌려주고, 엔진이 이 식을 사용자의 쿼리에 몰래 덧붙입니다. 컬럼 가리기(`getColumnMasks`, 같은 파일 1128행)도 같은 방식으로, 원래 컬럼 대신 `'***'` 같은 식으로 바꿔 끼웁니다.

### 2-3. 외부 권한 시스템이 없어도 규칙 파일 한 장으로 컬럼·행까지 된다

Trino에는 별도 서버 없이 쓰는 **기본 제공 규칙 파일**(JSON) 방식이 있습니다. 이 규칙의 테이블 항목이 받는 값입니다.

**[CatalogTableAccessControlRule.java#L36-L44](https://github.com/trinodb/trino/blob/483/lib/trino-plugin-toolkit/src/main/java/io/trino/plugin/base/security/CatalogTableAccessControlRule.java#L36-L44)**

```java

            @JsonProperty("user") Optional<Pattern> userRegex,

```

**[ColumnConstraint.java#L28-L33](https://github.com/trinodb/trino/blob/483/lib/trino-plugin-toolkit/src/main/java/io/trino/plugin/base/security/ColumnConstraint.java#L28-L33)**

```java

    public ColumnConstraint(
            @JsonProperty("name") String name,
            @JsonProperty("allow") Optional<Boolean> allow,

            @JsonProperty("mask_environment") Optional<ExpressionEnvironment> maskEnvironment)
```

▸ **읽는 법**: `@JsonProperty("...")` 안의 이름이 규칙 파일에 쓰는 항목 이름입니다. 테이블 규칙에 `filter`(**행 제한 조건식**)와 `columns`(**컬럼별 제약**)가 있고, 컬럼 제약에는 `allow`(**아예 차단**)와 `mask`(**가리기 식**)가 있습니다. `user`·`role`·`group` 으로 대상자를 고릅니다. 즉 **"영업팀은 고객 테이블의 주민번호 컬럼을 `***` 로 보고, 자기 지역 행만 본다"를 JSON 한 장으로 쓸 수 있습니다.** Ranger나 OPA는 이 규칙을 중앙 서비스로 옮기고 싶을 때 고르는 선택지입니다.

외부 권한 시스템 연결은 별도 플러그인(`plugin/trino-ranger`, `plugin/trino-opa`)으로 제공됩니다. **OPA 연결은 두 제품 중 Trino에만 있습니다.**

**[DefaultSystemAccessControl.java#L54-L64](https://github.com/trinodb/trino/blob/483/lib/trino-plugin-toolkit/src/main/java/io/trino/plugin/base/security/DefaultSystemAccessControl.java#L54-L64)**

## 3. StarRocks의 방식 — "권한을 제품 안에 들고, 필요하면 외부에 맡긴다"

### 3-1. 아무 권한도 주지 않으면 거부한다

StarRocks의 권한 판단 약속(`AccessController`)에는 검사 항목이 **31개** 있고, 그 기본 답이 전부 거부입니다.

**[AccessController.java#L60-L63](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/authorization/AccessController.java#L60-L63)**

```java
    default void checkTableAction(ConnectContext context, TableName tableName, PrivilegeType privilegeType)
            throws AccessDeniedException {
        throw new AccessDeniedException();
    }
```

▸ **읽는 법**: 본문이 `throw new AccessDeniedException()` 한 줄뿐입니다. **권한 체계를 명시적으로 구현해 허용하지 않는 한 무조건 거부**라는 뜻입니다. 2-4에서 본 Trino의 기본값과 정반대입니다. 4절에서 실제로 새 사용자가 아무것도 조회하지 못하는 것을 확인했습니다.

내장 권한 체계는 제품의 메타데이터 일부로 저장되고, 관리 노드(FE) 사이에 복제됩니다. **권한이 클러스터의 일부**라는 뜻입니다.

### 3-2. 외부 권한 시스템으로 Ranger를 붙일 수 있고, 기존 Hive 정책을 그대로 읽는다

**[RangerHiveAccessController.java#L30-L33](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/authorization/ranger/hive/RangerHiveAccessController.java#L30-L33)**

```java
public class RangerHiveAccessController extends RangerAccessController {
    public RangerHiveAccessController(String serviceName) {
        super("hive", serviceName);
    }
```

▸ **읽는 법**: `super("hive", ...)` 가 핵심입니다. Ranger에 **이미 등록돼 있는 Hive용 정책 정의**를 그대로 가져다 판단합니다. 회사가 하둡/Hive 시절부터 Ranger로 데이터 권한을 관리해 왔다면, **StarRocks를 들여오면서 정책을 새로 만들 필요가 없습니다.** 같은 폴더에 StarRocks 전용 정책 정의를 쓰는 `RangerStarRocksAccessController` 도 있습니다.

반면 **OPA 연결은 없습니다.** 관리 노드 소스 전체에서 "OPA"를 대소문자 구분 없이 검색해 0건이었습니다.

발상은 Trino와 같습니다. 권한 시스템에서 **조건식**을 받아 쿼리에 끼워 넣습니다.

```java
        return null;
    }

    default Expr getRowAccessPolicy(ConnectContext currentUser, TableName tableName) {
        return null;
    }
```

▸ **읽는 법**: 기본값이 `null`, 즉 **정책 없음**입니다. 내장 권한 체계(`NativeAccessController`)는 이것을 재정의하지 않습니다. 또 `CREATE MASKING POLICY` 같은 **정책을 만드는 SQL 문장도 없습니다.** 결과적으로 **StarRocks에서 컬럼 가리기와 행 제한은 Ranger를 통해서만 들어올 수 있습니다.**

### 3-5. 로그인 방식

비밀번호, LDAP, JWT, OAuth2를 지원하고, 사용자 그룹 정보는 파일·LDAP·유닉스 계정 세 곳에서 가져올 수 있습니다. MySQL 접속 방식을 쓰기 때문에 **기존 MySQL용 BI 도구와 클라이언트가 그대로 붙는다**는 부수 효과가 있습니다. Trino에 있는 **Kerberos 로그인**은 StarRocks 로그인 모듈(`authentication/`)에서 찾지 못했습니다(같은 폴더를 "kerberos"로 검색해 0건). 접속 구간 암호화(TLS)용 코드(`SslUtils`)는 있습니다.

## 4. 실제로 돌려서 확인한 것

시험 환경(2026-09-04, Trino 483 / StarRocks 4.0.14, 각 1노드)에서 **StarRocks 쪽만** 확인했습니다.

새 사용자를 만들고 `nation` 테이블에만 조회 권한을 준 뒤, 그 사용자로 접속해 두 테이블을 조회했습니다.

| 대상 | 결과 |
|---|---|
| `nation` (권한 줌) | **정상 조회 (25건)** |
| `lineitem` (권한 안 줌) | **거부** |
| 권한을 주기 전의 `nation` | **거부** |

거부할 때 나온 메시지입니다.

```
ERROR 5203 (42000): Access denied; you need (at least one of) the SELECT privilege(s)
on TABLE lineitem for this operation. Please ask the admin to grant permission(s) or
try activating existing roles using <set [default] role>.
Current role(s): NONE. Inactivated role(s): NONE.
```

메시지가 **필요한 권한, 대상, 현재 켜진 역할과 꺼진 역할**까지 알려 줍니다. "역할은 받았는데 켜지 않았다"는 흔한 실수를 바로 짚어 줍니다.

**Trino 쪽은 확인하지 못했습니다.** 시험 환경에 권한 설정 파일이 없어 2-4의 기본 상태(데이터 전부 허용)로 돌고 있었기 때문입니다. 이는 시험 환경 구성의 한계이며, **2절의 Trino 설명은 전부 코드 확인에 근거합니다.**

> **투명성을 위한 기록**: 기술 문서 초판은 Trino 기본값을 "모두 허용(`allow-all`)"이라고 적었습니다. 이번 보고서를 쓰며 기본값을 정하는 코드(`AccessControlModule.java:41`)까지 따라가 보니 실제로는 `default` 라는 별도 정책이었고, 다른 사용자 사칭과 시스템 정보 변경은 막고 있었습니다. 데이터 접근에 관한 결론은 같지만 원본을 고쳤습니다.

## 5. 실무에서 의미 있는 차이

### (1) 설치 직후 상태가 정반대다

| | Trino | StarRocks |
|---|---|---|
| 행동 | 설정 파일이 없으면 **데이터 전부 허용** | 권한을 주지 않으면 **전부 거부** |
| 실무적 의미 | 운영 투입 전 **권한 설정 파일 유무를 반드시 점검**해야 함 | 처음 쓰는 사람마다 권한 요청이 들어옴. 대신 실수로 열리지 않음 |

**Trino를 운영에 쓴다면 `etc/access-control.properties` 가 있는지를 가장 먼저 확인해야 합니다.** 없으면 접속할 수 있는 사람 누구나 무엇이든 할 수 있습니다.

### (2) 개인정보 컬럼 가리기·행 제한의 도입 비용이 다르다

| | Trino | StarRocks |
|---|---|---|
| 행동 | **규칙 파일(JSON) 한 장**으로 가능. 중앙 관리가 필요하면 Ranger·OPA | **Ranger 서버를 따로 운영해야** 가능 |
| 실무적 의미 | 작은 조직도 바로 적용 | Ranger를 이미 쓰는 조직이 아니면 **별도 시스템 도입 비용**이 듦 |

규제 대응으로 컬럼·행 단위 보안이 필수 요건이라면, StarRocks 쪽은 **Ranger 도입을 함께 계획**해야 합니다. 반대로 이미 Hive/Ranger로 권한을 관리하고 있다면 StarRocks는 **기존 정책을 그대로 재사용**할 수 있어 이전 비용이 크게 줄어듭니다(3-2).

### (3) 권한이 클러스터 밖에 사느냐 안에 사느냐

| | Trino | StarRocks |
|---|---|---|
| 행동 | 권한이 설정 파일 또는 외부 서비스에 있음 | 권한이 제품 내부 메타데이터에 있음 |
| 실무적 의미 | 여러 클러스터에 **같은 정책을 자연스럽게 공유** | 클러스터마다 따로 관리하거나 Ranger로 빼내야 함 |

여러 클러스터(업무별, 개발/운영 분리 등)를 운영할 계획이라면 Trino 쪽 구조가 관리하기 쉽습니다. 단일 클러스터라면 StarRocks의 "SQL로 `GRANT` 하면 끝" 방식이 더 간단합니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| Trino 권한 동작 전반 | 시험 환경에 권한 설정이 없음 | 규칙 파일(2-3)을 넣고 같은 시험 반복 |
| Ranger 연결의 실제 동작 | 양쪽 모두 Ranger 서버가 없음. 특히 Hive 정책을 **얼마나 충실히** 해석하는지 모름 | Ranger 서버와 샘플 정책 |
| 컬럼 가리기·행 제한 실측 | 위와 같음. Trino 규칙 파일은 Ranger 없이도 시험할 수 있으나 이번에 하지 않음 | 규칙 파일 시험, Ranger 시험 |
| 권한 검사가 쿼리 속도에 주는 영향 | 측정하지 않음. 검사 지점 84곳이 계획 단계 지연을 늘리는지 모름 | 권한 설정 유무별 반복 측정 |
| 노드 사이 통신 암호화 | StarRocks 내부 통신(FE-BE, BE-BE) 구간을 확인하지 않음 | 별도 조사 |
| 감사 기록(누가 무엇을 했나) | 이 보고서 범위 밖 | `report/13` 관측성 보고서 참조 |

**이번 보고는 "두 제품의 권한 체계가 어떻게 설계돼 있고 기본 상태가 어떤가"까지이며, "어느 쪽이 더 안전한가"가 아닙니다.** 안전성은 어떤 정책을 어떻게 설정하느냐에 달려 있습니다.
