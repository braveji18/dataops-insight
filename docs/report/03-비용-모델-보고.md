# [보고] Trino vs StarRocks 비교 (3) — 여러 실행 방법 중 하나를 고르는 기준

> 작성일: 2026-09-04 | 대상 버전: Trino 483, StarRocks 4.0.14
> 상세 기술 문서: `docs/A-2-03-비용-모델.md`
>
> 이 보고서의 모든 코드는 위 두 버전의 **실제 소스에서 그대로 발췌**한 것이며,
> 각 제목의 링크로 GitHub에서 원문을 바로 확인하실 수 있습니다.

## 한 장 요약

같은 조회를 처리하는 방법은 보통 수십~수백 가지입니다. 엔진은 그중 하나를 고르는데, **그 판단 기준을 "비용 모델"이라고 부릅니다.** 앞선 두 보고서(조인 순서·조인 분배 방식)에서 "같은 조건인데 두 제품이 다른 선택을 했다"고 남긴 대목이 있었는데, 그 원인이 여기 있습니다.

| | Trino | StarRocks |
|---|---|---|
| 무엇을 비용으로 보나 | 처리량(CPU) **75%** · 메모리 10% · 통신 15% | 처리량 **12.5%** · 메모리 **50%** · 통신 **37.5%** |
| 기준값을 바꿀 수 있나 | **설정 파일로 가능** | **불가** — 소스 코드에 박혀 있음 |
| 데이터 통계가 없으면 | **판단을 포기**하고 조회문에 쓴 순서대로 실행 | **임의의 값으로 메꾸고** 계속 판단 |
| 실행 특성 반영 | 데이터 크기만 계산 | 캐시 효율·병렬 처리 수까지 계산 |
| 조회가 이상할 때 손댈 곳 | 설정값 5종 이상 | 사실상 없음(조회문에 힌트를 적는 방법뿐) |

**결론: 우열을 가릴 수 없습니다. 두 제품은 애초에 재는 대상이 다릅니다. 다만 "선택이 잘못됐을 때 고칠 수단"은 Trino 쪽이 뚜렷하게 많습니다.**

> **주의**: 위 백분율은 **원본 코드값을 환산한 것**입니다. 코드에는 Trino가 `75 / 10 / 15`, StarRocks가 `0.5 / 2 / 1.5` 로 적혀 있고, 각각 합이 100과 4라서 그대로 비교할 수 없어 백분율로 맞췄습니다.
> 그리고 **이 백분율끼리 직접 비교하면 안 됩니다.** 뒤에서 설명하듯 두 제품의 "메모리" 항목은 계산 방식 자체가 다릅니다(2-1, 5-(1)).

## 1. 왜 이걸 봤나

데이터 조회가 느릴 때 원인은 크게 둘입니다. **처리할 데이터가 정말 많거나**, 아니면 **엔진이 나쁜 방법을 골랐거나**입니다. 앞의 것은 장비를 늘리면 해결되지만, 뒤의 것은 장비를 늘려도 그대로입니다.

엔진이 방법을 고르는 기준이 곧 비용 모델이고, 여기서 두 가지가 실무에 직결됩니다.

- **잘못 골랐을 때 사람이 고칠 수 있는가** — 기준값을 조정할 수 있는지, 아니면 제품을 다시 빌드해야 하는지
- **데이터 통계가 없거나 낡았을 때 어떻게 되는가** — 운영 현장에서 통계가 최신인 경우는 오히려 드뭅니다

두 제품이 이 둘에서 **거의 반대 방향**을 택했습니다.

## 2. Trino의 방식 — "적게 재고, 모르면 멈춘다"

### 2-1. 비용을 하나의 점수가 아니라 네 항목으로 따로 관리한다

Trino는 처리량·메모리·통신량을 **끝까지 각각 따로** 들고 다닙니다. 메모리는 두 종류로 더 쪼갭니다.

**[PlanCostEstimate.java#L34-L38](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/cost/PlanCostEstimate.java#L34-L38)**

```java
    private final double cpuCost;
    private final double maxMemory;
    private final double maxMemoryWhenOutputting;
    private final double networkCost;
    private final LocalCostEstimate rootNodeLocalCostEstimate;
```

▸ **읽는 법** — 눈여겨볼 것은 세 번째 `maxMemoryWhenOutputting` 입니다. "결과를 내보내기 시작한 뒤에도 **여전히 붙잡고 있는** 메모리"라는 뜻입니다. Trino는 메모리를 단순히 더하지 않고, *어느 단계에서 얼마나 동시에 점유하는지*를 추적하려고 이 항목을 따로 둡니다. 요약표의 "메모리 10%"가 낮아 보이는 이유가 여기 있습니다 — 이 10%는 **전체 합계가 아니라 동시 점유 최고치**에 붙는 가중치입니다.

### 2-2. 하나의 점수로 합치는 곳은 마지막 비교 시점 한 곳뿐이다

**[CostComparator.java#L63-L65](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/cost/CostComparator.java#L63-L65)**

```java
        double leftCost = left.getCpuCost() * cpuWeight
                + left.getMaxMemory() * memoryWeight
                + left.getNetworkCost() * networkWeight;
```

▸ **읽는 법** — 세 항목에 각각 가중치를 곱해 더합니다. 두 후보를 견줄 때 딱 한 번만 이 계산을 합니다. 그전까지는 항목별로 따로 관리하므로, 나중에 가중치를 바꿔도 앞의 계산을 다시 할 필요가 없습니다.

가중치의 기본값은 다음과 같고, **설정 파일(`config.properties`)에서 바꿀 수 있습니다.**

**[OptimizerConfig.java#L42-L44](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L42-L44)**

```java
    private double cpuCostWeight = 75;
    private double memoryCostWeight = 10;
    private double networkCostWeight = 15;
```

▸ **읽는 법** — 합이 100이라 그대로 백분율로 읽으면 됩니다. **처리량이 압도적으로 큰 기준**입니다. 각각 `optimizer.cpu-cost-weight` 같은 설정 이름으로 노출돼 있어, 제품을 다시 빌드하지 않고 조정할 수 있습니다(재시작은 필요합니다).

### 2-3. 하나라도 모르면 비교 자체를 거부한다

**[CostComparator.java#L59](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/cost/CostComparator.java#L59)**

```java
        checkArgument(!left.hasUnknownComponents() && !right.hasUnknownComponents(), "cannot compare unknown costs");
```

▸ **읽는 법** — `hasUnknownComponents` 는 "비용 항목 중 계산하지 못한 것이 있는가"입니다. 하나라도 있으면 비교를 **거부**합니다. 결과적으로 통계가 부족하면 Trino는 **순서를 바꾸려는 시도 자체를 포기하고, 사용자가 조회문에 적은 순서대로** 실행합니다.

이것은 특정 기능 하나의 성질이 아니라 **제품 전체의 일관된 방침**입니다. 판단할 근거가 없으면 추측하지 않는다는 쪽을 택한 것입니다.

### 2-4. 조건이 여러 개일 때의 가정을 설정으로 열어뒀다

`WHERE A AND B AND C` 처럼 조건이 여러 개면, 각 조건이 서로 얼마나 관련 있는지에 따라 남는 데이터 건수 예측이 크게 달라집니다. Trino는 그 **가정의 강도를 숫자 하나로 빼뒀습니다.**

**[PlanNodeStatsEstimateMath.java#L222-L225](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/cost/PlanNodeStatsEstimateMath.java#L222-L225)**

```java
        // For independenceFactor = 0.75 and terms t1, t2, t3
        // Combined selectivity = (t1 selectivity) * ((t2 selectivity) ^ 0.75) * ((t3 selectivity) ^ (0.75 * 0.75))
        // independenceFactor = 1 implies the terms are assumed to have no correlation and their selectivities are multiplied without scaling.
        // independenceFactor = 0 implies the terms are assumed to be fully correlated and only the most selective term drives the selectivity.
```

▸ **읽는 법** — 개발진이 소스에 직접 남긴 설명입니다. 이 값이 **1이면 "조건들이 서로 완전히 무관하다"**, **0이면 "조건들이 완전히 겹친다(가장 강한 조건 하나만 의미 있다)"** 로 계산합니다. 그 사이 값이면 두 번째·세 번째 조건의 영향을 점점 약하게 반영합니다.

기본값은 용도에 따라 다릅니다. **테이블을 잇는 조건**끼리는 서로 강하게 얽혀 있다고 봅니다.

**[OptimizerConfig.java#L48](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L48)**

```java
    private double joinMultiClauseIndependenceFactor = 0.25;
```

반면 **일반 필터 조건**끼리는 대체로 무관하다고 봅니다.

**[OptimizerConfig.java#L59](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L59)**

```java
    private double filterConjunctionIndependenceFactor = 0.75;
```

▸ **읽는 법** — 같은 계산식에 계수만 다르게 넣은 구조입니다. 설정 이름은 각각 `optimizer.join-multi-clause-independence-factor`, `optimizer.filter-conjunction-independence-factor` 입니다.

**둘 다 조회 단위로도 바꿀 수 있습니다.** 이 값을 돌리면 실제로 실행 방법이 바뀝니다(4-2에서 확인했습니다).

## 3. StarRocks의 방식 — "많이 재고, 모르면 메꾼다"

### 3-1. 가중치가 소스 코드 안에 박혀 있다

**[CostModel.java#L129-L136](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/CostModel.java#L129-L136)**

```java
    public static double getRealCost(CostEstimate costEstimate) {
        double cpuCostWeight = 0.5;
        double memoryCostWeight = 2;
        double networkCostWeight = 1.5;
        return costEstimate.getCpuCost() * cpuCostWeight +
                costEstimate.getMemoryCost() * memoryCostWeight +
                costEstimate.getNetworkCost() * networkCostWeight;
    }
```

▸ **읽는 법** — 세 줄의 가중치가 `double cpuCostWeight = 0.5;` 처럼 **메서드 안의 임시 변수**로 선언돼 있습니다. 설정 파일에도, 조회 단위 설정에도 노출돼 있지 않습니다. **바꾸려면 소스를 고쳐 다시 빌드해야 합니다.**

합이 4이므로 백분율로 환산하면 **처리량 12.5% / 메모리 50% / 통신 37.5%** 입니다. Trino와 정반대로 보이지만, 앞서 말했듯 메모리 항목의 정의가 달라 직접 비교는 성립하지 않습니다(5-(1)).

또 하나 다른 점은 **합치는 시점**입니다. Trino가 마지막에 한 번 합치는 데 비해, StarRocks는 **처리 단계 하나를 계산할 때마다 즉시 하나의 점수로 합칩니다.** 대신 그 덕분에 "지금까지의 점수가 이미 최고 후보보다 나쁘다"는 판단을 중간에 할 수 있어, 가망 없는 후보를 일찍 버립니다.

### 3-2. 통계가 없어도 멈추지 않고 값을 메꾼다

**[StatisticsCalculator.java#L1209-L1226](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/statistics/StatisticsCalculator.java#L1209-L1226)**

```java
        if (hasUnknownColumnStatistics) {
            // To avoid anti-join estimation of 0 rows, the rows of inner join
            // need to take a table with a small number of rows
            if (joinType.isAntiJoin()) {
                innerRowCount = Math.max(0, Math.min(leftRowCount, rightRowCount));
            } else {
                // if the large table is ten million times larger than the small table, we'd better multiply
                // a filter coefficient.
                double scaleFactor = Math.max(leftRowCount, rightRowCount) / Math.min(leftRowCount, rightRowCount);
                if (scaleFactor >= Math.pow(10, 7)) {
                    innerRowCount = Math.max(1, Math.max(leftRowCount, rightRowCount)
                            * pow(PREDICATE_UNKNOWN_FILTER_COEFFICIENT, eqOnPredicates.size()));
                } else {
                    innerRowCount = Math.max(1, Math.max(leftRowCount, rightRowCount));
                }

            }
        }
```

▸ **읽는 법** — `hasUnknownColumnStatistics`(통계를 모르는 컬럼이 있다)일 때의 처리입니다. **어느 경로로 가도 "모른다"를 돌려주지 않습니다.** 큰 쪽 테이블의 건수를 그대로 쓰거나(`Math.max(leftRowCount, rightRowCount)`), 두 테이블 크기 차이가 **1,000만 배**(`Math.pow(10, 7)`)를 넘으면 고정 계수를 곱해 줄입니다. 어떤 값이든 나오므로 **판단은 계속 진행됩니다.**

2-3의 Trino와 정확히 반대입니다. 한쪽은 모르면 멈추고, 한쪽은 메꾸고 갑니다.

### 3-3. 조인 실행 방식의 특성까지 비용에 넣는다

StarRocks에는 테이블을 잇는 작업 전용 비용 계산기가 따로 있습니다. 개발진이 소스에 남긴 설계 근거가 무엇을 재려는지 보여줍니다.

**[HashJoinCostModel.java#L41-L45](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/HashJoinCostModel.java#L41-L45)**

```java
 * 1. In the build hash table stage of broadcast join, the parallelism is 1
 * while it can be parallelized in shuffle join.
 * 2. Broadcast join consumes more memory for redundant data in multiple BEs.
 * 3. The data size in each hash table of shuffle join is 1/parallelism of right table_size
 * while it is full size in broadcast join. A small hash table can improve probe efficiency.
```

*(발췌입니다. 이 주석은 20줄가량이며 설계 근거 1~3번만 옮겼습니다.)*

▸ **읽는 법** — 세 가지를 비용에 반영하겠다는 선언입니다. ① 작은 쪽을 복사해 나눠주는 방식은 조회표 만드는 작업이 **병렬 처리되지 않는다**, ② 서버마다 같은 데이터를 갖게 되어 **메모리를 더 쓴다**, ③ 양쪽을 다시 나누는 방식은 서버당 조회표가 작아 **찾는 속도가 빠르다**.

특히 ③은 실제 계산식으로 구현돼 있습니다.

**[HashJoinCostModel.java#L142-L154](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/HashJoinCostModel.java#L142-L154)**

```java
        double mapSize = Math.min(1, keySize) * rightStatistics.getOutputRowCount();

        double cachePenaltyFactor;
        if (JoinExecMode.BROADCAST == execMode) {
            cachePenaltyFactor = Math.max(1, Math.log(mapSize / BOTTOM_NUMBER));
            // normalize ration when it hits the limit
            cachePenaltyFactor = Math.min(BROADCAST_MAT_RATIO, cachePenaltyFactor);
        } else {
            cachePenaltyFactor = Math.max(1, (Math.log(mapSize / BOTTOM_NUMBER) -
                    Math.log(parallelFactor) / Math.log(2)));
            // normalize ration when it hits the limit
            cachePenaltyFactor = Math.min(SHUFFLE_MAX_RATIO, cachePenaltyFactor);
        }
```

▸ **읽는 법** — `cachePenaltyFactor` 는 "조회표가 CPU 캐시에 안 들어가서 느려지는 정도"입니다. 조회표가 `BOTTOM_NUMBER`(**10만 건**)를 넘으면 벌점이 붙고, 양쪽을 다시 나누는 방식에서는 병렬 처리 수만큼 그 벌점을 깎아줍니다. **Trino의 비용 모델에는 이런 계산이 없습니다** — 데이터 크기만 셉니다.

### 3-4. 서버가 1대면 "양쪽 다시 나누기"의 통신 비용이 0이 된다

**[CostModel.java#L418-L429](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/cost/CostModel.java#L418-L429)**

```java
                case SHUFFLE:
                    // This is used to generate "ScanNode->LocalShuffle->OnePhaseLocalAgg" for the single backend,
                    // which contains two steps:
                    // 1. Ignore the network cost for ExchangeNode when estimating cost model.
                    // 2. Remove ExchangeNode between AggNode and ScanNode when building fragments.
                    boolean ignoreNetworkCost = sessionVariable.isEnableLocalShuffleAgg()
                            && sessionVariable.isEnablePipelineEngine()
                            && GlobalStateMgr.getCurrentState().getNodeMgr().getClusterInfo().isSingleBackendAndComputeNode();
                    double networkCost = ignoreNetworkCost ? 0 : Math.max(outputSize, 1);

                    result = CostEstimate.of(outputSize * factor, 0, networkCost * factor);
                    break;
```

▸ **읽는 법** — `isSingleBackendAndComputeNode()`(데이터 처리 서버가 1대인가)를 포함한 세 조건이 모두 참이면 `networkCost` 가 **0**이 됩니다. 서버가 1대면 실제로 네트워크를 타지 않으니 타당한 계산입니다. **다만 이 조건이 우리 시험 환경에 그대로 걸립니다** — 그래서 앞선 보고서에서 관찰한 StarRocks의 선택 하나는 **제품 성향이 아니라 시험 환경이 만든 결과**였습니다(4-1).

## 4. 실제로 돌려서 확인한 것

**시험 조건**: Trino 처리 서버 1대 / StarRocks 처리 서버 1대, TPC-H 표준 데이터 최소 규모(약 6만 건), 두 제품이 **같은 데이터 파일**을 봅니다. 실행 시간은 재지 않았고 **실행 계획만** 비교했습니다.

### 4-1. 서버 1대라서 나온 결과였음을 확정했다

앞선 2번 보고서에서 "같은 조회인데 Trino는 작은 쪽을 복사하고, StarRocks는 양쪽을 다시 나눴다"고 보고했습니다. 3-4의 코드가 원인 후보였고, 설정 하나로 그 조건을 깨서 확인했습니다.

| 조회 | StarRocks 기본 | 조건을 깬 뒤 |
|---|---|---|
| lineitem ⋈ orders (조회표 15,000건) | 양쪽 다시 나누기 | **작은 쪽 복사로 뒤집힘** |
| lineitem ⋈ supplier (조회표 100건) — 대조군 | 작은 쪽 복사 | 변화 없음 |

**대조군이 움직이지 않았으므로**, 이 설정이 무조건 결과를 바꾸는 게 아니라 **비용이 팽팽한 경우에만** 결론을 뒤집는다는 뜻입니다. 원인이 확정됐습니다.

**따라서 2번 보고서의 그 결과는 "StarRocks가 양쪽 다시 나누기를 선호한다"로 읽으면 안 됩니다.** 서버를 2대 이상 두면 이 경로를 타지 않습니다.

### 4-2. 6개 테이블을 잇는 조회에서 건수 예측이 갈리는 지점을 찾았다

TPC-H 5번 조회(6개 테이블)에서 **두 제품이 똑같은 순서를 골랐습니다.** 순서가 같으니 단계별 예측값을 직접 견줄 수 있었습니다.

| 단계 | Trino 예측 | StarRocks 예측 |
|---|---|---|
| nation ⋈ region | 5건 | 5건 |
| supplier ⋈ (…) | 20건 | 20건 |
| lineitem ⋈ (…) | 12,035건 | 12,035건 |
| orders ⋈ customer | 15,000건 | 15,111건 |
| **마지막 단계 (잇는 조건 2개)** | **5,448건** | **10,896건** |

**중간은 전부 같고, 잇는 조건이 2개인 마지막 단계에서만 정확히 2배 벌어집니다.** 2-4와 3-1에서 본 "조건이 여러 개일 때의 가정" 차이가 그대로 드러난 것입니다.

실제 건수는 **647건**이었습니다. 설정을 돌려가며 재보면 이렇습니다.

| 설정 | 예측 | 실제(647건) 대비 |
|---|---|---|
| Trino, 조건들이 완전히 겹친다고 가정 | 12,182건 | 18.8배 |
| StarRocks 기본값 | 10,896건 | 16.8배 |
| **Trino 기본값** | **5,448건** | **8.4배** |
| Trino, 조건들이 무관하다고 가정 | 609건 | **0.94배** |

**양쪽 기본값 모두 실제보다 한 자릿수~두 자릿수 배 크게 잡습니다.** 이 조회의 두 조건이 실제로는 서로 무관하기 때문입니다.

**다만 "무관하다고 가정하는 쪽이 낫다"고 일반화하면 안 됩니다.** 조건들이 실제로 얽혀 있는 데이터 구조에서는 방향이 반대가 됩니다. 여기서 확인된 것은 *두 제품의 기본값이 조건 간 관련성을 강하게 가정하고 있으며, 그 결과가 이 정도 크기로 나타난다*는 사실입니다.

그리고 **이 설정 하나가 실행 순서까지 바꿨습니다.** 예측이 바뀌면 선택이 바뀐다는 연결 고리가 실측으로 확인된 셈입니다.

> **투명성을 위한 기록**: 이번 검증 과정에서 **1번 보고서의 원인 설명 하나를 정정했습니다.** 8월 31일 시험에서 "StarRocks가 단순한 일렬 순서를 만든다"고 관찰하고 그 원인을 *설정 기준값* 때문이라고 적었는데, 이번에 같은 조건으로 다시 돌리니 **균형 잡힌 순서가 나왔습니다.** 원인을 추적한 결과 기준값이 아니라 **당시 데이터 통계가 완전하지 않았던 것**이었습니다. 실제로 특정 테이블의 통계를 지우자 8월 31일과 똑같은 결과가 재현됐고, 통계를 다시 수집하자 원래대로 돌아왔습니다.
> 관찰 자체는 정확했지만 **원인 귀속이 틀렸습니다.** 8월 31일 실험 기록은 지우지 않고 정정 표시만 붙여 보존했습니다.

### 4-3. Trino의 "통계 없으면 포기" 동작은 이번 환경에서 재현되지 않았다

대칭 실험으로 Trino 쪽에서도 통계를 지워봤습니다. **그런데 Trino는 순서 재배치를 포기하지 않았습니다.**

2-3의 조건은 *비용 전체를 계산할 수 없을 때*인데, 이번에 쓴 데이터 파일 형식(Iceberg)은 전체 건수를 항상 갖고 있어서, 컬럼별 통계만 지워도 건수 예측이 살아남았기 때문입니다. **코드 경로 자체는 유효하지만 이 파일 형식에서는 도달하기 어렵습니다.**

## 5. 실무에서 의미 있는 차이

### (1) 두 제품의 "메모리 비중"을 그대로 비교하면 안 된다

| | Trino | StarRocks |
|---|---|---|
| 메모리 항목의 정의 | 조회 전체에서의 **동시 점유 최고치** | 각 처리 단계 메모리의 **단순 합** |
| 가중치 | 10% | 50% |
| 실무적 의미 | 낮아 보이지만 재는 값이 다르다 | 높아 보이지만 재는 값이 다르다 |

**합계에 큰 비중을 주는 것과 최고치에 작은 비중을 주는 것은 같은 축이 아닙니다.** 확실히 말할 수 있는 것은 방향성뿐입니다 — **Trino는 "얼마나 많은 데이터를 처리하는가"를, StarRocks는 "메모리와 네트워크를 얼마나 쓰는가"를 주된 기준으로 삼습니다.**

### (2) 조회가 이상할 때 손댈 수 있는 지점이 크게 다르다

| | Trino | StarRocks |
|---|---|---|
| 가중치 조정 | **가능** (설정 파일, 재시작 필요) | 불가 (소스 수정 후 재빌드) |
| 조건 관련성 가정 | **가능** (조회 단위로도) | 불가 (두 알고리즘 중 선택만) |
| 서버 대수 가정 | **가능** (`cost_estimation_worker_count`) | 불가 |
| 최후 수단 | — | 조회문에 힌트 표기 |

**이것이 이번 보고의 실질적인 결론입니다.** StarRocks에서 엔진이 나쁜 방법을 골랐을 때, **판단 기준 자체를 조정할 방법이 없습니다.** 조회문에 "이 방식으로 해라"고 직접 적어 덮어쓰는 것이 유일한 수단입니다. 조회문을 고칠 수 없는 상황(BI 도구가 자동 생성하는 조회 등)이면 손쓸 방법이 없습니다.

반대로 Trino는 판단 기준을 열어뒀지만, **조회 하나만 급히 고치는 수단(힌트)이 없습니다.** 앞선 2번 보고서에서 짚은 것과 같은 구도입니다 — 두 제품은 "전체를 조정하는 손잡이"와 "한 건만 고치는 손잡이"를 각각 하나씩만 갖고 있습니다.

### (3) 데이터 통계 관리의 중요도가 다르다

| | Trino | StarRocks |
|---|---|---|
| 통계가 없을 때 | 순서 재배치를 **포기** — 조회문에 쓴 순서 그대로 | 임의 값으로 메꾸고 판단 계속 |
| 나쁜 통계의 위험 | 낮음(아예 판단을 안 함) | **있음**(틀린 값으로 판단) |
| 통계 관리 부담 | **사람이 챙겨야 함** | 엔진이 자동 수집 |

**Trino를 쓴다면 통계 수집을 정기 작업으로 편성해야 합니다.** 통계가 없으면 성능이 나빠지는 게 아니라 **엔진이 최적화를 아예 시도하지 않습니다.**

StarRocks는 자동으로 수집하므로 관리 부담이 작지만, 통계가 낡은 동안에는 **틀린 값으로 자신 있게 판단**하는 위험이 있습니다. 어느 쪽이 나은지는 조직의 운영 여력에 달렸습니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **어느 제품이 실제로 빠른가** | 시험 데이터가 6만 건으로 너무 작아 측정이 무의미하고, 시험 장비 메모리(7.6GB)가 부족합니다 | 메모리 24GB 이상 장비 + 100배 이상 데이터 |
| **서버를 여러 대 둔 환경** | 각 제품 1대씩으로만 구성했습니다. 4-1의 결과는 **1대 환경에서만 성립**합니다 | 서버 3대 이상 구성 |
| **데이터 읽기 비용이 빠진 채로 비교했다** | StarRocks는 이번에 쓴 파일 형식(Iceberg)의 읽기 비용을 **0으로 계산**합니다. Trino는 계산에 넣습니다. 즉 완전히 같은 조건의 비교가 아니었습니다 | StarRocks 자체 저장 방식으로 별도 시험 |
| **다른 형태의 조회에서의 예측 정확도** | 4-2는 6테이블 조회 한 건입니다 | 조회 유형별 반복 측정 |
| **StarRocks 계수들의 근거** | 소스에 근거 주석 없이 숫자만 있습니다(예: 벌점 1,000배, 계수 0.25). 의도인지 경험값인지 판별 불가 | 개발 이력 조회(현재 저장소는 축약 복제라 불가) |

**이번 보고는 "두 제품이 무엇을 기준으로 판단하는가"이며, "어느 쪽이 더 빠른가"가 아닙니다.**

특히 3번째 항목은 중요합니다 — **이번 시험에서 StarRocks 쪽은 데이터 읽기 비용이 0으로 계산된 상태**였습니다. 다행히 4-2에서 두 제품이 같은 순서를 골랐고, 읽기 비용은 순서를 어떻게 바꿔도 거의 일정하므로 영향이 제한적이라고 볼 근거는 있습니다. 그러나 **"완전히 동일한 조건에서 비교했다"고는 말할 수 없습니다.**
