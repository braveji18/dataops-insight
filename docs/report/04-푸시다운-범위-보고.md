## 한 장 요약

`WHERE 날짜 > '2025-01-01'` 같은 조건은 데이터를 **다 읽은 뒤 거르는 것**보다 **읽을 때 아예 거르는 것**이 훨씬 빠릅니다. 조건·정렬·개수 제한·집계를 얼마나 데이터 가까이 내려보내는지가 응답 시간을 좌우합니다. 이번에는 그 범위를 비교했습니다.

| | Trino | StarRocks |
|---|---|---|
| 조건을 저장소에 넘기는 방식 | 저장소에 **물어보고**, 저장소가 책임진 부분은 **조회 계획에서 제거** | 묻지 않고 **항상 붙여서** 내려보냄 |
| 무엇을 내려보낼 수 있는지 판단 주체 | **저장소 쪽 연결 모듈** | **엔진 안에 고정된 목록** |
| 집계를 앞당기는 기준 | 데이터가 **2배**만 줄어도 앞당김 | **100배**는 줄어야 후보로 봄 |
| 문제가 생겼을 때 끄는 스위치 | **있음** (소스에 "진단용"이라고 명시) | 없음 |
| 조건·정렬·개수 제한 내려보내기 | 실측 6항목 **전부 동등** | 실측 6항목 **전부 동등** |

**결론: 범위 자체는 대등합니다. 갈리는 것은 두 가지입니다 — ① 저장소에 물어보느냐 마느냐, ② 집계를 앞당기는 기준값이 50배 차이 납니다.**

---

## 1. 왜 이걸 봤나

이 항목은 **응답 시간에 직접 붙습니다.** 조건을 내려보내면 읽는 데이터 자체가 줄어들고, 집계를 앞당기면 서버 간에 주고받는 데이터가 줄어듭니다. 둘 다 배수 단위로 차이가 납니다.

운영 관점에서는 세 가지가 걸립니다.

- **저장소를 바꿨을 때 성능이 유지되는가** — Trino는 저장소 연결 모듈이 협조해야 성능이 나옵니다
- **조회가 느릴 때 무엇을 보고 원인을 찾는가** — 두 제품이 보여주는 신호가 다릅니다
- **엔진이 최적화를 안 해줄 때 강제할 수단이 있는가**

## 2. Trino의 방식 — "저장소에 물어보고, 책임진 만큼만 뺀다"

### 2-1. 저장소가 "여기까지는 내가 책임진다"고 답한다

Trino는 조건을 저장소에 그냥 넘기지 않습니다. **넘겨보고 답을 받습니다.** 그 답의 형식이 아래입니다.

**[ConstraintApplicationResult.java#L26-L29](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/connector/ConstraintApplicationResult.java#L26-L29)**

```java
    private final T handle;
    private final TupleDomain<ColumnHandle> remainingFilter;
    private final Optional<ConnectorExpression> remainingExpression;
    private final boolean precalculateStatistics;
```

▸ **읽는 법** — 이름에 `remaining`(남은 것)이 두 번 나옵니다. 저장소는 "이만큼은 내가 처리하겠고, **나머지는 네가 해라**"를 돌려줍니다. 엔진은 그 나머지만 조회 계획에 남깁니다. 저장소가 완전히 책임진 조건은 **조회 계획에서 사라집니다** — 두 번 검사하지 않습니다.

### 2-2. 저장소는 조건을 세 갈래로 나눈다

Iceberg 저장소 모듈의 실제 판단입니다.

**[IcebergMetadata.java#L3686-L3705](https://github.com/trinodb/trino/blob/483/plugin/trino-iceberg/src/main/java/io/trino/plugin/iceberg/IcebergMetadata.java#L3686-L3705)**

```java
            domains.forEach((columnHandle, domain) -> {
                if (!isConvertibleToIcebergExpression(domain)) {
                    unsupported.put(columnHandle, domain);
                }
                else if (canEnforceColumnConstraintInSpecs(typeManager.getTypeOperators(), icebergTable, partitionSpecIds, columnHandle, domain)) {
                    newEnforced.put(columnHandle, domain);
                }
                else if (isMetadataColumnId(columnHandle.getId())) {
                    if (columnHandle.isPartitionColumn() || columnHandle.isPathColumn() || columnHandle.isFileModifiedTimeColumn()) {
                        newEnforced.put(columnHandle, domain);
                    }
                    else {
                        unsupported.put(columnHandle, domain);
                    }
                }
                else {
                    newUnenforced.put(columnHandle, domain);
                }
            });
```

▸ **읽는 법** — 변수 이름 세 개가 답입니다. `unsupported`(저장소가 이해 못 하는 조건), `newEnforced`(**저장소가 완전히 책임지는 조건** — 조회 계획에서 빠집니다), `newUnenforced`(파일을 걸러내는 데는 쓰지만 완전히 책임지지는 못하는 조건). 두 번째 갈래에 들어가려면 `canEnforceColumnConstraintInSpecs` — 즉 **데이터가 그 컬럼 기준으로 나뉘어 저장돼 있어야** 합니다.

이 세 갈래가 실제 조회 계획에 그대로 보입니다(4-1).

### 2-3. 집계를 앞당기는 기준 — "2배만 줄어도 앞당긴다"

두 테이블을 잇기 **전에** 미리 집계해두면 잇는 작업의 입력이 줄어듭니다. 다만 집계해도 건수가 별로 안 줄면 헛수고입니다. Trino의 판단 기준입니다.

**[PushPartialAggregationThroughJoin.java#L239-L244](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/PushPartialAggregationThroughJoin.java#L239-L244)**

```java
        for (Symbol symbol : pushedAggregation.getGroupingKeys()) {
            double ndv = sourceStats.getSymbolStatistics(symbol).getDistinctValuesCount();
            if (isNaN(ndv) || ndv * 2 > sourceRowCount) {
                return true;
            }
        }
```

▸ **읽는 법** — `ndv` 는 그 컬럼의 **서로 다른 값의 개수**입니다. `ndv * 2 > sourceRowCount` 는 "값 종류가 전체 건수의 절반을 넘는다", 즉 **집계해도 절반까지밖에 안 줄어든다**는 뜻이고, 그러면 `return true`(포기)입니다.
> **환산**: 읽는 사람의 단위로 바꾸면 — **건수가 2배 이상 줄어들 것 같으면 앞당긴다**입니다. 아주 낮은 문턱입니다. `isNaN(ndv)` 는 "통계가 없으면 앞당기지 않는다"는 뜻입니다.

문턱을 이렇게 낮게 잡을 수 있는 이유가 코드 바로 위 주석에 있습니다 — *"잘못 앞당겨도 실행 중에 자동으로 꺼지므로 손해가 크지 않다"*. Trino가 앞당기는 것은 **가벼운 임시 집계**이고, 서버 간 데이터 재분배를 새로 만들지 않습니다.

### 2-4. 문제가 생기면 저장소 전달을 통째로 끌 수 있다

**[SystemSessionProperties.java#L668-L673](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/SystemSessionProperties.java#L668-L673)**

```java
                booleanProperty(
                        ALLOW_PUSHDOWN_INTO_CONNECTORS,
                        "Allow pushdown into connectors",
                        // This is a diagnostic property
                        true,
                        true),
```

▸ **읽는 법** — 개발진이 `// This is a diagnostic property`(**진단용 설정**)라고 직접 적어뒀습니다. 저장소 연결 모듈이 조건을 잘못 처리해 결과가 틀리거나 느릴 때, 이 설정 하나로 **저장소 전달을 통째로 끄고 엔진이 직접 처리하도록** 되돌릴 수 있습니다. 남의 구현에 의존하는 구조라서 필요한 안전장치입니다.

## 3. StarRocks의 방식 — "묻지 않고 붙이고, 쓸 수 있는 형태는 엔진이 안다"

### 3-1. 조건을 조건 없이 스캔에 붙인다

**[PushDownPredicateScanRule.java#L93-L98](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/transformation/PushDownPredicateScanRule.java#L93-L98)**

```java
        // clone a new scan operator and rewrite predicate.
        Operator.Builder builder = OperatorBuilderFactory.build(logicalScanOperator);
        LogicalScanOperator newScanOperator = (LogicalScanOperator) builder.withOperator(logicalScanOperator)
                .setPredicate(predicates)
                .build();
        newScanOperator.buildColumnFilters(predicates);
```

▸ **읽는 법** — `setPredicate(predicates)` 앞뒤로 **"이 조건을 저장소가 처리할 수 있는가"를 묻는 코드가 없습니다.** 조건을 무조건 스캔 단계에 붙입니다. 이 규칙이 적용되는 저장소 종류는 **17가지**(자체 저장소, Hive, Iceberg, Delta, Paimon, Kudu, Elasticsearch 등)이고, 전부 같은 처리를 받습니다.

결과적으로 별도의 거르기 단계는 사라지지만, **조건은 스캔 단계에 남아 행마다 다시 검사됩니다.** Trino가 "저장소가 책임진 조건은 아예 지운다"고 한 것과 대비됩니다.

### 3-2. 실제로 데이터 건너뛰기에 쓸 수 있는 형태는 엔진에 고정돼 있다

조건이 스캔에 붙었다고 해서 전부 "파일 건너뛰기"에 쓰이는 것은 아닙니다. 쓸 수 있는 형태를 엔진이 직접 정합니다.

**[OptExternalPartitionPruner.java#L517-L521](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rewrite/OptExternalPartitionPruner.java#L517-L521)**

```java
    /**
     * Only conjuncts of the form <column> <op> <constant> and <column> in <constant> are supported,
     * and <op> must be one of LT, LE, GE, GT, or EQ.
     */
    private static boolean isSupportedMinMaxConjuncts(LogicalScanOperator scanOperator, ScalarOperator operator) {
```

▸ **읽는 법** — 개발진 주석이 목록을 그대로 밝힙니다. **`컬럼 (비교기호) 상수`** 형태와 **`컬럼 IN (상수들)`** 형태만 쓰이고, 비교기호도 `<`, `<=`, `>=`, `>`, `=` 다섯 개뿐입니다. 이 목록은 **엔진 코드에 박혀 있고 저장소 종류와 무관합니다.**

즉 새 저장소가 더 많은 것을 처리할 수 있어도, **엔진 코드를 고치지 않으면 쓸 수 없습니다.** Trino가 저장소에게 물어보는 것(2-1)과 정확히 반대 구조입니다.

### 3-3. 외부 SQL 서버만 예외이고, 그 이유가 주석에 적혀 있다

**[PushDownPredicateToExternalTableScanRule.java#L44-L46](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/transformation/PushDownPredicateToExternalTableScanRule.java#L44-L46)**

```java
// Because the external table may not support the functions in StarRocks,
// to be on the safe side, we only push down partial predicates to the external table
public class PushDownPredicateToExternalTableScanRule extends TransformationRule {
```

▸ **읽는 법** — MySQL이나 다른 데이터베이스에 조건을 넘길 때만은 **일부만 넘긴다**고 밝힙니다. 이유는 "상대 데이터베이스가 StarRocks의 함수를 모를 수 있어서"입니다. 타당한 판단이지만, **무엇을 넘길 수 있는지의 목록 역시 엔진 안에 고정**돼 있고 **상대가 어떤 데이터베이스든 같은 목록**을 씁니다.

### 3-4. 집계를 앞당기는 기준 — "100배는 줄어야 한다"

StarRocks는 컬럼을 값 종류 수에 따라 세 등급으로 나눕니다. 등급을 가르는 계수가 이것입니다.

**[StatisticsEstimateCoefficient.java#L40-L42](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/statistics/StatisticsEstimateCoefficient.java#L40-L42)**

```java
    public static final double LOWER_AGGREGATE_EFFECT_COEFFICIENT = 10000;
    public static final double LOW_AGGREGATE_EFFECT_COEFFICIENT = 1000;
    public static final double MEDIUM_AGGREGATE_EFFECT_COEFFICIENT = 100;
```

**[PushDownAggregateCollector.java#L634-L641](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/tree/pdagg/PushDownAggregateCollector.java#L634-L641)**

```java
        if (rowCount == 0 || distinct * StatisticsEstimateCoefficient.MEDIUM_AGGREGATE_EFFECT_COEFFICIENT > rowCount) {
            return 2;
        } else if (distinct * StatisticsEstimateCoefficient.MEDIUM_AGGREGATE_EFFECT_COEFFICIENT <= rowCount &&
                distinct * StatisticsEstimateCoefficient.LOW_AGGREGATE_EFFECT_COEFFICIENT > rowCount) {
            return 1;
        } else if (distinct * StatisticsEstimateCoefficient.LOW_AGGREGATE_EFFECT_COEFFICIENT <= rowCount) {
            return 0;
        }

```

▸ **읽는 법** — `distinct`(값 종류 수)에 계수를 곱해 전체 건수와 견줍니다. 반환값 `2`는 "줄어드는 효과가 낮음", `1`은 "중간", `0`은 "높음"입니다.
> **환산**: 계수를 감소 배수로 바꾸면 — **100배 미만으로 줄면 "효과 낮음"**, 100~1000배면 "중간", **1000배 이상 줄어야 "효과 높음"** 입니다. 기본 설정에서는 "효과 낮음" 등급이 하나라도 있으면 앞당기지 않습니다.

**Trino의 2배와 비교하면 문턱이 50배 높습니다.** 이유가 있습니다 — StarRocks가 앞당기는 것은 임시 집계가 아니라 **서버 간 데이터 재분배를 새로 포함한 완전한 집계**입니다. 잘못 앞당기면 없어도 될 재분배가 하나 늘어나므로 신중할 수밖에 없습니다(4-2에서 실제 조회 계획으로 확인).

## 4. 실제로 돌려서 확인한 것

**시험 조건**: Trino 처리 서버 1대 / StarRocks 처리 서버 1대, TPC-H 표준 데이터 최소 규모(약 6만 건), 두 제품이 **같은 데이터 파일**을 봅니다. 실행 시간은 재지 않았고 **조회 계획만** 비교했습니다.

### 4-1. "저장소에 물어보는가"가 조회 계획에 그대로 보인다

데이터를 특정 컬럼 기준으로 나눠 저장한 시험용 표를 만들고, **나눔 기준 컬럼**과 **그렇지 않은 컬럼**에 같은 형태의 조건을 걸었습니다.

| | 나눔 기준 컬럼에 건 조건 | 일반 컬럼에 건 조건 |
|---|---|---|
| **Trino** | `TableScan[... constraint on [l_linestatus]]` — **거르는 단계가 아예 없음** | `ScanFilterProject[..., filterPredicate = ...]` — 거르는 단계 있음 |
| **StarRocks** | `IcebergScanNode` + `PREDICATES: ...` | `IcebergScanNode` + `PREDICATES: ...` (**같음**) |

**Trino는 저장소가 "책임지겠다"고 답한 조건을 조회 계획에서 지웠습니다.** StarRocks는 두 경우의 계획 모양이 같습니다 — 파일 건너뛰기 자체는 하지만(내부적으로 2개 중 1개만 읽었습니다), 조건은 스캔 단계에 그대로 남아 행마다 다시 검사됩니다.

저장소가 조건을 이해하지 못하는 경우도 확인했습니다. `l_orderkey % 7 = 0` 처럼 계산이 들어간 조건은 Trino 쪽에서 저장소에 전달된 기록이 **비어 있고**, StarRocks 쪽에서는 파일 건너뛰기용 조건 목록(`MIN/MAX PREDICATES`)에 나타나지 않았습니다. **결과는 같고, 판단한 주체가 다릅니다.**

### 4-2. 같은 통계를 갖고도 집계 앞당기기 결론이 갈렸다

두 제품이 **똑같은 통계값**을 갖고 있음을 먼저 확인한 뒤(`s_nationkey` 값 종류 25개 / 전체 100건 — 양쪽 동일), 두 가지 조회를 던졌습니다.

| 조회 | 앞당길 때 줄어드는 배수 | Trino | StarRocks (기본) |
|---|---|---|---|
| supplier ⋈ nation | **4배** | ✅ 앞당김 | ❌ 안 함 |
| lineitem ⋈ supplier | **602배** | ✅ 앞당김 | ✅ 앞당김 |

**2-3의 "2배"와 3-4의 "100배"가 그대로 나타났습니다.** 4배는 Trino의 문턱은 넘지만 StarRocks의 문턱에는 못 미칩니다.

StarRocks에서 설정으로 강제하면 첫 조회도 앞당깁니다 — **기능이 없는 게 아니라 기준값이 막은 것**입니다.

앞당긴 결과물의 모양도 달랐습니다.

| Trino | StarRocks |
|---|---|
| 잇는 작업 아래에 **가벼운 임시 집계 하나** | 잇는 작업 아래에 **집계 + 서버 간 재분배 + 집계 합치기** |

StarRocks 쪽이 무겁습니다. 3-4에서 설명한 문턱 차이의 이유가 여기서 확인됩니다.

### 4-3. 나머지 6가지는 전부 동등했다

| 확인 항목 | Trino | StarRocks |
|---|---|---|
| 한쪽에 건 조건이 잇는 조건을 타고 반대쪽으로 전파되는가 | ✅ | ✅ |
| 한쪽만 남기는 연결을 양쪽 모두 필요한 연결로 단순화하는가 | ✅ | ✅ |
| 집계 아래로 조건을 내려보내는가 | ✅ | ✅ |
| 단순 개수 제한을 읽기 단계까지 내려보내는가 | ✅ | ✅ |
| 정렬 + 개수 제한을 상위 N개 추출로 바꾸는가 | ✅ | ✅ |
| 한쪽만 남기는 연결 + 개수 제한에서 보존되는 쪽에만 제한을 거는가 | ✅ | ✅ |

**마지막 항목에서는 두 제품이 연결 방향을 뒤집는 방식까지 똑같았습니다.** 조회 계획이 사실상 동일한 모양이었습니다.

## 5. 실무에서 의미 있는 차이

### (1) 저장소 연결 모듈의 구현 품질에 대한 의존도

| | Trino | StarRocks |
|---|---|---|
| 저장소가 협조하지 않으면 | 조건 전달이 **통째로 사라짐** | 영향 없음 — 항상 스캔까지 감 |
| 저장소가 잘 구현돼 있으면 | 조건이 계획에서 **없어져 재검사 비용 0** | 항상 재검사 |
| 새 저장소가 더 좋은 기능을 지원하면 | **연결 모듈만 고치면 됨** | **엔진 코드를 고쳐야 함** |

**Trino는 저장소 연결 모듈의 품질이 성능에 직결됩니다.** 새로운 저장소를 붙일 때는 그 모듈이 조건 전달을 구현했는지 확인해야 합니다. 반대로 StarRocks는 저장소 품질과 무관하게 일정 수준이 나오지만, **저장소의 능력을 다 활용하지 못할 수 있습니다.**

### (2) 집계를 앞당기지 않아 느린 경우

| | Trino | StarRocks |
|---|---|---|
| 기준 | 2배만 줄어도 앞당김 | 100배는 줄어야 함 |
| 조정 | 켜기/끄기만 가능 | **5단계로 조절 가능** |

**중간 정도로 줄어드는 조회(예: 지점별 매출 집계처럼 값 종류가 수십~수백 개인 경우)에서 StarRocks는 기본 설정으로 집계를 앞당기지 않습니다.** 그런 조회가 반복된다면 `cbo_push_down_aggregate_mode` 를 2 또는 3으로 올리는 것이 튜닝 수단입니다.

Trino는 반대로 문턱이 낮아 대체로 앞당기지만, 조절 폭이 켜기/끄기뿐입니다.

### (3) 조건 전달이 오작동할 때의 격리 수단

**Trino에는 진단용 스위치가 있고(2-4), StarRocks에는 대응물이 없습니다.**

저장소 연결 모듈의 버그로 결과가 틀리거나 조회가 느려질 때, Trino는 설정 하나로 전달을 끄고 엔진이 직접 처리하게 되돌려 **문제 원인을 좁힐 수 있습니다.** StarRocks에는 이 경로가 없습니다 — 다만 애초에 저장소에 판단을 위임하지 않으므로 이런 종류의 문제가 생길 여지도 작습니다.

**두 제품이 각자의 구조에 맞는 대응을 갖고 있다고 읽는 것이 정확합니다.**

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **어느 쪽이 실제로 빠른가** | 조회 계획만 비교했고 실행 시간은 재지 않았습니다. 시험 데이터가 6만 건으로 너무 작습니다 | 메모리 24GB 이상 장비 + 100배 이상 데이터 |
| **집계 앞당기기 기준값 중 어느 쪽이 옳은가** | 시간을 재지 않아 판정 불가입니다. 확인된 것은 *같은 통계에서 결론이 갈린다*는 사실과 그 원인뿐입니다 | 위와 같음 |
| **외부 데이터베이스(MySQL 등)로의 조건 전달** | 시험 환경에 외부 데이터베이스 연결이 없어 3-3의 경로를 실제로 타지 못했습니다 | JDBC 연결을 갖춘 시험 환경 |
| **서버를 여러 대 둔 환경** | 각 제품 1대씩으로만 구성했습니다. 집계 앞당기기는 서버 간 재분배 비용과 함께 판단되므로 대수에 반응할 수 있습니다 | 서버 3대 이상 구성 |
| **StarRocks 자체 저장소** | 전부 공용 파일 형식(Iceberg) 기준으로만 확인했습니다. 자체 저장소는 색인 경로가 달라 결과가 다를 수 있습니다 | 자체 저장소 시험 별도 설계 |
| **저장소별 조건 전달 능력의 폭** | Trino의 50여 개 저장소 연결 모듈이 각각 어디까지 구현했는지는 이번 범위 밖입니다 | 별도 조사 (`A-5-02` 예정) |

**이번 보고는 "무엇을 어디까지 내려보내는가와 그 판단 주체"이며, "어느 쪽이 더 빠른가"가 아닙니다.**

한 가지 덧붙이면, **"규칙 개수"로 비교하면 안 됩니다.** 소스상 관련 규칙은 Trino 54개, StarRocks 40개인데 이는 **기능 범위 차이가 아니라 코드를 묶는 단위의 차이**입니다. 실제로 4-3에서 6항목이 전부 동등하게 나온 것이 그 방증입니다.
