## 한 장 요약

운영 중에 받는 질문은 크게 두 종류입니다. **"누가 어떤 데이터를 봤는가"**(감사·규제 대응)와 **"이 쿼리는 왜 느렸는가"**(성능 문제 해결)입니다. 두 제품은 이 두 질문에 서로 반대 방향으로 깊게 답합니다.

| | Trino | StarRocks |
|---|---|---|
| 실행 기록을 밖으로 보내기 | **구조화된 이벤트**, 보낼 곳 4종(HTTP·Kafka·MySQL 등) | 평면 목록 형태의 감사 로그 (항목 46개) |
| **어느 원본 컬럼에서 왔는지(계보)** | **엔진이 자동 계산** | 없음 |
| 엔진 내부 최적화 단계 통계 | **SQL로 조회 가능** | 없음 |
| 느린 이유를 연산 단계별로 보기 | 다시 실행하며 보기 (**1단계**) | **끝난 쿼리도 SQL로 조회** (4단계) |
| 파일 읽기 내부까지 보기 | 없음 | **있음** (캐시 적중, 페이지 읽기 시간 등) |
| 기본 수집 여부 | 볼 때마다 다시 실행 | **30초 넘는 쿼리만 자동 수집** |
| 메모리 부족 오류의 안내 | **범인 연산을 지목** | 위치와 해결 방법 안내 |
| 운영 지표 형식 | JMX + Prometheus 호환 | Prometheus |

**결론: "누가 무엇을 했나"는 Trino가, "왜 느렸나"는 StarRocks가 더 깊이 보여줍니다. 다만 StarRocks의 깊은 정보는 꺼내는 절차가 길고, 30초 미만의 짧은 쿼리는 미리 켜 두지 않으면 사후에 볼 수 없습니다.**

> **이번 보고에서 바로잡은 내용**: 기술 문서 초판에는 세 가지 오류가 있었습니다. (1) StarRocks 프로파일이 "기본 꺼짐이라 항상 다시 실행해야 한다"고 적었으나, 실제로는 **30초를 넘긴 쿼리는 자동으로 남습니다.** (2) 감사 로그 항목 수를 90개로 적었으나 **46개**입니다. (3) Trino 지표를 "JMX 전용"으로 적었으나 **Prometheus 호환 형식으로도 내보냅니다.** 모두 원본을 고쳤습니다.

## 1. 왜 이걸 봤나

관측 수단은 **장애가 났을 때 원인을 찾는 데 걸리는 시간**을 결정합니다. 그리고 규제 대응에서는 **"이 개인정보 컬럼이 어느 보고서로 흘러갔는가"** 를 증명해야 하는 경우가 늘고 있습니다.

이 항목은 비교 연구 전체에서 **가장 많이 직접 써 본 영역**이기도 합니다. 지금까지 열여섯 편의 기술 문서를 쓰면서 두 제품의 관측 수단으로 모든 시험 결과를 확인했고, **어디서 막혔고 어디서 잘 보였는지**가 기록에 남아 있습니다. 4절이 그 경험입니다.

> 용어 한 줄 설명
> - **계보(lineage)**: 결과의 각 컬럼이 어느 원본 테이블의 어느 컬럼에서 왔는지 추적한 정보입니다
> - **프로파일**: 쿼리 하나를 실행하는 동안 각 처리 단계가 얼마나 걸리고 몇 건을 처리했는지 기록한 상세 계측표입니다
> - **Prometheus**: 서버 운영 지표를 모아 그래프와 경보를 만드는 데 널리 쓰이는 수집 도구입니다

## 2. Trino의 방식 — "쿼리 밖에서, 무엇이 일어났는지를 구조적으로 남긴다"

### 2-1. 쿼리가 끝나면 구조화된 사건 기록을 내보낸다

**[QueryCompletedEvent.java#L31-L43](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/eventlistener/QueryCompletedEvent.java#L31-L43)**

```java

{
    private final QueryMetadata metadata;
    private final QueryStatistics statistics;
    private final QueryContext context;
    private final QueryIOMetadata ioMetadata;
    private final Optional<List<ColumnLineageInfo>> selectColumnsLineageInfo;
    private final Optional<QueryFailureInfo> failureInfo;
    private final List<TrinoWarning> warnings;

    private final Instant createTime;
    private final Instant executionStartTime;
    private final Instant endTime;
```

▸ **읽는 법**: 쿼리 하나가 끝날 때 만들어지는 기록의 목차입니다. `metadata`(무슨 쿼리였나), `statistics`(얼마나 걸렸나), `context`(누가 어디서), `ioMetadata`(**어떤 테이블을 읽고 썼나**), `failureInfo`(왜 실패했나)가 각각 **별도 묶음**으로 정리돼 있습니다. 그중 다섯 번째 `selectColumnsLineageInfo` 가 가장 특별합니다(2-2).

이 기록을 받아 밖으로 보내는 부분도 교체 가능한 부품(플러그인)이며, 기본 제공되는 것이 HTTP, Kafka, MySQL, 내장 서버용으로 **4종**입니다.

### 2-2. 결과 컬럼이 어디서 왔는지를 엔진이 계산해 준다

**[ColumnLineageInfo.java#L24-L29](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/eventlistener/ColumnLineageInfo.java#L24-L29)**

```java
/**
 * This record is JSON serializable for storing column lineage information for select queries.
 */
public record ColumnLineageInfo(
        @JsonProperty String name,
        @JsonProperty Set<ColumnDetail> sourceColumns)
```

▸ **읽는 법**: `name` 은 결과 컬럼 이름, `sourceColumns` 는 **그 컬럼을 만드는 데 쓰인 원본 컬럼들**입니다. 예를 들어 결과의 `고객등급` 컬럼이 `customers.가입일` 과 `orders.금액` 에서 계산됐다면 그 두 원본이 여기에 담깁니다. **별도의 데이터 계보 도구 없이 엔진이 직접 계산해 주는 정보**로, "주민번호 컬럼이 어떤 보고서로 흘러갔나" 같은 규제 대응 질문에 바로 쓸 수 있습니다.

### 2-3. 엔진 내부 최적화 규칙의 사용 통계를 SQL로 본다

**[RuleStatsSystemTable.java#L62-L69](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/connector/system/RuleStatsSystemTable.java#L62-L69)**

▸ **읽는 법**: `system.runtime.optimizer_rule_stats` 라는 조회용 테이블(같은 파일 52행)의 컬럼 정의입니다. 실행 계획을 다듬는 규칙마다 **몇 번 불렸고(`invocations`), 몇 번 실제로 적용됐고(`matches`), 평균 얼마나 걸렸는지(`average_time`)** 를 보여줍니다. "계획 세우는 데만 몇 초씩 걸린다"는 문제를 추적할 때 쓰는 창구이며, StarRocks에는 대응하는 것이 없습니다.

### 2-4. 메모리 부족 오류가 범인을 지목한다

**[QueryContext.java#L353-L360](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/memory/QueryContext.java#L353-L360)**

```java

                .sorted(comparingByValue(Comparator.reverseOrder()))
                .limit(3)
                .filter(e -> e.getValue() >= 0)
                .collect(toImmutableMap(Entry::getKey, e -> succinctBytes(e.getValue())))
```

▸ **읽는 법**: 메모리 사용량을 큰 순서로 정렬해(`reverseOrder`) **상위 3개(`limit(3)`)** 를 골라 오류 메시지 끝에 `Top Consumers:` 로 붙입니다. 실제 시험에서 `Top Consumers: {PagePartitioner=856B}` 처럼 나왔습니다. **어느 처리 단계가 메모리를 먹었는지 오류 메시지가 직접 말해 줍니다.**

### 2-5. 운영 지표와 분산 추적이 기본으로 켜진다

**[Server.java#L98-L103](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/server/Server.java#L98-L103)**

▸ **읽는 법**: 서버가 뜰 때 함께 올라가는 부품 목록입니다. `JmxModule`(자바 표준 운영 지표)과 함께 `JmxOpenMetricsModule` 이 있어 **같은 지표를 Prometheus가 읽을 수 있는 형식으로도 내보냅니다.** 마지막 `TracingModule` 은 OpenTelemetry 분산 추적으로, 쿼리를 처리하는 동안 메타데이터 조회와 권한 검사 같은 단계가 **추적 기록**으로 남습니다.

### 2-6. 느린 이유는 "다시 실행하며" 본다

처리 단계별 상세는 `EXPLAIN ANALYZE` 로 봅니다. 쿼리 앞에 이 말을 붙이면 **다시 실행하면서** 단계마다 읽은 건수, 걸러낸 비율, 읽은 용량과 시간을 보여줍니다. 실제 시험에서 나온 출력입니다.

```
└─ ScanFilterProject[table = iceberg:bench.o_part$data@..., filterPredicate = (o_orderkey < bigint '1000')]
       Input: 14269 rows (169.36kB), Filtered: 98.21%, Physical input: 225.41kB,
       Physical input time: 309.58ms, Splits: 75, Splits generation wait time: 8.08ms
```

*(시험 출력의 일부입니다. 소스코드가 아니므로 링크가 없습니다.)*

**필요한 정보가 한 줄에 다 있고 한 번에 끝납니다.** 한계는 **다시 실행해야 한다**는 점입니다. 이미 끝난 쿼리의 단계별 상세는 웹 화면의 JSON으로만 볼 수 있고, SQL로는 꺼낼 수 없습니다.

## 3. StarRocks의 방식 — "쿼리 안을, 파일 읽기 내부까지 깊게 잰다"

### 3-1. 감사 로그는 평면적인 항목 목록이다

**[AuditEvent.java#L100-L111](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/plugin/AuditEvent.java#L100-L111)**

```java
    @AuditField(value = "Time")
    public long queryTime = -1;
    @AuditField(value = "ScanBytes")
    public long scanBytes = -1;
    @AuditField(value = "ScanRows")
    public long scanRows = -1;
    @AuditField(value = "ReturnRows")
    public long returnRows = -1;
    @AuditField(value = "CpuCostNs", ignore_zero = true)
    public long cpuCostNs = -1;
    @AuditField(value = "MemCostBytes", ignore_zero = true)
    public long memCostBytes = -1;
```

▸ **읽는 법**: `@AuditField` 가 붙은 줄 하나가 감사 로그의 한 항목입니다. 걸린 시간, 읽은 용량·건수, 돌려준 건수, CPU·메모리 사용량이 **숫자 하나씩 나란히** 놓여 있습니다. 이런 항목이 파일 전체에 **46개** 있습니다. Trino(2-1)처럼 "어떤 테이블의 어떤 컬럼"이라는 **구조적 정보나 계보는 없습니다.** 민감한 문장을 가리는 장치(`AuditEncryptionChecker`)는 따로 있습니다.

### 3-2. 끝난 쿼리의 상세 계측표를 SQL로 꺼낸다

이 축에서 StarRocks의 결정적 강점입니다.

**[StarRocks.g4#L1721-L1723](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocks.g4#L1721-L1723)**

```
showProfilelistStatement
    : SHOW PROFILELIST (LIMIT limit =INTEGER_VALUE)?
    ;
```

**[StarRocks.g4#L1465-L1468](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocks.g4#L1465-L1468)**

```
analyzeProfileStatement
    : ANALYZE PROFILE FROM string
    | ANALYZE PROFILE FROM string ',' INTEGER_VALUE (',' INTEGER_VALUE)*
    ;
```

▸ **읽는 법**: SQL 문법 정의입니다. `SHOW PROFILELIST` 로 **최근 쿼리 목록**을 보고, `ANALYZE PROFILE FROM '<쿼리ID>'` 로 **그 쿼리의 계측표**를, 뒤에 번호를 붙이면 **특정 처리 단계의 상세**를 봅니다. 핵심은 **다시 실행하지 않는다**는 점입니다. 이미 끝난 쿼리의 기록을 꺼냅니다.

**[hive_connector.cpp#L524-L529](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/connector/hive_connector.cpp#L524-L529)**

```cpp
    _profile.raw_rows_read_counter = ADD_COUNTER(_runtime_profile, "RawRowsRead", TUnit::UNIT);
```

**[hdfs_scanner_parquet.cpp#L137-L147](https://github.com/StarRocks/starrocks/blob/4.0.14/be/src/exec/hdfs_scanner_parquet.cpp#L137-L147)**

```java
    public static String otlp_exporter_grpc_endpoint = "";
```

▸ **읽는 법**: 개발진 주석 그대로 "**빈 값이면 추적 기록을 내보내지 않으며, 기본값이 빈 값**"입니다. 켜더라도 관리 노드에서 추적을 쓰는 곳은 스키마 변경 작업, 트랜잭션 관리, 버전 반영 작업뿐입니다(`TraceManager` 를 쓰는 파일 4개). **Trino(2-5)가 쿼리 처리 경로를 추적하는 것과 대상이 다릅니다.** 운영 지표는 별도로 Prometheus 형식으로 내보냅니다(`metric/PrometheusMetricVisitor.java`).

## 4. 실제로 돌려서 확인한 것

이 항목은 별도 시험을 하지 않았습니다. 대신 **앞선 열여섯 편의 시험 전부가 이 두 제품의 관측 수단으로 이뤄졌으므로**, 그 경험 중 관측 수단 때문에 결과가 갈린 사례를 모았습니다(시험 환경: Trino 483 / StarRocks 4.0.14, 각 1노드, TPC-H 소규모 데이터).

### StarRocks가 없었으면 판단할 수 없었던 사례

| 사례 | 무엇을 확인하려 했나 | 경과 |
|---|---|---|
| 파일 건너뛰기 최적화 (`A-5-02`) | 조건으로 파일을 얼마나 건너뛰는가 | StarRocks의 `EXPLAIN` 에는 **예측치(250건)만** 나와 비교가 안 됐습니다. 프로파일에서 `RawRowsRead: 14269`, `ScanRanges: 80` 을 꺼내고서야 Trino(`Input: 14269 rows`, `Splits: 75`)와 비교할 수 있었습니다 |
| 캐시 적중 (`B-3-01`) | 두 번째 실행이 캐시를 탔는가 | StarRocks는 `FooterCacheReadCount: 1` 로 확인했습니다. **Trino는 대응 수치를 SQL로 꺼낼 수 없어 같은 확인을 못 했습니다** |

### Trino가 더 나았던 사례

| 사례 | 경과 |
|---|---|
| 메모리 부족 오류 (`B-1-01`) | Trino는 오류에 `Top Consumers: {PagePartitioner=856B}` 를 붙여 **범인 연산을 바로 알려줬습니다.** StarRocks는 위치(노드·단계)만 알려줬습니다 |
| 조건이 저장소까지 전달됐는지 (`A-5-02`) | Trino는 `EXPLAIN` 한 번으로 판단됐습니다. StarRocks는 계획에 조건이 찍혀 있어도 **실제로 파일을 건너뛰었다는 뜻이 아니어서** 반드시 프로파일을 봐야 했습니다 |

### 확인 절차의 길이

| | 판단에 필요한 절차 |
|---|---|
| Trino | `EXPLAIN ANALYZE <쿼리>` **1단계** |
| StarRocks | 스위치 켜기 → 쿼리 실행 → 목록 조회 → 상세 조회 **4단계** |

> **투명성을 위한 기록**: StarRocks 프로파일을 처음 읽을 때, 거른 **뒤** 건수(`OutputRows`)를 Trino의 거르기 **전** 건수(`Input rows`)와 짝지어 "15,000건 대 255건"이라는 **틀린 비교표를 만들 뻔했습니다.** 올바른 짝은 `RawRowsRead` 였습니다. 계측 항목이 많다는 것은 **잘못 고를 여지도 많다**는 뜻입니다.
>
> 또 기술 문서 초판은 "StarRocks 프로파일은 기본 꺼짐이라 문제가 난 뒤 항상 다시 실행해야 한다"고 적었습니다. 이번 보고서를 쓰며 코드를 다시 확인해 **30초 넘는 쿼리는 자동으로 남는다**는 사실(3-4)을 찾아 원본을 고쳤습니다. 이 30초 동작은 **코드로만 확인했고 실제로 돌려 보지는 않았습니다.**

## 5. 실무에서 의미 있는 차이

### (1) 규제 대응·감사에는 Trino의 계보 정보가 큰 차이를 만든다

| | Trino | StarRocks |
|---|---|---|
| 행동 | 쿼리마다 **결과 컬럼 ← 원본 컬럼** 관계를 이벤트로 내보냄 | 쿼리 단위 숫자 기록(시간·건수·용량)만 남김 |
| 실무적 의미 | 별도 계보 도구 없이 **개인정보 흐름 추적** 가능 | 계보가 필요하면 **별도 도구 도입** 필요 |

### (2) 성능 문제 해결에는 StarRocks가 깊지만, 미리 준비해야 한다

| | Trino | StarRocks |
|---|---|---|
| 행동 | 다시 실행하며 1단계로 확인. 항목이 적어 읽기 쉬움 | 끝난 쿼리도 조회 가능, 파일 읽기 내부까지 보임. 대신 4단계, 30초 미만은 자동 수집 안 됨 |
| 실무적 의미 | 재현 가능한 문제는 빨리 봄. 깊은 원인은 못 봄 | **"평소 0.2초인데 가끔 3초"** 같은 문제는 미리 켜 두지 않으면 영영 못 봄 |

StarRocks는 짧은 분석 쿼리를 빠르게 처리하는 것이 주 용도이므로, **문제가 되는 쿼리 대부분이 30초 기준 아래에 있습니다.** 운영 전에 **프로파일 수집 정책**(`enable_profile`, `big_query_profile_threshold`)을 정해 둘 것을 권합니다. 이때 수집 비용(4절에서 재지 못함)을 함께 고려해야 합니다.

### (3) 두 제품을 함께 쓴다면 역할을 나눌 수 있다

**감사와 계보는 Trino 쪽에서, 성능 분석은 StarRocks 쪽에서** 얻는 구성이 자연스럽습니다. 운영 지표는 양쪽 모두 Prometheus로 모을 수 있어 **한 화면으로 통합하는 데 걸림돌이 없습니다**(실제로 붙여 보지는 않았습니다).

## 6. 아직 확인하지 못한 것 (한계의 명시)

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| Trino 계보 정보의 정확도 | 시험 환경에 이벤트 수신 플러그인이 없음 | HTTP 수신 플러그인 설정 후 복잡한 쿼리로 시험 |
| StarRocks 감사 로그 내용 | 46개 항목을 실제로 열어 보지 않음 | 감사 로그 파일 확인 |
| **30초 자동 수집** | 코드로만 확인 | 30초 넘는 쿼리를 실행하고 `SHOW PROFILELIST` 확인 |
| 프로파일 수집이 속도에 주는 영향 | 측정하지 않음. StarRocks가 기본을 꺼 둔 이유일 것으로 보이나 근거 없음 | 수집 켬/끔 반복 측정 |
| 분산 추적 | 양쪽 모두 추적 수집기를 붙여 보지 않음 | OpenTelemetry 수집기 |
| 운영 지표 통합 | 실제 모니터링 시스템에 붙여 보지 않음 | Prometheus·Grafana 연결 |
| 여러 노드에서의 프로파일 | 노드 1대라 노드별 편차 표시가 의미 없음 | 다중 노드 환경 |
| 최적화 규칙 통계의 실용성 | 조회만 해 보고 분석에 활용하지 않음 | 옵티마이저 비교 축에서 재활용 |

**이번 보고는 "두 제품이 무엇을 어떤 방식으로 보여주는가"와 "실제 시험에서 어디서 막혔는가"까지이며, "어느 쪽이 장애 대응 시간을 얼마나 줄이는가"가 아닙니다.**
