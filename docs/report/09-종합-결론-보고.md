# [보고] Trino vs StarRocks 종합 결론 — 어느 쪽을 언제 쓸 것인가

> 작성일: 2026-09-07 | 대상 버전: Trino 483, StarRocks 4.0.14
> 상세 기술 문서: `docs/99-종합-결론.md` (본문 31편 · 실험 기록 18편의 종합)
>
> 이 보고서의 모든 코드는 위 두 버전의 **실제 소스에서 그대로 발췌**한 것이며,
> 각 제목의 링크로 GitHub에서 원문을 바로 확인하실 수 있습니다.

---

## 한 장 요약

두 제품을 소스코드 수준에서 **31개 항목**으로 나눠 비교하고, 그중 상당수를 **실제 시험 환경에서 돌려** 확인했습니다.

| | Trino 483 | StarRocks 4.0.14 |
|---|---|---|
| 성격 | 데이터를 **보관하지 않는** 조회 엔진 | 데이터를 **보관하는** 데이터베이스 |
| 붙일 수 있는 데이터 소스 | **27종**(+관계형 DB 15종) — 추가 개발 가능 | 10종 — 제품을 고쳐야 추가 가능 |
| 반복 조회 가속(미리 계산해둔 표 자동 활용) | **없음** | 있음 |
| 데이터 수정(UPDATE/DELETE/MERGE) | 공용 파일 형식에 **가능** | 자체 저장소만 가능 |
| 통계 관리 | 사람이 실행 | **자동** |
| 장시간 작업의 장애 복구 | **진행분을 살림** | 전체 재실행 |

**결론: 우열이 아닙니다. 두 제품의 거의 모든 차이는 "데이터를 자기가 보관하는가"라는 단 하나의 설계 결정에서 갈라져 나옵니다. 따라서 선택은 기능 목록 대조가 아니라, 그 결정이 우리 상황에 맞는지를 묻는 일입니다.**

명확한 우위가 확인된 항목은 **StarRocks 12개 · Trino 10개**로 비슷했고, **"차이 없음"으로 끝난 항목이 10개**였습니다.

---

## 1. 왜 이걸 봤나

두 제품은 겉보기에 같은 일을 합니다 — SQL을 받아 대용량 데이터를 조회합니다. 그래서 도입 검토 자리에서 **기능 목록 대조표**를 만들게 되는데, 이 방식은 두 가지를 놓칩니다.

- **되는 것끼리도 되는 범위가 어긋납니다.** 이번 연구에서 가장 자주 나온 형태가 이것입니다(4-2)
- **"왜 그런지"를 모르면 예측할 수 없습니다.** 지금 없는 기능이 다음 버전에 생길지, 구조상 못 만드는지가 갈립니다

그래서 기능 목록이 아니라 **소스코드에서 설계 결정을 찾는 방식**으로 접근했습니다. 그 결과 **하나의 결정이 거의 모든 차이를 설명한다**는 것을 확인했습니다.

## 2. Trino의 선택 — "보관하지 않는다. 대신 경계를 연다"

### 2-1. 확장점이 열려 있고, 아무것도 강요하지 않는다

Trino에 새 데이터 소스를 붙이는 방법은 **플러그인 파일 하나를 넣는 것**입니다. 그 입구가 이 코드입니다.

**[Plugin.java#L45-L48](https://github.com/trinodb/trino/blob/483/core/trino-spi/src/main/java/io/trino/spi/Plugin.java#L45-L48)**

```java
    default Iterable<ConnectorFactory> getConnectorFactories()
    {
        return emptyList();
    }
```

▸ **읽는 법** — `default` 로 선언된 기본 구현이 **빈 목록을 돌려줍니다.** 즉 "무엇을 제공할지는 전적으로 플러그인이 정한다"는 뜻입니다. 제품 쪽 코드에는 어떤 데이터 소스가 붙을지에 대한 목록이 **없습니다.** 3-1의 StarRocks 코드와 대비해서 보면 차이가 분명합니다.

그 결과 붙어 있는 데이터 소스가 **27종**이고, 여기에 관계형 데이터베이스 15종이 공통 기반 위에 얹혀 있습니다. 제3자가 직접 만들어 붙일 수도 있습니다.

### 2-2. 보관하지 않으니, 정리 작업까지 표준 문법으로 갖췄다

데이터를 남의 저장소에 두면 **그 저장소를 관리할 책임도 함께 져야 합니다.** 공용 파일 형식(Iceberg)은 쓰기를 반복하면 잔파일과 이력이 쌓여 반드시 정리해야 하는데, Trino는 그 작업을 전부 SQL 명령으로 제공합니다.

**[IcebergTableProcedureId.java#L16-L26](https://github.com/trinodb/trino/blob/483/plugin/trino-iceberg/src/main/java/io/trino/plugin/iceberg/procedure/IcebergTableProcedureId.java#L16-L26)**

```java
public enum IcebergTableProcedureId
{
    OPTIMIZE,
    OPTIMIZE_MANIFESTS,
    DROP_EXTENDED_STATS,
    ROLLBACK_TO_SNAPSHOT,
    EXPIRE_SNAPSHOTS,
    REMOVE_ORPHAN_FILES,
    ADD_FILES,
    ADD_FILES_FROM_TABLE,
}
```

▸ **읽는 법** — 이름만 읽어도 무엇을 하는지 보입니다. `OPTIMIZE`(잔파일 병합), `EXPIRE_SNAPSHOTS`(오래된 이력 정리), `REMOVE_ORPHAN_FILES`(버려진 파일 제거), `ROLLBACK_TO_SNAPSHOT`(과거 시점 되돌리기). **운영에 필요한 작업이 빠짐없이 SQL 명령으로 나와 있습니다.**

**이것이 4-1에서 "Trino가 명확히 앞서는 곳"의 핵심 근거입니다** — StarRocks에는 이 명령들이 없습니다.

### 2-3. 보관하지 않으니, 자원 사용을 "밖에서 관찰"할 수밖에 없다

조회 한 건이 자원을 너무 많이 쓸 때 막는 방식이 두 제품에서 다릅니다. Trino는 **실행 중인 조회를 주기적으로 들여다보고 한도를 넘었으면 실패시킵니다.**

**[QueryManager.java#L420-L424](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/execution/QueryManager.java#L420-L424)**

```java
            limitOpt.ifPresent(limit -> {
                DataSize scan = query.getBasicQueryInfo().getQueryStats().getPhysicalInputDataSize();
                if (scan.compareTo(limit) > 0) {
                    query.fail(new ExceededScanLimitException(limit));
                }
```

▸ **읽는 법** — `physicalInputDataSize`(**이미 읽은 양**)를 한도와 비교해서 넘었으면 `query.fail`(실패 처리)합니다. **읽는 것을 막는 게 아니라 읽은 뒤에 실패시킵니다.** 데이터를 직접 들고 있지 않으니 읽는 순간에 개입할 자리가 없습니다.

그리고 이 검사는 주기적으로 돕니다.

**[QueryManager.java#L140](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/execution/QueryManager.java#L140)**

```java
        }, 1, 1, TimeUnit.SECONDS);
```

▸ **읽는 법** — **1초 간격**입니다. 시험에서 확인한 결과, **1초 안에 끝나는 조회는 한도를 넘겨도 그대로 통과했습니다.** StarRocks는 데이터를 읽는 도중에 중단시킵니다(3절 설명 참조).

## 3. StarRocks의 선택 — "보관한다. 대신 목록을 닫았다"

### 3-1. 붙일 수 있는 데이터 소스가 제품 코드에 목록으로 박혀 있다

**[ConnectorType.java#L36-L45](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/connector/ConnectorType.java#L36-L45)**

```java
    ES("es", ElasticsearchConnector.class, EsConfig.class),
    HIVE("hive", HiveConnector.class, null),
    ICEBERG("iceberg", IcebergConnector.class, null),
    JDBC("jdbc", JDBCConnector.class, null),
    HUDI("hudi", HudiConnector.class, null),
    DELTALAKE("deltalake", DeltaLakeConnector.class, null),
    PAIMON("paimon", PaimonConnector.class, null),
    ODPS("odps", OdpsConnector.class, null),
    KUDU("kudu", KuduConnector.class, null),
    UNIFIED("unified", UnifiedConnector.class, null);
```

▸ **읽는 법** — **10줄이 전부입니다.** 붙일 수 있는 데이터 소스가 제품 소스코드 안에 목록으로 고정돼 있습니다. 새로 추가하려면 **이 목록을 고치고 제품을 다시 빌드해야 합니다.** 2-1의 Trino 코드에는 이런 목록 자체가 없었습니다.

게다가 StarRocks는 조회를 계획하는 부분(Java)과 실제로 데이터를 읽는 부분(C++)이 별개 프로그램이라, 데이터 소스 하나를 추가하려면 **두 언어와 그 사이 통신 규약까지 세 곳**을 고쳐야 합니다.

### 3-2. 보관하니, 테이블 종류를 고를 수 있다

**[KeysType.java#L39-L43](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/catalog/KeysType.java#L39-L43)**

```java
public enum KeysType {
    PRIMARY_KEYS,
    DUP_KEYS,
    UNIQUE_KEYS,
    AGG_KEYS;
```

▸ **읽는 법** — 같은 데이터를 넣어도 **테이블을 어떤 종류로 만들었느냐에 따라 결과가 달라집니다.** `DUP_KEYS`는 넣은 대로 다 쌓고, `AGG_KEYS`는 넣는 즉시 합계를 갱신하고, `PRIMARY_KEYS`는 같은 키가 오면 덮어씁니다.

**이 중 `PRIMARY_KEYS`가 실무에서 결정적입니다** — 데이터 수정(UPDATE)과 일부 컬럼만 갱신하는 기능이 이 종류에서만 됩니다. 공용 파일 형식에는 대응하는 개념이 없습니다.

**데이터를 자기가 보관하기 때문에 가능한 기능입니다.**

### 3-3. 보관하니, 통계도 자기 안에 쌓는다

**[StatsConstants.java#L66-L72](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/statistic/StatsConstants.java#L66-L72)**

```java
    public static final String STATISTICS_DB_NAME = "_statistics_";
    public static final String SAMPLE_STATISTICS_TABLE_NAME = "table_statistic_v1";
    public static final String FULL_STATISTICS_TABLE_NAME = "column_statistics";
    public static final String EXTERNAL_FULL_STATISTICS_TABLE_NAME = "external_column_statistics";
    public static final String HISTOGRAM_STATISTICS_TABLE_NAME = "histogram_statistics";
    public static final String EXTERNAL_HISTOGRAM_STATISTICS_TABLE_NAME = "external_histogram_statistics";
    public static final String MULTI_COLUMN_STATISTICS_TABLE_NAME = "multi_column_statistics";
```

▸ **읽는 법** — `_statistics_` 라는 **내부 데이터베이스**에 통계를 테이블로 쌓습니다. 이름을 보면 담는 종류가 드러납니다 — 표본 통계, 컬럼 통계, 값 분포표, 여러 컬럼 조합 통계.

Trino는 통계를 **데이터 파일 자체에** 남깁니다. 그래서 담을 수 있는 종류가 파일 형식이 허용하는 범위로 제한되고(문자 컬럼의 최소·최대값을 담지 못합니다), 대신 **다른 제품과 공유됩니다.**

**표현력과 이식성이 맞바꿔져 있습니다.** 그리고 **두 제품의 통계는 서로 공유되지 않아, 함께 쓰면 양쪽에서 각각 수집해야 합니다**(5-2).

### 3-4. 남의 저장소에 쓰는 것은 아예 막았다

**[MetaUtils.java#L91-L93](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/common/MetaUtils.java#L91-L93)**

```java
        if (!operation.equals("ALTER") && catalog.getType().equalsIgnoreCase("iceberg")) {
            throw new SemanticException("Table of iceberg catalog doesn't support [%s]", operation);
        }
```

▸ **읽는 법** — 데이터 소스 종류가 문자열 `"iceberg"` 이면 곧바로 거부합니다. **"이 저장소가 그 작업을 할 수 있는가"를 물어보지 않고, 이름만 보고 막습니다.**

**결과적으로 StarRocks로는 공용 파일 형식에 데이터를 넣을 수는 있어도 고치거나 지울 수 없습니다.** 자체 저장소가 있으니 남의 저장소를 고쳐 쓸 유인이 약했던 것으로 읽힙니다.

## 4. 실제로 돌려서 확인한 것

**시험 조건**: 두 제품을 같은 데이터 파일(Iceberg)에 붙이고, 표준 벤치마크 데이터(약 6만 건)로 조회 계획과 결과를 비교했습니다. **실행 시간은 한 번도 재지 않았습니다**(6절 첫 항목).

### 4-1. 명확한 우위가 확인된 항목

**StarRocks가 앞서는 곳 (12개)**

| 항목 | 크기 |
|---|---|
| 미리 계산해둔 표 자동 활용 | 전용 코드 약 18,000줄 대 **0줄**. Trino는 조회문에 이름을 직접 써야 함 |
| 통계 자동 수집 | 배경 작업이 **조회를 관찰해 필요한 컬럼을 스스로 고름**(실측 확인) |
| 테이블 종류 선택 | 4종. **데이터 수정은 `PRIMARY KEY` 종류에서만** 가능 |
| 검색용 색인 | 부분 문자열 검색(`LIKE '%…%'`)이 공용 파일 형식 통계로는 **전혀 걸러지지 않음** |
| 자동 파일 정리 | 제품이 알아서 수행. Trino는 사람이 명령을 불러야 함 |
| 실시간 적재 | Kafka 상시 구독을 제품이 직접 수행 |
| 자원 격리 강제력 | 데이터 읽는 도중에 중단시킴(실측). Trino는 1초 주기라 **짧은 조회가 빠져나감**(실측) |
| 캐시 기본 동작 | 설정 없이 작동(실측). Trino는 저장 위치를 지정해야 켜짐 |
| 중간 결과 재사용 | 기능 자체가 Trino에 없음 |
| 메모리 부족 시 디스크 활용 범위 | 12계열 대 4계열. **다만 양쪽 다 기본 꺼짐** |
| 관리 정보 이중화 | 자동 승격까지 갖춤. Trino는 이 계층이 없음 |
| 조회 내부 성능 분석 | 파일 읽기 내부까지 계측되고 **끝난 조회를 SQL로 사후 조회 가능** |

**Trino가 앞서는 곳 (10개)**

| 항목 | 크기 |
|---|---|
| 데이터 소스 확장성 | 플러그인 파일로 배포. StarRocks는 제품 재빌드 필요 |
| 데이터 소스 다양성 | 27종(+관계형 DB 15종). 관계형 DB 지원이 **15:1** |
| 공용 파일 형식 쓰기 | **StarRocks는 넣기만 되고 고치거나 지울 수 없음** |
| 장시간 작업 내결함성 | 작업 단위 재시도로 **진행분을 살림**. StarRocks는 전체 재실행 |
| 함수 추가 비용 | 표시 하나 + 플러그인. StarRocks는 두 언어 구현 + 재빌드 |
| 접근제어 세밀함 | 검사 지점 **84개 대 31개**(2.7배) |
| 데이터 흐름 추적 | 컬럼 단위 계보를 제품이 직접 계산. StarRocks에 없음 |
| 결함의 파급 범위 | 파일 읽기 결함이 Trino는 조회 실패, StarRocks는 **데이터 보관 프로세스 자체가 죽음** |
| 시간대·UUID 타입 | StarRocks는 전자를 구분 못 하고 후자는 **조회에서 실패** |
| (반대) 소수점 정밀도 | **StarRocks가 두 배**(76 대 38). 단 공용 파일 형식 상한이 38이라 실익 없음 |

### 4-2. "차이 없음"으로 끝난 것 — 이 연구의 중요한 결과

**예상과 달리 두 제품이 같은 답에 도달해 있는 곳이 많았습니다.**

조회 계획 내부의 조건 이동(6항목 전부 동일), 파일 건너뛰기(**165행/1파일로 완전히 일치**), 파일 읽기 호환성(복합 타입·압축 4종 전부 결과 일치), 스키마 변경 상호운용, 시점 조회, 데이터 표현 모델, 실행 방식, 메모리 최소 단위(16MB 대 18MB).

**특히 세 항목은 "다를 것"이라 예상하고 들어가 "같다"로 끝났습니다.** 계획 단계의 대비가 실제로는 성립하지 않았습니다.

그리고 **어느 쪽도 상위집합이 아닌** 형태가 6건 있었습니다 — 둘 다 되는데 **되는 범위가 서로 어긋납니다.** 예를 들어 날짜 함수를 감싼 조건에서 Trino는 `year`/`date_trunc`를, StarRocks는 `date_format`을 처리합니다. **서로 반대 방향으로 못 합니다.**

### 4-3. 투명성을 위한 기록 — 이 연구가 스스로 고친 것

> **계획 단계의 전제가 일곱 번 틀렸습니다.** 소스코드 비교에서 선입견이 얼마나 자주 개입하는지의 표본으로 남깁니다.

| 처음 전제 | 실제 |
|---|---|
| 문법 정의가 특정 위치에 있다 | 483에서 **다른 모듈로 분리**됨 |
| 실행 방식이 서로 대비된다 | **성립하지 않음.** 둘 다 같은 방식으로 수렴 |
| Trino 미리계산표는 두 형식 지원 | **한 형식은 실제로 구현돼 있지 않음** |
| StarRocks 문자열 최적화는 Trino에 없는 기능 | 맞지만 **공용 파일 형식에서는 StarRocks 자신도 기본으로 안 씀** |
| StarRocks 자원 격리는 OS 기능 기반 | **아님.** CPU 배정 + 가중치 방식 |
| 캐시는 StarRocks만, **Trino는 없음** | **Trino 483에 분산 파일 캐시가 있음** |
| StarRocks는 자체 권한 관리만 | **외부 정책 엔진 통합이 있음** |

여섯 번째 항목의 근거입니다.

**[AlluxioFileSystemCacheConfig.java#L37-L41](https://github.com/trinodb/trino/blob/483/lib/trino-filesystem-cache-alluxio/src/main/java/io/trino/filesystem/alluxio/AlluxioFileSystemCacheConfig.java#L37-L41)**

```java
    private List<String> cacheDirectories = ImmutableList.of();
    private List<DataSize> maxCacheSizes = ImmutableList.of();
    private Optional<Duration> cacheTTL = Optional.of(Duration.valueOf("7d"));
    private List<Integer> maxCacheDiskUsagePercentages = ImmutableList.of();
    private DataSize cachePageSize = DataSize.valueOf("1MB");
```

▸ **읽는 법** — 캐시 기능이 **실재합니다.** 다만 첫 줄 `cacheDirectories` 의 기본값이 **빈 목록**입니다 — 저장 위치를 지정하지 않으면 켜지지 않습니다. **"기능이 없다"가 아니라 "기본이 꺼짐"이었습니다.** Trino에 없는 것은 조회 결과 자체를 재사용하는 캐시뿐입니다.

> **그리고 코드를 읽어 내린 판단이 실제 시험에 두 번 뒤집혔습니다.**
>
> - "설정 기준값 때문에 StarRocks가 단순한 실행 순서를 만든다" → 실제 원인은 **통계 부족**이었습니다. 통계가 완전하면 균형 잡힌 순서가 나옵니다
> - "StarRocks는 함수를 감싼 조건을 파일 건너뛰기에 못 쓴다" → **특정 함수에서는 완전히 걸러냅니다.** 문제는 함수 종류의 범위였습니다
>
> **측정 설계에서도 두 번 함정에 빠질 뻔했습니다** — 읽은 양을 재려고 건수 세기를 썼다가 StarRocks의 최적화에 걸려 비교가 성립하지 않았고, 두 제품의 지표를 짝지을 때 필터 적용 전후가 다른 값을 잘못 맞출 뻔했습니다.

## 5. 실무에서 의미 있는 차이

### 5-1. 상황별 선택 기준

| 상황 | 선택 | 결정적 이유 |
|---|---|---|
| **서로 다른 시스템을 한 조회로 합쳐야 한다** | **Trino** | 데이터 소스 27종 대 10종. 대체 수단 없음 |
| **공용 파일 형식 데이터를 고쳐 써야 한다**(변경분 반영, 개인정보 삭제) | **Trino** | StarRocks는 수정·삭제·병합이 전부 막혀 있음 |
| **수십 분 이상 도는 야간 배치** | **Trino** | 장애 시 진행분을 살리는 기능은 Trino만 |
| **대시보드 · 반복 조회** | **StarRocks** | 미리계산표 자동 활용 + 캐시 기본 켜짐 + 자동 통계 |
| **잦은 갱신이 있는 서비스 데이터** | **StarRocks** | `PRIMARY KEY` 테이블 + 일부 컬럼 갱신 |
| **Kafka → 테이블 파이프라인** | **StarRocks** | 상시 구독을 제품이 소유해 구성 요소가 하나 줄어듦 |
| **부분 문자열 검색이 잦다** | **StarRocks** | 전용 색인. 공용 파일 형식 통계로는 전혀 안 걸림 |
| **운영 인력이 적다** | **StarRocks** | 통계·파일 정리·캐시가 자동. 단 자원 계획은 더 어려움 |
| **여러 제품이 같은 데이터를 함께 쓴다** | **Trino** | 통계가 데이터에 남아 공유됨 |
| **규제 대응(데이터 흐름 추적)** | **Trino** | 컬럼 단위 계보를 제품이 직접 계산 |
| **제품을 고쳐 쓸 계획이 있다** | **Trino** | 확장점으로 대부분 해결, 단일 언어 빌드 |
| **초 단위 대화형 분석이 목표** | **StarRocks** | 구조상 유리. **다만 실행 시간을 재지 못했습니다**(6절) |

### 5-2. 둘 다 쓰는 구성이 현실적인 답일 때가 많다

**두 제품을 같은 데이터 저장소에 함께 붙이는 것은 실제로 잘 동작합니다** — 이번 연구의 시험 환경이 그 증거입니다. 역할을 나누면 이렇습니다.

| 작업 | 담당 |
|---|---|
| 데이터 추가, 조회, 시점 조회 | 양쪽 다 |
| **데이터 수정·삭제** | **Trino만** |
| **파일 정리, 이력 만료** | **Trino만** |
| **반복 집계 가속** | **StarRocks** |
| 감사·데이터 흐름 추적 | Trino |
| 성능 분석 | StarRocks |

**주의 두 가지입니다.**

1. **통계는 공유되지 않습니다.** 양쪽에서 각각 수집 명령을 돌려야 합니다
2. **StarRocks만으로 공용 파일 형식을 운영하지 마십시오.** 데이터를 넣을 수는 있지만 정리할 수단이 없어 파일이 계속 쌓입니다

### 5-3. Trino에서 StarRocks로 옮길 때 — 오류로 드러나지 않는 것부터

**조용히 결과가 달라지는 것이 가장 위험합니다.**

| 순위 | 항목 | 왜 위험한가 |
|---|---|---|
| **1** | **문자열 이어붙이기 연산자** | 오류가 아니라 **조용히 빈 값**이 됩니다 |
| 2 | 근사 집계 함수 | 이름은 대응되나 **값이 약 2.7% 다릅니다**(15,432 대 15,022, 참값 15,000) |
| 3 | 시간대 포함 시각 컬럼 | 구분되지 않습니다. 값 자체는 맞습니다 |
| 4 | 날짜 함수를 감싼 조건 | 파일 건너뛰기가 조용히 사라집니다. 조회는 성공합니다 |
| 5 | 예약어 99개 | 오류로 드러납니다(`text`·`key`·`json`·`range`·`default` 등) |
| 6 | 중첩 조회 | 계획 실패가 오류로 드러납니다. 전수 확인 필요 |
| 7 | UUID 컬럼 | 스키마 조회는 성공하고 **데이터 조회에서 실패**합니다 |

**호환 모드를 일괄 이전 수단으로 기대하지 마십시오** — 옛 버전 기준 부분 지원이고 함수 대응표가 약 100건입니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

**가장 중요한 한계부터 적습니다.**

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **어느 쪽이 실제로 빠른가** | **한 번도 재지 않았습니다.** 시험 데이터가 약 6만 건으로 너무 작고, 큰 데이터로 재려면 메모리가 부족합니다(한도 15.3GB 대 실제 15.6GB, 임시 공간 0) | 메모리 24GB 이상 장비 |
| **여러 대로 묶었을 때의 동작** | 각 제품 **1대씩**으로만 구성했습니다 | 3대 이상 구성 |
| **데이터 전송 계층 전체** | 위와 같은 이유로 **실측이 하나도 없습니다** | 위와 같음 |
| **자원 격리가 설정대로 CPU를 나누는가** | 이 항목의 핵심 주장인데 1대에서는 확인 불가 | 위와 같음 |
| **한 대가 죽어도 계속되는가** | 이 항목의 핵심 질문인데 1대에서는 확인 불가 | 위와 같음 |
| **여러 시스템 연합 조회** | 시험 환경에 데이터 소스가 하나뿐이었습니다 | 다중 소스 구성 |
| **외부 정책 엔진 연동** | 정책 서버가 없었습니다 | 별도 구성 |
| **실시간 적재 경로** | Kafka가 없었습니다 | 별도 구성 |
| **제품 개발 활동·출시 주기** | 소스를 최신본만 내려받아 이력이 없습니다 | 전체 이력 복제 |

**미해결 과제 하나**: StarRocks 이전 버전에서 관찰된 데이터 보관 프로세스 사망 현상이 **특정 CPU 아키텍처 한정인지 확인하지 못했습니다.** 디스크 여유가 부족해 두 버전을 함께 둘 수 없었습니다.

**이번 보고는 "두 제품이 무엇을 어떻게 하는가와 그 이유"이며, "어느 쪽이 더 빠른가"가 아닙니다.**

측정으로 확인된 명확한 우위는 4-1의 두 표에 있고 **길이가 비슷합니다.** 4-2의 "차이 없음" 목록도 그만큼 깁니다. **성능 비교 없이 우열을 말할 수 없다는 것이 이 연구의 정직한 결론입니다.**
