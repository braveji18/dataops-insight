## 한 장 요약

여러 테이블을 합쳐서 조회할 때(조인), **어떤 테이블부터 합치는지**에 따라 응답 시간이 몇 배씩 차이가 납니다. 두 엔진 모두 이 순서를 자동으로 정해 주지만, **정하는 방식은 정반대**였습니다.

| | Trino | StarRocks |
|---|---|---|
| 기본 전략 | 가능한 모든 순서를 **전부 따져본다** | 규모에 따라 **방법을 바꿔 가며** 처리한다 |
| 전부 따져보는 한계 | 테이블 **9개**까지 | 테이블 **5개**까지 |
| 순서 조정을 아예 포기하는 시점 | 테이블 **10개 이상** | 테이블 **51개 이상** |
| 통계 정보가 없을 때 | **조정을 중단한다** (사용자가 작성한 순서를 그대로 쓴다) | 간이 방식으로라도 **재배치한다** |
| 쿼리 한 줄로 개입할 수 있는가 | **불가능하다** (설정으로 전체를 바꾸는 방법만 있다) | **가능하다** (SQL 힌트를 쓴다) |
| LEFT 조인과 RIGHT 조인 | 재배치하지 **않는다** | 재배치**한다** |

**결론을 말씀드리면 우열의 문제가 아니라 성향의 차이입니다.** 테이블을 10개 미만으로 적게 쓰는 쿼리는 Trino가 더 꼼꼼하게 따지고, 테이블을 많이 쓰는 복잡한 쿼리는 StarRocks만 순서를 조정해 줍니다.

---

## 1. 이 항목을 확인한 이유

조인 순서는 **쿼리 응답 시간에 가장 크게 영향을 주는 요소** 가운데 하나입니다. 100만 건과 10건을 합칠 때 어느 쪽을 먼저 놓는지에 따라 처리량이 크게 달라집니다.

그런데 가능한 순서의 수는 테이블이 늘어날수록 급격하게 증가합니다. 테이블이 10개이면 경우의 수가 수백만 가지에 이릅니다. 그래서 모든 엔진은 **얼마나 따져볼 것인지와 따지는 데 시간을 얼마나 쓸 것인지** 사이에서 기준을 정해야 하고, **그 기준을 어디에 두는지가 곧 제품의 성향이 됩니다.**

## 2. Trino의 방식: 따질 수 있으면 끝까지 따지고, 그렇지 않으면 조정을 중단한다

### 2-1. 가능한 모든 조합을 만들어 낸다

테이블들을 두 그룹으로 나누는 **모든 경우의 수**를 만들어서, 각각의 처리 비용을 계산합니다.

**[ReorderJoins.java#L285-L295](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java#L285-L295)**

```java
static Set<Set<Integer>> generatePartitions(int totalNodes)
{
    checkArgument(totalNodes > 1, "totalNodes must be greater than 1");
    Set<Integer> numbers = IntStream.range(0, totalNodes)
            .boxed()
            .collect(toImmutableSet());
    return powerSet(numbers).stream()
            .filter(subSet -> subSet.contains(0))
            .filter(subSet -> subSet.size() < numbers.size())
            .collect(toImmutableSet());
}
```

▸ **읽는 법**: `powerSet` 은 모든 부분집합을 뜻합니다. 테이블 목록을 나누는 모든 방식을 전부 만들어 낸다는 의미이고, 이 지점에서 경우의 수가 급격히 늘어납니다. 뒤의 두 줄에 있는 `filter` 는 같은 조합을 두 번 세지 않으려고 중복을 제거하는 부분입니다.

### 2-2. 각 조합의 비용을 계산해 가장 저렴한 것을 고른다

**[ReorderJoins.java#L248-L259](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java#L248-L259)**

```java
ImmutableList.Builder<JoinEnumerationResult> resultBuilder = ImmutableList.builder();
Set<Set<Integer>> partitions = generatePartitions(sources.size());
for (Set<Integer> partition : partitions) {
    JoinEnumerationResult result = createJoinAccordingToPartitioning(sources, requiredOutputs, partition);
    if (result.equals(UNKNOWN_COST_RESULT)) {
        memo.put(multiJoinKey, result);
        return result;
    }
    if (!result.equals(INFINITE_COST_RESULT)) {
        resultBuilder.add(result);
    }
}
```

▸ **읽는 법**: 만들어 낸 모든 조합을 하나씩 확인하면서 비용을 매깁니다. 중요한 부분은 가운데에 있는 `UNKNOWN_COST_RESULT` 입니다. **비용을 계산할 수 없는 조합이 하나라도 나오면 그 자리에서 전체 작업을 중단하고 반환합니다.** 이것이 통계가 없으면 조정을 중단한다는 동작의 실체이며, 그 결과 사용자가 SQL에 작성한 순서가 그대로 남습니다.

### 2-3. 한계값이 숫자 하나로 정해져 있다

**[OptimizerConfig.java#L50-L51](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L50-L51)**

```java
private JoinReorderingStrategy joinReorderingStrategy = JoinReorderingStrategy.AUTOMATIC;
private int maxReorderedJoins = 8;
```

▸ **읽는 법**: 조정할 수 있는 설정이 사실상 이 두 개뿐입니다. `8` 은 **조인 연산의 개수**이므로 테이블 수로는 9개에 해당합니다. 테이블 9개를 합치려면 조인을 8번 수행하기 때문입니다. 이 수를 넘으면 순서 조정을 포기합니다. **중간 단계가 없다는 점**이 StarRocks와 비교했을 때 가장 큰 구조적 차이입니다.

### 2-4. LEFT 조인과 RIGHT 조인은 대상에서 제외한다

**[ReorderJoins.java#L114-L117](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java#L114-L117)**

```java
this.pattern = join().matching(
        joinNode -> joinNode.getDistributionType().isEmpty()
                && joinNode.getType() == INNER
                && isDeterministic(joinNode.getFilter().orElse(TRUE)));
```

▸ **읽는 법**: `getType() == INNER` 조건 때문에 **일반 조인(INNER)에만** 순서 조정이 적용됩니다. LEFT JOIN과 RIGHT JOIN 등은 아예 대상이 아니므로 작성된 순서 그대로 실행됩니다.

## 3. StarRocks의 방식: 규모에 맞춰 방법을 바꾼다

### 3-1. 테이블 개수를 세어서 처리 경로를 가른다

**[QueryOptimizer.java#L955-L973](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L955-L973)**

```java
// Join reorder
int innerCrossJoinNode = Utils.countJoinNodeSize(tree, JoinOperator.innerCrossJoinSet());
if (!sessionVariable.isDisableJoinReorder() && innerCrossJoinNode < sessionVariable.getCboMaxReorderNode()) {
    if (innerCrossJoinNode > sessionVariable.getCboMaxReorderNodeUseExhaustive()) {

        new ReorderJoinRule().transform(tree, context);          // 규모가 크면: 간이 계산 경로

        context.getRuleSet().addJoinCommutativityWithoutInnerRule();
    } else {
        context.getRuleSet().addJoinTransformationRules();       // 규모가 작으면: 전수 탐색 경로
    }
}
```

*(원문에서 로그 출력 줄은 읽기 편하도록 생략했습니다. 나머지는 그대로입니다.)*

▸ **읽는 법**: 첫 줄에서 조인 개수를 셉니다. 그다음에 **분기가 두 번** 있습니다. 바깥쪽 분기는 규모가 50 이상으로 너무 크면 아예 수행하지 않는다는 뜻이고, 안쪽 분기는 4 이하로 작으면 전부 따져보고 그보다 크면 간이 계산으로 넘긴다는 뜻입니다. Trino에는 이 안쪽 분기가 없습니다.

### 3-2. 여러 계산 방법의 결과를 모두 후보로 넣는다

**[ReorderJoinRule.java#L247-L267](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/join/ReorderJoinRule.java#L247-L267)**

```java
enumerate(new JoinReorderLeftDeep(context), context, innerJoinRoot, multiJoinNode, true);
// If there is no statistical information, the DP and greedy reorder algorithm are disabled,
// and the query plan degenerates to the left deep tree
if (Utils.hasUnknownColumnsStats(innerJoinRoot) && ...) {
    continue;
}
int atomSize = multiJoinNode.getAtoms().size();
if (atomSize <= 62 && atomSize <= context.getSessionVariable().getCboMaxReorderNodeUseDP()
        && context.getSessionVariable().isCboEnableDPJoinReorder()) {
    // 10 table join reorder takes more than 100ms,
    // so the join reorder using dp is currently controlled below 10.
    enumerate(new JoinReorderDP(context), context, innerJoinRoot, multiJoinNode, true);
}

if (context.getSessionVariable().isCboEnableGreedyJoinReorder() &&
        multiJoinNode.getAtoms().size() <= context.getSessionVariable().getCboMaxReorderNodeUseGreedy()) {
    enumerate(new JoinReorderGreedy(context), context, innerJoinRoot, multiJoinNode, true);
}
```

*(발췌입니다. 통계 확인 줄의 두 번째 조건은 테스트 전용 분기라 `...` 로 줄였고, 나머지는 원문 그대로입니다.)*

▸ **읽는 법**: `enumerate(...)` 가 세 번 나옵니다. 각각 **단순 방식과 정밀 계산 방식, 간이 방식**에 해당하고, 조건을 만족하면 **결과를 모두 후보로 추가**합니다. 하나를 골라서 쓰는 구조가 아니라 선택지를 늘려 놓고 비용으로 고르는 구조입니다.

아래의 두 영문 주석은 개발진이 남긴 판단 근거이므로 그대로 인용할 가치가 있습니다.
- *"통계 정보가 없으면 정밀 방식과 간이 방식을 끄고 가장 단순한 형태로 내려간다"* 라는 주석은 **통계가 없어도 최소한의 재배치는 수행한다**는 뜻입니다. Trino는 이 지점에서 조정을 중단합니다
- *"테이블 10개를 계산하는 데 100밀리초가 넘게 걸린다"* 라는 주석은 기본 한계를 10으로 잡은 실측 근거를 알려 줍니다

### 3-3. 단계별 기준값

**[SessionVariable.java#L1752-L1768](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java#L1752-L1768)**

```java
@VariableMgr.VarAttr(name = CBO_MAX_REORDER_NODE_USE_EXHAUSTIVE)
private int cboMaxReorderNodeUseExhaustive = 4;

@VariableMgr.VarAttr(name = CBO_MAX_REORDER_NODE, flag = VariableMgr.INVISIBLE)
private int cboMaxReorderNode = 50;

@VariableMgr.VarAttr(name = CBO_MAX_REORDER_NODE_USE_DP)
private long cboMaxReorderNodeUseDP = 10;

@VariableMgr.VarAttr(name = CBO_MAX_REORDER_NODE_USE_GREEDY)
private long cboMaxReorderNodeUseGreedy = 16;
```

*(발췌입니다. 같은 구간에 있는 "정밀 계산 방식 사용 여부 / 간이 방식 사용 여부" 켜고 끄는 항목 두 개는 생략했습니다. 둘 다 기본값은 켜짐입니다.)*

이 값들을 **읽는 분의 기준인 테이블 개수로 환산**하면 다음과 같습니다.

| 테이블 수 | 처리 방식 | 품질 |
|---|---|---|
| **5개 이하** | 모든 조합을 전부 따져본다 | 최상 |
| **6개에서 10개까지** | 정밀 계산(DP)과 간이 방식을 모두 후보로 놓고 비교한다 | 상 |
| **11개에서 16개까지** | 간이 방식(탐욕적 선택)만 후보로 추가한다 | 중 |
| **17개에서 50개까지** | 가장 단순한 방식인 일렬 배치만 적용한다 | 하 |
| **51개 이상** | 순서 조정을 포기한다 | 해당 없음 |

> **주의할 점이 있습니다. 코드값과 표의 숫자가 다른 이유입니다.** 코드에 적힌 `4` 와 `50` 은 **조인 연산의 개수**로 테이블 수보다 1이 작고, `10` 과 `16` 은 **테이블 개수**입니다. **같은 파일 안에서 두 단위가 섞여 있어서** 설정을 조정할 때 혼동하기 쉽습니다. 위 표는 전부 테이블 개수로 통일했습니다.

### 3-4. LEFT 조인과 RIGHT 조인도 재배치한다

**[QueryOptimizer.java#L975-L978](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L975-L978)**

```java
if (!sessionVariable.isDisableJoinReorder() && sessionVariable.isEnableOuterJoinReorder()
        && Utils.capableOuterReorder(tree, sessionVariable.getCboReorderThresholdUseExhaustive())) {
    context.getRuleSet().addOuterJoinTransformationRules();
}
```

▸ **읽는 법**: `enableOuterJoinReorder` 는 **기본값이 켜짐(true)** 입니다. 2-4절에서 확인한 Trino의 `getType() == INNER` 제한과 정확히 대비되는 부분이며, LEFT JOIN을 많이 쓰는 리포트성 쿼리에서 실질적인 차이로 나타날 수 있습니다.

## 4. 실제로 실행해서 확인한 것

문서상의 분석만으로는 틀릴 수 있으므로, **양쪽 엔진에 똑같은 데이터를 올리고 똑같은 쿼리를 실행**해 확인했습니다. 테스트 환경은 `scripts/testenv/` 이고, 6개 테이블을 합치는 표준 벤치마크 쿼리를 사용했습니다.

**결과값은 두 엔진이 완전히 일치**했습니다. 소수점까지 같은 값이 나왔습니다.

조인 순서는 다음과 같이 나왔습니다.

| 조건 | Trino | StarRocks |
|---|---|---|
| 통계 정보가 **완전할 때** | 균형 잡힌 순서가 나온다 | **완전히 동일한 순서가 나온다** |
| StarRocks의 통계를 **일부 지웠을 때** | 해당하지 않는다 | 단순한 일렬 순서로 저하된다 |

**통계 정보가 갖춰져 있으면 두 엔진이 같은 결론에 도달했습니다.** 설계가 달라도 결과가 같았다는 점은 두 제품 모두 충분히 성숙해 있다는 근거로 해석합니다. 반대로 **통계 관리가 되지 않으면 성능이 분명하게 나빠질 수 있다**는 실무 시사점도 함께 확인했습니다.

> **투명성을 위한 기록입니다**: 이 항목은 처음에 "StarRocks는 구조적으로 단순한 순서를 만든다"라고 잘못 결론을 냈다가, 재실험을 거쳐 **원인이 통계 정보 부족이었다는 사실**을 확인하고 정정했습니다. 정정 경위를 지우지 않고 `docs/evidence/A-2/` 에 남겨 두었습니다.

## 5. 실무에서 의미가 있는 차이

### (1) 통계 정보가 부실할 때의 동작

| | 동작 | 실무적 의미 |
|---|---|---|
| Trino | 순서 조정을 **포기한다** (2-2절 코드) | 개발자가 SQL을 잘 작성해야 성능이 나온다 |
| StarRocks | 간이 방식으로라도 **재배치한다** (3-2절 코드) | 통계가 없어도 최소한의 보정은 이루어진다 |

데이터 레이크처럼 외부에 있는 데이터를 조회할 때에는 통계가 부실한 경우가 흔하므로, **외부 데이터 조회 비중이 높다면 반드시 확인해야 하는 항목입니다.**

### (2) 문제가 되는 쿼리 한 건만 빠르게 수정할 수 있는가

**StarRocks는 SQL 문장 안에 직접 지시를 넣을 수 있습니다.** 조인 종류 바로 뒤에 대괄호로 지시어를 붙이는 문법이 정의되어 있습니다.

**[StarRocks.g4#L2479-L2486](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocks.g4#L2479-L2486)**

```antlr
joinRelation
    : asofJoinType bracketHint?
            rightRelation=relationPrimary joinCriteria
    | crossOrInnerJoinType bracketHint?
            LATERAL? rightRelation=relationPrimary joinCriteria?
    | outerAndSemiJoinType bracketHint?
            LATERAL? rightRelation=relationPrimary joinCriteria
    ;
```

지시어의 종류는 여섯 가지입니다.

**[HintNode.java#L23-L29](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/analysis/HintNode.java#L23-L29)**

```java
public static final String HINT_JOIN_BUCKET = "BUCKET";
public static final String HINT_JOIN_SHUFFLE = "SHUFFLE";
public static final String HINT_JOIN_COLOCATE = "COLOCATE";
public static final String HINT_JOIN_BROADCAST = "BROADCAST";

public static final String HINT_JOIN_SKEW = "SKEW";
public static final String HINT_JOIN_UNREORDER = "UNREORDER";
```

▸ **읽는 법**: 앞의 네 개는 두 테이블을 어떻게 나누어 처리할지를 지정하고, `SKEW` 는 데이터가 한쪽으로 쏠리는 상황에 대응하며, **`UNREORDER` 는 이 조인의 순서를 바꾸지 말라는 뜻입니다.** 실제로 사용할 때에는 `... JOIN [broadcast] 테이블명 ON ...` 형태로 작성합니다.

**Trino의 SQL 문법에는 이런 지시어가 없습니다.** 문법 정의 파일 전체를 확인했으며 관련 구문이 존재하지 않습니다 ([SqlBase.g4](https://github.com/trinodb/trino/blob/483/core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4)). 개입할 수 있는 수단은 설정값뿐이고, 이 설정은 **쿼리 전체 단위**로만 적용됩니다.

| | Trino | StarRocks |
|---|---|---|
| 개입 단위 | **쿼리 전체** (설정으로 조정한다) | **조인 하나** (SQL 지시어로 조정한다) |
| 급한 상황에서의 대응 | 설정을 바꾸고 다시 실행해야 한다 | 해당 쿼리만 고치면 된다 |

**장애에 대응하는 시간과 직결되는 차이입니다.** 다만 지시어는 쿼리에 그대로 남아서 데이터가 바뀐 뒤에도 계속 강제되므로, **한번 넣은 지시어를 관리하는 규칙이 필요합니다.**

### (3) LEFT 조인과 RIGHT 조인의 처리

2-4절과 3-4절에서 확인한 대로 Trino는 제외하고 StarRocks는 포함합니다. LEFT JOIN을 많이 쓰는 리포트성 쿼리가 많다면 실질적인 차이가 될 수 있습니다.

## 6. 아직 확인하지 못한 것 (한계를 명시합니다)

보고의 신뢰를 지키기 위해, **확인하지 못한 것을 분명하게 적습니다.**

| 항목 | 확인하지 못한 이유 | 필요한 조건 |
|---|---|---|
| **어느 쪽이 실제로 더 빠른가** | 현재 테스트 데이터가 너무 작아서 시간 차이에 의미가 없다 | 메모리를 24GB 이상 갖춘 서버가 필요하다 |
| **여러 대로 늘렸을 때의 동작** | 현재 각 엔진을 1대씩만 구성해 두었다 | 다중 노드 환경이 필요하다 |
| **LEFT 조인과 RIGHT 조인의 실측** | 사용한 벤치마크 쿼리가 전부 INNER 조인이었다 | 별도의 쿼리를 설계해야 한다 |

**이번 보고는 설계가 어떻게 다른지까지만 다루며, 어느 쪽이 빠른지는 다루지 않습니다.** 속도 비교는 별도의 환경이 확보되어야 가능합니다.
