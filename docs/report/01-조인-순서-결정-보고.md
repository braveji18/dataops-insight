# [보고] Trino vs StarRocks 비교 (1) — 여러 테이블을 합칠 때 순서를 정하는 방식

> 작성일: 2026-09-03 | 대상 버전: Trino 483, StarRocks 4.0.14
> 상세 기술 문서: `docs/A-2-01-조인-순서-결정.md`

---

## 한 장 요약

여러 테이블을 합쳐서 조회할 때(조인), **어떤 테이블부터 합치느냐**에 따라 응답 시간이 몇 배씩 차이납니다. 두 엔진 모두 이 순서를 자동으로 정해주지만, **정하는 방식이 정반대**였습니다.

| | Trino | StarRocks |
|---|---|---|
| 기본 전략 | 가능한 모든 순서를 **다 따져본다** | 규모에 따라 **방법을 바꿔가며** 처리한다 |
| 다 따져보는 한계 | 테이블 **9개**까지 | 테이블 **5개**까지 |
| 순서 조정을 아예 포기하는 시점 | 테이블 **10개 이상** | 테이블 **51개 이상** |
| 통계 정보가 없을 때 | **손을 뗀다** (사용자가 쓴 순서 그대로) | 간이 방식으로라도 **재배치한다** |
| 쿼리 한 줄로 개입 가능? | **불가** (설정으로 전체 변경만) | **가능** (SQL 힌트) |
| 일부 조인 종류 제외 | LEFT/RIGHT/FULL 조인은 **재배치 안 함** | 재배치함 |

**결론: 우열이 아니라 성향 차이입니다.** 테이블을 적게(10개 미만) 쓰는 쿼리는 Trino가 더 꼼꼼히 따지고, 테이블을 많이 쓰는 복잡한 쿼리는 StarRocks만 순서를 조정해 줍니다.

---

## 1. 왜 이걸 봤나

조인 순서는 **쿼리 응답 시간에 가장 크게 영향을 주는 요소** 중 하나입니다. 100만 건과 10건을 합칠 때 어느 쪽을 먼저 놓느냐로 처리량이 크게 달라집니다.

그런데 가능한 순서의 수는 테이블이 늘어날수록 폭발적으로 증가합니다. 테이블 10개면 경우의 수가 수백만 가지입니다. 그래서 모든 엔진은 **"얼마나 따져볼 것인가 vs 따지는 데 시간을 얼마나 쓸 것인가"** 사이에서 선을 그어야 하고, **그 선을 어디에 긋느냐가 곧 제품의 성향**입니다.

---

## 2. Trino의 방식 — "따질 수 있으면 끝까지, 아니면 손 뗀다"

### 동작

테이블 9개까지는 **가능한 모든 조합을 만들어 비용을 계산하고 가장 싼 것을 고릅니다.** 중간에 대충 하는 단계가 없습니다.

9개를 넘으면 **순서 조정을 포기**하고 사용자가 SQL에 쓴 순서를 그대로 씁니다.

### 근거 코드

| 내용 | 위치 |
|---|---|
| 모든 조합 생성 (핵심 로직) | [ReorderJoins.java#L285-L295](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java#L285-L295) |
| 각 조합의 비용 비교 | [ReorderJoins.java#L249-L251](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java#L249-L251) |
| 한계값 설정 (`maxReorderedJoins = 8`) | [OptimizerConfig.java#L51](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/OptimizerConfig.java#L51) |
| INNER 조인만 처리 (다른 조인 제외) | [ReorderJoins.java#L116](https://github.com/trinodb/trino/blob/483/core/trino-main/src/main/java/io/trino/sql/planner/iterative/rule/ReorderJoins.java#L116) |

> **용어 메모** — 설정값은 `8`인데 위 표에는 "테이블 9개"로 적었습니다. 이 값은 **조인 연산의 개수**이고, 테이블 수는 그보다 하나 많기 때문입니다(테이블 9개를 합치려면 조인 8번).

### 관리자가 조정할 수 있는 것

- `max_reordered_joins` — 몇 개까지 따져볼지 (기본 8)
- `join_reordering_strategy` — 자동/끔 (기본 자동)

둘 다 **쿼리 전체에 걸리는 설정**입니다. 특정 쿼리 한 건만 손보려면 그 쿼리를 실행할 때만 설정을 바꿔 넣어야 합니다.

---

## 3. StarRocks의 방식 — "규모에 맞춰 방법을 바꾼다"

### 동작

테이블 개수를 세어 **네 단계로 나눠 처리**합니다.

| 테이블 수 | 처리 방식 | 품질 |
|---|---|---|
| **5개 이하** | 모든 조합을 다 따져봄 | 최상 |
| **6 ~ 10개** | 정밀 계산(DP) + 간이 방식 결과를 모두 후보로 놓고 비교 | 상 |
| **11 ~ 16개** | 간이 방식(탐욕적 선택)만 후보로 추가 | 중 |
| **17 ~ 50개** | 가장 단순한 방식(일렬 배치)만 | 하 |
| **51개 이상** | 순서 조정 포기 | — |

핵심은 **여러 방식의 결과를 모두 후보로 넣고 비용으로 고른다**는 점입니다. 하나를 골라 쓰는 게 아니라 선택지를 늘립니다.

> **읽을 때 주의** — 코드의 기준값은 `4 / 10 / 16 / 50` 인데 위 표는 `5 / 10 / 16 / 50` 입니다. StarRocks 코드가 **두 가지 단위를 섞어** 쓰기 때문입니다. `4`와 `50`은 **조인 연산의 개수**(테이블 수보다 1 작음)이고, `10`과 `16`은 **테이블 개수**입니다. 위 표는 전부 테이블 개수로 환산한 값입니다. 설정값을 직접 조정할 때 혼동하기 쉬운 지점이라 별도로 적어 둡니다.

### 근거 코드

| 내용 | 위치 |
|---|---|
| 테이블 개수로 처리 경로를 가르는 부분 | [QueryOptimizer.java#L956-L972](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L956-L972) |
| 여러 방식을 후보로 넣는 부분 | [ReorderJoinRule.java#L247-L268](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/rule/join/ReorderJoinRule.java#L247-L268) |
| 단계별 기준값 (4 / 10 / 16 / 50) | [SessionVariable.java#L1752-L1767](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java#L1752-L1767) |
| LEFT/RIGHT 조인도 재배치 | [QueryOptimizer.java#L976-L977](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/optimizer/QueryOptimizer.java#L976-L977) |

개발자가 코드에 근거를 주석으로 남겨둔 부분도 있습니다 — 정밀 계산 방식의 기본 한계를 10으로 잡은 이유가 `테이블 10개를 계산하는 데 100밀리초가 넘게 걸린다`입니다.

### 관리자가 조정할 수 있는 것

단계별 기준값을 **따로따로** 조정할 수 있습니다(4 / 10 / 16 / 50). 조정 폭은 Trino보다 넓지만, **지금 어느 단계로 처리되고 있는지 알아야** 손댈 수 있습니다.

## 4. 실제로 돌려서 확인한 것

문서상 분석만으로는 틀릴 수 있어, **양쪽 엔진에 똑같은 데이터를 올리고 똑같은 쿼리를 실행**해 확인했습니다(테스트 환경은 `scripts/testenv/`, 6개 테이블을 합치는 표준 벤치마크 쿼리 사용).

**결과값은 두 엔진이 완전히 일치**했습니다 — 소수점까지 같았습니다.

조인 순서는 이렇게 나왔습니다.

| 조건 | Trino | StarRocks |
|---|---|---|
| 통계 정보가 **완전할 때** | 균형 잡힌 순서 | **완전히 동일한 순서** |
| StarRocks의 통계를 **일부 지웠을 때** | (해당 없음) | 단순한 일렬 순서로 저하 |

**통계 정보가 갖춰져 있으면 두 엔진이 같은 결론에 도달했습니다.** 설계가 달라도 결과가 같았다는 점은 두 제품 모두 성숙해 있다는 신호로 읽습니다.

> **투명성을 위한 기록**: 이 항목은 처음에 "StarRocks는 구조적으로 단순한 순서를 만든다"고 잘못 결론 냈다가, 재실험으로 **원인이 통계 정보 부족이었음**을 확인하고 정정했습니다. 정정 경위를 지우지 않고 `docs/evidence/A-2/` 에 남겨 두었습니다.

## 5. 실무에서 의미 있는 차이 3가지

### (1) 통계 정보가 부실할 때의 행동

| | 행동 | 실무적 의미 |
|---|---|---|
| Trino | 순서 조정을 **포기** | 개발자가 SQL을 잘 써야 성능이 나옴 |
| StarRocks | 간이 방식으로라도 **재배치** | 통계가 없어도 최소한의 보정은 됨 |

외부 데이터(데이터 레이크)를 조회할 때는 통계가 부실한 경우가 흔하므로, **외부 데이터 조회 비중이 높다면 짚어봐야 할 항목**입니다.

### (2) 문제 쿼리 한 건만 급히 손볼 수 있는가

StarRocks는 **SQL에 직접 지시를 넣을 수 있습니다.** 예를 들어 특정 조인만 순서 고정을 지시하는 표기가 문법에 있습니다.

Trino는 **SQL에 그런 표기가 없습니다.** 문법 정의 파일 전체를 확인했으나 관련 구문이 존재하지 않습니다. 설정을 통해 쿼리 전체 단위로만 개입할 수 있습니다.

| 내용 | 위치 |
|---|---|
| StarRocks 힌트 문법 | [StarRocks.g4#L2480-L2509](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/sql/parser/StarRocks.g4#L2480-L2509) |
| StarRocks 힌트 종류 (6종) | [HintNode.java#L23-L29](https://github.com/StarRocks/starrocks/blob/4.0.14/fe/fe-core/src/main/java/com/starrocks/analysis/HintNode.java#L23-L29) |
| Trino SQL 문법 정의 (힌트 없음) | [SqlBase.g4](https://github.com/trinodb/trino/blob/483/core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4) |

**장애 대응 시간에 직결되는 차이**입니다. 다만 힌트는 쿼리에 남아 데이터가 바뀐 뒤에도 계속 강제되므로, 관리 규칙이 필요합니다.

### (3) LEFT/RIGHT 조인의 처리

Trino는 이 종류의 조인을 **순서 조정 대상에서 제외**합니다. StarRocks는 포함합니다. LEFT JOIN을 많이 쓰는 리포트성 쿼리가 많다면 실질적 차이가 될 수 있습니다.

## 6. 아직 확인하지 못한 것 (한계의 명시)

보고의 신뢰를 위해, **확인하지 못한 것을 분명히 적습니다.**

| 항목 | 왜 못 했나 | 필요한 것 |
|---|---|---|
| **어느 쪽이 실제로 더 빠른가** | 현재 테스트 데이터가 너무 작아 시간 차이가 의미 없음 | 메모리 24GB 이상 서버 |
| **여러 대로 늘렸을 때의 동작** | 현재 각 엔진 1대씩만 구성 | 다중 노드 환경 |
| **LEFT/RIGHT 조인 실측** | 사용한 벤치마크 쿼리가 전부 INNER 조인 | 별도 쿼리 설계 |

**이번 보고는 "설계가 어떻게 다른가"까지이며, "어느 쪽이 빠른가"가 아닙니다.** 속도 비교는 별도 환경이 확보되어야 가능합니다.
