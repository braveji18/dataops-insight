# [보고] Trino vs StarRocks 아키텍처 구성도 — 그림으로 보는 하나의 갈림길

> 작성일: 2026-09-07 | 대상 버전: Trino 483, StarRocks 4.0.14
> 상세 기술 문서: `docs/99-종합-결론.md` (본문 31편 · 실험 기록 18편의 종합)
>
> 이 문서는 **종합 결론을 그림으로 설명하기 위한 것**입니다.
> 각 그림의 근거는 개별 기술 문서에 있고, 그림 아래에 문서 번호를 표시했습니다.

---

## 한 장 요약

31개 항목을 비교한 결과, **두 제품의 거의 모든 차이가 하나의 설계 결정에서 갈라져 나온다**는 것을 확인했습니다.

> **데이터를 자기가 보관하는가.**

그림 한 장으로 줄이면 이렇습니다.

```
  Trino                                    StarRocks
  ─────────────────────────────            ─────────────────────────────
  ┌───────────────┐                        ┌───────────────┐
  │   조회 엔진    │                        │   조회 엔진    │
  ├───────────────┤                        ├───────────────┤
  │ ═══ 경계 ═══  │  ← SPI (16종)          │   저장 엔진    │  ← 경계 없음
  ├───────────────┤                        ├───────────────┤
  │   저장 엔진    │  ← 남의 것             │   디스크       │  ← 자기 것
  │   (없음)      │                        └───────────────┘
  └───────────────┘
```

**경계를 만들어 그 뒤를 남에게 맡긴 쪽**과 **경계를 없애 전부 자기가 하는 쪽**입니다.

**이 한 장의 차이가 뒤따르는 모든 것을 결정합니다.** 아래 그림들이 그 과정입니다.

---

## 1. 전체 구성도

### 1-1. Trino — 두 종류의 프로세스와, 그 밖의 모든 것

```
        SQL (JDBC / HTTP)
             │
             ▼
┌────────────────────────────────────┐
│  Coordinator  (Java 프로세스 1대)    │   ※ 이중화 계층 없음
│  ┌──────────────────────────────┐  │
│  │ 파싱 → 분석 → 최적화 → 배치   │  │
│  └──────────────────────────────┘  │
│  보관하는 것: 실행 중인 조회의 상태만 │
└────────────────────────────────────┘
             │  HTTP (조회 계획 전달)
             ▼
┌────────────────────────────────────┐
│  Worker  (Java 프로세스 N대)         │
│  ┌──────────────────────────────┐  │
│  │  실행 (읽기·조인·집계·정렬)    │  │
│  └──────────────────────────────┘  │
│  보관하는 것: 없음 (디스크 불필요)   │
└────────────────────────────────────┘
      │  Worker ↔ Worker : HTTP (받는 쪽이 가져감)
      │
   ═══╪════════ SPI 경계 ═══════════════════════════
      │
      ▼  플러그인 파일 (JAR) 로 붙음
┌──────────────┬──────────────┬──────────────┐
│  Iceberg     │  PostgreSQL  │  Kafka  …    │  ← 27종 (+관계형 DB 15종)
└──────────────┴──────────────┴──────────────┘
      │              │              │
      ▼              ▼              ▼
  오브젝트        외부 DB        메시지 큐        ← 데이터는 전부 남의 것
  스토리지
```

▸ **그림 읽는 법** — 굵은 가로선(`═══ SPI 경계 ═══`)이 이 문서의 주인공입니다. **선 아래는 Trino 코드가 아닙니다.** 플러그인이 담당하고, 제3자가 직접 만들어 붙일 수도 있습니다.

세 가지를 눈여겨보십시오.

- **Worker에 디스크가 없어도 됩니다.** 그래서 캐시가 기본 꺼짐입니다(`B-3-01`)
- **Coordinator를 이중화하는 계층이 아예 없습니다.** 보관할 메타데이터가 없기 때문입니다(`B-4-01`)
- **Worker끼리는 HTTP로 데이터를 주고받습니다.** 받는 쪽이 가져가는 방식입니다(`A-4-01`)

### 1-2. StarRocks — 두 종류의 프로세스가 모든 것을 나눠 가짐

```
        SQL (MySQL 프로토콜)
             │
             ▼
┌─────────────────────────────────────────────────┐
│  FE  (Java 프로세스 · 3대 이상 권장)              │
│  ┌───────────────────────────────────────────┐  │
│  │ 파싱 → 분석 → 최적화 → 배치                │  │
│  ├───────────────────────────────────────────┤  │
│  │ 메타데이터 (테이블·스키마·트랜잭션)        │  │
│  │ 자동 통계 수집 데몬 · 미리계산표 관리       │  │
│  │  (수집 결과는 _statistics_ 내부 테이블에)   │  │
│  └───────────────────────────────────────────┘  │
│                                                 │
│   LEADER ◄──복제──► FOLLOWER ◄──복제──► OBSERVER │
│      쓰기          선거 참여          읽기 확장   │
└─────────────────────────────────────────────────┘
             │  BRPC (조회 계획 전달 · 제어)
             ▼
┌─────────────────────────────────────────────────┐
│  BE  (C++ 프로세스 N대)                          │
│  ┌───────────────────────────────────────────┐  │
│  │  실행 (읽기·조인·집계·정렬)                │  │
│  ├───────────────────────────────────────────┤  │
│  │  저장 엔진                                 │  │
│  │   Tablet → Rowset → Segment                │  │
│  │   색인 (ZoneMap·Bloom·Bitmap·N-gram)       │  │
│  │   자동 compaction · Data Cache             │  │
│  └───────────────────────────────────────────┘  │
│  보관하는 것: 데이터 그 자체 (로컬 디스크)        │
└─────────────────────────────────────────────────┘
      │  BE ↔ BE : BRPC (보내는 쪽이 밀어넣음)
      │
      └─► (외부 소스는 목록에 든 10종만: Iceberg·Hive·JDBC …)
```

▸ **그림 읽는 법** — **경계선이 없습니다.** FE와 BE는 하나의 제품을 둘로 쪼갠 것이지, 확장점이 아닙니다. 새 데이터 소스를 붙이려면 FE(Java)·BE(C++)·그 사이 통신 규약 **세 곳을 모두 고치고 제품을 다시 빌드**해야 합니다(`A-5-01`).

그리고 **BE 상자 안에 조회 엔진과 저장 엔진이 함께 있습니다.** 이것이 이 문서 전체의 열쇠입니다.

> **프로토콜 표기 주의**: FE 가 BE 에 조회 계획을 보낼 때 쓰는 것은 **BRPC** 입니다(`fe/fe-core/.../rpc/BackendServiceClient.java`). 계획의 *자료 구조*는 Thrift 로 정의돼 있고(`gensrc/thrift/PlanNodes.thrift`), 그것을 직렬화해 BRPC 요청에 싣습니다. **정의와 전달이 다른 층입니다.**

## 2. 같은 조회가 어떻게 흐르는가

같은 조회(`SELECT 지역, SUM(매출) FROM 주문 WHERE 날짜 >= … GROUP BY 지역`)를 두 제품이 어떻게 처리하는지 나란히 놓았습니다.

```
  Trino                                  StarRocks
  ──────────────────────────             ──────────────────────────
  ① 조회 계획 수립                        ① 조회 계획 수립
     · 통계를 저장소에 "물어봄"               · 통계를 자기 DB 에서 "꺼냄"
     · 미리계산표는 이름을 써야 씀            · 미리계산표를 자동으로 갈아끼움
                                            (A-2-06 · A-2-07)
        │                                       │
  ② 조건을 저장소에 넘김                  ② 조건을 스캔에 붙임
     · "이거 처리해 줄 수 있나?"              · 묻지 않고 그냥 붙임
     · 저장소가 책임진 건 계획에서 삭제       · 엔진이 쓸 수 있는 형태를 이미 앎
                                            (A-2-04)
        │                                       │
  ③ Worker 가 원격 저장소에서 읽음        ③ BE 가 자기 디스크에서 읽음
     · 네트워크 왕복                          · 색인으로 먼저 걸러냄
     · 캐시는 설정해야 켜짐                   · 캐시 기본 켜짐
                                            (B-3-01 · C-1-02)
        │                                       │
  ④ Worker ↔ Worker HTTP 로 재분배        ④ BE ↔ BE BRPC 로 재분배
                                            (A-4-01)
        │                                       │
  ⑤ 결과 반환                            ⑤ 결과 반환
```

▸ **그림 읽는 법** — ①②③에서 **StarRocks는 "이미 알고 있어서" 한 단계씩 건너뜁니다.** 물어볼 필요가 없고, 색인이 있고, 캐시가 켜져 있습니다. 전부 데이터를 자기가 보관하기 때문입니다.

**반대로 ②의 Trino 쪽 "물어봄"이 27종의 데이터 소스를 붙일 수 있게 하는 바로 그 장치입니다.** 같은 구조가 한쪽에서는 비용이고 한쪽에서는 능력입니다.

## 3. 경계가 만든 결과 — 기능이 어느 쪽에 살고 있는가

같은 기능들이 두 제품에서 **어느 위치에 놓여 있는지**를 겹쳐 그렸습니다.

```
                    Trino                    │              StarRocks
 ───────────────────────────────────────────┼──────────────────────────────────
                                            │
  Coordinator ┌─────────────────────┐       │   FE ┌──────────────────────────┐
              │ 파싱·분석·최적화     │       │      │ 파싱·분석·최적화          │
              │ 접근제어 (84 지점)   │       │      │ 접근제어 (31 지점)        │
              │ 컬럼 계보 계산       │       │      │ ★ 통계 자동수집·관리      │
              └─────────────────────┘       │      │ ★ 미리계산표 자동 재작성   │
                                            │      │ ★ 메타데이터 이중화        │
                                            │      └──────────────────────────┘
  Worker      ┌─────────────────────┐       │   BE ┌──────────────────────────┐
              │ 실행                 │       │      │ 실행                     │
              │ (디스크 없어도 됨)   │       │      │ ★ 저장 엔진 (테이블 4종)  │
              └─────────────────────┘       │      │ ★ 색인 4종+              │
                                            │      │ ★ 자동 compaction        │
   ═══════ SPI 경계 (16종) ═══════           │      │ ★ 캐시 (기본 켜짐)       │
                                            │      │ ★ 실시간 적재 (Kafka 구독)│
  플러그인    ┌─────────────────────┐        │      │ ★ CPU 실격리             │
              │ ★ 파일 형식 쓰기·정리│        │      └──────────────────────────┘
              │ ★ 통계 보관          │        │
              │ ★ 미리계산표 보관     │        │      (경계 없음 — 외부 소스 10종 고정)
              │ (27종이 각자 구현)   │        │
              └─────────────────────┘        │

  ★ = 그 제품에서 우위가 확인된 기능
```

▸ **그림 읽는 법** — **★ 표시의 위치를 보십시오.**

StarRocks의 ★는 **전부 제품 안**에 있습니다. 그래서 자동으로 동작하고, 서로 맞물려 최적화됩니다.

Trino의 ★는 **경계 아래 플러그인 쪽**에 있습니다. 그래서 **플러그인 품질에 따라 성능이 달라지고**, 통계·미리계산표처럼 엔진이 소유해야 가능한 기능은 만들 수 없습니다.

**그런데 바로 그 위치 때문에 Trino의 ★는 27종에 각각 존재합니다.** 파일 형식을 고치고 정리하는 기능이 그 예입니다 — 남의 저장소를 빌려 쓰니 정리 책임까지 져야 했고, 그래서 완비돼 있습니다(`A-5-04`).

## 4. 자원을 다루는 방식이 갈리는 지점

"데이터를 보관하는가"가 **자원 관리**에서도 그대로 나타납니다.

```
  메모리
  ──────────────────────────────────────────────────────────────
  Trino    ┌────────────────────────────┐  힙 100%
           │ 조회에 배정 (최대 30%)      │
           ├────────────────────────────┤
           │ ░░ 비워 둠 (30%) ░░         │ ← GC·버퍼·플러그인 몫
           ├────────────────────────────┤
           │ 나머지                      │
           └────────────────────────────┘
           회계 대상: 조회만

  StarRocks┌────────────────────────────┐  물리 메모리 100%
           │ 사용 (90%)                  │
           │  조회 + 적재 + compaction   │ ← 보관 작업까지 같은 예산 안에서
           │  + 복제 + 캐시              │
           ├────────────────────────────┤
           │ ░ 10% ░                     │
           └────────────────────────────┘
           회계 대상: 제품이 하는 모든 일
```

▸ **그림 읽는 법** — Trino는 **조회가 쓰는 메모리만 계산하고 30%를 넉넉히 비웁니다.** 보관 작업이 없으니 셀 것도 없습니다.

StarRocks는 **90%를 쓰되 적재·파일 정리·복제까지 같은 예산 안에서 다툽니다.** 자원 계획이 더 어려운 대신, 그 전부를 제품이 조율합니다(`B-1-01`).

```
  CPU 격리
  ──────────────────────────────────────────────────────────────
  Trino      조회 목록을 1초마다 훑어봄 → 한도 초과면 실패 처리
             ┌──┐ ┌──┐ ┌──┐        ← 1초 안에 끝난 조회는 그냥 통과
             └──┘ └──┘ └──┘           (실측 확인)
             스레드는 OS 가 나눔

  StarRocks  BE 가 스레드를 소유 → 데이터 읽는 도중에 중단시킴
             ████████▌ 중단          ← 짧은 조회도 못 빠져나감
             CPU 배정 + 가중치로 실제 분배            (실측 확인)
```

▸ **그림 읽는 법** — **스레드를 누가 소유하는가의 차이입니다.** Trino의 Worker는 실행만 하므로 OS 스케줄러에 맡기고 입장만 통제합니다. StarRocks의 BE는 데이터를 들고 있으니 읽는 흐름 자체에 개입할 수 있습니다(`B-2-01`).

## 5. 장애가 났을 때 그림이 어떻게 달라지는가

```
  ① 조율 노드가 죽었을 때
  ──────────────────────────────────────────────────────────────
  Trino      Coordinator ✗
             └─► 진행 중이던 조회 전부 소실. 이중화 계층 없음
                 (앞단 게이트웨이로 보완하는 것이 일반적)

  StarRocks  FE(LEADER) ✗
             └─► FOLLOWER 중 하나가 자동 승격 (선거)
                 메타데이터는 이어짐. 단 진행 중이던 조회는 소실

  ② 실행 노드가 죽었을 때
  ──────────────────────────────────────────────────────────────
  Trino      Worker ✗
             기본        └─► 조회 실패 → 처음부터 재실행
             FTE 켬      └─► 죽은 작업만 다시 → ★ 진행분 유지

  StarRocks  BE ✗
             └─► 조회 전체 재실행 (최대 2회)
                 ※ 데이터는 복제본이 있어 소실되지 않음

  ③ 파일 읽기 중 결함이 났을 때
  ──────────────────────────────────────────────────────────────
  Trino      읽기 코드는 Java  → 조회 하나 실패
  StarRocks  읽기 코드는 C++   → ★ BE 프로세스 자체가 죽음
                                  (데이터를 든 프로세스가 죽는다)
```

▸ **그림 읽는 법** — ①에서는 StarRocks가, ②에서는 Trino가 앞섭니다. **서로 다른 층을 보호하고 있습니다** — StarRocks는 관리 정보를, Trino는 진행 중인 작업을.

③이 특히 중요합니다. **Trino는 실행과 저장이 분리돼 있어 결함의 파급이 조회 하나에 그칩니다.** StarRocks는 같은 프로세스가 데이터를 들고 있어 파급이 큽니다(`A-5-03`). **보관하는 대가입니다.**

## 6. 함께 쓸 때의 그림

종합 결론이 권하는 구성입니다. **두 제품을 같은 데이터 저장소에 붙이는 것은 실제로 잘 동작합니다** — 이번 연구의 시험 환경이 그 증거입니다.

```
                    ┌──────────────────┐
                    │  Iceberg 카탈로그 │
                    │  (오브젝트 스토리지)│
                    └────────┬─────────┘
                  ┌──────────┴──────────┐
                  ▼                     ▼
        ┌───────────────────┐  ┌───────────────────┐
        │      Trino        │  │    StarRocks      │
        ├───────────────────┤  ├───────────────────┤
        │ ✔ 여러 소스 조인   │  │ ✔ 반복 집계 가속   │
        │ ✔ 수정·삭제·병합   │  │ ✔ 대시보드 조회    │
        │ ✔ 파일 정리·이력   │  │ ✔ 성능 분석       │
        │ ✔ 장시간 배치      │  │                   │
        │ ✔ 계보·감사        │  │ (+ 자체 저장소에   │
        │                   │  │   실시간 적재)     │
        └───────────────────┘  └───────────────────┘

        ⚠ 통계는 공유되지 않음 → 양쪽에서 각각 수집
        ⚠ StarRocks 만으로 운영 금지 → 정리 수단이 없어 파일이 쌓임
```

▸ **그림 읽는 법** — **Trino가 쓰기·정리를, StarRocks가 읽기 가속을 맡는 구성**입니다. 두 제품의 ★가 겹치지 않기 때문에 성립합니다(3절 그림).

경고 두 가지가 실무에서 실제로 걸립니다. 특히 두 번째는 **StarRocks로 공용 파일 형식에 데이터를 넣을 수는 있으나 고치거나 정리할 수 없기** 때문입니다(`A-5-04`).

## 8. 이 그림들이 보여주지 못하는 것

**그림은 구조를 보여줄 뿐 성능을 보여주지 않습니다.**

| 항목 | 왜 그림에 없나 |
|---|---|
| **어느 쪽이 빠른가** | **실행 시간을 한 번도 재지 않았습니다.** 시험 데이터가 약 6만 건으로 너무 작고, 큰 데이터로 재려면 메모리가 부족했습니다 |
| **여러 대로 묶었을 때** | 각 제품 **1대씩**으로만 구성했습니다. 1·5절 그림의 N대 부분은 **코드를 읽어 그린 것**이고 동작을 확인하지 못했습니다 |
| **데이터 전송 계층** | 위와 같은 이유로 2절 ④단계에 **실측이 하나도 없습니다** |
| **자동 승격이 실제로 되는가** | 5절 ①의 FOLLOWER 승격은 **코드 기준**입니다 |
| **FTE가 실제로 진행분을 살리는가** | 5절 ②의 Trino FTE도 **코드 기준**입니다 |
| **StarRocks 저장·컴퓨트 분리 구성** | 1-2 그림은 기본 구성(BE가 디스크를 가짐) 기준입니다. 분리 구성은 별도 재구성이 필요해 확인하지 못했습니다 |

**따라서 이 문서는 "왜 그런 차이가 생기는가"를 설명하는 그림이며, "어느 쪽이 얼마나 빠른가"의 근거가 아닙니다.**

그림에 ★로 표시한 우위 항목들은 **구조에서 비롯된 기능 유무**이지 속도 비교가 아닙니다. 실제로 측정으로 확인된 우위는 **StarRocks 12개 · Trino 10개로 비슷했고**, "차이 없음"으로 끝난 항목도 10개였습니다.
