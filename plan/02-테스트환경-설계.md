# 테스트 환경(lakehouse-lab) 설계

> 목적: `docs/` 에 쓰는 **소스코드 분석 주장을 실제 쿼리로 검증**하기 위한 로컬 환경.
> 어느 머신에서든 동일하게 재현되어야 하고, 그 재현성이 AI의 판단이 아니라 파일로 보장되어야 한다.
> 구현체는 `scripts/testenv/`, AI 사용법은 `.claude/skills/lakehouse-lab/`.

---

## 0. 왜 필요한가

`plan/01` 의 비교 방식은 "코드를 읽고 `works/<engine>/경로:라인` 을 인용한다"이다. 이것만으로는 두 가지가 안 된다.

1. **주장의 반증** — "StarRocks가 이 술어를 푸시다운한다"는 코드 독해는 틀릴 수 있다. 실행해봐야 확정된다.
2. **독자의 검증** — 문서를 읽는 사람이 결론을 스스로 확인할 방법이 없다.

그래서 런타임 증거를 코드 증거 옆에 두는 구조로 간다. 이때 **버전 정합성**이 이 설계의 척추다. `works/` 클론 태그와 컨테이너 이미지 태그가 어긋나면 런타임 증거가 코드 인용을 검증하지 못하고, 문서 전체가 검증 불가능해진다.

## 1. 구성

```
                       MinIO (S3 호환, bucket=lakehouse)
                              ▲
                              │ s3a://
                   Hive Metastore (thrift:9083)  ← PostgreSQL
                       ▲                  ▲
        thrift         │                  │        thrift
   ┌───────────────────┘                  └────────────────────┐
   │                                                            │
Trino coordinator ── worker                    StarRocks FE ── BE
   catalog: iceberg (파일 선언)                  catalog: iceberg (DDL 등록)
```

양쪽 카탈로그 이름을 모두 `iceberg` 로 맞췄다. 그래서 `SELECT ... FROM iceberg.bench.lineitem` 이라는 **동일한 SQL 문자열**이 두 엔진에서 그대로 동작한다 — 비교 쿼리를 한 벌만 관리하기 위한 선택이다.

시드 데이터는 Trino의 `tpch` 커넥터로 생성해 Iceberg로 CTAS 한다. 적재 경로가 하나뿐이므로 두 엔진은 **같은 파일**을 읽는다. 별도 데이터 생성기도, 양쪽 적재 스크립트의 동기화 문제도 없다.

## 2. 설계 결정과 근거

### D-1. StarRocks는 CN이 아니라 **FE + BE (shared-nothing)**

"CN+BE"는 실제로는 택일 관계다. FE+BE(shared-nothing)를 고른 이유:

- Trino의 coordinator+worker와 **프로세스 수·역할이 대칭**이다. 규모를 맞춘 비교라는 전제가 성립한다.
- Iceberg 외부 카탈로그 조회는 BE로 충분하다. CN(shared-data)은 `run_mode=shared_data` + storage volume 설정이 한 겹 더 붙는다.
- `plan/01` **C-1(StarRocks 전용 스토리지 계층)** 검증에 로컬 스토리지가 필요하다. BE가 없으면 테이블 모델·인덱스·compaction을 아예 관찰할 수 없다.

shared-data 비교가 필요해지면 `profiles/shared-data.env` + compose 프로파일로 추가한다. **지금 넣지 않은 이유는 검증되지 않은 설정을 자산에 섞지 않기 위해서다.**

### D-2. 비교 대상의 버전은 `versions.env` 하나가 지배한다

`works/` 클론 태그와 이미지 태그를 같은 파일에 나란히 둔다.

| | 태그 | 근거 |
|---|---|---|
| Trino | `483` | 이미지·git 태그 모두 존재 확인. 이 시점 최신 라인 |
| StarRocks | `4.0.14` | 4.0 라인 최신 패치. **4.0.1 은 사용 불가** — 아래 참조 |

이 파일이 지배하는 것은 **비교 대상의 버전**이다. 인프라인 Hive Metastore 는 성격이 달라 `hive/hive<N>.env` 로 분리했다 — 근거는 D-7.

StarRocks는 처음에 `4.0.1` 로 고정했다가 4.0.14로 올렸다. 4.0.1 BE는 Trino가 쓴 Iceberg Parquet의 DATE 컬럼에 술어를 거는 순간 row-group zone-map 필터 경로에서 SIGSEGV로 죽는다(`Int32ToDateConverter::convert`). TPC-H Q1을 포함해 날짜 필터가 있는 모든 쿼리가 막히므로 비교 자체가 불가능했다.

이 사건이 D-2 설계의 근거이기도 하다. **버전 교체 비용이 `versions.env` 한 파일 + `bin/reset.sh` 였다.** 검증은 실제로 이 순서로 진행했다: 크래시 재현 → 4.0.14로 한 줄 교체 → reset → 동일 쿼리 정상. 자세한 재현 절차는 `docs/evidence/A-5/20260820-starrocks-4.0.1-parquet-date-zonemap-crash.md`.

이미지는 태그가 아니라 **manifest digest 로 고정**한다. 태그는 재태깅될 수 있고, `latest` 는 재현성의 반대말이다.

버전 변경 절차: `versions.env` 수정 → `works/` 재클론 → `bin/reset.sh` → `docs/` 상단 버전 표기 갱신.

### D-3. 카탈로그는 **HMS 단독**

Iceberg REST 카탈로그가 구성은 더 간단하지만(S3A jar 이슈 회피), 운영 환경에서 실제로 쓰는 구성은 HMS다. 비교 결과가 실무 판단에 쓰이려면 실무 구성과 같아야 한다.

대가: 순정 `apache/hive` 이미지에는 `hadoop-aws` / `aws-java-sdk-bundle` 이 없어 `s3a://` 경로에서 죽는다. **이 스택에서 가장 자주 깨지는 지점**이라 `conf/hms/Dockerfile` 로 굽고 jar 버전까지 고정했다.

REST 카탈로그가 필요해지면(양 엔진의 카탈로그 구현 차이 자체가 `plan/01` A-5 소재다) compose 프로파일로 추가한다.

### D-4. 환경 자산은 `scripts/testenv/`, 스킬은 참조만

자산을 스킬 디렉토리 안에 넣지 않은 이유:

- 검증 주체가 사람이기도 하다. Claude 없이 `bin/up.sh` 로 띄울 수 있어야 한다.
- `README.md` 의 디렉토리 규약(`scripts/` = 비교 작업 코드)을 지킨다.
- 스킬은 얇게 유지된다 — "무엇을 실행하고 무엇을 판정하는가"만 담고, 파일 내용을 중복하지 않는다.

### D-5. 스킬 1 + 에이전트 1

| | 역할 | 이유 |
|---|---|---|
| skill `lakehouse-lab` | 환경 기동·상태·쿼리 실행 절차 | **AI가 compose 파일을 매번 생성하면 재현성이 깨진다.** 스킬은 검증된 자산을 실행하는 절차만 담는다 |
| agent `dual-engine-runner` | 양쪽 실행 → 판정 표만 반환 | **컨텍스트 방화벽.** 두 소스트리를 읽는 메인 세션이 EXPLAIN 원문·컨테이너 로그로 오염되지 않게 한다 |

`claim-verifier`(주장 → 판별 쿼리 설계 → 판정)를 따로 두는 안도 검토했으나, 초기에는 역할 경계가 흐려질 위험이 더 크다고 봤다. `dual-engine-runner` 의 프롬프트가 붐비면 그때 분리한다.

### D-6. 배포는 플러그인이 아니라 이 저장소

"어디서든 동일하게"의 배포 단위는 **이 git 저장소**다. `.claude/skills/`, `.claude/agents/`, `scripts/testenv/` 를 커밋했으므로 clone 하는 순간 어느 머신에서든 따라온다. 플러그인화는 *다른 저장소에서도* 이 랩을 쓰게 될 때 검토한다.

### D-7. HMS 버전은 `hive/hive<N>.env` 로 분리한다

**문제** — 실무에 남아 있는 HMS 상당수가 아직 Hive 3 계열이다. Iceberg 카탈로그 동작이 HMS 메이저 버전에 걸리는지(테이블 등록, 통계, 파티션 API) 확인하려면 두 버전에서 같은 비교 쿼리가 돌아야 한다. 그런데 HMS 버전을 바꾸면 **이미지 태그 하나가 아니라 최소 4개 값이 함께 움직인다.**

```
이미지 → 번들 Hadoop → hadoop-aws → aws-java-sdk-bundle,  그리고 아키텍처 지원 범위
```

`hadoop-aws` 가 번들 Hadoop 과 어긋나면 빌드는 성공하고 **런타임에 S3A 가 깨진다**(D-3 의 그 지점이다). 손으로 맞추면 반드시 어긋난다.

**결정** — `versions.env` 에 HMS 를 두지 않고 `hive/hive3.env`, `hive/hive4.env` 로 세트를 묶는다. 선택은 `bin/up.sh --hive 3|4`, 기본값은 `versions.env` 의 `LAB_HIVE_DEFAULT`.

D-2 와 어긋나 보이지만 아니다. **HMS 는 비교 대상이 아니라 두 엔진에 동일 조건으로 제공되는 인프라**다. `versions.env` 가 지배하는 것은 "비교 대상의 버전"이고, 그 정합성 요구(=`works/` 클론 태그와 일치)는 HMS 에 적용되지 않는다. 성격이 다른 두 축을 한 파일에 섞으면 오히려 `versions.env` 의 규율이 흐려진다.

**분기를 한 곳에 가두기** — 이 결정의 핵심은 파일 분리가 아니라 **분기가 번지지 않게 하는 것**이다. Hive 3/4 의 기동 차이는 전부 `conf/hms/hms-entrypoint.sh` 가 흡수하고, `docker-compose.yml` 과 `metastore-site.xml` 은 두 변형에서 **완전히 동일하게 유지**된다. 분기가 여러 파일로 번지는 순간 "동일 조건 비교"라는 전제가 깨지기 때문이다.

Hive 3 에서 실제로 걸렸던 것과 대응 위치:

| 차이 | 대응 | 구현 위치 |
|---|---|---|
| arm64 매니페스트 없음(amd64 단독) | 플랫폼 고정 + 메모리 2배 보정 | `hive3.env`, `common.sh` |
| 번들 Hadoop 3.1.0 (4.x 는 3.3.6) | hadoop-aws/aws-sdk 를 맞춰 주입 | `hive3.env`, `conf/hms/Dockerfile` |
| `postgresql-9.4` 동봉 (SCRAM 미지원) | 제거하고 42.7.4 만 남김 | `conf/hms/Dockerfile` |
| `schematool` 이 매번 `-initSchema` (멱등하지 않음) | 기존 스키마 감지 시 건너뜀 | `hms-entrypoint.sh` |
| `schematool` 이 `metastore-site.xml` 을 못 읽음 | 같은 파일을 `hive-site.xml` 로 복사 | `hms-entrypoint.sh` |

**전환에 `reset` 을 강제하는 이유** — Hive 3 과 4 는 metastore 백엔드 스키마 버전이 다르다(3.1.0 vs 4.0.0). 같은 볼륨 위에서 변형만 바꾸면 `schematool` 이 죽거나, 더 나쁘게는 **반쯤 동작한다**. 후자가 훨씬 위험하다 — 한참 뒤에 이상한 비교 결과로 발견된다. 그래서 `up.sh` 가 변형 전환을 감지하면 실행을 거부하고 `bin/reset.sh --hive N` 을 안내한다. 사고를 나중에 발견하는 것보다 여기서 멈추는 편이 싸다.

**대가** — arm64 호스트에서 hive 3 은 에뮬레이션으로 돈다. 기능 검증에는 문제없지만(HMS 는 메타데이터만 다루고 데이터 IO 는 엔진이 직접 한다) HMS 왕복이 포함된 시간은 부풀려진다. `bin/bench.sh` 가 결과 JSON 에 `hive.emulated` 를 기록하는 이유이고, 측정 규칙은 `references/protocol.md` 에 있다.

| 이미지 아키텍처 | Trino / StarRocks FE·BE / MinIO / **Hive 4.0.1** 은 arm64 매니페스트 보유 | 에뮬레이션 불필요 |

| HMS 메모리 | 이미지 entrypoint 가 `-Xmx1G` 강제 | `HMS_MEM > HMS_HEAP` 불변식. `common.sh` 의 `lab_check_hms_mem` 이 강제 |

### 실행 검증 현황

| 조합 | 상태 |
|---|---|
| macOS arm64 / `functional` / hive 4 | ✅ 기동·시드·재기동 멱등성·양쪽 행 수 일치 확인 |
| macOS arm64 / `functional` / hive 3 | ✅ 확인 (에뮬레이션) |
| macOS arm64 / `perf` | 미검증 |
| linux (x86 / arm) | **미검증** |

스크립트는 리눅스 대응이 되어 있으나(BSD/GNU 차이 회피, bash 3.2 문법) 실행한 적이 없다.
특히 **linux/arm64 에서 `--hive 3` 은 qemu binfmt 등록이 별도로 필요하다** — Docker Desktop 은 자동 제공하지만 리눅스 네이티브 도커는 그렇지 않다. 예상 지점은 `references/troubleshooting.md` 의 "리눅스에서만 나는 문제" 절에 정리했다.

## 4. 한계 — 결론을 쓸 때 반드시 붙일 한정

1. **arm64 성능 숫자는 x86으로 이전 불가.** StarRocks BE는 x86에서 AVX2/AVX512, arm에서 NEON 경로를 탄다. `bin/bench.sh` 가 결과 JSON에 호스트 아키텍처를 항상 기록하는 이유다.
2. **worker 1 / BE 1 규모.** 분산 셔플·스케줄링 특성(`plan/01` A-4)은 이 규모에서 드러나지 않는다.
3. **컨테이너 자원 제약.** spill·메모리 관리(B-1) 비교는 실제 한도가 아니라 인위적 한도에서의 동작 관찰이다.
4. **적재 경로가 Trino 고정.** 파일 크기·레이아웃이 Trino 기준이다. StarRocks가 쓴 Iceberg 파일을 읽는 경우와 다를 수 있고, 쓰기 성능 비교는 이 랩의 시드 경로로 대신할 수 없다.
5. **hive 변형이 다른 결과는 시간 비교 불가.** arm64 에서 hive 3 은 에뮬레이션이라 HMS 왕복이 포함된 구간(플랜 생성, 첫 쿼리 지연, 메타데이터 조회)이 부풀려진다. 스캔·조인·집계는 영향받지 않는다(데이터 IO 는 엔진이 직접 한다). 결과 JSON 의 `hive.emulated` 로 구분한다.

이 한계들은 `perf` 프로파일이나 linux/x86 호스트에서 같은 compose 를 돌려 일부 완화할 수 있다. 호스트별 분기가 compose 가 아니라 `hive/*.env` 와 `bin/common.sh` 에 모여 있어 이식에 파일 복사가 필요 없다 — 다만 **저장소 clone 만으로 끝나는 것은 아니다.** linux/arm64 에서 hive 3 을 쓰려면 qemu binfmt 등록이 선행되어야 한다(3절 참조).
