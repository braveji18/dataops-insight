# Trino vs StarRocks 소스코드 비교 항목 정리

> 목적: 두 엔진을 **소스코드 차원**에서 기능 비교하기 위한 비교 축(axis) 정의와 우선순위.
> 아래 소스 경로는 각 프로젝트의 일반적인 모듈 구조 기준이며, `works/` 에 클론한 실제 리비전에서 반드시 재확인해야 한다(버전별로 패키지가 이동한 항목이 있음).

---

## 0. 두 엔진의 근본적 차이 (비교의 전제)

| | Trino | StarRocks |
|---|---|---|
| 성격 | **쿼리 엔진 전용** (스토리지 없음) | **스토리지 + 쿼리 엔진** (레이크하우스 겸용) |
| 프로세스 | Coordinator / Worker (단일 Java 프로세스) | FE(Java) / BE(C++) 또는 CN(C++) 이원 구조 |
| 언어 | Java 전체 | FE=Java, BE=C++ |
| 메타데이터 | 자체 저장 없음, 커넥터/외부 메타스토어 위임 | FE가 자체 메타데이터 보유(edit log + image, BDB JE 복제) |
| 프로토콜 | HTTP REST + JDBC 드라이버 | MySQL wire protocol 호환 |
| 강점 축 | 페더레이션·커넥터 다양성 | 벡터화 성능·머티리얼라이즈드 뷰·실시간 적재 |

**주의**: "동일 기능의 구현 비교"가 성립하는 영역(파서/옵티마이저/실행엔진/커넥터)과, **한쪽에만 존재하는 영역**(StarRocks의 스토리지·테이블 모델·적재 트랜잭션 / Trino의 Plugin SPI 생태계)을 구분해서 문서를 나눠야 한다. 후자는 "비교"가 아니라 "부재 및 대체 수단" 형태로 기술한다.

---

## 1. 비교 항목 (우선순위 A: 핵심)

### A-1. SQL 파싱 & 분석 계층
| 항목 | Trino | StarRocks |
|---|---|---|
| 문법 정의 | ANTLR4 `SqlBase.g4` (`core/trino-parser`) | ANTLR4 `StarRocks.g4` (`fe/fe-core/.../sql/parser`) |
| 분석기 | `sql/analyzer/StatementAnalyzer.java`, `Analyzer.java` | `sql/analyzer/*` (Analyzer, ExpressionAnalyzer) |
| 타입 시스템 | `trino-spi` `Type`/`TypeOperators` | `com.starrocks.catalog.Type`, BE `runtime/types` |

확인할 질문
- SQL 표준 준수 범위 차이 (ANSI SQL vs MySQL 방언 호환) — 문법 파일 규칙 수/커버리지 비교
- 타입 체계 차이(DECIMAL 정밀도, 복합 타입 ARRAY/MAP/STRUCT/JSON, 시간대 처리)
- 함수 등록 방식: Trino `@ScalarFunction` 애노테이션 기반 vs StarRocks 빌트인 함수 테이블 생성(gen) 방식

### A-2. 옵티마이저 (가장 중요)
| 항목 | Trino | StarRocks |
|---|---|---|
| 구조 | `IterativeOptimizer` + `PlanOptimizers` 규칙 목록 | Cascades 스타일 `Optimizer` + `Memo`/`GroupExpression`/Task |
| 규칙 | `sql/planner/iterative/rule/*` | `sql/optimizer/rule/transformation`, `.../implementation` |
| 통계·비용 | `io.trino.cost.*` (StatsCalculator, CostCalculator) | `sql/optimizer/statistics/*`, 자동 통계 수집 잡 |

확인할 질문
- **Join reorder / join distribution 결정 로직** 차이 (탐색 공간, 컷오프, 힌트)
- Predicate/Aggregation/Limit/TopN **푸시다운 범위**
- 서브쿼리 언네스팅, CTE 재사용, 윈도우 함수 최적화
- **머티리얼라이즈드 뷰 쿼리 재작성** — StarRocks 고유 (`rule/transformation/materialization/*`), Trino는 MV 지원이 커넥터(Iceberg/Hive) 한정. 이 항목은 기능 격차가 가장 큰 부분 중 하나
- 통계 수집 주체: Trino는 커넥터가 제공 vs StarRocks는 엔진이 직접 수집·관리

### A-3. 실행 엔진
| 항목 | Trino | StarRocks |
|---|---|---|
| 데이터 표현 | `Page` / `Block` (Java 컬럼너) | `Chunk` / `Column` (`be/src/column/*`, C++) |
| 실행 모델 | Driver/Operator 파이프라인, 스레드당 split | Pipeline 엔진 (`be/src/exec/pipeline/*`), 논블로킹 스케줄러 |
| 연산자 | `io.trino.operator.*` | `be/src/exec/*` (aggregator, join, sort, scan) |
| 벡터화 | JIT 의존, 부분적 | C++ SIMD 명시적 벡터화 |
| 표현식 평가 | 바이트코드 컴파일(`sql/gen/*`) | `be/src/exprs/*` + JIT(LLVM) 일부 |

확인할 질문
- 연산자별 알고리즘 차이(해시 조인 빌드 전략, 집계 spill 조건, 정렬 구현)
- **런타임 필터**: Trino Dynamic Filtering vs StarRocks Runtime Filter — 생성/전파/적용 시점 비교
- StarRocks의 **저카디널리티 문자열 전역 딕셔너리 최적화** (Trino 대응물 부재)
- 스레드/스케줄링 모델: Trino의 협력적 멀티태스킹 vs StarRocks 파이프라인 폴러

### A-4. 데이터 교환 / 셔플
- Trino: `execution/scheduler/*`, `operator/ExchangeClient`, HTTP 기반 / FTE의 `exchange manager`(스풀링)
- StarRocks: `be/src/runtime/data_stream_sender|receiver`, BRPC 기반
- 확인: 직렬화 포맷, 백프레셔, 셔플 파티셔닝 전략, 대용량 셔플 시 디스크 스풀 여부

### A-5. 커넥터 / 페더레이션
| | Trino | StarRocks |
|---|---|---|
| 인터페이스 | `trino-spi` `ConnectorMetadata` / `ConnectorSplitManager` / `ConnectorPageSource` | FE `com.starrocks.connector.*` + BE `be/src/connector/*` |
| 구현 수 | 50+ (`plugin/trino-*`) | Hive/Iceberg/Hudi/Delta/Paimon/JDBC/Elasticsearch 등 |
| 파일 리더 | Java (Parquet/ORC 자체 구현) | C++ (`be/src/formats/parquet|orc`) |

확인할 질문
- 커넥터 **푸시다운 능력 비교**(필터/집계/조인/LIMIT/샘플링)
- 쓰기 지원 범위(INSERT/CTAS/MERGE/DELETE/UPDATE), Iceberg·Delta 트랜잭션 지원 수준
- 커넥터 추가 난이도: SPI 안정성 vs FE/BE 양쪽 수정 필요 여부 — **확장성 관점의 핵심 차이**

## 2. 비교 항목 (우선순위 B: 운영·성능 영향)

### B-1. 메모리 관리 & Spill
- Trino: `io.trino.memory.*` (MemoryPool, ClusterMemoryManager), 쿼리별 한도, spill-to-disk
- StarRocks: `be/src/runtime/mem_tracker` 계층, 연산자 spill, FE 측 쿼리 큐
- 확인: OOM 시 동작(쿼리 kill 정책), 한도 계층 구조, spill 대상 연산자 범위

### B-2. 리소스 격리 / 멀티테넌시
- Trino: Resource Groups(큐잉·동시성 제한 중심), 하드 CPU 격리 없음
- StarRocks: Resource Group (BE에서 CPU/메모리 실격리), 쿼리 큐, 대분류/소분류 라우팅
- 확인: 격리 강도(스케줄러 수준 vs cgroup 수준), 워크로드 분리 실효성

### B-3. 캐시
- Trino: 결과 캐시 없음, 메타스토어 캐시 / 파일시스템 캐시(Alluxio 등)
- StarRocks: **Data Cache**(외부 테이블 블록 캐시), **Query Cache**(부분 결과 재사용), MV
- 확인: 캐시 무효화 정책, 캐시 계층 위치, 반복 쿼리 이득 크기

### B-4. 고가용성 / 장애 복구
- Trino: 코디네이터 SPOF(HA는 게이트웨이로 보완), **Fault-Tolerant Execution**(task/query retry + 스풀링 익스체인지)
- StarRocks: FE Leader/Follower/Observer 복제, 태블릿 다중 복제, 쿼리 재시도는 제한적
- 확인: 장수 쿼리(ETL) 실패 복구 전략의 근본적 차이 — Trino FTE vs StarRocks 재실행

### B-5. 보안
- Trino: Access Control SPI, Ranger/OPA 플러그인, 인증(OAuth2/Kerberos/JWT/mTLS), 컬럼 마스킹·행 필터
- StarRocks: 내장 RBAC(3.0+), LDAP/OAuth, Ranger 연동
- 확인: 권한 모델 표현력(카탈로그/스키마/테이블/컬럼 단위), 외부 정책 엔진 통합 방식

### B-6. 관측성
- Trino: `EventListener` SPI, JMX, Query JSON, Web UI
- StarRocks: FE Audit Log 플러그인, **Query Profile**(연산자별 상세 지표), Prometheus 메트릭
- 확인: 프로파일 상세도와 튜닝 실용성 — 실제 튜닝 워크플로우 차이로 직결

## 3. 비교 항목 (우선순위 C: 한쪽에만 존재)

### C-1. StarRocks 전용 — 스토리지 계층
- 테이블 모델: Duplicate / Aggregate / Unique / **Primary Key** (`fe/.../catalog`, `be/src/storage/*`)
- 파일 포맷: Segment, Rowset, Tablet, 파티션/버킷, Colocate Join
- 인덱스: Prefix index, ZoneMap, Bloom filter, Bitmap, N-gram
- Compaction (`be/src/storage/compaction*`)
- **Shared-data 모드**(스토리지-컴퓨트 분리, `be/src/storage/lake/*`) vs Shared-nothing
- 적재/트랜잭션: Stream/Broker/Routine Load, Transaction Manager, publish version, MVCC
- → Trino에는 대응물이 없음. "Trino는 이 계층을 커넥터+오브젝트 스토리지에 위임" 형태로 기술

### C-2. Trino 전용 — 플러그인 생태계
- Plugin SPI 전반(커넥터/함수/타입/이벤트리스너/접근제어/리소스그룹)
- 커넥터 다양성 자체가 기능(RDBMS, NoSQL, Kafka, Elasticsearch, Kudu, ...)
- Trino Gateway(별도 저장소)
- → StarRocks는 외부 카탈로그가 데이터레이크 중심으로 한정

## 4. 비교 항목 (우선순위 D: 코드베이스 자체)

- 빌드: Trino Maven 멀티모듈 단일 / StarRocks Maven(FE) + CMake·thirdparty(BE) 이중 빌드
- 테스트: Trino 단위 + Product Test(Testcontainers) / StarRocks FE 단위 + BE gtest + SQL regression 프레임워크
- 코드 규모·모듈 수, 커밋 활동, 릴리스 주기
- 확장/기여 난이도 (SPI 안정성 vs 내부 구조 직접 수정)

## 5. 진행 방식 제안

각 비교 축마다 다음 형식으로 `docs/` 에 문서 1건을 생성한다.

```
1. 비교 관점 요약 (한 문단)
2. Trino 구현  — 핵심 클래스/파일 + 경로:라인 인용 + 설계 요약
3. StarRocks 구현 — 동일 형식
4. 설계 차이와 그 원인
5. 성능/운영 관점의 영향
6. 결론 (동등 / Trino 우위 / StarRocks 우위 / 비교 불가)
```

**권장 착수 순서**: A-2 옵티마이저 → A-3 실행 엔진 → A-5 커넥터 → B-2 리소스 격리 → C-1 스토리지.
옵티마이저와 실행 엔진에서 두 엔진의 설계 철학 차이가 가장 선명하게 드러나고, 나머지 축의 해석 기준이 된다.

**분석 원칙**
- 두 트리 모두 규모가 커서 전수 읽기는 불가능하다. 반드시 축을 먼저 고정하고 검색 기반으로 접근한다.
- 모든 주장에는 `works/<engine>/경로:라인` 인용을 붙여 검증 가능하게 한다.
- 비교 기준 버전(태그/커밋 해시)을 문서 상단에 명시한다. 두 프로젝트 모두 변화 속도가 빨라 버전 없는 비교는 수명이 짧다.
